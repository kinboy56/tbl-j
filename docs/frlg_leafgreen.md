# リーフグリーンと 2 本のカートリッジのオフセットマップ

このセクションの残りは、フランス語版 FireRed (BPRF、バージョン 0x0A) から読み取りました。フランス語版 LeafGreen は
BPGF、0x0A (ヘッダーに `POKEMON LEAF` とあります)。すべてのペイロードはそのまま動きますが、ROM のアドレスは一致しません。
計測はふしぎなおくりもののメニュー内で行うため、本体はセーブポイントから離れません。

## 計測したアドレス

| シンボル | LeafGreen | FireRed |
|---|---|---|
| `gDecompressionBuffer` | 0x0201C000 | 同じ |
| ふしぎなおくりもの呼び出し箇所 | 0x08148C50 | 0x08148C74 |
| `Random` | 0x080486B0 | 同じ |
| `SeedRng` | 0x080486D0 | 同じ |
| `gRngValue` | 0x03004220 | 同じ |
| `gPlayerParty` | 0x02024280 | 同じ |
| `gPlayerPartyCount` | 0x02024025 | 同じ |
| `gEnemyParty` | 0x02024028 | 同じ |
| `gSpeciesInfo` | 0x0824CDD8 | 0x0824CDFC |
| `CreateMon` | 0x08041150 | 同じ |
| `sEasyChatGroups` | 0x083E353C | 0x083E3700 |
| `gSpecialVar_0x8000` | 0x020370B4 | 同じ |
| `gSpecialVars` | 0x08163984 | 0x081639A8 |
| `gSaveBlock1Ptr` | 0x03004228 | 同じ |
| `gSaveBlock2Ptr` | 0x0300422C | 同じ |

`rom_map.LEAFGREEN` はこれらを根拠とともに保持します。`rom_map.leafgreen(symbol)` は表にないシンボルに対して
FireRed の値へフォールバックせず、例外を送出します。

計測したすべての IWRAM と EWRAM のアドレスは同一です (同じコードのリンク時グローバル変数のため)。0x080486C8 より上のすべての ROM
アドレスは異なります。15 個のシンボルがこれを確認しています。新しい ROM シンボルは予測ではなく計測します。

## 領域ごとのデルタ

FireRed のアドレスから LeafGreen の対応アドレスへのオフセットは、少なくとも 8 つの
区間にわたって区分的に一定ですが、単調ではありません (下位の 4 区間は、それぞれ直下の区間より 4 バイト小さい値だけずれています):

    +0x0   -0x2C   -0x28   -0x24   -0x20   -0x1C4   -0x124C   -0x1240   -0x12D8

`rom_map.leafgreen_guess(firered_address)` は計測済みの区間の内側で答えを返し、隙間では答えを拒みます。これは
ダンプの狙いを定めるためのもので、内容については何も示しません。`pokeldn/frlg/rom/leafgreen_twins.py` には 738 組のペアが
あり、それぞれ対応するカートリッジから読み取ったものです (約 200 件は名前付き関数です)。`leafgreen_twins.leafgreen(address)` は
ペアがある場所では正確に答え、ない場合は `leafgreen_guess` にフォールバックします。

### 境界

    step             span                          what is in it
    0     -> -0x2c   644 B, 0x0807CF68..0x0807D1EC  title_screen.o
    -0x2c -> -0x28    62 B, 0x080DE2E4..0x080DE322  mystery_event_script.o
    -0x28 -> -0x24    90 B, 0x081480CE..0x08148128  mystery_gift.o
    -0x24 -> -0x20    31 B, 0x08251D8E..0x08251DAD  pokemon.o rodata
    -0x20 -> -0x1c4 1209 B, 0x083B7B47..0x083B8000  title_screen.o rodata
    -0x1c4 -> -0x124c  30 KB, 0x0843AFFF..0x08442800  graphics
    -0x124c -> -0x1240 17 KB, 0x08442BFF..0x08447000  graphics
    -0x1240 -> -0x12d8 63 KB, 0x0844F3FF..0x0845F000  graphics

境界とは、版によって差が出る領域そのものであり、ここではどのデルタも当てはまりません。区間は、古いデルタに一致する最後の
ウィンドウから、新しいデルタに一致する最初のウィンドウまでです。`rom_map.LEAFGREEN_DELTA_BOUNDARIES` にこれらが保持され、
テストが境界テーブルと区間テーブルの一致を確認します。0x0843C800 より上では、カートリッジ同士でバイト列が異なるため (版固有のグラフィック)、
そこでのデルタは内容からは定義できません。

## 計測方法

### 対応する定数

両方のカートリッジで `RAND_MULT` をスキャンしたところ、それぞれ 11 件のヒットがあり、1.3 MB にわたって順番どおりに対応しました。

### needle としてのポインタ

両方の本体で計測したアドレスへの参照はすべて、対応点になります。各カートリッジで
それぞれ自身の `gSpeciesInfo` をスキャンすると、どちらも昇順に 56 件のリテラルプール参照が見つかり、1 対 1 で対応しました:

| デルタ | FireRed の範囲 | 対応ヒット数 |
|---|---|---|
| 0 | 0x080001BC .. 0x0805359C | 42 |
| −0x2C | 0x080CBFB0 .. 0x080CE36C | 2 |
| −0x28 | 0x080EBA14 .. 0x0813E8CC | 9 |
| −0x24 | 0x0815A3F4 .. 0x0815A630 | 3 |

0x0815A630 より上にヒットはありません。

### シンボルのない箇所で needle を作る

0x083E3700 より上には名前がありません。片方の本体から 1 KB をダンプし、その中に 1 回だけ現れる、4 種類の異なるバイトからなるワードは、ある箇所の指紋になります。それを
もう片方の本体でスキャンすると、そこでのその箇所のアドレスが得られます。2 回の実行で 1 点が定まります (ROM のどこでも可):

| FireRed | LeafGreen | needle | デルタ |
|---|---|---|---|
| 0x086003E0 | 0x085FF108 | 0xE1926F4D | −0x12D8 |
| 0x086803FC | 0x0867F124 | 0xC35D61AE | −0x12D8 |

各スキャンは 2 MB のウィンドウ内で 1 件の一致を返しました。一致する 2 点では、その間の範囲が制約されないため、
対照点が必要です。スクリプト層のスキャンは次のとおりです:

| needle | 取得元 | LeafGreen での発見位置 | デルタ |
|---|---|---|---|
| 0x49050B80 | `ScrCmd_special` の内部 | 0x0806D7F4 | 0 |
| 0x4831D940 | ハンドラブロックの先頭 | 0x080701C0 | 0 |
| 0x49040A00 | フラグ・変数ワーカーの内部 | 0x08071E1C | 0 |
| 0x47708008 | `FlagGet` の手前 | 0x08071FC4 | 0 |
| 0x18210094 | `AddBagItem` の内部 | 0x0809DA80、FireRed では 0x0809DAAC | −0x2C |

デルタ 0 は、誤った本体をスキャンした場合にも返る値です。そのため、境界より上から取った最後の行は、
ずれた値で返ってこなければなりません。

### リテラルプール: 無償で使えるポインタテーブル

関数は本体の後ろのプールに、触れるアドレスを保持します。そのため 1 KB のコードウィンドウには、
数十個のポインタが含まれます。コードの区間デルタがわかっている場合、
両方のカートリッジでウィンドウを置くのにコストはかかりません。m4a のコードは `lib_text` (−0x24 の区間) にあり、
そのプールは ROM の末尾にあるサウンドデータを指します。2 つの 1 KB ダンプからは、それぞれ 24 個のプールワードが得られ、そのうち 13 個は同一でした (RAM アドレスと定数)。
5 つのカートリッジポインタはすべて同じように動きました:

| FireRed | LeafGreen | デルタ |
|---|---|---|
| 0x0847DCF8 | 0x0847CA20 | −0x12D8 |
| 0x0847DDAC | 0x0847CAD4 | −0x12D8 |
| 0x0847DF10 | 0x0847CC38 | −0x12D8 |
| 0x0849758C (`gMPlayTable`) | 0x084962B4 | −0x12D8 |
| 0x084975BC (`gSongTable`) | 0x084962E4 | −0x12D8 |

`gMPlayTable` と `gSongTable` は、どちらの ROM でも 0x30 離れています。これは 12 バイトの `struct MusicPlayer` 4 個で、
`sound/music_player_table.inc` が保持するとおりです。

16 ブロックずつのプールペア 2 組から、550 と 288 の対応箇所が得られ、−0x20 の区間を発見しました。この区間は −0x24 と −0x1C4 の間で 1 MB 以上にわたります。
対応づけは必ずコードのオフセットで行い、インデックスでは行わないでください。552 語と 550 語のプールを順番どおりに対応づけると、
最初の不一致の後に偽のデルタ (−0x53BADA0) が生まれます。

`bl` は相対指定なので、両方のカートリッジで同じ命令は、飛び先の位置にあるデルタ分だけ異なる飛び先に解決されます。
16 KB のハンドラウィンドウには 834 個の `bl` があります。`tools/frlg/cartridge_pair.py` は、両方のカートリッジに保持されている
すべてのウィンドウからプールと `bl` を読み出します。1592 点あり、すべての箇所が対応づけられました (734 中 734、834 中 834)。
各ウィンドウには 4 つの異なるデルタがあり、外れ値はありません。

### 同じアドレスで両カートリッジをダンプする

デルタ d を持つ共通アドレスでは、LeafGreen のブロックは
FireRed のブロックを d だけずらしたものを保持します。|d| が 1 KB 未満であれば、相互相関から d を直接読み取れます。
`memory-dump-scatter` は同じ 27 個のアドレスを両方の本体に送信します。ブロック内では、どのデルタがウィンドウごとに一致し続けるかを調べることで、
バイト単位まで段を特定します。5 つのコード段の境界は合計 2036 バイトで、
272 個すべての特殊スクリプトに LeafGreen のアドレスがあります。

広い隙間には複数の段が隠れていることがあります。−0x1C4 から −0x12D8 までの 421 KB には 3 つの段があります。グラフィックは
自分自身に似ているため、各読み取り値は代替案と比較して採点します。0x08442800 では −0x124C が 436/436 の得点、
−0x1240 は 6.9%、−0x12D8 は 2.7% です。0x08457000 では 74.7% 対 57.3% で、判定なしとして記録されています。

## LeafGreen のダンプを FireRed のテーブルと照合する

ここにあるテーブルはすべて FireRed から読み取ったものです。`tools/frlg/rom_functions.py --console leafgreen` は、エントリ、本体、名前を計測済みの対応アドレスへ移します。
境界の内側に入るエントリは除外されます。
213 件のフィールド本体のうち 184 件、252 件の配置可能な特殊スクリプトのうち 33 件が戻り、
FireRed と同じ 3 つの名前のない呼び出し先が残ります。

スクリプト層は、0x0807AF04 より下では両方のカートリッジで同一です
(`rom_map.SHARED_WITH_LEAFGREEN_THROUGH`)。`gScriptCmdTable` のハンドラブロック (0x0806D7C0..0x080700B8)、
スクリプトエンジン (`ScriptContext_Stop`、`ScriptJump`、`ScriptCall`、`ScriptReturn`、`callnative` が使うネイティブポインタの
セッター)、`GetVarPointer`、`VarGet`、`FlagSet`、`FlagClear`、`FlagGet`、そして
`_call_via_r0` の veneer (中継関数) です。

## フィールドと色違いのミュウツー

[seek スタブ](frlg_rng.md) 内のすべてのリテラルは、FireRed と共有されるリンク時の IWRAM ワードです。
そのためスタブは移植されていない状態で動きます。RAM スクリプトは、バインド先となるマップオブジェクトを必要とします。
`initramscript` はマップグループ、マップ番号、オブジェクト ID を受け取り、`GetRamScript` はオブジェクト自身のスクリプトの代わりに
そのスクリプトを実行します [field_control_avatar.c:458]。セルリアンケイブ B1F はグループ 1 のマップ 74 [data/maps/map_groups.json] です。
ミュウツーはオブジェクト 3 [data/maps/CeruleanCave_B1F/map.json] です。`rng-mon-hunt-both` を、`setwildbattle` の
種族 150、レベル 70 でそこにバインドすると、ミュウツーのスクリプトが置き換わり、
狙いを定めたミュウツーとの戦闘がすぐに始まります (市販の LeafGreen で色違いであることを確認済み)。

- stray-draw 検索は LeafGreen で動作します。スタブは実行時に `gSaveBlock2Ptr` から
  `TID ^ SID` を読み取ります [asm/field/mon-seek-both.s:73]。
- バインドは電源を切っても維持されます。ただし `gSaveBlock1Ptr` は読み込みのたびに振り直されます。
- バッファースクリプトはカードを送信せず、RAM スクリプトスロットには触れません。Wonder Card のセッションは、そのスロットを取り戻します。通常のカードは
  `InitRamScript_NoObjectEvent` を通じてスロットを再バインドし、
  ミュウツー自身のスクリプトが戻ります。

バインドされている間、本体は Wonder Card を持っていないと報告します。カードは無傷のまま残ります
([RAM スクリプトスロットは一つ](frlg_gift.md#the-one-ram-script-slot))。

## ダンプした領域は動いてはならない

0x03004220 (`gRngValue`、1 フレームに 2 ターン) の `memory-dump` は、送信の途中で *erreur
de connexion* (通信エラー) を出して止まります。CRC と送信が異なるフレームで行われるためです。フレームをまたいで値が変わる領域のダンプは CRC で失敗し、
同じサイズの ROM 領域は失敗しません。仕組みと防止策は次のとおりです:
[本体上のコード](frlg_rom.md#repointing-the-consoles-outgoing-message)。

4 バイト上から始めると、セーブブロックのポインタを読み取ります。両方は一緒に動き、
`SetSaveBlocksPointers` が振る 0..124 の範囲内で、4 バイト境界に揃った 1 つの共通オフセットだけ動きます [load_save.c:75]。

## 英語版ビルド

`pret/pokefirered` は、Switch 版リリースのリビジョンである REVISION 10 で両方のカートリッジをビルドします:

    make firered_switch     -> pokefirered_switch.gba    baa452d0b24629dd7782cfc07a8984085dde1311
    make leafgreen_switch   -> pokeleafgreen_switch.gba  62b9fc77549dbc67032eb6cbd0ea6ad3b825690f

binutils と `pret/agbcc` でビルドすると、どちらも decomp の sha1 に一致します。一致しないビルドは
使用できません。ROM はコミットしません。

これは英語版リリースです。同じアドレスでは、フランス語版の本体と英語版ビルドは、バイトの 3.7% で一致します。フランス語の文字列は長さが異なるためです。
これは、同じソースとリンク順序から作られた 2 つ目のカートリッジペアとして役立ちます。
すべてのシンボルが既知です。

### オフセット: フランス語版アドレスから英語版アドレスへ

区分的に一定で、言語間でオブジェクトのサイズが変わる箇所でのみ段が生じます。コードの連続部分は数十 KB に及び、最長のものは 1.3 MB です。
2 つの独立した読み取りは、両方が当てはまる箇所ではどこでも一致します:

- テーブル: `gSpecials[i]`、`gScriptCmdTable[i]`、`gMysteryEventScriptCmdTable[i]` は、
  両方のビルドで同じ関数です。既存のダンプから 675 点が得られます。
- ダンプ: 英語版 ROM に 1 回だけ現れる 16 バイトのウィンドウは、同じフランス語版のバイトに対応します。1 KB のコードは何百回も投票し、
  ブロック内の段は 2 つの連続した一致として現れます。

      ./.venv/bin/python tools/frlg/english_build.py --offsets

### 対照

英語版 ELF (リンクマップと異なり static 関数を含みます) は、オフセットを通じてフランス語版アドレスに名前を付けます。
`worker_names` と照合したところ、本体自身から計測された名前は 232 件が一致し、0 件が
不一致でした。`GetBoxMonData2` は `__attribute__((alias("GetBoxMonData3")))` です [pokemon.c:3332]。読み取りでは、
アドレスが持つ名前をすべて保持します。

    ./.venv/bin/python tools/frlg/english_build.py --check

英語版ビルドから得た名前は推論によるものです。`rom_map.CALLABLE` は、効果を伴って実機で呼び出されたことを意味し、
`worker_names` は、本体自身が呼び出した本体をソース順で名付けたことを意味します。`pokeldn/frlg/rom/english_names.py` には、
この方法で名付けられた 7573 個のフランス語版関数アドレスが、オフセットの区間とともに保持されています (`scripts/gen_english_names.py`)。
`rom_functions` はこれらを最後に読み込み、`[english]` と印を付けます。そのため推論が、本体自身が名付けた本体を上書きすることはありません。
`gen_worker_names` は `with_english=False` を渡します。

名前のない 177 個の呼び出し先のうち、158 個は計測済みのオフセット区間の内側に入り、名前が付けられます。残りは
区間の間に落ち、`english_names.BRACKETED` に入ります。これは、隣接する 2 つのオフセットのどちらか一方で名付けられたもので、
関数の先頭に正確に一致し、もう一方は一致しない場合に限ります (`[english?]`)。2 個は残ります。さらに、それぞれ十数本の本体から到達する 3 個の呼び出し先は
`__divsi3`、`__modsi3`、`__umodsi3` と読み取られます。これらは agbcc の
除算ヘルパーです。

### 英語版ペア自身のデルタマップ

比較した 2 つの英語版 ROM は、フランス語版カートリッジが計測したものと同じ 6 つのデルタを、順番どおりに与えます:

    +0x0   -0x2c   -0x28   -0x24   -0x20   -0x1c4

各段は、版によって差が出るオブジェクト (`title_screen.o`、`mystery_event_script.o`、
`mystery_gift.o`、`pokemon.o`) の内側にあり、両方のビルドに共通のシンボルはありません。バイト比較により、各段は 79..1606 バイトの範囲に絞り込まれます。
オフセットマップによって持ち越すと、予測したフランス語版の境界 5 つすべてが、
実機で計測した範囲の内側に入ります。

    ./.venv/bin/python tools/frlg/english_build.py --boundaries

### 落とし穴

- `.gcc2_compiled.` シンボルは、そのファイルの最初の関数を覆い隠します。`.` または `$` で始まる名前は読み飛ばしてください。
- パディングはすべてのデルタに一致します。一致を有効とみなす前に、ウィンドウ内で 16 種類の異なるバイト値を要求してください。さもないと
  0xFF の埋め草が一致として読まれます。
- オフセット (フランス語版から英語版へ、1 本のカートリッジ) は、デルタ (FireRed から LeafGreen へ) とは異なります:
  `french delta = offsetFR - offsetLG + english delta`。
- 新しいダンプの後は、`scripts/gen_english_names.py` で `english_names.py` を再生成してください。

## 使えない参照

`gSongTable` (347 個の `{header, ms, me}` エントリ) は、9 KB の中に 122 個の曲ヘッダーを詰め込んでいるため、
1 か所しか確定できません。

FireRed の ROM データは、0x086ABE68 (最後の曲ヘッダー) と 0x08800000 の間で終わります。0x08800000 は
すべて `0xFF` を読み、0x08E00000 はすべて `0x00`、0x08680000 は高エントロピーのデータです。
