# コントローラー基板

コントローラー基板は、USB-C ポートで Switch が有線コントローラーとして扱う ESP32-S3 か、
Bluetooth Classic で Pro Controller としてペアリングする従来型の ESP32 です。ホストがゲーム機のボタンを押し、基板が自身のクロックで再生するマクロを読み込みます。
ファームウェア `firmware/pad`、ホスト側 `pokeldn.pad`、アプリのページ [コントローラー](gui.md#the-controller)、
コマンドライン `tools/switch/pad.py`。

## 対応する基板

| チップ | コントローラー | 理由 |
|---|---|---|
| ESP32-S3 | 有線、USB 経由 | USB-OTG ブロックにより、任意の USB デバイスとして動作できる |
| classic ESP32 | ワイヤレスの Pro Controller、Bluetooth Classic。ホストは USB-to-serial ポートに接続 | 独自の USB デバイスを持たない。Pro Controller の転送方式である Bluetooth Classic を備える |
| ESP32-C3, ESP32-C6 | なし | USB Serial/JTAG は機能が固定されており、Bluetooth は LE のみ |

## USB 側

基板は HORI Pokken controller (`0f0d:0092`) として列挙され、HID インターフェースを 1 つ持ちます。
そのインターフェースは割り込み IN と割り込み OUT のエンドポイントを持ちます。Switch は、
Pro Controller のハンドシェイクなしの素の HID ゲームパッドとして、この ID を受け付けます。ファームウェア 23.0.1 の市販 Switch Lite は、
設定を変えずに HOME メニューからこれを認識し、基板のレポートでカーソルを動かしました。

入力レポートは 8 バイトで、ホストが受け取れる状態のとき 1 ミリ秒ごとに送られます。

| オフセット | サイズ | フィールド |
|---|---|---|
| 0 | 2 | ボタン、リトルエンディアン |
| 2 | 1 | hat: 0 が上、時計回りに 7 が左上、8 が中央 |
| 3 | 4 | LX, LY, RX, RY。128 が中央、0 が左または上 |
| 7 | 1 | ベンダーバイト。ファームウェアが Bluetooth の状態をここに入れる |

| ビット | ボタン | ビット | ボタン |
|---|---|---|---|
| 0x0001 | Y | 0x0100 | Minus |
| 0x0002 | B | 0x0200 | Plus |
| 0x0004 | A | 0x0400 | 左スティック押し込み |
| 0x0008 | X | 0x0800 | 右スティック押し込み |
| 0x0010 | L | 0x1000 | HOME |
| 0x0020 | R | 0x2000 | Capture |
| 0x0040 | ZL | | |
| 0x0080 | ZR | | |

ベンダーバイトは、1 が同期済み、2 が広告中、3 が接続済みを表します。その段階が失敗したときは `0x80 | step` になります。

## ケーブル接続

基板からゲーム機へは USB-C to USB-C ケーブルで接続します。
ゲーム機は電源と USB ホストを兼ね、基板はそこから電力を得ます。
XIAO ESP32S3 の LED (GPIO21) は、ホストがデバイスを設定している間点灯します。

Mac に C-to-C ケーブルで接続した Switch Lite は、電源になるだけで、
何も列挙されません。Mac の USB-A ポート経由で "Copy to a Computer via USB Connection" を開いた状態にすると、
`057e:201d` として列挙されます。MTP インターフェース 1 つ、読み取り専用の "Album" ストレージ、
読み取り専用の操作 10 個 (`0x1001`-`0x100a`) を持ちます。

## Bluetooth 側

基板は、サービス `7a1e0001-5d2c-4c3e-9f4b-504f4b454c44` を 1 つ持つ `POKELDN-PAD` として広告します。

| キャラクタリスティック | アクセス | 内容 |
|---|---|---|
| `...0002` | 書き込み、応答なし書き込み | 8 バイトの入力レポートをそのまま送る。マクロの再生中は無視される |
| `...0003` | 読み取り | ステータス (後述) |
| `...0004` | 書き込み | コマンド (後述) |

ステータスはリトルエンディアンで、mounted u8、レポート書き込み回数 u32、playing u8、ループ完了回数 u32、
エントリ番号 u16、エントリ数 u16、ファームウェアのバージョン文字列、NUL、リセット理由 u8 (`esp_reset_reason`)、
前回の起動が到達した段階 u8、電源投入後の起動回数 u16 の順に並びます。
1.0.0 より前のファームウェアは、先頭 5 バイトだけを送ります。

| コマンド | ペイロード | 効果 |
|---|---|---|
| `0x10` load | エントリ数 u16、ループ開始位置 u16、ループ回数 u32 | マクロを停止し、プログラムのサイズを設定する。loops が 0 のときは、停止されるまで再生する |
| `0x11` data | 先頭エントリ番号 u16、続いてエントリ | 各エントリはレポートと保持時間 u16 (ミリ秒) からなり、10 バイト |
| `0x12` play | | プログラムを開始する |
| `0x13` stop | | 停止し、すべてのボタンを離す |
| `0xB0` download | | チップを ROM ローダーに再起動する |

プログラムは 8192 エントリを保持できます。ループ開始より前のエントリは 1 回だけ再生され、残りは繰り返されます。再生側は
1 kHz のティックで `vTaskDelayUntil` を使って待つため、保持時間は積み上がってもずれません。Mac の USB 側では、
10 ループのマクロが毎ループちょうど 500 ms で再生されました。

macOS で bleak を使うと、CoreBluetooth のキューがいっぱいのとき応答なし書き込みは失われます。
bleak は `canSendWriteWithoutResponse` を読まないため、ニュートラルのレポート 300 件を連続で送ると、
基板の書き込みカウンターに届いたのは 67 回でした。20 ms 以上の間隔では、40 件中 40 件が届きました。
`pokeldn.pad.link` は、レポートを書き込む前にこのフラグを待ち、
フラグが存在しない場合、または 1 秒間 false のままの場合は、応答ありで書き込みます。

| レポート書き込み | レポート 1 件あたり (連続送信) | 基板に届いた数 |
|---|---|---|
| 応答なし、間隔調整なし | 0.1 ms | 300 件中 67 件 |
| 応答あり | 60 ms、接続後最初の 25 秒間は一定 | 300 件中 300 件 |
| 応答なし、フラグで間隔調整 | 2.4 ms | 200 件中 200 件 |

ファームウェア 1.2.0 は、接続時に 15 から 30 ms の接続間隔を要求します。応答ありでも書き込みには 63 ms かかり、
macOS がこの要求を受け入れたかどうかは不明です。

切断するとレポートはニュートラルに戻るため、ホストが消えてもボタンが押しっぱなしになることはありません。
再生中のマクロは続きます。

## シリアル側

従来型 ESP32 はコンピューターの USB に接続したままです。UART0 は 921600 baud で両方向にフレームを送受信し
(`firmware/pad/main/uart_link.c`、`pokeldn/pad/serial_link.py`)、コンソール出力は無効になっています。
コンソールが無効だと UART0 を GPIO1 と GPIO3 に接続する経路がないため、
ファームウェアがピンを自分で設定します。これがないと基板は応答しません。

    A5 5A | length u16 (type and payload) | type u8 | payload | sum of type and payload mod 256

| 種別 | 方向 | ペイロード |
|---|---|---|
| `0x01` | 基板へ | 8 バイトのレポート。`0x81` で応答される |
| `0x02` | 基板へ | なし。`0x82` でステータスレコードが返される |
| `0x03` | 基板へ | コマンド (制御キャラクタリスティックと同じ)。`0x81` で応答される |
| `0x81` | ホストへ | 結果 i8: 0、-1 は長さ不正、-2 は拒否 |
| `0x82` | ホストへ | ステータスレコード。mounted は、Switch がプレイヤーランプを設定したことを意味する |

ホストは DTR と RTS を Low にした状態でポートを開きます。DevKit の CP2102 は、macOS でポートを開くと依然として基板を再起動させ、
起動中に送られた要求は失われるため、ホストは最大 3 秒間ステータス要求を繰り返します。
サービスは Bluetooth LE をスキャンする前に、S3 のネイティブ USB 以外の各 USB シリアルポートを試します。
ポートは 1 つのプロセスで保持してください。ポートを開くたびに基板が再起動し、
Bluetooth 接続が切れます。

## Bluetooth Classic 側

`firmware/pad/main/bt_esp32.c` は Bluedroid の HID デバイスを登録します。内容は、170 バイトの Pro Controller レポートディスクリプタ、
サービス "Wireless Gamepad"、プロバイダー "Nintendo"、サブクラス 0x08、Class of Device 0x002508、名前 "Pro Controller"、
入出力なしの SSP、モデムスリープ無効です。0x01 サブコマンドには ID ごとに応答します。0x02 デバイス情報 (ファームウェア 4.00、種別 0x03、
Bluetooth アドレス)、0x10 SPI 読み取り、0x03 レポートモード、0x04 トリガー時間、0x21 MCU 設定に応答し、
残りには単純な ACK を返します。0x30 (プレイヤーランプ) を受けると、コントローラーを使用中として記録します。
応答は、どの 0x30 よりも先に送られます。

0x30 レポートは、ボタンやスティックが変化したときはすぐに送られ、それ以外のときは接続が開いた時点から 100 ms ごとに送られます。
基板が何も送らないままだと、接続した Switch Lite はハンドシェイクを始めませんでした。
接続が開いた後、基板は 1 秒待ちます。スニフモードへの切り替え後は 250 ms、
混雑で送信が拒否された後 (理由 8) は 45 ms 待ちます。これらは friendmaker の Switch Lite の値です
(`classic_bt_controller_transport.cpp`、`SWITCH_LITE`)。

| 0x30 の送信間隔 | 市販の Switch Lite |
|---|---|
| 0x03 のモード切り替え後は 15 ms ごと | プレイヤーランプまでハンドシェイクが進みます。その後 Bluedroid がスニフモードを切り替え、送信が混雑で失敗し、ランプ点灯の 2 から 20 秒後に Switch が切断します (HCI 0x13)。入力は画面に反映されませんでした |
| 変化時、それ以外は 100 ms ごと。上記の待ち時間を適用 | 接続は維持され、501 回の送信で失敗は 0 回。ボタン入力により、Change Grip/Order と Controllers メニューでカーソルが動きました |

Switch のハンドシェイクは、この順に行われます。0x02、0x08、アドレス 0x6000 と 0x6050 の 0x10、0x03 (0x30)、0x04、
アドレス 0x6080、0x6098、0x8010、0x603D、0x6020、0x40 の 0x10、0x30 (0)、0x48、0x21、0x30 (プレイヤー 1)。

ペアリング済みの基板は、起動時に Switch へ再接続します。統合イメージを書き込むと NVS パーティションが上書きされ、ペアリング情報も失われます。
Change Grip/Order から再度ペアリングしてください。

`pro_report.c` は共有レポートを Pro Controller のバイト列に対応付けます (dekuNukem `bluetooth_hid_notes.md`)。
スティックは静止時に 0x800、どちらの向きにも 0x700 を取り、0x603D で返す工場出荷時のキャリブレーションに合わせています。
シリアル番号とユーザーキャリブレーションには、未書き込みのフラッシュ (0xFF) を使います。
`tests/test_pad_pro.py` はこれをホスト上でコンパイルし、すべてのボタンビットとキャリブレーションを確認します。

## マクロ

マクロは、拡張子 `.pokemacro` を持つ JSON ファイルです (`pokeldn.pad.macro`)。

```json
{
  "format": "pokeldn-macro", "version": 1,
  "name": "Soft reset", "description": "", "author": "", "game": "",
  "press_ms": 100, "gap_ms": 150,
  "setup": [{"press": "HOME"}, {"wait": 1000}],
  "loop": [
    {"press": ["A", "B"], "ms": 500, "after": 2000, "note": "skip the intro"},
    {"repeat": 3, "steps": [{"press": "A"}]},
    {"press": [], "left": [0, 1], "ms": 300},
    {"wait": 5000}
  ],
  "loops": 0
}
```

| フィールド | 意味 |
|---|---|
| `press_ms`, `gap_ms` | ステップが指定しないときに使われる、そのステップが入力を保持する時間と、その後の休止時間 |
| `setup` | 一度だけ実行されるステップ |
| `loop` | `loops` 回繰り返されるステップ。0 の場合は停止されるまで繰り返す |
| 押下ステップ | `press`: ボタン名、または同時に保持するボタン名のリスト (`A B X Y L R ZL ZR PLUS MINUS LSTICK RSTICK HOME CAPTURE UP DOWN LEFT RIGHT UPLEFT UPRIGHT DOWNLEFT DOWNRIGHT`)。`left` と `right`: スティックの `[x, y]` (-1 から 1、上が正)。`ms`: 保持時間。`after`: 休止。`note`: メモ |
| 待機ステップ | `wait`: すべてのボタンを離した状態で待つ時間 (ms) |
| 繰り返しステップ | `repeat`: `steps` を 1 から 10000 回繰り返す。最大 8 段までネストできる |

コンパイラーは繰り返しを展開し、同じレポートを保持する隣接エントリを結合し、65535 ms を超える保持は分割します。
展開後に 8192 エントリを超えるマクロは拒否されます。同じ 2 回の押下の間にある `after: 0` は、それらを 1 回の保持にまとめます。
`version` がリーダーより新しいファイルは拒否されます。

## ホスト側

`pokeldn.pad.service` は Bluetooth 接続を保持し、`127.0.0.1:47800` で 1 行に 1 つの JSON リクエストを受け付けます。
受け付けるのは `status`、`connect`、`send`、`tap`、`play`、`stop`、`download`、`scan`、
`disconnect` です。アプリはこれを自身の子プロセスとして起動します。`tools/switch/pad.py` は、
動作中のサービスがなければ自身のプロセスで起動します。

macOS では、接続中に基板の電源が切れると (Switch から外れたとき)、CoreBluetooth が読み取りまたは書き込みを、
エラーなしで保留したままにすることがあります。
サービスは、すべてのリクエストに制限時間内で応答します (`status` は 5 秒、`play` は 120 秒、`scan` は 20 秒、
その他は接続も含めて 40 秒)。
制限時間を過ぎると、サービスは基板が再び広告するように接続を閉じ、エラーを返します。アプリのクライアントは 150 秒後に待機をやめます。

    ./.venv/bin/python tools/switch/pad.py A
    ./.venv/bin/python tools/switch/pad.py HOME wait:1 'RIGHT*3' A
    ./.venv/bin/python tools/switch/pad.py hold:B:2 stick:L:-1:0:0.5
    ./.venv/bin/python tools/switch/pad.py --play soft_reset.pokemacro
    ./.venv/bin/python tools/switch/pad.py --stop --status

macOS は、責任アプリが `NSBluetoothAlwaysUsageDescription` を宣言していないと、Bluetooth を開くプロセスを中止します。
これは、別のアプリに組み込まれたターミナルの下で起きます。
`pad.py --make-app PATH` は、サービスを実行する小さなアプリを書き出します。
一度 `open` して Bluetooth の使用を許可すると、以降の `pad.py` の呼び出しとソースチェックアウトのアプリがそれを使います。

## 再書き込み

pad が USB ポートを占有しているため、esptool はローダーへリセットできません。ダウンロードコマンド、
Board ページのインストール、`pad.py --download` は Bluetooth 経由で行います。
基板を接続しながら BOOT を押すと、ファームウェアなしで行えます。

- `RTC_CNTL_USB_CONF` は、リセット後も保持されます。USB-OTG のままにすると、ローダーは OTG CDC デバイス
  `303a:0009` として起動し、esptool が接続できるのは約半分の確率でした。
  ファームウェアは、リセットの前に NimBLE と TinyUSB を停止し、PHY を USB Serial/JTAG に戻して
  `RTC_CNTL_FORCE_DOWNLOAD_BOOT` を設定します。その後、ローダーは毎回 `303a:1001` になります。
- Bluetooth と USB を有効にした状態の `esp_restart()` は、一度ハングしました。列挙され、LED は点灯しましたが、レポートは出ませんでした。
- macOS では、新しいローダーのポートを初めて開いても何も読めず、esptool はそのプロセスの間ポートをロックし続けます。
  `gui/board.py` は、コントローラーのファームウェアを書き込むときに、リセットせずに接続する前に 8 秒待ちます。
  無線側が動作中の基板では、リセットに切り替えます。
- 強制ローダーからの書き込み後は、USB 経由のリセットではローダーに留まります。ウォッチドッグリセットでイメージが起動します
  (`--after watchdog-reset`)。

無線側からコントローラー基板へ、またその逆へ、どちらの方向も、
`python -m gui.board --kind pad|radio` で書き込みました。`--from-loader` は、
ダウンロードコマンドによりすでにローダーに入れた基板に書き込みます。待機し、リセットせずに接続して、
ウォッチドッグでイメージを起動します。コントローラーのファームウェアの場合と同様です。

注意点: FreeRTOS の既定の 100 Hz では、USB ループの遅延が 0 ティックになり、NimBLE の実行時間が不足します。
ファームウェアは 1000 Hz でビルドします。

## ビルド

    . scratchpad/esp/env.sh
    cd firmware/pad && idf.py -B BUILD_DIR -D SDKCONFIG=SDKCONFIG_PATH build

TinyUSB は、コンポーネントマネージャー (`espressif/esp_tinyusb` 2.4.0) から取得します。リリースビルドでは、無線側のイメージと並べて
`pokeldn-pad-s3.bin` を作成します。
