# Pia レイヤー

Pia は Nintendo の P2P セッション用ミドルウェアで、確認したすべてのタイトルで UDP ポート 12345 を使います。すべてのデータグラムはマジック `32 AB 98 64` で始まります。Pia のバージョンによってヘッダの構造が決まります:

| | ファイアレッド・リーフグリーン (GBA アプリ) | ブリリアントダイヤモンド・シャイニングパール | ソード・シールド |
|---|---|---|---|
| Pia バージョンバイト | 15/16 (6.32+) | 9 (5.27-5.45) | 4 |
| ヘッダサイズ | 0x1D | 0x20 | 0x20 |
| 変数 ID | 各 2 バイト | 各 4 バイト | 1 バイト + ハーフワード |
| 通信上の GCM タグ | | 16 バイトから切り詰めた 8 バイト | 16 バイトすべて |
| モジュール | `pokeldn/ldn/pia_connect.py` | `pokeldn/ldn/pia5.py` (キャプチャをバイト単位で再現できる) | `pokeldn/ldn/pia4.py` |

セクションで別のビルドが指定されていない限り、`0x01...` のアドレスは ソード・シールド 1.3.2 の展開済み `main` のもので (`tools/switch/nso_read.py` の配置どおり)、`main.bin 0x01...` のアドレスは BDSP 1.3.0 のものです。

## パケットヘッダ

### バージョン 9 (Pia 5.27-5.45)

`nn::pia::common::Packet::Header` より。パーサは 3 つのフィールドを `rev` でバイトスワップします。

    0x00  4  magic 0x32AB9864, big-endian
    0x04  1  0x80 (encrypted) | version (0x7F)
    0x05  4  destination variable id, big-endian   (0 = broadcast to the mesh)
    0x09  4  source variable id, big-endian
    0x0d  2  packet id, big-endian
    0x0f  1  footer size
    0x10  8  AES-GCM nonce, a monotonic counter
    0x18  8  AES-GCM tag, truncated from 16
    0x20     ciphertext: the plaintext padded to a multiple of 16

### バージョン 4

デシリアライザ `0x01774730` より。このルーチンは 0x1f バイトより多いことを要求します (`cmp w2, #0x1f; b.hi`):

    0x00  4  magic 0x32AB9864, big-endian
    0x04  1  0x80 (encrypted) | version (0x7F) = 4
    0x05  1  connection id
    0x06  2  packet id, big-endian
    0x08  8  AES-GCM nonce, a monotonic counter
    0x10  16 AES-GCM tag, not truncated
    0x20     ciphertext

2 つの小さなフィールドは宛先ステーションごとに持たれます。特定のステーションに宛てないパケットでは両方とも 0 になります。製品版ソードが送った 484 個のパケットはすべてこの形でした (`0x017beb14`, `0x017beb20`)。1 つのステーションに宛てて送る場合 (`0x017beb74`, `0x017beb78`。1 バイト目は呼び出し元から、ハーフワードはセッションオブジェクトから取られる) は次のとおりです:

- 接続 ID: 送信側のステーションの +0x78 にあるバイト。接続時に `2 + (tick mod 254)` (`0x017c6a00`) に設定される。相手側の値は接続セットアップで届き、+0x79 に保持される。受信側 (`0x017bdbd0`) は、保持している値と異なる 2 以上の ID を破棄する。0 と 1 は通す。
- パケット ID: ステーションごとのカウンタで、送信のたびに `0x0185dd00` が進める。値は 1 から 0xFFFF まで。受信側 (`0x0185dd20`) は 0 を順序なしとして通す。0 以外の ID で、そのステーションから最後に受けた値以下のものは破棄され、飛んだ分はステーションの欠落パケット数 (+0x18) に加算される。

コンソールと同様に両方へ 0 を入れて送れば、すべての経路を通ります。初期化関数 `0x017748bc` は `0x00000004_32AB9864` を 64 ビットの 1 ワードとして格納し、nonce とタグを 0 にします。検証関数 `0x017749f0`, `0x01774b60`, `0x01774d00` は `(byte & 0x7f) == 4` を確認します (BDSP では 9 で同じ)。ヘッダより下では、バージョン 4 はバージョン 9 のセッション鍵と IV を共有し、そのフレーミングに 1 フィールドを加えた形になります。

### バージョン 11: 受信側が破棄する条件 (スカーレット 4.0.0)

`0x6e9744` は、どのプロトコルも読む前にパケット全体を受理するか破棄するかを決めます。破棄されたパケットは、すべてのプロトコルから同時に失われたものとして扱われます。`st` は送信元アドレスのステーション、`V` は受信側の変数 ID、`D` はヘッダの宛先、`S` はヘッダの送信元とします:

| 項目 | 破棄されるとき |
|---|---|
| 送信元 | `st` に印が付いている (`+0x78`) か、状態 3 のとき |
| 宛先 | `D >= 2` かつ `D != V` |
| 送信元 ID | `S != 0` でステーションを指していない、`D == V` のとき、または `D` が 0 か 1 でフッタがあるとき |
| パケット ID、`D == 1` | 宛先 1 用のカウンタ (`st+0x60`, `0x6e9854`) で、`st` から最後に受けた値より新しくないとき |
| パケット ID、その他の `D` | その他のカウンタ (`st+0x48`, `0x6e98b4`) で、`st` から最後に受けた値より新しくないとき |

カウンタの確認 `0x6f3ff4` は、パケット ID 0 を通して何も格納しません。それ以外では `(int16)(id - last) >= 1` が必要なので、同じ ID での再送は破棄されます。参加中で送信元アドレスにステーションがないときは、パケット ID は一切確認されません。確認処理はフッタの ID を読みません。製品版の送信側 (`0x6b6b38`) は、宛先 1 のパケットを 1 つのカウンタ (`0x696d04`) で、1 つの変数 ID 宛てのパケットを受信者ごとのカウンタ (`0x696ce4`) で番号付けします。どちらも 0 は飛ばします。

## メッセージのフレーミング

Pia のペイロードには 1 個以上のメッセージが入ります。各メッセージは、続くヘッダフィールドを示す存在バイトで始まります。省略されたフィールドは、パケット内の直前のメッセージから引き継がれます (`0x01853050`、ビット単位)。フラグは +9、サイズは +0xA、プロトコル|ポートは +0xC、宛先は +0x10、送信元は +0x18 にあります。引き継いだサイズは 0x589 に対して境界チェックされます。走査が止まるのは `0xFF` のときだけです。`0x00` は 1 バイトの正当なヘッダで、すべてのフィールドを引き継ぐメッセージを意味します。

各バンドの読み取り処理は、直前のヘッダを先に複写し、ビットが立っているフィールドだけを読み込みます:

| ヘッダバージョン | 読み取るタイトル | 読み取り処理 | 終了判定 | 次のメッセージの開始位置 |
|---|---|---|---|---|
| 4 | ソード | `0x01852da0` | `0xFF` | 4 の倍数の位置 |
| 9 (5.27-5.45) | シャイニングパール 1.3.0 | `0x159b980`, 複写 `0x159b9ec`..`0x159ba10`, フィールド `0x159bb60` | `0x159b9d4` の `cmp w8, #0xff` | 4 の倍数の位置 (`0x15abf68`..`0x15abf70`、呼び出し元 7 か所すべて) |
| 11 (6.16-6.30) | Pokemon LEGENDS アルセウス 1.1.1 | `0x7484cc`, 複写 `0x748538`..`0x74855c`, フィールド `0x7486a8` | `0x748520` | ペイロードの終端 (`0x743f14`..`0x743f18`) |
| 11 | スカーレット 4.0.0 | `0x6ed2d0`, 複写 `0x6ed348`..`0x6ed360`, フィールド `0x6ed4b4` | `0x6ed324` | ペイロードの終端 (`0x6e9054`..`0x6e905c`) |
| 16 (6.39-7.2) | Pokemon LEGENDS Z-A | `0x256e088`, 複写 `0x256dac4`, フィールド `0x256de5c` | なし: パケットヘッダがパディングを明示している | ペイロードの終端 |

ステーションは、同じサイズのメッセージの連続を存在バイト 0x00 の後ろにまとめて送ります。スカーレットはゼロ埋めのレコードチャンク、シャイニングパールは同サイズのメッセージの後に信頼性メッセージを 1 つ、アルセウスは 2 つ目の 24 バイトのレコードをまとめます。0x00 をメッセージとして扱うと、すべての走査が `0xFF` のパディングでちょうど終わります (シャイニングパール 5,866 パケット、アルセウス 11,501 パケット、スカーレット 38,350 パケット)。0x00 で止めると、そのうち 3,444 パケットで読み残しが出て、それ以降はすべて捨てられます。`tests/test_pia_bundled.py` は各タイトルのパケットを 1 つずつ固定しています。

バージョン 3 (Let's Go 1.0.2) には存在バイトがありません。固定長 0x16 バイトのヘッダで、2 バイト目は 1 でなければなりません (`0x5ae7d0`)。走査は `0xFF` で止まります (`0x5ae790`)。

バージョン 4 では、ヘッダサイズを 18 か所でその場計算しており、常に基準の 1 に対して 5 つの条件付き加算を行います:

    tst w9, #1    -> +1       message flags
    tst w9, #2    -> +2       payload size, big-endian
    tst w9, #4    -> +4       protocol id and a 3-byte port
    tst w9, #8    -> +8       destination
    tst w9, #0x10 -> +8       the sender's station constant id

プレゼンス 0x7F では 24 バイトのヘッダになります。ビット 0x20 と 0x40 は何も加えません。バージョン 9 も同様で、そのヘッダは 16 バイトです。8 バイトの定数 ID は、送信側の MAC に対して `station_protocol.ldn_constant_id` で求められます。Local Protocol の `host_constant_id` と同じ値ですが、ここではビッグエンディアン、Local Protocol の本体ではリトルエンディアンです。

バージョン 16 (Z-A) ではフィールドが絞られています。ヘッダサイズ `0x256dfc8` は、フラグ用の 1 バイトに加えて、サイズ用の 2 バイト、ビット 0x04 (プロトコル)、0x08 (ポート)、0x10 用にそれぞれ 1 バイトです。ビット 0x10 のバイトはプロトコルとポートの間に置かれます (`0x256df54`、セッター `0x256a8e8`)。新しく初期化されたヘッダは、プロトコルに 0xFF, 0xFD を、ポートに 0 を持ちます (`0x256a8c0`)。読み取り処理はビット 0x20 から 0x80 を無視し、0x590 以上のサイズを拒否します (`0x256df04`)。ビット 0x10 は実際の通信ではまだ観測していません。`pokeldn.ldn.reliable.parse_messages` がこれを読みます。

バージョン 4 と 9 では、各メッセージは 4 の倍数になるようパディングされます (シャイニングパールは 0x00 で埋める)。このパディングは読まずに飛ばされ、パケットの末尾は `0xFF` です。`pia4.parse_packet()` が引き継ぎを解決し、`pia4.parse_messages()` は送られたとおりの各ヘッダを返します。走査が正しいのは、読み取ったバイト数と `0xFF` のパディングを合わせると、各パケットの平文全体になるときです。

### 圧縮

ペイロードは zlib ストリームの場合があり、メッセージフラグでメッセージごとに示されます。5.27-5.45 では 0x20、バージョン 4 では 0x10 です。バージョン 5 の信頼性ヘッダには独自の zlib フラグ 0x10 があり、BDSP は一部のゲームメッセージでこれを設定します (23 バイトのメッセージは、4 KB ウィンドウの 20 バイトのストリームとして送られた) ([BDSP のプロトコル](bdsp_protocol.md))。

BDSP はセッションの途中で圧縮を切り替えます。生のまま読むと、圧縮された 31 バイトのメッセージは、ペイロードが 0x6260 だと主張するヘッダとして解析されてしまいます。バージョン 4 の 2835 個のメッセージでは、`flags & 0x10` で展開可能かどうかが完全に予測できました (1 のものは 256 個でどれも有効、0 のものは 2579 個でどれも無効)。zlib ストリームの先頭 2 バイトは、ビッグエンディアンのハーフワードとして読むと 31 の倍数になります。

### フッタ

複数のコンソールに送られるパケットにはフッタが付きます。受信者ごとにビッグエンディアンのハーフワードが 1 つあり、その値は変数 ID の下位 16 ビットです。フッタの長さはヘッダの 0x0f のバイトに入ります。GCM タグはフッタを対象にしません。暗号文は `data[0x20 : len(data) - footer_size]` (`pokeldn/ldn/pia5.ciphertext()`) で、フッタを残したままにすると、ほかに症状を出さずに認証が失敗します。一部のパケットだけ認証が通らないときは、まず失敗したものをフッタのサイズごとに分けてください。

## セッション鍵

ネットワークの種類ごとにセッション鍵の実装があり、それぞれ別のクラスに分かれています:

| ネットワークの種類 | クラス | 導出 |
|---|---|---|
| LDN (ローカル無線、ユニオンルーム) | `nn::pia::local::LocalProtocol` | ゲーム鍵による AES-128-ECB。セッション値をシードにした xorshift128 から取り出した 16 バイトに対して行う |
| LAN | `nn::pia::lan::LanProtocol` | HMAC-SHA256(ゲーム鍵, 末尾バイトを増やす 32 バイトのパラメータ) の先頭 16 バイト |
| NEX (インターネット) | `nn::pia::nex::*` | マッチングサーバーから受け取るセッション鍵 |

公開された文章にある「SSID またはセッションパラメータをシードにした乱数値」は 2 つの実装を指しており、どちらのキャプチャが使われたかはクラス名で分かります。

### ゲーム鍵

    key = cryptoKeyDataSeed                     the game's own 16-byte constant
    key[1]  = (version >> 8) & 0xFF
    key[3]  = (version >> 4) & 0xFF             version = the local communication version,
    key[7]  = (version >> 1) & 0xFF                       which the advertisement carries
    key[12] = (version >> 0) & 0xFF

公開されているゲームごとの鍵は、あるゲームバージョンについてこの値になり、シードとはバイト 1, 3, 7, 12 の 4 バイトだけが異なります (`ldn_game_key()`)。ソード・シールドの鍵は 16 バイトの ASCII 定数で、1 回の `ldp` で読み込まれ、そのまま使われます。シードも、バージョンによる置き換えもありません。

### LDN セッション鍵

Pia 5.9-5.45 の場合:

    rnd = four SEAD draws, seeded with the session parameter from the advertisement (+0x0c),
          packed little-endian into 16 bytes
    session key = AES-128-ECB(game key).encrypt(rnd)

SEAD は Nintendo の標準ライブラリの乱数生成器で、状態を `s[i] = (prev ^ (prev >> 30)) *
0x6C078965 + i` でシードし、シフト量 11, 8, 19 の xorshift128 を回します (`pokeldn/ldn/sead.py`、
`pia5.ldn_session_key()`)。Pia 6.16 以降 (ファイアレッド) では、セッション鍵は SSID をゲーム鍵で AES したものです ([無線レイヤー](ldn.md#hosting-for-an-emulator))。

### AES-GCM の IV

Pia 5.27-5.45 とバージョン 4 の場合 (`ldn_nonce_crc()`、`gcm_iv()`):

    IV[0..2]  = first three bytes of crc32( network id (little-endian) || source MAC address )
    IV[3]     = source variable id & 0xFF        from the packet header
    IV[4..11] = the packet's 8-byte header nonce

送信元の MAC はパケットに含まれていないため、残りはキャプチャまたは広告から得ます。平文は `0xFF` で 16 の倍数になるようパディングされます。この既知の平文を使うと、候補の鍵を 1 つの AES ブロックで検証できます。

### メッシュへの参加

ステーションは、アップデートセッション (0x24)、接続要求 (0x14)、参加要求 (0x18) の順で参加します。各要求は、確認応答を受けるまで 500 ms ごとに再送されます。

Mesh Protocol には確認応答の型がありません (5.31-5.43 にはビルダーもありません)。メッシュメッセージを確認応答する 4 か所はすべて `MeshStationProtocol` を呼ぶので、確認応答は 0x14 上の 8 バイトの型 5 の確認応答となり、`05 00 00 00` とビッグエンディアンの確認 ID が続きます。確認 ID は、長さに関係なくメッセージ末尾の 4 バイトです (`size - 4`、借用チェック付き。4 バイト未満のときは 0)。`pokeldn/ldn/mesh_protocol.ack_for()`。ホストは参加応答を送る前に参加要求へ確認応答を返します。受信側は、届いたコピーのすべてに確認応答を返します。

### セッションからの離脱 (Pia 6)

`Session::LeaveAsync` は `LeaveSessionJob` を開始します。その最初のステップである LeaveSessionJob::LeaveMesh は、ホストでないステーション上で `LeaveMeshJob` を開始します (ホストでは `LeaveMeshWithHostMigrationJob`)。`LeaveMeshJob` の最初のステップ SendLeaveRequest は、Session の型 3 の離脱要求を送り、ホストの型 4 の応答を 500 ms 待ちます。送信は最大 4 回です。呼び出しから最初の型 3 までの間に Pia 内でタイマーは動きません。その前の遅延はゲーム側の処理です。

| | Pokemon LEGENDS アルセウス 1.1.1 | GBA アプリ (Pia 6.39) |
|---|---|---|
| `Session::LeaveAsync` | `0x72a6dc` | `0xb1060` |
| `LeaveSessionJob` の開始、最初のステップ LeaveMesh | `0x72c5a4` -> `0x72c640` | `0xb460c` -> `0xb46f0` |
| ホストでない場合の分岐から `LeaveMeshJob` の開始へ | `0x734f04` -> `0x734dd0` -> `0x73b820` | |
| SendLeaveRequest | `0x73b898` | `0xcacf4` |

ステップの名前は、ジョブが各ステップポインタの横に格納している文字列で示されます (`LeaveSessionJob::LeaveMesh` は Arceus では `0x37a2eb9`、GBA アプリでは `0x174e53` にあります)。ほかのステップは WaitLeaveMesh、WaitLeaveMeshWithHostMigration、WaitHostMigrated、MeshCleanup、DisconnectNetwork で、6.39 ではさらに WaitDisconnectNetwork、SendMonitoringData、CompleteProcess があります。

## Local Protocol (0x24)

ホストは、すべてのステーションが確認応答するまで、約 100 ms ごとにアップデートセッション (型 0x11) をブロードキャストします:

    local message header  version 1, type 0x11, size 73
    sequence id
    network id            random, not the advertisement's network id
    host variable id      the same value as the packet header's source variable id
    host constant id
    allow participating
    node 0..7             address:port and a ranking byte each
    host migration state

ノードスロットは 9 バイトのものが 8 個と、1 バイトです。Pia のメッセージヘッダはビッグエンディアンですが、これらのフィールドはリトルエンディアンで、その中のローカルアドレスはビッグエンディアンです。`pokeldn/ldn/local_protocol.py` がこれと、バージョン 4 のものを解析します。

### 確認応答

確認応答 (型 0x21) は 20 バイトで、`LocalAckMessage::Serialize` (`main.bin 0x016bc0f4`) で作られます。0 バイト目は `1`、1 バイト目は型、2 バイト目からのハーフワードはペイロードサイズ、4 バイト目から 6 バイトはゼロ、0x0C にはシーケンス ID、0x10 から 4 バイトはゼロです。コンストラクタ (`0x016bc0c8`、`mov w8, #0x14; str w8, [x0, #0x14]`) は +0x14 のハーフワードに 20 を書き、+0x16 のペイロードサイズを 0 にします。

`LocalProtocol` は 4 種類すべてに 1 つの送信経路 (`0x016af22c`) を持つので、確認応答はアップデートセッションと同じ形でフレーム化されます: プレゼンス `0x7F`、フラグ `0x11` (「宛先はビットマップ」と「バンドル不可」)、プロトコル 36、ポート 0、宛先 0。ビットマップ (`0x0159a15c`) は `1 << ステーションのインデックス` で、ブロードキャストのときは 0 です。クライアントは確認応答をネットワークのブロードキャストアドレスへ送り、パケットの `dst_var` は 0、メッセージの宛先は 0 です。再ブロードキャストが止まれば合格のサインです。

確認応答は送信元アドレスで帰属が決まります。`0x016af96c` は `0x016aec94` を呼び、`this+0x188` にある 9 個のノードスロット (ストライド 0x40) を走査して、+8 の 16 バイトのアドレスと +0x18 のポートを比較します。クライアントの変数 ID は IV に使われる (送信元変数 ID の下位バイト) ため、1 回の実行中は一定で、0 以外でなければなりません。

## Mesh Station Protocol (0x14)

ディスパッチャは、0 バイト目から 1 を引いた値で 7 エントリのテーブルを引きます (バージョン 4: `0x017c5f50`、テーブル `0x02081804`。BDSP: `0x0154e848`、テーブル `0x3e6b38f`)。エントリは、接続要求と応答、切断要求と応答、確認応答、中継接続要求と応答です。

### バージョン 9 の接続要求

順に確認されます:

| オフセット | フィールド | 失敗時の結果 |
|---|---|---|
| | サイズ 15..949 | 破棄 |
| 0x0 | メッセージ型、接続結果、プラットフォーム ID | 破棄 |
| 0x3 | 宛先の定数 ID (ビッグエンディアン u64)。コンソール自身の値と比較 | 無応答 |
| 0xB | 宛先の変数 ID (ビッグエンディアン u32)。コンソール自身の値と比較 | 無応答 |
| 0xF | プロトコル数。コンソール自身の数と比較 | 無応答 (エラー 0x11c26) |
| 0x10 | その数だけの (ID, バージョン) の組 | バージョンが低い → 結果 2、高い → 結果 3。どちらも応答する |
| | ステーションの位置情報のサイズ (ビッグエンディアン u16)、0x20..0x40 | 破棄 |
| | ステーションの位置情報 | 破棄 |

`0x0159b850` は未登録の ID に対してバージョン 0 を返すため、`(0xFF, 1)` は必ず「高すぎる」と判定されます。拒否を引き起こす `(0xFF, 1)` の組の数 N が、コンソールのプロトコル数です。

結果のバイトは、`0x0154f5e8` の内部エラーから次のように対応づけられます:

| エラー | 結果 | 意味 |
|---|---|---|
| 0x646f | 2 | 要求側のバージョンが低すぎる |
| 0x6470 | 3 | 高すぎる |
| 0xc24 | 4 | |
| 0xc25 | 1 | |
| 0x11c0f | 7 | 解析でき、すべてのバージョンが一致したが、第 2 段階で拒否された。また「この変数 ID はすでに自分のステーションの 1 つ」という意味でもある (ステーションが離脱したとき、プレイヤーが部屋に入り直したとき、新しい ID が使われたときに解除される) |
| 0x11c26 | *(なし)* | プロトコル数の不一致: 無応答 |

ID は一切確認されません。9 個の `(0xFF, 0)` の組があれば、ネゴシエーションを通ります。

ステーション位置情報のアドレスサイズのバイトは、ポートも数に含みます。InetAddress のパーサは `1 << size` を `0x00040044` と照合するので、通るのは 2, 6, 18 だけです。要求のパーサは位置情報のエラーを捨てるため、不正な位置情報は変数 ID 0 の要求として読まれ、どの変数 ID も同じ拒否を受けます。

バイナリから得たサイズ: 確認応答 8 バイト (`0x0154fa2c`)、拒否 15 バイト (`0x015501ec`)、切断応答 1 バイト (`0x0154ea60`)。

### バージョン 4 の接続要求

ハンドラ `0x017c62a0` は、同じプロトコル上の別のメッセージを読みます:

    [0]     message type            1
    [1]     a byte compared against the station's own byte at +0x79
    [2]     platform id             must be 9   (5.27-5.45 checks 4)
    [3]     0 or 1; anything higher is rejected. 1 means the request also names a target variable id
    [4]     target constant id      big-endian u64, compared against the console's own
    [0xC]   target variable id      big-endian u32, checked only when [3] is 1
    [0x10]  protocol count          compared against the console's own count at +0x78
    [0x11]  the sender's station location

オフセット 3 以降では、バージョン 9 のフィールドが 1 バイト手前にあります。プロトコルの一覧はありません。0x11 以降はステーションの位置情報で (シリアライザの 1 回の呼び出しは 0x40 バイトまで)、バージョン 9 から変わりません (デシリアライザ `0x0185ee20`、同じオフセット、アドレスサイズは 2, 6, 18)。このため [1] と [0x10] は、NAT のフラグと NAT の位置情報になります。

[3] が 1 のとき、コンソールは応答しません (96 件の要求で確認)。[3] が 0 のときは、コンソールが自分の要求で応答します。その内容は、自身の位置情報、定数 ID、アップデートセッションが参加者に与えた変数 ID、サービス用の変数 ID、NAT の 4 つ組、続いて確認 ID です。確認 ID は、メッセージサイズから 4 を引いた位置で `0x017d5750` が読むメッセージごとのカウンタです。

プラットフォームの確認 (`0x017c62e8`) が最初に実行され、不一致の場合は応答されます。応答の送信関数 `0x017c6c30` は 17 バイトを確保し、`[0] = 2`、`[1] = 結果`、`[2] = 9`、`[3] = 0` を書きます。後続の確認は無応答なので、「ハンドラに届かなかった」と「後の確認で失敗した」は区別できます。プラットフォーム 4 の場合、製品版ソードは `02 02 09 00 00 00 00 00 00 00 00 00 00 00 00 00 00` の応答を返し、結果は 2 でした。

[3] が 0 のときのハンドシェイク:

    ->   the console's connection request
    <-   the joiner's connection response, result 0, carrying the console's constant and variable ids
    ->   `05 00 00 00 <ack id>`, a type-5 ack, eight bytes
    ->   its own connection response, result 0, ~600 bytes, carrying the joiner's constant id,
         variable id and the player's name in plain ASCII, repeated until acknowledged

確認応答の中の u32 は、確認されたメッセージ末尾のカウンタです。コンソールの要求に対する型 5 の確認応答を送ると、再送が止まります (ブリッジドライバの `--ack-request` がこれを送ります)。応答ハンドラは確認応答の状態を読みません。型 5 のハンドラ (`0x017c6034`) は保留テーブル (`0x017d5770`) から ID を消すだけで、コンソールの接続ジョブ (`0x017afa70`) は、確認応答を受けるか、ステーションが状態 5 になるかのどちらかで終わります。製品版ソードは、確認応答を送らなくても、送られた応答 12 件をすべて読みました。

### 読み取られるために接続応答が満たすべき条件

型 2 と 7 はハンドラ `0x017c6e70` に届きます (エントリ `0x017c5fb4` と `0x017c60c0`、テーブル `0x02081804`。型 7 のエントリは w2 = 1 を渡します)。結果が 2 でない応答は、フィールドごとに確認され、どの失敗も無応答の破棄になります:

| ハンドラが読む項目 | 要求される条件 | 失敗時の結果 |
|---|---|---|
| `[1]` 結果のバイト | 2 は別の経路をとる | |
| `[5]` ビッグエンディアン u64 | 受信側自身の定数 ID | 破棄、`0x017c6f48` |
| `[0xD]` ビッグエンディアン u32 | 受信側自身の変数 ID | 破棄、`0x017c6f68` |
| 送信側のステーション位置情報 | 既知のステーションに解決できる | 破棄、`0x017c6f04` |
| `[0x37]` 1 バイト、結果 0 のみ | 5 未満 | 破棄、`0x017c6ff0` |
| +0x48 のステーション状態 | 4。確認応答を送った後に確認 (`0x017c71a4`) | 戻る。受理されると 5 (`0x017c7990`) |

コンソールは `0x017c7134` で応答を確認応答します。これは `[0x37]` の確認の後、状態の確認の前です。確認応答されない応答は、ID、位置情報、`[0x37]` のいずれかで失敗したものです。結果が 0 以外のとき、または `[0x37]` が 5 以上のときは、その結果 (ゲートでは 2) をステーション +0xa0 のオブジェクトの +0x79 のバイトに格納します。

そのオブジェクトは、ステーションのメッシュ用 ConnectStationJob です。ステップ `0x017afa70` は、期限内で、かつステーションが状態 5 でない間、そのバイト (`0x017afc34`) を読みます。0 は待ち続け、1 はエラー `0xc25`、2 は `+0x7c` (`response[2] - 9`) の符号によって `0x646f`、`0x6470`、`0x11c26` になり、それ以外の値は `0xc24` になります。エラーは待機中のコンテキスト (`0x01769720`) に渡され、保留中の確認 ID (`0x017d5770`) を解放し、ステーションを状態 4 から 6 に移します (`0x017afafc`)。
State 4 は、ステーション +0x48 へのポインタ (`str w9, [x8]`) を通して、次の 2 か所で書き込まれます。型 1 の要求では `ProcessConnectionRequestJob::ConnectToRequesterStation` (`0x017c8e90`、格納 `0x017c8fd8`)、型 6 のメッセージでは `::WaitInverseConnection` (`0x017c9760`、格納 `0x017c98a8`) です。どちらも要求ハンドラ `0x017c62a0` (`0x017c6aac`、`0x017c6aa4`) から呼ばれ、ハンドラは相手の ID を +0x79 に、状態 3 を、自身の ID を +0x78 に格納した後に呼び出します。状態 3 で `request[3]` が 1 でない場合、それぞれが相手に向けて ConnectStationJob を開始し (`0x017af520` または `0x017b0120`)、状態 4 を書き込み、期限を設定し、ステップ `0x017c9080` を設定します。このステップは、コンテキストがエラーを持つと終わります (`0x017c90d4`)。`request[3]` が 1 の場合は 0 を返し、何も書き込みません。

17 バイトの応答 (`RESPONSE_SIZE`。短い形の確保は `0x017c6c30` の `mov w3, #0x11`) では、`[0x37]` は末尾から 38 バイト先を指し、そこは古いバッファのバイトです。そのため読まれるかどうかは、送信側が制御できないメモリに依存します。ldn_mitm 下でエミュレートした ソード・シールド 1.3.2 は、要求の確認応答の有無にかかわらず、52 件中 3 件を受理しました。製品版ソードは 12 件すべてを受理しました。エミュレートしたシールドは、`[0x37]` に 1 を入れて 56 バイトにパディングした応答を 23 件中 23 件受理し、`[0x37]` に 5 を入れた 4 件はいずれも受理されませんでした。要求への確認応答を送らずにパディングした形を送ったところ、最初の送信で受理されました (`bin/swsh_connect.py --ip-join`)。コンソール自身の受理応答は 840 バイトで、`[0x37]` に 1 があります。`station4.build_connection_response(..., min_size=ACCEPTED_RESPONSE_SIZE)` は 0x38 までパディングして 1 を書きます。この層での受理は、その上のゲームを開始させるわけではありません。ソードとシールドは、0x37 より後のフィールドを待ちます ([ゲーム層に到達する](swsh_session.md#reaching-the-game-layer))。

応答の後について: コンソールの接続応答は受理を意味します。コンソールの要求が同じ末尾カウンタのまま 500 ms ごとに再送される場合は拒否です (参加者自身の ID を運ぶ応答には、20 回の再送の後、無応答が続いた)。無応答だけでは、どちらとも言えません。コンソールの ID を含む応答で返答された要求が確認応答されなかった場合、44 秒の間、再送はありませんでした。

コンソールの要求の [1] にある NAT フラグのバイトは、接続ごとに変わり、参加者が制御するどのバイトにも従いません (それぞれの読み方を 26 回の接続で試して確認)。何がこれを書き込むかは不明です。そのレコードは、ステーション位置情報のパーサ `0x0185ee20` が埋めます。

## Mesh Protocol (0x18)

`MeshProtocol::vfunc9` (受信スロット) は、0 バイト目から 1 を引いた値を、0x80 を上限としてテーブル経由で引きます (バージョン 4: ディスパッチャ `0x017c0c80`、テーブル `0x02081564`)。129 エントリのうち 19 個が有効です。バージョン 4 のものは、BDSP のものから 0x22 DUMMY_MESSAGE と 0x23 DUMMY_ACK を除いたものです。

参加要求は 6 バイトです。型 1、ステーションのインデックス 253 (「まだメッシュに入っていない」)、確認 ID。バージョン 4 のハンドラ (`0x017c1700`) は [1] を 0xFD と照合し、`0x017d5770` で確認 ID を取り、0x14 上で確認応答します (`0x017c6dd0`)。Pia はこれを約 10 秒間再送します。

参加応答のヘッダは、両方のバンドで 16 バイトです。バージョン 4 のパーサ `0x017b4830` は、まず拒否の形を読みます (`[1] == 0`、`[2] == 0xFF`、`[3] == 0xFF`、理由は [4])。次に、[1] のステーション数を最大値と比較し、[8] [9] [0xA] をビッグエンディアンの 24 ビット値として読み、0xC からはビッグエンディアンの更新カウンタを読みます。

ステーションのエントリ: 5.31-5.45 では 68 バイトを使います (64 バイトのステーション位置情報、ステーションのインデックス、ビッグエンディアンのハーフワードの参加順)。バージョン 4 では 64 バイトで、インデックスは 0x3E にあり、参加順はありません (カーソルは `0x10 + 0x3E` から始まり、`ldrb w8, [x20], #0x40` で進みます。`0x810 = 0x10 + 32 * 0x40` を超える応答は、`0x017bfa34` の 32 ステーション上限で拒否されます)。2 つの長さがこれを裏づけます:

    join response   148 B  =  0x10 + 2 * 0x40 + 4        68-byte entries would give 156
    update mesh     524 B  =  12   + 8 * 0x40            BDSP's eight 68-byte seats give 556

バージョン 4 は、経路ごとに異なるフィールドからエントリ数を取ります。分割されていない場合 (`fragments == 1`、`0x017b48f4`) は、基点 0 から `stations` 個のエントリを走査し、[6] と [7] は一度も読みません。分割されている場合 (`0x017b4b6c`、最大 3 個の断片) は、[6] 個のエントリを走査して [7] のスロットに入れ、[1]-[4] を最初の断片と照合します。5.31-5.45 は両方で [6] を使うため、[6] が 0 の 1 断片の応答は、そこでは空のメッシュとして読まれます。`parse_join_response(version4=True)` は両方の経路に従います。

UPDATE_MESH (0x20) は、およそ 1 秒に 1 回送られ、メッシュに参加しているステーションの一覧をホストが送るものです。BDSP では常に 556 バイトすべてを送り、未使用の席はゼロにされるので、`entries` のバイトを走査します (`mesh_protocol.parse_update_mesh()`)。5.31-5.45 の参加順は、メッシュが作られてからの参加数を数えます。1 台のマシンから 3 回続けて接続したところ、ホストは 0、インデックス 1 のクライアントは 3 を読みました。

### ホスト移行

次のホストに指名されたステーションは応答しなければなりません。0x18 のポート 1 上のメッシュメッセージは、信頼性ヘッダの下で届きます。

MIGRATION_START (0x44) は 3 バイトです。ハンドラ `0x017c1f00` は、次の条件を満たさない限りメッセージを拒否します

    size == 3                                     0x017c1f54
    [1] == the mesh's HOST index, byte 0xAB       0x017c1f64, getter 0x017bbfe0
    [2] <= 0x1F                                   0x017c1f78, the 32-station bound
    [2] != that host index                        0x017c1f8c

送信側 `0x017c31b8` は、正確に `[0x44, ホストのインデックス, 新しいホストのインデックス]` を組み立てます。

応答は `[0x48, 自身のステーションのインデックス]` です。MIGRATION_RESPONSE ハンドラ `0x017c10ac` は `size == 2` を要求し、ビルダー `0x017c3310` は w22 (`0x017bc430` から取得) を使って `[0x48, w22]` を書きます。ゲッターは 1 バイトずつずれています: `0x017bbfe0` の `ldrb w0, [x0, #0xAB]` (ホストのインデックス)、`0x017bc430` の `ldrb w0, [x0,
#0xAC]` (自身のインデックス)。メッシュをホストしているステーションでは両者が一致します。

MIGRATION_FINISH (0x41) で移行が完了します: `[0x41, ホストのインデックス, flag & 1]` (`0x017c2ef0`)。ハンドラ `0x017c0fb0` は `size == 3` と、[1] がホストのインデックスと一致するかを確認します。

応答は新しいホストへ送られます (`0x017c3250`、呼び出し元は `0x017ca1a0`)。そのステーションが `MIGRATION_FINISH` をブロードキャストします。離脱するホストへ応答を送っても、引き継ぎは完了しません。

`pokeldn/ldn/mesh_protocol.py`: `parse_migration_start`、`build_migration_response`、`build_migration_finish`、`parse_migration_finish`。公開されているソード・シールドのクライアント 4 つは、どれも移行を処理しません。2 台のコンソール間では、指名されたステーションがこれに応答します。

## RTT プロトコル (0x58)

ホストは、各ステーションがメッシュに入った時点から時間を計ります (この内容を扱う wiki のページはありません)。バージョン 9 のメッセージは 13 バイトです:

    u8   kind        0 = request, 1 = response; anything else is dropped
    u64  timestamp   big-endian, the sender's own clock
    u32  target      big-endian, whose reply this is; zero is accepted by everyone

バージョン 4 は ID 0x58 を保持します (vfunc4 `0x0185d590`)。そのパーサ (`0x0185d2a0`) は 16 バイトを平坦に読み、13 バイトの応答は無視します。観測したすべての要求で 1..7 バイト目はゼロでした。意味は不明です。`rtt_protocol.response_for_v4()` はこれらをそのまま返し、種類だけを設定します。

ステーションは、種類 1 に対して、タイムスタンプをそのまま返して応答します。ホストは `(now - echoed) / ticks per ms` を、ステーションごとの 9 サンプルのリングに入れます。リングが埋まると、その中央値が RTT になります。BDSP のタイムスタンプは約 31.36 MHz で進みます。計測した BDSP のセッションでは、RTT プロトコルが無応答のステーションを切り捨てることはなく、そのステーションのサンプリングを止めただけでした。アップデートの要求周期は `0x015ace54` の背後に 2 つの分岐があり、410 ms と 500 ms です。応答がない間、BDSP は 410 ms ごとに要求し、すべてのリングが埋まると 508 ms ごとになります。信頼性再送の間隔は、計測された小さな RTT に従いました (1 秒あたり約 6 回)。

BDSP のアドレス: ID とバージョン `0x015ada10`/`0x015ada18`、サイズ (`mov w0, #0xd`) `0x015adab4`、シリアライズ/パース `0x015ada24`/`0x015ad54c`、アップデート `0x015acd90`、応答のビルダー `0x015ad024`、宛先の確認 `0x015ad000`、サンプルリング `0x015ad058`。

## 信頼性のあるスライディングウィンドウ (0x7c)

### バージョン 9 (Pia 5.29-5.43)

    0x0  1  flags     1 application data, 2 message start, 4 message end, 8 is initialized,
                      16 zlib, 32 reset, 64 reset ack
    0x1  1  stream id
    0x2  2  payload size, big-endian
    0x4  2  sequence id, big-endian
    0x6  2  lowest sequence id pending ack, big-endian
    0x8  1  number of destination bits (N)
    0x9  4 * ceil(N / 32)  destination bitmap words, big-endian
            payload

`GetSize` は `9 + (((N + 0x1f) >> 3) & 0x3c)` で、9 または 13 バイトです。N が 0x20 以上のものと、ペイロードが 0x5a1 以上のものは拒否されます。

アプリケーションデータのフラグが立っていない場合、ペイロードは一括確認応答です:

    0x0  1   a bitfield; 0 in every captured ack. Its bit 0 sets a flag on the receiver
    0x1  1   entry count, refused at 0x21 or more
    0x2  21 * n  entries: u8 stream id, u16be ack id, u16be `ack id - 1`, 16-byte ack mask

製品版コンソールが、シーケンス 0 と 1 に対して返した確認応答:

    00 00 0017 ffff 0003 00   00 01   00 0002 0001  00 * 16

フラグなし、ストリーム 0、シーケンス ID 0xFFFF (制御メッセージはシーケンスを持たない)。続いて、送信側がまだ待っている最小の ID。`ack id` は受信した最大のシーケンスより 1 大きい値です。`pokeldn/ldn/reliable5.build_ack_message()` はこれをバイト単位で再現します。シーケンス 0 のデータメッセージには確認応答は返されず、シーケンス 1 には返されます。

### 受信側が黙って破棄するもの

受信経路は、1 つのメッセージをポートのウィンドウに照らして確認し、ペイロードをスロットにコピーします: Scarlet 4.0.0 `main.bin` の `0x006f0330`、ブリリアントダイヤモンド 1.3.0 の `0x159fb98`。後者は、フラグのビット 0 について `ReliableSlidingWindow` の受信 `0x159f1e4` から到達します (ビット 5 はリセット、ビット 6 はリセットの確認応答、それ以外はウィンドウのスロット 13 への確認応答; `0x159f88c..0x159f8b8`)。5 つの条件はメッセージを破棄しますが、成功を返します。そのうち 2 つは、さらに「確認応答が必要」のバイトも設定します (Scarlet のプロトコルの +0x48、BDSP のウィンドウの +0x738)。そのため送信側は、アプリケーションが受け取らなかったメッセージに対する確認応答を読むことになります。

| 次の場合にメッセージを破棄 | Scarlet | BDSP | 確認応答は送られるか |
|---|---|---|---|
| ウィンドウが初期化されておらず、フラグに `is initialized` (ビット 3) がない | `0x6f037c` | `0x159fbd8..0x159fbe4` | いいえ |
| シーケンス ID がウィンドウの基点 `+0x18` より小さい | `0x6f03cc` | `0x159fc30..0x159fc3c` | はい、`0x6f03d0` / `0x159fc3c` |
| 宛先の数 (解析済みヘッダの `+0x10`) が 0 でなく、ビットマップに受信側のビットがない | `0x6f0430` | `0x159fc7c..0x159fca4` | いいえ |
| ストリーム ID (ワイヤ上の 1 バイト目、解析済みヘッダの `+9`) が、ウィンドウの `+0x1e` で初期化時に保持した値と異なる (BDSP は `strb w26, [x24, #0x1e]` `0x159fc14`) | `0x6f0454` | `0x159fcc0..0x159fcc8` | いいえ |
| リングのスロットがすでに使用中 | `0x6f0540` | `0x159fdb0..0x159fdb4` | はい、`0x6f0530` / `0x159fda4` (確認の前) |

3 つの条件は、読み取れる結果を返します (Scarlet の場合): ウィンドウの末尾を超えるシーケンス `0x4c0d` (`0x6f04a4`)、`0x5a1` バイトを超える再組み立て `0x10407` (`0x6f05cc`)、展開できない zlib ペイロード `0x2c03` (`0x6f0580`)。

BDSP の受信リングはウィンドウの `+0x38` にあります。スロットバッファは `+0x8`、スロット数は `+0x10`、リングの先頭は `+0x14`、基点シーケンスは `+0x18`、ストリーム ID は `+0x1e`、初期化済みフラグは `+0x1f` です。スロットは `0x5b8` バイトで、リングのインデックスは減算で折り返します。スロットの内容は、使用中のバイトが `+0`、メッセージ末尾のフラグが `+1`、zlib フラグが `+2`、ペイロードサイズが `+4`、ペイロードが `+6` から、ポートごとのハンドルが `+0x5a8`、タイムスタンプが `+0x5b0` です。メッセージ先頭のフラグは格納されず、再組み立ては基点から、末尾フラグのある最初のスロットまで行われます。

ストリームの最初のメッセージは、基点を自身のシーケンス ID に設定します (`strh w25, [x24, #0x18]` `0x159fc10`)。初期化済みフラグは、宛先とストリーム ID の確認を通った後にだけ立てられます (`0x159fce4`)。`seq - base + [ring+0x1c] >= [ring+0x10]` のとき、シーケンスは `0x4c0d` で拒否されます (`0x159fc60..0x159fc78`)。`+0x1c` はリングの先頭のオフセットで、新しいストリームでは 0 です。

BDSP のウィンドウ更新 `0x159fea8` は、タイマー (ウィンドウの `+0x740` と周期 `+0x778` の合計) が切れると、未送信の確認応答を送ります (`0x15a003c..0x15a005c`)。ウィンドウのスロット 11 `0x15a1c78` を、`+0x750` のパケット書き込み関数 (`0x15a0318`、`0x15a0354..0x15a0364`) とともに呼びます。`+0x738` が 0 ならスロット 11 は戻ります (`0x15a1cb8`)。それ以外は、シーケンス 0xFFFF の制御メッセージを組み立て (`0x15a1de4`)、データと同様に任意で圧縮し (`+0x7ac`、`0x15a1f70`)、スロット 10 経由で送ります (`0x15a203c..0x15a2044`)。その後 `+0x738` を消去し (`0x15a1fe8`)、タイマーを再開します (`0x15a1ff8`)。スロット 10 は `+0x748` にあるプロトコルとポートの語をヘッダに書き込み (`0x15a1be8`)、パケットを書き込み関数に渡します (`0x15a1c0c`、`0x15a1c20`)。確認応答は、ウィンドウ `+0x638` にある生きているすべての相手に送られます。相手がいなければ何も送られず、バイトが消去されます (`0x15a1eb4`、`0x15a1fd8..0x15a1ff8`)。スロット 11 はデータの経路でも動くため (`0x15a0298..0x15a02b8`)、確認応答はデータに相乗りします。

Scarlet は、基点をウィンドウの `+0x18` に書き込みます。これは初期化時 (`0x6f03a8`)、配達されたメッセージごとの 1 ステップ (`0x6f0238`)、そして空のスロットを、ウィンドウの `+0x20` にある目標へ向かって進む走査 (`0x6f1734`/`0x6f176c`) のときです。目標の値は `0x6ef228` で -1 され、負の間は走査しません。走査は最初の使用中のスロットで止まります。受信関数 `0x6efc2c` は、ウィンドウの確認の前にヘッダを `sp+0x18` へ逆シリアライズします (`0x6efdc8`、`MessageHeader` の vfunc3)。`0x6eff24`/`0x6eff28` は、ヘッダの `lowest pending` (ヘッダの +0x6、`[sp+0x26]`) をウィンドウの `+0x20` にコピーし、`0x6eff2c` の走査は、基点とリングの先頭を `lowest pending - base` スロットまで進めます。

そのため、送信側自身の `lowest pending` が、相手の受信基点を動かします。送信側の次のシーケンスより上に宣言されると、基点はまだ送られていないメッセージを越えて進みます。それらのメッセージは基点より下に届き、`0x6f03cc` で確認応答付きで破棄されます。エミュレートした Scarlet のステーションは、基点 8 のときにホストのコミット (シーケンス 7) を破棄しました。BDSP のコンソールは、ホストのシーケンス 5 と 6 を `(7, 7)` と `(8, 8)` として確認応答し、配達しませんでした。確認応答は、送信側自身の最小の未確認シーケンスを、ヘッダとエントリの 2 つ目のハーフワードに運びます。

### ウィンドウの送信先 (Pia 6)

`ReliableSlidingWindow` の送信先は、インデックスごとにウィンドウの `+0x40` にあるステーションポインタです。サイズは `[[0x46d0860]]+0x50` で決まります (Scarlet 4.0.0 の `main`)。ゲーム側のコードはなく、ステーションのイベントで Pia が埋めます。null でない格納は `0x6ef588` 内の `0x6ef69c` (`str x23, [x8, x25, lsl #3]`) だけで、これがステーションをインデックスに登録します。null は `0x6ef3dc`、`0x6ef4e0`、`0x6ef9b4` で格納されます。`0x6ef588` は次の場合に拒否します:

| 拒否の理由 | コード |
|---|---|
| ウィンドウに空きがない (`[w+0x28]` が 0) | 0x1040c |
| ステーションが null、ウィンドウ自身の `[w+8]` である、またはインデックスがウィンドウ自身の `[w+0x10]` である | 読まない |
| インデックスがすでに使われている | 0x10407 |
| インデックスのステーションごとのレコード (ウィンドウの vfunc `0x40`) で、バイト `+0x1f` が立っている (`0x6ef650`..`0x6ef664`) | 0x10408 |
| そのステーションが別のインデックスですでに登録されている | 0x10408 |

成功すると、そのレコードをリセットし (vfunc `0x10`)、インデックスを `+0x24` に、`w3` の u16 を `+0x26` に書き込み、`[w+0x74]` のインデックスのビットを立てます。呼び出し元は、スロット 11 のステーションイベントのメソッドです。`0x6e6288` は、BroadcastReliableProtocol (0x80) の `0x6e630c` にある `bl` から呼ばれ、また StreamBroadcastReliableProtocol のスロット 11 `0x6f51a8` (`0x6f51bc`) からも最初に呼ばれます。もう 1 つは `0x6ee528` で、ReliableProtocol (0x7C) の呼び出し箇所 `0x6ee5d4` から呼ばれます。`0x6e6288` は、イベントの `+8` にある ID でイベントのステーションを検索し (`[[0x46d0860]]` -> `0x1e7c4e8` -> vfunc `+0x38`)、プロトコル自身のステーションインデックスが 0xfd (`0x6ec4f0`) の場合か、ステーションが自分自身 (`0x6ec4a8`、`[station+0x30]` と比較) の場合に戻ります。イベント 0 は `[station+0x30]` を、インデックス `[station+0x28]` に `[station+0x38]` とともに登録します。イベント 1 はそのインデックスを削除します (`0x6ef75c`)。

ステーションがリストから欠けるのは、参加イベントの前、離脱の後、プロトコルのステーションインデックスが 0xfd の間、または `0x6ef588` がそれを拒否したときだけです。一括確認応答を組み立てる `0x6f2138` も同じリストを読みます。null は飛ばし (`0x6f2324`..`0x6f232c`)、確認応答の状態を確認した後にステーションのヘッダの宛先ビットを立てます (`0x6f22f8`..`0x6f230c`)。立たない場合は呼び出し元のマスクにフォールバックします (`0x6f2360`..`0x6f2370`)。確認応答のビットは、ウィンドウがそのステーションを登録したことを示すだけで、そのステーションに送られたメッセージについては何も示しません。

### バージョン 4

1 つのヘッダクラスが 0x7C と 0x80 の両方に使われます: `nn::pia::transport::ReliableSlidingWindow::MessageHeader` (GetSize `0x0184e480`、Deserialize `0x0184e390`、Serialize `0x0184e230`)。

    0x0  1  flags
    0x1  1  stream id
    0x2  2  payload size, big-endian    refused at 0x589 and above (0x0184e3cc)
    0x4  2  sequence id, big-endian
    0x6  2  lowest sequence id pending ack, big-endian
    0x8  1  destination count           refused at 0x20 and above (0x0184e404)
    0x9  8 * count  station constant ids, big-endian

`GetSize` は `9 + 8 * count` です。2 つのバージョンが一致するのは count が 0 のときだけで、これは両側が送るすべての 0x7C メッセージに当たります。そのため、バージョン 9 のパーサは、フィールドがずれることなくバージョン 4 のメッセージ 221887 個を読み取れます。

受信経路 (`0x01859338`) は、次の 5 つを黙って拒否します:

    0x0185952c   payload size <= 0x57F - 8 * count     tighter than the deserialiser's own bound
    0x0185954c   the Pia message length equals 9 + 8 * count + size exactly
    0x0185956c   the stream id is the window's own for this station, [w + 0x18*st + 0x46]
    0x01859578   a count above 0 is a list the receiver must find itself in; count 0 is unfiltered
    0x01859ca0   the first message on a stream carries FLAG_IS_INITIALIZED

`0x01859734` のフラグで振り分けます: ビット 5 は RESET、ビット 6 は RESET_ACK、ビット 0 は APPLICATION_DATA です。それ以外は、フラグがないものを含めてすべて確認応答ハンドラ `0x01859a70` に送られます。

ステーションごとのバイト `[window + 0x18*station + 0x47]` が 0 の間、そのストリームは存在しません。最初のデータメッセージは FLAG_IS_INITIALIZED を持たなければならず、ストリーム ID (`+0x46`) と開始シーケンス (`+0x40`) を設定します。コンソールは最初のメッセージでフラグ 0x0F を送り、以後は 0x07 を送ります。`reliable4.build_data_message(bytes.fromhex("610000000a00"))` は、コンソールのシーケンス 1 をバイト単位で再現します: `0f0000060001000100610000000a00`。

確認応答のペイロードは正確に 0x260 バイトで、5.29 が数付きのリストに置き換えた、wiki 上の元の "Ack Data" です:

    5.29-5.43   1 unknown byte, 1 count, then `count` x 21 bytes
                    u8 stream id, u16be ack id, u16be the window's field 0x50, 16-byte mask
    version 4   32 entries of 19 bytes, always
                    u8 stream id, u16be ack id, 16-byte mask

ハンドラ `0x01859a84` は `ldrh w8, [x2, #0xa]; cmp w8, #0x260; b.ne` で始まり、本体を読まずに 0x2c03 で応答します。シリアライザ `0x0185bfb0` は 0x20 回ループして、ストリーム ID、ビッグエンディアンの確認 ID、16 バイトのマスクを、2 つのビッグエンディアン u64 として書き込みます。スロットの読み取りは、ハンドラの 4 番目の引数から得たステーションインデックスで行われますが、その呼び出し箇所がどのステーションかは示していません。スロットのストリーム ID はウィンドウのものと一致しなければなりません (`0x01859c1c`)。`reliable4.build_ack_payload` は、どちらの読み方でも正しくなるよう、すべてのスロットに同じエントリを入れます。

ソード・シールドは、使わないスロットに古いバイトを残します。ストリーム ID 0 の下にあり、スロット 0 が 2 を持つ間、スロット 1, 2, 4, 5 に `22284`, `16`, `57080`, `2517` が入っていました。確認されたストリームのエントリだけを読んでください。全スロットの最大値は古い値であり、それに従う送信側は、コンソールのウィンドウを超えて送ってしまいます (ウィンドウ 97 に対して 401 件のメッセージを送った)。その後、コンソールは確認応答を止めます。

固定の `lowest_pending` のままシーケンス ID が増えると、未処理の滞留が増えます。メッセージごとの `lowest_pending` と、シーケンス ID ごとの再送回数を計測してください。

## プロトコル 0x80 (ブロードキャスト信頼性ウィンドウ)

`nn::pia::transport::BroadcastReliableProtocol` (vfunc4 `0x0184d880` が 0x80 を返す) は、0x84 の `ReliableBroadcastProtocol` とは別のクラスです。そのメッセージは圧縮されています (バージョン 4 のフラグ 0x10)。生のサイズは 42 バイト、展開後は 625 バイトで、宛先の数が 1 の信頼性ヘッダと、0x260 バイトの確認応答ペイロードの上にある 8 バイトのステーション定数 ID を含みます (バージョン 9 のビットマップ規則なら 621 バイトになる)。確認応答には、メッシュが保持できるステーションごとに 1 つずつ、ステーションインデックス順のスロットがあります。コンソールは 0..7 に実際の確認 ID を入れ、8..31 はゼロのままにします。8 は参加応答の `max_total` です。

## プロトコル 0x81 (ストリーム型ブロードキャスト信頼性転送、Pia 6)

`StreamBroadcastReliableProtocol` は、固定サイズのブロックを、要求したすべてのステーションへチャンクに分けて送ります (Scarlet 4.0.0 の `main`)。スロット 10 はその更新 `0x6f5360`、スロット 11 は `0x6f51a8`、スロット 17 は `0x6e6818`、スロット 19 は BroadcastReliableProtocol の `0x6e69a0` です。`0x6e69a0` は `[proto+0x70]` からウィンドウを読み込み、バイト予算 `[proto+0x64]` で `ReliableSlidingWindow` の送信ループ `0x6f0638` を実行します (`0x6e69c0` の `bl`)。ループは、各スロットの次の時刻を再送期限 `0x6f0d14` から得ます (`0x6f073c` の `bl`)。チャンクは `0x6f1994` を通してキューに入り (`0x6f5c2c`、`x0 = [proto+0x70]`)、この関数がスロットに現在時刻を刻みます (`0x6f1bd4`)。0x81 の転送は、0x7C と 0x80 と同じ期限で再送され、どの宛先にも RTT の計測値がないときは再送しません。

各メッセージには、`0x6f60e8` が書き込む 11 バイトの StreamData ヘッダが付きます:

    +0  1  kind: 0 a receive posted, 1 the first chunk, 2 a later chunk, 3 to 6 control
    +1  1  transfer id
    +2  1  percent of the block delivered after this chunk
    +3  4  big-endian u32: the receive capacity in a kind 0, zero in a chunk
    +7  4  big-endian u32: the length of the data that follows
    +11    the data

ゲームの送信 API は、バッファ、サイズ、転送 ID を受け取ります。受信 API は、送信者、バッファ、容量、ID を受け取ります。受信の要求が出されると、容量を載せた種類 0 を送ります。次の場合、送信は拒否されます: サイズが `[proto+0xa0]` を超える場合、ID が 0xff の場合、どのステーションの `[proto+0x98]` のバイトも ID と等しくない場合。チャンクのループ (`0x6f5560` 内の `0x6f5b54`..`0x6f5c58`) は、`0x6f1ef8` が空きスロットを見つける間キューに入れます。チャンクは `[window+0x70] - 11` バイトで、種類は `(offset != 0) + 1` (`0x6f5bb0`..`0x6f5bbc`)、ID は `+0xa4` から、進捗率は `(offset + chunk) * 100 / size` (`0x6f5b78`..`0x6f5b98`) で、`+0xba` にも保持されます。

受信ループ `0x6f5cdc` は、`0x6f5560` の後のアップデートから呼ばれ、BroadcastReliableProtocol の vfunc13 (`0x6e644c`、送信者は `sp+0xb80`) でメッセージを 1 つずつ取り出します。ヘッダは StreamData の vfunc3 (`0x6f635c`) で復号し、送信者のインデックスを `0xe42ddc` で解決します。種類は `0x3c0d5e5` のバイトテーブルで振り分け、6 を超える種類は無視します:

| 種類 | 対象 | 受信側の処理 |
|---|---|---|
| 0 (受信の要求) | `0x6f5e5c` | 自身が状態 1, 2, 4, 5, 8, 9, 10 のいずれかの場合 (マスク 0x736)、送信者を `[+0xc0]` に印付ける。それ以外 (`0x6f6094`) は `[+0x98][sender] = id` と `[+0xa0] = min([+0xa0], capacity)` を行う |
| 1 (最初のチャンク) | `0x6f5e90` | 受信数 `+0xac` と `+0xba` を消去し、状態を 4 から 5 にする。そのあと種類 2 と同じ処理 |
| 2 (チャンク) | `0x6f5eb4` | 状態 5 のときだけ。送信者 `+0xb0` からの ID `+0xa5` のもの: `+0x90` に収まる場合、データを `[+0x88] + [+0xac]` にコピーし、長さを加え、進捗率を `+0xba` に保持する |
| 3 (送信側が忙しく受信を拒否) | `0x6f5f2c` | 状態 4 のときだけ。転送をリセットし、すべての `[+0x98]` を 0xff にして、状態 7 にする |
| 4 (送信側の取り消し) | `0x6f5f9c` | 転送をリセットし、すべての `[+0x98]` を 0xff にして、状態 0xC にする |
| 5 (受信側の取り消し) | `0x6f6000` | `[+0x98][sender] = 0xff` とし、送信者を `[+0xc8]` に印付ける |
| 6 (送信側が取り消しを確認応答) | `0x6f6024` | 状態 0xA のときだけ。リセットして、状態 0xB にする |

制御の種類は ID 0xff を持ちます。アップデート `0x6f5560` は、`[+0xc0]` に印の付いたステーションへ種類 3 を送ります (`w2 = 3` の `0x6f6268`、`0x6f5750`)。`[+0xc8]` に印の付いたものへは種類 6 を送ります (`0x6f57d8`)。状態 9 では、想定される送信者 `[+0xb0]` へ種類 5 を送り (`0x6f5904`、`0x6f1de8` 経由のユニキャスト)、その後状態 0xA になります。状態 8 では、その宛先へ種類 4 を送ります (`0x6f5984`)。受信要求された最小の容量が、送信 API が受け付けるブロックの上限になります。

`+0x78` の状態 (`0x6f53b0`): 受信は、`+0xba` が 0x64 に達すると 5 から 6 に進みます (`0x6f5460`)。送信は、`[+0x98]` のエントリが `+0xa4` と等しく、ウィンドウがシーケンス `+0xb8` の確認を報告すると 2 から 3 に進みます (`0x6e7128`、`0x6f54e4`)。一致するエントリがなければ 0xC に進みます。

## プロトコル 0x84 (信頼性ブロードキャスト転送)

`nn::pia::transport::ReliableBroadcastProtocol` は、ソード・シールドの交換スナップショットを運びます:

| 種類 | 意味 |
|---|---|
| 0x11 / 0x12 | データの断片。[4] にカウンタ、[10] に容量 |
| 0x19 | 転送が完了 |
| 0x21 | 連続する基点と、先に届いたものを示すビットマスクを運ぶ確認応答 |
| 0x28 | 0x19 への応答 |

応答しない受信側は、最後の 3 種類を一度も見ることがなく、送信側は再送を続けます (上限は計測していません)。
`pokeldn/ldn/broadcast4.py`。コンソールは自身の転送をポート 0 で送り、相手の転送への確認応答をポート 1 で返します。
