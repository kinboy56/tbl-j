# ユニオンサークル

ユニオンサークルは、フィールドを共有する最大 4 人のスカーレット・バイオレットのセッションです。コード上は
チームサークル (`TeamCircle`) と呼ばれ、ブルーベリークエスト (BBQ) は `bbmission` です。pokeldn はコンソールの
ローカルのユニオンサークルにゲストとして参加し、ホストに BP を支払い、スナックスワースの伝説のポケモンを
解放する BBQ のクリアを報告します。また、ホストのプレイヤーの周囲に野生のポケモンを出現させます
([フィールドでの遭遇](#overworld-encounters))。アプリのユニオンサークル用ツールは 2 つあり、
[アプリガイド](gui.md#union-circle) にあります。

以下の Lua は、スカーレット 4.0.0 のチャンク `be21e65463b9a98f` (`main.blua`、SHA-256
`c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815`、[テラレイド](sv_raid.md) のチャンク) です。
ただし `main_dynamic` と書かれている場合を除きます。`0.N` はチャンクのメイン関数の N 番目の
プロトタイプで、0 から数えます。プロトタイプの番号は、公開されている 3.0.1 の逆コンパイル (Martmists-GH/SV-Script-RE) でも同じです。
山括弧で囲まれた名前はハッシュ一覧から得たものです。それ以外の名前は
まだハッシュのままです。

## Lua の取得

チャンクは `arc/data.trpfs` 内の `script/lua/bin/release/main/main.blua` にあり、Oodle で格納されています。4.0.0 アップデートの
仮想 RomFS には、ベースゲームのものが必要です。`arc/data.trpfd` の一部はベースゲーム側にあります。

    ./.venv/bin/python tools/switch/nso_read.py main main.bin
    ./.venv/bin/python tools/switch/trpfs_read.py --update UPDATE.nsp --base BASE.nsp --keys prod.keys \
        --image main.bin --extract script/lua/bin/release/main/main.blua --out-dir OUT

`main` はアップデートの ExeFS モジュール (`pokeldn.switch.container.exefs`) で、`--image` はその
`OodleLZ_Decompress` (`0xcc8750`) を実行します。チャンクは、トップレベルのプロトタイプが 30,829 個ある標準の Lua 5.4 バイトコードです。
イベントのスクリプトは 2 つ目のチャンク `main_dynamic` にあり、
(`script/lua/bin/release/main_dynamic/main_dynamic.blua`、トップレベルのプロトタイプが 6,431 個) を、
同じ方法で取り出します。

## BBQ

クエストの進行はネイティブ側で持っており、Lua モジュール `c5137FC87` にあります。Lua のゲームイベントは
`C00099C1DFBF96B11.S110BDDB84DEB4379` (`0.7064`) を通じてそこへ報告されます。これは (クエストの種類、2 つの値、回数) を
`c5137FC87.f4246D9CA` に渡します。たとえば進化は、回数 1 の種類 28 として報告されます。サークル側のクエストは、
2 つ目のネイティブモジュール `c4D400AC0` が担当します。

すべてのクエストにはグレードがあります。これはクラブデータ内の `MissionInfo` 行の `mission_grade` です
(`arc/worlddataclubMissionDifficultyWeightAdvanced.bin.trpak`)。0 がノーマル、1 がボーナス、2 がチーム。
スナックスワースは、チームのクエストをグループクエストと呼びます。クリアのイベントには、そのクエストのグレードが含まれます。

パックのクエストテーブルは、64 個の `MissionInfo` 構造体からなる FlatBuffer です。各構造体は、カテゴリ (1 バトル、2 フィールド、
3 カメラ)、`mission_type`、`mission_id`、目標、報酬 BP、差し替え用の再読み込み BP、解放タイプ、
グレード、難易度 (0 ビギナーから 2 アドバンスド)、重みを持ちます。メッセージ内のクエスト ID は、その行の `mission_type` です。
`mission_id` は同じ種類の行を区別します。これらはグレード、難易度、目標、BP が異なります。
BBQ の一覧は、組 (`0x29de0f4`) を使ってクエストを探します。2 つ目のテーブル `MissionSettings` は、
種類ごとのバリエーション (ポケモンのタイプ、バイオーム、フレーバーなど) の文言を `club_bbmission` に持ちます。
クエストテーブルが使う種類は次のとおりです。

| ID | クエスト | グレード |
|---|---|---|
| 1 | オートバトルで野生のポケモンを倒す | ノーマル、ボーナス |
| 2 | 一定の距離を移動する | ノーマル |
| 3 | 同じ種類の服を着た友達と写真を撮る | チーム |
| 5 | 友達と四つ星のサンドイッチを作る | チーム |
| 6 | 1 種類のフレーバーのサンドイッチを作る | ボーナス |
| 7 | 指定した数の材料でサンドイッチを作る | ボーナス |
| 8 | ポケモンを洗う | ボーナス |
| 9 | 野生のポケモンの背後から驚かせる | ノーマル |
| 10 | タマゴを孵す | ボーナス |
| 11 | 地面のアイテムを拾う | ノーマル |
| 14 | ヒントが示すポケモンを捕まえる | チーム |
| 15 | バイオームで Ditto のブロックを探す | チーム |
| 21 | 1 種類の野生のポケモンを撮影する | ボーナス |
| 22 | 飛んでいる野生のポケモンを撮影する | ノーマル |
| 23 | 泳いでいる野生のポケモンを撮影する | ノーマル |
| 25 | バイオームで友達と写真を撮る | チーム |
| 27 | テラレイドバトルに勝つ | ボーナス |
| 29 | わざマシンを作る | ノーマル |
| 30 | 野生のテラスタルポケモンとバトルする | ボーナス |
| 31 | テラスタルした後に野生のポケモンを倒す | ノーマル |
| 32 | 1 種類のポケモンを捕まえる | ノーマル |
| 33 | バイオームで野生のポケモンを撮影する | ノーマル |
| 34 | ポケモンを捕まえる | ノーマル |

ノーマルの行はすべて 20 から 40 BP、ボーナスの行はすべて 100 から 200 BP、チームの行はすべて 400 から 600 BP を支払います。

BBQ マネージャーが作られると (`0.7062`)、ネイティブ側に取得関数を渡します。`c16FE4B25` は
プレイヤー自身のフィールド (`f61488ABA`、セーブデータの `currentFieldId`) とメンバーのフィールドを取得します
(`f45B80F87`、ステーションのインデックスに対応する 110 の値)。`c5137FC87` は、プレイヤーがフィールドにいるかどうか (`f01FF34BD`) と、
2 つのクラブレベルのフラグ `FSYS_CLUB_BBMISSION_LVUP_01` と `_02` を取得します。

毎フレーム、マネージャーの `PreUpdate` (`0.7069`) が 3 つのネイティブキューを処理します。

| キュー | 発生元 | Lua の処理 |
|---|---|---|
| `c5137FC87.fB8D11637` / `f35493666` | プレイヤー自身のクリア | `c4D400AC0.f5770F782` が保持されている間、各クリアを `c4D400AC0.fAC449469` に渡します。サークル内で発生したボーナスのクリア (`c4D400AC0.f48603105`) は、ホストでは `c4D400AC0.f263D7D28` と `f07578A96` に渡され (`c4D400AC0.fE8E53DDE`)、ゲストはそれに対して何も加算しません。それ以外のクリアは BP のキューに入ります |
| `c4D400AC0.fD7C6549F` / `f37737462` | 他のメンバーのクリア | それぞれを通知として表示します。ボーナスのクリアでなければ BP のキューに入れます |
| `c4D400AC0.fD961BFD2` / `f541C4B17` | サークルからの BP 付与 | 各付与を BP のキューに入れます |

`0.7075` は、キューのイベントを同じグレードのものに統合し、その BP を合計します (`fBCA6AEB8`)。`0.7076`
はキューの合計を通貨マネージャーに加算し、`0.7077` は BP のメッセージを表示します。マネージャーの加算処理
(`0.15120`) は、プレイヤーの BP を 0 から 9,999,999 (`0.15128`) の範囲に収めます。そのため、クリアの BP は s32 ですが、
1 回のクリアで数えられる最大は 9,999,999 BP です。

そのため Lua 側では何も確認しません。ホストには、メンバーのノーマルまたはチームのクリアの分が 2 つ目のキューから直接支払われます。
ボーナスのクリアは、ネイティブのサークルモジュールが 3 つ目のキューに入れる付与を通じてのみ支払われます。
そしてホストでは、そのモジュールがメンバーのクリアも受け取ります。

## ネイティブモジュール

以下のアドレスは、スカーレット 4.0.0 の `main` 内のものです。

ネイティブモジュールの名前と関数名は、`main` の読み取り専用データ内にある単純な文字列です。例えば `c4D400AC0` や `f5770F782` は、
実行時に計算されるものではありません。各モジュールには、`.data` 内に `luaL_Reg` 形式のテーブルがあります。これは {名前, 関数} のポインタの組で、
`R_AARCH64_RELATIVE` の再配置で埋められ、null の組で終わります。`c4D400AC0` のテーブルは `0x442e500` にあり (関数 22 個)、
`c5137FC87` のテーブルは `0x4420630` にあります (関数 45 個)。
クリアのイベントは、メソッドが `0x441dc50` のテーブルにある userdata として Lua に渡されます。
`fBCA6AEB8` は BP (`+0x10` の s32) を返し、`f0C278E84` はグレード (`+0xd` の s8) を返します。
イベントは `0x29dd878` が組み立てます。
クエスト ID (`+0x0` の u16)、`+0x4` の u32、グレード、BP はすべて、そのクエストの行から得られます。

`c4D400AC0` の関数は、遅延生成されるシングルトンのサークルオブジェクト (`0x4739410`) 1 つを操作します:

| 関数 | 役割 |
|---|---|
| `f5770F782` | サークルの準備ができているか (`0xa0d038`) |
| `f48603105`、`fE8E53DDE` | プレイヤーがサークルに入っているか、そのサークルをホストしているか (`0xa0e9ac`) |
| `fAC449469` | プレイヤーのクリアを、メッセージ 3 として送信します (`0xa0db20`) |
| `f263D7D28` | ホストで、ボーナスのクリアをメッセージ 5 として送信します (`0xa0dcf4`) |
| `f07578A96` | ホストで、自身のボーナスのクリアを加算します (`0xa0df34`、続けて付与の通知 `0xa0e164`) |

サークルは、これらのメッセージを `TeamCircleNetReceiver` を通さず、独自のチャネル (オブジェクトの `+0x70`) で送信します。
ゲームのキーは 0x80 ポート 0 上の 0x0048 で、メッセージの種類は kind バイトに入ります。各メッセージは続けて、
ゲームのタグ付き形式によるクリアのイベント (`0xb9`、続けて 18 個のフィールド。`0xa17694` が読む) になり、
その後に送信者のメッセージ番号 (オブジェクトの `+0xb8`、送信ごとに増加) が続きます。メッセージ 3 にはさらに
送信者の BBQ 状態レコード (`0xa0f37c` が書き、`0xa17170` が読む) が含まれ、そのバイト
`+0x185` が送信者のボーナスのクリア数です。

市販版のホストによる、20 BP のノーマルのクエストのクリアです (メンバーが受け取った形)。

| フィールド | 値 |
|---|---|
| 0 | クエスト ID (29) |
| 1, 2 | 0, 0 |
| 3 | クエストのスロット (2、3 番目) |
| 4 | グレード (0、ノーマル) |
| 5 | BP (20) |
| 6 | 送信者のステーション ID の組 (u64、タグ 0x83) |
| 7 | クエストの `MissionInfo` 行: カテゴリ (2、フィールド)、ID (29)、`mission_id` (0)、目標 (1)、BP (20)、再読み込み BP (10)、解放タイプ、グレード、難易度 (0、ビギナー)、重み (8.0) |
| 8, 9, 10 | 0, 0, (0) |
| 11 | 同じスロット |
| 12, 13 | そのスロットに入るクエスト: (ID、0.0、0、0) とその行 |
| 14から17 | 空の行 (0, 0, 0, 32767, 0, 0, 0, 0, 0, 0.0)、0、空の行、0 |

その番号は 4 でした。その 0.1 秒前にホストは kind 2 を送信しました。内容は、クエスト、-1、-1、その
進行度 (1.0)、3、そして状態レコードです。タグ付き形式では、-64 から 127 の整数は 1 バイトで表され、
それより大きい値は符号付きタグ (0x84 から 0x86) の後ろに置かれ、浮動小数点数は 0x88 の後ろに置かれます。

### BBQ の状態レコード

各プレイヤーの BBQ マネージャーは、状態レコードを `+0x40` に保持します。サークルはそれを (`0xa0f37c`)
メッセージ 1、2、3 に書き込みます。メッセージ 1 (kind 1) は、送信者のメッセージ番号とレコードだけからなります。
プレイヤーは、サークルの開始時にステップ 1 としてそれを送り、続けてボディのない kind 4 (`480004`)、次にステップ 2 を送ります。
ホストは、メンバーのクリアのたびに別のものを送ります。レコードは 11 要素の組です:

| 要素 | レコードのオフセット | 値 |
|---|---|---|
| 0 | `+0x0` | すべてのレコードで 1 (マネージャーの `+0x40` のバイト) |
| 1から3 | `+0x4`、`+0x50`、`+0x9c` | プレイヤーの 3 つのクエストスロット |
| 4 | `+0xe8` | 1 バイトのバイト列。すべてのレコードで 1 |
| 5、6 | `+0xec`、`+0x138` | さらに 2 つのスロット。確認したすべてのレコードで空 |
| 7 | `+0x184` | 符号付きバイト。すべてのレコードで要素 9 と等しい |
| 8 | `+0x185` | 次の付与までのプレイヤーのボーナスのクリア数 |
| 9 | `+0x188` | ソロの合計 (マネージャーの `+0x1c8`) |
| 10 | `+0x18c` | チームの合計 (マネージャーの `+0x1cc`) |

スロット (`0xa0fa18`) は 0x4c バイトで、レコードには 4 つ含まれます。クエストの ID (u16、空のスロットは 0)、
進行度 (浮動小数点数)、テキストのバリエーション (`MissionSettings` のバリエーション。クエストが指す種類、バイオーム、フレーバー。
指定がないクエストは 0)、そして行の `mission_id` です。
市販版のメンバーの「バイオームで写真を撮る」クエストは
3 を持っていました (キャニオンバイオーム)。BBQ の一覧は、ID と `mission_id` (`0x29e17ec`) でスロットを行に対応させます。
メンバーがホストのレコードを受け取り、ホストの 5 番目のスロット (要素 6) が自分のものとは別のクエストを指している場合、
メンバーはホストのものを自分のものとして取り込みます (`0xa14290`、`0x29e1ea0` へ)。

`circle.bbq_record` は、メッセージ 1、2、3 の末尾にあるレコードを読みます。

確認したすべてのキャプチャで、市販版のホストのスロットには、それぞれ種類のビギナーのノーマルの行 (`mission_id` 0: 20 BP、
クエスト 1 は目標が 10 体の撃破、それ以外は目標が 1)が入っており、報告によって完了されるまで進行度は 0 でした。
ホスト自身のクリアは、空いたスロットに入ったクエストを、その行とともに示していました。
残りのスロットは空のままで、ボーナスのクリア数は 0 でした。チームの合計は、pokeldn からのチームのクリアが 1 回ごとに 1 増えました。
これは [スナックスワース](#snacksworth) の記載のとおりです。

### ホストのクエストに対するメンバーの進行

メンバーは、ホストのクエストを、クリアではなく進行の報告によって完了させます。2 台のコンソールで取得した例では、
市販版のバイオレットのメンバーが、スカーレットのホストのクエスト 9 (背後から野生のポケモンを驚かせる) を行いました。
これは自身のクエストではありませんでした。バイオレットはメッセージ 2 (kind 2) だけを、0x80 ポート 0 上で送信しました。
内容は、クエスト (9)、2 つの値 (-1、-1)、回数 (1.0)、メッセージ番号 (3)、そして自身の状態レコードです。
0.1 秒後、ホストは、クエスト 9 の進行度を 1 にしたレコードと、続けて自身のメッセージ 3 を送信しました。
これはクエスト 9 のクリアで、バイオレットのステーション ID (フィールド 6)、20 BP、スロット (1)、
そこに入るクエスト 23 を記録しています。ホストのソロの合計は 5 から 6 になりました。

メッセージ 2 は、Lua の進行報告 (`c5137FC87.f4246D9CA`) が渡すものを運びます。クエスト、その 2 つの値、
回数です。ホストの受信ハンドラーは、この 4 つを、メンバーのフラグと送信者とともに、
自身の報告が届くのと同じネイティブの進行ディスパッチャー (`0x29dc838`、`0x29dc6b0` から呼ばれる) に渡します。そのためホストは、
メンバーの進行を自身のものとして数え、クエストを完了させてクリアし、そのクリアを
自身のクリアと同じようにソロの合計に加算します。

`circle.progress_message` はメッセージ 2 を組み立てます。スナックスワースの実行 ([参加](#joining)) では、各報告を、
ホストの 3 つのスロットのうち次のものへ、その最新のレコードが示すとおりに送信します。回数は 500 です (ノーマルの行で最大の目標)。
最初の値はスロットのバリエーションで、ない場合は -1 です。市販版のホストは、この方法で報告された各クエストをクリアし、
そのたびにソロの合計が 1 増えました。

## メンバーのクリアに対してホストが行うこと

受信ハンドラー (`0xa13b00`) は、`0x3c5b7a4` のジャンプテーブルを通じて種類ごとに処理を振り分けます。メッセージ 3 について、
ホストは次の処理を行います。

1. メンバーのボーナスのクリア数を、BBQ の状態内のそのメンバーのスロットに保存します。
2. クエストを、自身の BBQ 一覧で検索します (`0x29de0f4`、クエスト ID と `+0x4` の u32 で)。自身のボーナスのクエストの
   いずれかに一致した場合にのみ、そのクリアがホスト自身の集計に加算され、
   ホストは自身の通知をキューに入れます。
   ステップ 4 のフラグを除き、この結果は下記に影響しません。
3. クリアをメンバーの通知としてキューに入れます (`fD7C6549F` キュー)。
4. クリアがボーナスの場合、イベントの `+0x7c` を min(3、ホスト自身のボーナスのクリア数に、
   メンバーの 3 つのスロット分を足したもの) に設定します。`+0x80` にはステップ 2 が一致したかを設定し、それをすべてのメンバーにメッセージ 5 として送信します。そのうえで、
   受け取ったイベントのまま、付与の通知によって自身にも加算します。
5. クリアがチームのクリアで、ホストの BBQ マネージャーが有効な場合、ホストのチームの合計に 1 を加えます
   (下記)。

その後になって初めて、ホストはメッセージの番号をメンバーの最後のものと比べます。
その番号が制限するのはメンバーの状態レコードだけです。

メッセージ 5 を受け取ったメンバーは、同じ付与の通知によってイベントを加算します。ただし、その番号が
ホストから最後に見た番号より古い場合は除きます。

つまりホストは、メンバーのメッセージが指定するものを支払います。`+0x10` の BP はメンバーから来ており、
この経路ではそれを確認せず、クエストが存在するかどうかも確認しません。ノーマルまたはチームのクリアは、すぐに Lua によって支払われます。
ボーナスのクリアは付与の通知を経由し、それが唯一の順序制御です。
各イベントを一時的に保持し、`+0x7c` が直前に解放されたイベントの値より 1 大きいか、2 小さいか、どちらも 0 のときだけ、
付与のキュー (オブジェクトの `+0x108`) に解放します。この値はスロットから作られるため、
メンバーの次のボーナスのクリアは、前回より 1 大きい回数を報告しなければなりません。

## スナックスワース

BBQ マネージャーは 2 つの累計を保持します。これは `c5137FC87.f6ED7C9B6` (`+0x1c8`) と
`fECB0EBF0` (`+0x1cc`) によって読まれます。

| 合計 | 加算される条件 | 併せて読まれる箇所 |
|---|---|---|
| ソロ、`+0x1c8` | プレイヤー自身のノーマルまたはボーナスのクリア (`0x29dda40`) | クラブの BBQ レベルアップイベント (15 と 45 のとき) |
| チーム、`+0x1cc` | プレイヤー自身のチームのクリア、およびホストではメッセージ 3 におけるメンバーごとのチームのクリア (`0xa14918`) | |

スナックスワースはイベント `s2_sub_012` で、彼の 25 体の伝説のポケモンは、イベント `s2_sub_013` から `s2_sub_037` です。
それぞれの状態は `WEVT_S2_SUB_0NN_STATE` にあります。`main_dynamic` にあるイベントのクラス (プロトタイプ
`0.1995` から `0.2032`) は、`0.2019` でソロの合計を、`0.2020` でチームの合計を読みます。
プレイヤーが話しかけると、`0.2002` は、ソロの合計が
ソロのルートですでに解放された伝説のポケモン 1 体ごとの `missionReleaseCount` を差し引いた値が
`missionReleaseCount` に達したとき、次のソロルートの伝説のポケモンを解放します。`0.2003` は、チームルートについて、
チームの合計と `teamMissionReleaseCount` で同様の処理を行います。どちらの回数も、イベントの設定テーブルから得られます
(`s2_sub_012.ReleaseConfigTable`、
`arc/worlddataeventcommandcommand_data_rootcommand_data_root.bin.trpak` 内)。パックにある同じ形のテーブルは 1 つだけで、
その値は 10 と 1 です。

同じパック内の `s2_sub_012.ReleasePokeTable` は、各伝説のポケモンを 4 つのルートのうち 2 つに割り当てます。ソロ 2 つ
(`MissionA`、`MissionB`) とチーム 2 つ (`TeamMissionA`、`TeamMissionB`) です。

| 割り当て | 伝説のポケモン |
|---|---|
| ソロの両方のルート | Articuno、Zapdos、Moltres、Kubfu |
| チームの両方のルート | Rayquaza、Kyurem、Necrozma |
| それぞれ 1 つずつ | 残りの 18 体 |

スクリプトは `CA4C5F9FA83D2AF80.SDF0C255E6E08D740` に、プレイヤーがどの組のルートにいるかを尋ねます (A のルートか B のルートか)。
スカーレットは A のルートにいます。スカーレットでのチームのクリアは、`TeamMissionA` だけが持つ Zekrom を解放しました。
各組は 25 体の伝説のポケモンを、重複なしで分けます。ソロのルートに 13 体、チームのルートに 12 体です。
1 回の会話では、多くとも 1 つのスナックを解放し、チームのルートを先に試します。
各ルートは、まだ解放されていない伝説のポケモンの中からランダムに選びます (`0.2007`)。ルートの次の解放には、
その合計が、回数に、そのルートですでに解放された伝説のポケモン数に 1 を足した値を掛けたものに達する必要があります。
そのため、25 体すべての解放には、ソロの合計 130 とチームの合計 12、そして 25 回の会話が必要です。

そのため、どのメッセージもスナックを指定しません。ホストで動くスナックスワースのスクリプトは、ホスト自身の合計を
設定と比べます。チームのクリアを含むメッセージ 3 は、ホストのチームの合計に 1 を加えます。
また、メンバーが完了させたホスト自身のクエストのそれぞれ ([ホストのクエストに対するメンバーの進行](#a-members-progress-on-the-hosts-quests)) は、
ソロの合計に 1 を加えます。ホストは、そのクエストが自身が持つチームのクエストかどうかを確認しません。
また、番号は繰り返しを止めません。`teamMissionReleaseCount` が 1 の場合、それぞれが 1 つのチームルートのスナックになり、
スナックスワースに話しかけることで受け取ります。これはホストのチームルートの 12 体を賄います。
ソロのルートの 13 体には、ソロのクリアが必要です。
これはメンバーが、ホストのためにクエストを完了させることで行います。

## 参加

`bin/sv_join.py --union-circle` は、レイドのゲストがレイドに参加するのと同じ方法で、コンソールがホストしているサークルに参加します
(`pokeldn.sv.circle`)。席を確保し、自身の識別レコードを送信し、0x7C ポート 1 上のホストのチャネル一覧を写し、
`--hold` で席を保持します。既定では `--seconds` の全体です。ロビーのメッセージは送らず、コンソールが退出しても、
ホストの役割を引き継ぎません。ホストのフィールドが表示されると、プレイヤーをそこに配置します (`circle.Member`、[フィールド](#the-field))。
利用者が追う内容を表示します。
`--verbose-circle` を付けると、送信するサークルのメッセージとエリア検索の各ステップを追加で表示します。
エリア検索の各ステップは、とにかく `--capture` ファイルに保存されます。

    ./.venv/bin/python bin/sv_join.py --union-circle --code 3707 --hold 540 --capture circle.jsonl

リンクコードでサークルをホストする市販版のスカーレット 4.0.0 は、シーン 5 と、最大 4 人の参加者を通知します。
また、交換のアプリケーションデータとして、パスワードとゲームバイト内のコード、およびその長さ (+0x24) を通知します。
ゲームバイトには、+0x21 にも `aa 08 3e` が入っています。検索中のコンソールは、これをゼロのままにします。

ゲストは、リンク交換やテラレイドのホストと同じ方法で席に座ります。参加応答、ステーション一覧、
チャネル一覧 (キーは 0x007B、0x0132、0x0232、0x0332)、両方のストリームの開始、時計の応答、そして識別レコードです。
その後ゲストは、ホストのプレイヤーがサークルを開始するまで待ちます。

## サークルの開始

開始時にホストは、メンバー数を数える広告とともに Net 0x50 を送信し、種類 7 のお知らせを
0x80 ポート 2 で送信します (各メンバーを受け入れる種類 9 も含む)。また、サークルのメッセージを 0x80
ポート 0 で送信します。

サークルのメッセージは、Lua のネットメッセージです。各メッセージは、ゲームのメッセージ (ハンドラーキー、種類、ステップ、
続けてシリアライザーのヘッダー。[テラレイド](sv_raid.md#the-lobby) を参照) で、キー 0x0132 の下にあり、その種類が
Lua のメッセージ ID です。レイドの「読み込み中」と「読み込み完了」(0x0132、種類 0x6E と 0x73) は、同じ受信処理のメッセージ 110
と 115 です。ペイロードの一部は FlatBuffer のテーブルで、それ以外は固定の構造体です。104 と
106 は LZ4 で圧縮されています (シリアライザーの圧縮 2)。

| メッセージ | 送信元 | ペイロード | `TeamCircleUI` の処理 |
|---|---|---|---|
| 100 | 開始時のホスト | 1 つの u32 のテーブル。常に 12345678 | 開始の音。ゲストの開始フラグ |
| 101 | すべてのステーション (ホストは 100 の直後、メンバーはホストの 100 に応じて) | 32 バイト。ステーションの立っている場所 (フィールド ID、3 つのポケモンセンターのフラグ) | ステーションごと |
| 103 | すべてのステーション | 1 つの u32 のテーブル。同期ポイントの ID | 1 と 2 は UI へ (スタートデモの読み込みと終了)、それ以外の ID は同期オブジェクトへ |
| 111 | ホスト | 5916 バイト。4 バイトのゼロに続けて、テーブルのベクター 2 つ (30 と 10) の FlatBuffer | フラグのみ。内容はネイティブ側で読まれる |
| 104 | ホスト | テーブル。ゲーム内時間、実時間とそれぞれの経過秒数 (浮動小数点数)、天候のシード (u64)、抽選の長さ、現在と次の天候の {type, duration} の組 | 時計と天候。ゲーム時間マネージャーと `WeatherManager.Sync` へ |
| 102 | ホスト | 2 つの u32。メンバーがワープする飛行地点 | ワープ |
| 106 | すべてのステーション | 6 バイトのスロット 300 個 (テラレイドのクリスタル)。空のスロットは `ffffffff0000` | ステーションごと |

ホストは、これらを表の順に送信しました。101 の後にキー 0x0048 のメッセージを 3 つ続け、
開始から 2 秒以内に送りました。

すべてのステーションは同じ開始処理を実行します。同期ポイント 2215 に到達し、すべてのステーションの
101 を待ち、自身の 106 を送信し、他のすべてのステーションの 106 を待ちます (`IsGemInfo`)。フィールドが表示されると、
スタートデモが始まります。ID 1 と 2 の 103 を、同じ方法で待ちます。同期ポイントは、すべてのメンバーがその ID の 103 を送信したときに到達します
(`CEEE8D2836ABEDE23`)。メンバーが 101 と 103 を送っていないホストは、
2215 のための自身の 103 の後には何も送信しません。

市販版のコンソールは、1395 バイトより長いメッセージを断片に分割します。
分割されていない 1818 バイトの 106 (300 スロット、非圧縮) は、確認応答されないまま残されていました。
106 は、ホスト自身のものと同じく LZ4 で圧縮されます。

すべての 106 が揃うと、ホストは 102 の飛行地点へワープし、115 (1, 0) を送信します。

## フィールド

その後、ホストのプレイヤーがフィールドに入ります。ホストは、さらに 14 個のチャネルキー (下位バイトは 0x1E から 0x2A、一部はサブチャネル 0 と 1) を開き、
各メンバーに 0x7C ポート 1 上で zlib 圧縮された更新を送ります。市販版のメンバーは、同じ方法で同じ更新を返します。
ホストは、ボディのないキー 0x0024 の種類 1、ステップ 1 を送り、
その後は 0x80 ポート 0 と信頼性のないプロトコルで、プレイヤーを送信し続けます。
- **アニメーションの状態:** キー 0x001E の信頼性のある送信 (種類 5、状態の名前。例:
  `Top/pc_field/move/defaultwait01`)。3 から 7 秒ごと。
- **トランスフォーム:** 信頼性のないプロトコル 0x68 で送信します。これは 0x80 と同じくメッシュアドレスで指定されます。キー
  0x011E (種類 4、38 バイトの浮動小数点数) で毎秒約 20 回送られ、種類 6 と 7 は 1 回ずつ送られます。

スタートデモを組み立てる前に、ホストは (`F9FFADFE613D572B7`)、他のすべてのステーションのプレイヤーオブジェクトがそのフィールド上に存在するまで待ちます。
プレイヤーを送らないメンバーは、黒い「通信中」画面のままになります。ホストは、メンバーを `playables.Player` オブジェクトとして
ネイティブモジュール `c2A8846F6` を通じて生成します。
(その `f6BD530B6` は、待機の直前に実行されます)。

プレイヤーオブジェクトは、フィールドのキーの後に、0x7C ポート 0 で各メンバーとホストの間をやり取りされます。

| キー | メッセージ | 内容 |
|---|---|---|
| 0x001F | ID (u16)、種類 (u16) | コンソールが自身のオブジェクトを 1 つ宣言します |
| 0x001E | 種類 0、0、ID (u16) | コンソールが、相手の宣言したオブジェクトを要求します |
| 0x001E | 種類 1、2 か 3、0、ID (u16)、状態 | 応答。オブジェクトの状態で、宣言の中での位置により種類 1、2、3 のいずれか |

各コンソールは 4 つのオブジェクトを宣言します。市販版のメンバーは種類 0、2、3、10 を宣言し、ホストは
0、1、3、10 を宣言しました。そのため、2 つ目の種類は変わりますが、状態の種類 (2) は変わりません。ID は
ステーションのインデックスから 4 ずつ増えます。ステーション 1 の ID は 0x01、0x05、0x09、0x0D で、2 台のホストの ID は 0x20 から 0x2C、
0x30 から 0x3C でした。コンソールは、相手が宣言したすべてのオブジェクトを要求します。ホストは、メンバーのものを
順番に、最後に宣言されたものから要求します。種類 10 のオブジェクトへの要求には、誰も応答しません。状態は 70 バイト (種類 2)、
または 214 バイト (種類 1 と 3) で、zlib で圧縮されています。それぞれがハンドル、スケール、回転、位置を持ちます。
種類 1 はプレイヤーで、FlatBuffer も持ちます。ホストは、メンバーの種類 1 の応答の 0.5 秒後にデモを開始します。
種類 2 の応答の有無は関係ありません。

続けてメンバーは、キー 0x0025 の u64 ID の一覧についてホストに尋ね、ホストは各一覧に
フラグを付けて応答します ([フィールドでの遭遇](#overworld-encounters))。

キー 0x0048 (BBQ モジュールのもの、[ネイティブモジュール](#native-modules)) は、ホストの最初のチャネル一覧にあります。
ポート 2 のお知らせの前後に、ホストは種類 1 のステップ 1、ボディのない kind 4 (`480004`)、
そして種類 1 のステップ 2 を送ります。どちらのステップにも、ホストの状態レコード ([BBQ の状態
レコード](#the-bbq-status-record)) が含まれます。

`circle.Member` は次の処理を行います。
- ホストの 100 には、ホスト自身の 101 のコピーで応答します。これにより、ゲストのプレイヤーは
  ホストのプレイヤーと同じ位置に立ちます。
- ホストが送るすべての 103 にエコーで応答します。
- ホストの 106 には、300 個の空のスロット (LZ4 圧縮) で応答します。クリスタルのない世界です。
- ホストが送るそれぞれの 110 と 115 のコピーを、自身のものとして送信します。ホストのフィールドに従います。
- `sv_join` がフィールドのキーを返信すると、ステーション 1 の 4 つのオブジェクトを宣言し、
  ホストの各オブジェクトを要求します。ホストからの要求には、ホスト自身のその種類のオブジェクトの状態を、
  ゲストの ID で応答します。これによりゲストのプレイヤーは、ホストのプレイヤーと同じように立ちます。

`--follow-host` を付けると、ゲストのプレイヤーもホストのプレイヤーとともに動きます。ホストの 0x68 上の各フレームと、
キー 0x001E 上のオブジェクトのメッセージは、宣言の同じ位置にあるゲストのオブジェクトとして送信されます。
乗り物の添付 (種類 6) は、ゲスト自身の乗り物を指定します。ホストの変換は毎秒約 27 回、最大 0.3 秒の間隔で
ゲストに届きます。市販版のコンソールは約 60 回送るため、ゲストの送信は独自の 60 Hz のクロックに従います。
その時点の 0.3 秒前にホストがいた位置を、その瞬間の前後の 2 つのフレームの間から使います。
ゲストのプレイヤーは、ホストが 5 m 以内にいる間はその場に留まり、それより離れると 5 m まで引き寄せられ、
常にホストの方を向きます。ホストのアニメーション (種類 5) は、その瞬間のフレームとともに送信されます。
その移動ブレンド (番号 1 と 2。1 は速度、0 は立ち止まりから 1.5 の走りまで) は、ホストに対するゲストの歩調で拡大縮小されます。
そのため、ホストがリードの範囲内を走り回る間、ゲストのプレイヤーは
立ち止まったままになります。

`--circle-task` を付けると、タスクが完了した時点でゲストのプレイヤーはサークルを離れ、実行が終了します。
- `snacksworth` は、最初の状態レコードからホストのソロとチームの合計を読みます。スタートデモの終了時 (ID 2 の 103) から、
  チームの合計が 12 に足りないチームのクリアを 1 秒に 1 回送ります。次に、ソロの合計が 130 になるまで、
  ホストのクエストを完了させたと報告します ([ホストのクエストに対するメンバーの進行](#a-members-progress-on-the-hosts-quests))。
  その後、チームの合計にまだ不足がある間は、さらにチームのクリアを 1 回送ります ([スナックスワース](#snacksworth))。
  各チームのクリアは、ゲームが抽選するチームのクエストのものです。
  (`circle.TEAM_QUESTS`、各クエストと BP を確率とともに)。
  そのクエストの BP を支払います。進行は、ホストの合計が上がるたびに表示され、
  20 回連続で上がらなかったときに停止します。
- `bp` は、スタートデモの終了から 1 秒後に、クエスト 29 のノーマルのクリアを 1 回送ります。これは
  `--bbq-clear` の BP (1 から 9,999,999) を支払います。

各クリアは、BP、ゲストのステーション ID、ゲストの状態レコードを含むメッセージ 3 です。

市販版のホストは、この方法で送られたすべてのクリア (ノーマルもチームも) を、その前にゲストからのメッセージ 1 なしで支払いました。
通知と BP は、ホストのプレイヤーが BP のサイドバーを閉じると表示されます。チームのクリア 1 回だけでも、
それがチームのクエストでなくても、スナックスワースが次のチームルートの伝説のポケモンを解放するのに十分でした
([スナックスワース](#snacksworth))。
ホストがブルーベリー学園の外にいる場合も同様でした。

## フィールドでの遭遇

サークル内のすべてのコンソールは、自身のゲームバージョンに応じて、自身のプレイヤーの周囲に野生のポケモンを出現させ、
それぞれを他のコンソールに送信します。エリアゼロにいるスカーレットのホストとバイオレットのメンバーは、
それぞれ自身のバージョンのパラドックスポケモンを出現させました。ホストはスカーレット専用の種族 (開発用 ID 982)、
メンバーはバイオレット専用の種族 (992) です。メンバーは、もう一方のバージョンの限定ポケモンを捕まえることができます。
それは、もう一方のコンソールがそれらを出現させ、共有しているからです。バージョンは交換されず、
ホストはここで特別な役割を持ちません。

共有されるポケモンは、0x80 ポート 0 と信頼性のないプロトコルで送られ、所有者が放送します。
個別の要求と、その拒否だけは、0x7c ポート 0 上で 1 つのステーションに送られます。

| キー | メッセージ | 内容 |
|---|---|---|
| 0x0026 | 種類 1、96 バイトのレコード (バイト列) | 所有者が出現させた実体 (ステーション、n) |
| 0x0026 | 種類 2、(ステーション、n) | 実体がなくなった |
| 0x0026 | 種類 5、((ステーション、n)、(ステーション、n)) | コンソールが、要求側自身の ID で戦うための実体を所有者に要求する。0x7c ポート 0 上で所有者だけに送られる |
| 0x0026 | 種類 6、同じ組 | 所有者が拒否する。要求側に返される |
| 0x0026 | 種類 7、同じ組 | 実体は今、2 つ目の ID のステーションに属し、そのステーションが戦う。その実体の種類 2 の 15 秒前に 1 つ届いた |
| 0x0126 | 種類 3、(ステーション、n)、(浮動小数点数、0.0、0.0、0、0 か 1) | 実体の状態。0.2 秒ごと (メンバー) から 0.5 秒ごと (ホスト)。最後の要素がステータス |
| 0x011E | 0x68 上の種類 4、オブジェクト ID ごと | プレイヤーと同様の、実体の変換 |

実体のオブジェクト ID は、ステーション + 4n で、そのレコードの先頭の u16 です。ホストの (0, 37) は 0x94、
メンバーの (1, 159) は 0x27D です。削除はまとめて届き、各コンソールはプレイヤーが動くたびに新しい実体を出現させ続けました。
コンソールは、自身の近くにプレイヤーがいるメンバーにだけ実体を共有します。
ホストは、そのプレイヤーがホストに追従するまで、pokeldn のゲストには何も送りませんでした。
どの ID も符号なし整数の組です。ディスパッチャー (`0x1dbd4b0`、
ジャンプテーブル `0x3c5b9a0`) は、符号付きタグを読みません。

コンソールは、他のコンソールの実体を未確定 (状態 1) として登録し、状態が状態 0 を指定するまで、その実体との戦闘を拒否します
(`BattleStartWait`)。確定した実体に近づくと、"!" を表示し、
所有者に尋ねます (`0x1972664`)。実体には自身の新しい ID を与え、その組と
コールバックを保存します。マネージャーの更新 (`0x1593884`) は、
種類 5 を、実体のレコードを送ったステーションに送信します。
その後、エンカウント (`GameEventEncount`、NetInitWait) は、タイムアウトなしで、
同じ組を指定した所有者の応答を待ちます (`0x1dbdd70`)。所有者は、実体が自身のものであり、
他のコンソールが保持していない場合にその実体を引き渡し (`0x1dbdc20`、続けて `0x15934c8` での更新の放送)、そうでなければ拒否します (`0x1593914`)。
引き渡しの際、すべてのコンソールは実体の名前を要求側の ID に変え (`0x1595a1c`)、交戦中とマークします。
要求側はそれを自身のものとして登録し、戦闘を開始します。
自身の実体と戦うとき、コンソールは同じ組を 2 回指定した種類 7 を放送します。

レコードは 96 バイトです。`EncountManager.UpdateNetworkSpawn` は、そのフィールドを
Lua モジュール `c4CF1D719` が束縛するゲッター (ネイティブの `0x90e344` から `0x90e588`) を通じて
`pml.pokepara.InitialSpec` にコピーし、続けてリボン、テラタイプ、Alcremie の装飾を
ポケモン自身に設定します。取得したすべてのレコードは、この配置に一致します。

| オフセット | ビット | フィールド |
|---|---|---|
| 0x00 | u16 | オブジェクト ID |
| 0x04 | u64 のビット 0-10 | 開発用の種族 |
| | 11-22 | 持ち物 |
| | 23-30 | スケール |
| | 31 | 性別 (1 がメス) |
| | 32 | 色違い。設定されていると出現は色違い |
| | 33-37 | フォルム |
| | 38-44 | レベル |
| | 45-52 | リボン (マーク)。0 でない場合に適用 |
| | 53-57 | 性格 |
| | 58-62 | テラタイプ |
| 0x0C | u32 のビット 0-3 | Alcremie の装飾 |
| | 8-27 | 個体値 HP、攻撃、防御、素早さ (各 5 ビット) |
| 0x10 | u16 のビット 0-9 | 個体値 特攻、特防 |
| | 10-11 | 特性スロット |
| 0x24 | s32 | -1。確認できたメタモン (Ditto) とゾロア (Zorua) だけでは 0 |
| 0x30 | 浮動小数点数 3 つ | 位置 |
| 0x40 | 浮動小数点数 4 つ | 回転。すべてのサンプルで同一 |

そのほかのバイトは 0 です。ただし、市販版のレコードは 0x02、0x28、0x54 の隙間に古いメモリを保持しています。レコードの前に、
所有者は 0x68 上で実体のフレームを送信します。種類 6 は親なしで、
(`00000000 00000000 0000003f 0000003f 00000000 0000003f 0000003f`)、種類 7 はスケール 1.0 です。
`circle.Spawner` (`sv_join --spawn SPECIES:LEVEL`、`--spawn-shiny`、`--spawn-tera`、
その他の `--spawn-*` フィールド) は、ゲスト自身の出現を同じ方法で、ホストのプレイヤーの周囲に送信し、
戦うことを要求したコンソールにそれぞれを渡します。
市販版のホストは、これらを戦って捕まえました (下記の「作成された遭遇」)。

`UpdateNetworkSpawn` は、ポケモンをレコードのみから組み立てます。種族、フォルム、持ち物、スケール、
性別、性格、レベル、6 つの個体値、特性スロットは `InitialSpec` に入ります。色違いのビットは、
設定されていると、そのレアリティ値 (`+0x18`) を `0x2ffffffff` にし、クリアされていると `0x1ffffffff` にします。そのため、所有者のビットがどちらでも決まります。
続けて、マーク (0 でない場合)、テラタイプ、Alcremie の装飾が、
作成されるポケモン (`c113335A8.f7AC1FE6B`) に設定されます。レコードには、技、PID、暗号化の定数は含まれません。
そのうえで捕獲すると、野生の捕獲と同様に、捕まえたトレーナー、ボール、場所、日付、
レベルが追加されます。

そのため、ゲームは任意のレコードを受け入れます。しかし PKHeX (Core 26.8.26) は、
捕獲した場所での野生の遭遇として判定します。

| フィールド | PKHeX が受け入れる条件 |
|---|---|
| 種族、フォルム、レベル | 捕獲した場所にある、その種族とフォルムのスカーレット / バイオレットの野生スロットで、そのレベルを含むレベル範囲を持つもの。Rayquaza のような色違い固定または固定出現のみの種族は決して受け入れられない |
| テラタイプ | その種族自身のタイプのいずれか。配布による大量発生がその場所の種族を対象にしている場合を除く |
| 性別 | 種族の性比の範囲内 |
| マーク | Mightiest Mark や Titan Mark ではない。Jumbo はスケール 255 のときだけ、Mini はスケール 0 のときだけ。天候マークは、スロットがその天候を指定する場合のみ |
| 色違い、性格、個体値、特性スロット (隠れ特性も)、スケール、持ち物 | 任意 |

PKHeX は、すべてのスカーレット / バイオレットの野生スロットを両方のバージョンの下に一覧にするため、サークルを通じて捕まえたもう一方のバージョンの限定ポケモンも合法です。
保存されたポケモンは捕獲時刻を持たないため、時間帯スロットによる制限を受けません。
レコードの種族は内部のインデックスです (`gen9.national` は全国図鑑番号を与えます)。
ホストが出現させて捕獲したすべての例は、スロットの種族、フォルム、レベル範囲に合います。
Scatterbug のランダムなパターンは、PKHeX のランダムフォルムの規則を通じて確認されます。

フィールドのそのほかの内容は次のとおりです。
- **ホストの大量発生:** キー 0x0029 の種類 1。フィールドが開くときに、大量発生ごとに 1 回放送されます。
- **ホスト自身の状態:** キー 0x0024 の種類 1 と、キー 0x002A の種類 3 から 5。いくつかの小さな整数です。
- **メンバーの ID 問い合わせ:** キー 0x0025。メンバーからホストへのみ。

メンバーは、自身の MAC をアドレス 2 にして、放送を自分で送信します。
そのため、1 台のコンソールの MAC で絞り込んだスニッフィングには、そのコンソールの放送と 2 台の間のユニキャストだけが残ります。

両方のゲームは、マップごとに 1 つのエンカウントテーブル (`world/data/encount/pokedata/pokedata*_array.bin`) を出荷しており、
両方のバージョンの行を持ちます。各行にはバージョンのテーブル (フィールド 28: スカーレット、バイオレット) があり、
指定されたバージョンでのみ抽選されます。

| マップ | 両方 | スカーレットのみ | バイオレットのみ |
|---|---|---|---|
| パルデア | 315 | 20: Larvitar、Deino、Drifloon、Stunky、Skrelp、Oranguru、Stonjourner、古代のパラドックスポケモン... | 20: Bagon、Dreepy、Misdreavus、Gulpin、Clauncher、Passimian、Eiscue、未来のパラドックスポケモン... |
| キタカミ | 146 | 4: Gligar... | 4: Aipom、Morpeko... |
| ブルーベリー | 160 | 4: Vulpix、Cranidos... | 4: Sandshrew、Shieldon... |

大量発生のメッセージは組です。中心 (浮動小数点数 3 つ)、その近くの 2 つ目の点、種族、
0、フォルム、0、90 から 110 の数、マップ (0 パルデア、1 キタカミ、2 ブルーベリー)、そして 0 です。あるホストの 14 件すべての大量発生は、
ゲームの大量発生ポイント (`world/data/encount/point_data/
outbreak_point_data`) の中心を使っていました。メンバーは大量発生を受け取るだけで、何も返しません。

キー 0x0025 は、メンバーからホストへの定期的な問い合わせです。種類 1 は ID の一覧を送り、種類 3 は各 ID に
0 か 1 のフラグ (`((id,), flag)`) で応答し、種類 2 はメンバーが手放す ID の一覧を送ります。ほとんどはホストが 1 と答えたものです。
ID は、遭遇や地点のファイルには含まれません。ID の上位 5 ビットはカテゴリで、
メンバーは同じカテゴリ (1、2、3、4、5、9、10、13、16) を約 9 秒ごとに巡回し、それぞれ数個から 250 個の ID について問い合わせます。
フィールドが開いた直後、ホストはすべての ID に 1 で応答します。その後は約半分を 0 で応答します。
ホストがメンバーに問い合わせることはありません。

## 作成された遭遇

`sv_join --spawn SPECIES:LEVEL` は、メンバーとしてサークルに参加し、ユーザーが作成したポケモンの出現を 3 つ、
ホストのプレイヤーの周囲に保ちます。`--follow-host` を付けると、ゲストのプレイヤーはホストのプレイヤーに追従します。
`--spawn-*` フラグは、レコードが持つ内容を指定します。フォルム、色違い、テラタイプ、性格、性別、特性スロット、
サイズ、持ち物、個体値です。指定されなかったものは、ホストの野生のポケモンと同じ方法で抽選されます。サイズ、
性格、各個体値はランダムに、特性スロットは 0 か 1、持ち物はなしです。各出現は、ホストのプレイヤーから 15 から 25 m の位置に来ます。
ホストが戦ったもの (その要求に応じて引き渡されたもの)、削除されたもの (それを指定する種類 2)、または 50 m 以上離れたものは解放され、
別のものがホストの近くに来ます。キャプチャでは、ホストがメンバーの出現に対して種類 2 を送ったことはなく、
戦うための要求だけでした。

`--spawn-legal` を付けると、PKHeX が判定します。PKHeX のスカーレット / バイオレットの野生スロットは、
そこで捕まえた場所を指定します。PKHeX ヘルパーの `wild_areas` コマンドは、スロットの抽選されたフォルム
(Scatterbug のパターン) を任意のフォルムとして、場所ごとに一覧にします。`wild_legal` コマンドは、各場所のスロットから
捕まえた作成済みの出現を、その種族、フォルム、レベルで、テラタイプごとに 1 回ずつ組み立て、
それぞれについて PKHeX の合法性解析を実行します。レコードの性別ビットは、2 つの性別を持つ種族にのみ数えられ、
それ以外の種族は、その種族の持つ性別を取ります。どの場所でも PKHeX が受け入れない出現があると、実行は停止します。
パルデアで、種族自身のタイプのすべてをスロットが与える場合、PKHeX は他の場所で任意のテラタイプを受け入れることがあります
(キタカミでは、そこの大量発生による Pikachu が該当します)。
そのため、テラタイプを決めるのは種族ではなく解析です。

出現は、その後ホストのエリア (`wild.Locator`) を待ちます。ホストのコンソールが共有する野生のポケモン (キー 0x0026 の種類 1、
ゲストのプレイヤーが近くにいるとき) のそれぞれは、場所を、その種族、フォルム、レベルのスロットを持つものに絞り込みます。
残っているすべての場所が、PKHeX がその出現を受け入れる場所になると、エリアが見つかったとみなされます。必ずしも 1 つである必要はありません。
その後、出現が来て、ホストがエリアを見つけた時点の位置から 50 m 以上移動すると、すべてが消えます。その場合、発見は最初からやり直しになります。それより前でも、
ホストが重み付けした出現から 100 m 以上離れたとき、
または残っている場所のどれにも含まれない出現から離れたとき、発見は最初からやり直しになります。
どの野生のスロットにも含まれない出現 (レイドやイベントのもの) は除外されます。

エリアゼロ (およびその入口へ降りる途中) では、ホストのコンソールは自身のプレイヤーの変換を送信しません。最後に読んだ変換は (0, 0, -2) です。
それでもプレイヤーの周囲に出現させた野生のポケモンは共有します。外では、それらはプレイヤーから 8 から 46 m の位置にありました。
2 秒間変換がない場合、ホストは直近 30 秒の 6 つの最も新しい出現の中央に置かれます。
外では、そのような推定 10 回のうち 9 回が、ホストのプレイヤーから 50 m 以内に収まりました。
出現はその推定の周囲に来て、留まります。その間に出現がない場合、ホストのいる位置は不明で、
どれか 1 つが来るまで新しい出現は来ません。原点から 10 m 以内の変換 (乗り物に乗っている、または降ろされた) では、
ホストの位置は決まりません。

実行中は、検索の状況をステータスカード (ID `zone` の `[panel]` 行。変化したときに表示) として表示します。アプリはこれをツールのオプションの上に表示します。
検索の状況とは、まだ可能なエリア、出現を許すエリアの数、重み付けされた野生のポケモンの数です。
残っているエリアのどれも出現を許さない場合、カードには行くべきエリアが示されます。
ホストが離れすぎた後は、検索が最初からやり直された理由が示されます。見つかった後は、
ホストがエリア発見時の位置からどれだけ離れているかが示されます。ホストの位置が出現から推定されている場合や、不明な場合も示されます。
エリアが見つかるまでは、ピクニックを開始できる場所を提案します。
ピクニックを片付けると、プレイヤーの周囲に野生のポケモンが新たに出現し、
エリアの絞り込みが速くなります。
