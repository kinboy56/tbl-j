# コンソールでのコード実行

ふしぎなおくりものクライアントは、送られてきたコードを 2 つのインタプリタで実行する。`CLI_RUN_MEVENT_SCRIPT`（オペコード 15）はバイト列を Mystery Event VM に渡し、`CLI_RUN_BUFFER_SCRIPT`（オペコード 21）は CPU に渡す。
どちらもグリッチ、準備したセーブデータ、特別な設定を必要としない。コンソールはふしぎなおくりもののメニューに留まったままである。

このページのアドレスは、フランス語版ファイアレッド（カートリッジ BPRF、ソフトウェアバージョン 0x0A）のものである。リーフグリーンのアドレスは [リーフグリーン](frlg_leafgreen.md) に、テーブルは [ROM マップ](frlg_rom_map.md) にある。

# Mystery Event VM

独立したインタプリタ [src/mystery_event_script.c] で、専用の 17 コマンドのテーブル [data/mystery_event_script_cmd_table.s] を持つ。ふしぎなカードの配信スクリプトがコンパイルされるフィールドスクリプト VM とは別物である。`pokeldn/frlg/rom/mystery_event.py` が全コマンドをアセンブルする（`MysteryEventScript.blob()` がデータを保持し、アセンブラがポインタを解決する）。全オペコードは実機で検証済みである。

## `checkcompat` は省略できる

`checkcompat` はすべての公式スクリプトを開き、言語とバージョンのマスクを検査する（デコンプの `LANGUAGE_MASK` は英語）。スクリプトはこれを省略できる:

```c
bool32 RunMysteryEventScriptCommand(struct ScriptContext *ctx)
{
    if (RunScriptCommand(ctx) && ctx->data[3])   // data[3] is set only by checkcompat
        return TRUE;
    return FALSE;
}
...
while (MEventScript_Run(&ret));
```

`RunScriptCommand` [script.c:107] は 1 回の呼び出しの中で、コマンドが TRUE を返すまでループする。`checkcompat` がないと `data[3]` は 0 のままなので、スクリプトは最初の TRUE を返すコマンド（通常は `end`）まで実行され、外側の `while` が止まる。マスクは一切評価されない。ポインタは `operand - ctx->data[1] + ctx->data[0]` で再配置される。`data[1]` は 0（`checkcompat` だけが設定する）、`data[0]` はコンソールの 1024 バイトの `client->recvBuffer` である。つまり N のオペランドは、送信されたデータの先頭から N バイト目を指す。`checkcompat` は、アセンブラがその後ろにコードを置くことを許す唯一のコマンドである。

## 戻り値のチャネル

`MEventScript_Run` はステータスを `client->param` に書き込み [mystery_event_script.c:75]、`CLI_LOAD_TOSS_RESPONSE` がそれを `MG_LINKID_RESPONSE` に読み込む [mystery_gift_client.c:204]。次の 4 つのクライアントコマンドは、スクリプトが選んだ u32 を返す:

    CLI_RECV MG_LINKID_RAM_SCRIPT
    CLI_RUN_MEVENT_SCRIPT
    CLI_LOAD_TOSS_RESPONSE
    CLI_SEND_LOADED

`setstatus` は任意の値を設定できる。標準のステータスは次のとおり:

| ステータス | 意味 |
|---|---|
| 0 | どのコマンドも設定しなかった |
| 1 | `setenigmaberry` がきのみを検証できなかった、または `checksum`/`crc` が一致しなかった |
| 2 | 成功。仕事を完了したオペコードはすべてこれを設定する |
| 3 | `SetIncompatible`、または `givepokemon` で手持ちがいっぱいだった |

`CLI_COPY_RECV_IF` と `CLI_COPY_RECV_IF_N` は、このステータスでクライアントスクリプトを分岐できる [mystery_gift_client.c:170]（未使用）。

メニューは結果を `CLI_RETURN` から表示する [`GetClientResultMessage`, mystery_gift_menu.c:884] ので、ここでは `setmsg` は見えない。成功メッセージだけが `MG_STATE_SAVE_LOAD_GIFT` [:1379] に届き、それがないとイベントの書き込みはリセット時に失われる。そのため `CLIENT_SCRIPT_MEVENT_DONE` は、カードがなくても `CLI_MSG_CARD_RECEIVED` を返す。もう 1 つの成功の終了経路である `CLI_MSG_BUFFER_SUCCESS` (13) は、`CLI_COPY_MSG` が押し込んだ 64 バイトを表示する。

### プローブスクリプト

`--gift mystery-event-probe` は無害である。`givenationaldex` は全国図鑑が有効になった後は何もせず、`checksum` は読み取るだけである。

    givenationaldex; setstatus 42; checksum 1026, 16, 31

| ステータス | 証明できること |
|---|---|
| 42 | コマンドの連鎖が最後まで実行され、ポインタのオペランドが送信バッファへのオフセットである |
| 1 | 連鎖は実行されたが、再配置されたポインタがプローブのバイト列に届かなかった |
| 2 | `givenationaldex` は実行されたが、その後は何も実行されなかった |
| 0 | VM には入ったが、どのコマンドも実行されなかった |
| なし | VM ではなく、クライアントスクリプトの形が間違っている |

`checksum` は終端のコマンドで、一致した場合は先のステータスを維持する。実機の FireRed では 42 が返る。

## `givepokemon`

`pokeldn/frlg/save/mevent_pokemon.py` がペイロードを作る。内容は 100 バイトの暗号化された手持ちポケモンと、続く 34 バイトの `struct Mail` で、コンソールは `pointer + sizeof(struct Pokemon)` の位置からこれを読む。`--gift mystery-event-celebi` が 1 つ同梱している。フィールドスクリプトの `givemon` と異なり、こちらは次のとおり:

- メールを付ける。`ItemIsMail` がゲートするので、持たせるアイテムは 12 種のメールアイテムのいずれかでなければならない [mail_data.c:167]。`GiveMailToMon2` は構造体全体（ワード、送信者の名前、トレーナー ID、種族、アイテム）を `gSaveBlock1Ptr->mail` にコピーする [:100];
- 全国図鑑の番号に `FLAG_SET_SEEN` と `FLAG_SET_CAUGHT` を立てる;
- ふしぎなおくりもののメニューに着地する。メニューを閉じたとき、ポケモンは手持ちにいる。

ステータス 2 は成功、3 は手持ちがいっぱいで何も書かれなかったことを表す。その後ろに `setstatus` を置いてはならない。

ビルダーが強制する落とし穴:

- ポケモンの `mail` バイトは `MAIL_NONE`（0xFF）でなければならない。0 はメールスロット 0 で、実際のメールとして読まれてしまう;
- `personality == otId` は暗号化の鍵を 0 にするので、そのポケモンはシャッフルされていてもいなくても検証を通り、シャッフルされていない方が送られてしまうことがある;
- 手持ちの末尾は導出される。末尾がゼロだとレベル 0 として読み戻される;
- 持たせるアイテムとメールの `itemId` は一致しなければならない。`GiveMailToMon2` は、メールから持たせるアイテムを設定する。

## `initramscript`

`initramscript 3, 0, 2` は、グループ 3、マップ 0、オブジェクト 2 にフィールドスクリプトを紐づける。そのオブジェクトは、マサラタウン南のふとったおじさんである。再起動の後、彼はスクリプトの台詞を、`{PLAYER}` を展開しながら話す。

`CLI_SAVE_RAM_SCRIPT` は `InitRamScript_NoObjectEvent`（MAP_UNDEFINED、オブジェクト 0xFF）を使う [script.c:578]。これを読むのは配達員の `GetSavedRamScriptIfValid` [:554] だけで、有効なふしぎなカードがあるときに限られる。実際の座標は `GetRamScript(gSpecialVar_LastTalked, script)` [:514, field_control_avatar.c:458] に届く。これはオブジェクト自身のスクリプトの代わりにそのスクリプトを実行し、カードは無視する。`gSpecialVar_LastTalked` は、`map.json` の順に 1 から数えたオブジェクトのローカル ID である。

これはふしぎなカードを 1 枚使う（[RAM スクリプトの枠は 1 つだけ](frlg_gift.md#the-one-ram-script-slot)）。次の通常のカードが枠を取り戻すまで、セッションのログには「ふしぎなカードを持っていない」と出る。バインドされている間、オブジェクトは自身のスクリプトを失う。静的な遭遇のオブジェクトにバインドすると、そのスクリプトが遭遇を置き換える。

## 落とし穴

- `setenigmaberry` はアイテム効果を設定できない。`struct ReceivedEnigmaBerry` [berry.c:944] は 1322 バイトで、`Berry2`（28 バイト）、`u8 unk_001C[0x4FA]`、続けて `itemEffect[18]`、`holdEffect`、0x516 の `holdEffectParam` からなり、1024 バイトのバッファを越える。末尾はヒープ上で `recvBuffer` の後ろにあるものになる（`build_enigma_berry_blob`。シミュレータは `read_past_buffer` を報告する）。
- `struct Berry2` の 2 つの ROM 説明ポインタは、カートリッジから読み取り、変更せずに送り返さなければならない。きのみポーチがセーブデータからこれを参照し続けるからである。
- `giveribbon` の index 7..10: `GiveGiftRibbonToParty` [pokemon_size_record.c:193] は `index < 11` を受け付けるが、`sGiftRibbonsMonDataIds` は 7 要素しかなく `u8[8]` にコピーされているため、7..10 では初期化されていないスタックからのフィールド ID で `SetMonData` が呼ばれる。アセンブラは 6 を超える値を拒否する。FRLG にはリボンの UI がなく、リボンは交換の後にだけ表示される。
- 終端のコマンドがないスクリプトは、残りのゼロ埋めされたバッファをオペコードとして解釈してしまう。`assemble()` とサーバーはこれを拒否する。
- `setrecordmixinggift` と `enableresetrtc` はそれぞれ `SetIncompatible` を 1 回呼んで連鎖を止める [mystery_event_script.c:227, :291]。コンポーザーはこれらを拒否する。
- `addrareword` と `setenigmaberry` はゲーム内では見えないので、セーブデータから読み戻す: `additionalPhrases`（SaveBlock1 + 0x2F10、簡単ことばが 1 語増える）と `enigmaBerry`（+0x30EC）。`setenigmaberry` が設定する `VAR_ENIGMA_BERRY_AVAILABLE` は、FRLG の他の場所では読まれない。

## 配線

- `pokeldn/frlg/rom/mystery_event.py`: オペコード、アセンブラ、逆アセンブラ（`describe`）、そしてオフラインクライアントが使うシミュレータ `run()`。
- `pokeldn/frlg/gift/mg_script.py`: `CLIENT_SCRIPT_SAVE_CARD_AND_MEVENT`（カードを持っていないとき: カード、配信スクリプト、イベント）、`CLIENT_SCRIPT_RUN_MEVENT`（カードを持っているとき: イベントだけで、何も放り出さない）、`CLIENT_SCRIPT_MEVENT_DONE`（成功時に共通の末尾）。
- `pokeldn/frlg/gift/mg_server.py`: `SVR_LOAD_MEVENT` と `SVR_READ_MEVENT_STATUS` を使う `SCRIPT_SEND_MYSTERY_EVENT`。ステータスは `server.mevent_status` とホストのログに入る。
- `pokeldn/frlg/gift/gift_composer.py`: `WonderGift.mevent` がアセンブル済みのバイト列を検証する。

# ネイティブ ARM コード

```c
case CLI_RUN_BUFFER_SCRIPT:
    memcpy(gDecompressionBuffer, client->recvBuffer, MG_LINK_BUFFER_SIZE);
    client->funcId = FUNC_RUN_BUFFER;
    ...
static u32 Client_RunBufferScript(struct MysteryGiftClient * client)
{
    u32 (*func)(u32 *, struct SaveBlock2 *, struct SaveBlock1 *) = (void *)gDecompressionBuffer;
    if (func(&client->param, gSaveBlock2Ptr, gSaveBlock1Ptr) == 1)
```

[mystery_gift_client.c:237,276]。どのペイロードも次の 5 つの事実に基づく:

- 送信されたものに関係なく 1024 バイト（`MG_LINK_BUFFER_SIZE`）がコピーされるので、ペイロードは前回の受信の末尾を後ろに抱えて動く。したがって自己完結している必要がある。
- `r0 = &client->param`、`r1 = gSaveBlock2Ptr`、`r2 = gSaveBlock1Ptr`。両方のセーブブロックは読み書き可能である。
- `client->param` は、`CLI_LOAD_TOSS_RESPONSE` が `MG_LINKID_RESPONSE` として返すものである [:204]。
- 1 を返すまで 1 フレームに 1 回呼ばれる。1 を返さないペイロードは、ふしぎなおくりものメニューを抜け出せないまま固まらせる。`memcpy` は `CLI_RUN_BUFFER_SCRIPT` [:239] で 1 回だけ実行されるので、ペイロードはフレームをまたいで状態を保持できる。
- ARM 状態: 呼び出し側は、ワード境界に揃えたアドレスへの `bx` でそこに到達する。

`gDecompressionBuffer` は 0x0201C000 にある（`anchors` で測定）。ペイロードは位置に依存しない。

## ビルド

アプリのふしぎなおくりものビルダーは、同じツールチェーン（`pokeldn/frlg/rom/custom_code.py`）で ARM ソースをアセンブルする。あるいは生の `.bin` を受け取り、送信の前にシミュレートしたコンソール上で実行する。`.pokegift` ファイルには、コンパイル済みの ARM バイト列、カートリッジの対象、応答の設定が入る。梱包と共有の方法は [ふしぎなおくりもののファイル](gifts.md#console-code) に書かれている。

- `asm/*.s`: ペイロードごとに 1 つの ARM ソース。`scripts/gen_buffer_scripts.py` がアセンブルして、コミット済みの `pokeldn/frlg/rom/buffer_payloads.py` に出力する。`arm-none-eabi-as` が入っているとき、`tests/test_buffer_script.py` が再アセンブルして比較する。
- `pokeldn/frlg/rom/buffer_script.py`: レジストリ、検証、`emulate()` / `emulate_repeating`。コンソールの 3 つの引数を使い、GBA のメモリマップ上で unicorn によりペイロードを実行する。異常終了するか 1 を返さないものは、電波に乗ることはない。
- `pokeldn/frlg/gift/mg_script.py`: `CLIENT_SCRIPT_RUN_BUFFER`（受信、実行、戻り値チャネルの読み込み、送信、次のスクリプトの受信）と `CLIENT_SCRIPT_BUFFER_SUCCESS`。
- `pokeldn/frlg/gift/mg_server.py`: `SCRIPT_RUN_BUFFER_SCRIPT`。カードも放り出しの確認もない。持っているふしぎなカードは保持される。
- デコンプから独立に書かれた 2 つのシミュレートしたコンソールは、どちらもフレームごとの再入でペイロードを実行する: `pokeldn/frlg/gift/mg_client.py` と、`tests/test_mystery_gift_flow.py` の `ConsoleClientModel`。

毎回、まずオフラインで確認する:

    ./.venv/bin/python -m pytest tests/test_buffer_script.py -q
    ./.venv/bin/python scratchpad/mg_client_harness.py --buffer-script -v

実機では、コンソールは ふしぎなおくりもの → ふしぎなカード → ともだち で待機し、ホストに参加する。下の実行行では、`HOST` が次のコマンドを表し、
`POKELDN_RADIO=esp32:auto ./.venv/bin/python -u bin/frlg_mg_host.py --live --keys PROD_KEYS --dump-file DUMP.bin`
`IP_HOST` は `./.venv/bin/python -u bin/frlg_mg_host.py --over-ip --dump-file DUMP.bin` を表す。後者は無線もキーもなしに、LAN 越しにエミュレートしたコンソールを提供する。`DUMP.bin` が存在する前にホストを SIGTERM してはならない。`Buffer script dump: N bytes` の数秒後に書き込まれる:

    until ls DUMP.bin >/dev/null 2>&1; do sleep 2; done

## ペイロードを置ける場所

バッファスクリプトはフレームごとに再コピーされるので、自分のイメージに書き込んだものは何も残らない。メニューの後も残るコードは、ゲームが決して書き込まない場所に置く:

    0x0203FC00 .. 0x02040000    1024 bytes, above every symbol the game links

最大サイズの EWRAM シンボルは 0x0203FBAC で終わる（[EWRAM は両ビルドで同じアドレス](frlg_rom_map.md)）。デコンプ由来の名前を使うと（`gHeap` の 114688 バイトは、シンボルテーブルにサイズがない）、これが唯一の未使用の EWRAM 区間で、残りは 3 バイトと 8 バイトのアライメント用の隙間である。

    0x0203F768 .. 0x0203FBAC    1092 bytes, newlib's malloc state

`__malloc_av_` とその後ろの malloc のカウンタに到達するのは、newlib の stdio だけである。stdio を呼ぶのはリリースビルドでは未使用の `AGBPrintf` だけである（pokefirered_switch.elf では、`_malloc_r`、`_calloc_r`、`_free_r` への唯一の `bl` が libc の中にある）。そこに 0xA5 を埋めた領域は、mGBA 上のフランス語版ファイアレッドで、メニュー、移動、野生ポケモンとの戦闘全体を通して残った。GB-Link Team のカードは、再配置したスクリプトをそこに保持している（[frlg_gift.md](frlg_gift.md#gb-link-team-cards)）。
`scratchpad/ewram_symbol.py ADDR LEN` でアドレスを確認する。

ゼロが読めるからといって、アドレスを選んではならない。0x0202B280、0x020185C4、0x0203B0E9 は数十 KB のゼロを読むが、それらはバトルとボックスのバッファ、`gDecompressionBuffer` へ向かう領域、およびアロケーターの管理領域である。0x02012304 は `gHeap` の中にある。0x0202B280 は `gPokemonStorage` の内側にあり、そこへの書き込みは、ボックスのポケモンのチェックサムに当たり、セーブデータがタマゴ（Bad Egg）を保持し続けることがある。

ソフトリセットは EWRAM を 2 回クリアする。`DoSoftReset` は `SoftReset(RESET_ALL & ~RESET_SIO_REGS)` を呼び [main.c:488]（`svc 0x1` の後に `svc 0` [libagbsyscall.s:69]）、その後 `AgbMain` が `RegisterRamReset(RESET_ALL)` を呼ぶ [main.c:134]。0xFF のビット 0 は `RESET_EWRAM` である [include/gba/syscall.h:4,12]。
Switch 版のラッパーもエミュレートしたコンソールを再起動するので、`AgbMain` は 2 回走る。`gIntrTable` と `INTR_VECTOR`（0x03007FFC）は、起動のたびに 2 回クリアされて組み直され、その間にエントリ 1、2、7 が無線の値を取る（毎秒 328000 でサンプリング: 33.3 ms、続いて 2 回目のクリアまで 133.6 ms、その組み直しまで 33.6 ms）。起動では 0x0203B0E8 より上は何も組み直されない。2 回の起動の間に 0x0203FC00..0x02040000 へ書き込むものはない。そこのマーカーは、タイトル画面、再読み込み、メニュー、セーブ、マップ移動、戦闘、PC ボックスをまたいで残り、ソフトリセット（A+B+START+SELECT）でクリアされる。

## フレームごとのフック

`gIntrTable` はフランス語版カートリッジでは 0x03002720 にある。エントリ 4 の V-blank ハンドラーは `VBlankIntr`（0x0800071D）を保持する。これは `InitIntrHandlers` が `gIntrTableTemplate` [main.c:339] から 1 回書き込む 14 個の関数ポインタで、BIOS が `IntrMain` を通して到達する。その `IntrMain` のアドレスは、0x03007FFC のベクターが保持する。エントリ 4 を置き換えると、どのゲーム状態でも毎フレーム、コードが呼ばれるようになる。`gMain.vblankCallback` と `gMain.callback2` は、メニューや戦闘が始まるたびに書き直される。

コンソールの IWRAM では、`IntrMain_Buffer` は 0x03002760（英語版では 0x03002810）、`gSaveBlock1Ptr` は 0x03004228（英語版では 0x030042D8）にある。そのため、これらのアドレスではカートリッジの IWRAM は英語版より 0xB0 低い位置にある。IWRAM は、EWRAM のようにはビルド間で移らない。

| エントリ | カートリッジ | 英語版 | |
|---|---|---|---|
| 0 VCount | 0x08000805 | 0x0800081C | `VCountIntr` |
| 1 Serial | 0x03004B34 | | リンクが繋がっている間の IWRAM のハンドラー |
| 2 Timer3 | 0x08005AE1 | | `Timer3Intr`。別の ROM セグメントと差分 |
| 3 HBlank | 0x080007D5 | 0x080007EC | `HBlankIntr` |
| 4 VBlank | 0x0800071D | 0x08000734 | `VBlankIntr` |
| 5, 6, 8-13 | 0x08000885 | 0x0800089C | `IntrDummy`、8 回 |
| 7 | 0x081E0D35 | | RFU のタイマーハンドラー。`sTimerIntrFunc = gIntrTable + 0x7` [main.c:85] |

無線が動いている間、エントリ 1 と 7 は decomp の予測どおりテンプレートと異なる。エントリ 1 と 2 は、セッションの後もリセットまで無線の値を保つ。ゲームがエントリ 4 を書くのは `InitIntrHandlers` の中だけで、これはソフトリセットでしか再実行されない。

### セッションを越えて残るコード

ステージングエリアにある 20 バイトのスタブで、エントリ 4 に組み込まれ、セッションが閉じた後のすべてのゲーム状態でフレームごとに実行される。`asm/resident/vblank-hook.s`:

```arm
    ldr     r0, .Lcounter
    ldr     r1, [r0]
    add     r1, #1
    str     r1, [r0]
    ldr     r0, .Loriginal
    bx      r0                      @ tail branch: lr still points at intr_return
```

`IntrMain` は SYS モードで、`lr` を `intr_return` にしてハンドラに入り、ハンドラが r0-r3 を破壊することを許す [crt0.s, `jump_intr`]。そのため置き換えられたハンドラは、自身の `bx lr` で戻る。2 つのリテラルは送信の前にパッチされる。

`call-chain` がこれを組み込む: 5 ワードを先に、エントリ 4 を最後に書き、すべての書き込みを読み戻して確かめる。

    read32  [0x03002730]                gIntrTable[4], 0x0800071D
    write32 [0x0203FC00] = 0x68014802   the stub
    write32 [0x0203FC04] = 0x60013101
    write32 [0x0203FC08] = 0x47004801
    write32 [0x0203FC0C] = 0x0203FC40   the counter's address
    write32 [0x0203FC10] = 0x0800071D   the handler being replaced
    write32 [0x03002730] = 0x0203FC01   the hook, THUMB bit set
    read32  [0x0203FC40]                the counter

フックはすべてのゲーム状態でフレームごとに 1 回実行される。19995 フレームの間に、メニュー、タイトル画面、フィールド、手持ちメニュー、野生ポケモンとの戦闘、ゲーム内の再起動をまたいで、毎秒 59.0 から 63.3 回の呼び出しを数えた。ソフトリセットで終わる。`InitIntrHandlers` がエントリ 4 を書き直す [main.c:339]（`gIntrTable[4]` はまず 0 になり、続いて 0x0800071D になる）。ふしぎなおくりものは、EWRAM をクリアする起動の後でしか到達できないので、新しいセッションなしで存在しなければならないペイロードは、インストーラーをセーブデータに入れておく必要がある。

### リセット後の再武装

`--gift resident-hook` は、ふしぎなカードを送る。そのふしぎなできごとのスクリプトは `initramscript` で、プレイヤーの母親にフィールドスクリプトを紐づける。このバインドはセーブデータに残り、電源の入れ直しを生き延びる（[RAM スクリプトの枠は 1 つだけ](frlg_gift.md#the-one-ram-script-slot)）。どの起動の後でも彼女に話しかければ、リンクもホストもなしにフックが組み込まれる。

`asm/field/install-vblank-hook.s`（68 バイト）は、`setptr` で 1 回あたり 6 スクリプトバイトずつステージングし、`callnative` で実行する。RAM スクリプトの本体が持つ 995 バイトのうち 418 バイトを使う。

    read  gIntrTable[4]
    if it already names the stub: return, writing nothing
    write the five words of the V-blank stub to the staging area
    write the handler just read into the stub's fifth word
    zero the counter
    write the staging area, Thumb bit set, into gIntrTable[4], last

尾部分岐の先はテーブルから取るので、フックはそこにあるハンドラが何であれ連鎖させる。先頭のガードは必須である。2 回インストールすると、スタブは自分自身に尾部分岐し、割り込みハンドラの中で回り続けてオーバーワールドが凍る。

`SaveBlock1 + 0x32E0` のスクリプトブロックは、再抽選されたポインタでソフトリセットを生き延びる（エミュレータで確認）。

スクリプトは武装のたびにコードを再構築するので、コードはスクリプト本体の大きさで制限される。ステージングで 162 バイト、あるいは最後のコマンドの後ろに約 755 バイトを追加し、トランポリンで到達する。

### スクリプト本体より大きいペイロード

`asm/field/save-loader.s`（64 バイト）は、ペイロードの大きさに関係なく RAM スクリプトがステージングするすべてである。`gSaveBlock2Ptr` を毎回読み、0xB20 を加え、N ワードをステージングエリアにコピーし、最初のワードをマジック値（一度も書かれていないセーブデータ、または後で別のカードが到達した領域）と照合して、その中へ分岐する。使うのは r0-r3 だけで、一度もプッシュしないので、ペイロードは `ScrCmd_callnative` の呼び出し元へそのまま戻る。

ブロブは 936 バイトで、1 回の `save-write`（`MAX_SAVE_WRITE_BYTES`。1024 バイトの受信バッファからライタを差し引いた量）に収まる:

    +0x000  magic 0x444C4B50
    +0x004  installer
    +0x054  the V-blank hook
    +0x068  filler
    +0x3A4  checksum over the filler

インストーラーは、フィラーの合計が正しくない限り何もインストールしない（[サイズの証明](frlg_rng.md#proving-the-size-rather-than-the-jump)）。

セーブデータのコピーにおけるフックの尾部分岐先は、計測した `VBlankIntr` でなければならず、0 であってはならない。ローダーは生きているかもしれないフックの上にコピーし、2 回目の訪問ではインストーラーがフックのインストール済みを見つけて何もパッチしないからである。そこが 0 だと、2 回目の会話の後にコンソールが黒い画面でクラッシュする。

RAM スクリプトは、ペイロードに関係なく 995 バイトのうち 394 バイトである。`filler_B20` は 1024 バイトを保持し、セーブデータの他の未使用領域は約 700 バイトである。より大きなブロブは、ペイロードごとに 936 バイトずつ、1 回のセッション内で書き分けられる（[`save-write`](#save-write)）。全部の 1024 バイトにすると、ブロブは EWRAM の上端に届き、カウンタはステージングエリアの下の 84 バイトへ移る。ステージングされたコピーは、フックの 5 番目のワードを除いてセーブデータと同じで、武装のたびに同じバイト列がステージングされる（エミュレータで確認。カウンタは毎秒 60.0 で動いた）。

### ラッパーの呼び出し

GBA のコードは、Sloop のシステムコールを通して Switch エミュレータに到達する。`swi 0x40` から `swi 0x62` までの間に 23 個あり、0x46、0x4E、0x52、0x58 から 0x60 までに欠番がある [src/sloopsvc.c]。常駐ペイロードはそのどれも発行できる。ビルダーは、番号をパッチしたサンク `swi N ; bx lr` をブロブにアセンブルする。戻らないシステムコールの後には読めるものが何も残らないので、呼び出しの前にマーカーを書いておく:

    +0x00  0xB0B00001   the probe was reached
    +0x04  the syscall number
    +0x08  0xB0B00002   it returned, and zero until it does
    +0x0C  r0, r1, r2, r3 as the syscall left them

`swi 0x54`（`svc_CommsAllowedByParentalControls` [sloopsvc.c:182]）は、ペアレンタルコントロールのないコンソールで非 0 を返す。

#### ディスパッチャー: Sloop システムコールの境界

ディスパッチャーは `main + 0x057014` にあり、そのジャンプテーブルは `main + 0x17D7F6` にある。`N` の値として 0x40..0x62 を受け付ける:

    cmp   w2, #0x2b ; b.lo default       below 0x2B, the BIOS syscalls
    sub   w9, w19, #0x40 ; cmp w9, #0x22 ; b.hi default
    ldrh  w12, [table, w9, lsl #1]       a u16 word-offset from 0x05706C
    br    base + offset * 4

エントリは 35 個、異なるハンドラは 23 種類ある。`sloopsvc.c` が名前を付けているすべての番号には、それぞれ専用のエントリがある。
0x46、0x4E、0x58 から 0x60 はデフォルトを共有しており、これはデコンプの欠番そのものである。0x48 と 0x56 は 1 つのハンドラ（`WriteSector`、`ReplaceSector`）を共有する。0x40 と 0x41 は、番号で分岐する 1 つのハンドラを共有する。
ディスパッチャーの `x0` は CPU オブジェクト、`w2` は番号、`x3` はハンドラが読むレジスタのコンテキストである。ゲストの `r0` は `+0x48`、`r1` は `+0x4C` にある（`mov x20, x3` の後の `0x52` ハンドラの `ldp w1, w22, [x20, #0x48]`）。

デフォルトは `cmp w19, #0x2a ; cset w0, hi ; ret` である。その `w0` はラッパー自身の「処理済み」フラグで、ゲストの r0 ではない。そのため未実装の番号は何もせず（ハングしない）、ゲストのレジスタはどれも変えない。0 を渡して 0 を読むプローブは、何も計測できていない。

0x40..0x62 を盲目的に走査してはならない。0x48 と 0x56 はセクター番号とポインタを取り、0x4C はセーブを完了させ、0x55 は SaveBlock2 のポインタを渡し、0x43、0x57、0x61、0x62 は引数を取る。r0 にマーカーを入れると、ガベージのフラッシュソースになる。

プローブは各呼び出しの前に自身の `swi` を書き換える（命令キャッシュなし）。番号を先に書くので、ハングしたときはどの番号かが記録に残る。7 個のヘッダワードの後に、番号ごとの `r0` を記録する（35 件の結果、140 バイト）。`p_probe_num_step` は番号を進め、`p_probe_a0_step` は番号の増分をゼロにして `r0` を進める。

| 番号 | 入力の r0 | 出力の r0 |
| --- | --- | --- |
| `swi 0x52` | `0xA5A00052` | `0` |
| `swi 0x53` | `0xA5C00052` | `1` |
| `swi 0x54` | `0xA5E00052` | `1` |
| `swi 0x55` | `0xA6000052` | `0xA6000052`（変化なし） |
| `swi 0x56` | `0xA6200052` | ラッパーがフォールトした |

領域テーブルが拒否する接続先（r0 にマーカー）を指定した `swi 0x56`（`ReplaceSector`）は、エミュレータを `0xFF8`（`main+0x573F8`）でフォールトさせ、セーブデータは無傷のまま残る:

    Invalid memory access at virtual address 0x0000000000000FF8
    PC  = main+0x573F8     LR = main+0x573EC
    x19 = 0x56                  the syscall number
    x22 = 0xA6200052            the guest's r0
    x13 = 0x0203FFC2            the guest's PC, the halfword after the thunk's `swi`
    x03 = 0x655DB09BE8          0x2D0 above the object 0x52's index 45 resolves to

ログは `0x0855D3F8` を `gba-app:0x573f8` と表示しており、これは `main` のベースを 0x08506000 に置く。

#### `swi 0x52` と `swi 0x55`: メモリバス

0x52 には、デコンプにないハンドラが `main + 0x05728C` にある:

    ldp   w1, w22, [x20, #0x48]     guest r0 into w1, guest r1 into w22
    lsr   x9, x1, #0x15             r0 >> 21
    ldr   x8, [x21, #0xe0]!         the region table
    and   x9, x9, #0x7f8            bits 3..10, so x9 is a BYTE OFFSET, not an index
    add   x8, x8, x9
    ldr   x0, [x8, #0x50]           the object for this selector
    ldr   x8, [x0]                  its vtable
    ldr   x8, [x8, #0x48]           slot 9
    blr   x8
    mov   x0, x20 ; mov w1, wzr ; mov w2, wzr ; b 0x0855D584

戻り値は捨てられる。`main + 0x057584` の書き戻しは `w1 = wzr` を受け取るので、ゲストは常に r0 = 0 を読み、r1 から r3 は変わらない。`swi 0x52` は、オーバーワールドから、セレクタ 45 から 54 まで（`r0` は `1 << 21` ずつ進む）にわたって、r0 = 0 を返し、r1 から r3 とセーブデータを変えずに残す。`main + 0x057304` の `swi 0x55` は、同じシフトで同じテーブルを引き、スロット 9 を呼び、書き戻しを飛ばす `main + 0x057588` から抜ける。そのため r0 は変わらないまま返る。

オブジェクトとターゲットを読むには、`blr x8`（`main + 0x0572AC`、仮想アドレス `0x0855D2AC`）で止める。`x0` がオブジェクト、`x8` がスロット 9 のターゲット、`w1` がゲストの r0 である。1 命令後も戻り値はまだ `x0` にある。256 エントリすべてを調べるには、何も参照される前の `ldr x8, [x0]`（`main + 0x0572A4`）で止める。ヌルまたは未マップのオブジェクトは、ここでフォールトする。

`0x7f8` は 1 命令でマスクとスケーリングを行う:

    entry = (r0 >> 24) & 0xFF        and the byte offset is entry * 8

これを `(r0 >> 21) & 0xFF` と読むと、すべてのエントリが 8 倍大きくなる。`r0` は GBA のアドレスで、テーブルはメモリバスである。上位バイトが領域を選び、スロット 9 がそのアドレスの折りたたみである。

| エントリ | 領域 | オブジェクト | スロット 9 |
| --- | --- | --- | --- |
| 0x00 | BIOS | 専用 | `and w0, w1, #0xffffff` |
| 0x01 | 未マップ | デフォルト | `and w0, w1, #0xffffff` |
| 0x02 | EWRAM, 256 KB | 専用 | `and w0, w1, #0x3ffff` |
| 0x03 | IWRAM, 32 KB | 専用 | `and w0, w1, #0x7fff` |
| 0x04 | I/O | 専用 | |
| 0x05 | パレット, 1 KB | 専用 | `and w0, w1, #0x3ff` |
| 0x06 | VRAM, 96 KB | 専用 | `and w8, w1, #0x1ffff` の後、`0x18000..0x1FFFF` を `0x8000` だけ折りたたむ |
| 0x07 | OAM, 1 KB | 専用 | `and w0, w1, #0x3ff` |
| 0x08, 0x09 | ROM ウェイトステート 0 | 両方で 1 つのオブジェクト | `ldr w8, [x0, #0x34] ; and w0, w8, w1`（カートリッジのサイズマスク） |
| 0x0A, 0x0B | ROM ウェイトステート 1 | 両方で 1 つのオブジェクト | 同じ vtable |
| 0x0C | ROM ウェイトステート 2 | 専用 | 同じ vtable |
| 0x0D | ウェイトステート 2 の上端（EEPROM が置かれる） | 専用 | デフォルトの vtable |
| 0x0E | SRAM | 他のどの領域オブジェクトからも離して確保 | |
| 0x0F | SRAM のミラー | 専用 | |
| 0x10 から 0xFF | 未マップ | デフォルト | `and w0, w1, #0xffffff` |

エントリ 0 から 15 は 14 個のオブジェクトと 11 個の vtable を与える。VRAM の折りたたみはハードウェアのミラーである（`0x18000` は `0x10000` を、`0x1FFFF` は `0x17FFF` を読む）。デフォルトのオブジェクトは `0x655DB09918`、vtable は `main + 0x1C1FB0`、スロット 9 は `main + 0x01F7D8` である。そのスロット 10 は `mov x0, xzr ; ret`、11 は素の `ret`、2 は 2 回ストアするセッターである。すべての vtable は `-0x08` に null の typeinfo ポインタを持つ。RTTI もクラス名もない。

EWRAM の vtable は `main + 0x1C21A0` である（`x0` が領域オブジェクト、`x1` がサイクルカウンタ、`x2` がアドレス、`x3` が値）:

| スロット | 内容 |
| --- | --- |
| 2 | `+0x24` と `+0x2C` のオブジェクトに 2 ワードを書き込む |
| 3, 4, 5 | 16, 32, 8 ビットを読む |
| 6, 7, 8 | 16, 32, 8 ビットを書く |
| 9 | アドレスを領域に折りたたむ |
| 10, 11 | null を返す、および何もしない |

アクセサは、まずサイクルカウンタに加算してから（ハーフワードまたはバイトは 3、ワードは 6）、`+0x10` のホストのバッキングポインタを添字で引く。サイズは `+0x20`、ROM のサイズマスクは `+0x34` にある。

7 個のシステムコールがテーブルに到達する（0x45、0x47、0x48 と 0x56、0x4D、0x52、0x55、0x62）。いずれもスロット 9 だけを呼ぶ。読み書きのアクセサはエミュレータの CPU コアに属する。`swi 0x62` はカウンタを増やす 4 命令である。

ハンドラの範囲は、その制御フローで決める。いくつかは最後のテーブルエントリの後にアウトオブラインの継続部を持つので、次のハンドラの開始位置で区切ると誤って帰属させてしまう。

### フラッシュセクターの経路

`swi 0x48` と `swi 0x56` は `main + 0x057084` のハンドラを共有し、継続部は `main + 0x057364` にある。ゲストの `r0` は 4 KB のセクター番号、`r1` はソースである:

    source      = r1, resolved through the region table and folded
    destination = 0x0E000000 + r0 * 0x1000, resolved the same way

接続先アドレスは 32 ビット演算で作られ [main + 0x05737C]、`0x0E000000 + ((r0 & 0xFFFFF) << 12)` となる。領域エントリはそのアドレスの上位バイトである [main + 0x057384]: `0x0E + ((r0 & 0xFFFFF) >> 12)` を 256 で割った余り。そのため `r0` が領域を選ぶ。EWRAM、IWRAM、またはカートリッジバッファへの接続先は、両方の境界チェック（`fold < size`、`size - fold >= 0x1000`）を通過する。`r0 = 0xFA000 + n` とすると、接続先はどのソース領域からでも、ROM コピーの `n * 0x1000`（`n` は 0..0xFFF）の 4 KB に折りたたまれる。

ROM 側の接続先は、カートリッジバッファへの生の書き込みである。これは IP ホスト経由で、エミュレートしたコンソール（パッチを当てた Ryubing ビルド）で計測した（実機のコンソールには触れていない）。`r0 = 0xFA3FF`（`dest` 0x083FF000、`n` = 0x3FF、領域エントリ 0x08）と EWRAM のソース（`r1` 0x0201C400、fold 0x1C400、マスク 0x3ffff）の場合、両方のゲートを通過し、コピーが着地する。カートリッジバッファの 0x3FF000 のバイト列は、ソースの 0x1000 バイトそのものになった（0x3FF000..0x3FF31F に選んだパターンの 200 ワード、続けて 0x3FF320 以降はソース自身の末尾のバイトがそのまま運ばれる。たとえば両方の場所でワード 200 = 0x11111000）。その後、0x083FF000 からのゲストの読み込みは、折りたたまれた ROM のウィンドウ越しにパターンを読む。ホストのセッションは保たれた。ペイロードは 1 を返し、`client->param` はパターン自身の最初のワードを運び、コンソールは成功メッセージを表示して、リンクをきれいに閉じた。

同じ方法でコピーされたコードも実行される。ソースのワード 0 を 2 命令の THUMB ルーチン（`0x47706001`: `str r1,[r0]; bx lr`）にし、ワード 1..199 をパターンにすると、コピーの後にペイロードは折りたたみを読み戻し（`0x47706001`、ルーチン）、`r1` にナンスを、`r0` に自身の結果ワードのアドレスを入れて `0x083FF001` に分岐した。コンソールの応答はナンスを運んだ。つまり、ラッパーの命令フェッチはシステムコールが書いたのと同じライブのバッキングを読み、コピーされたバイト列は通常のフェッチ経路を通ってコードとして実行される。セッションは成功メッセージとともに閉じ、ゲームはセーブされた。

書き込みはソフトリセットを越えて残る。A+B+START+SELECT の後、EWRAM のソースのスクラッチをクリアした状態でデバッガーから読むと、同じ fold 0x3FF000 の 4 KB がバイト単位で一致した（4096 バイト中 0 バイトが変化）。リセット後に開いた 2 回目のセッションは、0x083FF000（`0x47706001`）を読み、新しいナンスとともに 0x083FF001 に分岐した。常駐ルーチンは、そのナンスを返した。アプリケーションを完全に再起動すると、エミュレータの ROM ファイルからバイト列が復元された。新しいプロセスは、fold に元のファイルのバイト列を持っていた。書き込みの寿命は、エミュレータのプロセスの寿命である。

領域のバッキングポインタ `+0x10` が null のとき、折りたたまれたオフセットが `+0x20` のサイズ以上のとき、または残りが `0x1000` バイト未満のとき、どちらの側も（ポインタを null にして）拒否される。両側とも、`0x1000` バイトがコピーされる前に解決される。その後 `swi 0x56` は、null チェックなしで接続先の `+0xFF8` に `0xFF` を書き込む:

    cmp   w19, #0x56
    b.ne  exit
    mov   w8, #0xff
    strb  w8, [x21, #0xff8]

`+0xFF8` はセクターの署名である [pokeldn/frlg/save/save_inject.py]。`0x08012025` は `0x080120FF` になり、そのセクターは無効になる。`ReplaceSector` は書き込んで無効化し、`WriteSector` は書き込むだけである。拒否された接続先では `x21` が null のままになるので、`swi 0x56` は上で述べた中断のとおり `0xFF8` でフォールトする。

エミュレートしたコンソールで `swi 0x48` を使って計測した:

| 呼び出し | 結果 |
| --- | --- |
| フラッシュサイズを越えるセクターの `r0`、未マップ領域の `r1` | 何も書かれず、フラッシュはバイト単位で同一、フォールトもフリーズもなし |
| `r0 = 30`、`r1 = 0x08000000`（ROM ヘッダー） | セクター 30 がカートリッジの最初の 4 KB になった（4096 バイト中 4096 バイト）。隣接するセクターは無傷 |
| `r0 = 30`、ペイロードが埋めた EWRAM のバッファを `r1` | セクター 30 がそのバイト列になった。バッファは変わらず読み戻された |
| `r0 = 0xFA3FF`（接続先 0x083FF000）、EWRAM のバッファを `r1` | コピーがカートリッジバッファに着地した。fold 0x3FF000 のバイト列は、ソースの 4 KB とバイト単位で一致した。0x083FF000 からのゲストの読み込みはパターンを返した。セッションはきれいに終わった |
| 同じコピー（ソースのワード 0 が THUMB ルーチン）の後、`r1` にナンスを入れて `0x083FF001` に分岐 | コピーされたルーチンがナンスを返した。コンソールは成功を表示し、セーブして、きれいに閉じた |
| ソフトリセット後、同じ fold をデバッガーで読む | EWRAM のソースのスクラッチがクリアされている間も、4 KB はバイト単位で一致した（4096 バイト中 0 バイトが異なる） |
| リセット後、ルーチンを読んでから `0x083FF001` に分岐する 2 回目のセッション | 常駐ルーチンは新しいナンスを返し、1 つのプロセスの中でリセットをまたいで呼び出せ続けた |
| アプリケーションの完全な再起動後、同じ fold をデバッガーで読む | fold には元の ROM ファイルのバイト列が復元されていた。書き込みの寿命はプロセスの寿命である |

ゲストのレジスタは一切変更せず、ステータスも返さない。受け付けられた呼び出しと拒否された呼び出しを区別できるのは、フラッシュの読み込みだけである。

エミュレータは、ゲームがセーブしたときにだけ 128 KiB のフラッシュイメージを確定させ、その際に異物のセクターも一緒に運ぶ。システムコールの書き込みの後にハードキルすると、ホストのファイルは変わらないまま残る。ふしぎなおくりものセッションの中の書き込みは、セッションが成功メッセージで終わると永続化される。成功メッセージはセーブを行うため [mystery_gift_menu.c:1379]、それ以外の結果の後、および常駐フックからの場合は、次のセーブを待つ。

### ブレークポイントフック

ラッパーの GBA CPU オブジェクトは、`cpu + 0x170` に 256 個のフックスロットを持ち、`bkpt` の即値ごとに 1 つずつある。ARM のデコードは `(insn & 0xFFF000FF) == 0xE1200070` で判定し、THUMB のデコードは `(insn & 0xFF00) == 0xBE00` で判定する（`main + 0x01FCE4`）。THUMB のハンドラ（`main + 0x01EFC0`）は、`imm8` のスロットにあるフックの vtable スロット 2 を、`main + 0x01F820` 経由で呼ぶ（フック、`&insn`、`bkpt` のアドレス、CPU）。フックが 1 を返すと、コアは `insn` に格納した命令を実行する。0、または空のスロットのときは、`bkpt` は何もしない。`main + 0x022A2C` はフックを登録し、埋まったスロットを拒否する。2 つのスロットが埋まっている:

| スロット | 所有者 | フック | 役割 |
| --- | --- | --- | --- |
| `bkpt #0x52` | Sloop コンポーネント、vtable `main + 0x1C3878` | `main + 0x05499C` -> `main + 0x056368` -> `main + 0x03E850` | 下記の librfu パッチ |
| `bkpt #0xFF` | アプリケーションのオブジェクト、vtable `main + 0x1B4078` | `main + 0x001140` | イベント `0x82EF0054` を引数 1 で投稿し、アプリケーションを終了させる |

ロード時に、ラッパーはゲストの ROM コピーに 3 つのパッチを書き込む。`0x08000000..0x09000000` のうち、カートリッジと異なるのはこの 10 バイトだけで、v0 と 1.0.1 のどちらでも同じである（ブロックのチェックサムと、ふしぎなおくりものクライアント越しの読み込み。実機とエミュレートしたものの両方）:

| アドレス | カートリッジ | ゲスト |
| --- | --- | --- |
| `0x081E1696` | THUMB `mov ip, r1` (`468c`) | `bkpt #0x52` (`be52`) |
| `0x081E187C` | ARM `ldr r3, [pc, #0x50]` (`e59f3050`) | `bkpt #0x52` (`e1200572`) |
| `0x081E1F90` | ARM `mov lr, r0, lsr #14` (`e1a0e720`) | `b 0x081E1FB8` (`ea000008`) |

3 つ目のパッチは待ちループを取り除く。`0x081E1F74` の関数は、`REG_SIOCNT`（`0x04000128`）のビット 2 を呼び出し側の `r0`（`r0` を u16 にマスク、`lr = r0 >> 14`）と照合してポーリングし、`[*(0x03000030) + 0x10]` のバイトが 1 のとき、そのバイトをクリアして 1 で答え、早期に戻る。エミュレーションではポーリングが一致しないので、ラッパーは本体を `mov r0, #0; return` に置き換える。待ちは即座に 0 で答える。

`bkpt #0x52` はアドレスで鍵付けされる。そのフックは 2 つのレコード `{u32 pc, u32 original insn, ..., u32 hits at +0x0C}` を `+0x120` と `+0x148` に持ち、`main + 0x0546C0` はアドレスを照合して元の命令を返す。`Sio32IDMain` のパッチ（`0x081E1696`）では、ゲストの `r0`（`&gRfuSIO32Id`）を解決し、`+0x0A` に `0x8001` を書き込む。これは `AgbRFU_checkID` が待つアダプター ID である [librfu_sio32id.c]。ほかのアドレスの `bkpt #0x52`（`0x081E187C` のパッチ）は、2 つ目のレコードを、そのセッションの残りの間、自分自身に鍵付けし直す。

#### レコード解決部 (`main + 0x03E850`)

フック `main + 0x05499C` は `bkpt` 自体を `insn` に書き込み、次に `x0 - 0x60` を `this` として `[[x0 - 0x60] + 0x98]` の仮想関数を呼ぶ（逆アセンブル、`main + 0x549c4`-`0x549cc`）。Sloop コンポーネントの場合、それは `main + 0x056368` に解決される。これはレコードホルダー `[component + 0x40] -> [+0xA8] + 0x68` を導き、`&insn`、`bkpt` のアドレス、CPU とともに解決部 `main + 0x03E850` を末尾呼び出しする（`0x3e850` はイメージ内に呼び出し元が 1 つだけあり、それは `0x56378` である）。ゲストの `r0` の上位バイトが領域を選ぶのは、後述の解決部の Sio32ID エミュレーションの中でだけである。解決部は次のとおり:

- `main + 0x0546C0` を通してレコード 1（ホルダー `+0x120`）を照合する。一致すると、`+0x0C` のヒット数を増やし、`+0x4` の元の命令を `insn` にコピーする。コアはそれを実行する。
- レコード 1 が一致したら、Sio32ID エミュレーションに進む。ゲストの `r0` は領域テーブルで折りたたまれ、折りたたまれたオフセットは `offset < region size`（`+0x20`）だけで境界チェックされる。ホルダー `+0x108` のフラグバイトが立っていると、`strh` が `backing + offset + 0xA` に `0x8001` を書き込み、`main + 0x2209C` が `backing + offset + 1` のバイトをゲストの `r1` に書き込む（`str w2, [regfile + 4 + 0x48]`）。`+0xA` は境界チェックの対象外なので、領域の最後の `0xA` バイトにあるオフセットは、領域のバッキング割り当てを越えて、終端から最大 11 バイト先まで書き込む。フラグが立っていて範囲外のオフセットのときは、バッキングポインタが null になり、ラッパーはアドレス `0x1` の読み込みでフォールトする。フラグが下りていると、解決部は書き込みなしで戻る。ホルダー `+0x108` は `[+0xA8] + 0x170`（ホルダーは `[+0xA8] + 0x68`）で、後述するアダプターの電源スイッチと同じバイトである。コンソール自身のふしぎなおくりものの検索中に、`main + 0x03E850` 経由で 3 回ライブで読むと、毎回 `0x1` だった。そのため `swi 0x40` だけで書き込み経路が武装される。
- レコード 1 が一致しなければ、レコード 2（ホルダー `+0x148`）を鍵付けし直す: `record2.pc := the bkpt address`。その後それに一致させるので、コアはレコード 2 の元の命令を実行する。この元の命令は更新されない。古い `0x081E187C` の元の命令 `e59f3050`（`ldr r3, [pc, #0x50]`）が、ゲストが実行しているどのアドレスから `bkpt #0x52` を発行したときでも、ゲストがどの CPU モードであっても実行される。コンソール自身のふしぎなおくりものの検索では、すべてのディスパッチがこの経路で鍵付けし直される。レコード 2 のヒット数（ホルダー `+0x154`）は、3 回のライブ読み込みの間に 0.33 秒あたり約 20 増えたが、レコード 1 は動かなかった。そのため検索画面が毎フレーム実行するのは、`Sio32IDMain` の ROM 上の箇所ではなく、`0x081E187C` の実行時の IWRAM コピーにある STWI ドライバー自身の `bkpt #0x52` である。
- レコード 2 が `+0x108` フラグ付きで一致すると、`main + 0x03E954` に落ちる。`+0x170` のホルダーに格納されたアドレスを折りたたみ、折りたたまれたアドレスにあるワードを読む。そのワードの上位バイトを領域セレクタとして使い、ワード自体を再び折りたたむアドレスとして使う。これは境界チェックされ、ホルダー `+0x42B8 + 0x7C` のカウンタを減らす。
- レコード 2 が `+0x108` フラグなしで一致すると、`main + 0x03E960` に落ちる。`+0x170` のホルダーに格納されたアドレスを折りたたみ、そこのワードを読んで、ビット 15 から 26 が `0x600` と一致するか調べる。一致すると、そのワードの下位 24 ビットを同じ領域テーブルで折りたたみ（境界チェック付き）、ホルダー `+0x42B8 + 0x7C` のカウンタを減らす。一致しなければ何もしない。

ゲストはトリガー全体を制御する。選んだ `r0` で `0x081E1696`（パッチを当てた箇所、THUMB）に分岐するペイロードは、ラッパーに `fold(r0) + 0xA` へ `0x8001` を書き込ませ、`r1` を `fold(r0) + 1` のバイトに設定させる。それ以外の場所で `bkpt #0x52` を実行するペイロードは、そこで古い `e59f3050` を実行させる。どちらもゲストに相対的である。`+0xA` の書き込みが、ゲストの領域の外に出る唯一の経路である。どの領域のバッキング割り当ての終端からも最大 11 バイト先まで、2 バイトの定数 `0x8001` を書き込むことができ、16 MB の ROM コピーの終端も含まれる。

#### ROM バッファの後ろにあるもの: Sloop コンポーネント

ROM オブジェクトのマスク（`+0x34`）は、カートリッジが `0x1000000` バイトを占める間 `0x1ffffff` である。そのため `0xFFFFF6..0xFFFFFF` の fold は境界チェックを通過し、書き込みは ROM バッファの直後の 10 バイトに載る。そこにあるオブジェクトが Sloop コンポーネントである（[ブレークポイントフック](#the-breakpoint-hooks)）。その最初のワードは vtable ポインタ `main + 0x1C3878` で、`+8` は `0x000004bf`、`+0xC` は `0x0A828400`、`+0x18` と `+0x20` は `main + 0x16EB83`、`+0x28` は `0x655db` のヒープポインタ、`+0x60` と `+0x88` はさらなる vtable（`main + 0x1C3948`、`main + 0x1C3978`）、`+0xE0` は CPU バスのオブジェクトである。

ROM の隣のオブジェクトは起動ごとに変わる。ある起動での ROM の隣は、最初のワードが vtable `main + 0x1C36D8`、`+0x60` が vtable `main + 0x1C3790` のオブジェクトだった。コンストラクタ `main + 0x547CC` はまさにその組を書き込み、静的ポインタ `main + 0x86D67E8` を読む（加算値 `main + 0x1C36C8` [main_relocs.json]）。そのクラスのフィールドは、そのコンストラクタと自身のコードによって書かれ、ゲストのセッションからの書き込みはそれに届かない。

植え付けられた箇所では、カートリッジ自身のコードが自身の `r0` を退避する（`ldr r0, [pc, #0x10]` は `0x0300744A` を読む。これは自身の `&gRfuSIO32Id`、IWRAM にある）。そのため、ゲーム自身のディスパッチは常にゲーム自身の構造体へ fold される。ラッパーの `0x8001` の格納は、`AgbRFU_checkID` が待つアダプター ID である `gRfuSIO32Id.lastId`（`RFU_ID = 0x8001` [librfu.h]）に届くものである。`0x081E1696` へ直接分岐するペイロードは、その読み込みを飛ばして自身の `r0` を退避するので、代わりに格納の方が動く。

strh 自体（`main + 0x3E928`）とその継続部で計測した。`r0 = 0x08FFFFF6` で直接分岐すると、格納の `x8` は `backing + 0xFFFFF6`（`0x66209f9ff6`。その後ろにはテールの `ff` パディングがある）であり、格納の前後のダンプは、格納の前が `78 98 6c 08 ...`、後が `01 80 6c 08 ...` を読んだ。約 90 ms 離れた 2 回の格納である（ペイロードのトリガーと、退避した `r0` を使って同じ箇所を通る 2 回目のディスパッチ）。

コンポーネントの最初の 2 バイトへの書き込みは、vtable ポインタ `0x086C8001` を植え付ける。ディスパッチャー `main + 0x1F820` は、そこからフックのスロット 19（オフセット `+0x98`）を読む。`main + 0x1C2099` の 8 バイトは `f7 01 00 00 00 00 00 00` なので、ラッパーの次の仮想呼び出しは、ゲストの PC `0x1F7` で実行される。これは、ゲストのどの経路も到達しない未マップのアドレスである。エミュレータでは、これによりプロセスが中断される（`Unhandled guest exception InstructionAbortLowerEl`）。一方、領域の内側で fold する同じトリガーでは、セッションはローカルな fold への書き込みだけで終わり、そのようなディスパッチは起きない。箇所にあるカートリッジ自身のコードは、もう 1 つの候補を除外する。`mov ip, r1` は `ip` を値として格納し（`mov r0, ip; strh r0, [r4]`）、そこを経由して分岐されることはない。

フックは、`[component + 0x40] -> [+0xA8] + 0x170` のバイトが立っている間だけ動作する。これは仮想アダプターの電源スイッチである。`swi 0x40` がそれを立て、`swi 0x41` が下ろす（ハンドラ `main + 0x05706C` は `number == 0x40` を格納する。[sloopsvc.c:23] の「未参照のフラグ設定」）。ふしぎなおくりものメニューからの `swi 0x41` は RFU のフレームを止める。ゲームはリンクエラーを表示し、LDN から離れる。アダプターはソフトリセットをまたいで切れたままになるので、次の無線メニューは "L'adaptateur sans fil GBA n'est pas connecté" と報告する。このバイトはソフトリセットを越えて残る。再起動するか `swi 0x40` を実行すると元に戻る。フレームごとに読まれるので、1 つのペイロードの中で `swi 0x41` の後に `swi 0x40` を実行しても無害である。

#### bkpt からリゾルバーに至る連鎖

NSO の vtable スロットは、ファイル内で再配置されていない加算値を保持する。ローダーがイメージのベース（`main` は `0x8506000`）を加える。そのベースを適用すると、ゲストの `bkpt #0x52` は次の連鎖を実行する:

- 両方のデコード経路（THUMB `main + 0x1EFE0`、ARM `main + 0x1B7B8`）は、ディスパッチャー `main + 0x1F820` を `(CPU, bkpt のアドレス, 即値, &insn)` として呼ぶ;
- ディスパッチャーは、フック = `[CPU + (imm & 0xff) * 8 + 0x170]` を取る。`bkpt #0x52` の場合、それはコンポーネントの下位オブジェクト `component + 0x60` になる（コンポーネントは GBA CPU オブジェクトである: `+0x84` が現在の pc、`+0x170` がフックテーブル、`+0x960` が 2 つ目のバステーブル、`+0xE0` がバスのオブジェクト）。それはフック自身の vtable（`main + 0x1C3948`）のスロット `+0x10` を読み、`f(hook, &insn, bkpt のアドレス, CPU)` として呼ぶ。スロット `+0x10` は直接 `main + 0x5499C` である;
- `main + 0x5499C` は `insn` に `0xE1200572` を書き込み、次に `[component]` を読んで、`[that pointer + 0x98]` の仮想関数を `(component, &insn, bkpt のアドレス, CPU)` で末尾呼び出しする。`main + 0x1C3878` のスロット `+0x98` は `main + 0x56368` で、これがレコードホルダーを導き、リゾルバー `main + 0x03E850` に到達する。

そのため、コンポーネントの最初の 10 バイトへの格納は、スロット `+0x98` で消費される。`+0x10` の読み込みはフックの下位オブジェクト上で起き、それら 10 バイトの外側にある。リゾルバーの書き込み先は `buffer_data + fold + 0xA` であり、fold は選ばれた領域のスロット 9 である（[`swi 0x52` と `swi 0x55`: メモリバス](#swi-0x52-and-swi-0x55-the-memory-bus)）。

#### 継ぎ目への植え付けがもたらすこと

`fold = size - 0xB`（範囲内）のとき、書き込みの組は `(size-1, size)` である。領域の最後のバイトは `0x01` を受け取り、隣のバッキング割り当ての最初のバイトは `0x80` を受け取る。`fold = size - 0xA` のとき、組は `(size, size+1)` で、隣のバッキング割り当ての最初の 2 バイトに `0x01 0x80` が入る。ふしぎなおくりもの 1 セッションにつき、訪問ごとに選べる fold は 1 つである。

サイトの後ろの本体は、5 ワードのフレームを通って戻る。そのエピローグ `0x081E177C` は `movs r0,#0 ; pop {r4,r5,r6,r7} ; pop {r1} ; bx r1` である。サイトに分岐するペイロードは、関数のプロローグを飛ばすので、`lr` を継続部に向けて、そのフレームを自分で push しなければならない。すると本体はペイロードへ戻り、ペイロードはさらにコードを実行して、セッションを普通に終えられる。ほかのフレームを push するペイロードは、代わりに呼び出し元のスタックを巻き戻す。計測した実行は、同じ退避 `r0` でサイトに再入した。

ウィンドウ 4（GBA の IO レジスタ）は、それ自身のバッキング割り当ての直後にある 0x400 バイトの領域オブジェクトに対応する。バッキングはバス `+0x14C0`、オブジェクトはバス `+0x18C0` にあり、キー割り込みの下位オブジェクトはオブジェクト `+0x88` に埋め込まれている。そのため植え付けは、バスがすべての IO アクセスを経由させるオブジェクトに載る。イメージの CPU コアには、アクセサの形をした呼び出し箇所が 210 個ある（[`swi 0x52` と `swi 0x55`: メモリバス](#swi-0x52-and-swi-0x55-the-memory-bus)）。

エミュレートしたコンソールでは:

| 植え付け | 消費される箇所 | 結果 |
| --- | --- | --- |
| コンポーネントのバイト組 `01 80`（`0x086C8001`） | `main + 0x1C2099` で読まれるスロット `+0x98`、再配置なし、`0x1f7`（[上述](#what-follows-the-rom-buffer-the-sloop-component)） | |
| コンポーネントのバイト 0 `0x80`（`0x086C9880`） | `main + 0x5492C`。同じメソッドだが `-0x60` がない | 植え付けられたままのコンポーネント上で `[x0] + 0x98` を読み直し、自分自身に再帰する。スレッドのスタックが尽き、プロセスはデータアボート（`InvalidMemoryRegionException`）で終わる |
| IO オブジェクトのバイト 0 `0x80`（`0x086C8480`） | バスのストアスロット `+0x38`/`+0x40`。植え付けられた接続先は生の `0xffffffffffffe5e0` と `0` | 植え付けの後の最初の IO ストアで、約 30 ms 以内にプロセスが中断される。ロードの接続先（`main + 0x30EAC`、`main + 0x31114`、`main + 0x36D54`）は一度も実行されない |
| name-hash ブロックのバイト 0（`0x80`） | このブロックは SDK のバインダー/サーフェス記述子オブジェクトであり（`android.gui.IGraphicBufferProducer` などは SDK イメージ内の静的文字列である）、ディスパッチされるオブジェクトではない | 反応なし。ゲームは自身の正常終了まで進む |

植え付け `0x086C8080`（バイト `80 80`: その後、すべての `bkpt #0x52` が純粋なカウンタのゲッター `main + 0x1F7F0` を実行するので、各 bkpt は何もしなくなる）は、間にディスパッチを挟まない 2 回の書き込みを必要とする。1 セッションで得られる書き込みは 1 回だけで、途中の単一書き込みの状態は両方ともプロセスを中断させる。一方、デバッガーで植え付けると、そのポインタはゲームが動きプロセスが生きている状態で 5 分間残った。イメージ内のどのコード箇所も、init の後にラッパーオブジェクトのヘッダーを書き込まない。

#### 1 回の書き込みの植え付けが作れるすべての配置

植え付けは、隣のオブジェクトに 2 つのバイトパターンのどちらかを書き込む。最初のバイトに `80`（その領域自身の最後のバイトは `01` を受け取る）、または `k` と `k+1` のバイトに `01 80`（`k` は 0..9）。隣のオブジェクトの最初の 8 バイトは vtable ポインタなので、消費側が読むポインタは、イメージ内のファイルとその再配置に対して解決される。生きているメインメモリを読む植え付けは 4 つある:

| オブジェクト | 書き込むバイト | 植え付けポインタ | 消費側 |
| --- | --- | --- | --- |
| コンポーネント（vtable `main + 0x1C3878`） | +0 の `80` | `0x086C9880` | `bkpt #0x52` 連鎖の `[P + 0x98]` = `main + 0x1C3918` = `main + 0x5492C` |
| コンポーネント | +0..1 の `01 80` | `0x086C8001` | `[P + 0x98]` = `main + 0x1C2099` = 生の `0x1F7` |
| IO オブジェクト（vtable `main + 0x1C2408`） | +0 の `80` | `0x086C8480` | 下記のバスのアクセサスロット |
| IO オブジェクト | +0..1 の `01 80` | `0x086C8001` | バスのアクセサスロット: `0x1F7`、ゼロ、生の加算値 |

ほかの植え付けは、イメージの外側に解決される。+1 の `01 80` は `0x08800178`（コンポーネント）と `0x08800108`（IO オブジェクト）を与え、これらは main の bss の内側にある。ゼロ埋めされた bss のモデルは、そこで null の呼び出しを予測するが、ファイルイメージだけでは、ライブのセッション中の内容は確定しない。+2 から +7 の `01 80` は、バイト 2 またはバイト 3 を動かすので、消費側の読み込み自体がフォールトする。+8 と +9 では、組が `+8` のフィールドに載り（コンポーネントの `0x000004BF` は +8 で `0x00008001` になり、+9 で `0x008001BF` になる）、vtable ポインタは残るので、ディスパッチはオブジェクト自身のものである。

2 回の箇所への訪問は、間に `0x04` のアクセスが起きなければ、IO オブジェクト上で組を合成できる。ペイロードの ROM または EWRAM からの命令フェッチは、それ自体では当該オブジェクトにアクセスしない。植え付けの繰り返しは冪等であり、+8 または +9 への書き込みは vtable ポインタを変えない。バイト 0 と 1 に限られた異なる植え付けでも、上記のイメージ内ポインタの 1 つが残ることがある。上位のポインタバイトを変える合成は、別途の分析が必要である。コンポーネントでは、次の `bkpt #0x52` が現在の植え付けを消費する。リンクが繋がっている間、STWI ドライバーは毎秒約 60 回そのような呼び出しを生むが、その速度だけでは、ペイロードの訪問の各組の間に呼び出しが挟まることは確定しない。

IO オブジェクトの植え付けブロックを、バススロットごとに示す。アクセス種別は呼び出し側の結果マスクから来る（16 ビットのロードは `main + 0x18378` の `and #0xffff`、32 ビットのロードは `main + 0xBDB8` のワードの回転、8 ビットのロードは `main + 0xD914` の `and #0xff`）。

| バススロット | アクセス | 植え付けた接続先 | IO オブジェクトを `this` としたとき |
| --- | --- | --- | --- |
| `+0x18` | 16 ビットのロード | `main + 0x30EAC` | キーハンドラーの default の場合: `w2` は完全な `0x04xxxxxx` アドレスで、ハンドラーが切り替えるどのレジスタ ID よりも大きいため、`[x1]` に `w3 & 0xffff` を格納する。`main + 0x18330` の呼び出し箇所は `x1 = CPU + 0x20` と `w3 = 1` を渡し、ゲストのロードはハンドラーの残りの `w0` を返す |
| `+0x20` | 32 ビットのロード | `main + 0x31114` | `(箇所からの x1、IO + 0x20)` で `main + 0x3580C` を呼び、次に `x0 = [[IO + 8] + 0x90]` で `main + 0x22404` を末尾呼び出しする |
| `+0x28` | 8 ビットのロード | `main + 0x36D54` | 0x76000 バイトのオブジェクトの破棄ファミリー: `[x0 + 0x76C70]`、`+0x76C30`、`+0x76C00`、`[x0 + 0x4E68]` |
| `+0x30` | ストア | `main + 0x36E40` | `x0 -= 0x1A10` の後、再配置されたポインタに対する同じ破棄ファミリーの `main + 0x3664C` |
| `+0x38` | ストア | 生の `0xFFFFFFFFFFFFE5E0` | 呼び出しがフォールトする |
| `+0x40` | ストア | `0` | null の呼び出し |
| `+0x48` | | `main + 0x36E4C` | `+0x76C60`、`+0x76C20`、`+0x76BF0`、`[x0 + 0x4E58]` の破棄ファミリー |
| `+0x68` | | `main + 0x310A8` | `x0 -= 0x10` の後、`main + 0x30EAC` |

上の植え付けのどれも、ゲストのメモリが供給するディスパッチ先には届かない。メイン内の 4 つの植え付けはメイン自身のデータを読み、IO オブジェクトのブロックは、バスの引数を使ってメイン自身のハンドラーを呼ぶ。

実機（Switch Lite、英語版ファイアレッド、XIAO ESP32S3 の無線経由で LDN にペイロードを届けた）では、コンポーネントの植え付けと範囲内の書き込みは、画面ではなくリンクの破棄で区別される。どの実行も、スクリプトの約 2 秒後に "The software was closed because an error occurred" とともに HOME に戻った。そのためメッセージは一般的なもので、正常な Pia の離脱（`Session type 3`）はそうではない:

- フォールトがカートリッジバッファの 1 つ先（コンポーネント、`r0 = 0x08FFFFF6`）のとき、コンソールは `Session type 3` なしで LDN を離れた（タグ `pl01`、`pl04`）。エミュレータのディスパッチが示す急な中断が、実機でも起きた;
- フォールトが範囲内（`r0 = 0x08FFFFF0`、タグ `pl03`、バッファの `+0xFFFFFA` への書き込み）のとき、および VRAM に着地する EWRAM の末尾超過（`r0 = 0x0203FFF6`、タグ `pl02`）のとき、コンソールは `Session type 3` を送り、正常に離脱した。通常のカードセッション（`scratchpad/re1_host.log`、`rt02`..`rt04`）も同じである。

そのため、レコードリゾルバーの格納は、フォールトが ROM バッファの終端をまたぐと、実機で生きているラッパーのオブジェクトに届き、アプリはそこで中断する。ゲストから見えるメモリに置かれた同じ格納は届かない。ボディのフレームを push するペイロードは、実機でも同様にサイトから戻る。

植え付けの後のディスパッチは、アプリの次の `bkpt #0x52` である。ゲームはそれを 2 か所から生む。1 つは STWI ドライバーの IWRAM コピーで、リンクが繋がっている間は毎秒約 60 回（そのヒット数のライブ読み込み）。もう 1 つは、箇所にある `Sio32IDMain` からの自身の呼び出しで、レコード 1 のライブ読み込みで 12 ヒットである。
vtable の下位バイトが `0x80` のとき、そのディスパッチは `main + 0x5492C` に届く。これは植え付けられたポインタ上で `[component] + 0x98` を読み直し、スレッドのスタックが自身の領域を出るまで再帰する。コンソールは `Session type 3` なしで HOME に戻る。カートリッジ自身の命令を IWRAM コピーの `bkpt #0x52` の上に戻し、両方の箇所を含む 4 KB ブロックを `swi 0x48` 経由でカートリッジコピーの 2 つのロード時パッチを元に戻すペイロードは、両方の発生源を取り除く。その場合、コンソールはゲーム自身の通信エラーを表示し、`Session type 3` で LDN を離れ、通信レポートを提出して動き続ける。植え付けはその状態で無効になっているだけで、修復されてはいない。vtable を戻すコードの箇所は存在しない。元に戻されたカートリッジコピーも、プロセスの寿命にわたる状態である。無線メニューはアダプターが接続されていないと報告し、完全な再起動でラッパーのロード時パッチが再適用される。

### 境界の現状

このページで検討したゲストの経路には、領域のバッキングを越える格納が含まれる。リゾルバーの `fold + 0xA` への `0x8001` の strh である。植え付けられたポインタの消費側は、静的アドレスで `main` 自身のデータから接続先を読む（[1 回の書き込みの植え付けが作れるすべての配置](#every-placement-a-one-write-plant-can-make)）。生きたメモリを読む 4 つの配置と、ほかのすべての配置が残すものは、そこに載っている。下位バイト `80` の植え付けの後のセッション中のコンポーネントの消費側は、`bkpt #0x52` フックの連鎖からの `main + 0x5492C` である。単一書き込みの分析は、ゲストのバイトが供給する呼び出し先を特定しない。ただし、書き込みのすべての列の結果を確定するものではない。連鎖の 2 つのゲストの発生源を取り除くと、観測されたディスパッチは防がれた。コンポーネントへのシステムコールの格納と、その読み手は [残りのシステムコール](#the-remaining-syscalls) にある。`main + 0x1C36C8` クラスのフィールドは、そのコンストラクタと自身のコードによって書かれる（[ROM バッファの後ろにあるもの](#what-follows-the-rom-buffer-the-sloop-component)）。3 つ目のロード時パッチは待ちループを置き換える。不適語フィルターの 2 つのバッファは、ディスパッチャー自身のフレーム内で長さで制限される（[不適語フィルター](#the-bad-word-filter)）。フラッシュセクターの経路の境界は [フラッシュセクターの経路](#the-flash-sector-path) にある。

Pia 側は両端が解読されている。ゲストの `RfuGameData` とユーザー名は、アドバタイズのレコードに詰め直され base85 でエンコードされる（[アドバタイズのレコード](#the-advertisement-record)）。相手の `NetworkInfo` のバイト列は、候補リストに一字一句そのまま届く（[ラッパー独自のスキャンパイプライン](#the-wrappers-own-scan-pipeline)）。相手のセッションメッセージは、ハンドラーが読む前に型ごとの境界を通過する（[Pia のセッションメッセージディスパッチャー](#the-pia-session-message-dispatcher)）。続く [ワイヤーのパース節](#the-pia-librarys-own-wire-parsing) は、静的リンクされた `PiaCommon-6_42_1` の経路を UDP ソケットからセッションキューまで追う。その追跡は、長さチェックや全メッセージハンドラーの網羅的な検証ではない。

#### 残りのシステムコール

ハンドラーのアドレスは、`main + 0x17D7F6` のジャンプテーブルから得る `main + 0x05706C + entry * 4` である。最後の列は、`sloop-svc` を付けた Mystery Gift クライアントから 1 回発行したときに表示されたものである。

`component + 0x6052A0` は 16 バイトである: 4 バイトのカウント、4 バイトの未使用、`main` へのポインタ 8 バイト。起動直後では、カウントは 1、ポインタは `main + 0x1E8D20`、占有されたスロットの後に 2 つの null が続くポインタの配列である。

タグ付きプロパティのディスパッチャー `main + 0x4EBD0` は、コンポーネント上のリスナーリストを走査する: `component + 0x10` の `0xd0` のエントリ、`+0x688` のカウント、`+0x690` の有効バイト。最初のワードが 2 であるエントリごとに、`entry - 8` の 8 バイトとタグ付きエントリを伴って、コンポーネントの vtable スロット `+0x50` を呼ぶ。セッター `main + 0x058BB4` は `0x4757` のリスナーである。`main + 0x50618` の `0x59` リスナーは、`[tagged entry + 4]` の値を `component + 0x3324 + index * 4` に書き込む。その index は `[x2]` から読まれ、`main + 0x4DB0C` によって 0..7 に制限される。`0x59` のエントリを組み立てたり、その 3 つ目の引数を供給したりするシステムコールはなく、ディスパッチャーの 12 回の呼び出しは、ラッパー内部のフィールドからエントリを組み立てる。`0x4757` リスナーが `component + 0x6052A0` に格納するカウントを読むのは、ゲッター `main + 0x058BA4`（`swi 0x50`）だけである。イメージ内でオフセット `0x6052A0` または `0x6052A8` を作る、ほかのすべてのコード箇所は、init のときにそれ自体かその隣のポインタを書き込む。`0x4F` の呼び出し元が供給する値には、何の効果もない。

ふしぎなおくりもの検索を行うコンソール自身は、バッファスクリプトの前に `swi 0x47` を発行し、`activity` 0x15（`ACTIVITY_WONDER_CARD` [include/constants/union_room.h:46]）を広告する。ペイロードの呼び出しはそれを上書きする。`main + 0x0586B4` のブレークポイントは、`x8 + 0x280` を通して `component + 0x605360` を読む。ゲームデータのオブジェクト（vtable `main + 0x1C3B30`）は、`bkpt #0x52` のフックテーブルが解決する CPU/バスのオブジェクト（vtable `main + 0x1C3878`、領域テーブル、システムコール 0x45、0x48、0x52、0x55、0x62）の兄弟である。ライブのアドレスは `0x100000000` だけずれている。

0x45 が書き込む候補ごとのレイアウトは未確定である。コピーループのバイト数が `sizeof(struct RfuTgtData)` と一致しない。依存する前に、ライブで読むこと。

`swi 0x47` がコピーする `component + 0x6050D8` の 24 バイト（[main + 0x058694]、ゲストの `r0` のバッファからの事前添字付きストア）は、同じハンドラーによって読み戻され、アドバタイズのレコードに詰め直される。`component + 0x605360` の読み手は、アクティビティの差分 `main + 0x058698`（`component + 0x6050E0` 経由）と、`svc_SetActivity` のセッター `main + 0x058B40` である。どちらもアクティビティコードを比較するか格納する。

#### アドバタイズのレコード

`swi 0x47` ハンドラーは、アドバタイズが運ぶ 24 バイトの RFU レコードを、ゲスト自身の `RfuGameData`（16 バイト）と `gHostRfuUsername`（8 バイト）から組み立てる [include/link_rfu.h:103-115, src/sloopsvc.c:34-46]:

| レコード | 元データ |
| --- | --- |
| `[0:2]` | `RfuGameData[2:4]`、トレーナー ID（`compatibility.playerTrainerId`） |
| `[2:10]` | ユーザー名 |
| `[10:12]` | ラッパーの RFU セッション ID、`main + 0x3F2E0([component + 0x6050D0])` |
| `[12:16]` | `RfuGameData[4:8]`、`partnerInfo` |
| `[16:20]` | 検索ワード。`RfuGameData[0:2]` と `[8:12]` から詰める |
| `[22:24]` | `RfuGameData[8:10]`、`tradeSpecies` |

検索ワードのビットは、2 つの元ワードから来る。0-6 はアクティビティ（`RfuGameData` のビット 16-22）、7 は性別（ビット 24）、8-10 はバージョン（`RfuGameData[0:2]` のビット 10-12）、11-14 は言語（ビット 0-3）、15 は `startedActivity`（ビット 23）、16 は `canLinkNationally`（ビット 7）、17 は `hasNationalDex`（ビット 8）、18-23 は `tradeType`（ビット 10-15）、24 は `gameClear`（ビット 9）、25-31 は `tradeLevel`（ビット 25-31）。`hasNews` と `hasCard`（ビット 4 と 5）はコピーされない。`[20:22]` の 2 バイトは、フレームが保持していたままになる。

エンコーダー `main + 0x2A90` は、4 バイトのグループごとに 5 文字を、下位の桁から先に書く。アルファベットは `0x23` から上へ、`0x5C` を飛ばして並ぶ。出力が与えられた容量を超えるときは拒否する。ハンドラーは 24 バイトに対して容量 `0x20` で呼ぶので、30 文字が収まり、テキストは `component + 0x6C0` に、その `strlen` は `component + 0x700` に格納される（`main + 0x15FAE0` と `main + 0x15FB20`、`strlen`/`memcpy` の PLT スタブ）。

ホストのビーコン（`pokeldn/frlg/link/host_beacon.py`）がクローンする取得済みのアプリデータは 122 バイトである: Pia のシステムヘッダーの `0x5C` と、トレーナー ID `0x1050`、名前 `GREEN`、RFU セッション ID `0xac65`、検索ワード `0x1584`（アクティビティ 4、バージョン 5、言語 2、ビット 7 が立つ）として読み戻される 30 文字。

レコードのテキストは、ハンドラーがその機会のために組み立てるアドバタイズデータのビルダーに入る（クラスの vtable `main + 0x1CB8C8`、コンストラクタ `main + 0x87514`）。`+0x1C` には `0x180` バイトの Pia アドバタイズ領域があり、使用サイズは `+0x18` にあって `0x5C` のヘッダーから始まる。アプリデータのポインタ `main + 0xA2C70` は `+0x78` に、アプリデータのサイズ `main + 0xA2C90`（使用量から `0x5C` を引いたもの）は `0x124` で頭打ちにされる（スロット `+0x28`、`main + 0x875AC`。ヘッダーのオフセット `0x5C` はスロット `+0x30`、`main + 0x875A4`）。`main + 0xA3480` は、それが `+8` に保持するバッファオブジェクトを通して、アプリデータのオフセットに 30 文字を追記する（その容量はバッファの vtable スロット `+0x28`、使用サイズはバッファの `+0x18`、追記はバッファの `+8` のビット 1 を立てる）。その唯一の呼び出し元はハンドラー（`main + 0x58838`）である。

ハンドラーは続いて `main + 0x58854` でビルダーを届ける: `x0 = [component + 0x3528]`、`main + 0xB1304`。そのメソッドは `[session + 0xD0]` のメソッドを呼び、それを引数として渡し、`+0xD8` の u32 をゼロにしてから次を呼ぶ:
`main + 0xD4DD0(x0 = [session + 0x70], x1 = [session + 0xD0], x2 = [session + 0x30], x3 = the
builder)`。配信は `X = [session + 0x30]` を取り、`X` のスロット `+0xD8`（true を返す必要がある）と `+0xE8`（false を返す必要がある）でゲートしたあと、`X` の vtable スロット `+0xA8` を `(X, [session + 0x70] + 0x90, builder)` として呼ぶ。セッションの `+0x30` は、セッション所有者の `+0xB8` である `[[session + 8] + 0xB8]` から、`main + 0xAF760` によって設定される。

`X` は facade クラスの形をしている。`nn::pia::local::LocalFacade`（vtable `main + 0x1CB548`）と `nn::pia::net::NetFacade`（`main + 0x1CBE60`）は実装を共有し、そのスロットは次のとおり: `+0xA8` = `main + 0x8D4AC`、`+0xD8` = `main + 0x8D84C`（facade の `+0x28` が立ち、`+0x30` が非 null のとき true）、`+0xE8` = `main + 0x8D920`（`[[facade + 0x30] + 0x12D8]` が非 0 のとき true）。facade の `main + 0x8D4AC` は `main + 0x8C6FC` を通して検証し、マネージャーをロックする（`[facade + 0x30] + 0x2B8` を `main + 0x94B78` 経由で。つまり facade は `+0x30` にマネージャーを保持する）。ビルダーの `+8`（`main + 0xA3710`）の値を取り、マネージャーの `main + 0x99C3C` に渡し、次に `[facade + 0x48]` にトランスポート、`[facade + 0x40]` に状態 8 を記録する。マネージャーはバッファを、ジョブの受信側（下記）に渡す。ジョブの公開側は、マネージャーのブロックビルダーを通して `nn::ldn::SetAdvertiseData` に到達する。

ワンフレームでエミュレーター上の 8 ホップすべてを確認した。`swi 0x47` はバージョン 5、言語 2、トレーナー ID `0x1234`、アクティビティ `0x45`、ユーザー名 `PKLDNTST` を運んでいた。ハンドラーの影が 24 バイトを受け取った。ゲートのバイトとアドレスの組を等しくなるよう書き換えると、セッションの `main + 0xB1304` が実行され、facade の `main + 0x8D4AC` がスタックのビルダーを受け取った（そのアプリデータは 30 文字のレコードテキスト ``Z8J4;Vk.+>`.uN;#####<P?>######`` を運んでいた）。マネージャーの `main + 0x99C3C` と、その `+0x250` のデリゲートの `main + 0xA28E4` がそれを次へ渡し、ジョブの `+0x60` が検証して、`0x180` バイトの領域をジョブのビルダーの `+0x8C0`（`main + 0x87578`）にコピーした。ジョブの `+0x130` はステートマシンから実行され、マネージャーのブロックビルダー `main + 0x80C3C` は、ジョブのビルダーを同じレコードテキストとともに受け取った。ジョブ自体はステートマシンとして動く。その `+0x38`/`+0x40` は現在のステップを保持し（1 ビットの仮想フラグを持つ vtable スロット、または直接の関数）、基底メソッド `main + 0x6EAA0`（"ExecuteCore"、ジョブのスロット `+0x20`）がそれをディスパッチする。見られたステップは、vtable スロット `0xB8`、`0xC8`、`0xD8`、`0xE8`、`0xF8`、`0x108`、`0x118`、`0x138`、`0x148` と、`main + 0x891F0` などの直接の関数である。

マネージャーのクラス（`nn::pia::local::LdnProtocol`。vtable `main + 0x1CA5B0`、ポインタは再配置済みスロット `main + 0x1D1E98` から `main + 0x7E244` で作られる）は、自身の `NetworkInfo` を `[manager + 0x2D8] + 0xB8` に保持する。アドバタイズのサイズは `NetworkInfo + 0x26A`（`+0x322`）、ブロブは `NetworkInfo + 0x26C`（`+0x324`）、`NetworkInfo + 0x282` は `+0x33A` である。そのメソッド `main + 0x80C3C`（ビルダーのアプリデータの唯一の消費側。`main + 0xA2C70` にはこの呼び出し元が 1 つだけある）は、`+0x380`（`NetworkInfo + 0x2C8`）をゼロにし、そこにアプリデータをコピーし、サイズをアプリデータに `0x5C` を足したものとして `+0x322` に書く。`0x5C` バイトの Pia システムヘッダーは、ホルダー自身のメソッド（その vtable スロット `+0x68`）で `+0x324` に書き込み、`nn::ldn::SetAdvertiseData(holder + 0x324, size)` を呼ぶ（PLT `main + 0x160A90`、GOT `0x1d3800`）。さらに 2 つのマネージャーのメソッドが、2 つ目のオブジェクトのデータをアドバタイズする（`main + 0x7F990`、`0x81140`: `[object +

### プレイレポートの組み立て元

ゲームレポートはフラッシュイメージから解析される。`main + 0x05A280` はセクターのフッター（署名 `0x08012025`）で最新のスロットを見つけ、その 14 セクター（0xE000 バイト）を `component + 0x140 + 0x70` にコピーする。`main + 0x05A370` はそれを、ゲームごとの記述テーブルで走査する: バッジのフラグビット、殿堂とポケモン図鑑のフラグ、そしてセーブデータの鍵で XOR されたお金。すべてのオフセットとビット番号は静的テーブルから来る。コピーされたセーブデータが供給する唯一の個数 `playerPartyCount`（1 バイト）が `main + 0x05AAE0` のパーティ走査を制限し、0x64 バイトの 255 エントリは 0xE000 のコピーの内側に収まる。`swi 0x57` は `MonsSelect`（スターター。`main + 0x17DA8C` の内部から全国図鑑へのテーブルを通る）を埋める。出力される JSON は、テーブルの固定の部分集合を運び、`MonsSelect` を省く。`swi 0x62` は `component + 0xE1B0` を増やし、それは `CommsError` になる。各呼び出しは、Ryujinx の `ServicePrepo ProcessPlayReport` がホストのログに出力する次のレポートの `CommsError` に 1 を加える。`swi 0x55` が `component + 0xE1BC` に格納する SaveBlock2 ポインタの唯一の読み手は `main + 0x0577D8` で、これは `optionsButtonMode == 2`（L=A）を調べる。格納箇所はハンドラー自身の `main + 0x057308` で、ディスパッチャーが `main + 0x057058` で `x8 = component + 0xE1B0` を設定し、ハンドラーがゲストの生の `r0` を `[x8 + 0xC]` に格納する。読み手は、格納されたワードを領域テーブルで折りたたみ、境界チェックしたうえで、折りたたんだ領域の 1 バイト `+0x13` を読む。どちらもゲストに相対的で、境界チェックされる。

`main + 0x059CE4` はゲームコードからテーブルを選ぶ。アプリはすべて 5 つを持つ:

| ゲームコード | テーブル | `Flavor` の基底 |
| --- | --- | --- |
| `AXV?` | ルビー | 0x10 |
| `AXP?` | サファイア | 0x20 |
| `BPE?` | エメラルド | 0x30 |
| `BPR?` | ファイアレッド | 0x40 |
| `BPG?` | リーフグリーン | 0x50 |

`Flavor` は、言語の `JEFIDS` の索引を加える。そのためフランス語版ファイアレッドは `0x42`（66）を報告する。

テーブルは 14 セクターを ID の順に、それぞれ 0x1000 ずつ扱う。バイトオフセット `o` は SaveBlock1 のオフセット `((o >> 12) - 1) * 0xF80 + (o & 0xFFF)` である。フラグは `(bit, byte)` の組で、ビットが 7 を超えるときは存在しないことを意味する。3 つのデコンプと照合して解読した:

| --- | --- | --- | --- |
| バッジ、8 フラグ（開始位置） | バイト `0x23A0` のビット 7、`FLAG_BADGE01_GET` 0x807 | `0x23FC` のビット 7、0x867 | `0x2064` のビット 0、0x820 |

### The bad-word filter

`swi 0x4D`（ハンドラー `main + 0x0571FC`）は、`r0` を GBA のアドレスとして解決し、その後ろに 256 バイトを要求し、ASCII 文字列を UTF-16 に変換してプラットフォームの不適語チェックを実行し、文字列をその場で書き換える。`r1` が非 0 だと、ゲームが使わない 2 つ目のモードを選ぶ（`r1` = 1 も同じ方法でマスクされる）。ゲームは `svc_BadWordCheck` を通じて呼び出し、名前を ASCII に変換して戻す [sloopsvc.c:211]。名前入力画面は、0 を返したときだけ入力された名前を保存する [naming_screen.c:686]。

| 送信された文字列 | `r0` | 処理後の文字列 |
| --- | --- | --- |
| `hello world` | 0 | `hello world` |
| `hello fuck` | 1 | `hello ` の後に 4 つの `0xA1` バイト |
| `POKELDN` | 0 | 変更なし |
| `ASSASSIN` | 0 | 変更なし |
| `NINTENDO` | 0 | 変更なし |

経路は [main + 0x0571FC -> main + 0x057458] である。ハンドラーは `r0` を折りたたみ、折りたたみの後ろに `0x100` バイトを要求し、文字列をフレームの `-0x100` にある `0x100` バイトのスタックバッファにコピーする（`main + 0x85645F0` のコピーは、その `w1 = 0x100` の引数で制限される）。UTF-16 への変換は、そのバッファから `sp + 0x10` の `0x200` バイトのバッファへ行われ（[main + 0x855F100]、`w2 = 0x200`）、不適語チェックはグローバルポインタ（[main + 0x574AC、呼び出し先 `main + 0x86664C0`]）を通して行われ、マスクされた文字列はゲストの fold にコピーし戻される。どちらのバッファもディスパッチャー自身の `0x310` バイトのフレームの内側で終わる（`sp + 0x210` と `sp + 0x310`）。そのコピーは保存レジスタにも、フレームの外側にも届かない。置き換えバイトは定数 `0xA1` である。

### The wrapper's own scan pipeline

ラッパーは、自前の PLT（`main + 0x160B70`。`ScanPrivate` は `main + 0x160B60`）を通して `nn::ldn::Scan` でネットワークを走査する。マネージャーオブジェクト `x23` から、呼び出し箇所 `main + 0x80944`/`0x8095C` で `w2 = 0x18` のネットワーク数を指定し、結果を `manager + 0x14C0` のインライン配列に書き込む（24 エントリ × `0x480`。初期化時に 1 回だけゼロ埋めされる。`main + 0x7E290`）。エミュレーターのネットワークサービスは、ワイヤーの `ScanResponse` 本体を、長さのチェックなしに `NetworkInfo` へキャストするので、相手側のフィールド値は一字一句そのままラッパーに届く。

消費ループ（`main + 0x80A20..0x80B9C`）は配列を走査する。`sp + 0x128` の `0x480` バイトのレコードをゼロにし（`main + 0x874A0`）、エントリをそこへ変換する（`main + 0x87374`）。これは `0x480` 全体を `record + 0xB8` へ 1 回の memcpy で行い、その後にビット単位で正確なフィールド読み取りを行う: ソースの `+0xA`、`+0x11`（15 バイトの整数の解析。`main + 0xA9830`、`b`/`x` 接頭辞付きの 16 進・8 進・10 進・2 進を、進むたびに境界チェックする）、`+0x26A`（アドバタイズデータのサイズ）、`+0x281`/`+0x282`、`+0x11A..0x11F`。レコードの `+0x90`、`+0xA0`、`+0xA2`、`+0xA4`、`+0xA6`、`+0xB0` に格納する。その後、レコードをフィルターの仮想関数と受け入れの仮想関数に通す（`main + 0x80A88..0x80A94`）。

受け入れられたネットワークは、親の候補リストに入る。`owner + 0x6050F2` に 16 スロット × `0x1A` バイトがあり、書き込みインデックスは `owner + 0x605294` にあって 15 で頭打ちになる（`cmp w8, #0xf; b.le` [main + 0x58C3C]）。配列は `+0x605292` で終わり、インデックスと接している。埋める処理は、オーナークラス（vtable `main + 0x1C3B30`）のスロット `+0xA0`（`main + 0x58BF8`）で、`main + 0x536A4` によってスキャン結果のステーションごとに呼ばれる。ステーションの名前の長さは、ステーション自身の仮想関数（[スロット `+0x50`]）から来て、`sub w8, w0, #1; cmp w8, #0x3f; b.hi`（[main + 0x5364C]）が、呼び出しの前に `x6 > 0x40` のものを落とす。埋める処理の内側では、`sp + 7` にある `0x41` バイトのスタックバッファが `memcpy(sp + 7, x5, x6)` を受け取る。末尾をゼロにする memset は `x6 > 0x40` のとき省略される [main + 0x58C68]。`x6 > 0x40` の場合、コピーはフレームに保存された `x29`/`x30` に届く（バッファのオフセット `0x59`/`0x61`）。デコードできた呼び出し元は、まず長さを頭打ちにするので、そこを通る長さは最大で `0x40` である。クラスのスロット `+0xA0` を読み込むイメージの 8 箇所のうち、このクラスへのディスパッチが確認されているのは `main + 0x536A4` だけである。

エミュレートしたコンソールで、ホスト 1 台がアドバタイズした場合に計測した: 件数 1、スロット 0 はホストのアドバタイズをバイト単位で保持していた。16 バイトのゲームデータ（アクティビティ `0x15`）、8 バイトの表示名、親 ID の u16（`0x59f1`）。

`main` では、リストは埋める処理の一族（`main + 0x58BB4`、`0x58BE4`、`0x58BF8`）を通してだけ書き込まれ、すべて仮想である。イメージ内のそのほかの、コンポーネントを起点にしたアクセスはすべて読み取りである。オーナークラスの vtable ポインタ `main + 0x1C3B30` は、`main` では再配置済みスロット `main + 0x1D1B38`（値は `main + 0x1C3B20`）を読み込み、`0x10` を足すことで作られる。`main + 0x58558` は、それを格納しながら `component + 0x6050F0` の候補リストをゼロにする。`main + 0x58FD8`/`0x59054` は、2 つのコンポーネントの初期化子にある。同じ慣用句が、マネージャークラスのポインタ（スロット `main + 0x1D1E98`。`main + 0x7E244`、`0x7E4D0`）と、セッションクラスのポインタ（スロット `main + 0x1D2770`。`main + 0xB7D24`、`0xB7E78`）も作る。

### Pia セッションメッセージのディスパッチャー

ラッパーのネイティブな Pia セッション受信は、`main + 0xB9FC0` の型スイッチである。ノードの連鎖を走査する。`[node + 0x10]` がメッセージ本体で、その最初のバイトが型である。一方、ノード自身の先頭 3 バイトは、キューのキーとして使われるプロトコルアドレスである。ノードは、マネージャーオブジェクトの `[x0 + 0xA0]` が非 0 で、型が `0x11` 以下のとき、ディスパッチされる。スイッチは `adr x8, main + 0xB9FD0`（`main + 0xB9FCC`）、`ldrb w9, [main + 0x180FC9 + type]`（`main + 0xB9FC4`。`adr x27, main + 0x180FC9` は `main + 0xB9EFC`）、`add x8, x8, w9, lsl #2`、`br x8` である。`main + 0x180FC9` のバイトテーブルは型ごとに 1 エントリを持ち、18 個のケースブロックは `main + 0xB9FD0 + index * 4` に並ぶ。それぞれは無条件の `b main + 0xB9F80` で終わり、それぞれがハンドラーを呼ぶ（`main + 0xBCB60`、`main + 0xBE438`、`main + 0xBE8BC`、...）。

各ハンドラーは、メッセージに触れる前に読み取りをメッセージに対して境界付けする。型 1 のハンドラー `main + 0xBE438` は `cmp w2, #0x15; b.ne` で始まり（`0x15` バイトのメッセージだけがコピーに届く）、監査で解読された型ごとのテストは、型 2 が `>= 4`、型 3 が `== 0x16 or 0x22`、型 4 が `== 0xf`、型 6 が `>= 0xf`、型 9 が `== 0x1e or 0x2a`、型 10 と 12 が `== 0x15`、型 11 が `>= 0xe`、型 13 が `== 0xa`、型 14 が `>= 0x4d`、型 17 が `>= 0xd` である。可変長のリーダー `main + 0xC0D90` は、ビット数からバイト数を求め、宣言された長さと比較し、短ければ拒否する。この集合のどのハンドラーも、メッセージが決める長さを固定バッファにコピーしていることは確認されなかった。

型は Pia セッションプロトコル自身のメッセージ型である。ホストのセッション層（`pokeldn/ldn/pia_connect.py`）は、それらを 0 参加要求（join request）、1 参加承認（join ack）、2 参加応答（join response）、3 退出要求（leave request）、4 退出応答（leave response）、5 更新（update）、6 更新承認（update ack）、7 ホスト移行の開始（start host migration）、8 移行の承認（migration ack）と番号付けする。型 1 のハンドラー `main + 0xBE438` は、21 バイトのメッセージを、`[0]` が型、`[1:9]` と `[9:0xB]` が送信元ステーションの固定 ID と可変 ID、`[0xB:0x13]` と `[0x13:0x15]` が宛先のものとして読む。宛先のペアがトランスポート自身のもの（[transport + 0x1B8]、`+0x1C0`）と一致しない限り拒否する。そのあと送信元ステーションを探し、それに対して `main + 0xC9B4C` を呼ぶ。型 2 のハンドラー `main + 0xBE8BC` は、4 バイト以上を受け入れ、マネージャーの状態バイト（`+0x30 == 0xFD`）で判定し、メッセージのバイト 3 の値を 3 から 0x10 の範囲で切り替える。

受信パスの所有者は、セッションクラス（`nn::pia::session::SessionProtocol`。vtable の基底 `main + 0x1CE8E0`。vtable ポインタは再配置済みスロット `main + 0x1D2770` から `main + 0xB7D24`/`0xB7E78` で作られ、コンストラクタは `main + 0xB7E70`）である。ポンプはそのクラスの vtable スロット `+0x50`（`main + 0xB9CA0`）で、ウォーカー `main + 0xB9DB0` を呼ぶ。連鎖は、`[protocol + 0xF8]`（プロトコルマネージャーが取り付けるセッションのパケットリーダー）のオブジェクトにある `+0x70` のテーブルにかかる（`main + 0xD6D68` がそのアドレスを返す）。メッセージオブジェクトは `main + 0xD4430` で構築される（その vtable ポインタは再配置済みスロット `main + 0x1D27B0` から来る）。Pia ライブラリ自体は、`main` に静的リンクされている（イメージは `SDK MW+Nintendo+PiaCommon-6_42_1-Release` とセッションジョブの名前を持つ）。

`main` は Pia 6.42.1 のスタック全体をリンクしている（イメージは `PiaCommon`、`PiaLocal`、`PiaNet`、`PiaSession`、`PiaTransport`、`Pia_ZStandard` の `SDK MW+Nintendo+...` リリース文字列を、マングルされたクラス名とともに持つ）。vtable だけで上に記述したクラスは次のとおり:

**パケット。** パケットオブジェクトは `0x1D18` バイトである。解析済みのヘッダーは `+8` から `+0x24` まで、データグラムのバッファは `+0x30` にある（容量 `0x1C5C`。追記ヘルパー `main + 0x75664` と `main + 0x75694` が境界を与え、後者はフッターのサイズを `+0x14` に記録する）。受信サイズは `+0x1C90` にある（ローカルの受信経路は、`0x5AC` バイトの受信とその上限に対するチェックの後、`main + 0x7DE40` でこれを格納する）。その解析（`main + 0x752D4`、vtable スロット `+0x18`。エントリ `main + 0x752C8` がオブジェクト自身のバッファと定数 `0x1C5C` を供給する）は、`0x1C` バイトより多くを要求し、`0x1D` バイトのヘッダーを読む:

| 位置 | サイズ | 意味 | 格納先 |
| --- | --- | --- | --- |
| 0x00 | 4 | マジック `0x32AB9864`（ビッグエンディアン） | `+0x08` |
| 0x04 | 1 | ビット 0-6 がバージョン、暗号化フラグ `0x80` | `+0x0C` |
| 0x05 | 1 | 1 バイト。送られた通りに保持 | `+0x0D` |
| 0x06 | 2 | 宛先の変数 ID（ビッグエンディアン） | `+0x0E` |
| 0x08 | 2 | 送信元の変数 ID（ビッグエンディアン） | `+0x10` |

このアプリが話すバージョンは `0x10`（16）である。有効性の検査 `main + 0x75610` は、マジック、`([+0xC] & 0x7F) == 0x10`、`size - 0x1D < 0x1C40` を要求する。ペイロードのポインタは `+0x4D`（ヘッダーの後ろのバッファ、`main + 0x75474`）である。`main + 0x75458` は `buffer + t` を返す。ここで `t = (n + 0x1D)` は 32 ビット演算で、`(t >> 2) > 0x716` のときは null を返す。この容量の検査は `t` を `0x1C5B` まで通す。メッセージのウォーカーは別に、受信サイズからヘッダーとフッターを引いた値（`main + 0xDE278`）と照合する。

**ソケットと受信ストリーム。** ソケットは小さなホルダーである（コンストラクタ `main + 0x6D93C`: `+0` に fd `-1`、`+4` にカウント、`+8` にファミリー、`+0xC` にプロトコル）。`main + 0x6D95C` が開き（`nn::socket::Socket`、PLT `main + 0x160940`）、`main + 0x6DBF4` が閉じ（`main + 0x160950`）、`main + 0x6DCD0` がバインドし（`main + 0x160960`）、`main + 0x6DE6C`、`0x6DF44`、`0x6E00C`、`0x6E0F0` がオプションを設定する（`main + 0x160970`）。データグラムの呼び出しは、`main + 0x6E1D0`（`nn::socket::RecvFrom`、PLT `main + 0x160980`、フラグ `0x80`、送信元アドレスは `main + 0x6E9D0` で元に戻される）と、`main + 0x6E538`（`nn::socket::SendTo`、`main + 0x160990`）である。ローカルの受信ストリーム（変数 ID は `+0x88`、ロックは `+0x68`、ソケットホルダーのポインタは `+0x18`）は、ポンプ `main + 0x7DD10`（vtable スロット `+0x10`）を走らせる。これはパケットのバッファに受信し、そこへヘッダーを解析する（`main + 0x7DDEC`。`main + 0x6E1C8` はサンク）。パケットフィルター `main + 0x91280`（スロット `+0x20`）は、まず有効なパケットを要求する。バージョンが 7 以上で、フッターが空でなく、宛先の変数 ID が 1 以下のとき、フッターは少なくとも 2 バイトを含まなければならず、そのストリーム自身の ID（`+0x88`）は非 0 で、ビッグエンディアンの u16 の受信者 ID（`footer_size >> 1` 個のエントリ）の中になければならない。別に、`([+0xC] & 0x7E) >= 6` かつ宛先が 2 以上のときは、ストリーム自身の `+0x88` と等しくなければならない。

フィルターは、受信者のポインタを `packet + (size - footer) + 0x30` として作る。これは `main + 0x912EC` の `sub w8, w8, w9` の後である。メッセージのウォーカー `main + 0xD6460` と、パーサー `main + 0xDE278` は、ウォークの上限を `size - footer - 0x1d` として作る（`main + 0xD651C`、`main + 0xDE298`）。どちらの減算も、フッターのサイズがデータグラムに収まるかでゲートされていない。フッターのサイズのバイトは、平文のヘッダーのデータグラムのオフセット 12 にあるので、相手がそれを自由に設定できる。データグラムのサイズを超えるフッターのサイズでも、フィルターはフォールトしない。フッター `0x40` を付けた 31 バイトのデータグラム 6 個はソケットに届き、セッションは動き続けた（エミュレーターで計測）。

**スレッド。** トランスポートの受信ループと送信ループは、`nn::os` のスレッドである。名前は "Pia ReceiveThreadStream"（`main + 0xE9020` で開始し、名前は `main + 0xE9034` の `adr` で得る）と "Pia SendThreadStream"（`main + 0xEA758`）で、`main + 0xF6010` を通して作られる（`nn::os::CreateThread`、PLT `main + 0x15FDF0`、および `StartThread`、`main + 0x15FE00`）。

**受信からセッションハンドラーまで。** 受信したセッションメッセージは、セッションのパケットリーダーによってパースされ、アドレスごとのテーブルに置かれる。セッションプロトコルは、そのテーブルを各更新で走査する。

`nn::pia::session::SessionPacketReader`（vtable `main + 0x1CE748`）は `nn::pia::transport::PacketReader`（vtable `main + 0x1CF1A8`）を継承する。リーダーの `+0x30` メソッド（`main + 0xD5DE0`）は受信したパケットを処理し、`main + 0xD6460(reader, packet)` を呼んでそのメッセージを走査する。ウォーカーはデータグラムのオフセット `0x1D` から始まり、`packet_size - footer_size`（`main + 0xDE278`、`0xD6510`-`0xD6538`）の手前で止まる。フッターはペイロードに続く。各メッセージは `main + 0x74EA8` でパースされ、キューのキーとして使われるプロトコルアドレスは、リーダーの `+0x78` の仮想関数（`main + 0xD6D0C`: メッセージの `+0x2C` の u16 と、その上位部分としての `+0x2E` のバイト）を通して取られ、`main + 0xD6944(table, address, message)` が呼ばれる。

テーブルは `reader + 0x70` に埋め込まれている。`+0` が u32 のバケット数、`+8` がバケット配列へのポインタ（バケット 1 つあたり 0x18 バイト。連鎖の先頭が `+0`、末尾が `+8`）、`+0x40` が任意のハッシュコールバックである。`main + 0xD6944` は、`index * 0x18` を足す前に配列のポインタを読み込む。バケットはテーブルの中に埋め込まれていない。バケットの添字は `callback(address) % count` で、コールバックが設定されていなければ `(address[0] + address[1] + address[2]) % count` である。`main + 0xD71F0(bucket, address, message)` はノードを受け取り、メッセージをそこにコピーし（`+0` の 3 つのアドレスバイト、`+0x10` のボディのポインタ、`+0x18` の ID、`+0x20` から `+0x30` までの追加フィールド、残りは `main + 0x74C54` 経由）、バケットの二重連結リスト（次は `+0x78`、前は `+0x80`）に追加する。

プロトコル側: `nn::pia::session::SessionProtocol` の `+0x50` 仮想関数（`main + 0xB9CA0`）は、更新のたびに `main + 0xB9DB0` を実行する。これは `[protocol + 0xF8]`（後述のとおり取り付けられたリーダー）を読み、リーダーのテーブルを `+0x70` で取り、プロトコル自身の 3 バイトのアドレスのバケットを計算する（`+0x120` の u16 と `+0x122` のバイト。`+0x18` の仮想関数 `main + 0x828E4` が読む。その組は `nn::pia::transport::Protocol` のフィールドで、`main + 0xDA614` が設定する）。連鎖を歩き、ボディ `[node + 0x10]` の最初のバイトでジャンプテーブルを通して各ノードをハンドラーにディスパッチする（`main + 0xBCB60`、`main + 0xBE438`、`main + 0xBE8BC`、`main + 0xBF2D4` など）。渡すのは `(protocol, node, id)` である。

取り付け: プロトコルマネージャー（所有者の `+0xC8` に埋め込まれ、プロトコルテーブルは `+0x18` にある）は、自身のテーブルを走査し、すべてのプロトコルの `+0xF0` と `+0xF8` を、所有者の `+0xF8` と `+0x100` から設定する（セッター `main + 0xDA8C8` と `main + 0xDA8D0`、ブロードキャスト `main + 0xDB740`。`main + 0xEC0E4` のペアで呼ばれ、どちらかの引数がゼロなら拒否する）。`+0xF8` のオブジェクトはリーダーであり、だからウォーカーのテーブルはリーダーの `+0x70` なのである。

ライブでは、マネージャーは `[session + 8] + 0xC8`（上記の所有者）にあり、そのテーブル `[manager + 0x18]` は、`+0` に u32 のバケット数、`+8` にバケット配列へのポインタを持つ。バケットは 1 つ 0x18 バイトである。`+0` がノード、ノードの `+8` がプロトコル、ノードの `+0x30` が次のノードへ連鎖する。エミュレートしたセッションでは、テーブルのカウントは `19` で、プロトコルはちょうど 6 つあり、種類ごとに 1 つずつ、プロトコルのアドレス（u16。`+0x122` のバイトはゼロで、各プロトコルの `+0x108` はネットワークの Pia 変数 `0x8fa2`/`0x0766` を保持する）で鍵付けされていた: `0xfd01` `nn::pia::local::LdnProtocol`、`0xfd03` `nn::pia::transport::RttProtocol`、`0xfd05` `nn::pia::transport::UnreliableProtocol`、`0xfd0a` `nn::pia::transport::ReliableProtocol`、`0xfd0d` `nn::pia::session::SessionProtocol`、`0xfd0f` `nn::pia::transport::MonitoringDataProtocol`。プロトコルはステーションごとではなく、種類ごとに 1 つである。`SessionProtocol` のポンプは単一のインスタンスを 8 回中 8 回たどり、リーダーのテーブルのノードは、プロトコルのアドレス（`0xfd0a`、メッセージ ID `0x60`）の下に登録されていた。インスタンスは `main + 0xB1F60` によって作られ、登録される（`main + 0xDB114` で `0xD8E8` バイトを確保し、コンストラクタ `main + 0xB7D0C` を使い、アドレスの組で鍵付けしてマネージャーのマップに挿入する）。Session のコンストラクタはそれを 1 回呼び、返されたアドレスを `+0x12`/`+0x14` に格納する。

`nn::pia::transport::Protocol` の基底（vtable `main + 0x1CF308`、コンストラクタ `main + 0xDA548`、vtable ポインタは再配置済みスロット `main + 0x1D2808` から）は、`+0x120`/`+0x122` に 3 バイトのアドレス、`+0xC8` にロック、`+0xF0`/`+0xF8` に取り付けられた組、`+0x100`/`+0x108` と `+0x110`/`+0x118` に設定された 8 バイト + u16 の値 2 組、`+0x123` に状態バイト、`+0xD8` にフラグを持つ。

## コンソールの送信メッセージを付け替える

`r0` は `&client->param` なので、`struct MysteryGiftClient` [include/mystery_gift_client.h:71] は、そこから固定のオフセットに置かれる:

| フィールド | `r0` からの位置 |
| --- | --- |
| `client->sendBuffer` | 0x10 |
| `client->link.sendSize` | 0x34 |
| `client->link.sendBuffer` | 0x3C |

`MysteryGiftLink_InitSend` は、渡されたポインタを格納する [mystery_gift_link.c:59]。CRC は送信時に、`link->sendSize` バイトにわたって `link->sendBuffer` から取られる [:166]。InitSend と送信の間で動くペイロードは、コンソールの送信メッセージを任意のアドレスに向ける:

    CLI_RECV -> CLI_LOAD_TOSS_RESPONSE -> CLI_RUN_BUFFER_SCRIPT -> CLI_SEND_LOADED

逆の順序では、InitSend がペイロードのパッチを上書きする。

CRC フレームと送信フレームの間で動く領域は、決してダンプしないこと:

```c
case 0:  header.crc = CalcCRC16WithTable(link->sendBuffer, link->sendSize);   // one frame
case 1:  SendBlock(0, link->sendBuffer + blocksize, ...);                     // the next
case 2:  if (CalcCRC16WithTable(...) != link->sendCRC) LinkRfu_FatalError();  // the one after
```

[mystery_gift_link.c:155]。`gRngValue`（0x03004220）はフレームごとに 2 ステップ進む。その上でダンプすると本体の CRC に失敗し、コンソールは "erreur de connexion" と報告する。`buffer_script.build_memory_dump` はそれと重なる範囲をすべて拒否する。その周りをダンプするか、4 バイトのチャネル経由でそれを返す `rng-trace` を使う。ほかの揮発性の領域も、同じ方法で見つけなければならない。

## ペイロード

### `trainer-id-probe`

24 バイトで、読み取りのみ。コンソールは数秒前に `MysteryGiftLinkGameData` で既に `playerTrainerId` を送っているので、答えは分かっている [mystery_gift.c:337]。

```arm
    ldrh    r3, [r1, #0x0A]         @ SaveBlock2.playerTrainerId[0..1]
    ldrh    ip, [r1, #0x0C]         @ SaveBlock2.playerTrainerId[2..3]
    orr     r3, r3, ip, lsl #16
    str     r3, [r0]                @ *param
    mov     r0, #1
    bx      lr
```

一致は、本物の `gSaveBlock2Ptr` に対して、デコンプの引数で ARM 状態で実行され、1 を返したことを意味する。異なる値は、引数かオフセットが間違っていることを意味する。`Buffer script status:` の行がない場合は、クライアントスクリプトの形が間違っているか、呼び出しに到達しなかったことを意味する。7 文字のプレイヤー名の終端が、ゲームデータの `playerTrainerId[0]` を上書きする [mystery_gift.c:364]。そのためホストは上位 3 バイトを比較する。

### `save-dump` と `memory-dump`

`memory-dump` は絶対アドレスを取る。`save-dump` は、どのビルドでも、r1 と r2 を通して任意のオフセットからどちらのセーブブロックでも読む。1 回の実行で最大 1024 バイト。`MGL_Receive` はそれ以上を拒否する [mystery_gift_link.c:102]。

    HOST --buffer-script save-dump --dump-block sav2 --dump-size 256 --version firered
    HOST --buffer-script memory-dump --dump-address 0x0201C000 --version firered

これらは `SaveBlock1.playerParty` を 0x0038 で、`money` を 0x0290 で（`SaveBlock2.encryptionKey` を 0xF20 で XOR した値）、バッグ、フラグと変数、そして IWRAM（`gRngValue`）に届く。

### `memory-dump-multi` と `memory-dump-scatter`

`MG_LINK_BUFFER_SIZE` が制限するのはメッセージであり、セッションではない。クライアントは 1024 バイトの受信バッファ [mystery_gift_client.c:140] からコマンドのスクリプトを走らせ、ダンプの 3 つ組

    CLI_LOAD_TOSS_RESPONSE -> CLI_RUN_BUFFER_SCRIPT -> CLI_SEND_LOADED

は収まる限り繰り返す。ループの前後に固定の 3 コマンドがあり、コマンド 1 つあたり 8 バイトとすると 41 回になる。`mg_script.MAX_DUMP_BLOCKS` はそれを 32 に抑える。途中で死んだセッションは、すべてのブロックを失うからである。16 KB のダンプは、ESP32 の無線で約 57 秒かかり、ブロックは約 2.5 秒おきだった。

`CLI_RUN_BUFFER_SCRIPT` は毎回のパスで画像を再コピーする [:238] ので、カーソルは `client->param` に置かれる。各パスは `base + index * 1024` を送り、次のインデックスを渡す。上位半分に `0x5A5A0000` がない `param` は、パス 0 である。

`memory-dump-scatter` は代わりにベースのテーブルを添字で引く:

    adr     r3, .Ltable
    ldr     r3, [r3, r1, lsl #2]    @ this block's own base
    str     r3, [r0, #0x3C]         @ client->link.sendBuffer

`adr` は PC 相対である。32 個のスロットすべてが埋められ、使われないものは最後のアドレスで埋められるので、余分なパスは、メッセージを 0 に向けるのではなく、保持しているブロックを再送する。散らばったブロックは、連続したブロックの約 4 倍の短い関数本体を、参加 1 回あたりに捕まえる。1 MB を超える 166 個の未読の関数本体の 1 セットについて:

| 1 回の参加、無線から受け取った 16 KB | 捕まえた本体の数 |
|---|---|
| `memory-dump-multi`、最適なベースの 16 個の連続したブロック | 22 |
| `memory-dump-scatter`、最も密な 16 キロバイト | 83 |
| `memory-dump-scatter`、32 ブロック | 166 のうち 119 |

読み取り可能性のガードは、散らばったブロックのそれぞれを検査する。ブロックは 1 つのファイルに端から端まで届く。`--dump-scatter A,B,C` は `script_read.dumps` が、それぞれをそのベースに配置し、`<run>[0]`、`<run>[1]`、... のタグを付けることを可能にする。`--dump-blocks 1` は、`CLIENT_SCRIPT_DUMP_MEMORY` をバイト単位で返す。

### `anchors`

11 個のワードを `client->sendBuffer` に書き込み、`link->sendSize` を 44 に広げる。`CLI_LOAD_TOSS_RESPONSE` がすでに `link->sendBuffer` をそこに向けているので、再ポイントは不要である [`MysteryGiftClient_InitSendWord`, mystery_gift_client.c:91]。

| ワード | 内容 | ある起動での値 |
| --- | --- | --- |
| 0 | `sub ip, pc, #8`。コンソールがコードを置いた場所 | 0x0201C000 |
| 1 | `lr`。呼び出し後の ROM アドレス [mystery_gift_client.c:276]。呼び出し元が THUMB なのでビット 0 が立つ | 0x08148C75 |
| 2 | `sp` | 0x03007DB8 |
| 3 | `r0` = `&client->param`。つまり `AllocZeroed` がクライアントを `gHeap` に置いた場所 | 0x020020D4 |
| 4-5 | gSaveBlock2Ptr、gSaveBlock1Ptr | 0x02024598、0x0202553C |
| 6-9 | `AllocZeroed` の 4 つのバッファ: 送信、受信、スクリプト、メッセージ | 0x02006510 .. 0x02007140 |
| 10 | InitSend が残した `link->sendBuffer`。ワード 6 と等しくなければならない | 0x02006510 |

ワード 4-5 は、戦闘とロードのたびに変わる [load_save.c:75]。ワード 3 と 6-9 はヒープの状態に依存する。ワード 1 は decomp の呼び出し箇所を固定し、ワード 10 がワード 6 と等しいことは構造体のオフセットを確かめる。バッファは 0x410 離れている（1024 バイトに 16 バイトのブロックヘッダーを加えたもの）。これは `malloc.c` が記述するとおりである。`buffer_script.describe_anchors` は、11 個すべてを整合性チェックとともに出力する。

### `save-write`

ブロックの末尾のペイロードをコピーし、次に `link->sendBuffer` を接続先に向けるので、答えは今セーブデータが保持している内容になる。セッションは `CLI_MSG_BUFFER_SUCCESS` で終わり、これは `MG_STATE_SAVE_LOAD_GIFT` に届いて、書き込みをフラッシュにコミットする。タイトル画面からの再読み込みをまたいで残る。

    HOST --buffer-script save-write --dump-block sav2 --dump-offset 0xB20 \
        --write-text "some text" --version firered

1 つのペイロードは 936 バイトを運ぶ。より長いデータは 936 バイトずつに分けて書かれ、それぞれが独自のペイロードになり、すべてセッションの中で順に実行される。クライアントは、コマンドリストが指示するとおりにそれらを受け取って実行する [mystery_gift_client.c:145, 236]。答えは、最後の断片の下でセーブが保持している内容である。

`build_save_write` は、`struct SaveBlock2` [global.h:345,357] の 0x090 の `filler_90[8]` と 0xB20 の `filler_B20[0x400]` の外側にある範囲をすべて拒否する。これらは `src/` のどこからも参照されない。`filler_B20` の 4 バイト後ろは `encryptionKey` で、お金はこれで XOR される。`--write-unsafe` で上書きできる。ブロックがフラッシュのどこに着地するかは回転する（[ID の所在](#where-an-id-lives-and-which-sector-carries-the-slots-counter)）。

`save-write` が変えるのは、指定した範囲だけである。256 バイトの書き込みは、SaveBlock2 の 196 バイトを変えたが、すべて範囲の内側で、SaveBlock1 は一切変えなかった。ゲームは `filler_B20` に何も書き込まない。そこへの書き込みは、セーブをまたいで残り（10 世代を計測）、ふしぎなできごと、ふしぎなカード、ソフトリセット、プレイをまたいで残る（1 分間のプレイで SaveBlock1 の 1456 バイトが動いた間、256 バイトは変わらなかった）。

### `memory-scan`

32 ビットの針と範囲を取る。各呼び出しは、32 バイトのブロックのその予算分を走査し、カーソルを自身のイメージに書き戻して 0 を返す。終端に達した呼び出しは、`link->sendBuffer` を結果に向け直して 1 を返す。イメージは、そのパラメーターの上を飛び越える分岐で始まる:

| オフセット | |
|---|---|
| 0x000 | `b .Lcode` |
| 0x004 | カーソル。開始アドレス。ペイロードが進める |
| 0x008 | 終端 |
| 0x00C | 針（needle） |
| 0x010 | 1 回の呼び出しあたりのブロック数 |
| 0x014 | max_calls。ウォッチドッグ |
| 0x018 | 結果: 見つかった一致数、最終カーソル、使った呼び出し数、格納した一致数 |
| 0x028 | 結果: 64 × (アドレス、値) |
| 0x228 | コード |

予算はフレームを必要とする RFU リンクを守るためのものである。内側のループは 8 ワードの `ldmia` と、8 つの連鎖した `cmpne` で、8 ワードあたり約 14 命令である。既定の 512 ブロックは unicorn 下で 1 回の呼び出し 7703 命令で、EWRAM からのフレームの 280896 サイクルのうち約 60000 である（16 ビットバス、ARM フェッチ 1 回あたり約 6 サイクル）。16 MB のカートリッジは 1024 回の呼び出しで、約 17 秒である。`--scan-blocks` がそれを設定する。ホストは全体を通して毎秒約 60 の子フレームを読む。

`max_calls` の既定は、範囲が必要とする回数に 2 を足したものである。ウォッチドッグによる停止は、再開すべき場所を示す短いカーソルで答える。答えは常に 528 バイトなので、`len(dump) == buffer_dump_size` が再ポイントを証明する。`found` はすべての一致を数え、`hits` は最初の 64 個を保持する。`ldmia` が見るのは、ワード境界に揃った一致だけである。実際のストライドに対してワード境界に揃わない針は、ゼロを返す。

### `table-scan`

各要素が直前の要素より正確に `delta` だけ大きい、`runlen` ワードの極大な連続を見つけ、連続の開始位置と最初の値で答えることで、形からテーブルを探す。`gSpecialVars`（[data/event_scripts.s:51]）は `gSpecialVar_0x8000` から `0x800B` までを並べ、12 個の連続した `u16` である（[event_data.c:16]）。そのため最初の 12 ワードは 2 ずつ増え、最初の値は `&gSpecialVar_0x8000` になる。

    HOST --buffer-script table-scan --table-delta 2 --table-runlen 12 \
        --table-start 0x08140000 --table-end 0x08400000 --version firered

エントリ 12 は `gSpecialVar_Facing` で、`Result` と `LastTalked` の後に宣言され、エントリ 11 からは +6 である。そのため連続はちょうど 12 で、13 では何も見つからない。

形の検査は、ワードあたり約 7 命令で、値の約 1.75 命令に比べて重い。そのため `TABLE_SCAN_DEFAULT_BLOCKS` は 16 バイトのブロック 192 個で、`memory-scan` の 32 バイトのブロック 512 個と同じ負荷である。`run`、`runstart`、`expect` は、カーソルの隣の 0x22C..0x234 にあり、連続は `ldmia` とフレームの境界をまたぐので、毎回の yield で保存される。`expect` は 0 から始まるので、最初のワードがゼロのときは、書き込まれていない `runstart` を持つ連続に計上される。`read_table_scan` は、範囲の外の一致を捨てる。

同じ形で、生きている `struct ScriptContext` も見つかる。`InitScriptContext` はコマンドテーブルとその終端を +0x5C と +0x60 に格納し [include/script.h]、17 エントリのテーブルでは 68 離れる。そのため EWRAM 上の `--table-delta 0x44 --table-runlen 2` は、コンテキストのアドレスとテーブルのアドレスで答える。コンテキストは、スクリプトが一度走るまでゼロなので、スキャンは同じ起動内でふしぎなできごとのギフトに続かなければならない。`--table-delta 0x358`（214 エントリ）は、フィールドスクリプトのコンテキストを見つける。その `cmdTable` は既知の `gScriptCmdTable` である。

### `rom-checksum`

範囲を最大 128 ブロックに分けて、ブロックごとに 1 つの合計を取る。そのためホストは、ROM イメージと異なるカートリッジのブロックを名指しできる。1 つのブロックを、より小さなブロックで走らせる 2 回目の実行は、それを絞り込む。フレームのループ、予算、ウォッチドッグ、再ポイントされた送信は `memory-scan` のものである。各ブロックは、0 から昇順にワードを合計する:

    acc = w + ror(acc, 31)          one `add r0, rN, r0, ror #31` per word, mod 2^32

`rom_checksum_reference` は、ROM ファイルから同じ値を計算する。XOR では打ち消しが起きる（同じワードの繰り返しは 0 に合計され、32 ワード離れた等しい変化は打ち消し合う）。参照の終端を越えるブロックは、その合計で名前が付けられる: ゼロ埋め、0xFF 埋め、オープンバス（各ハーフワードが、それ自身のアドレスの半分）、ミラー、または CONTENT。

| オフセット | |
|---|---|
| 0x000 | `b .Lcode` |
| 0x004 | カーソル。開始アドレス。ペイロードが進める |
| 0x008 | 終端 |
| 0x00C | 開始 |
| 0x010 | 1 回の呼び出しあたりの 32 バイトのチャンク数 |
| 0x014 | max_calls。ウォッチドッグ |
| 0x018 | shift: ブロックサイズの log2、5 から 25 |
| 0x01C | 進行中のブロックの実行中の合計。呼び出しをまたいで保持される |
| 0x020 | 結果: 最終カーソル、使った呼び出し数、格納した合計、エコーされた shift |
| 0x030 | 結果: 128 × u32 のブロック合計 |
| 0x230 | コード |

答えは 0x020 から 528 バイトである。ビルダーは、ブロックに揃っていない開始位置、ブロックの整数倍でない範囲、128 ブロックを超えるもの、そして 32 バイトから 2 の冪でないブロックを拒否する。8 ワードあたり 13 命令で、512 チャンクは 1 回の呼び出し 6688 命令である。既定の 0x08000000..0x09000000 を 128 KiB のブロックで走らせると、1024 回の呼び出しで、約 17 秒である。

    HOST --buffer-script rom-checksum --version firered
    HOST --buffer-script rom-checksum --sum-start 0x08120000 --sum-end 0x08140000 \
        --sum-block 0x400 --version firered

ホストは、ブロックごとの範囲、両方の合計、そして `SAME` か `DIFF` をログに出し、続いて `rom-checksum: N of M blocks differ from <image>` を出力する。イメージは `config.REFERENCE_ROMS[game code]` で、すべてのビルドに対しては `--sum-reference` である。イメージの外側のブロックは列挙されるが、数えられない。

### `rng-trace`

各フレームに 1 回ワードをサンプリングし、各サンプルの 2 回の読み取りの間で ROM 関数を呼ぶ（`--trace-call 0` にすると、単純なサンプラーになる）。

    HOST --buffer-script rng-trace --trace-address 0x03004220 --trace-call 0x080486B1 \
        --trace-samples 96 --version firered

呼び出しは `mov lr, pc; bx r2` である。pc は `bx` の次の命令として読まれ、ビット 0 は落ちているので、呼び出し先は ARM 状態に戻る。実機の FireRed では、`Random` のトレースのすべてのサンプルが LCG に従う（計測したトレースでは 96 件中 96 件）。結果は [乱数](frlg_rng.md) のページにある。

### `string-gather`

最初のポインタのアドレス、ストライド、個数を与えると、指される各文字列を、0xFF の終端を含めて、1 つの答えにコピーし、次の実行がどこから再開するかを報告する。

    HOST --buffer-script string-gather --gather-address 0x083E0D54 --gather-count 69 \
        --gather-stride 12 --version firered

`--gather-stride` は `struct EasyChatWordInfo`（`text` は 0）なら 12、`const u8 *` の配列なら 4 である。答えは 776 バイトである: 4 つのヘッダーワードと、最大 760 バイトの文字列。切り詰めることはない。収まらない文字列は実行を終え、`next` がそれを指す。`--gather-maxlen`（既定は 64）は、文字列ではないポインタを制限する。

### `create-mon`

```c
void CreateMon(struct Pokemon *mon, u16 species, u8 level, u8 fixedIV,
               u8 hasFixedPersonality, u32 fixedPersonality, u8 otIdType, u32 fixedOtId)
```

4 つの引数は `r0..r3` に、4 つはスタックにある。`asm/create-mon.s` はコンソール自身のプロローグに従う:

    08041150  push {r4,r5,r6,r7,lr}    ; sp -= 20
    08041152  mov  r7, r8
    08041154  push {r7}                ; sp -= 4
    08041156  sub  sp, #28             ; sp -= 28, so entry sp is now sp + 52
    0804115c  ldr  r4, [sp, #52]       -> entry sp +  0   hasFixedPersonality  (masked to u8)
    0804115e  ldr  r7, [sp, #56]       -> entry sp +  4   fixedPersonality     (NOT masked: u32)
    08041160  ldr  r5, [sp, #60]       -> entry sp +  8   otIdType             (masked to u8)
    08041184  ldr  r0, [sp, #64]       -> entry sp + 12   fixedOtId            (u32)

4 つは `sp+0..sp+12` にワード単位で置かれ、ペイロードが自分でそれらを pop する。ポケモンは、ペイロードのイメージの中、コードの前の 32 バイトのガードの内側で組み立てられる。`--create-mon-destination ADDR` はそれをさらにコピーし、`--write-unsafe` が必要である。

    HOST --buffer-script create-mon \
        --create-mon-species 151 --create-mon-level 30 --create-mon-iv 31 \
        --create-mon-personality 0x3ADE0000 --version firered

`--create-mon-call` の既定は `rom_map.py` の `CreateMon | 1` である。`0` は何も呼ばず、ゼロ埋めされたバッファで答える。答えは 116 バイト（4 つのヘッダーワードと、100 バイトの `struct Pokemon`）で、`*param` は性格値である。

サブ構造体は `personality ^ otId` で暗号化され、チェックサムが付くため、有効なチェックサムは 2 つのワードを証明する。`check_create_mon` は種族、レベル、個体値を検査する。`scratchpad/verify_create_mon.py` は、13 個の導出されたフィールドを予測する: `gExperienceTables[growthRate][level]` からの経験値、`gSpeciesInfo` からのなつき度と特性スロット、覚えた技の一覧からの技と PP、`CalculateMonStats` からの 6 つのステータス。ニックネームは `gSpeciesNames` [pokemon.c:1810]（カートリッジのフランス語表）から来るので、予測ではなく読み取られる。3 つのフィールドはコンソールで計測する:

| フィールド | 値 | 意味 |
| --- | --- | --- |
| `language` | 3 | `gGameLanguage` は LANGUAGE_FRENCH [global.h:22] |
| `metGame` | 4 | `gGameVersion` は VERSION_FIRE_RED [global.h:11] |
| `metLocation` | 91 | `GetCurrentRegionMapSectionId()` [overworld.c:1265]。プレイヤーが立っていた場所 |

`buffer_script.shiny_personality(tid, sid)` は色違いの `fixedPersonality` を与える。`CreateMon` のオフラインのスタブは次のとおり: `CREATE_MON_ARG_MODEL` は 8 個の引数を接続先に書き込み、`create_mon_copy_model(source)` は準備した 100 バイトをコピーする。

#### `--create-mon-append`

これはセーブブロックのパーティではなく、`gPlayerParty` に書き込む:

```c
void SavePlayerParty(void)
{
    gSaveBlock1Ptr->playerPartyCount = gPlayerPartyCount;
    for (i = 0; i < PARTY_SIZE; i++)
        gSaveBlock1Ptr->playerParty[i] = gPlayerParty[i];
}
```

セーブブロックへの追記は成功を報告するが、次のセーブで失われる [load_save.c:160,196]。`slot == playerPartyCount` に書き込み、捕獲の場合と同じく数を増やす。占有されたスロットには決して触れず、満杯のパーティは何も書き込まない。5 番目の答えのワードは `countBefore | slot << 8 | status << 16` を報告する（0 は要求されていない、1 は追記された、2 はパーティが満杯、3 はドライラン）。絶対的な `--create-mon-destination`、または `--create-mon-call 0` を伴う追記は拒否される。

    # dry run first: the same code with the two stores left out
    HOST --buffer-script create-mon --create-mon-append-dry-run \
        --create-mon-species 59 --create-mon-level 30 --version firered
    HOST --buffer-script create-mon --create-mon-append \
        --write-unsafe --create-mon-species 59 --create-mon-level 30 --version firered

ドライランは、件数、接続先のアドレス、そのスロットの現在の 100 バイトを報告する。これは、パーティと食い違う `playerPartyCount` を捕まえる。空のスロットは、すべてゼロではない。`ZeroMonData` は `SetMonData(mon, MON_DATA_MAIL, &MAIL_NONE)` [pokemon.c:1737] で終わるので、オフセット 0x55 は `0xFF` である（`buffer_script.EMPTY_PARTY_SLOT`、`is_empty_party_slot`）。

| | 変わるか | 扱い |
| --- | --- | --- |
| `gSaveBlock1Ptr` | 変わる。戦闘とロードのたびに振り直される、4 バイト境界のランダムなオフセット [`SetSaveBlocksPointers`, load_save.c:75] | 呼び出しのたびに `r1`/`r2` から取る |
| `gPlayerParty` | 変わらない。リンク時に決まる EWRAM のグローバル | アドレスをそのまま使ってよい |

`gPlayerParty` は 0x02024280、`gPlayerPartyCount` は 0x02024025 である。EWRAM のダンプのうち、チェックサム付きの `struct Pokemon` としてデコードされる 4 バイト境界のウィンドウは、これだけである。

### `call`

アドレス、最大 8 個の引数ワード、返された `r0`、そして呼び出しの前後それぞれで読むアドレス 1 つ。

    HOST --buffer-script call \
        --call-address 0x080486D1 --call-arg 0xC0DE --call-watch 0x03004220 --version firered

    0x000  b .Lcode
    0x004  function    THUMB pointer (bit 0 set), or 0 to call nothing
    0x008  argc        how many of the eight words below are meant
    0x00C  args[0..7]  r0, r1, r2, r3, then [sp+0], [sp+4], [sp+8], [sp+12]
    0x02C  watch       a word to read before and after the call, or 0
    0x030  result      calls used, function, argc, r0, *watch before, *watch after

`asm/call.s` は常に 16 バイトのスタックをプッシュする。呼び出し先がそれを pop することはない。`SeedRng` は何も返さない（`gRngValue = seed` [random.c:15]）ので、ウォッチワードが証拠になる。すでにコードとして読まれたアドレスだけを呼ぶこと。`tests/test_buffer_script.py` は、コンソール自身の `SeedRng` のバイト列を unicorn 下でペイロードを通して走らせ、2 の冪による 8 引数の経路も走らせる。

### `flash-write`

EWRAM で 4 KB のセクターを組み立て、[`swi 0x48`](#the-flash-sector-path) でフラッシュに書き込む。ゲームのセーブのコードはバイパスする。スクラッチは `gDecompressionBuffer + 0x400` で、ペイロード自身のイメージより 0x400 上である。

    --flash-sector N            the sector, 0..31; 0..27 are the save bands and need --write-unsafe
    --flash-fill-base WORD      word[i] = base + i * step, the data pattern
    --flash-footer              compose a well-formed sector instead of a raw pattern
    --flash-id N                the sector id at +0xFF4
    --flash-derive              read the save globals and place it where that id actually lives
    --flash-position N          aim at band position N and derive the id from it instead
    --flash-counter-bias N      added to gSaveCounter for the footer

`--flash-footer` は、ゲームがするように、パターンの終わりから `+0xFF4` までをゼロにし、ゲームのチェックサムを計算して、ID、チェックサム、署名、カウンタを置く。ステータスワードは物理セクター（上位半分）とチェックサム（下位半分）である。`--flash-derive` は書き込みの時点で `gLastWrittenSector` と `gSaveCounter` を読む。どちらもセーブのたびに進み、成功メッセージで終わるふしぎなおくりもののセッションはセーブする [mystery_gift_menu.c:1379]。

### `sloop-svc`

1 つのセッションで、ホストが選んだオペランドを持つ最大 8 個の Sloop システムコールを発行し、結果ブロックを通して答える。

    IP_HOST --buffer-script sloop-svc --svc-number 0x4d --svc-text "hello fuck" \
        --svc-data-in r0 --version firered

    0x000  b .Lcode
    0x004  flags       bit 0: r0 = &copy, bit 1: r1 = &copy
    0x008  r0..r3
    0x018  scratch     gDecompressionBuffer + 0x400
    0x01C  length      of the data, at most 256
    0x020  thunk       swi N ; bx lr (THUMB), or bkpt N ; bx lr with --svc-bkpt
    0x024  count       1..8
    0x028  numbers     eight bytes, one per call
    0x030  data

各呼び出しの前に、ペイロードはデータを新たにコピーし、番号をサンクの下位バイトに書き込む。結果ブロックは次のとおり: マーカー `0x53565331`、件数、マーカー `0x53565332`、長さ、20 バイトのレコード 8 個（サンクのワードと、その後の `r0..r3`）、そして最後の呼び出しが残したデータ。値のみの番号（0x46、0x49..0x4B、0x4D、0x4E、0x50..0x54、0x58..0x60）はそのまま渡される。0x48、0x56、0x4C、0x55 は拒否される。残りと `--svc-bkpt` は `--write-unsafe` が必要である。`--svc-bkpt` は `#0x52` を拒否する。

### `install-resident`

1 つのセッションで、常駐の THUMB フックを `0x0203FC00` にコピーし、`gIntrTable[4]` に組み込む。ソフトリセットまで、CONTINUER とオーバーワールドを通して、毎フレーム実行される。

    IP_HOST --buffer-script install-resident --resident turbo \
        --resident-param extra=4 --resident-param field=1 --resident-param battle=1 \
        --resident-param overlay=0x03004220 --resident-param hold=0x100 \
        --resident-param budget=228 --write-unsafe --version firered

    0x000  b .Lcode
    0x004  dest          0x0203FC00
    0x008  length        of the hook, whole words
    0x00C  table         &gIntrTable[4], 0x03002730
    0x010  entry_off     the hook's entry inside it
    0x014  original_off  its p_original word
    0x018  blob_off      where the hook starts in this image, after the installer's code

THUMB インストーラーは 148 バイトで、データ（`p_frames`、`p_ring`、`p_state`）を持つフックのために 876 バイトを残す。そのデータはインストーラーのコードと重なってはならず、`0x02040000` を越えてはならない。REG_IME はコピーとテーブル書き込みの前後でクリアされる。最初のインストールは、置き換えたハンドラーを `0x0203FBFC` に保持する。後続のインストールは、その語に連鎖し、それが空のときは `0xBAD0BAD0` で拒否する。答えは見つかったハンドラーである: クリーンなインストールでは `0x0800071D`。フックは一度に 1 つだけ常駐し、すべてが `0x0203FC00` の 1 KB を共有する。

#### `turbo`

`asm/resident/turbo.s` は `VBlankIntr` を実行し、次に、アイドルフレームでは、オーバーワールドのコールバックを `field` 回、戦闘のコールバックを `battle` 回、そして `RunTextPrinters`（`0x08002D51`）を `extra` 回、余分に実行する。パスは、`callback1`/`callback2` が正確に `CB1_Overworld`（`0x08059E49`）/`CB2_Overworld`（`0x08059EC9`）であるか、または `BattleMainCB1`（`0x08015B6D`。戦闘の初期化が `0x08013FDE` に格納する）/`BattleMainCB2`（`0x08014889`）である間だけ実行され、2 回の呼び出しの間で再確認される。`newKeys` と `newAndRepeatedKeys` は最初にクリアされるので、押下は 1 回だけ処理される。

`gPaletteFade.active`（`0x02037AB4`）が立っている間は、どのパスも走らない。ハードウェアのフェードは、`UpdatePaletteFade` が 1 ビットの `hardwareFadeFinishing` を立て、次の V-blank がそれを見るときに終わる [palette.c:701, 743]。1 フレームに 2 回目の更新があるとビットが 0 に回り、`CompleteWhenChoseItem` は、戦闘中にバッグが閉じた後、永遠に待つ。さらに 2 つのゲート:

- `VBlankIntr` の前に読まれる `gMain.intrCheck`（`0x030022EC`）のビット 0 がクリアされていること。メインループは `WaitForVBlank` [main.c:462] で止まっている。立っていれば遅れのフレームなので、触らない。
- `sTextPrinters`（`0x02020034`、0x24 バイトのうち 32 個）の起点（`currentX ==
  x`、`currentY == y`）に、アクティブなプリンターがないこと。フィールドのメッセージは、その箱が描かれる前にプリンターを追加する [field_message_box.c:44]。箱が描かれる前のパスは、箱がその後消すウィンドウに出力してしまう。

エミュレーターでの計測: 毎秒 60 フレーム、97% がアイドル、テキストは 1 フレームに 5 グリフ。`field=1` はオーバーワールドを倍にし、`battle=1` は戦闘とそのメニューを倍にする。

`hold=MASK` は、`gMain.heldKeys`（`gMain + 0x2C`）がマスク内のすべてのボタンを保持している間だけ、コールバックのパスを走らせる。テキストの追加分は、それに関係なく走る。`hold=0x100`（R）のとき、フックはフレームごとに 1 を `gHelpSystemToggleWithRButtonDisabled`（`0x0203F171`。`RunHelpSystemCallback`（`0x0813F65C`）内の `0x0813F6FC` のリテラル）に格納するので、R はヘルプシステムを開かない [help_system_util.c:50]。L は開く。

`budget=LINES` は、時間によってパスを制限する。Switch エミュレーターは、フレームのコードが走る間、`REG_VCOUNT`（0 から 227、V-blank は 160 から）を進める。パスは、V-blank からの行数に、直前のパスのコストの 2 倍を足した値が `LINES` に収まるときだけ始まる。直近のコストはカウンタ `+0x0C` にあり、保留されたパスの数は `+0x10` で数えられる。保留された各パスは、保持されているコストを 8 分の 1 ずつ縮める。

エミュレーターでの計測:

| 設定（R を保持） | フレームあたりの追加パス | 備考 |
|---|---|---|
| `field=2 battle=2` | 2 のうち 1.70 から 1.90 | 約 2.9 倍。目に見える遅れなし |
| `field=3 battle=3` | 3 のうち最大 2.38 | フレームの約 4 分の 1 が遅れる。目に見えるカクつき |
| `field=3 battle=3 budget=228` | 最大 2.48 | 滑らか。歩行中のパスは 36 から 42 行、戦闘中は 100 から 108 行のコスト |

`overlay=ADDRESS` は、`ADDRESS` のワードを、オーバーワールドの右上隅に 8 桁の 16 進数として描く（`0x03004220` は `gRngValue`）。エントリは `gMain.oamBuffer[120..127]`（`0x030026C8`）に入り、2 色は `gPlttBufferFaded`（`0x020375F4`）と `gPlttBufferUnfaded`（`0x020371F4`）の OBJ パレット 15 に入る。これは `VBlankIntr` の `LoadOam` と `TransferPlttBuffer` の前に行われる（後だと、上の行が 1 フレーム遅れる）。128 バイトの 1bpp フォント（16 個の 3x5 の数字。ピクセルは行 1 から 5 の 2 から 4 まで。`asm/resident/overlay.inc`）は、2 つの番兵ワードが異なるとき、OBJ タイル 1008 から 1023 に展開される。オーバーレイは、ゲームがパレット 15 とそれらのタイルで保持しているものを何でも上書きする。

`ring=ADDRESS`（140 バイト。`0x0203FF74` が EWRAM の上端で終わる）は、`VBlankIntr` が見つけるとおりに `gRngValue` を保持する。32 フレームの間、1 フレームに 1 ワードずつで、`watch`（`gEnemyParty[0]` の性格値、`0x02024028`）が変わると凍結する。草むらの遭遇の性格値は、保持されたすべてのシードから導かれる。エミュレーターで草むらを歩いている間に計測: 1 フレームに `Random` が 2 回呼ばれ、前のフレームのシードから、性格の判定は 5 番目の呼び出しである（`VBlankIntr` [main.c:412] のフレーム自身の呼び出し、スロット、レベル、性格の順）。

#### `shiny`, `ivs`, `noencounter`

`shiny`（`asm/resident/shiny.s`）は、次の野生の色違い抽選までをカウントダウンする。`VBlankIntr` はフレームごとに 1 回 `Random` を呼ぶ [main.c:412]。野生のポケモンは、性格のために `Random() % 25` を振り、続いて性格が一致するまで `Random() | Random() << 16` を引く [wild_encounter.c:233, pokemon.c:1864]。`method=1` は最初の組を取る（スクリプトの `CreateMon`）。色違いは `TID ^ SID ^ high ^ low < 8` で、TID と SID は `gSaveBlock2Ptr`（`0x0300422C`）の `+0x0A` から来る。フックは `gRngValue` をフレームごとに追う（最大 64 ステップ。それ以上なら再開する）。アイドルフレームごとに `search` 個の候補を探し、目標の性格と `target - current - offset` を 10 進で表示する（`offset=4`、草むらの場合）。あるいは `FF` と検索距離を表示する。`slow`（R）が保持されている間、フレームごとに `slow_frames` 回の追加の V-blank を待つ。`IntrMain` はハンドラー内で VCount を有効のままにするので [crt0.s]、`m4aSoundVSync` が走り、フックは待った V-blank ごとに `m4aSoundMain`（`0x081DF53D`、`gSoundInfo` `0x03005F80` からの `gPcmDmaCounter` `0x03002F68`）を呼び、`REG_IF` でそれをクリアする。状態は `0x0203FF80` の 36 バイトである。

`ivs`（`asm/resident/ivs.s`）は、先頭のポケモンの個体値を 2 行に表示する（`OVERLAY_TWO_ROWS`。2 行目は `gMain.oamBuffer[112..117]` の y 10）。上段は HP、攻撃、防御、素早さ、下段は特攻、特防、そして `personality % 25`。`GetMonData(mon, MON_DATA_IVS)`（66、`0x080432E5`）は、HP を最下位とする 5 ビットの個体値 6 個を返す [pokemon.c:3250]。`GetBoxMonData` はその場で復号して再暗号化するので [pokemon.c:2992, 3327]、呼び出しはアイドルのオーバーワールドフレームでだけ行われる。

`noencounter`（`asm/resident/noencounter.s`）は、`sWildEncountersDisabled`（`0x020386D8`）にフレームごとに 1 を格納する。`StandardWildEncounter`（`0x08086528`）は、まずこれを検査する [wild_encounter.c:360]。`DisableWildEncounters`（`0x08085FAC`）がもう 1 つの唯一の書き込み元である。草むら、水、徘徊ポケモンの遭遇は止まる。釣りと甘い香りは、それぞれ独自の経路を取る。

#### `noclip`

`noclip`（`asm/resident/noclip.s`、304 バイト）は、`hold`（既定は `0x100`、R）のすべてのボタンが保持されている間、プレイヤーが壁を通り抜けて歩けるようにする。アイドルのオーバーワールドフレームごと（`gMain.intrCheck` のビット 0 がクリアされ、`callback2` が `CB2_Overworld`）に、マップグリッド `VMap.map`（`gBackupMapData`、`0x02031DF8`）の中で、プレイヤーの `currentCoords` の周囲の 4 つのブロックを、メタタイル ID を保ったまま、衝突 0 と標高 15 に書き直す。`VMap` は `0x03004260`（フランス語版）または `0x03004310`（英語版）にある `{s32 Xsize, s32 Ysize, u16 *map}` で、`MapGridGetCollisionAt` のリテラルである。ブロックは `metatile | collision << 10 | elevation << 12` である [global.fieldmap.h:7]。`GetCollisionAtCoords` は衝突ビットで阻み、次に、標高 15 を通す `IsElevationMismatchAt` で阻む。`ObjectEventUpdateElevation` は、15 のタイルの上でプレイヤー自身の標高を変えない [event_object_movement.c:4830, 8346, 8400]。

次のアイドルフレームは、各ブロックを元に戻す。ただし、`gMapHeader.mapLayout`（`0x02036DF8`）が変更されたレイアウトであり、ブロックがまだメタタイル ID を持ち、標高 15、衝突 0 である間に限る。ワープやゲームが書き直したメタタイルは、新しいブロックを保つ。`MAPGRID_UNDEFINED`（`0x3FF`）に等しいブロックは残る。さもないとプレイヤーはマップの外に出てしまう。オブジェクトイベントは依然として阻み（`DoesObjectCollideWithObjectAt`）、崖は依然としてジャンプさせ、プレイヤーの隣をうろつくオブジェクトイベントは、開かれたブロックに踏み込むことがある。R が保持されたままだとヘルプシステムが開くので、フックはフレームごとに 1 を `0x0203F171` に格納する（`turbo` を参照）。状態は `0x0203FF80` の 24 バイトで、レイアウト、件数、そして 4 つの `{u16 index, u16 block}` である。

`tests/test_noclip.py` は、各カートリッジ自身のクライアントを通してそれをインストールし、結果をカートリッジ自身の `MapGridGetCollisionAt` と `MapGridGetElevationAt` で読む。
マサラタウンでフランス語版カートリッジを使い mGBA で計測: 南へ歩くと、R なしではプレイヤーは柵で止まり、R を保持すると柵を 6 タイル通り抜ける。オブジェクトイベントは依然としてそれを止める。

#### `follower`

`asm/resident/follower.s` は、先頭のポケモンを、プレイヤーの 1 タイル後ろを、本物のオブジェクトイベントとして歩かせる。ゲーム自身の移動アクションで動くので、ゲームは歩数、走り、崖のジャンプ（弧、影、着地の砂ぼこり）、ドアのフェード、スプライトの優先度を描く。この設計は GB-Link の `cards/follow.s`（GPL-3.0）に従う。984 バイトあり、1 回の `install-resident` セッションを越えるので、セーブから組み込まれる
（[セーブに保持される常駐フック](#a-resident-hook-kept-in-the-save)）。

アイドルのオーバーワールドフレームごと（`gMain.intrCheck` のビット 0 がクリアされ、`callback2` が `CB2_Overworld`）に、`VBlankIntr` の後で:

| 見つける | ローカル ID `0xF0` のアクティブなオブジェクトイベント。どのマップも使わないローカル ID で、マップのロード後にはない |
| 出現 | プレイヤーのタイルに `SpawnSpecialObjectEventParameterized(gfx, MOVEMENT_TYPE_NONE, 0xF0, x, y, elevation)`。プレイヤーの最初の一歩まで隠しておく |

#### 検証済み

| --- | --- | --- |
| `turbo` `extra=4 field=3 battle=3 hold=0x100 budget=228` | R を保持すると早送りになる | |
| `overlay` | 8 桁が描かれ、毎フレーム変わる | CONTINUER の後の回想の間に描かれる |
| `shiny` | 草むらでカウントダウンし、R で遅くなる | 追跡したシードは `gRngValue` と一致し、Python のモデルは色違いについて一致する |
| `ivs` | 先頭の個体値ワードと `personality % 25` が、`SaveBlock1 + 0x34` の `save-dump` と一致する | `gPlayerParty`（`0x02024280`）と一致する |
| `noencounter` | 草むらを歩いても野生の遭遇がない | なし。ソフトリセット後に遭遇が戻る |

未解決: エミュレーターでは、オーバーレイは CONTINUER の後の回想の間には描かれたが、通常のプレイ中には描かれなかった。一方で `field` はゲームの速度を上げ続けた。

すべてのフックは、1 か所のアドレスを変えた上でリーフグリーンでも動く。`m4aSoundMain` は `0x081DF518`（`VBlankIntr` の `0x08000772` にある `bl`）である。そのほかの定数は、ファイアレッド自身の参照を通して同じように対応する。`follower` は、セクションに列挙した、位置が動く ROM テーブルと関数も読む。ビルダーは `version=` を取り、ホストは `--version leafgreen` を使う。エミュレートしたリーフグリーンで検証した: turbo と `shiny` は動き、音楽も正常だった。

### 複数のフックを同時に

どのフックも、置き換えたハンドラーを関数として呼ぶ（`p_original` の `bx r3` への `bl`）。そして自身が積んだ `lr` を通して戻るので、あるフックの `p_original` は別のフックを指しうる。`--resident turbo-lite+noclip+noencounter` は、フックを `0x0203FC00` から背中合わせに並べ、それぞれの `p_original` を次のフックのエントリ（THUMB ビットを立てる）として書き、インストーラーには、エントリが先頭のフックで、`p_original` が最後のフックであるような 1 つのブロブを渡す。`install-resident`、`install-kept` と MOM のローダーは変わらない。設定はフックを名指しする: `--resident-param turbo-lite.hold=2`。

| 規則 | 理由 |
|---|---|
| 順序は turbo、noclip、shiny、ivs、noencounter | turbo のコールバックのパスは、他のフックがそのフレームを終えた後に走る |
| 各フックのデータは `0x0203FBB4..0x0203FBFC` に、その後コードの上に置かれる | 既定値が重なる: `shiny`、`ivs`、`noclip` はすべて `0x0203FF80` に状態を保持する |
| `shiny`、`ivs`、turbo の `overlay` のうち多くても 1 つ | いずれも `gMain.oamBuffer[120..127]` と OBJ パレット 15 に描く |
| `follower` は単独で走る | 984 バイト。ほかのどのフックと組んでも、セーブが保持する 1004 を越える |
| コードは `0x0203FC00..0x02040000` に収まる | 1024 バイト。876 を越えるとセットはセーブ経由になり、1004 を越えると置き場所がない |

`turbo-lite`（`asm/resident/turbo-lite.s`）は、`TURBO_LITE` を設定して組み立てた `turbo.s` である。同じパス、ゲート、hold、budget を持ち、オーバーレイも RNG の履歴もない。356 バイトで、`turbo.s` は 696 バイトである。turbo のすべてのフレームのテストはこれで走る（`tests/test_turbo_lite.py`）。連鎖を通るフレームは、各フックと `VBlankIntr` を一度ずつ走らせる（`tests/test_resident_chain.py`）。

### `install-kept`

`asm/install-kept.s`（192 バイト）は、`install-resident` が自分のものをインストールするのと同じように、`filler_B20` に保持されたフックをインストールする。`gSaveBlock2Ptr` を読み（ブロックはロードのたびに動く）、マジック、チェックサムが `filler_B20` の内側に収まる長さ、そして合計を検査してから、REG_IME をクリアし、ゲームのハンドラーを `0x0203FBFC` に保持し、フックをコピーして、その `p_original` を書き、`gIntrTable[4]` をそれに向ける。答えはテーブルで見つかったハンドラーであり、何もインストールされなければ `0xBAD0BAD0` である。+0 の ARM エントリはバッファスクリプトのものである。MOM の RAM スクリプトは +8 の THUMB エントリを走らせ、答えをイメージ内のワードに向ける。最後の 2 ワードはカートリッジごとにパッチされる: `&gSaveBlock2Ptr` と `&gIntrTable[4]`。

    IP_HOST --buffer-script install-kept --version firered

### セーブに保持された常駐フック

どの常駐フックも `filler_B20` に置け、起動後に MOM に話しかけると再びインストールされる。リンクもホストもいらない。2 つのギフトセッションがそれを設定する:

    IP_HOST --buffer-script save-write --resident follower --version firered
    IP_HOST --gift resident-save --version firered

1 つ目は、このブロブを `SaveBlock2 + 0xB20` に書き込み、同じセッションでそこからフックをインストールする:

    +0x00  magic     0x32524B50, "PKR2"
    +0x04  length    the hook's bytes, whole words
    +0x08  dest      0x0203FC00
    +0x0C  entry     u16 offset of the hook's entry
    +0x0E  original  u16 offset of its p_original word
    +0x10  the hook
    +len   checksum  the sum of every word before it

1 回の `save-write`（936 バイト）を越えるブロブは 2 回で書かれる。セッションは、すべての書き込みと、続けて [`install-kept`](#install-kept) を実行する。それぞれが独自のペイロードである。クライアントは、コマンドリストが指示するとおりにバッファスクリプトを順に受け取って実行し [mystery_gift_client.c:145, 236]、最後の答えだけが戻ってくる。

    client  RECV RUN  RECV RUN  RECV RUN LOAD_TOSS_RESPONSE SEND_LOADED  RECV COPY_RECV
    host    script    write 1   write 2  install-kept   <- the handler found

セッションは `CLI_MSG_BUFFER_SUCCESS` で終わり、これはセーブするので、`filler_B20` はフラッシュに届く。

2 つ目は、MOM に RAM スクリプトを紐づける。このスクリプトは 36 バイトの [ram-jump トランポリン](#a-payload-larger-than-a-script-body) を用意し、`install-kept` の THUMB エントリに分岐する。そのエントリはスクリプト本体に 1 バイトずつ入れて運ばれる（995 のうち 428 バイト）。MOM に話しかけるとフックがインストールされる。2 回目の訪問は、保持されたハンドラーに連鎖し、ソフトリセットは、再び MOM に話しかけるまでフックを取り除く。

| フック | ブロブ | `save-write` のペイロード |
| --- | --- | --- |
| `noencounter` | 48 | 1 |
| `ivs` | 520 | 1 |
| `turbo-lite` | 376 | 1 |
| `turbo` | 716 | 1 |
| `shiny` | 888 | 1 |
| `follower` | 1004 | 2 |

`tests/test_resident_save.py` は、ホストとエミュレートしたクライアントの間のセッション全体と、起動済みコンソール上の MOM の本体スクリプトを走らせる。1 バイトの反転、2 回目の書き込みの欠落、`filler_B20` を越える長さのいずれでも、何もインストールされない。実機のファイアレッドは、`PKR2` ブロブからフォロワーをインストールする。

新しいふしぎなカードは、バインドを取り消す。`SaveWonderCard` は `ClearSavedWonderCardAndRelated` を呼び、それが `ClearRamScript` を呼ぶ [mystery_gift.c:172, 160]。`filler_B20` は書かれたまま残る。

### `call-chain`

1 フレームの中で順に最大 16 ステップ。ステップごとに答えのワードが 1 つ返る。

    HOST --buffer-script call-chain \
        --chain-step call:FlagGet,0x828 \
        --chain-step call:FlagSet,0x828 \
        --chain-step call:FlagGet,0x828 --version firered

ステップは 24 バイト（op、target、4 つの引数）で、`OP:TARGET[,ARG]...` と書く。op は `call`、`read32/16/8`、`write32/16/8`。call の target は `rom_map.CALLABLE` の名前でよい（デコンプのアドレスは不可）。

ステップは、対象または最初の引数を前の結果 `prev` から取れる:

    --chain-step call:GetVarPointer,0x4024      prev = the address the GAME computed
    --chain-step read16+keep:prev               the value before, prev untouched
    --chain-step write16:prev,7                 the store, read back by the payload itself
    --chain-step read16:prev                    the value after

`ScrCmd_setvar` は `GetVarPointer` の戻り値を通して書き込む [scrcmd.c:472]。ScrCmd のワーカーに `VarSet` はない（[ROM マップ](frlg_rom_map.md)）。書き込みが `prev` になることはなく、読み取りは `+keep` を付けない限り `prev` になる。どの書き込みも、答えの中で自分自身を読み戻す。

    0x000  b .Lcode
    0x004  count       how many steps are meant, 0..16
    0x010  steps[16]   {op, target, a0, a1, a2, a3}, 24 bytes each
    0x190  result      calls, count, steps executed, the op word that stopped it
    0x1A0  values[16]  one word per step, in order

未知のオペコードは実行を止め、答えの中でそれを名指しする。ARM もステップ数を制限する。ビルダーは、空の連鎖、16 ステップを超えるもの、ARM のポインタへの呼び出しや、カートリッジの外への呼び出し、`prev` からの呼び出し先（誤ったものだとメニューがハングする）、アライメントのない読み取りや、到達できない読み取り、4 つを超える引数、そして `--write-unsafe` のない書き込みを拒否する（その後コンソールはセーブをコミットする）。

    call GetVarPointer(0x4024)   -> 0x020265B4
    read16 [prev] keep           -> 0
    write16 [prev] = 3           -> 3        the store, read back by the payload
    read16 [prev]                -> 3
    call VarGet(0x4024)          -> 3        the game's own reader, same frame

`gSaveBlock1Ptr` がベースを変えた後も、変数は 3 を読み続ける。お金は `*moneyPtr ^ gSaveBlock2Ptr->encryptionKey` である [money.c:14]:

    read32 [0x03004228]              -> 0x02025554     gSaveBlock1Ptr
    read32 [prev + 0x290] keep       -> 0x5A5A198C     the ciphertext, before
    call GetMoney(prev + 0x290) keep -> 0x00000BB8     3000, the plaintext
    call AddMoney(prev + 0x290, 1234) keep
    call GetMoney(prev + 0x290) keep -> 0x0000108A     4234, exactly +1234
    read32 [prev + 0x290]            -> 0x5A5A02BE     the ciphertext, after

（例示の値。）両方の XOR の組から鍵が得られる。ここでは 0x5A5A1234 で、SaveBlock2 + 0xF20 にあるワード（`rom_map.SAV1_MONEY`、`SAV2_ENCRYPTION_KEY`）。特殊な関数は、オペランドを特殊変数から読む。`gSpecialVar_Result` を `GET_CARD_BATTLES_WON` に設定すると、特殊 390 はカードの `battlesWon` を答える。その値は、同じフレームで `SaveBlock1 + 0x3434` が保持する値である。

バッファスクリプトから、ワープやメッセージのワーカーを決して呼び出さないこと。ふしぎなおくりもののメニューにはオーバーワールドがない。それらは [フィールドのスタブ](frlg_rng.md#the-payload-in-the-script-body) に属する。

## ゲームがロードするセクターを書く

以下はすべて、エミュレーターで計測した。

### チェックサムは ID のチャンクを覆う

`CalculateChecksum(data, size)` は `size` バイトを、リトルエンディアンの u32 ワードとして合計し、`(sum >> 16) + sum` を u16 に畳み込む [decomp:src/save.c]。`size` は、`sSaveSlotLayout` の ID 自身のチャンクで、フランス語版カートリッジの `0x083F58C4` にある、{u16 offset, u16 size} の 14 エントリである:

| id | size | id | size |
| --- | --- | --- | --- |
| 0 | 3876 | 4 | 3816 |
| 1-3 | 3968 | 5-12 | 3968 |
| 13 | 2000 | | |

`HandleWriteSector` は、チャンクをコピーする前にセクターのバッファ全体をゼロにする [save.c:181-183]。そのためゲームが書いたセクターは、チャンクの後ろがゼロで、3968 バイトすべてを合計しても同じチェックサムになる。チャンクの後ろにデータを持つ組み立てたセクターは拒否される。チャンクだけを埋めること。ID がコンソール上で決まるときは、最も小さいチャンクである 2000 バイト以下だけを埋める。そうすれば、どの ID に対してもそのチェックサムは有効になる。

### id がどこにあるか、スロットのカウンタはどのセクターが運ぶか

スロットは 14 セクターで、ゲームは 2 つのスロットを交互に使い、ID を回転させる [decomp:src/save.c:174]:

    physical = ((gLastWrittenSector + id) % 14) + 14 * (gSaveCounter % 2)

`gLastWrittenSector` は、完全なセーブのたびに 1 進み、14 で折り返す [:147]。通常のプレイでは `gSaveCounter` と一致するが、書き込みが破損と記されると分かれる。ゲームは `gLastKnownGoodSector` から復元し [save.c:159]、`Save_ResetSaveCounters` [:104] はそれを独立にリセットする。`gLastKnownGoodSector` と `gLastSaveCounter` は、進む前にライブの組を受け取るので、前の世代を正確に記述する。セクターは、固定のファイルオフセットではなく、フッターを解析して見つけること。

`GetSaveValidStatus` は、署名が `0x08012025` で、`locations[id].size` にわたるチェックサムが一致するセクターを数える。ID は、そのフッターから取られる:

- スロットが OK になるのは、14 個の ID すべてが存在して有効なときだけである。スロット内のカウンタが一致する必要はない;
- `slotNsaveCounter` は、物理的な順序で有効なすべてのセクターに割り当てられるので、最後の有効なセクターのカウンタを保持する。

そのため、最後のセクターがより高いカウンタを持つ完全なバンドは、すべてのセクターがより低いカウンタを持つバンドに勝つ（129 の 13 個と 131 の 1 個は、130 の 14 個に勝つ）。

| アドレス | シンボル | 幅 |
| --- | --- | --- |
| `0x030045A0` | `gLastWrittenSector` | u16 |
| `0x030045A4` | `gLastSaveCounter` | u32 |
| `0x030045A8` | `gLastKnownGoodSector` | u16 |
| `0x030045AC` | `gDamagedSaveSectors` | u32 |
| `0x030045B0` | `gSaveCounter` | u32 |

IWRAM、フランス語版ビルド。ロードの後、`gLastWrittenSector` は採用されたスロットを記述する。

### セッション自身のセーブが書かないバンド

通常のセーブは、前のペアを割り当て、`gLastWrittenSector` と `gSaveCounter` を進め、その後、増えたカウンタが選ぶバンドを書く [save.c:144-153]。成功メッセージで終わるふしぎなおくりもののセッションはセーブする [mystery_gift_menu.c:1379]。ほかのどの結果で終わるセッションも、セーブせずにメニューへ戻る。セッションが成功で終わるとき、今 `gSaveCounter % 2` が選ぶバンドを書く。するとセッションのセーブは、もう一方を書く。採用されるには、セクターはバンドの位置 13 にあり、カウンタは `gSaveCounter + 2` で、セッションの `gSaveCounter + 1` の 1 つ上である。位置 13 の ID は `(13 - gLastWrittenSector) % 14` で、コンソール上で導かれる。

### RAM のスナップショットからセクターを組み立てる

セーブのルーチンは、セーブの時点でシリアライズするので、SaveBlock2 のライブの内容は、それが書くはずのものと異なる。下の 2 つのケースのどちらでも、すべてのチェックサムは通り、`gDamagedSaveSectors` は 0 のままである:

- 暗号鍵はロードのたびに振り直される。`LoadGameSave` はブロックを復元し、新しい鍵を作り、RAM 上の暗号化されたすべてのフィールドに適用して、SaveBlock2 に格納する [decomp:src/load_save.c:126-128]。触られていない SaveBlock1 の隣で RAM から組み立てた SaveBlock2 は、お金を `raw ^ flash_key ^ ram_key` として読む。暗号化された集合 [ApplyNewEncryptionKeyToAllEncryptedData] は、SaveBlock2 のトレーナータワーのタイム、ゲームの統計、バッグの数量ときのみのパウダー、そしてお金とコインである。
- 保存されたマップビュー。SaveBlock2 の `+0x898` にある 420 バイト（210 個の u16 メタタイル ID、`0x03FF` は空白）は、セーブの時点でだけ埋められ、RAM ではゼロである。組み立てられたセクターは、オーバーワールドを空白のグリッドとして描く。

通常のセーブは 14 個のセクターすべてを一度に書くので、鍵と暗号文は一緒に動く。一部だけの書き込みは、それを保たなければならない。

### フラッシュを読む: 128 KiB のチップ上の 64 KiB のウィンドウ

`swi 0x48` はチップを線形にアドレス指定する。ゲストのロードには、`0x0E000000` に 64 KiB のアパーチャが見え、1 Mbit のパーツはそれを 2 つのバンクとして届く:

    sector N is bank N / 16 at 0x0E000000 + (N % 16) * 0x1000

アパーチャより上のアドレスはエイリアスになる: `0x0E01E000`（セクター 30）は、選ばれたバンドのセクター 14 である `0x0E00E000` を読み、通常はゼロである。バンドとウィンドウは、セクターから計算すること。バンクの選択はゲーム自身の 4 回のストアである [decomp:src/agb_flash.c SwitchFlashBank, `0x081E0C74`、7 命令、ループなし、`REG_WAITCNT` なし]。ペイロードが ROM 呼び出しをしないように、インラインで展開する:

    strb 0xAA -> 0x0E005555 ; strb 0x55 -> 0x0E002AAA ; strb 0xB0 -> 0x0E005555 ; strb bank -> 0x0E000000

読み取りはバイト幅である。フラッシュのバスは 8 ビットである。

`ReadFlash`'s one lasting effect, `REG_WAITCNT`'s SRAM field set to
3 (`WAITCNT_SRAM_8` [decomp:src/agb_flash.c:149]), is already in place after boot: `AgbMain` clears it
[main.c:143], the boot save load calls `ReadFlash` [intro.c:1006], and every flash routine writes 3
(`gFlash->wait[0]` [agb_flash_mx.c:28, agb_flash_le.c:28]).

送信メッセージを決してフラッシュに向けないこと。ヘッダーと本体は、異なる幅でウィンドウを読む:

| ステップ | コード | ロード | 読んだもの |
|---|---|---|---|
| ヘッダーの CRC | `CalcCRC16WithTable` [mystery_gift_link.c:166] | `ldrb` | フラッシュ: `0xDEC2` は物理 `0x1BC00..0x1BFFF` の CRC、`0x5907` は `0x1E000..0x1E0FB` の CRC（バンク 1 が選ばれている） |
| 本体 | `Rfu_InitBlockSend` が、252 バイト以下の各チャンクを `memcpy`（`0x081E44F4`）で `gBlockSendBuffer` にコピーする [link_rfu_2.c:1357] | 送信元と接続先がワード境界に揃い、16 バイト以上残っているとき `ldm` で 1 ワード | そのほかのバイト: バイト組 `01 cb`、`10 3a`、`04 3a` の連続。`0x0E01BC00` と `0x0E01E000` で同一 |

本体の CRC は失敗し、ホストはそれを捨て、ふしぎなおくりもののメニューは RFU リンクが繋がったまま固まる。本体のバイトがどこから来るのかは分かっていない。`build_memory_dump` とその 2 つの兄弟は、`0x0E000000..0x0FFFFFFF` に触れる範囲をすべて拒否する。`flash-read` は、`ldrb` でセクターを EWRAM にコピーし、そのコピーを送る。これはセクターを正確に返す。

### 実際のセーブの 1 つのフィールドを変える

`flash-patch` は、実際のセーブが書いたセクターを読み、1 つのフィールドを変えて書き戻すので、暗号鍵とマップビューは一貫して保たれる。編集は 2 つのセクターである:

    A   the target id's sector: patch the field, recompute the checksum over the id's own chunk,
        set the counter to gSaveCounter + 2
    B   the sector at band position 13: set its counter to gSaveCounter + 2 and nothing else, not
        even the checksum, because +0xFFC is outside the summed data area

ローダーは、バンド（古いカウンタの 12 セクターと、新しいカウンタの 2 セクター）を採用する。14 個の ID すべてが有効で、最後の有効なセクターがより高いカウンタを持つからである。プレイヤー名の `flash-patch` は、セクター A のフィールドとチェックサム、セクター B のカウンタだけを変える。ロードは、不良なチェックサムなしでバンドを採用し、お金とオーバーワールドは変わらず、暗号鍵のコピーとマップビューは、ゲームが書いたものである。

### 連鎖の端から端まで

エミュレートしたコンソールでの計測: バッファスクリプトがライブのグローバルからセクターを組み立て、`swi 0x48` がそれを書き、ゲームの次のセーブが画像をコミットし、次のロードが `gDamagedSaveSectors` がきれいなままバンドを採用する。届けられたパターン（ローダーの事前テストのパターンとは異なり、どこにも現れない）は、2 つの箇所それぞれで 500 個の連続したワードとして EWRAM に読み戻される。

# セーブを読む

ふしぎなおくりもののセッションは、ライブのセーブを読む。秘密の ID と、手持ちの各ポケモンの PID、個体値、性格である。何も書き込まれず、カードのやり取りも起きない。ホストのログは、オフセット 0 からの SaveBlock2 の `save-dump`（名前、性別、TID、SID、プレイ時間）、または 0x38 を覆う SaveBlock1（各手持ちポケモンの性格、個体値、努力値）を、`pokeldn.frlg.save.readout` を通してデコードし、`trainer-id-probe` の答えを TID と SID として扱う。

## トレーナー ID と秘密の ID

SaveBlock2 のオフセット 0 には、プレイヤー名、性別、32 ビットのトレーナー ID、プレイ時間がある [global.h:327]。下位半分がトレーナーカードの TID で、上位半分が秘密の ID である。これはどこにも表示されず、どのリンクメッセージにも送られない。

    POKELDN_RADIO=esp32:auto ./.venv/bin/python -u bin/frlg_mg_host.py --live --keys PROD_KEYS \
        --buffer-script save-dump --dump-block sav2 --dump-size 64 --dump-file dump.bin

    ./.venv/bin/python tools/frlg/dump_read.py dump.bin --block sav2

    dump.bin: 64 bytes from sav2 + 0x0
      playerName    'PLAYER'
      gender        boy
      trainerId     0x12345678  TID 22136  SID 4660
      playTime      12h 34m 56s

トレーナーカードと一致しない TID は、読み取りが誤っていることを意味する。

## The party

SaveBlock1 の 0x34 は `playerPartyCount`、続いて 0x38 の `playerParty[6]`（各 100 バイト）である [global.h:772]:
6 体で 604 バイトである。

    POKELDN_RADIO=esp32:auto ./.venv/bin/python -u bin/frlg_mg_host.py --live --keys PROD_KEYS \
        --buffer-script save-dump --dump-block sav1 --dump-offset 0x34 \
        --dump-size 608 --dump-file party.bin

    ./.venv/bin/python tools/frlg/dump_read.py party.bin --block sav1 --offset 0x34

    party.bin: 608 bytes from sav1 + 0x34
      playerPartyCount 5
      slot 1: PIKACHU   Lv25 nick='PIKACHU' OT='PLAYER' PID=0x00000019 Hardy   IVs=[10,20,30,15,5,25] checksum ok
      slot 2: ...

(Illustrative values.)

IV は HP、ATK、DEF、SPE、SPA、SPD の順に読む。色違いの列は、各ポケモンの PID を自身の OTID と比較する。すべてのスロットで `checksum ok` なら、本物の手持ちである。手持ちのポケモンは、`.pk3`/`.ek3` と同じ形式で格納される（`pokeldn.frlg.save.mon`）。0x20 の 48 バイトが `PID ^ OTID` で XOR され、4 つのサブ構造体は `PID % 24` で並ぶ。

SaveBlock1 は、最後のセーブ時点の手持ちを保持する（`SavePlayerParty` [load_save.c:160]、`--create-mon-append` を参照）。ライブの手持ちをダンプするには `gPlayerParty` を使う。計測した両方のカートリッジでは 0x02024280 である:

    --buffer-script memory-dump --dump-address 0x02024280 --dump-size 600

実行をまたいで、セーブブロックの絶対アドレスを持ち越さないこと。`save-dump` はポインタを毎回新しく取る。IWRAM と `gRngValue` は [乱数生成器](frlg_rng.md) にある。
