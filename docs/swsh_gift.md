# ふしぎなおくりものメニューのローカル無線の分岐

ソード・シールドのふしぎなおくりものメニューは、ローカル無線でワンダーカードを受け取ります。配布元は LDN ネットワークを広告し、その広告データにカードを断片に分けて載せます。「Sword」と明記しない限り、アドレスは Shield 1.3.2 の `main` のものです。電波に乗せたときの挙動は、市販の本体で計測しています。

## メニュー

受け取り方法を選ぶ `StateSelectReceiveDataBase` には、メニューのボタンごとにサブクラスがあります (`L_mystery_top_btn_00` .. `_04`)。

| state | method |
|---|---|
| `StateSelectReceiveDataInternet` | ネットワーク経由 |
| `StateSelectReceiveDataSerial` | シリアルコードかパスワード |
| `StateSelectReceiveDataLocal` | ローカル無線 |
| `StateSelectReceiveDataFromBall` | モンスターボールPlus |
| `StateSelectReceiveDataRankMatch` | ランクマッチの報酬 |

受け取り側の状態は、`StateReceiveBase`、`StateReceiveInternet`、`StateReceiveSerial`、`StateReceiveLocal` (`0x01004938`。この状態自体のコードが参照するのは進捗バーのレイアウトだけです)、`StateReceiveFromBall`、`StateReceiveRankMatch`、`StateReceiveNews`、`StateReceiveComplete` です。プレイ記録のキー `fushigi_net`、`fushigi_serial`、`fushigi_p2p` は、`yy_battle_single_p2p` / `_net` と並んで、経路ごとの受け取り回数を数えます。

ベース RomFS の `/bin/message/French/common/mystery.dat` の内容です。

| line | text |
|---|---|
| 9 | `Recherche de cadeau en cours...` |
| 11 | `Aucun cadeau n'a été trouvé.` |
| 39 | `Connexion à Internet activée.` |
| 42 | `Communication sans fil locale activée.` |
| 63 | `Via Internet` |
| 64 | `Via un code ou mot de passe` |
| 65 | `Voir vos Cadeaux Mystère` |
| 69 | `Via communication sans fil locale` |
| 72-75 | トップメニュー。`Recevoir un Cadeau Mystère`、ワイルドエリアのニュース、モンスターボールPlus、バトルスタジアムの報酬 |

### アプリのステートマシン

ディスパッチャ `0x00FE6F80` は、`app+0x718` にあるリクエストオブジェクトを読みます。`+0x60` が準備完了フラグ、`+0x64` が次の状態 ID です。フラグが立っていて ID が 16 以下なら、`0x020641A4` を経由してジャンプし、その状態を作ります。`SetNextState(id)` は `0x00FF0DE0` にあり、呼び出し箇所は 63 か所です。

| id | state | id | state |
|---|---|---|---|
| 0 | TopMenu | 9 | SelectReceiveDataSerial |
| 1 | ReceiveMenu | 10 | SelectReceiveDataRankMatch |
| 2 | ReceiveLocal | 11 | SelectReceiveDataFromBall |
| 3 | ReceiveInternet | 12 | ConfirmGift |
| 4 | ReceiveSerial | 13 | ReceiveNews |
| 5 | ReceiveRankMatch | 14 | ReceiveComplete |
| 6 | ReceiveFromBall | 15 | ConnectPalma |
| 7 | SelectReceiveDataLocal | 16 | (既定値、TopMenu) |
| 8 | SelectReceiveDataInternet | | |

ローカル無線は、状態 2 で検索を行い、その後、配布元が提示する候補から選ぶ状態 7 に進みます。2 から 7 への遷移を起こす処理は未確認です。`StateReceiveLocal` 自体は次の状態を設定しません。`0x00FE700C` は `mov w8, w21` で、ディスパッチャのジャンプテーブルの添字です。これを `mov w8, #N` に書き換えると、状態 N を強制できます。状態 7 を強制すると空の一覧が表示され、ネットワークには一切触れません (`Connect`、`OpenStation`、セッションの作成がなく、最大数、登録テーブル、広告バイトも変わりません。最大数を書き換えて 100 秒以上座らせた場合も同じです)。そのため、一覧は入る前に埋められます。

クラスの主 vtable は `0x025737C8` です。グループの基底 `0x025737B8` は `main+0x2624698` にだけ保持されています。コンストラクタ `0x00FE5D60` は呼び出し元がありません (アプレットのフレームワークが vtable を経由してアプリを作ります)。`main` のどこからもアプリを指しているものはないため、vtable をヒープから検索して探します。このイメージには ふしぎなおくりもの のプロトコルバッファのモジュールがありません。`.pb.cc` はすべて `gflnet3` の p2p フレームワーク、交換、3 つのバトルモジュール、レイドの巣穴、地下、キャンプ、`comp_organize`、`btl_spot` のいずれかに属します。

## ギフト画面のネットワーク

ローカル無線の画面では、本体が常時稼働のローカル通信ネットワークを広告します。ローカル通信 ID は `0x0100ABF008968000` (両タイトル共通)、バージョン 4、シーン ID は 65535 (リンク交換では 60001)、受け入れポリシーは ALL、`NodeCountMax` は 2、広告データは 384 バイト、パスワードの CRC はゼロです。ゲームは読み込みから数秒後 (計測で 16 から 31 秒) にこのアクセスポイントを一度だけ作ります。ふしぎなおくりものに入るか出るかで、LDN の呼び出しは起きません。ギフト画面がするのは、広告データを設定することと、Pia の参加フィルタを有効にすることだけです。

この画面では、ゲームが `nn::ldn::Scan` を毎分およそ 40 回呼び出します (40 秒の IPC トレースでは 33 回)。その間に `SetAdvertiseData` と `GetNetworkInfo` が挟まり、`Connect` や `CreateNetwork` は一度も呼ばれません。スキャンは 802.11 の層では受動的です。フィルタが指定するのはローカル通信 ID とネットワークの種類だけで、`SessionId` と `SceneId` は絞り込まれません。

本体がチャンネル 6 でホストしている間のモニタ取得結果は次のとおりです。

| channel | この局からのビーコン | LDN の広告アクションフレーム | プローブ要求 |
|---|---|---|---|
| 1 | 0 | 90 秒で 153 | 0 |
| 6 | 70 秒で 339 | 70 秒で 435 | 0 |
| 11 | 0 | 90 秒で 95 | 0 |

### モードのバイト

`session_config+0x70` がローカル通信のモードです。`0x01096730` は、ジャンプテーブル `0x02066C14` を経由して、このモードを Pia のシーン ID と参加人数に対応づけます。`0x010961a8` は、`0x02066C40` を経由して、このモードを広告データのバイト `0x97` に対応づけます (広告は `0xAF`。ゲームのデータは `0x18` から始まります)。

| mode | scene id | 参加人数 | 広告データ `0x97` |
|---|---|---|---|
| 0 | なし。作成処理は `0x01096764` で false を返す | | 0xFF |
| 1 | 60021 | 2 | 0x01 |
| 2 | 60001 | 2 | 0x0D |
| 3 | 60002 | 2 | 0x0E |
| 4 | 60003 | 2 | 0x0F |
| 5 | 60004 | 4 | 0x10 |
| 6 | 60005 | 2 | 0x1E |

リンク交換はモード 2 です (計測で 0x0D)。ギフト画面はモード 0 で動作し (計測で 0xFF)、セッションは作られません。アプリに入ると、モードを読み取り (`0x01096d20`)、`app+0xFE8` に保存して 0 に設定します (`0x01022f08`)。出ると元に戻します (`0x01023198`)。このバイトは、放置しても、出ても、入り直しても `0xFF` のままです。最大レイドのホストは `0x11` を広告しますが、これは表にない値です。

同じ本体から交換の広告 5 件とギフトの広告 4 件を比べると、画面によって異なる残りのバイトは `0xB9` (ギフトは 0x00、交換は 0xAA) だけでした。意味は未確認です。ほかのバイトはセッションごとに固定か、ランダムです。スキャンしたリンク交換のネットワークでは LDN の `SceneId` は 60001 を示し、ギフト画面では 65535 を示します ([席につく](swsh_session.md#taking-a-seat))。

## ギフト画面の Pia メッシュ

この画面のメッシュは参加者を受け入れず、無理に座らせた局はカードを何も受け取りません。カードは [ビーコン転送](#the-card-travels-in-beacon-advertise-data) を使います。

参加者は 0x14 で局のハンドシェイクを完了します (本体の接続要求、結果 0 の応答、タイプ 5 の ack、840 バイトのタイプ 2 の局レコード)。その後、0x18 で送られるメッシュの参加要求は拒否されます。

    02 00 ff ff 01        JOIN_RESPONSE, refused, reason 1

同じ参加要求をリンク交換に送ると、148 バイトの応答が返ります。0x58、0x7C、0x80 では、その後に何も続きません。参加要求を送らずに待つと、本体はハンドシェイクの後に更新セッションだけを送ります。このセッションでは、参加者が `allow_participating` を立てた座席 1 として並んでいます。

`ProcessJoinRequestJob` は、`InitialStep`、`CheckApprovalJoin`、`SendJoinRefused`、`SendJoinResponse`、`WaitResponseAck`、`JoinSucceeded` の順に処理します。理由 1 はアプリケーションのコールバックからだけ返ります。ほかの理由は、トランスポートの確認によって決まります。

| | Sword | Shield |
|---|---|---|
| 状態名の文字列 | `0x03ad0f4e`..`0x03ad1010` | |
| `CheckApprovalJoin` | `0x01553d20` | `0x017cc450` |
| 理由 1 の格納 | `0x01553d58 strb w9, [x19, #0xbc]` | `0x017cc59c strb w9, [x19, #0xba]` |
| `MeshProtocol` のグローバル | `0x04c4db60` | |
| `MeshProtocol+0x60` の Pia トランポリン | `0x0157fcfc`, global `0x04c4b848` | `0x018414b0`, global `0x02616a30` |
| trampoline installed by | `0x0171a0b4`、スロット `0x04c513f8` から | |
| `SendJoinRefused` | `0x01553d80`。`0x0154cd00` が `0xFFFF0002` を書き、続けてオフセット 4 に理由を書く | |
| transport check | `0x0154806c`: `0xFF`、または理由 0、2、4、5 | `0x017bb2e0` |

    0x01553cc0  ldr  x8, [x8, #0x60]      ; the approval callback (Sword)
    0x01553cc4  cbz  x8, #0x1553d34       ; no callback installed -> accept
    0x01553d2c  blr  x8
    0x01553d30  tbz  w0, #0, #0x1553d4c   ; bit 0 clear -> refuse
    0x01553d54  mov  w9, #1

    0x018414b0  adrp x8, #0x2616000 ; ldr x8, [x8, #0xa30] ; ldr x8, [x8]    (Shield)
    0x018414bc  ldr  x1, [x8, #0xb0]
    0x018414c0  cbz  x1, #0x18414c8      ; null -> mov w0, #1 ; ret
    0x018414c4  br   x1

トランポリンは、オブジェクトの `+0xb0` が null のとき承認し、そうでなければそのアドレスへ末尾呼び出しします。ゲームは `0x01841490` (`str x1, [x0, #0xb0]`) でこのフィールドを書き込みます。これは `0x006b47b0` から、スロット `0x02616a38` のフィルタ `0x006b41c0` を渡して呼ばれます。また `0x018414a0` (`str xzr`) で消去し、これは `0x006b5340` から呼ばれます。どちらの呼び出し箇所も、モード切り替えの `0x006a9af0` から到達します。

### 参加フィルタ 0x006b41c0

`manager` は `[0x02610000 + 0x4b0]`、`session` (ゲームのセッション) は `[manager+0x58]` です。フィルタは 4 つのゲートを順に通ります。値は検索画面でライブに読み取りました。

| 順序 | site | 検査 | ライブの値 | 判定 |
|---|---|---|---|---|
| 1 | `0x006b4204` | ブロックリストが有効 (`manager+0x21C`) かつ空でない (`+0x1C0`。16 バイトのエントリを `0x006be4a0` でたどる) | 有効、空 | 通過 |
| 2 | `0x006b8230` 内の `0x006b8260` | Pia の局数 `pia_obj+0x1A8` が `session+0x1F0` 未満か (符号なしの `b.lo`) | 局数 1、最大 0 | 拒否 |
| 3 | `0x006b827c` | 募集中の判定。`session` の vtable `+0xB0` = `0x006ccb00` (`ldrb w0, [x0, #0x4f5]; ret`)。非ゼロなら `session+0x4c0` の許可リストを、件数 `+0x4c8` ぶんたどる (`0x006b8290`) | フラグ 0 | 承認 |
| 4 | `0x006b4248` | identity `+0x10` の halfword に対する `cbz`。そうでなければ `[manager+0x2b0]` (件数 `+0x2b8`) を検索し、`[manager+0x220]` と比べる | IPv4 の局はすべて 0 | 承認 |

許可リストのフラグ `session+0x4f5` は `0x006b86c4` と `0x006cc7bc` で立てられ、`0x006ca848` で下ろされます。下ろすのは `LdnCreateSessionSetting` を `0x006ca86c` で組み立てる直前です。エントリは `0x006b5c80` -> `0x006b9920` で追加され、`0x006b5c70` -> `0x006b9910` で空にされます。

identity は `0x0177b7b0` で作られ、`0x017b1bd0` で埋められます。この関数は、参加者のメッシュ局の位置情報エントリ (`+0x448` が局、`+0x440` が 3 のもの) の `+0x10` から 32 バイトをコピーします。

    0x017b1c50  add x1, x23, #0x10 ; mov w2, #0x20 ; mov x0, x20 ; bl 0x18fde50

`InetAddress` (デシリアライザ `0x01767a10`) は、`+0x08` にゼロ埋めの 16 バイトのアドレス欄を持ちます。サイズのバイトが 0x12 でなければ、ここにはビッグエンディアンの IPv4 が入ります。ポートは `+0x18` にあります。位置情報は、公開アドレスを `+0x00`、非公開アドレスを `+0x28` に保持します。そのため identity は公開アドレスの中にあり、identity の `+0x10` はアドレスの 8 バイト目です。IPv4 ではこれがゼロです。コールバックがたどるリストは、参加者のアドレスをキーにしています。バージョン 4 の位置情報のデシリアライザ (`0x0185eff8` 以降) は、中継ポートを `+0x60`、定数 ID を `+0x68`、可変 ID を `+0x70`、サービス可変 ID を `+0x74`、NAT の 4 要素を `+0x78`..`+0x7b` に格納します。これらはコピーされる範囲の外です。定数 ID `0x1249a221d8580000` は、ギフトのシーンでは拒否され、交換のシーンでは受け入れられます。

`session+0x1F0` の最大値を書き込むのは `0x006b9900` (`str w1, [x0, #0x1f0]`) だけです。これは、呼ばれない thunk `0x006b5c00` とラッパー `0x0110e5e0` を経由して到達します。ラッパーの 2 つの呼び出し元 (`SetMax(GetCount())`) は、ダイマックスアドベンチャーのマッチング (`0x00bd9b30`。`ChikaMatchingState*` 状態 `0x00bd1978..0x00bda158` のうち) と、マックスレイドの巣穴 (`0x01031c74`。`View_NestHole`、`StateGuestReady`、`StateHostReady` `0x0102aba4..0x010370cc` のうち) です。ゲームを 1 本動かしてライブで読むと、ギフト画面では 0、リンク交換をホストしているときは 2、マックスレイドをホストしているときは 4 でした。3 つとも同じフィルタを有効にした状態です。レイドのホストは `NodeCountMax` 4 を広告します。ギフト画面は、Pia の最大値が 0 の状態で 2 を広告します。

`game_session+0x3F8` は、ギフト画面では 1、受け入れを行う 2 つのセッションではどちらも 0 です。`+0x365`、`+0x33D`、広告の `+0xF9` はレイドの後も、レイドの値のまま残ります。そのため、これらはモードの残り香です。`manager` は、ギフト画面と交換のホストでバイト単位で同一です。

### 転送の確認

`0x017bb2e0` は、コールバックの前に `CheckApprovalJoin` から実行されます。`0xFF` か理由のバイトを返し、その値はそのまま送られます。

    0x017bb358  bl   0x017bab70        the live station count
    0x017bb35c  ldrh w9, [x19, #0xa8]  the maximum
    0x017bb368  b.hs 0x017bb380        count >= max, reason 0
    0x017bb370  bl   0x017bb5a0        the index of the first free station slot
    0x017bb378  cmp  w8, #0xfd         no free slot, reason 0

そのオブジェクトは `read_u64(read_u64(main + 0x0262F7B0))` で、`pia_obj` (`main + 0x02616A30`) や `game_session` とは別物です。

| field | width | 内容 |
|---|---|---|
| `+0xA8` | u16 | 最大の局数 |
| `+0xAA` | u8 | 有効化のバイト。ゼロなら、ほかの検査の前に 2 を返す |
| `+0xAB` | u8 | 局数を読むビットマスクのワードを選ぶ |
| `+0xAC` | u8 | 局数の数え上げで、ビットマスクをたどる幅 |
| `+0xC4` | u32 | 占有のビットマスク。`[0xAC] == [0xAB]` のときに読む |
| `+0xC8` | u32 | それ以外のときの占有のビットマスク。空きスロット検索が読むのはこれだけ |

カウントは、立っているビットごとに 1 を足し、それに 1 を足した値です (`0x017bad94`)。空きスロットの検索は、最初に立っていないビットを返します。該当しなければ `0xFD` です。エミュレータのリンク交換画面で、待機中と 49 回の試行にわたってライブに読むと、max 8、enable 1、sel 0、bits 0、`+0xC4` 0、`+0xC8` 1 でした。そのため最初の 2 つの判定は通ります。ほかに 3 つの終了経路があり、どれも 0 を返します。

| site | 検査 |
|---|---|
| `0x017bb380` | `count >= max`、または空きスロット検索が `0xFD` を返す。計測では通過 |
| `0x017bb498` | `mesh_obj+0x370` のテーブル。そのサイズを `read_u64(main + 0x02616710) + 0x70` の u16 と比べ、次に `table+0x48` の容量と比べる。テーブルにすでにある参加者は両方を飛ばす (`0x017bb41c`) |
| `0x017bb4d4` | `mesh_obj+0x132` のバイト。型 0x18 のイベントで `mesh_obj+0x120` のハンドラが立て、読んだあとに下ろす |

`+0xAA` がゼロか、予備の判定が成り立つと 2 を返します。`mesh_obj+0x131` が型 0x19 のイベントで立っていると 4 を返します。

### 局が座った状態

- 検索画面で `game_session+0x1F0` に 8 を書き込むと、参加がすぐに許可されます (148 バイトの応答、局数は 1 から 2 へ)。0 を書き込むと理由 1 に戻ります。
- エミュレータで `+0x1F0` と `+0x1F4` を 2 に書き換えると、参加への応答は `02 00 ff ff 00` になりました (理由 0。転送の確認の短い形式です)。同じ画面でリンク交換のホストが返すのも同じ 5 バイトです。すべてのパケットが認証されます。
- LDN のノードが参加すると、本体は約 1 秒に 6 回、そのノードを座席 1 として載せたローカルプロトコルの更新セッションを送ります。ノードがいなければ送りません。ack を 1 回返すと止まります。ack を返さない場合 (`--no-ack-update`) は送り続けます。注意点として、エミュレータの 12345 番のワイルドカードソケットは、ほかのリスナー宛ての放送を奪うことがあります。更新は外部のキャプチャで観測してください。
- ノード間の通信は、12345 番の Pia と 11452 番の ldn_mitm の制御チャネルだけです。
- 座った状態では、シーンは RTT のプローブ、2 つのポートでの信頼性ウィンドウの開始、メッシュの更新を送ります。アプリケーションのペイロードは送りません。0x84 では何も開きません。0x7C で ping に順に ack を返します。
- 交換のドライバの 4 バイトのヘッダ (`u16 id, u8 disc, u8 0`) の後ろにある 0x2D0 のレコードは、0x7C と 0x80、ポート 0 と 1 で送られ、ack が返ります。受け取りのジョブには届きません。
- 本体自身のセッションから作られた広告は、6 種類のバリアントとシーン ID 60001..60021 を持ちます。それらは本体のスキャンで返され、`pia_obj+0x3C0` に登録されます。いずれも `Connect`、`OpenStation`、受け入れポリシーの呼び出し、最大値や `+0x3F8` の変更を引き起こしません。

## 受け取りジョブとインポーター

gfl net マネージャは `read_u64(read_u64(main+0x0261CBA8))` です (vtable `0x025819A0`)。null のグローバルは、どの送信スタブでも行われるセッション無しの検査になります。`+0xD0`/`+0xD8` にエントリの配列はありません。ローカル無線の分岐に入ると、`StateReceiveLocal` のドライバ `0x01004C80` (`state+0x2A0` にあるケースのマシン) が、`0x010B7100` を経由して受け取りジョブを作ります (コンストラクタ `0x010B73E0`、vtable グループ `0x0257DD88`、ポーリング `0x010B74D0`)。そのジョブを `manager+0x68` にリンクし、`state+0xB0` に受け取りのデリゲートを設定します (`0x0100504C` グループ)。

ジョブは、データ先のシンクを `job+0x60` (ターゲット `0x01005BC0`) に、進捗のコールバックを `job+0xE0` (`0x01005C70`) に持ち、そのメッセージのソースとして `job+0x08` のセッションオブジェクトを持ちます (vtable `0x0250DAE0`)。検索画面を開くと現れ、閉じると解放されます。注意点として、画面に入り直すと、ジョブとシンクのオブジェクトは新しいアドレスに作り直されます。

シンク (受け取りのデータ先) は `0x00FF0E00` -> `0x00FF1FB0` -> `0x00FF2170` と末尾呼び出しし、インポーターに渡します。インポーターは、0x2D0 バイトのレコードの整数倍でない本体を拒否します (720 バイトで、PKHeX の第 8 世代のワンダーカードのサイズです。アプリは `0x00feba7c` でも 0x2D0 のオブジェクトを確保します)。

    0x00ff22e4  umulh x8, x21, x8        ; x21 = the length
    0x00ff22e8  lsr   x28, x8, #7        ; x28 = length / 0x2d0, the record COUNT
    0x00ff22ec  mov   w8, #0x2d0
    0x00ff22f0  msub  x8, x28, x8, x21   ; the remainder
    0x00ff22f4  cbnz  x8, #0xff272c      ; not a whole number of records -> refuse

各レコードは `0x00FF2354` で [レコードが持つべき内容](#what-a-record-must-carry) の検査を通り、`0x01449820` でフィルタされ、`0x00FF3EC0` で実体化されます。何も受け取っていない状態で `StateConfirmGift` (12) を強制すると、null のカードで異常終了します (`0x015C9230 ldrb w8,[x0,#0x1AC]`。コントローラ `0x015BFFA0` からアプリ `0x00FFA458` を経由して呼ばれます)。`StateReceiveComplete` (14) を強制すると、空のパネルが表示されます。

インポーターの 2 番目の引数はルートです。これは `0x00FF0E00` と `0x00FF1FB0` を経て `0x00FF2170` まで変更されずに渡され、`[sp+0x35c]` に保持されます。カードの `+0x64` (`0x00FF3F5C`) になり、`route != 0` のときはヘッダの `+0x0E` (`0x010B5FAC`) にもなります。呼び出し元は、受け取り状態の vtable のスロット 16 にあるラムダです。

| state | route | 呼び出し箇所 |
|---|---|---|
| `StateReceiveLocal` | 0 | `0x01005bf8` |
| `StateReceiveInternet` | 1 | `0x01011588`, `0x010115f0` |
| `StateReceiveSerial` | 2 | `0x0100a268`, `0x0100a2d0` |
| `StateReceiveFromBall` | 2 | `0x0100fc78`, `0x0100fce0` |
| `StateReceiveRankMatch` | 3, 4 | `0x01012458`, `0x010124c0` |

ルートが 0 以外なら、レコードの日付を上書きします ([カードの日付](#the-cards-date))。インポート後 (`0x00ff24e0..0x00ff26d4`)、ルート 3 と 4 は、ブロック `0xa83021c1` (0x268 バイト) と `0xce07d358` (0x1c バイト) の 2 から 4 のバイトを設定します。ルート 3 では、レコードの `+0x1c` から得た添字 (最大 0x2f) に設定します。その添字は `+0x1e` で選んだ半分と、`+0x11` の種類で選んだグループの中にあります。ルート 4 では、レコードの `+0x18` にある u32 がブロックの先頭ワードと一致するときに設定します。ルート 0 は、どちらのブロックにも触れません。

## カードはビーコンの広告データで届く

配布元は何にも参加しません。カードを載せた広告データを持つネットワークを広告し、受け取り側は `Scan` の結果からカードを組み立て直します。

ふしぎなおくりものは gflnet3 のコアの利用者で、交換の同期ポンプとは別です (交換のポンプは登録配列 `0x006db3b0`、マネージャ `read_u64(read_u64(main+0x02616750))` を使い、ギフト画面では空です)。交換のポンプは 0x7C と 0x80 を、4 バイトのヘッダつきで処理します。コアのマネージャ `read_u64(read_u64(main+0x02616B80))` は自身を `BeaconCommunication` と名乗り (`0x02068858`。`conn+0x278` と `conn+0x308` にも同じ名前があります)、`nn::ldn::Scan`、`GetNetworkInfo`、`SetAdvertiseData`、`OpenAccessPoint` を呼び出します (ラッパーは `0x017978F0`、`0x01794C3C`/`0x01799BE0`、`0x017961B0`、`0x01794CF0`)。`core+0x50` の接続オブジェクトは、どの相手よりも前に存在します。送信のゲート `+0x2FA` は一度も立ちません。Pia メッシュの参加が変えるのは、この中の LDN ノード数のミラーだけです。コアの送信 `0x006C2840` は `core+0xF8` でキューに入ります。送信の経路では、`0x136` が `0x010F7E00` の `memset` の長さになり、メッセージ ID はゲッター `0x010F7050` から得られます。

## ビーコンの本体フレーム

LDN の広告データ 0x180 バイトは、0x18 バイトのヘッダと、ビーコンのコアが枠づける 0x168 バイトの本体からなります。

| body 内の offset | size | 内容 |
|---|---|---|
| `+0x00` | 2 | `body[2:0x168]` に対する CRC-16/ARC。初期値 0、最後の XOR なし |
| `+0x02` | 12 ビット | ネットワーク ID。下位 8 ビットは `body[2]`、上位 4 ビットは `body[3]` の下位ニブル |
| `+0x03` high nibble | 4 ビット | 捕まえたすべてのビーコンでゼロ |
| `+0x04` | 1 | 捕まえたすべてのビーコンでゼロ |
| `+0x05` | 最大 0x163 | アプリケーションのペイロード |

ネットワーク ID は、ふしぎなおくりもの、リンク交換、マックスレイドの各画面で捕まえたすべてのビーコンで `0xD70` です。ペイロードの上限は `0x006c2174` の `cmp x2, #0x163` で、`body+5` への `memcpy` を守ります (`add x0, x8, #5`、`0x006c2148`)。

チェックサムのルーチン `0x0065dcb0` はテーブル駆動です。テーブルは `0x0065def0` が `0x02615fd8` の裏で遅延して作ります。多項式 `0xA001` の反転した CRC-16/ARC のテーブルで、0 から `crc = T[(crc ^ byte) & 0xFF] ^ (crc >> 8)` の式で更新されます。捕まえた 40 個の本体は、保存されたチェックサムを再現し、デコードしたフィールドからバイト単位で作り直せました。

ビルダー `0x006c1fa0` は、本体をゼロで埋め、ビットパックのライタ `0x006c1830` で `body+2` にネットワーク ID を書き、ペイロードを `body+5` にコピーします。そして `body+2` から 0x166 バイトに対するチェックサムを `body+0` に保存します。ペイロードがない、または大きすぎる場合は、代わりに `0xFFFF` を保存します (`0x006c21d4`)。

## 受け取ったビーコンが通るゲート

`0x006c1be0` は 1 つのエントリオブジェクトを受け取り、承認するなら 1 を返します。作る経路では、`SetAdvertiseData` の前に本体を検査します (`0x006b5ba8` が作り、`0x006b5bb0` が検証します。`0x006c3de4` と `0x006c42c4` は、0x168 のコピー (`0x017760e0`) の前に、`conn+0x360` の広告オブジェクトを検証します)。受け取る経路では、`0x006bb9d4`、`0x006c4b38`、`0x006ca0dc` が、受け取った広告を `0x006c2360` を経由してスタック上のエントリにコピーし、ゲートを呼びます。エントリをストア `0x006c53b0` に渡すのは、ビット 0 が立っているときだけです。どれか 1 つの検査が失敗すると拒否されます。

1. `0x02616b80` の背後にあるコアのオブジェクトが存在すること
2. `body+0` が、`body[2:0x168]` から再計算したチェックサムと一致すること
3. 本体のネットワーク ID が、`0x02616b88` の背後にある halfword と異なること (コアがないときのビルダーのフォールバック)
4. ネットワーク ID が、コア自身のものとニブル単位で一致すること (`0x006c1cf0`)。下位ニブルが等しくなければならず、2 番目のニブルが異なれば承認します。そうでなければ、3 番目のニブルが等しくなければなりません

古いチェックサムのビーコンはスキャンされますが、保存されることはありません。同じビーコンでもチェックサムが正しければ、最初のスキャンで保存されます (計測で 0.21 秒)。

注意点として、0x480 バイトの `NetworkInfo` スキャン結果のスロット (`pia_obj+0x3C0` を含みます) は、チェックサムに関係なく、本体を 0x180 バイトまるごとコピーします。そこにマーカーがあっても、受信したことが分かるだけです。

`0x006c53b0` は、承認されたエントリを保存済みの各エントリと比べ (`0x006c1da0`。本体と ID の構造体)、新しいものだけを `0x006c5460` で追加します。ストアは、配列を `+0x40`、件数を `+0x48`、容量を `+0x50` (0x32)、ミューテックスを `+0x60` に持ちます。エントリは 0x180 バイトで、先頭が vtable のポインタ、`+8` に本体があります。同じ vtable は `conn+0x360` にあり、本体自身の `conn+0x368` より 8 バイト前にあります。2 つのストアは `0x006c5300` で交互に使われます。

`0x010f6600` はストアをたどります。ネットワーク ID は `0x006c1d50` で読み、ペイロードは `0x006c1f80` で読みます (`body+5` を返します。呼び出し元は `0x010f66c4` だけです)。そしてペイロードを `0x010f8cf0` に渡します。`0x010f8cf0` は、それを `[gfl_job+0x68]` の vtable `+0x38` のハンドラ用のメッセージオブジェクトに格納します。受信側の局情報の構造体はこのペイロードそのもので、そのオフセットは広告データの 0x1d バイト目から始まります。

## ポーリングが組み立て直すメッセージ

ペイロードのバイト 0 がメッセージの種類です。`0x010f6600` は、既知の種類ごとに型付きのビューを作ります。ビューは `payload+1` を指します。

| type | view | 行き先 |
|---|---|---|
| 0 | `0x010f8730` | `0x02610958` の背後にあるオブジェクトを使う `0x0110f270`。受信側が自分のビーコンを送る (局情報) |
| 1 | `0x010f8830` | `[manager+0x68]` のジョブ。vtable のスロット `+0x38` |

ギフト画面では、そのジョブは受け取りジョブです。スロット `+0x38` (`0x0257dd88+0x48`。vtable のポインタはグループに 0x10 を足したものです) はそのポーリング `0x010b74d0` なので、種類 1 のペイロードはインポーターに渡ります。

ポーリングは、`0x010f7bf0` を経由して `payload+1` から 10 バイトのヘッダを読みます (フィールドのアクセサは `0x010F7A40..0x010F7A80`。送信側は `0x010F7C08` でレイアウトします)。その後に断片が続きます。

| offset | size | 意味 |
|---|---|---|
| `+0` | 4 | ゼロなら、ポーリングはすぐに戻る |
| `+4` | 2 | メッセージ全体の長さ |
| `+6` | 1 | 断片の数 |
| `+7` | 1 | この断片の添字。断片数より小さくなければ拒否する |
| `+8` | 2 | 組み立て直したメッセージの CRC-16/ARC (`0x0065dcb0`) |

組み立ての文脈は 0x88 バイトで、送信中のメッセージごとに 1 つあります。`job+0x160` と `job+0x168` の間に置かれます。`0x010f7550` は、添字を除くすべてのヘッダフィールドについて、断片を文脈と照合します。一致しなければ、`0x010f7360` が文脈を追加し、`+0`、`+8`、`+0x10`、`+0x18` にフィールドを格納します。`+0x20` のバッファは長さ (`0x010f6fa0`) から、`+0x58` の到着ビットマップは断片数から決めます。`0x010f7430` は断片を受け入れ、`0x010f7100` は `index * 300` の位置にコピーします。最後の断片は残りの長さを取ります。添字がバッファの外にあるか、ビットがすでに立っている断片は捨てられます。メッセージは最大 65535 バイト、256 断片までです。720 バイトのカードは、300、300、120 バイトの断片になります。

`0x010f7610` がすべてのビットが立ったと報告すると、`0x010f7680` は `context+0x18` を `0x010f71e0` (`0x0065dcb0` までのバッファ) と比べ、一致しなければ null を返します。ポーリングは null のときシンクを飛ばし (`0x010b77fc`)、どちらの場合も 1 回のポーリングの中で文脈を消します。

注意点:

- チェックサムの誤ったメッセージは痕跡を残しません。その文脈は、断片 1 つ手前までしか観測されず、その後消えます。シンク `0x01005bc0` には届きません。
- ビーコンのあとで文脈リストが空なのは、組み立てが完了したメッセージが残す状態です。
- ヘッダの `+0` がゼロでないとき、`job+0x160` は null のままで、文脈リストは確保されません。ゼロのときは、リストが確保され、`manager+0x80` が最初の刻印を受け取ります。

## レコードが持つべき内容

| offset | size | 内容 |
|---|---|---|
| `+0x00` | 8 | 日付 ([カードの日付](#the-cards-date)) |
| `+0x08` | 4 | カード ID。u16 で、ワード全体として比べる。`+0x0A..+0x0B` はゼロでなければならない |
| `+0x0C` | 2 | 働かない |
| `+0x0E` | 2 | ゲームバージョンのマスク |
| `+0x10` | 1 | フラグ。bit 0 はカードごとの回数制限の表を飛ばす。bit 2 はカードの日付ごとに 1 回 |
| `+0x11` | 1 | ふしぎなおくりものの種類。1 から 5 |
| `+0x12` | 1 | カードごとの回数の上限 |
| `+0x13` | 1 | カードごとの回数のタグ |
| `+0x15` | 1 | タイトルの添字 |
| `+0x1C` | 1 | ヘッダの `+0xf` に保持される |
| `+0x20` | | 種類ごとのペイロード |
| `+0x2CC` | 2 | この欄をゼロにしたレコードの CRC-16/CCITT-FALSE |

バージョンのマスク: インポーターは `0x007d4270` を呼び (Shield では `mov w0,#0x2d; ret`)、値が `0x2D` のときは `1 << 1`、そうでなければ `1 << 0` をマスクに対して試します (`0x00ff2330..0x00ff2358`)。Shield はビット 1 を取ります。`0xFFFF` はどちらのバージョンも通り、ゼロは飛ばされます。

カードごとの回数制限の表: `+0x13` がゼロでないとき (`0x00ff236c`)、`0x01449820` は、アルバムの `+0x1660` にある表のエントリ (ブロック `0x112D5141` のオフセット `0x1600`。4 バイトのエントリが 50 個あり、halfword のカード ID と 1 バイト) のどれかが、`+8` のカード ID と `+0x13` のバイトに一致すると、レコードを拒否します。保持する場合、`+0x12` がゼロでなく、`+0x10` の bit 0 が下りているとき (`0x00ff152c`)、`0x00ff1544` が `0x014494a0(album, record)` を呼びます。これは 50 個のエントリを 1 つずつ後ろにずらし、`{card id, +0x13}` を `+0x1724` に追加します。このカード ID のうちゼロでないバイトを持つエントリが `+0x12` に達すると、先頭 49 個の中のそれらをゼロにします。`+0x13` か `+0x12` がゼロのとき、または `+0x10` の bit 0 が立っているときは、カードは毎回インポートされます。

最後に受け取った表: `+0x10` の bit 2 が立っていると、保持の経路は `0x01449560(album, record)` を呼びます (`0x00ff1548`、`0x00ff1558`)。アルバムの `+0x15c0` にある 16 バイトのエントリが 10 個あり、`+0` に u64 の日付、`+8` に u16 のカード ID を持ちます。ID を持つエントリがあれば、レコードの日付を取ります (`0x01449650`)。なければ、日付が古い (符号なし、`0x016cc1f0`) 最初のエントリが、ID と日付を取ります (`0x01449804`、`0x0144980c`)。空のエントリは、日付がゼロで古いので取られます。

受け入れたレコードは、0x338 バイトの構造体にコピーされます (先頭の 0x68 バイトはゼロにし、`+0x68` にレコードを置きます。`0x00ff2380`)。その後、長さ `0x2D0` で検証器 `0x010b5de0` に渡されます。作られるカードのオブジェクトは 0x3A8 バイトで、構造体を `+0x70` に保持します。

`0x010b5de0` は、レコードをスタック上にコピーし、`+0x2CC` をゼロにして、0x2D0 バイト全体に対して CRC-16/CCITT-FALSE を計算します。テーブルは多項式 `0x1021` の MSB 先頭で作ります (`0x010b5e60`)。初期値は `0xFFFF`、更新式は `T[(byte ^ (crc >> 8)) & 0xFF] ^ (crc << 8)` です (`0x010b5f54`)。戻り値は、ヌルポインタか長さが `0x2D0` 以外のとき `0x80000000`、チェックサムが一致しないとき `0x80000001` です (インポーターは `0x00ff23d0` でこれを 1 に変換します)。それ以外は 0 で、1 から 5 の範囲外の種類も含みます (`0x010b6004`)。種類 1 と種類 4 のビルダーの結果は捨てられます。`0x68` バイトのヘッダを埋めます (`0x010b5f98..0x010b5fbc`)。カード ID を `+8` に、`+0x15` を `+0xa` に、`+0x11` を `+0xc` に、`route != 0` を `+0xe` に、`+0x1C` を `+0xf` に入れます。エミュレータでは、封印されたレコードは受け入れられ、`+0x20` のワードを使って種類 3 の経路に入ります。封印されていないのと同じレコードと、すべてゼロのレコードは、`0x80000001` を返します。

カード ID: インポートのループの後、`0x00ff2760` が ID の一致するカードを集めます。`0x00ff2f50` は、レコードの `+0x08` の u32 (`0x00ff30c0`、`ldr w8,[card+0xe0]`) を 16 ビットの ID と比べます。そのため `+0x0A` か `+0x0B` にゼロでないものがあると、何とも一致せず、インポーターは 2 を報告します (このゲームでは入手できないふしぎなおくりものです)。市販の本体では、`+0x0A` に `80 06` を入れたものはこの方法で拒否されました。`+0x0A` がゼロで、`+0x0C` に `a5 6a` を入れたものは受け取れました。読み取った中で `+0x0C` に触れるものはありません。projectpokemon の EventsGallery にある SwSh のカード 161 枚はすべて、`+0x0A` がゼロで、`+0x0C` は 3 かタイトルの添字のどちらかです。

タイトル: `+0x15` は、PKHeX が `text_wondercard8_<lang>.txt` として同梱しているタイトル表の添字です。カードを受け入れる前に、一覧に表示されます。ビルダーが使う添字は、1 がポケモンのタマゴ、3 がアイテム名、21 が "{species} (Gigantamax Pokemon)"、34 がお小遣い、36 が衣装、39 がバトルポイントです。添字 0 はポケモン名だけです (`+0x0C` が `0b 00` でタイトルが 0 のレコードは "Pikachu" と表示されました)。添字 11 は "{species} de {original trainer}" で、フランス語の本体では "Pikachu de POKELDN" と表示され、そのまま保持されました。

種類: 1 から 5 は `0x02067620` を経由して振り分けられます。それ以外は、何も作らずに成功を返します。種類 3 と 5 (`0x010b5fd8`) は、ヘッダ `+0x30` の `+0x20` のワードを保持するだけで、何も作りません。種類 1 は `0x010b58f0` に進みます。種類 2 はアイテムの組をコピーします。種類 4 は `0x010b5bb0` に進みます。

言語の添字は `0x02067650` の表から得られます (ゲームの言語を 0 から 8 に対応づけます)。リボンのバイトは `0x00775d50` に渡されます。127 を超える添字は何も設定しません。リボンのバイトがゼロのレコードは、リボン 0 を 32 回指定したことになります。そのため、一覧は `0xFF` で埋めます。

パーサはレベルと出会ったレベルを読みません。どちらのオフセットも、コードではなくカードから得ています。`0x238..0x272` のうち、2 枚の請求カードのレベルが異なることを予測できるのは `+0x244` と `+0x249` だけです (レベルは 28 と 63、出会ったレベルは 32 と 59)。

レベル: ビルダーは `r = random & 0x7f` を、`r <= 99` になるまで引き、`r + 1` を取ります。これは 1 から 100 の一様分布です (`0x010b6218`)。あるレコードは 20 のあとに 35 になりました。タマゴ (`+0x245` = 1) は、それに関係なくレベル 1 になります (`0x010b6400`)。乱数で決まったポケモンの出会ったレベルは 0 になり、`+0x249` は空のままです。経験値は常に種族の成長タイプと一致します (立方型の種族はレベル 20 で 8000、もっと遅い種族はレベル 4 で 96 でした)。

個体値: ビルダーは 6 つのバイトを HP、攻撃、防御、特攻、特防、素早さの順に調べます。`0xFC..0xFE` の最初のバイトは、完璧な個体値の数 `byte - 0xFB` (1 から 3) を `[sp+0x110]` に保存し、6 つの個体値すべてを `0xFFFF` にします。残りの値は捨てられます (`0x010b6300..0x010b63c4`)。そうでなければ、32 以上のバイトは `0xFFFF` になり、32 未満のバイトはそのまま残ります。仕様は `0x007667a0` から `0x007662a0`、`0x00777f40`、`0x00766660` を経由して届きます。ここでレベルは 100 で頭打ちになり (`0x00766a14`)、個数が 1 から 5 のときは、その数だけ別々のランダムな位置に 31 を書き込みます (`0x00766a50..0x00766b04`)。個数が 6 以上のとき (カードの届く範囲外です) は 31 を書きません (`0x00766a2c..0x00766a44`)。まだ `0xFFFF` の個体値は、0 から 31 の乱数で決まります (`0x00766de8`、`0x007660d0(0x20)`。`n` 未満のゲームの乱数)。そのため、どの個体値のバイトでも `0xFC`、`0xFD`、`0xFE` があると、31 のランダムな個体値がちょうど 1、2、3 個になります。

ユニコーンで動かしたビルダーが示したとおり、ゼロのまま残したレコードは、最初の特性を持つ、オスのがんばりやのポケモンで、個体値は 0 になります。`pokeldn.swsh.wc8.pokemon_card` は、フィールドを指定しない限り、性別 3、性格 `0xFF`、特性 3、すべての個体値のバイトを `0xFF` にします。そのためゲームが、それぞれを乱数で決めます。

性別 3 はビルドごとに 1 回だけ乱数で決まります。受け取りの 1 回で、ポケモンは 2 回作られます。見せる状態 `0x00fe3720` は、レコードから 1 つ作り (`0x00fe3a50`)、そのオスメスをモデルのために読みます。また、受け取りの処理 `0x010159d0` は、パーティに入るほうを作ります (`0x01015a0c`)。市販のソードでは、1 回の受け取りで、メスと表示されたのにオスが渡されました。性別 0、1、2 のときは乱数を振らないので (`0x00766d94`)、両方のビルドは一致します。市販のソードでは、0 のときはオスと表示されてオスが渡され、1 のときはメスと表示されてメスが渡されました。アプリと `bin/swsh_gift_host.py` は、カードを作るときに性別を 1 回だけ決めます。ゲームが決めるのと同じ方法です (`r + 1 < ratio` のときメス。`r` は 253 未満。比率は PKHeX による種族の個体別の比率)。`--set gender=3` を指定すると、ゲーム本来の乱数に戻ります。

## ビーコンで届いたカードの end-to-end

3 つの断片に分割した 720 バイトのレコードを、合成したビーコンから配信すると、メモリもコードも変更していない、エミュレートした本体のインポーターに届きます。インポーターの結果は `bound+0x2C0` にあります (`bound` は `job+0x80`)。バージョンのマスクだけが異なる 2 つのレコードは次のとおりです。

| version mask | result | 本体のメッセージ |
|---|---|---|
| `0x0000` | 2 | ギフトは受け取ったが、このゲームでは入手できない |
| `0xFFFF` | 1 | ギフトの受け取りに失敗した |

`0x00ff1fb0` は、値がゼロでなければインポーターの値を返します。カードの一覧が空なら 2 を返します。マスクで除外されたレコードは、一覧を空のままにします。`0xFFFF` のレコードは `+0x2CC` のチェックサムがゼロで、検証器の `0x80000001` は 1 として返りました。どちらも異常終了しませんでした。

封印された種類 3 のレコードは、一覧に載り、確認され、保存されます。画面には、`+0x11` の種類からタイトルを、`+0x20` のワードから数量を表示します。日付がゼロなら 2070 年 1 月 1 日と表示されます。ID がゼロのものは、何も届けません。

## 市販の本体に届けたカード

`bin/swsh_gift_host.py` は、LDN 経由でカードを市販のソードに届けます。市販のソードは、広告データが Pia のヘッダで始まるときだけカードを一覧に載せます。

| ホストが広告したもの | 一覧に載るか |
|---|---|
| LDN プロトコル 3 (GBA アプリのもの)。広告データが 24 個のゼロバイトで始まる | いいえ |
| LDN プロトコル 1。本体自身のもので、24 個のゼロバイト | いいえ |
| LDN プロトコル 1。広告データの先頭が Pia のヘッダ | はい |

Pia のヘッダは、本体自身のギフトの広告が始まるものと同じです ([ソードのセッション](swsh_session.md))。ランダムなネットワーク ID、ゼロのパスワード CRC、システム通信のバージョン 5、ヘッダのサイズ 0x18、ランダムなセッションのパラメータ、8 個のゼロバイトからなります。シーン ID 0 とアプリケーションのバージョン 4 は受け入れられました。本体自身の広告はシーン 65535 とアプリケーションのバージョン 7 を持つため、どちらでも絞り込まれません。ldn_mitm は 802.11 の広告を運ばないので、エミュレータではこれらの変数を検証できません。

PKHeX の検査は、進化先にキョダイマックスの形があるポケモンについて、キョダイマックスの要素を取ります。カード 1641 と 1642 がフシギバナとゼニガメにそれを与えたためです。また、マックススープが手を付けないメルメタルについても同様です (`services/pkhex/Program.cs` の `CanGigantamax`)。それ以外の種族は拒否されます。

### Pokemon HOME

Pokemon HOME は、ふしぎなおくりもの (Wonder Card) としてではなく、自分のボックスに直接ギフトを入れていました。このグループには、コミュニティが作ったそのカードが入っています。ギャラリーの `HOME Simulated WCs` (ソード・シールド用。カード ID は 9000 以上で、PKHeX の `WC8.IsHOMEGift` が判定します) です。各カードは、PKHeX のイベントデータベースが持つカードとバイト単位で一致します。projectpokemon のタイトルで並んでいます。たとえば、隠れ特性のフシギバナ、ヒトカゲ、ゼニガメ (HOME の初心者用)、初回ログインのピカチュウ、全国図鑑のマギアナ、最初のワンダーボックスのイーブイ、最初の GTS のロトム、最初のチャレンジのピチュー、隠れ特性のサルノリ、ヒバニー、アシマリ、色違いのゼラオラ、Pokemon GO のメルメタル、キョダイマックスのフシギバナとゼニガメ、色違いのケルディオです。カード 9000 から 9007 の初版は、すべての PID を 0 に固定します。残してある 2 版目は、ゲームに乱数で決めさせます。

そこから受け取ったポケモンには、HOME のトラッカーがありません。PKHeX は、HOME が出したギフトにはこれを要求します。本体がポケモンを作るので、HOME のトラッカー設定にかかわらず、PKHeX はトラッカーがないことを指摘します ([HOME トラッカーの設定](gui.md#the-home-tracker-setting))。ただし Pokemon HOME は、現在これを受け入れます。アプリはこれらのカードを琥珀色で囲み、その旨を表示します。

`+0x10` のフラグは、本体がカードを受け取る頻度を決めます ([メニューが拒否するもの](#what-the-menu-refuses))。

| flags | カード数 | 受け取り |
|---|---|---|
| bit 0 | 130 | カード ID ごとに 1 回。以降はメッセージ 7 で拒否される |
| bit 2 | 13 | カードの日付ごとに 1 回。1 日に最大 10 枚 |
| neither | 46 | 毎回 |

バージョンのマスクが 1 または 2 のポケモンのカードが 2 枚あり、もう一方のバージョンでは飛ばされます。

### ID を共有するカード

配布が異なっても、カード ID を使い回していました。セーブデータが回数制限つき (フラグ bit 0) のカードを 1 枚受け取ると、同じ ID の別のカードはすべて拒否されます。

| card id | ID ごとに 1 回のカード |
|---|---|
| 1 | 2022 年の色違いガラルフリーザー、ファイヤー、サンダー (J と M それぞれ)。モンスターボール、ハイパーボール、ウルトラボールのおじさんのTシャツ |
| 101 | ポケモンセンターのイーブイとピカチュウ。それぞれ 2 版 |
| 118 | PCSG のイーブイとピカチュウ |
| 122 | ポケモンセンターのマホミル、リボンスイーツ、スタースイーツ。それぞれ 2 版 |
| 125 | PCSG のマホミル、リボンスイーツ、スタースイーツ |

カード 103 (6 枚) と 139 (7 枚) はフラグ bit 2 を持ちます。1 枚を受け取ったセーブデータは、2 枚目の日付が後でない限り、同じ ID の別のカードを拒否します。

アプリの「公式イベント」モードは、カードごとにカード ID を受け取り (ツールの値の `event_ids`)、選んだカードの ID を共有するカードを一覧にします。ID を変更すると、`+0x08` の u16 だけを書き換えて、レコードを封印し直します。unicorn の下では、受け取りの検査 `0x00ff1a30` は、ビットマップに ID 1 を持つセーブデータで、公式のフリーザー (ID 1) を拒否し、同じカードを ID 2 として受け取ります。検証器 `0x010b5de0` と PKHeX は、変更後のレコードを受け入れます。回数制限つきカードの ID は 1 から 2047 の範囲に収まります。ビットマップの読み取りには上限がないためです ([メニューが拒否するもの](#what-the-menu-refuses))。コマンドラインでも `--gift-file FILE --patch 0x08=0200` で同じことができます。市販の本体で、ID を変更したカードを受け取ったものはまだありません。

## 衣装

種類 4 のレコードは、`+0x20` から、u32 の組を 12 組持ちます。各組は、カテゴリ、次にインデックスです。プレイヤーの状態バイト `+0x105` がゼロなら最初の 6 組 (`+0x20..+0x4F`) を使い、そうでなければ最後の 6 組 (`+0x50..+0x7F`) を使います。そのバイトは、状態オブジェクト `[[0x2610798]+0x1e8]` に対して `0x01424c20` が読みます。PKHeX の `MyStatus8` は、プレイヤーの性別をブロックのオフセット `0xA5` に持ち、そこから `0x60` 下にあります。そのオブジェクトが `+0x60` にブロックを持っているかどうかは未確認です。

パーサ `0x010b5bb0` は、プレイヤーの 6 組をヘッダの `+0x30..+0x5F` にコピーします。また、インデックスが `0xFFFFFFFF` でない組の数をヘッダの `+0x0D` に入れます。受け取りの処理 `0x01015eb0` は、同じ判定でレコードの組をもう一度読みます (`0x01015f14`。レコードの `+0x20` はヘッダとレコードの `+0x88`)。そして、インデックスが `0xFFFFFFFF` でない組ごとに、衣装の棚 `[[0x2610798]+0x218]` に対して `0x0143a450(wardrobe, category, index, 1)` を呼びます。このセッターは、カテゴリが 14 を超えるか、インデックスが 1023 を超えると拒否します。そうでなければ、バイト `wardrobe + 0x68 + category * 0x80 + index / 8` のビット `index & 7` を立てます。組 `(0, 0)` はカテゴリ 0 のビット 0 を立てます。インデックスが `0xFFFFFFFF` のスロットは飛ばします。

状態バイトを 0 と 1 にして unicorn で動かすと、検証器、パーサ、受け取りの処理は、アプリが提示するすべての衣装について、レコードの最初の 6 組と最後の 6 組を、衣装の棚のビットとしてちょうど設定しました (`tests/test_swsh_gift.py`)。組は projectpokemon の EventsGallery にある公式の衣装カード 14 枚から得ています。

## メニューが拒否するもの

選んだカードを受け取る前に、`0x01014a60` は種類 `card[+0x7c]` (`0x01014bcc`) と、`w25 = 0x00ff1750(card) - 1` (`0x01014bd4`、`0x01014be4`)、レコードのフラグ `[card+0xe8]` の bit 2 (`0x01014be8 ubfx w24,w8,#2,#1`) を読みます。種類 1 のときは、空きの検査 `0x013adee0` (`0x01014d68`) も行います。順番は次のとおりです。

    0x00ff1750 returned 1, 2 or 3    message 7, 0x10 or 0x11     0x01014d9c cmp w25,#3; table 0x02065360 = 7, 16, 17
    kind 1 and no room               message 8                   0x01014c14 mov w21,#8
    flag bit 2 set                   message 0xF, then state 3   0x01014d38 mov w1,#0xf; continuation 0x010156f0
    otherwise                        state 3, the redemption     0x01014e70

`0x02064f80` は `mystery.tbl` のラベルのハッシュを、メッセージの添字ごとに 1 つの u64 で持ちます。`0x01000718` の初期化処理がエントリ k を `owner+0x5f8+8k` に解決し、`0x01002da0` が読み戻します。以下は 1.3.2 の英語版 `mystery.dat` の内容です (メッセージ本文は、ゲームのデータとして原文のまま載せています)。

| メッセージ | ラベル | 本文 |
|---|---|---|
| 7 | `msg_o_mystery_win_13` | You can't get that gift, since you've already received the same gift before. |
| 8 | `msg_o_mystery_win_14` | There's no room for another Pokémon. Make room in your party or Pokémon Boxes, and then try again. |
| 0xF | `msg_o_mystery_win_34` | You can receive this gift just once a day. Once you've received it, you can't claim another one until the next day. |
| 0x10 | `msg_o_mystery_win_35` | You can only receive this gift once per day. You've already claimed the one for today, so check in tomorrow for your next chance. |
| 0x11 | `msg_o_mystery_win_36` | You can only receive 10 gifts per day. You've already claimed 10 gifts today, so check in tomorrow to be able to claim more. |

拒否の続きを行う `0x01015740` は、メニューの最初の状態である `+0x80` に 0 を書き込みます。拒否されたカードは配置も保持もされず、原因が解消されれば再び受け取れます。

`0x013adee0` は、ボックスのストアに空きスロットがなく (`0x013adfb4 cset w20,eq`)、パーティも満杯だと報告する (パーティの vtable `+0x60`、スロット 12、`0x013adfc4`。`0x013adfd0 and`) とき、1 (空きがない) を返します。

`0x01014bd4` からだけ呼ばれる `0x00ff1750` が受け取りの検査です。`[card+0x60]` か `[card+0x68]` がゼロなら、すぐに 1 を返します (`0x00ff1750..0x00ff1770`)。ルート 0 から 2 では、`0x00ff17b4` を経由して `0x00ff1a30` に続きます。

    data = album+0x60 (0x014480e0)
    record flag bit 0, and the card id's bit set in the bitmap at data+0x1450 (album +0x14b0)   -> 1
    record flag bit 2 clear (0x00ff1ab0)                                                       -> 0
    the record's day invalid (0x00ff1b84)                                                      -> 3
    ten entries of 0x10 bytes from data+0x1560 (album +0x15c0), 0x00ff1b88..0x00ff1c70:
        entry id == card id and card day <= entry day (0x016cc210, cset ls)                   -> 2
        card day > entry day (0x016cc1f0, cset hi): a free entry
    a free entry                                                                               -> 0
    none                                                                                       -> 3

ビットマップの読み取りは、バイト `id >> 3` を (`0x00ff1a8c ubfx x9, x23, #3, #0xd`)、上限なしで読みます。ビットマップは 0x100 バイト (ID 0 から 2047) なので、フラグ bit 0 があり ID が 2048 以上のレコードは、その先を読みます。ID 13000 以上では、ブロックの 0x17C8 バイトも越えます。フラグ bit 0 が下りているレコードは、これを一切読みません。ビットは受け取ったときに立ちます。書き込む箇所は特定できていません。市販のソードでは、EventsGallery のモンスターボール x100 のカード (ID 0x6A、フラグ 1) を、ローカル無線で 2 回目に送ったところ、メッセージ 7 で拒否され、一覧から消えました。フラグ 0 で ID 0x270F のレコードは 10 回受け取れました。

エントリを書き込むのは `0x01449560` だけで、その唯一の呼び出し元 `0x00ff1558` は、`[card+0xe8]` に対する `0x00ff154c tbz w8,#2` の後ろにあります。エントリには、受け取った時刻ではなく、レコード自身の日付を格納します (`0x01449570`、`0x01449648`)。フラグ bit 2 を持つカードは、カードの日付ごとに 1 回、1 日に最大 10 枚まで受け取れます。日付を変えずに再送すると、エントリが残っている間はメッセージ 0x10 で拒否されます。

保持の経路 `0x00ff13f0` の呼び出し元は 1 か所だけで、ポケモンを配置する前に、受け取りの処理 `0x01014eb0` の中の `0x01014f74` から呼ばれます (`0x01014fb0 bl 0x010159d0`)。その本体 `0x00ff14c0` (呼び出し元は `0x00ff1404` だけ) は、`0x01449470`、`0x014494a0`、`0x01449560`、`0x01444f80`、`0x018fdc60`、`0x01444d60`、`0x01445000`、`0x01444de0` を呼びますが、いずれもポケモンは読みません。そのあと `0x00ff13f0` は、現在時刻 (`0x01449ca0` -> `0x01900050`) をルート 1 から 4 では `card+0x70` に書き、ルート 0 では `card+0xd8` の値をそこにコピーします。そしてカードを格納します (`0x014480f0`)。保持の経路では、適法性の検査は行いません。

ビルダーと受け取りの検査は、種族に対して技、教えわざ、性格、ボール、持ち物、フォルムを検査しません。ビルダー `0x010b6110` には出口が 1 つだけあり、拒否はありません。4 つの技と 4 つの教えわざを、受け取った値のまま格納します (`0x77bfb0`、`0x77b9a0`。格納は `0x770c7c`)。また、技の ID が 826 を超えると、変わるのは PP の参照だけです (`0x00781490`)。受け取りの処理 `0x010159d0` が検査するのは、種類のバイト、ビルドが null でないこと、パーティかボックスに空きがあることだけです (`0x7840f0` は、種族 0 かパーティ満杯を拒否します。`0x1406b00` は空きスロットを必要とします)。1.3.2 の個体データを使って unicorn で動かすと、ビルダーはピカチュウの不正な技 14、337、57、900、教えわざ 1、2、3、9999、性格 200、ボール 200、持ち物 9999 を、そのまま保持しました。

種族の検査は 1 つだけで、PokemonParam のコンストラクタ `0x777f40` にあります (`0x778118..0x778148`)。個体データのバイト 0x21 のビット 6 が下りている種族 (`0x764990`、`0x77f530`) は、レコードの `+0x04` ワードのビット 2 が立ちます (`0x76eb40`)。このビットが立つと、すべてのアクセサは、種族が 0x383 の代替の構造体を読み書きします (`0x776c50`。`0x776bc0` が埋めます)。このビットはゲームのバッドエッグのフラグです。`0x77d610(pp, mode)` は `0x767f40` を経由してこれを読みます (mode 0 はタマゴで、バッドエッグでないもの、mode 1 はバッドエッグ、mode 2 はどちらでも)。`0x77f600` は、0x382 を超える種族に対して、1.3.2 の英語版 `monsname.dat` の「Egg」というテキスト 0 を割り当てます。メニューの経路で、こうしたカードを拒否するものはありません。検証器 `0x010b5de0` が種族を読むのは、チェックサムとヘッダのコピー (`0x010b59b8`) だけです。`0x01014a60` の分岐はどれも種族を読みません。パーティへの追加 `0x7840f0` は種族 0x383 を受け入れます。図鑑の登録は、タマゴのバイトで戻ります (`0x01434b24`)。そしてコピー `0x766390` は、フラグと、レコードの種族を含む生の 0x148 バイトを保持します。unicorn の下では、種族 19 と 493 にはフラグが立ち、種族 25 と 1000 には立ちませんでした。検証器はコラッタのレコードを受け入れます。そのレコードを、エミュレートしたフランス語版 Shield 1.3.2 に渡したところ (種族 19、図鑑に不在)、「Rattata」として一覧に載り、見せる演出まで進み、「Vous avez reçu un Rattata !」と表示され、アルバムには「Rattata」として登録されました。パーティには、名前が「Egg」で、タマゴのモデルと、言語タグ ANG を持ち、要約のすべての欄が空のエントリが入りました。ゲームは受け取った時点で保存しました。パーティの枠は、種族 19 と `+0x04` のビット 2 を保ったままでした。種族 898 を超える種族は、個体データの 0 を読みます。その個体データは存在するとマークされています。フォルムが種族のフォルム数以上のときは、基本の種族を読むため、どちらにもフラグは立ちません。ソード・シールドにない種族は決して送らないでください。アプリの PKHeX の検査が、そうした種族を拒否します。

ビルダーが補正する唯一のフィールドは性別です (`0x777490`。個体データのフィールド 0x14 を `0x7774a4` で読みます)。比率 0、254、255 は、それぞれオス、メス、性別不明に固定されます (表 `0x1c4d2d0`)。ほかの比率では、要求された 2 は 0 になります (`0x7774d8`)。ビルダーは、レコードの性別 3 を、乱数の 0xFF に変えます (`0x010b62ac`)。

## カードの日付

レコードの先頭 8 バイトは、アルバムに表示される日付です。絶対 UTC 時刻を表す、リトルエンディアンの u64 のビットフィールドです。公開された資料はその名前を挙げていません。PKHeX の `WC8.cs` は、`+0x08` のカード ID から始めています。

| bits | 内容 |
|---|---|
| 0-5 | 秒 |
| 6-11 | 分 |
| 12-16 | 時 |
| 17-21 | 日 |
| 22-25 | 月。1 から 12 |
| 26-39 | 年。絶対値 |

`0x016cc5e0` は、days-from-civil によって値を posix 時刻に変換します (定数 `146097`、`1461`、100 での割り算がその中にあります)。値が `main+0x2616900` の背後にある番兵と等しいときは 0 を返します。アルバムの描画 `0x00ffbaa0` はこれを `nn::time::ToCalendarTime` (`0x00ffbaf0`) に渡すため、本体のタイムゾーンが適用されます。失敗時は `ToCalendarTimeInUtc` を使います。年は 2 桁で表示されます。

| レコードのバイト | フランス語版の本体での表示 |
|---|---|
| ゼロ | 01/01/2070 01:00 |
| 10 月 18 日 16:26 UTC | 18/10/2018 18:26 |
| 年 8218 | 2018 |
| `01 02 03 04 05 06 07 08` (年 321 の月 0) | 01/12/2020 15:53 |

日付を保持するのは、ローカル無線で受け取ったカードだけです。ほかのすべての経路では、8 バイトを `nn::time::StandardNetworkSystemClock::GetCurrentTime` (`0x00ff3f8c` -> `0x01449ca0`。PLT は `0x01900050`、GOT は `0x0260fbb8`) の値で上書きします。この値は `0x016cbfd0` と `0x016cc1d0` でパックされます。

配布元は、カードを送る直前に、空の日付をコンピュータの現在の UTC 時刻で埋め、その後チェックサムを封印し直します。配布元の日付がゼロでなければ、そのまま残ります。公式イベントのファイルは、受け取り時刻をオンライン経路が与えるため、8 バイトのゼロを持つことが多いです。このフォールバックによって、そのファイルはローカル無線でも日付を持つようになります。書き出したファイルは元の日付を保持します。本体のアルバムに保存済みのカードは変わりません。ポケモン自身の出会った日付は、アルバムの日付とは別物です。

## カードをアルバムに保持する場所

アルバムはセーブブロック `0x112D5141` (PKHeX の `KMysteryGift`。0x17C8 バイト) で、`0x01447eb0` が `+0x60` のアルバムオブジェクトに読み込み、`0x01449d90` が書き戻します。保持するのは再エンコードしたヘッダだけで、720 バイトの配線上のレコードや、その文字列は保持しません。`tools/switch/swsh_save.py` は `main` をブロックに読み分けます (PKHeX の SwishCrypto。ファイル全体に対する静的な xorpad、ブロックごとにキーでシードした XorShift32 のストリーム、2 つの定数に挟まれた暗号化された本体に対する SHA-256)。`--key 112d5141 --out FILE` はこのブロックを書き出します。`--patch KEY OFF HEX --write OUT` はブロックのバイトを書き換え、ファイルを封印し直します。

    0x0000  50 slots of 0x68 bytes, newest in slot 0; an insert moves every slot down one
            (0x01449880 indexes them, cmp w1, #0x31; a slot is in use when its +0x0C is non-zero)
    0x1450  0x378 bytes, zero in every save read; the last-receipt table is 0x1560..0x15FF
            (album +0x15c0) and the once-per-card table 0x1600..0x16C8 (album +0x1660)

スロットは、インポーターがレコードから埋める `0x68` バイトのヘッダです。

    +0x00  8    the record's date bitfield (zero draws 1 January 2070)
    +0x08  u16  card id
    +0x0A  u16  the record's byte at +0x15 (0 on Pokemon cards, 1 on kind-3, 3 on an item card)
    +0x0C  u8   kind: 1 Pokemon, 2 item, 3 the empty kind
    +0x0D  u8   kind 2: how many of the six item quantities are non-zero; 0 otherwise
    +0x0E  u8   1 when the card came by any route but local wireless
    +0x0F  u8   the record's byte at +0x1C (1 on kind-3 cards)
    +0x12  u16  level (kind 1)
    +0x30  u32  species (kind 1); kind 2: the item pairs (u16 id, u16 quantity) as at record +0x20
    +0x38  4 x u32  moves (kind 1)
    +0x48  26   nickname, UTF-16 (kind 1)
    +0x62  u8   3 on every Pokemon card

スロットの `+0x0C..+0x62` をゼロにすると、そのカードはアルバムから消えます。そのカードが配ったアイテムは `MyItem` (`0x1177C2C4`) に残ります。

## ストアを空にするフレームごとの更新

`0x010f65a0` は gfl net マネージャのフレームごとの更新で、`0x0261cba8` からマネージャを渡されて呼ばれます。安定したクロックの値を取り、`0x006c5300` の入れ替えを経由して `manager+0x60` の受信側を空にし、エントリをたどります。そして、空でないストアを見つけるたびに、その値を `manager+0x80` に書き込みます。インポーター `0x00ff2170` の周りの `+0x80` へのアクセスは別のものです。`nn::os::GetTlsValue` が返すスレッドローカルのガードのスタックで、`0x006c54a4` のストアへの追加の周りで同じく push と pop を行います。

一部のセッションでは、ストアが決して空になりません。受け入れたボディが溜まり続け (最初のボディが 27 分後もまだ残っていました)、`manager+0x80` は変わらず、`job+0x160` は null のままです。ほかのセッションは正常に空になります。原因は未解決です。注意点として、ビーコンの結果を読む前に、`manager+0x80` が進んでいることを確認してください。

更新を動かしているものは未解決です。その唯一の呼び出し元は `0x01109240` で、これは `0x00f1df30` の中にあるサブシステムごとの更新の並びです。`0x00f1df30` は `bl` による呼び出し元も vtable のスロットもなく、登録されたコールバックから到達します。
