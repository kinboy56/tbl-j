# カートリッジ、鍵、セッション

アドレスは、`tools/switch/nso_read.py` が展開して配置した、Let's Go Pikachu 1.0.2 の展開済み `main` へのオフセットです。text は `0..0xd32ba8`、rodata は `0xd33000` から、data は `0x1527000` からです。

## タイトルの構成要素

アップデートの NSP には、Program NCA `2b7730a9e56498bbafac2002d4908c6b`（タイトル `010003f003a34000`、権利 ID `010003f003a348000000000000000007`、鍵世代 6）が入っています。その exefs には、`main`（圧縮時 13.0 MB）、`rtld`、`sdk`、`subsdk0`、`subsdk1` があります。`nn::pia` と `gflnet3` の参照はすべて `main` にあります。

    ./.venv/bin/python tools/switch/xci_read.py "<the .nsp>" --keys prod.keys \
        --nca 2b7730a9e56498bbafac2002d4908c6b --exefs 0 --extract main
    ./.venv/bin/python tools/switch/nso_read.py main main.bin
    ./.venv/bin/python tools/switch/rtti_names.py main.bin 0xd32ba8

Pia は静的にリンクされています。`nn::pia` のクラスが 269 個、名前付きの仮想メソッドが 2112 個あります。`nn::pia::local` は `Ldn*` と `Local*` のファミリー（`LdnCreateNetworkJob`、`LdnCreateSessionSetting`、`LdnJoinSessionSetting`、`LocalProtocol`）を持ちます。`nn::ldn` は nnSdk から取り込まれ（`CreateNetwork`、`Connect`、`Scan`、`SetAdvertiseData`、`GetSecurityParameter`、`*Private` の各種）、GOT のスロットは `0x15fa1e0..0x15fa2a8` にあります。Pia の上では、`gflnet3` がプロトコルバッファを同梱しています（`lib/gflnet3/external/include/google/protobuf/`）。

## LDN のパスフレーズ

    W3GoSMEn7RIIUQ89rzqBHGhGferRNb7K18ZBq2aNuj8Us9RO9Q9JYyGOZlLy8MYL

64 バイトで `0xf73a50` にあり、そのまま使われます。ソードとシールドのものと同じです。2 つの呼び出し箇所が、リテラルの長さ `0x40` とともに渡します。

    0x004db6b4  adrp x1, #0xf73000 ; add x1, x1, #0xa50
    0x004db6c4  mov  w2, #0x40
    0x004db6c8  bl   #0x5c0fb0              LdnCreateSessionSetting passphrase setter

    0x004dbba4  adrp x1, #0xf73000 ; add x1, x1, #0xa50
    0x004dbbb0  mov  w2, #0x40
    0x004dbbbc  bl   #0x5c1280              LdnJoinSessionSetting passphrase setter

`LdnCreateNetworkJob`（コンストラクタ `0x5ce640`。ソードのオフセット）は、パスフレーズを +0xC4 に、その長さを +0x104 に保持し、それらから `nn::ldn::SecurityConfig` を組み立ててから、`nn::ldn::CreateNetwork`（`0x5ce988`、PLT スタブ `0xd31c78`）を呼びます。

## Pia のゲームキー

    p1frXqxmeCZWFv0X

`0xefd659` にある 16 バイトの ASCII 文字列で、wiki がソード・シールド、Pokemon LEGENDS アルセウス、スカーレット・バイオレットについて挙げているリテラルのキーです。1 つの呼び出し箇所が、モードのフィールドを条件にして、これを暗号設定に格納します。

    0x0011a364  ldr  w9, [x19, #0x98]
    0x0011a368  orr  w9, w9, #2 ; cmp w9, #2 ; b.ne   (mode 0 or 2 takes the key)
    0x0011a374  adrp x9, #0xefd000 ; add x9, x9, #0x659
    0x0011a380  ldp  x10, x9, [x9]
    0x0011a384  stp  x10, x9, [x8]          x8 = setting + 0x24c

## Pia ヘッダ

バージョン 3（wiki の Pia 5.11 から 5.17）。初期化関数 `0xd122d4` は、マジックとバージョンを 1 回の 64 ビットストアで書き込みます（`0x00000003_32AB9864`）。検証関数 `0xd12400` は、マジックと `(byte & 0x7f) == 3` を検査します。

    0x00  4  magic 0x32AB9864, big-endian
    0x04  1  0x80 (encrypted) | version (0x7F) = 3
    0x05  1  connection id
    0x06  2  packet id
    0x08  8  AES-GCM nonce
    0x10  16 AES-GCM tag, not truncated
    0x20     ciphertext

wiki の 5.11 から 5.21 のレイアウトです。バージョンのバイトを除き、ソードのバージョン 4 と同じです。`pokeldn/ldn/pia4.py`。

## メッセージのフレーミング

固定 22 バイトのメッセージヘッダです（Pia 5.11 から 5.12。5.18 以降は存在フラグ付き）。`ProtocolMessageAccessor::Header` のデシリアライザ `0x5ae870` は、0x16 バイト未満を拒否します。ライタ `0x5aeb00` は、バイト 1 にリテラルの 1 を格納します。

    0x00  1  message flags: 1 = destination is a bitmap, 2 = relay needed, 4 = relayed, 8 = unbundled
    0x01  1  version, always 1
    0x02  2  payload size, big-endian
    0x04  1  protocol type
    0x05  1  protocol port
    0x06  8  destination, big-endian: a constant id, or a station bitmap when flag 1 is set
    0x0E  8  source constant id, big-endian
    0x16     payload, then padding to a multiple of 4

`pokeldn/ldn/pia3.py` は、pia4 のヘッダの上にこれを実装します。

## セッションキー

`LocalProtocol` の導出 `0x5cd560` は、BDSP とソードのものと同じです。1 つの 32 ビットの値から SEAD の xorshift128 を初期化し（`0x57cfc0`、漸化式は `0x6C078965` 付近）、4 回の抽出で 16 バイトにします。`LocalProtocol+0x49c` のゲームキーで AES-128-ECB をかけます（有効フラグは +0x498）。`pokeldn.ldn.pia5.ldn_session_key`。

広告のアプリケーションデータ（Pia 5.9 から 5.18）は、24 バイトのヘッダで始まります。次のとおりです。

    0x00  4  network id, random per session
    0x04  4  CRC32 of the user password
    0x08  1  system communication version, 4 for 5.11-5.17
    0x09  1  header size, 0x18
    0x0A  2  padding
    0x0C  4  session param
    0x10  8  zero
    0x18     the game's application data

シードは、+0x0C にあるセッションパラメータです。Let's Go Pikachu のホストからの 392 個のデータグラムがすべて認証されました。認証は、`ldn_session_key(game key, session param)` のもとで、pia4 の IV（`crc32(network id little-endian || host MAC)` の 3 バイト、送信元 ID のバイト 0、8 バイトのヘッダのノンス）を使って行われました。

## リンクコード

リンクコードは NetworkInfo のシーン ID です。アプリケーションデータの +4 にあるパスワードの CRC32 は 0 のままで、SSID は `01000000000000000000000000000000` のままです。シーン ID は `1000a + 100b + 10c + 1` で、a、b、c には、3 回の選択それぞれの、選択画面での index を入れます（ピカチュウ 0、イーブイ 1、フシギダネ 2、ヒトカゲ 3、ゼニガメ 4、ポッポ 5、キャタピー 6、コラッタ 7、プリン 8、ディグダ 9）。

実行時に組み立てられます。`0x891580` が選択を `100a + 10b + c` にまとめ、`0x978080` が `10 * number + mode` を計算します。トレードでは mode 1 です（mode 2 と 3 は `0x9765f4` の switch から来ますが、その機能は未確認です）。その値は、`0x349010` と `0x4da710` を通って、セッションのコンストラクタ `0x4db1e0` に渡されます（`+0x302` の `u16`）。`0x4db6ac` が `LdnCreateSessionSetting+0x60` に入れ、Pia は `nn::ldn::CreateNetwork`（`0x5ce988`）の前に、それを `NetworkConfig.intentId.sceneId` にコピーします。

同じコンストラクタは、検索側の本体がホストするチャンネルも決めます。`{1, 6, 11}[scene % 3]` で、テーブル `0xf73a44` を `0x4db248..0x4db254` で引きます。`pokeldn.lgpe.search_channel(code)`。

| 本体が検索に使ったコード | 広告されるシーン ID | チャンネル |
|---|---|---|
| ピカチュウ、ピカチュウ、ピカチュウ | 1 | 6 |
| フシギダネ、ヒトカゲ、ゼニガメ | 2341 | 6 |
| フシギダネ、ヒトカゲ、フシギダネ | 2321 | 11 |
| イーブイ、ピカチュウ、ディグダ | 1091 | 11 |
| ピカチュウ、ピカチュウ、フシギダネ | 21 | 1 |

検索中の本体は、本体自身のチャンネル上で、本体のシーン ID を広告しているネットワークにだけ参加します。`bin/lgpe_host.py --code NAMES` はコードのチャンネルでホストします（`--channel auto` は、代わりに本体のネットワークを探します）。Let's Go Pikachu と Let's Go Eevee がそこに参加します。`bin/lgpe_join.py` はコードを送らず、本体ホストがそれとトレードします。

## Local Protocol の計測

セッションの状態は、BDSP とソードと同じく、Pia プロトコル 0x24、ポート 0 で送られます。wiki の 5.7 から 5.45 の更新セッションのメッセージです（`pokeldn.ldn.local_protocol.parse_update_session`）。12 バイトのローカルヘッダ（バージョン 1、type 0x11）、シーケンス ID、ローカルのネットワーク ID、ホストの変数 ID、サービス変数 ID と定数 ID、参加を許可するバイト、そして 8 つのノード（IPv4 アドレス、ポート、移行の順位）からなります。ホスト `169.254.105.1` は順位 0、参加者 `169.254.105.2` は順位 1、残りは 255 です。

ボディは、ホストの定数 ID をリトルエンディアンで載せます（`000048f120229beb`。MAC `48:f1:eb:20:9b:22` に対する `station_protocol.ldn_constant_id`）。Pia のメッセージヘッダは、送信元として、これをビッグエンディアンで載せます（`eb9b2220f1480000`）。ソードと同様です。

## メッシュ参加のためのステーションプロトコル

プロトコル 0x14 で接続要求を行い、そのあと 0x18 でメッシュに参加します。接続要求のハンドラ `0x5b8800` は、wiki の 5.10 から 5.18 のレイアウト、ステーションプロトコルのバージョン 9 を読みます。

    [0]     message type            1
    [1]     connection id
    [2]     version number          must be 9 (`cmp w8, #9` at 0x5b8848; 5.27-5.45 checks a platform)
    [3]     is inverse connection request; rejected above 1
    [4]     target constant id      big-endian u64, compared against the console's own at 0x5b6830
    [0xC]   target variable id      big-endian u32, checked only when [3] is 1 (0x5b6840)
    [0x10]  inverse connection id   compared against the station's own record at +0xA0
    [0x11]  station location        the 5.11-5.45 layout, unchanged from Sword
    [...]   ack id                  u32, the message size minus four

ソードのバージョン 4 の要求（[2] のプラットフォームのバイト、[3] のシフトフラグ）と、5.29 から 5.45 のレイアウト（[1] のプロトコルの一覧）は、ここではすべてのフィールドを間違った位置に置きます。ターゲットの定数 ID は本体自身のもので、その MAC から得られます。参加者の位置情報は、その定数 ID、変数 ID、サービス変数 ID を運びます。

市販の Let's Go Pikachu は、5.27 で削除された逆方向の接続要求を含む、バージョン 9 の完全な手順を実行します。

    ->  connection request (type 1, is_inverse 0, target the host constant id, own location)
    <-  type-5 ack; inverse connection request (type 1, is_inverse 1) to the joiner's constant and
        variable ids, with the host's location and a trailing ack id
    ->  type-5 ack; connection response (type 2, result 0, host constant id at [5], variable id at
        [0xD], gate byte 1 at [0x37], padded to 0x38)
    <-  connection response (type 2, result 0, 840 bytes, platform 4, the joiner's ids, a network
        id, one player info), repeated until acknowledged
    ->  type-5 ack

接続応答のパーサ `0x5b9270` は、`[1]` の結果、`[5]` のビッグエンディアンの u64、`[0xD]` のビッグエンディアンの u32 を、自分の ID と照合して読みます。`[0x37]` のゲートバイトは、5 以上のとき、結果 0 の経路が捨てます。

### ステーションが送る接続応答

0x348 バイトです（パーサは 0x3C バイトを受け付けます）。

    0x00  1  message type 2
    0x01  1  result
    0x02  1  version 9
    0x03  1  platform 4
    0x05  8  the receiver's constant id, big-endian
    0x0D  4  the receiver's variable id, big-endian
    0x31  4  the network id, big-endian: the advertise data's first u32, read little-endian
    0x35  2  01 01
    0x37  0xC3  a PlayerInfo: the station name "username", then the Switch profile's nickname,
             then the language. Its first byte is the gate the parser drops when 5 or more
    0x344 4  the ack id

PlayerInfo は、`station_protocol.player_info` が組み立てる 195 バイトの構造体です。市販の本体は、これをプロフィール名で埋めます。`station9.build_connection_response(..., network_id=N, player_name=B)`。`bin/lgpe_join.py --player-name NAME`（`--short-response` は 0x3C バイトを送ります）。

接続要求における参加者のステーションの位置は 36 バイトです。公開アドレスは空（ポートは 0）で、NAT のフラグと位置はゼロです。`station_location(..., public=False, nat_flags=0, nat_location=0)`。

## メッシュへの参加

0x18 のメッシュ参加要求（`mesh_protocol.build_join_request`。type 1、ローカルのステーション index 253、末尾の確認応答 ID）には、参加応答で答えられます。応答は type 2 で、148 バイト、2 つのステーション、ホストの index 0、参加側の index 1、断片 1 つ、両方の位置を含む 2 つのステーション情報、最大アクティブ数 2、最大総数 8 です。その後ホストは、更新メッシュ（type 0x20、524 バイト、更新カウンタ 1）をブロードキャストします。参加応答には、0x14 の type 5 の確認応答が返されます（`mesh_protocol.ack_for`）。参加者のステーション index は 1 です。

その後ホストは、Local Protocol の更新セッション（0x24。0x21 で確認応答）、RTT（0x58）、Sync Clock（0x1C）、Clone（0x73）を連続して送ります。参加者はそれぞれに応答し、着席した時点から自分の RTT と Sync Clock の要求を送ります。

## RTT プロトコル（0x58）、バージョン 3

16 バイトです。[0] にビッグエンディアンの u32 の kind（ソードでは 1 バイト）、[8] に送信側の 19.2 MHz のシステムティックを u64 で置きます。応答は kind 1 でティックをコピーします。各ステーションは、およそ毎秒 1 回要求します。

    00000000 00000000 0000000049845557     request
    00000001 00000000 0000000049845557     the answer to it

`rtt_protocol.build_v3` と `response_for_v3`。`bin/lgpe_join.py --connect` は両方向で実行します（`--no-rtt` で無効にできます）。

## Sync Clock プロトコル（0x1C）

ホストが制御する単調増加のメッシュのクロックです（wiki の Sync-Clock-Protocol）。ステーションは 2 秒ごとに要求し、ホストが返す値に、往復時間の半分を加えます。

    request, 16 bytes   [0] u64 the sender's system tick (19.2 MHz), [8] u64 zero
    reply,   16 bytes   [0] u64 the tick copied back, [8] u64 the mesh clock in milliseconds

参加者は、メッシュの参加応答の直後に最初の要求を送ります。クローンのプロトコルのクロックは、このクロックです。参加者自身の稼働時間で計時されたクローンのメッセージを受けたホストは、そのクローンを解放して離脱します。`pokeldn.ldn.sync_clock`。`bin/lgpe_join.py --connect` がこれを実行します（`--no-sync-clock` で止められます）。

キープアライブはプロトコル 0x08 で、ボディはなく、同じ種類で応答します。

## 信頼性プロトコル（0x7C）、ゲームのデータが流れる場所

Pia 5.11 のヘッダは 24 バイトです（5.29 から 5.43 では 9 または 13 バイト）。32 ビットのシーケンス ID は、両方のステーションで 0xFFFFF82F から始まります。

    0x00  1  flags
    0x01  1  stream id, 3 for the game's stream and 0 on an acknowledgement
    0x02  2  payload size, big-endian
    0x04  4  zero
    0x08  4  sequence id, big-endian
    0x0C  4  the next sequence id expected from the peer, big-endian
    0x10  8  zero
    0x18     the payload

確認応答はヘッダだけで、ストリームとサイズはゼロです。`pokeldn.ldn.reliable3`。ペイロードは、ゲームのフレーミングです（下の「信頼性プロトコル上のゲームのメッセージ」を参照）。

## Clone プロトコル（0x73）

`nn::pia::clone::CloneProtocol`（GetProtocolId `0x158aab8`。SDK の文字列 `PiaCommon-5_11_4`）は、パートナー間の同期を運びます。型のバイトは `0xAB` で、上位 4 ビットが構造、下位 4 ビットがバリアントです。すべてのメッセージは、バージョン 3、型、そして送信側のフレームカウンタをビッグエンディアンの u16 で始まります（送信側の Pia セッション開始から毎秒およそ 60）。計測は、Ryujinx の ldn_mitm を通じた 2 台の Let's Go Pikachu 1.0.2 のエンドポイント間で行いました。両側は同じステートマシンを実行します。

### クロック同期、最初の 2 秒

両側は、クロックの要求（type 0x11、18 バイト、シリアライザ `0x51f9b0`）を毎秒およそ 5 回送ります。相手の要求には、応答（type 0x21、22 バイト、`0x51fab0`）で答えます。

    clock request                              clock reply
    [0]   1  version 3                         [0]   1  version 3
    [1]   1  type 0x11                         [1]   1  type 0x21
    [2]   2  sender frame counter              [2]   2  sender frame counter
    [4]   4  sender message count              [4]   4  sender message count
    [8]   2  destination station bitmap       [8]   2  destination station bitmap
    [0xA] 8  sender system tick                [0xA] 4  sender clone clock, ms
                                               [0xE] 8  the request's system tick, echoed

- メッセージカウントは、送信側ごとに 1 つのカウンタです。クロックの要求、応答、参加を通じて、1 から数えます。
- ビットマップは宛先で、`1 << station index` です。ホスト（0）は 0x0002、参加者（1）は 0x0001 を送ります。応答は要求元に返します。
- ティックは送信側の `os::GetSystemTick`（19.2 MHz）です。応答は要求のティックをそのままエコーし、それ以外は何も返しません。
- クローンのクロックは、送信側のクローンのプロトコルが始まってからのミリ秒です（要素 +0x14）。最初の要求の約 60 ms 前から数えます。クロックがゼロの応答を受けると、市販の本体は要求を出し続けます。

### 参加（Participate）

応答された要求が 10 回に達すると、参加者は participate（type 0x31、10 バイト、シリアライザ `0x51fbd0`）を送ります。内容は、ヘッダ、メッセージカウント、ビットマップ 0x0003 です。ホストは 0x33（ビットマップ 0x0002）で答え、そのあと自分の participate を送ります。参加者はそれに 0x33（0x0001）で確認応答します。最初の participate 以降、クロックの応答は type 0x22 になります。

### クローンの要素

クローンは、クローン type（1 から 4）、所有ステーション（なしのときは 0xFD）、32 ビットのクローン ID で識別されます。両方のステーションが、それぞれ自分のコピーを発行します。最初のトレードでは、トレード画面が進むにつれて、ホストが ID 1、2、3 を作ります。以降のトレードでは、さらに告知されます。クローン type 3 の ID 0 は、両側が参加すると存在します。

    every command message   [0] version 3, [1] type, [2] u16 the sender's frame counter,
                            [4] u8 clone type, [5] u8 owning station, [6] u16 0,
                            [8] u32 clone id
    types 0x81 to 0xc4      [0xC] u32 the sender's message count, [0x10] u16 destination bitmap,
                            then the structure's own fields
    types 0xd1 to 0xf4      [0xC] the data, with no message count and no bitmap

下位 4 ビットは、コマンドトークンに 1 を加えた値です。1 は告知（`SendClone::AnnounceCommandToken`、`0x522480`）、2 は要求（`ReceiveClone::RequestCommandToken`、`0x520df0`）、3 は終了（`SendClone::EndCommandToken`、`0x522490`）、4 はロック（`AtomicSharingClone::LockCommandToken`、`0x517820`）です。上位 4 ビットは構造体で、`0x51c110` がテーブル `0xf769c4` を通じてこれを振り分けます。

| 型 | 追加される内容 | メッセージ、長さ | 受信の分岐 |
|---|---|---|---|
| 0x8N | なし | 0x12 | `0x51c614` |
| 0x9N | [0x12] にある、ms 単位の u32 のクロック | ClockCloneCommandMessage、0x16 | `0x51c62c` |
| 0xaN | クロック、[0x16] の u8 カウント、u8 と u16 | ClockAndCount、0x1a | `0x51c64c` |
| 0xbN | クロック、[0x16] の u32 参加者ビットマップ | ClockAndParticipant、0x1a | `0x51c66c`（`0x51c680`） |
| 0xcN | クロック、カウント、[0x1A] のビットマップ | ClockAndCountAndParticipant、0x1e | `0x51c68c` |
| 0xeN | [0xD] の zlib ストリーム | クローンの状態、確認応答 | |
| 0xfN | [0xD] のバイト、[0xE] の zlib ストリーム | クローンの状態とそのデータ | |

zlib ストリームを展開すると、レコードになります。タグ 0x20、その長さ、u16 のクローン ID、そしてコピーが空の間は 1、満たされたあとは 3 です:

    0x20 0x06 u16 clone id  0x01  0x00
                                          a copy with nothing in it yet
    0x20 len  u16 clone id  0x03  u8 the station the data belongs to  u16 0
              u16 participant bitmap  u32 clock  then the clone's data
    0x20 0x0A u16 clone id  0x05  u8 the station being acknowledged   u32 clock

ステーションは、まず 6 バイトの形を、そのあとに満たされた形を発行します。6 バイトの形は、再試行されている発行です。落ち着いたセッションでは、レコードは組み立てられません。deflate は、1 回の圧縮、sync flush、最後の空のブロックからなり、レベルは 2 から 5 です。`clone.pack_record` は、取得したすべてのストリームを再現します。0xfN ヘッダの [0xC] のバイトは、そのレコードの参加者ビットマップを運びます。0xeN ヘッダのバイトは、確認応答するステーションを運びます。

| やり取り | メッセージ |
|---|---|
| 所有者の告知 | 0xa1 と、参加者ビットマップを載せた 0xb1。相手はデータの前に 0xa2 と 0xc1 で応答する |
| 引き継ぎ | 相手は 0xa1 に 0x91 で応答する |
| データ | 所有者の 0xf3。相手の 0xe3 は同じクロックを載せる |
| 解放 | 0x83。0x84 が確認応答する |
| クローンのセッションからの離脱 | 0x32。0x41（14 バイト。応答側のビットマップは [0xA] にある）。応答のない 0x32 は、ゲームがあきらめるまで繰り返される |

0xa2 は、メッシュのクロックとカウントを載せます。カウントは、クローン type 4 では 1、クローン type 2 では 0 です。

`ClockAndCountCloneCommandMessage`（vtable `0x158ac58`、シリアライザ `0x51f4c0`）は、ビッグエンディアンで、[0x12] に `+0x1c`（クロック）、[0x16] に `+0x20`（カウント）、[0x17] に `+0x21`、[0x18] に `+0x22`（u16）を書きます。カウントは、クローンの vfunc 16 が返す値です。SendClone では 0（`0x519290`）、ReceiveClone では `+0x112`（`0x520de0`）、AtomicSharingClone では `+0x188`（`0x517800`）です。バイト `0x17..0x19` はスタックの残りかすで、どの受信側も読みません。組み立て関数（`0x51b3b0`、`0x51cb64`、`0x51ccf0`、`0x51cd8c`）は、カウントより後ろには何も書きません。そして回収処理 `0x51b380` は、0xbN の経路が参加者のワードを残すバッファを再利用します（`0x51b7a0`）。そのため、`01 2808ab` になります。`0x51c110` は、その場で解析します。すべてのペイロードは、受信ループ `0x51ad90`、またはループバック（`0x51e330`、`0x51e4c4`）からここに届きます。

`0x51c110` は、共通ヘッダを読みます（`0x51c2c0`: `[8]`、`[4]`、`[5]`）。グループ 0x80..0xc0 のバイト 0x10-0x11 については（`0x51ce80`、テーブル `0xf76e08` -> `0x51ced0`）、上の表のフィールドだけを読み、それ以上は読みません。クローン type のテーブル `0xf769e4`（index は `[4] - 1`）は、0xa1 と 0xa2 を、バッファではなく、クローン、ステーション、クロックを受け取るハンドラへ振り分けます。

| クローン type | 0xa1 | 0xa2 |
|---|---|---|
| 1 | `0x51c714` -> `0x51cb38`、`0x522350(clone, station, clock)`。未知のクローンには 0x91 が返される | 無視 |
| 2 | 無視（`0x51c3b8`） | `0x51cafc`。`[5]` はローカルのステーションでなければならない。`0x520ce0(clone, clock)` |
| 3 | `0x51c934` -> `0x51cc00`、`0x522a60` | `0x51c838`、`0x522b20(clone, station, clock)` |
| 4 | `0x51c8c0` -> `0x51cbc4`、`0x522a60` | `0x51c838` |

バッファを運ぶ後続の呼び出し（`0x51c268`、`0x51c2fc`、`0x51c32c`、`0x51c784`、`mov x3,x22; b 0x51d450`）は、ほかのメッセージ種別を扱います。

`0x522a60` は、クローン type 3 と 4 の 0xa1 のハンドラで、要素の状態 `[x0+0x38]` が 1 でないとき 1 を返します。送信側のビットが `[[x0+0x30]+0xc0]` に立っているとき 2 を返します。それ以外はステーションを記録し、0 を返します。呼び出し元は、0 に対して型 `0xfd04` の 0xa2 で応答します（クローン type 3 では `0xfd03`、`0x51cd00`）。1 に対しては 0x91 で応答し（`0x51cbe4`）、2 に対しては何も送りません。未知のクローンへの 0xa1 は、直接 0x91 を返します（`0x51c494`）。`0x51c110` は、宛先の検査 `0x51ce80`、送信側ごとのカウントのフィルタ（`0x51c1e0`。`proto+0x714+4*station` のカウントが、メッセージの `[0xC]` 以上であること）、長さと型の範囲の検査で、黙って捨てます。

マスク `+0xc0` は、ステーションのマスク `+0x38` と状態ワード `+0x40` と並んで、クローンのプロトコルのオブジェクトに属します。

| 事象 | `+0xc0` への影響 | アドレス |
|---|---|---|
| 状態が `0x22` になる（`[[proto+0x48]+0x24]` が 2 から 4 のとき） | `+0x38` に設定 | `0x51b060..0x51b06c` |
| 状態が `0x42` になる | `+0x38` に設定 | `0x51b140..0x51b150` |

| 状態 `0x31` か `0x22` で 10 バイトの 0x33 を受ける | 送信側のビットを消す | `0x51c354..0x51c3b4` |
| 状態 `0x42` で、`[0xa..0xd]` が `[proto+0x3c]` と等しい 14 バイトの 0x41 を受ける | 送信側のビットを消す | `0x51c380..0x51c3b4` |
| ステーションが離脱する | そのビットを消す | `0x51bce0..0x51bce8` |

状態 `0x22` では、プロトコルはマスクが空になるまで待ってから `0x31` へ進みます（`0x51b074..0x51b084`）。

### クローン 0 の組

クローン type 3 のクローン 0 の所有者は、0xa1 と 0xb1 で告知します。相手は 0xa2 と 0xc1 で応答し、そのあとで初めて所有者は発行します。市販の本体ホストは、応答が届かなかった場合（`bin/lgpe_join.py` の `--withhold-clone0-answer` を使うテスト専用の設定）、最初の 0xa1 の 114 ms 後に 0xb1 と 0xa1 を再送し、その 108 ms 後に 0xb1 だけを送って、再送への応答を受け取ります。組を一度だけ送って応答を失ったホストでは、本体は "vous allez bientôt être connecté"（間もなく接続されるという表示）の画面に留まり、クロックのやり取り以外は何も進みません。`bin/lgpe_host.py` は、本体の 0xa2、0xc1、または 0x91 が届くまで、110 ms ごとに組を、最大 20 回まで再送します。最初の組に応答していた市販の本体は（起動スクリプトの `--ignore-clone0-answer` で、最初の組への応答を無視できます。テスト専用）、再送に 0xa2 で応答します。

### 信頼性プロトコル上のゲームのメッセージ

`0x7c` のメッセージはすべて、16 バイトのヘッダとボディからなります:

```
+0x00  4  kind: the channel id, 1 to 4 in one trade
+0x04  4  body length: 0x168 for kind 1, 0xe8 for kinds 2 and 4, 4 for kind 3
+0x08  4  step, counting every message a station sends from 1
+0x0c  1  tag, 0 on every trade message
+0x0d  1  destination station index, 0xff for every station
+0x0e  2  zero
+0x10     the body
```

`0x116f30(mgr, kind, buf, len, tag, dest)` は、`mgr+0x288` にヘッダを組み立てます。ステップは `mgr+0x274` に 1 を加えた値です。トレードの送信側は `0x4d94e0` を通ります（タグ 0、宛先 0xff）。`0x34945c`（kind 1）、`0x34a24c`（差し出し）、`0x838300` と `0x83838c`（コミット）がこれを使います。`0x4d9520` は両方を呼び出し元から受け取ります。その呼び出し元は、`0x9dce94..0x9dede8` にあるバトルシーンの送信側で、そのうち 1 つはタグ 3 を使います。

受信処理 `0x1171d0` は、どのステーションからでも、ステップがそのステーションの次の値（`mgr+0x278[station] + 1`、`0x117334..0x117354`）である最初のキュー済みメッセージを取り出します。取り出したものと捨てたものは、すべて数えます。宛先が 0xff でもローカルのステーション index `mgr+0x1288`（セッション前は 0xfd）でもないメッセージ、または登録されたチャンネルのない kind のメッセージは捨てます（`0x11722c`。16 件のテーブル `mgr+0x110`、`0x117398..0x1173f8`）。登録済みの別の kind やタグのメッセージは、キューに残ります。そして、どのステーションからのものでも、その後ろのすべてのメッセージを止めます。トレードの受信側（`0x4d9570`）は、タグ 0 を要求します（`0x11746c..0x117478`）。

kind はチャンネル ID です。これは `0x116e80` が、セッションごとのカウンタ `mgr+0x270`（1 から始まり、セッション開始時にだけステップのカウンタと一緒に 0 になります、`0x116a10`）から払い出し、`0x4d9450` が `chan+0x60` に格納します。チャンネルが 16 個（`mgr+0x118 > 0xf`）登録されているときは、ID は 0 になります。`0x117920` は、有効な件数 `+0x54` が 0 のチャンネルを取り除きます。`0x4d9450` の呼び出し元は 5 つあります。トレードのセッションのオブジェクト（`0x3492f8`）、手持ち発行オブジェクト（`0x349d88`）、同期セーブの状態 2（`0x8382a8`）、`0x347e10` のクラス（`0x3481fc`）、バトルシーン（`0x9dce1c`）です。トレードでは、最初の 3 つで 1、2、3 を登録し、トレード後のセーブが作り直す手持ち発行オブジェクトで 4 を登録します。各登録は、クローンの一式も告知します（`0x4d94b8`。サンク `0x11b4c0` を経て `0x11aec0`）。そのため、クローン ID はチャンネル ID と異なります。

どちらの上限も、1 つの席でのトレード数を制限しません。カウンタは、検査なしで増やされる u32 です（`0x116ea4..0x116eac`）。kind は通信上も u32 なので、ID は 2^32 - 1 回の登録のあとで初めて折り返します。16 件の上限は、有効なエントリを数えます。各エントリは弱い参照（`[chan+0x58]`、`0x4d98a0` が作る）を持ちます。アクティブなセッションでは、マネージャーの更新 `0x1175d0`（`0x11761c`）から毎フレーム `0x117920` が実行され、チャンネルの強い参照数 `handle+0x54` が 0 のエントリを消します。コミットのチャンネルは同期セーブとともに消えます（`0x838c40`）。同期セーブは、ディスパッチャーの状態 3 が抜ける（`0x886670`）前に、セーブのプロセス（`0x835000`）とともに消えます。差し出しのチャンネルは、手持ち発行オブジェクトとともに消えます（`0x349dfc`）。コミットのあとに解放され（`0x886c70`）、トレード後のセーブが置き換えます（`0x3445e0`）。1 つの席は、有効なチャンネルを約 4 つ保持します。

kind 1、ボディ 0x168 は身元です。セーブの MyStatus ブロックを `obj+0x450` にコピーしたもの（`0x3493f4`）で、どちらのステーションも何かを受信する前に、状態 6 から送ります。そのトレーナーは PKHeX の `MyStatus7b` にあたり、名前は UTF-16LE です。

```
+0x00  4  trainer id, then secret id
+0x04  1  version: 42 Pikachu, 43 Eevee
+0x05  1  gender
+0x35  1  language
+0x38 26  trainer name, up to the Pokemon name; --trainer-name on both launchers
+0x52 16  Pokemon name
```

受け取る側のプレイヤー向けに作られたおくりものは、ここで本体のトレーナーを読み取ります（`pb7.first_trainer`、[受け取るプレイヤー向けに作られたもの](gift_simulated.md#made-for-the-receiving-player)）。

`pokeldn.lgpe.reference` には 1 つ含まれており、トレーナーが `POKELDN` のエミュレートしたセーブから記録されています。`bin/lgpe_join.py` は既定でそれを送ります。トレーナー ID の組は `--our-trainer` で置き換えられます。

kind 2、ボディ 0xe8 は差し出しです。ステーションが発行する状態ワードが 2 に達すると、すぐに送られます。プレイヤーが差し出すポケモンを変えるたびに、次のステップのもとでもう一度送られます（選択画面でボックスを見て回ります）。新しいステップには応答します。同じステップの繰り返しは再送であり、応答しません。

送信側は手持ち発行オブジェクトです（コンストラクタ `0x349bf0`、0x278 バイト、`mgr+0x68` にあります）。その更新 `0x34a210` は、`+0x270` が立っていて `+0x272` が消えているとき、`+0xa0` の構造体を送ります。そのあと `+0x270` を消します。トレード UI が選択の変更時に呼ぶ `0x34a3d0`（`0x8f0c04`、`0x8f0c38`、`0x8f8fb0`、`0x90b87c`、`0x90b8c0`）は、ポケモンを `+0xa0` に詰め（`0x7294e0`）、ステータスが許すときに `+0x270` を立てます（A 0 はローカルの状態が 1 でも 2 でもないとき、A 1 はローカルの状態が 3 か、4 より大きいとき、A 2 は決して、A 3 は相手の離脱のとき。`0x3490c0`）。`0x344620` は、コミットのあとに（`0x886c70`）、またリンクが終わるときに（`0x8869f0`）、このオブジェクトを破棄します。トレード後の通常のセーブは、新しいチャンネル ID のもとで作り直します（`0x8375a4`）。

kind 3、ボディ 4 はコミットです。同期セーブが送る u32 で（下の「コミットとトレードロック」を参照）、各ステーションが 1 を送り、そのうち 1 つは相手の 1 を受けたあとに 2 を送ります。2 を送るステーションは、相手の 1 を受け取ったとき（状態 5、`0x838310`）にそれを送ります。状態 6 で受け取った 2 はコミットします。それ以外のボディは無視します（`0x83839c`）。そのため、参加者が 2 に 2 で応答しても許容されます。コミットのあと、ステーションはボタンの案内なしでスピナーを表示します。やり取りが完了しないと、トレードロックは立ったままになります。

kind 4、ボディ 0xe8 は、通常のセーブが `SaveThread` の 3000 ms 後に作り直す手持ち発行オブジェクトのチャンネルに乗ります（`0x8377ec`、`0x8375a4`）。これはトレードのデモのあとです。次のトレードの選択を運びます。最初はステーションの最初のスロットです（ステップ 2 の差し出しとバイト単位で同一）。その後は選択ごとに 1 つずつです。kind 4 を送る前にトレードがセーブされます。kind 4 が次のトレードを開きます。

トレード r は、0 から数えて、kind 2 + 2r で差し出し、3 + 2r でコミットし、4 + 2r で終わります。4 + 2r はトレード r + 1 の差し出しのチャンネルです（`0x116e80` はセッションごとのカウンタから ID を払い出し、ディスパッチャーは各トレードで両方のチャンネルを登録し直します）。計測した連続する 2 回のトレードでは、トレード r の手持ちの組はクローン 2 + 3r と 3 + 3r で、そのコミットのクローンは 4 + 3r でした。トレードのセーブのあとに告知される組は、次のトレードに属します。ホストする場合、`bin/lgpe_host.py --next-offer` は、以降の各トレードで本体の選択に次のレコードで答えます。参加する場合、本体ホストの最初の kind 4 は、その最初のスロットです。`bin/lgpe_join.py` はそれに答え、以降の各選択には次の `--offer` で答えます。コミットには kind 5 で答え、kind 6 をそのトレードの終わりとして扱います。最後のレコードのあとは、何も答えません。

どちらの起動スクリプトも、2 のコミットが送受信されたときに、トレードの受け取ったレコードを書き込みます。それにより、本体上でそのトレードがコミットされるためです。表示されてから取り下げられた差し出しは、何も書き込みません。

本体ホストは、以降の各トレードを最初のトレードと同じように実行します。次の手持ちの組は、最初の kind 4 の前に告知されます。kind 4 は選択ごとのステップです。コミットのクローンは確認時に告知されます。コミットは kind 5 で送られます。次の組は kind 6 の前に告知されます。`bin/lgpe_host.py --lead` は、促されなくても差し出し、投票して、`bin/lgpe_join.py` に対して本体ホストの役割を演じます。`tests/test_esp32.py` は、2 つの間で 2 件ずつのレコードを両方向にトレードします。

両方のステーションが自分のステップを数えた、トレード 1 回分の完全な流れは次のとおりです。

```
step 1  kind 1   identity
step 2  kind 2   the offer, again under a fresh step per selection
step 5  kind 3   commit, body 1
step 6  kind 3   commit, body 2
step 7  kind 4   the first slot, again under a fresh step per selection
```

kind 2 と kind 4 のボディは、232 バイトのボックス構造体です。第 6 世代の暗号化のもとにある第 7 世代のレイアウトで、暗号化の定数は +0x00、ゼロの健全性ワードは +0x04、チェックサムは +0x06 にあります。+0x08 から始まる 56 バイトのブロック 4 つは、`((ec >> 13) & 0x1F) % 24` で並べ替えられ、定数で初期化された 16 ビットの LCRNG の列と XOR されます。`pokeldn.lgpe.pb7` は、取得した差し出しを 1 バイトずつ往復させられます。

状態ワードは `f3` の状態データのバイト 12 で、ステーションが持つクローンごとに 0、1、2 と進みます。2 を発行して kind 2 を送ったステーションは、相手の kind 2 を待ちます。

### ゲーム自身の最初のメッセージを止めるもの

リンクトレードのオブジェクトの、フレームごとのステートマシンは `0x349200` です（`+0x68` でジャンプテーブル `0xf4e994` を引きます）。状態 6 は、ネットワークからの入力なしに最初のゲームメッセージを送ります。2 つのステーションは、どちらも何かを受信する前に、18 ms 間隔で送ります。唯一のゲートは状態 4 の `0x11b080` で、Pia のチャンネルが準備完了かを確かめます。

- オブジェクトの `+0x90` にある SendClone は、準備完了を報告します（`0x5221b0`）。その要素の参加中のステーション（`element+0x3C`）が、すべてクローンの確認応答済みの集合（`clone+0xA8`）に入っていなければなりません。
- `+0x1258` にある SharingClone も、同じ方法で準備完了を報告します（`0x522610`）。
- `+0x250` にある各ステーションのエントリ（0x118 バイトごと）は、最初のワードが 1 で、`+0xD8` にあるバイトが 0 以外でなければなりません。
- ステーションの index である `+0x1430` のバイトは、0xFD（"none"）ではありません。そのような場合はすべて 0 を返します。

SendClone の判定は `(element+0x3C & ~clone+0xA8) == 0`、SharingClone の判定は `((clone+0x114 | ~clone+0xA8) & element+0x3C) == 0` です。どちらも 1 つの要素を共有します。正常に動いているセッションでは、確認応答済みの集合が埋まり、`+0x114` が空になり、すべての `+0xD8` が 1 になります。参加中の集合は最初から満たされています。ステーションのビットが `clone+0xA8` に届くのは、そのステーションからのクローン type 2 の 0xa2 を通じてだけです（`0x51c52c` のジャンプテーブル `0xf76c38` から `0x522350` へ）。

状態 7 は、届いた最初のメッセージのそれぞれを `this + node * 0x1C8 + 0xC0` に格納し、`this+0x470` で数えます。自分のメッセージもループバックして数えられるため、沈黙した相手がいると、数えは 1 のままになります。

### 市販の本体をトレード画面までホストする

ホストされたセッションに参加する本体が必要とするものは、参加者のレイヤーより上で、次のとおりです。

- Local Protocol のボディは、ホストの定数 ID をリトルエンディアンで載せます。ゲームは、送信元をステーションのテーブルで解決します（`0x1171b0` -> `0x5bbe70` -> `0x5b6130`）。`0x117334` の受信処理は、解決できないもの（ノード 0xFD）を飛ばします。ID をビッグエンディアンにすると、本体は状態 7 で待ち続け、画面には間もなく接続されると表示されます。
- 更新セッションは、セッションが変わったときに送られ、その後にもう一度送られます。タイマーでは送りません。そのノードリストは、相手がメッシュに参加するまで 1 つのノードだけを保持します。
- ステーションは、参加した瞬間に、クローンのクロックの要求を止めます。
- ホストは、クローン 0 を発行するフレームでクローン 1 を告知します。本体は、その数十ミリ秒後に自分の告知を送ります（計測値 31 ms）。待つホストはこの競争に負け、役割が入れ替わります。
- ホストが所有するクローンの告知に応答する `0xa2` は、`0x81` の後ろにある `0xa1` のクロックを載せるため、データグラム全体を解析したあとに組み立てられます。ホストのクロックを載せると、本体は 0.5 秒ごとに再告知し続け、自分のコピーを決して発行しなくなります。
- 両方のステーションは、クローン type 2 の発行のたびに自分のコピーで応答します。セッション全体で、毎秒およそ 10 回です。
- 差し出しには、それを運んできたステップのもとで応答します。新しいステップのもとで応答すると新しいラウンドが始まり、ステーション同士が際限なく応答し合います。

### トレードが歩く 2 つのクローンレコード

トレードのオブジェクトは、自分のクローンに状態を発行し、相手のクローンを読みます。クローン type 2 のコピーの 20 バイトのデータは 5 ワードで、`0x11bc00` とその兄弟の関数が書き込みます。

```
+0x00  4  the state: 1 a vote (0x11bc00), 2 a vote withdrawn (0x11b4e0), 4 a forced leave (0x11bcf0)
+0x04  4  that call's argument, 1 on selection and 2 on confirmation
+0x08  4  a counter, incremented on each call
+0x0c  4  the station's own step, the number of game messages it has sent
+0x10  4  the trailing word
```

クローン type 4 のコピーの 32 バイトのデータは、セッションのホスト（権限を持つ側）の見た目です。

```
+0x00  4  A, the agreed argument
+0x04  4  B
+0x08 16  one counter per station index (host 0, joiner 1): the counter of the vote it last saw withdrawn
+0x18  4  the station's step
+0x1c  4  the trailing word
```

権限を持つ側 `0x11b6c0` は、セッションのホスト上で毎ティック実行されます。A を X へ動かすのは、すべてのステーションが、現在の末尾のワードのもとで引数 X の状態 1 を発行したときだけです。このとき、A と末尾のワードに 1 を加えた値を同時に発行します。状態 4 は、A を即座に動かします。引数が A と異なる状態 2 のステーションについては、そのステーションのカウンタを自分のスロットに書き込み、末尾のワードを 1 進め、A と B を保持して、新しい末尾のワードのもとで自分のクローン type 2 を再発行します。

トレード画面のステータスは、`0x34a300` を通じて A と自分のレコードの状態から決まります（A でジャンプテーブル `0xf4e9b0` を引きます）。`+0x271` が立ち、`+0x272` が消えているときは、まず 1 になります。

| A | ローカルの状態 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| 0（テーブル `0xf4e9d0`） | 0 | 1 | 1 | 0 | 0 |
| 1（テーブル `0xf4e9f0`） | 2 | 3 | 3 | 0 | 2 |

A が 2 のときは、ローカルの状態にかかわらず 4 になります。A が 3 のときは 5 になり、相手の離脱を表します（`0x3490c0`）。

同様のステータス関数 `0x3488b0`（テーブル `0xf4e920..0xf4e980`、ループ `0x9c3300`）は、クラス `0x347e10` に属します（`mgr+0x70` の 0x718 バイト、`0x344690` が作成）。このクラスは、`0x886530` がモード 1 と 2 で作ります。

トレード UI の更新（`0x756a20`、サブ状態 `[ui+0xa8]`）は、手持ち発行オブジェクト（`0x7568ec`）をもとに動きます。確認では 2 に投票し（`0x756e34` -> `0x34a4e0` -> `0x11bc00`）、サブ状態 2 に入ります（`0x757058`）。そこでステータス 4 は、`[[x21+0x78]+0x60]` に 5 を書き、`0x74a590(ui, 2)` を呼んで進みます（`0x756c0c..0x756c38`）。ステータス 2 は選択画面に戻ります（`0x756cb4`）。ステータス 1 か 3 のもとでのメニュー結果 3 は、投票を取り下げます（`0x756d94` -> `0x34a500` -> `0x11b4e0`。状態 2）。サブ状態 0 では、`[x22+0x258]` が 0 のときのステータス 1 が `0x34a4a0` を呼びます（`0x756b94`）。これがもう一方の取り下げです。

`0x11b688` は、届いたクローン type 4 のレコードを `+0x1638` に段階的に置きます。`0x11ba20` は、`+0x1638` を `obj+0x04` と、`+0x163c` を `obj+0x10` と比べ、`+0x1640` から始まるノードごとのワードを `obj+0x0c` と比べます。そこに 32 個のゼロを発行するホストがあると、本体は "communication en cours" の画面に留まり、Retour 以外のボタンはすべて灰色になります。

差し出されている手持ちのクローンは、`1 1 1`、末尾のワード 1、次に `x 2 2`、末尾のワード 2 と歩いていきます。コミットのクローンは、手持ちのクローンより 1 つ大きな ID で、最初の 2 つを取り、そのあとゼロを取ります。市販の本体もエミュレートしたものも、ホストのフレームは、クローン type 2 のデータを 5 ワードで送ります。

```
+0 ms     type 4 data, 32 zeros, with the announcement
          the peer publishes 1 1 1 step 0 once its player has confirmed
          1 1 1 step 0                 the host's own confirmation
+30 ms    1 1 1 step 1                 type 4 data 1, zeros, step, 1
+8 ms     the peer answers 0 1 1 step 1
+27 ms    0 1 1 step+1 1               the offered clone goes 0 2 2 step+1 2 in the same frame,
                                       and the kind 3 carrying 1 goes under that step
+3 ms     the peer's kind 3 carrying 1, its copies under its own next step
+63 ms    kind 3 carrying 2 under the next step, every copy republished under it
after the trade demo and the normal save (3000 ms past SaveThread, 0x8377ec):
          two more clones announced, 32 zeros on type 4; the peer publishes 0 0 0 on each
then      kind 4 under the next step, every copy republished under it
```

相手は、型 4 のコピーの最初のワードが 1 のときだけ、末尾のワード 1 に応答します。相手の `1 1 1` が届く前に組み立てられたコピーは 0 を載せるため、本体は待ちます。コミットのクローンを `1 2 2` まで歩かせると、`0 1 1`（末尾のワード 2）が返ります。kind 3 は届かず、本体は確認画面に留まります。

本体ホストは、まずすべてのクローンを告知します。クローン 1、最初のスロットの前の手持ちの組 2 と 3、A 2 のあとのコミットのクローン 4（状態 1 のランダムな遅延、`0x8380d8`）、セーブのあとの次の組 5 と 6、そのあとに最初の kind 4 です。投票も先に行います。クローン 3 に `1 1 1`、末尾のワード 1 を付けた A 1、`1 2 2`、末尾のワード 2 を付けた A 2 を出します。コミットのクローンには `0 0 0`、`1 1 1`、末尾のワード 1 を付けた A 1 を出し、告知の 152 ms 後に、1 を載せた kind 3 とともに `0 1 1` を送ります。各クローンを引き継ぎ、ホストの最初の 3 ワードと末尾のワードを、自分の状態ワードのもとで再発行する参加者が、トレードを完了させます。

確認画面で A をもう一度押してボタンを灰色にすると、投票が取り下げられます。`1 2 2` のあとに `2 2 3`（状態 2、引数 2、カウンタ 3）が出ます。A 2 に応答すると、ステータス 4 になります。本体は同期セーブを始め、コミットのやり取りの前に、トレードロック（600）をコミットします。市販の本体は、そのように応答して `0 2 3` を再発行し、5.0 秒後にコミットのクローンを告知しましたが、その後は沈黙しました。やり取りは完了せず、ロックは立ったままで、通信メニューは次のトレードを拒否しました（`0x976634`）。エミュレートした本体も同じ応答をしましたが、トレードは完了しました（[未解決](lgpe.md#unresolved)）。正しい応答は、type 4 の `1 0 0 3 0 0 step T+1` です。これは `0x11ba20` のもとで、そのレコードを状態 0 へ進めます。状態 0 の A 1 はステータス 2 になり（`0xf4e9f0[0]`）、選択画面に戻ります。A 0 のもとで取り下げられた選択 `2 1 4` は、`0 0 0 4 0 0 step T+1` になります。`bin/lgpe_host.py` はそのように応答し、1 回の発行で次の投票に合意します。`tests/test_lgpe_host_withdraw.py` は、両方をゲームのコードで実行します。

市販の本体同士のトレードでは、どちらの向きでも、クローン type 4 と 1 にクローンのデータが載りません。そこに何も発行しないホストがあると、参加する本体はゲート `0x11b080` に届かず、検索画面に留まります。

### トレードのアニメーション

本体は、ステップ `0e` のあとにトレードのアニメーションを再生し、その間はトレードのペイロードを送りません。市販の Let's Go がホストし、`bin/lgpe_join.py` が参加する場合、そのステップからアニメーションは約 1.7 秒で始まります。受け取ったポケモンは約 15.3 秒で現れます（手動で押す場合は最大 2 秒遅れます）。本体の type 4 のペイロード（248 バイト）は 27.0 秒で届き、プレイヤーが操作を取り戻すのは約 28.8 秒です。

### コミットとトレードロック

トレードロックは、セーブの MyStatus ブロックにある、秒単位の u32 のカウントダウンです。トレードのセーブは、これを 600 に設定し、コミットのやり取りの前にコミットします。やり取りが完了すると、0 に戻してコミットします。

MyStatus ブロックのオブジェクトは `[[[0x15fad08]]+0x98]+0x58` -> `+0x78` にあり、データは `obj+0x58`、0x168 バイトです（`0x1c9ff0`、`0x1ca000`、vtable `0x153e0b0` のスロット 5 と 6）。これは kind 1 の本体です。カウンタは `obj+0xe8`、MyStatus の `+0x90` です（セッター `0x1c9d40`、ゲッター `0x1c9d50`）。`savedata.bin` では、ブロックは `0x1000..0x1168` にあり（トレーナー名は `0x1038`）、カウンタは `0x1090` にあります。中断されたトレードのあとに保存されたセーブは、そこに `58 02 00 00` を保持し、ブロックには他の変更がありません。取得したすべての kind 1 は、`+0x90` に 0 を載せています。

セッターの呼び出し元は、600 を入れる同期セーブ（`0x837f90`、`0x837fb0`）、0 を入れる受け取ったポケモンの適用（`0x838bec`、`0x838c0c`）、カウントダウン（`0x1ca54c`、`0x1ca56c`）です。セーブを読み込むと、ブロックが書かれます。通信メニューの検査 `0x9765f4` は、通信モードで分岐します。モード 1（トレード）はカウンタを読み（`0x976634`）、0 以外なら拒否 `0x0248810f825b1fee` を付けて -1 を返します（`0x97663c`）。0 の場合は、カウントの検査へ進みます（メッセージ `0x0248800f825b1e3b`）。モード 3 は `[x22+0x62] <= 1` のとき拒否します（メッセージ `0x02487f0f825b1c88`）。

ロックはプレイ時間に応じて減ります。`0x1ca450(playtime, seconds)` は、`seconds > 1`（`0x1ca46c`）または `playtime+0x100` が 0 のとき（`0x1ca474`）、すぐに戻ります。それ以外では、カウンタから `seconds` を引き（0 で下限、`0x1ca500`）、その分をプレイ時間に加算します（時間は `+0x54` の u16、分は `+0x56`、秒は `+0x57`。上限は 999:59:59、`0x1ca5a0`）。`0x1ca7e0` は、`playtime+0x100` に `nn::oe::GetCurrentFocusState() != 3`（バックグラウンド）を書きます。呼び出し元の `0x1462a0` は、有効バイト `+0x54` が立っていて、セーブのスレッドがないあいだ（`0x1ce8f0`）、20 回目の呼び出しごとに実行されます（カウンタ `+0x70`）。`GetSystemTick` から基準のティック（`+0x68`）を引いた値を秒に変換し、すでに数えた秒（`+0x60`）からの増分を `0x1ca450` へ渡します（`0x146314..0x14637c`）。基準が動くのは、ティックが逆戻りしたときだけです（`0x146384..0x1463c0`）。2 秒以上の飛びは捨てられるので、時計はゲートを通る呼び出しごとに最大で 1 秒しか進みません。600 のロックは、数えられたプレイ時間で 10 分間続きます。これはフォーカス状態 1 と 2 のときだけで、バックグラウンドのとき、またはゲームが閉じているときには進みません（開始時に基準を読み直します、`0x14628c`）。
秒数は実時間に従います。`0x1462a0` は、ティックの差をナノ秒に換算したものを 10^9 で割ります（`0x14632c..0x146354`）。フレームごとに 1 回の呼び出しで、初期の周期 33.3 ms なら、ゲートを通る本体は 0.667 秒ごとに実行され、増分として 0 か 1 を見ます。そのため、600 のロックはフォーカス中の実時間で 600 秒続きます。ゲートの間隔が 1 秒を超えると、捨てられた飛びごとに秒が失われます。エミュレートした Let's Go 1.0.2 でオーバーワールドを 30 フレーム毎秒で動かすと、呼び出しカウンタ `+0x70` は 0.125 秒ごとに 4 進みました。つまり、フレームごとに 1 回の呼び出しで、ゲートを通る本体は 0.67 秒ごとに実行されます。

`0x13c944` は `0x13c850` の中にあり（`0x13c850` は `0x145560`、`0x13f0d0`、`0x142cd0`、`0x1427a0` も実行します）、`0x13c5a0` からだけ呼ばれます。これは 0x210 バイトのジョブのスロット `+0x40` です（vtable `0x15379d8`。セットアップ `0x13b650` の中で `0x13c440` から `0x13bfa0` を経て作られ、`G+0x50` に格納されます。完了バイトは `+0x204`）。実行器 `0x231a0` は、ワーカーのループ `0x20f30` から、`+0x204` が 0 のあいだ、これを実行します（`0x23264..0x23288`）。`0x13bfa0` は、ジョブを依存関係のグラフへ `0x1ca00` でつなぎます（`0x13c02c..0x13c120`）。毎フレーム何がグラフを提出するか、つまりプレイ時間のティックがどれくらいの頻度で動くかは不明です。フレーム周期の表 `0xf7eeb8` は、16666667 から 83333334 ns までの 5 段階を持ち、`0x39600` で引かれます。フレームのループは 33333334 ns で始まり（`0x38ba0..0x38bb8`、vtable `0x1529968`）、`clamp(period / 16666666, 1, 5)` 回の vsync ごとに表示します（`0x29e80..0x29eb4`）。

`0x347190` は、3 種類のセーブのシーケンスのどれかを組み立てます。0 は「通常のセーブ」（`0x3474d0`）、1 は「同期セーブ」（`0x347670` -> `0x347ae0`、0xc8 バイト）、2 は「致命的エラー」（`0x347810`）です。トレードは同期セーブを使います。その初期化 `0x837c70` は、コミットのチャンネルのオブジェクト（`0x4d9030`）を `seq+0xb8` に作り、カウンタを 600 に設定し（`0x837f88`）、`SaveThread`（`0x1cdc80`）を始めます。`SaveThread` は呼び出し元のスレッドで直列化され、書き終えるとコミットします（`0x1cedd4..0x1cede0`、`nn::fs::CommitSaveData`）。その更新 `0x838070` は、ジャンプテーブル `0xf867c4` を通じて `seq+0xa8` で実行されます。

### バトルシーンのチャンネル

ゼロ以外のタグを使う送信側は `0x9dce94..0x9dede8` だけで、状態を `0x1640eb0` のグローバルブロックに保持します。そのブロックの先頭のワードがチャンネルです（`0x9dce10..0x9dce1c`: `ldr x0,[0x1640eb0]; b 0x4d9450`）。`0x9dce50` は、ブロック `+0x78f0` から 4 バイト（u16 のステーションのバイトと u16 の 0x6e）を、タグ 1 で 0xff へ送ります。`0x9dd3ec` はポケモン（`0x721ef0`）を `+0x348` に詰め、`0x9dd3fc..0x9dd40c` がそれをタグ 3 で送ります。ステーションごとのレコードは 0x1788 バイトです（`0x9dcee8`）。

登録処理（`0x9d2d90`）は、バトルプロセスの段階的なセットアップ `0x9d2c30` にあります（ジャンプテーブル `0xf92c1c`。このプロセスは `Pop_BGM_battle_to_field`、`vs_wild`、`btl_sky.gfbmdl` を参照します）。ディスパッチャーの状態 1 から呼ばれるのは、モード 1 と 2 のときだけです（`0x886f18` -> `0x95c470` -> `0x95c5c0` -> `0x28cd10` -> `0x28e630` -> `0x9cbba0`）。モード 3 では、バトルのチャンネルは登録されません。ステップ 0 はチャンネルを作成し（`0x9dc5c0`）、リンクセッションのオブジェクト `[[[0x15faec8]]+0x50]` が状態 8 のときに限って `0x1640eb0` に格納します（`0x9dc6f4`、`0x9dc61c..0x9dc634`）。`0x1640eb0` が null の間、`0x9dce10` は何も登録せず、準備完了判定 `0x9dce30` はチャンネルがなくても 1 を返すため、野生のバトルでは何も登録されません。解体処理（`0x9d3df0` -> `0x9dcce0`）がポインタを消去します。

### ホストしたトレードがセーブに書き込むもの

差し出されたボックスの構造体は、検査されないまま送られた形でセーブに入ります。次の値を持つレコードは、Let's Go Pikachu のサマリー画面で変わらずに読み戻されます。種族は 132、経験値は 1,000,000（レベル 100）、特性は隠れ特性の 150、PID は色違い判定の xor が TID 41234 と SID 12345 に対して 0 になるもの（`(sid << 16 | tid) % 1000000` で 083154 と表示）、性格は 10、性別なし、個体値はすべて 31、努力値はすべて 200（レベル 100 で HP 437。ゲームの最大値）、わざ 1 つ、捕まえたレベル 30、捕まえた場所 4（2番道路）、言語 2、親の名前 `POKELDN`。オフセットは PKHeX の PB7 マップに従います。

### 参加者が離脱する場合

本体が Retour で抜けるときは、差し出しているクローンに対して状態 4 を、新しいカウンタのもとで引数 0、続けて引数 3 で発行します。ホストは 30 ms 後にそれぞれへ応答します。最初の 3 ワードはゼロ、末尾のワードは 1 増やした値、引数は type 4 のコピーの最初のワードとして返します。その後、本体はクローンを解放します。ステーション 0xFD のクローン type 4 に 0x83 を送り（クローン 0 は type 3）、0x84 が応答するまで繰り返します（約 100 ms ごと、計測値）。ホストは自分のクローンを解放します（自ステーション配下のクローン type 2 と、クローン type 4 の 0x83）。最後の解放のあと、クローンのプロトコルがアイドルになると（[離脱前の待機](#the-wait-before-leaving)）、本体は 24 バイトの信頼性ヘッダのもとで、メッシュのプロトコルの信頼性ポートにメッシュ離脱要求を送ります。

```
04 01        leave request, station index
```

この要求には、そのポートで信頼性のある確認応答が返されるはずです。また、信頼性のないポートでは 2 バイトの離脱応答が返ります。その内容は `08` とメッシュのホストのインデックス（`08 00`）です。離脱側のハンドラ `0x591bf4` は、応答のバイト [1] が、ホストのゲッター `0x58e5d0`（`ldrb [x0,#0xa3]`）が指すステーションのインデックスと一致するときに限って応答を受け取り、離脱ジョブのフラグ `+0x78` を消去します。ジョブ（`LeaveMeshJob`、コンストラクタ `0x589470`）は、要求を送るときに 5000 ms の期限を設定します（`0x5895bc`）。`WaitLeaveResponse`（`0x5896c0`）は、フラグか期限を待ち、要求を再送（40 ms ごと、計測値）してから、ステーションを切断してネットワークから離れます。離脱する相手を指す応答（`08 01`）は破棄されます。その場合、本体は離脱要求の 5.00 秒後に認証を解除します（2 台の本体で 6 回の離脱を計測し、4.98 から 5.01 秒、いずれもホストの切断要求に応答）。`08 00` に 2 回応答されたときは、離脱要求の 0.04 秒後に自分の切断要求を送り、その約 0.06 秒後に認証を解除します。Retour のあと、ホストは 1 バイトのステーション切断要求（type 3）を送ります。本体は 50 ms 以内に type 4 で応答します。

ホストになっている本体は、参加者の離脱要求に `08 00` を 2 回返し、その後は Local Protocol の「ホスト移行の開始」（type 0x13、0.3 秒ごと、計測値）を繰り返します。離脱応答として送られた参加者の切断要求が届くと、ホストのプレイヤーはメニューに戻ります（"l'autre joueur a choisi d'annuler l'échange"。相手がトレードの取り消しを選んだという、ゲーム内の原文です）。待ち続ける参加者がいると、ホストは 0x13 を 5 秒間繰り返し続けます。`bin/lgpe_join.py --leave-after SECONDS` は、離脱処理（`pokeldn.lgpe.leave`）を実行します。

両方のステーションがクローン上で引数 1 を付けて状態 1 を発行すると、本体のホストの type 4 のコピーは 0.27 秒以内に A へ移ります。権限を持つ側は、各ステーションが保存しているコピーを読みます（`container + 0x8d8 + i*0x260`。i はセッションのステーション数より小さい値）。コピーが置き換わるのは、クロックが厳密に新しいレコードのときだけです（`0x52184c`）。クロックが等しいときは確認応答を返し、古いデータを残します。参加者が、そのクローン上の前回のレコードのクロックで、コミットのクローンに投票すると（どちらも同じメッシュのクロックのティック内にあるとき）、本体は古いコピーを保持したまま、プレイヤーをトレード画面に残します。`pokeldn.ldn.clone.Participant.record_clock` は、クローン上のすべてのレコードに、直前より大きいクロックを与えます。`bin/lgpe_join.py` は、そのような投票が kind 3 が届く前に `--stall-leave` 秒（既定値 5）の間、合意されないまま残ると、離脱処理を実行します（`pokeldn.lgpe.leave.unagreed_vote`）。離脱処理は待機を終えますが、トレードロックは外しません。トレードロックは、コミットのクローンへの投票より前に同期セーブが書き込んだものです（`0x838070` の状態 0）。

### ホストが離脱する場合

プレイヤーが抜けるホストの本体は、状態 4 と引数 3 を発行し、クローンを解放します（0x83、応答は 0x84）。最後の解放のあと、クローンのプロトコルがアイドルになると（[離脱前の待機](#the-wait-before-leaving)）、信頼性ポートにメッシュ移行の開始を送ります。内容は `44 00 01`（ホストのインデックス、次のホストのインデックス）です。その待機（`0x58aeb0`）は、接続中のステーションごとのフラグを `job+0x6e+index` に保持し、すべてのフラグが消えるか、5000 ms（`0x58a8f0`）が過ぎると終わります。移行の応答 `48 <index>` がそのステーションのフラグを消し（ハンドラ `0x591e98` -> `0x58b010`）、ステーションが離脱しても同様に消えます。応答がなければ、本体は 5.0 秒間、45 ms ごとに開始を再送します。

続いて本体は、ノードリストを変えずに、ホスト移行の状態 1 を載せた更新セッションをブロードキャストします。さらに Local Protocol の「ホスト移行の開始」（type 0x13）を 301 ms ごとに送り（`0x5d40ac`）、自分以外に LDN ネットワークへ接続しているステーションがなくなるまで（`0x5cc2d0` が数えます）、または 10000 ms が過ぎるまで（`0x5d4050`）繰り返します。その後、LDN の切断フレーム 8 個（理由 3）を 200 ms にわたってブロードキャストし、ネットワークを破棄します。どちらにも応答しない参加者がいると、本体のホストは移行の開始から 15.0 秒の間その場に留まります。エミュレートしたホストは、ack と `48 01` で応答すると、34 ms 後に更新セッションと最初の 0x13 を送りました。市販のホストは同じ形で応答すると、最初の 0x13 を移行の開始から 0.06 秒後に送りました。`bin/lgpe_join.py` は両方の応答を送り、最初の 0x13 でネットワークから離脱します（`pokeldn.lgpe.leave.host_departure`）。

### 離脱前の待機

ゲームの後片付けの段階 `0x116bc0`（リンクオブジェクトの更新 `0x4d9b70` の状態 8）は、クローンのセッション（`0x51bee0`）を終えます。その後、クローンのプロトコル状態 `& 0xf0` が `0x10`（アイドル。`0x5db760` が `obj+0x16f4` に読み込みます）であれば、すぐに戻ります。それ以外の場合は、`[obj+0x80]` の vfunc `0x68` で離脱を呼ぶ前に、150 回の呼び出し（`obj+0x16fc`、`0x116d38` の `cmp 0x95`）を数えます。数え終えるまでの時間は、どちらの役割でも 2.49 から 2.51 秒です。

プロトコルは状態 `0x41` を経てアイドルに至ります。`0x41` では、確認応答されていないデータトークンを持つクローンがある間は待ちます（`0x51b0f0`、`0x5180cc`）。続いて状態 `0x42` で、クローンの終了（0x32）を送り、各ステーションの 0x41 を待ちます。クローン 0 の解放（クローン type 3 の 0x83）のあと、本体はクローン type 2 のコピーを約 100 ms ごとに発行し続けます。各コピーに自分のコピーで応答する相手は、それらを未確認のままにします。その結果、本体は 0x32 を送らず、数え終えてから離脱します。ステーション 0xFD のクローン type 1 に、発行元のステーションとクロックを載せた 0xe3 で応答する相手には、クローンごとに type 2 の 0x83 と 0x32 が届き、離脱要求は本体の最後の解放の 0.11 秒後と 0.29 秒後に現れます。ホストの本体は、最後の解放の 0.13 秒後に移行の開始を送ります。`pokeldn.ldn.clone.Participant` は、相手のクローン 0 の解放のあとに確認応答を返します。

### クローンのデータを持たない参加者に対してホストがすること

0x3C バイトの接続応答（ネットワーク ID もプレイヤーもなし）を受け取った本体ホストは、クローンの告知に応答し、自分の告知を送ります。ただし、クローンのデータ（0xb1 なし）は決して送らず、メッシュへの参加から数秒後にクローンのセッション（0x32）を離脱します。完全な応答を送った参加者は、参加（participate）の後にクローンのデータを受け取ります（計測値 1.1 秒）。

### ゲートを越えたあと

ゲートを通過すると、ホストは状態 4 から落ち着いた状態 8 へ進みます。状態 6 が最初のメッセージを送ります（`obj+0x450` から 0x168 バイト）。状態 7 は自分のループバックと参加者のメッセージを `obj+0x470` に数え、ちょうど 2 になると（`b.ne`）8 へ抜け、それ以上は受け取りません。ホストの画面には、プレイヤーが見つかったと表示されます。最初のメッセージのヘッダは次のとおりです。

    01000000 68010000 01000000 00ff0000    kind 1, 0x168 bytes, step 1
    02000000 e8000000 02000000 00ff0000    kind 2, 0xe8 bytes, step 2
    02000000 e8000000 03000000 00ff0000    kind 2, 0xe8 bytes, step 3

正常に動いているセッションでは、kind 1 のメッセージが確認応答され、クローン ID 2 と 3 が告知され、続けて kind 2 のメッセージが届きます（間隔は 70 ms、3.2 秒、0.4 秒）。`0x349200` にとって状態 8 は終端です。モードワード `+0x8C` が 0 のままの間は、クローン ID 2 と 3 が告知されることはありません。

### ゲートより上のステートマシン

`0x349200` の状態 3 は、`+0xB8` にセッション用のサブオブジェクトを確保し、サンク `0x11b4c0`（オブジェクト `[x0+0x20]`、クローン ID `[x0+0x18]`）経由で `0x11aec0` を呼び、状態 4 へ無条件に進めます。状態 4 は `0x11b4d0` 経由でゲートを呼び、真を返すと進みます。状態 3 と 4 は、ネットワークから何も読みません。同じガードを持つセッターが 3 つ、連続する vtable スロットにあり、vtable 経由でしか到達しません。`0x154f648` -> `0x3495e0`（状態 9、10、11 以外のどの状態からでも状態 3 へ）、`0x154f650` -> `0x349600`（状態 2）、`0x154f658` -> `0x349620`（状態 11、その後に中断 `0x4d8b00`）です。`0x349650`、`0x3497d0`、`0x349880`、`0x3498e0`、`0x349940` がこれに続きます。

`0x11aec0` は、1 フレームでステーションのクローン一式を登録して告知します。内訳は、`game+0x90` の type 1 クローン（`game+0x678` から）、`game+0x1258` の type 4 クローン（`game+0x13f0` から）、そして手持ちのポケモン 1 体ごとの 1 つです（`game+0x218` から歩幅 0x118、`game+0x8d8` から読み出し側の歩幅 0x260）。それぞれ `0x51a550` か `0x51a510` に渡され、どちらも要素のリスト `+0xD8` に告知役を積みます。回収処理 `0x51b380` は 1 ティック後にそれを取り出します。種別バイトは、積まれたオブジェクトの種類に応じてテーブル `0xf46acc`（0x81、0xa1、0x83、0xb1）から取られます。そのため、1 フレームのうちにクローン type 2 では `0x81`、type 4 では `0xa1`、type 1 でも `0xa1` が出ます。

告知はゲートより前に来ます。この 3 つを出すステーションは状態 3 を通過しています。出さないステーションは状態 3 に届いておらず、ゲートの入力に向けたメッセージを送っても助けになりません。本体がホストのときは、トレードのステートマシンからクローン ID 1 に対してだけこの 3 つを出します。ID 2 と 3 は、二つ目の発行元（下の `0x349a90`）から来ます。参加者として参加するときは `0x81` を出さず、引き継ぎのまとめ送りだけを出します。ステーションは、クローン ID ごとに `0x11aec0` を 1、2、3 の順に 1 回ずつ実行します。

### 二つ目の発行元とモードワード

`0x11aec0` の呼び出し元は 2 つあります。トレードのステートマシンは、状態 3 でクローン ID 1 に対して 1 回だけ呼びます。ID 2 と 3 は約 3.2 秒後に、フレームごとの別のディスパッチャーから来ます。その経路は `0x13a780` -> `0x13a160` -> `0x886530` -> `0x344510` -> `0x349bf0` -> `0x349a90` で、手持ちのポケモン 1 体ごとに 1 つのゲームオブジェクトがあり、間隔は 0x1680 です。その間、状態ワードは 8 のままです。

`0x886530` はフィールドに出てから毎フレーム実行され、モードワード `+0x8C`（`0x886ed0..0x886ee8`）で分岐します。値が 1 か 2 ならバトルシーン（`0x886ef8`）へ、3 なら発行の分岐（`0x886f24`）へ進み、それ以外は 8 のまま止まります。`0x344510` は一度だけ実行されます。`[x19+0x68]` が null でなければ早期に戻り、そうでなければ 0x278 バイトを確保して `0x349bf0` を呼びます。

セッター `0x7c4530`（モード 1）、`0x7c4580`（モード 2）、`0x7c45d0`（モード 3。後の 2 つは、さらに引数 0 で `0x147c90` も呼びます）は、`[singleton+0x288]` 経由でワードを書きます。クラスの vtable `0x15afa68`（スロット 9 は `0x886530`）は、`0xe13388` 付近の再配置で埋められます。フィールドから落ち着いた交換まで追うと、モードワードが 0 から 3 へ動く間、3 つのセッターと `0x5a733c` は一度も発火しません。`+0x8C` に書くクラスのメソッドはなく、`.text` にある `+0x8C` への定数の書き込み 16 件のどれも 3 を書きません。書き手は不明です。

### 引き継ぎが運ぶべきシーケンス

クローンを告知するステーションは、シーケンスを確保し、その告知に付けます。要求側の `0x520c30` は、クローンの `+0x38` が 0 のとき、`+0x110` が設定済みのとき、または `+0xB0` と `+0xB8` がどちらも null でないときに早期に戻ります。それ以外では、シーケンスを `+0x10C` に確保して告知役を積みます。完了側の `0x520ce0` は、告知役を積みから外し、`+0xB0` と `+0xB8` がどちらも null でなく、`+0x10C` が渡された値と等しいときに限って `+0x110` へ 1 を書きます。`+0x110` はゲートのステーションごとの項です。`+0x250` の各要素は手持ちのクローンで、`station[i]` = `partyClone[i]+0x38` です。

参加者による引き継ぎ（クローンの種別に対する `0x91`）は、相手の告知のクロックを返します。自分のコピーの告知は、自分のクロックを載せます。

    host   0xa1 clone type 4   00000cfe 01 2808ab      the sequence it allocated
    host   0xa1 clone type 1   00000cfe 01 2808ab
    joiner 0x91 clone type 4   00000cfe               echoed
    joiner 0x91 clone type 2   00000cfe               echoed
    joiner 0xa1 clone type 4   00000d21 01 2808ab      its own clock, the host's content
    joiner 0xa1 clone type 1   00000d21 01 2808ab

`+0xB0` と `+0xB8` は、`clone+0xA8` に埋め込まれた告知役のリストのリンク（`sub+0x08`、`sub+0x10`）です（`0x51e790` がリンクし、`0x51e810` がリンクを外します）。null は、告知リストに入っていないことを表します。正常に動いているセッションでは、両方のクローンはリンク済みで届き、何も確保されません。リンクされていない手持ちのクローンが届くと確保が行われ、その後の完了は拒否されます。受信した `0x82` も `0x520c30` に確保させるため、再告知のたびに `0x82` を載せたまとめ送りで応答すると、まとめ送りごとにシーケンスが 1 つ生まれ、毎秒およそ 30 個になります。

クローンごとに告知のクロックは 1 つだけです。告知側は `0xa1` にメッシュのクロックを押印し、そのクローンに対する相手の確認応答と次の `0xa1` は同じ番号を載せます。`+0x10C` がそれを保持します。レコードは、そのクローンについて他のステーションが最後に送った `0xa1` のクロックを載せているときに一致します。`0x520d30` は、クローン type 2 の `0x91`（否定応答）を、`0x520ce0` は `0xa2` を、同じ前提条件のもとで処理します。どちらも告知役を積みから外しますが、`+0x110` へ 1 を書くのは `0xa2` だけです。一致する `0x91` は告知を取り消し、一致する `0xa2` は告知を完了させます。参加者自身のクロックから作った `0xa2` は一致しません。

シーケンスは手持ちのクローンごとに持ち、`0x520cb8` で確保し直されます。確保のたびに 0x34 から 0x38 へ進みます。参加者自身のクロックを載せた引き継ぎでは、ホストは手持ちの 2 体のクローンに対して `0x1114b` を確保しました。クローン 0 の完了は `0x1114b` を載せて `+0x110` を設定しましたが、クローン 1 の完了は `0x111b0` を載せ、拒否されました。その結果、ゲート `0x11b080` は偽のままで、状態ワードは 4 から抜けませんでした。相手の最初のクローン type 2 の発行にだけ応答し、残りに確認応答を返さないと、相手は毎回新しいシーケンスで再告知に戻ります。

### 参加者がクローンごとに一度行う引き継ぎのやり取り

引き継ぎは所有権の移転です。`0x520d30` は相手の告知を取り消し、参加者は自分のクロックでクローンを告知します。手持ちの 2 体のクローンに対する参照用のやり取りを示します。ホストの告知を 0 ms とします。

```
+0 ms   host    0x81 clone 2, 0x81 clone 3, dest 0x0003
        host    0xa1 x2 per clone                        clock 0x197e, the host's
+5 ms   joiner  0x82, 0x91 x2, 0x82, 0x91 x2, 0x84 x2    echoing 0x197e
+75 ms  joiner  0x81 clone 2, 0xa1 x2                    clock 0x19c1, the joiner's own
        joiner  0x81 clone 3, 0xa1 x2                    clock 0x19c1
+102 ms host    0xa2 per clone                           clock 0x19c1, the joiner's
        host    0xa1 per clone                           clock 0x19e2, the host's own
+141 ms joiner  0xa2 per clone                           clock 0x19e2, the host's
```

参加者は、自分が所有していないクローンの最初の告知で、そのクローンを一度だけ引き継ぎます。それ以降の再告知には、その告知のクロックを載せた `0xa2` を 1 つずつ返します。これは参加者のステーション配下のクローン type 2 で、ペイロードは `<clock> 00 00 00 02` です。二度目の引き継ぎは、所有を移すつもりのなかった告知を取り消すため、相手は際限なく再告知します。

完了は `0xa2` が進めます。ステーション自身の告知役は、自分の `0xa2` のループバックを約 6 ms 以内に受けて完了するので、最初の手持ちクローンは必ず完了します。二つ目には、参加者の `0xa2` が必要です。正常に動いている参加者のまとめ送りには確認応答が含まれません。相手の `0xa2` の組は +37 ms に届き、参加者の単独の `0xa2` は応答として +72 ms に送られます。再告知しない相手は、ティックごとのビルダーがリンク後およそ 30 ms で行うリンク解除も起きず、シーケンスも確保しません。

相手だけを宛先にした再告知には、20 から 60 ms 後に、相手のクローン type 1 の `0x82` が返ります。この `0x82` を受けて、ホストは 32 個のゼロからなる type 4 のコピーを送り、本体はこれに `1 1 1` で応答します。市販のホストは、1 回の再告知の後に、コミットのクローンに対する `0x82` もその後のメッセージも届かないと、トレードロックを保存済みのまま確認画面に留まります。`pokeldn.ldn.clone` は、`0x82` が届くまで、相手だけを宛先にした `0x81` を 100 ms ごとに最大 20 回再送します。

市販の本体は、コミットのクローン 4、7、10 に対する最初の相手だけの告知に、それぞれ 63、26、62 ms 後に応答しました。最初の相手だけの `0x81` を保留すると（`bin/lgpe_host.py` と `bin/lgpe_join.py` の `--withhold-announce 1`、テスト専用）、100 ms 後の再送に対して本体の `0x82` が返り、どちらの役割でも交換が 3 件完了します。

### 告知の宛先フィールドが決めること

コマンドヘッダ `0x51f820` は、`+0x10` をステーションのビットマップとして配置します。クローンを初めて告知する 0x81 はメッシュ全体（0x0003）を載せます。その後ろにある、クローン type 4 と type 1 の 2 つの 0xa1 と、35 ms 後に繰り返される告知は、相手だけ（0x0001）を載せます。メッシュのビットマップを受けた相手は、2 つの 0xa2 で応答します。1 つはクローン type 4、もう 1 つは自分のステーション配下のクローン type 2 です。相手のビットマップを受けた場合は、どちらにも応答せず、クローン type 1 の 0xa1 を送り続けます。その結果、ゲート `0x11b080` は、確認応答された集合が埋まるのを見ることがありません。

クローン type 1 の `0xa1` の再送回数で、正常なセッションと止まったセッションを見分けられます。正常なときは、ステーションごとに 9 回です。再告知のたびに引き継がれた相手からは、0.12 秒ごとに際限なく 1 回ずつ送られ、その相手のゲームは無反応のままです。

クローンのメッセージはすべて `0x51e3d0` で組み立てられます。これはプロトコルオブジェクトの 9 番目の vtable スロットです（4 番目は 0x73 を返します）。呼び出し元での直接の種別値は次のとおりです。クローン type 2 の 0xa2 は `0x51cbb8`、0x81 は `0x51e92c`、クローン type 3 の 0xa2 は `0x51cdd4`、0xc1 は `0x51c9e4`、0x82 は `0x51c60c` と `0x51cd5c`、0xe3 は `0x51ad2c`、0xf3 は `0x51ef18` です。ゲームは 1 つの要素に対してクローンオブジェクトを 3 つ持ちます。type 1 は `game+0x90` と `game+0x1710` に、type 4 は `game+0x1258` にあります。メッセージのクローン type は、これらと一対一には対応しません。

| アドレス | 役割 |
|---|---|
| `0x51ab20` | CloneProtocol::vfunc9。要素ごとの受信 |
| `0x51c100` | 受信のディスパッチ。テーブル `0xf7673c` で (type - 0x11) によりクロックのメッセージとコマンドのメッセージを分け、`0xf76800` で (type - 0x84) によりコマンド経路へ進みます |
| `0xf769c4`, `0xf769e4` | 上位 4 ビットによる構造。クローン type |
| `0x51b010` | 応答のステートマシン。テーブル `0xf76674` を (type - 0x21) で引きます |
| `0x51b1d0` | クロック駆動の再送スケジューラー |
| `0x51f9b0`, `0x51fab0`, `0x51fbd0`, `0x51f820`, `0x51f4c0` | シリアライザー: クロック要求、クロック応答、参加、コマンドヘッダ、ClockAndCount |
| `0x51c1e0` | [0xC] のカウントが送信者の前回の値を超えないメッセージを破棄します |

要素のオフセットは、+0x34 がステーション、+0x40 が状態、+0x50 がクロック、+0x7a0 が送信時刻、+0x32c が結果です。
