# Pokemon LEGENDS アルセウス

Pokemon LEGENDS アルセウス (2022 年、title id `01001f5010dfa000`) は、Pia を `main` に静的リンクしたネイティブの Switch タイトルです。

アドレスは、`tools/switch/nso_read.py` が配置する、アップデート 1.1.1 の展開後の `main` からのオフセットです (text は `0x0..0x32a5690`、rodata は `0x32a6000` から、data は `0x401a000` から)。

## 無線層

| | 値 |
|---|---|
| Pia ヘッダーのバージョン | 11。wiki の Pia 6.16 から 6.23 の帯 (ソード・シールド 4、ブリリアントダイヤモンド・シャイニングパール 9、GBA アプリ 15/16) |
| ヘッダーサイズ | 0x1C |
| 通信上の GCM タグ | 16 バイトから切り詰めた 8 バイト |
| LDN パスフレーズ | ソード・シールドのもの。綴りは `HGhG` (wiki の `HGHG` の行は誤り) |
| Pia ゲームキー | `p1frXqxmeCZWFv0X`。ソード・シールドおよびスカーレット・バイオレットと同じ |
| LDN のローカル通信 ID | `0x01001f5010dfa000` (タイトル ID と同じ) |

ゲームキーとパスフレーズは、rodata の `0x3985308` と `0x3985319` にあり、どちらも NUL 終端です。`0x2c1e684` の LDN セットアップは、ローカル通信 ID を `x3` で受け取り (`0x264082c` の `mov`/`movk` の並び)、ゲームキーを `0x2c1e880` に設定します。

ヘッダー初期化関数 `0x6f0744` は、オブジェクトの `+8` にマジック `0x32AB9864` を、`+0xc` に `0x0b` を格納します。検証関数 `0x6f07d0` は、マジック、`(byte & 0x7f) == 11`、パケット長から 0x1C を引いた値が 0x5a5 未満であることを確認します。パケットバッファは `+0x30` にあり (容量 0x5c0)、長さは `+0x5f8` にあります。`0x6f0878` のコピー代入が各フィールドのサイズを決めます:

    wire  object  size  field
    0x00  +0x08   4     magic 0x32AB9864, big-endian
    0x04  +0x0c   1     0x80 (encrypted) | version (0x7F) = 11
    0x05  +0x0e   2     destination variable id
    0x07  +0x10   2     source variable id
    0x09  +0x12   2     packet id
    0x0b  +0x14   1     footer size
    0x0c  +0x15   8     AES-GCM nonce
    0x14  +0x1d   8     AES-GCM tag, truncated from the 16 the object holds
    0x1c                ciphertext, then the footer

フッターは暗号化の対象外です。暗号化関数 `0x6f09f4` は、フッターサイズを差し引き、ブロックサイズまで 0xFF でパディングし、バッファ `+0x4c` から暗号化します。タグは、タグ長 8 の AES-GCM エントリ `0x6e68d0` を経由して `+0x1d` に書き込まれます (`0x6f0b24` の `mov w4, #8`)。最後に、バージョンに `0x80` を OR します。

## 受信経路 (ブレークポイント用)

    0x6ff6d8   nn::pia::local::LocalInputStream::vfunc4, the socket read
    0x6f07d0   the header validator (five callers; 0x6ff6fc is the input stream's)
    0x6f0b84   the packet decrypt, through the GCM entry at 0x6e6aac; failing here is key, IV or tag
    0x6f09f4   the packet encrypt
    0x7015b4   LdnBackgroundProcessJob::WaitConnected, the step body a stalled joiner sits in
    0x70c304   LdnProtocol vfunc18, which that step requires to return 0

## 参加者が止まるゲート

述語 `0x6f63fc` は、LdnProtocol オブジェクト上の 2 つのエンドポイントスロット `+0x98` と `+0xb8` を読みます (それぞれ 0x20 バイトで、`+8` に 16 バイトのアドレス、`+0x18` にネイティブ u16 のポート):

    0x6f0ee4(a)     -> set: port non-zero and address not the sixteen zero bytes at 0x3972091
    0x6f0f48(a, b)  -> equal: same port, same sixteen address bytes
    0x6f63fc(obj)   -> 0 unless both are set, then 0x6f0f48's answer

参加者が接続されているとき、両スロットは本体自身のアドレスと Pia ポートを保持しており、1 を返します。スロットが 0 になるのは、切断から次の参加までの間だけです。このゲートが参加者を止めることはありません。

## メッセージの振り分け基準

振り分けのキーは、パケットの送信元変数 ID です。レジストリにない局からのメッセージは、そのプロトコルを参照される前にスキップされ、変数 ID はセッションごとに振り直されます。フラグ `0x01` は「送信元変数 ID の検査を省略する」を意味します。相手がまだ送信者を知らない時点で送られるメッセージ用で、`bin/pla_host.py` は両方のプローブにこれを設定します。

## Net プロトコルの実測

自分でネットワークをホストする本体は、`NetUpdateNetworkConnectionStatusMessage` (プロトコル 0x2C、type 0x11) で交換を始めます。wiki の 6.16 から 6.39 のレイアウトに一致し、ネットワーク ID も広告された SSID から導出されたものです:

    01 11 002a          header version 1, type 0x11, payload size 0x2a
    00000002            sequence id
    eb6f                host variable id, a fresh value every session
    ac56011000020000    host constant id, ldn_constant_id of 02:00:ac:10:56:01
    000000004f264487    network id, the low four bytes being crc32(ssid[1:16])
    01                  is network open
    0002                number of stations
    00                  is migrating host
    ...                 two NetStation entries

この帯では NetStation は 21 バイトです (6.39 では 22 バイト):

    +0x00  1   host migration state
    +0x01  1   host migration ranking
    +0x02  1   one byte where 6.39 has two, disconnection candidate and kicking
    +0x03  18  station address: 16 bytes of address, then a big-endian u16 port

どちらのエントリもポート 12345 を持ち、ランキングは本体が 0、参加者が 1 です。

交換をホストしている本体は、自分の変数 ID 宛の Session (0x98) 参加要求には応答しません (下の読み取りゲートがこれを破棄します)。代わりに、参加済みの局にホストの役割を引き継ぐよう求めます:

| 参加者の挙動 | 本体 |
|---|---|
| 0x11 に 0x12 の ACK で応答する | 新しいシーケンス ID を付けた 0x11 を `is migrating host` 1 とともにもう一度送り、その後は `01 40 00 00` (素の `NetStartHostMigrationMessage`) を毎秒約 2 回送る |
| 参加要求は送るが、0x11 には決して応答しない | 同じ 0x11 を 0.5 秒ごとに送り、続いて `is migrating host` を立てて `01 40 00 00` を送る。その後ネットワークが落ちる (アソシエーションから 8.6 から 10.1 秒後、13.5 から 14.1 秒後、16.8 から 17.5 秒後) |
| `NetUpdateNetworkHostMessage` で応答する | 0x40 を繰り返し送り続ける |

宛先 0 への参加要求を伴って席に着き、本体の最初の 0x11 から 4.5 秒保持された参加者は、局リストの 0.02 秒後に、後継として自分を指名する Session type 7 を受け取ります (エミュレートした本体では 4 回中 4 回、実機 1 台では ESP32 ボード経由で確認)。新しいホストは、同じコードでネットワークを作成して移行を完了させます。本体は依頼から 3 から 6 秒後に自分のネットワークを落とし、新しいネットワークに参加して参加者として交換します。`bin/pla_join.py` は最初の 0x40 で席を離れ、同じコードとチャネルで `bin/pla_host.py` を動かします。`--ip-join` を付けると IP 経由になります (`--take-host` は既定で有効で、ホストの役割を引き継ぐ動作全体を指します)。エミュレートした本体に対する順序は、type 7、type 8、参加側のホストが最後のパケットから 5.2 秒後に起動、そして本体がその 0.02 秒後にそのホストに参加、です ([本体のネットワークへの参加](#joining-a-consoles-network))。

Net のメッセージはそれぞれ、シリアライザ付きの名前付きヘッダークラスを持ちます。`NetUpdateNetworkHostMessageHeader` (`0x6fe03c`) は、wire の +4 に u64、+0xc に u64、+0x14 に u16 を持ち、サイズは 0x16、big-endian です。0x11 のヘッダー (`0x6fd9dc`) は、オブジェクトの +0x0c、+0x10、+0x18、+0x20、+0x28、+0x2a を、wire の +4、+8、+0xa、+0x12、+0x1a、+0x1b に対応させます。`nn::pia::session::ClusterPacketWriter` (0x732264 から 0x7336e8) は Session メッセージをインラインで書き込みます。

検索をしている本体は、離脱することでホストの役割を手放します。`Session::LeaveAsync` は `LeaveSessionJob` を開始します。その DisconnectNetwork 段階 (`0x72c9dc`) は、ネットワークのファサードのスロット 15 を呼びます。ネットワークのホストでは、`NetProtocol+0x248` が立っているとき、ホスト移行を伴う `NetDestroyNetworkJob` (`0x7069d0`) が開始されます。このフラグは、コンストラクタ `0x6f48fc` が 1 に設定します (`0x6f4a14`)。書き込み箇所はこれだけです。ジョブは、新しいシーケンス ID と `is migrating host` 1 を付けた Net 0x11 を送り (`0x6f6af0`)、すべての 0x12 を最大 4000 ms 待ち (`0x706b34`)、その後 `NetStartHostMigrationMessage` (`0x6f7674`) を 300 ms ごとに、自分が唯一の局になるか締め切りを過ぎるまで送ります。締め切りは、完全に ACK された 0x11 の後は 4000 ms、タイムアウトした 0x11 の後は 2000 ms です (`0x706df0`、`0x706e98`)。その後 LDN ネットワークを破棄し、そこに残っていた局がホストの役割を引き継ぎます。本体がセッション参加要求を破棄し、参加応答が来なかった `bin/pla_join.py` の 14 席では、最初の移行中の 0x11 が席に着いてから 8.3 から 10.3 秒後に届き、4.0 秒間繰り返されて、その後 2.0 秒間 0x40 が続きました。

Session の参加要求を送らずに関連付けだけした局は、この経路でスロットを終えます。検索をしているエミュレートした本体で `bin/pla_join.py --join-delay 20` を使うと、WaitMember タイマーの期限切れ (`0x2bdb7a0`) が席に着いてから 0.99 秒後に発火し、その 2 ms 後にマッチメイキングのシーケンスのエラーハンドラが離脱要求を組み立てました (`0x2c27fb8`。捕捉したエラーの型名が一致しないとき `0x2c4ee60` から呼ばれ (`0x2c4ee3c`))。`Session::LeaveAsync` (`0x72a6dc`) は約 1.4 秒後に続きました。その後 `LeaveSessionJob` は `LeaveMeshWithHostMigrationJob` (`0x72c640 -> 0x734c8c -> 0x73eee4`) を実行します。これは、8000 ms 先の締め切り (`0x73efb4`) まで次のホストを探し続けます。Session の経路を持たない局 (経路バイト +0x90 と +0x91 が 0xfd) は条件を満たさないので、切断と移行中の 0x11 は 8 秒後になります。ブレークポイントなしでは、席に着いてから 10.48 秒後でした。

本体は、フルメッシュのホストとしてメッシュを作成します (`CreateSessionJob`、待機なし)。参加側の本体は、自分の変数 ID から、ヘッダーの宛先 0 宛に Session の参加要求を送ります。ホストの `ClusterPacketReader` ゲート `0x744644` (vfunc `0x98` 経由、`0x731edc` から `0x743ec0` で呼ばれる) は、ユニキャストパケットの送信元変数 ID を自分の局の中から探し (`0x744718`、マネージャの vfunc `0x48`)、一致するものがなければパケットを破棄します (`0x7447a8`)。宛先 0 または 1 で、フッターがないパケット、または送信元変数 ID が 0 のパケットは、探索を省略します。そのため、まだ登録されていない参加者からホストの変数 ID 宛に届いた参加要求は、復号の後、Session ディスパッチャの前で破棄されます。宛先 0 に送ると、参加応答と type 5 の局リストが返ります。検索をしているエミュレートした本体は、そのように席に着いたのにデータ交換レコードを送らない参加者の約 10 秒後に、移行を伴って離脱します。エラーは表示されず、検索に戻ります。

## パケット暗号

| | |
|---|---|
| セッションキー | ネットワーク SSID の 1 ブロックに対する `AES-128-ECB(game key)` |
| ネットワーク ID | 先頭 1 バイトを落とした SSID (`ssid[1:16]`) の CRC-32 |
| GCM IV | `u32be(network id XOR source IP)` の後に、ヘッダーの 8 バイトの nonce |
| ヘッダーの nonce | パケットごとのカウンタ (big-endian) |
| タグ | GCM タグの先頭 8 バイト (ヘッダー内) |

`0x70d61c` がセッションキーを導出します。16 バイト未満のシード (`0x70d66c` の `0x10 / len`) を繰り返し、`LdnProtocol+0x238` のゲームキーで ECB の 1 ブロックを暗号化します。`LdnProtocol+0x234` の暗号モードが 0 の場合、キーは全部 0 のままです。

`nn::pia::local::LocalOutputStream::vfunc3` (`0x711710`) が IV を組み立てます。`0x6ed380` が `IV[0]` に big-endian の XOR を書き込み、その後ヘッダーの 8 バイトの nonce が `IV[4]` に入ります。送信側はパケットごとに nonce を増やし、`0x6ed360` を通して書き込みます。GCM の暗号設定は `{mode +0, IV pointer +8, IV length +0x10, key pointer +0x18, key length +0x20}` で、mode 1、IV 12、key 16 です。

`pokeldn/ldn/crypto.py` は、6.16 から 6.42 の帯の全体に同じ導出を行います。

## パケットより上のプロトコル

Pia 6.16 から 6.30 では、5.29 から 5.45 の ID をセッション層の下に残し、局とメッシュのプロトコルを 1 つの Session Protocol に置き換えます。ID は 6.32 で再び変わりました:

| プロトコル | 5.29-5.45 | 6.16-6.30 | 6.32-6.40 |
|---|---|---|---|
| Net | なし | 0x2C | 1 |
| RTT | 0x58 | 0x58 | 3 |
| Unreliable | 0x68 | 0x68 | 5 |
| Clone, atomic から clock まで | 0x74-0x77 | 0x74-0x77 | 6-9 |
| Reliable | 0x7C | 0x7C | 10 |
| Broadcast reliable | 0x80 | 0x80 | 11 |
| Session | 0x94 | 0x98 | 13 |
| 監視データ | 0xA4 | 0xA4 | 15 |
| Station、mesh、sync clock、local | 0x14, 0x18, 0x1C, 0x24 | なし | なし |

`pia_connect.py` (6.32 の Net、Session、RTT) は、ID を振り直したうえでこの帯に合います。`station_protocol.py` と `mesh_protocol.py` は、ここにないプロトコルを実装しています。

本体の参加要求は、自分のプロトコルのバージョンを列挙します:

    Net 0x2c v0   RTT 0x58 v3   Unreliable 0x68 v1   Clone 0x74 v0   Clock 0x77 v0
    Reliable 0x7c v2   BroadcastReliable 0x80 v3   0x81 v3   Session 0x98 v0   Monitoring 0xa4 v0

### Session の参加要求

`ClusterPacketWriter` が送る 115 バイトの Session type 0 メッセージです。type バイト、プロトコル数、上の 10 組の `(id, version)`、続いて以下が並びます:

    +22  4   random, fresh on every repeat; Scarlet seeds it from the system tick
             (`docs/sv.md`, The Session join request)
    +26  8   source constant id, ldn_constant_id of the console
    +34  2   zero
    +36  2   source variable id, the joiner's own, fresh per session
    +38  1   NAT mapping
    +39  1   private-IPv6 flag
    +40  32  identification token, all zero on a codeless join
    +72  1   address kind, 0 for IPv4
    +73  4   source station address, IPv4
    +77  2   source station port, 12345
    +79  8   destination constant id, the host's
    +87  2   zero
    +89  2   destination variable id, the host's, `00c6`
    +91  1   player count, 1
    +92  1   a flag, 1
    +93  22  one player record: id `00..01 00..00` (two big-endian u64, 1 and 0), a big-endian u32
             name length of 1, a kind byte of 1, the name, a single space

wire 上の location id は 12 バイトです。big-endian の u64 の constant id、2 バイトのゼロ、big-endian の u16 の variable id からなります。メッセージフラグは、繰り返しのすべてで `0x01` です。`pokeldn.ldn.pia6.build_session_join` は 115 バイトを再現します (`tests/test_pla_session_v11.py`)。

### Session の参加応答

参加側は、ACK を `0x737534` で、参加応答を `0x7379c0` で解析します。どちらも受信ループ `0x7353a0` から、`main+0x3973f19` の type テーブル経由で振り分けられます。それぞれ 4 つの ID を比較し、一致しなければメッセージを黙って破棄します。ホストは、要求の宛先 ID を自分の ID として、送信元 ID を本体の ID として返します。

ACK は Session type 1 で、25 バイトです。type バイト、ホストの location id、本体の location id からなります。`JoinMeshJob+0x69` を設定し、参加の締め切り `job+0x80` を 8000 ms 延長しますが、何も完了させません。

参加応答は Session type 2 で、43 バイトです:

    +0x00  1   02
    +0x01  1   protocol id 0x98, read only when status is 3
    +0x02  1   Session version, read only when status is 3
    +0x03  1   status, 1 is the accept path
    +0x04  8   unread on the accept path
    +0x0c  12  host location id, four-field compare
    +0x18  12  console location id, four-field compare
    +0x24  1   route byte A, stored to the self station +0x90
    +0x25  1   route byte B, stored to +0x91
    +0x26  1   station index, sets bitmap bit [+0x788][index]
    +0x27  2   join order, big-endian u16, stored to +0xf8
    +0x29  2   sequence id, big-endian u16, stored to +0xde

割り当てのフィールドは検証されずに保存されます (本体の書き込み `0x736cec` は、最初の参加者に対して route `00 01`、index 1、join order 1 を設定します)。status 1 は `JoinMeshJob+0x68` を設定し、要求の繰り返しを止めます (1 ウィンドウあたり約 16 回)。完了フラグ `JoinMeshJob+0x7c` は、シーケンスが `+0x29` に達した type 5 の更新 `0x738740` が適用されると立ちます。参加側は、13 バイトの Session type 6 で応答します。内容は、type バイト、本体の constant id、2 バイトのゼロ、シーケンスです。

### type 5 の局リスト更新

`0x73897c` が読む前に、`0x7404a8` が更新を組み立て直します。断片 1 つで全体を運びます。7 バイトの断片ヘッダーは、type バイト、big-endian の u16 シーケンス、断片数、断片インデックス、big-endian の u16 オフセットです。バッファには type とシーケンスが入っているので、ペイロードはホストの constant id から始まり、オフセットは 3 です。組み立て後の本体:

    +0x00  1   05, the reassembly byte
    +0x01  2   sequence id, big-endian u16
    +0x03  8   host constant id, big-endian u64
    +0x0b  4   host variable id, a [0000, u16] big-endian u32
    +0x0f  1   station count, at most 0x18
    +0x10  n   IPv6 bitmap, (count + 31) / 32 * 4 bytes, little-endian u32 words, bit i set for an
               IPv6 station
       ...     station entries

局エントリ 1 つは `0x739050` が読みます。IPv4 の形式は次のとおりです:

    +0x00  8   constant id, big-endian u64
    +0x08  4   variable id, a [0000, u16] big-endian u32, the low half passed to the admit
    +0x0c  4   IPv4 address
    +0x10  2   port, big-endian u16
    +0x12  1   route byte A
    +0x13  1   route byte B
    +0x14  1   station index
    +0x15  2   join order, big-endian u16
    +0x17  1   NAT mapping
    +0x18  1   private-IPv6 flag
    +0x19  32  identification token
    +0x39  1   player count
    +0x3a  1   participant count
    +0x3b  ..  player records, each a 16-byte id, a big-endian u32 name length, an encoding byte, and
               the name

IPv6 の局は、6 バイトの代わりに 18 バイトのアドレスを持ちます。ホストは route `00 00`、index 0、join order 0 です。最初の参加者は `00 01`、1、1 です。プレイヤーレコードは参加要求のものです。`0x738bc0` は constant id ごとに局を更新または作成し、その後 `JoinMeshJob+0x7c` を設定して type 6 を送ります。参加済みの本体は、その後 RTT、Clone Clock、Stream Broadcast Reliable のストリームを動かします。

## メッシュの維持

参加済みの本体は、ゲームの DataExchangeStart 段階が参加要求から 10.2 秒後にタイムアウトすると離脱します。ただし、それより先に 0x81 のデータ交換が完了した場合は除きます ([ゲームのリーダーとハンドラ前段階](#the-games-reader-and-the-pre-handler-phase))。RTT (0x58) は 11 バイトです。種別、8 バイトのタイムスタンプ、2 バイトの宛先からなり、宛先 0 の種別 1 のエコーは受け入れられます。

Stream Broadcast Reliable (0x81) は、`pokeldn/ldn/reliable5.py` のスライディングウィンドウを運びます。9 または 13 バイトのヘッダーの後に、アプリケーションデータが続きます。アプリケーションデータのフラグが立っていない場合は、`2 + 21 * count` バイトの一括 ACK が続きます。ACK の先頭の type バイトは、ビット 0 だけが読まれます。21 バイトの各エントリは、局バイト、big-endian の u16 の確認応答 ID、big-endian の u16、16 バイトのマスクからなります。受信側 (`BroadcastReliableSlidingWindow` の vf13 `0x742730`) は、自分の局インデックスのエントリを読み、その局バイトが送信者のインデックスと一致することを求めます。そのため、インデックス 1 の参加者に ACK するホストは、局バイトがすべて 0 の 2 つ以上のエントリを送ります。ID とマスクは [確認応答](#acknowledgement) に従います。

受信側は、各エントリの 2 番目のハーフワードを `[window + 0x528 + 2 * station]` に格納します (`0x742828..0x742830`)。type のビット 0 で `[window+0x4b8]` を設定し、0x7c ウィンドウの `0x74f0ec` (`0x742880`) を通して ID を適用します。送信経路の vf11 `0x742304` は、ハーフワードが `0xffff` であるか、ウィンドウの基点以上であるか、スロットが空である局を、宛先ビットマップから除きます (`0x74238c..0x74242c`)。そして ACK の送信関数 `0x74ea00` に渡します。`[window+0x4b8]` が立っていなければ何もしません。ビットマップが空なら、それを消して `[window+0x4c0]` を刻印します。それ以外は AckMessage を送ります。シーケンスは `0xffff`、長さは `2 + 21 * count` (`0x74eb64..0x74eb94`)、埋まっている局ごとに 1 エントリです (`0x74eba0..0x74ec2c`、`0x74ec80` と `0x743160` でシリアライズ)。ハーフワードは ACK をゲートするだけで、再送はゲートしません。キャプチャした 30 回の参加のすべてで、本体の 0x81 アプリケーションメッセージはシーケンス 1 を持っていました。そのため、ホストの確認応答は `ack_id 2` を指定します。ホストは、受信した最大シーケンスの 1 つ先をまだ ACK します。

本体は、INITIALIZED のデータメッセージ (フラグ `0x0f`、seq 1) とその次のメッセージでストリームを開きます。その ACK は約 1 秒ごとに送られ、ホストが沈黙している間に増えていくホストストリーム ID を運びます。宛先ビットマップのうち、本体の局インデックスのビット (ビット 1、count 2) が立っているホストのデータは適用されます。違うビットのものは、送信元局のチェックで破棄されます。

### 沈黙した局のチェック

Session の開始 `0x729d3c` は、起動設定の `+0x28c` を `SessionProtocol+0xd8` にコピーします (`0x72a098`)。下限はありません (Pokemon LEGENDS Z-A には 4000 ms の下限があります)。また `+0x290` を沈黙送信の上限に渡します (`0x746fe4`。負の値は 0x10407 で失敗し、0 は 1000 ms になります)。更新 `0x73564c` のたびに、状態 2 の局のうち、最後のパケット (`ClusterStation+0x88`) が `[SessionProtocol+0xd8]` ms より古いものを列挙します。ホストでも参加者でも同じです。先頭のエントリが 3000 ms 古くなると (`0x735364`)、`0x7359ac` がリストに従って動きます。ホストは各局を `KickoutManageJob` (`0x73cad4`) に渡します。リストにホストの名前がある参加者は、ホストがいなくなったものとして扱います (`0x735b28`)。設定の `+0x28c` は 10000 ms です (検索をしているエミュレートした本体では `0x72a09c` で `w9 = 0x2710`)。Pokemon LEGENDS Z-A と同じです。ボックス画面で沈黙したホストは、約 13 秒後に相手の離脱メッセージを表示します。これは 10000 ms と 3000 ms の猶予によるものです。

## ゲームのリーダーとハンドラ前段階

ゲームは `main+0x2ca4f30` (`0x741494`) でリーダーをポーリングします (計測した 1 つの区間で 365 回の呼び出し)。0x7C と 0x80 の 2 つのループが、1 つのハンドラテーブルを共有します。0x81 のホストデータは、ここには届きません。メッセージの最初の 8 バイトは、2 つの u32 からなるハンドラキーです。一致したハンドラが残りを受け取り、一致しないキーは破棄されます。

交換の検索画面では、ハンドラテーブルが空です (読み取りの後の `ldr x8, [x19+0xd0]; cbz x8`)。そのため、すべてのメッセージは読まれないまま捨てられます。`0x2ca5264` はフローのステップ 0x1e でハンドラを登録しますが、タイムアウトするセッションでは到達しません。メニューを離れると、ハンドラ配列のポインタは null になります。計測したところ、アイドル中のリーダーのループは毎秒約 2.5 回回っていました。ゲームの Pia 呼び出し箇所 9 つが解決するのは 0x68、0x7C、0x80 だけです (読み取りループ 3 つ、送信経路 4 つ)。0x77 のクロックのトラフィックは Pia 自身のものです。

10 秒の離脱は、Pia のメッシュ参加より上にあるゲームのマッチングシーケンスの失敗分岐です。交換シーンは、その成功分岐です。交換のフローは `0x13d5bfc` で、ステップは `[flow+0xa4]` にあり、ステップ 0x15 から 0x22 のジャンプテーブルは `0x397c118` です。ステップ 0x17 は `0x26bdcac` を呼び、これが `[manager+0x70]` にシーケンスを組み立てます。ステップ 0x18 は、vtable のスロット 9 (`0x12b3290`) を通してこれをポーリングします。未完了の子カウンタ `[request+0x70]` が 0 のとき真になります。フローは、ネットワーク、セッション、メッシュのどのフィールドも読みません。ステップ 0x1e はハンドラを登録します (`0x13d5f94 -> 0x26d8c2c -> 0x2bcb8c8 -> 0x2ca5264`)。シーケンスのステップは、`0x26bdcac` が名前の文字列と組にしたファンクタによるもので、次のとおりです:

    LoginRelayServer     looked up before the sequence is built; a missing one returns false
    Matching             the matchmaking, from the TradeMatchmakingConfig record
    DataExchangeStart    the two-round data exchange and its 10.0 s deadline
    OnCancelDataExchange
    OnSuccess            the trade scene
    OnFailure            event 8, flow step 0x23 (table `0x397c134`), the leave
    OnCancel
    Cleanup

ステップ 0x18 の 2 つ目のゲートは `0x13de870` で、永続的なネットワークメニューのオブジェクトの `[obj+0x7c] == 1` です。これは、現在のページ (`[obj+0x88]`。ViewTop は `[obj+0x90]` (`0x13de950`)、ViewAlert は `[obj+0x98]` (`0x13de9d8`)、ViewInMatching は `[obj+0xa0]` (`0x13dea28`)。`netm` のレイアウトから `0x13de3cc` が組み立てる) が、その `+0x5bc` に結果 1 を報告したとき、case 0 の更新 `0x13de888` が設定します。これを書き込むのはプレイヤーの入力だけです。InputDecide と InputBack からは 1 (`0x13dc7b4`、`0x13dc7ec`、`0x13dd3ec`。`0x13dc0a4`、`0x13dc1a0`、`0x13dc9a0` で設置)、`button_00` と `button_01` からは 2 と 3 です (`0x13ddcb4`)。これらは `[obj+0x7c] = 2` と `[obj+0x84]` を設定します。最初のゲートである子カウンタは、`0x13d6130` で 0 を読みます。

DataExchangeStart 段階の開始 `0x26c5288` (`0x26be3f0` が組み立て、段階の名前の後に `0x26bde74` から呼ばれる。Matching は `0x26be354`) は、データ交換のオブジェクトを `[step+0x118]` に格納し、OS の tick (`0x26c539c`) で `[step+0x120]` のストップウォッチを開始します。その更新 `0x26c6988` は、少なくとも 2 つの局のレコードが届き、埋まっているスロットがすべてレコードを持つと完了します (`0x26c6b70`、`0x26c6c04`)。そうでなければ、経過秒数をリテラルの 10.0 と比較し (`0x26c6a94` の `fmov d1, #10.0`。参加要求から 10.2 秒後に計測)、`net_contents::p2p::ErrorLeaveAnyone` (vtable `0x416c628`、`0x26c6d30` が組み立てる) で要求を失敗させます。失敗は `0x13d654c -> 0x13d6384 -> 0x2c43d78 -> 0x2ca0a10 -> Session::LeaveAsync (0x72a6dc)` の順に進み、その後 Error 7 のダイアログが出ます。`0x2c43d78` への入り方は間接的です。それを参照する命令はなく、入口でのフレームのたどりでは、戻り先アドレス `0x12b37fc`、`0x12b23d0`、`0x2c227c0`、`0x26be9b0`、`0x13d63d0` が得られました。検索をしているエミュレートした本体で、データ交換のレコードを控えた参加者がいた場合、失敗 (`0x26c6d30`、`0x13d6384`、`0x2c43d78` の順) は席に着いてから 11.2 秒後に、その順で動きました (ストリームは 1.17 秒後に開きました)。type 7 は、その 0.07 秒後に参加者へ届きました。`0x26d4ae8` は、結果のコールバック `0x26d4aa0` の中にあります。このコールバックはエラーを `gflnet::request::Error::Timeout` と照合し、次に `ErrorLeaveAnyone` (`0x26d4e04`)、次に `gflnet::npln::NplnResult` と照合します。どのエラーもここを通ります。この段階は、確立したセッションの上でのみ始まります:
`[exchange+0x80]` の局オブジェクトがセッション確立を報告し、かつ自分の局インデックスが 0xfd 以外でなければ、`0x26c564c` は false を返します。`Error::Timeout` を生成するのは、ウォッチャー `0x2bdb754` だけです。これは、マッチメイキングの 2 つの WaitMember 段階で `0x2bda8cc` によって起動されます。1 つ目は 25000 ms (`0x2bda24c`、要求 `0x2bcd394`、目標 2)、2 つ目は `3000 + rand % 1000` ms (`0x2c491b8`、`0x2c4874c`。目標はマッチメイキングのレコードから) です。WaitMember 段階は、セッションのメンバー数 (vfunc `+0xd8`) が目標バイト `+0x88` に達すると完了し (`0x2c1a8f0..0x2c1a920`)、タイマーは延長されません。2 つ目の段階の目標は、レコードの `+0x22` のハーフワードです (`0x2c48a28` の `ldrh w28`。待機オブジェクトの `+0x88` に `0x2c48cf4` で格納)。検索をしているエミュレートした本体で、コード 00000000 の下でこれは 2 を読みました。vfunc は、3 つのセッションドライバの vtable (`0x4197120`、`0x4197310`、`0x4197cf0`) のすべてで `0x2bcbdb4` です。これは `Session+0xd0` にある Pia セッションのメンバーリストのサイズ `[Session+0xe0]` を返します (`0x72ab78`)。このリストは、ローカルの局 (セッション開始時に追加。`0x72ad4c`) と、セッション参加イベントごとに 1 エントリを持ちます。ホストでは受け入れた参加要求 (`0x737608`、イベントは `0x7378bc`)、参加者では type 5 の更新の各局 (`0x738bc0`、`0x738f08`) です。LDN に関連付けただけの局や Net 0x11 を送っただけの局は数えられません。離脱イベント (`0x735cb8`) がそれを削除します。

局が 1 つもいない検索は、そのタイマーでホストし直します。コード 00000000 の下で検索をしているエミュレートした本体では、どのネットワークも同じ経過で終わりました。WaitMember の期限切れ (`0x2bdb7a0`)、その 0.3 秒後の `0x2c4ee60` での離脱要求、さらにその 0.3 秒後の `Session::LeaveAsync` (`0x72a6dc`) です。その後 LDN ネットワークは破棄され、新しいセッション ID と、バイト単位で同一の広告データを持つ新しいネットワークが作られます。ブレークポイントを仕掛けずに 32 個のネットワークを観察したところ、ネットワークは 2.43 から 4.33 秒ごとに作られ (中央値 3.23 秒)、2 つの間で 0.25 から 0.5 秒ネットワークが見つからないことがありました (21 個のセッション ID はすべて異なっていました)。そのため、参加する局がメンバーとして数えられるまでに残されているのは、1 つのネットワークの `3000 + rand % 1000` ms のうちの残りだけです。

検索をしているエミュレートした本体で、`bin/pla_join.py` を IP 経由で参加させたとき、ホストの WaitMember は、席に着く 1.4 秒前に、カウント 1 を目標 2 と比較しました (`0x2c1a904`、w0 は 1、w8 は 2)。参加者の変数 ID は、席に着いてから 0.09 秒後に参加応答とともにメンバーリストに入り (`0x7292f4`)、10.0 秒のストップウォッチは、席に着いてから 1.19 秒後に開始しました (`0x26c539c`)。その後、2 ラウンドのデータ交換が完了し、席を保っていた 29 秒の間に移行中の 0x11 は来ませんでした。そのため、席に着いたホストの枠は 10.0 秒の締め切りで終わります。ストップウォッチはマッチメイキングが戻った後に始まり、その失敗はセッションをホスト移行付きで離脱させます。完了コールバックは `[request+0x90] -> 0x26d69e8 -> 0x26d6a88` です。

DataExchangeStart 段階は、メッシュ参加の後に、Stream Broadcast Reliable (0x81、ポート 0 と 1) で 2 ラウンドのデータ交換を待ちます。各局は type 0x0f のメッセージでストリームを開き、フラグ 0xa0 の下で 44 バイトの `0000002c ffff` メッセージで ACK し ([本体のネットワークへの参加](#joining-a-consoles-network))、先頭が `484b6264` の 64 バイトのペイロードを持つ 74 バイトの type 0x1f のコンテンツレコードを 1 つ送ります。この段階は、相手の 2 ラウンド目のレコードで完了します (受信の 17 ms 後に計測)。そして `OnSuccess` (`0x26d5f64`) をキューに入れます。ストリームを ACK するだけのホストは、タイムアウトになります。参加側の本体は、催促されずにストリームを開き、ホストのものの後 (ホストのレコードの 86 ms 後に計測) にコンテンツレコードを送ります。ホスト側の本体は、参加者のストリームが開いたときに、先にレコードを送ります。交換ボックス (399 バイトの type 7 レコード) は、その後 0x7c で届きます。

メッセージは、ペイロードの終わるところで終わります。この帯ではメッセージを 4 バイトに揃えません (5.27-5.45 では揃えます)。パディングはパケットだけです ([パケットの読み書き](#reading-and-writing-a-packet))。本体のストリーム開始に応答するホストは、1 つのパケットに 2 つのメッセージをまとめます。ポート 0 のレコードと、続けてポート 1 の自分のストリーム開始です。後者は、サイズ、プロトコル、ポートを指定し、メッセージフラグを引き継ぐヘッダーを付けます。`bin/pla_host.py` は、そのまとまりを参加ごとに 1 回送ります。電波上で失われると、本体は 10.2 秒のタイムアウトで Error 7 を表示します。

| プロトコル | ヘッダーの宛先 | フッター |
|---|---|---|
| Session、Clone Clock、Reliable | 相手の変数 ID | なし |
| RTT、Stream Broadcast Reliable | mesh の宛先 0x0001 | 受信者の変数 ID (平文) |

ヘッダーで相手の変数 ID 宛になっている 0x81 メッセージは、ゲームには届きません。64 バイトのコンテンツペイロードは、同じセーブどうしのペアの両方向で、送信元の局インデックスを除いて同一です。これは 139 バイトのレコード (`pokeldn.pla.data_exchange`) を zlib (4 KB ウィンドウ、レベル 5) で圧縮したものです。Pia の StreamData ヘッダー ([プロトコル 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)) の下の 1 つのチャンクで、セーブの 0x80 バイトの MyStatus ブロック (PKHeX `MyStatus8a`) を保持します:

    +0x00  1   StreamData kind, 1: the first chunk
    +0x01  1   transfer id, 0
    +0x02  1   percent of the block delivered, 0x64
    +0x03  4   zero
    +0x07  4   big-endian u32 0x80, the bytes that follow
    +0x0b  128 the MyStatus block: trainer id pair +0x1b, version +0x1f (47), gender +0x20,
               language +0x22, UTF-16LE name +0x2b

Pia はヘッダーを書き出します (シリアライザ `0x7533e8`、チャンクループ `0x7529f8`)。ゲームは、ブロックだけを `0x26bfd28` の `0x753554(stream, exchange + 0xa0, 0x80, 0)` に渡します。これは `0x26c564c` がステップ自身のコピー (`0x1024038`。ブロック自身のシリアライザで、ブロックはオブジェクトの `+0x68` にあります) からブロック全体をコピーした後です。受信するプレイヤー向けに作られたギフトは、本体のトレーナー情報を読みます (`data_exchange.read_trainer`、[受け取るプレイヤー向けに作られたもの](gift_simulated.md#made-for-the-receiving-player))。

参照レコードでは、ブロックの他の 0 でない 2 つのフィールドは 32 ビットです。製品版のセーブのレコードには、さらにレコード +0x60 に 22 文字のアカウント識別子、レコード +0x7d に 1 が入ります:

- +0x3c (レコード +0x47) は、導入画面の 4x2 の `grid_player` からプレイヤーが選んだ見た目です。列 + 4 x 行 で決まります (`0x1348df8`、セッター `0x1023f94`)。同じ選択で性別も決まり、列 2 と 3 は女性になります (`column > 1`、`0x134d728`)。さらにスキンも決まります。8 つの値は `p1skin001` (0)、`p1skin004` (1)、`p2skin001` (2)、`p2skin004` (3)、`p1skin002` (4)、`p1skin003` (5)、`p2skin002` (6)、`p2skin003` (7) です。`p1` は男性のプレイヤー、`p2` は女性のプレイヤーです。ゲームはこれを `0x1023f9c` で読み戻し、プレイヤーの写真 `photo_player_0N` とエンドクレジット `credit_end_0N` に使います。参照レコードの 5 は、3 番目のスキンを持つ男性プレイヤーです。性別 (+0x15、レコード +0x20) と列が食い違う見た目は、どのセーブからも生成されません。`bin/pla_host.py` と `bin/pla_join.py` は、`--gender` で指定された性別、アプリの設定から得た性別、そして同じスキンの見た目を持つ参照レコードを送ります。男性は 5、女性は 7 です (`data_exchange.build_record`)。
- +0x50 (レコード +0x5b、PKHeX の `Unk_0x50`) は 1 です。ブロックの初期化子が書き込みます (`0x10230e4` の中の `0x1023144`。ここでバージョン 47 も書き込まれます)。このクラスには、これにアクセサはありません。

Game Freak は、これらの名前を、オフセット基底 `0xcbf29ce484222645` からの FNV-1a 64 でハッシュします。スキンは、`0x1348cbc` がキーにする 8 つのハッシュと一致し、`grid_player` は `0x13497fc` が開くレイアウトと一致します。

## ゲームの reliable チャンネル

データ交換の後、交換のフローは `0x13d5cac` に進みます。ここでは、ゲームのネットワークオブジェクトの `[net+0xb8] > 1` を検査します。このオブジェクトは、ゲームが 0x7c で読んだ内容に応じて進みます。状態 0 から 1 は `0x26d9170` を通ります。1 から 2 は `[net+0x78]` で行われます。`[net+0x78]` は、セレクタ 1 の受信ハンドラ `0x26da310` が設定します (ジャンプテーブルのインデックス 1、`0x26da3a4`)。

ディスパッチャ `0x2ca4a88` は、メッセージの 8 バイトのキーを各チャンネルの `+0x6c` と照合し、本体を渡します。チャンネルは 2 つあり、どちらも `0x2bcb8c8` で登録されます。交換ボックス用はキー `00 00 00 00 00 00 00 00` (`0x26d8c2c`)、フェーズのプロトコル用はキー `01 00 00 00 00 00 00 00` です (`0x26d7aa0`)。

ポート 0 とポート 1 は、どちらも Reliable のインスタンスです。`0x2bba180` のプロトコル列に `0x7c000000` と `0x7c000001` として登録されます (ストリームのブロードキャストは `0x80000000` と `0x80000001`)。ハンドルは、ポートをインデックスとして `0x4308a80` のテーブルに入ります (`0x4308a84` が 0x7c のポート 1)。`0x2ca4a88` は、0x68、0x7c、0x80 のポート 0 を読みます。0x7c のポート 1 は、下のチャンネルテーブルを通して読まれます。

両方のポートは、`reliable5` のストリームで開きます (宛先ビットマップなし、相手の変数 ID 宛、シーケンス 1、メッセージ開始・メッセージ終了・初期化のフラグ付き)。各局は、相手のメッセージを 1 エントリで ACK し、同じポートで同じメッセージを返します:

    port 0    key eight zero bytes      body 0100        the host opens it
    port 1    b9 01 01 b9 02 b9 02 00 00 01              the joiner announces the zero key open

### 確認応答

`ReliableSlidingWindow` (vtable `0xc5b4d98`) は、vf12 `0x74ee1c` で確認応答を組み立てます。ID は受信ウィンドウの `+0x50` で、その先に保持しているエントリごとに 1 ビットを、16 バイトのマスクに立てます (`0x74ef18..0x74efb8`)。`[window+0x54]` が立っている間は、マスクは空です。vf13 `0x74efbc` がこれを適用します。AckMessage を解析し (`0x742da0`)、ペイロードが `2 + 21 * count` バイトで、かつエントリのストリームバイトがウィンドウの `+0x36` と一致する場合を除いて破棄します。そして `0x74f09c` で `0x74f0ec(window, station, ack_id, mask)` を呼びます。送信エントリは 0x5d0 バイトで、シーケンスは `+0x24`、局ごとの保留ビットマップは `+0x2c` にあります:

| エントリのシーケンス | 確認応答した局の保留ビット |
|---|---|
| `ack_id` より小さい | クリア (`0x74f274`) |
| `ack_id` と等しい | 保持 |
| `ack_id` より大きい | マスクのビット `seq - ack_id - 1` が立っていればクリア。オフセットは 0x7f まで (`0x74f280..0x74f2a8`) |

| `ack_id` | 効果 |
|---|---|
| 0 | 何もしない (`0x74f0fc`) |
| ウィンドウの基点より小さい | `[window+0x4b8]` を設定して戻る (`0x74f17c`、`0x74f2d0`) |
| `base + count` (count は `[window+0x32]`)。最後に送った次 | すべて解放 |
| `base + count` より先 | `0x20000000` を付けて `[vt+0x30]` に渡される (`0x74f18c..0x74f1c0`)。vf6 `0x74f2e8` は、両方のウィンドウクラスで素の `ret` なので無視される |
| `0xffff` | ウィンドウ全体に適用する (`0x74f104..0x74f11c`) |

比較は、2 つの 16 ビット ID の 32 ビットの差で行います。1 つのストリームで 65536 個のメッセージを送った後は、ウィンドウより先の ID が、ウィンドウより小さいものとして読まれます。

ID は累積です。n+2 を ACK すると、n が届いたかどうかにかかわらず n が解放されます。本体は、連続した区間の 1 つ先を ACK します。マスクには、保持しているエントリが入ります。これは 4 つのリトルエンディアンの語です (`0x742f00` で memcpy され、`0x74f2a0` が語ごとに読みます)。ビット `seq - ack_id - 1` は、128 ビットのリトルエンディアン整数のビット n です (`pokeldn.ldn.reliable5.build_mask`)。製品版の本体は、ホストの 0x7c データを数十ミリ秒以内に ACK します (計測で 17 から 67 ms)。

受信側は、フラグを読む前に、すべてのメッセージの最小保留フィールド (確認応答を含む) で、ウィンドウの基点を動かします (`0x74c250` が `[x0+0x20]` に格納し、基点 `+0x18` は空のスロットを、埋まっている最初のスロットまで進めます (`0x74c2f0..0x74c2f8`)。フラグの振り分けは `0x74c3ac`)。より小さい値では動きません (`0x74c25c`)。未 ACK のメッセージより先に宣言された最小保留は、その再送を基点より下に落とさせて破棄させます。製品版の本体の ACK は、その ID より小さい値を宣言します (ACK 8、最小保留 6)。

`bin/pla_host.py` と `pokeldn.pla.joiner` は、`pokeldn.ldn.reliable5` (`SendWindow`、`ReceiveWindow`) を使います。各 0x7c メッセージは ACK されるまで保持し、0.4 秒後に同じシーケンス ID と新しい nonce で再送します。最小保留としては、自分の未 ACK の最小シーケンスを上限として宣言します。(キャプチャでは、ホストとして動く本体のポート 0 の番号が、参加者より 1 つ先行していました。それ以上を宣言すると、その基点が参加者の未送信フェーズ 6 を越えてしまいます。) マスクを付けて、連続した区間の 1 つ先を ACK し、順序どおりに 1 回だけ配送します。参加者の 0x81 メッセージは 1 秒ごとに再送します。本体がポートで最初に送る 0x7c メッセージは、シーケンス 1 を持ちます (記録した 66 ポートすべて)。

本体は、0x7c と 0x81 のデータを同じように、`0x74c9c8` を通して再送します (tick は、0x81 が `0x7419ec`、0x7c が `0x74a27c` と `0x74a2f8`)。基点から 127 までのすべてのエントリのうち、保留ビットマップ `+0x2c` が 0 でなく、締め切りを過ぎたものが対象です (`0x74cd10..0x74cd80`。0x81 は `0x742194` を通り、保留中の局にだけ送ります)。締め切りは、現在時刻 + 33 ms + 最大の往復時間の 1.4 x です (`0x74d06c`、float `0x3fb33333`。`0x74a784` では 33 ms)。回数 `+0x14` には再試行の上限がありません。保留ビットは、ウィンドウ内の ACK (`0x74f1f4..0x74f204`) か、局の離脱 (イベント 1、`0x7411cc` から `0x74b528`) でのみクリアされます。局が参加すると、すべての締め切りがゼロになります (`0x74b358`)。ウィンドウより先の ID でしか答えない相手には、本体は永遠に再送し続けます。

## ポート 1 のチャンネルテーブル

0x7c のポート 1 は、チャンネルテーブルを運びます。各局は、どのハンドラキーを開いているかを告知します。局がキーで送るのは、相手がそのキーを開いたと告知した後だけです。

ディスパッチャの初期化 `0x2ca36f0` は、0x298 バイトのオブジェクトを組み立てます (vtable `0x41997d8`)。ポートのバイト `+0x70` は 1 で、ディスパッチャの `+0x20148` に保持されます。毎フレーム、ポーリング `0x2ca82d0` が 0x7c のポート 1 から `0x2ca9800` に受け取り、送信関数 `0x2ca83dc` を実行します。0x18 バイトのエントリからなるテーブルが 2 つあります。各エントリは、`+0x00` に 8 バイトのキー、`+0x08` に局のビットマスクを持ちます:

| テーブル | 保持するもの |
|---|---|
| `+0xa0` | 局自身のチャンネル。チャンネルが存在する間、エントリの `+0x10` のバイトが立ち、ビットマスクは告知済みの局を示す |
| `+0xd8` | 告知された相手のチャンネル。ビットマスクは、そのキーを開いたと告知した局を示す |

送信関数は、各ポーリングの最初に実行されます (`0x2ca8310`)。ダーティフラグ `[obj+0x90]` が立っている間です (`0x2ca83fc`)。自分のテーブルを局のビットごとにたどります。ビットが立っていない既存のチャンネルは、開いたと告知してビットを立てます。ビットが立っている破棄済みのチャンネルは (`0x2ca86c4`)、閉じたと告知してビットを下ろします。チャンネルのデストラクタは、そのキーを付けてインターフェースのスロット 1 `0x2caa12c` を呼びます (`0x2ca3168..0x2ca3178`。テーブルのスロット 13 `0x2caa0d4` も同じ本体です)。これは `+0x10` をクリアし、ダーティフラグを立てます。

受信側 `0x2ca9800` は、保留中のポート 1 のメッセージごとに、ポーリング `0x2ca83a8` から 1 回ずつ実行されます (`0x2ca8398..0x2ca83d4`)。送信元の局インデックスを、セッションの `[vt+0x38]` で解決します (`0x2ca9854`)。0xfd なら破棄し、2 以上なら中止します (`0x2ca9df0`)。キーごとの処理は次のとおりです:

| 相手のテーブル | 開く | 閉じる |
|---|---|---|
| キーを持つ | 局のビットをマスクに OR する (`0x2ca9a6c`)。同じキーを重ねて開いても何も変わらない | ビットを AND で落とす (`0x2ca9ae4`)。どの局のビットも残らなければ、末尾を前に詰めて `[obj+0xe0] -= 0x18` とし、エントリを消す (`0x2ca9b14`) |
| キーを持たない | 局のビットを付けてエントリを追加 | ゼロのマスクを付けてエントリを追加 |

どの分岐もゲームを呼び出さず、相手のテーブル以外には書き込みません。収集関数 `0x2ca8f58` (毎ポーリング、`0x2ca8318`) は、ゼロのマスクのエントリを消します (`0x2ca9060..0x2ca90c8`)。また、`[obj+0x98]` のどのビットも立っていなければ、テーブルを空にします。局の離脱経路 `0x2ca90e0` (`0x2ca4a48` から) は、局のビットを `[obj+0x98]` と、すべてのマスクからクリアします。相手のエントリを消すのは、ほかにはありません。

チャンネルを作成するとき (`0x2bcb8c8` -> `0x2ca5264` -> コンストラクタ `0x2ca3024`。それぞれ次の 1 つだけが呼びます) は、テーブルのインターフェース (`[dispatcher+0x20148]` + 0x68、vtable `0x41998c8`) を、チャンネルの `+0xb8` に格納します (`0x2ca30d0`、`0x2ca5acc` で組み立て)。これは `+0xa8` の弱参照の後ろに置かれます (呼び出しの前に使用カウント `+0xc` を検査)。そのうえで、キーを付けてインターフェースのスロット 0 `0x2caa0cc` を呼びます (`sub x0,x0,#0x68; b 0x2ca9dfc`、テーブルのスロット 12)。`+0x10` がクリアなら、それをセットします (`0x2ca9e78`)。セットされていれば戻ります (`0x2ca9e74`)。なければ `{key, 0, 1}` を追加します (`0x2ca9e90..0x2ca9ec0`)。1 つ目と 3 つ目はダーティフラグを立てます (`0x2caa034`)。(`0x2ca3c6c` の `stp xzr,xzr,[x23,#0xb8]` が、テーブル自身の `+0xb8` をゼロにします。) 相手のテーブルへの問い合わせは次のとおりです:

| 関数 | スロット | 答え |
|---|---|---|
| `0x2ca9218` | インターフェース 2 | 自分のテーブルがキー K を持つか |
| `0x2ca92e0` | インターフェース 3 | スロット 10 の判定。ハンドルで与えられ、`[vt+0x38]` で解決された局に対して |
| `0x2ca93d4` | インターフェース 4 | スロット 10 の判定。局インデックスで |
| `0x2ca958c` | インターフェース 5 | テーブルオブジェクトに対する `0x2ca9448` |
| `0x2ca9360` | テーブルの vtable `0x41997d8` スロット 10 | 相手のテーブルが、局のビット i を付けてキー K を持つか |
| `0x2ca9448` | テーブルのスロット 11 | K を告知した局は、自分以外のすべての局か |

どのチャンネルの送信も、`+0x6c` にあるキーを付けて `+0xb8` 経由でインターフェースのスロット 3 を呼び、yes のときだけ送ります。フェーズの送信は `0x2ca34e0` を通します (`0x26d7d8c` の中の `0x26d7e00`、`0x26d7e84` の中の `0x26d7ef8`)。交換ボックスの送信は、`0x26d9200`、`0x26d92f0`、`0x26d950c`、`0x26d9688`、`0x26d980c` (セレクタ 5)、`0x26d9a1c` にインラインで実装されています。相手のテーブルは、ポート 0 の送信もゲートします。それぞれ自分のキーで判定します。これは、ホストがポート 1 で沈黙している間、交換画面が表示する待ちです。インターフェースのスロット 2、4、5 は、`+0xb8` を通した呼び出し箇所がありません。

テーブルのポインタは `[dispatcher+0x20148]` にあります (最後のフィールドで、確保は `0x20150`、`0x2bcac00`)。ディスパッチャの中だけで使われます。初期化は `0x2ca3d24`、デストラクタは `0x2ca3f88` (`0x2ca3f48` の中)、局の参加は `0x2ca4774` (`0x2bcb2b8` からの `0x2ca4574`。ビットを `[+0x98]` に OR し、ダーティを立てる)、局の離脱は `0x2ca4a38` (`0x2ca90e0`)、フレームのポーリングは `0x2ca5020`、チャンネルの作成は `0x2ca5284` (テーブルのスロット 8 `0x2ca91cc`) です。もう 1 つのコピーは、各チャンネルの `+0xb8` にあります (インターフェースのスロット 0、1、3)。ほかに相手のテーブルを読む箇所は見つかりませんでした。vtable `0x41997d8` を参照するのは `0x2ca3c18` と `0x2ca7f2c` だけで、`0x41998c8` を参照するものはありません。`0x2ca3000..0x2cab000` の中で `+0x48/+0x50/+0x58` を通す呼び出しは、`0x2ca92c0`、`0x2ca9340` (スロット 10)、`0x2ca9490` (セッション) だけです。`0x2ca6000..0x2cab000` への外部からの呼び出しは、`0x2caa960..0x2caafec` にしか届きません。スロット 9 `0x2ca9264` を呼ぶものはありません。

メッセージは、ゲームのタグ付きシリアライズです。0x80 未満の符号なし整数は、そのまま 1 バイトになります。タグ 0x80、0x81、0x82、0x83 は、それぞれリトルエンディアンの 1、2、4、8 バイトの値の前に付きます (`0x2661ec4`、`0x26619cc`、`0x2661f78` が u32、u64、u16 を書き込みます)。サイズテーブル `0x397dfcc` は、0x84 から 0x87 に同じ幅を与え、0x88 は 4 バイト、0x89 は 8 バイト、0xb5 から 0xbf は 1 バイトです。0xb9 はタプルを開き、その後にフィールド数が続きます。

    b9 01              a tuple of one field, the list
    NN                 the number of entries
    per entry:
      b9 02            a tuple of two fields, the key and its state
      b9 02 LO HI      the key as two u32, low word first
      01 | 00          1 open, 0 closed

交換の間、本体は次の 3 つを送ります:

| メッセージ | 意味 | タイミング |
|---|---|---|
| `b9 01 01 b9 02 b9 02 00 00 01` | 交換ボックスのキーの open | ポート 1 の open とともに、交換のステップに到達したとき |
| `b9 01 01 b9 02 b9 02 01 00 01` | フェーズキーの open | 確定の後、`0x26d7aa0` がフェーズのチャンネルを作るとき |
| `b9 01 01 b9 02 b9 02 01 00 00` | フェーズキーの close | 交換が書き込まれた後 |

`pokeldn.ldn.channel_table` がこれらを組み立て、解析します。ホストは、各 open に対してキーごとに 1 回、自分の open で応答します。close には応答しません。close を送り返すと、本体の相手エントリのうちフェーズキーのものが消えます (相手のテーブルを読む処理はないので、交換の中では無害です)。残りのエントリは次の交換にも使われます ([1 つのセッションでの 2 回目の交換](#a-second-trade-in-one-session))。

## 交換ボックス

両方のチャンネルが開いた後、ゲームのメッセージは、ゼロのキーの後ろのポート 0 を通ります。受信ハンドラ `0x26da310` は、セレクタとカウンタを読み、バイトテーブル `0x397e388` で振り分けます。7 より大きいものは破棄します。

    1   ready                0x26da3a4   sets [net+0x78], what step 0x20 waits on
    2   showing a Pokemon    0x26da3f0   stored at [net+0x98] by 0x26da1d8, nothing else
    3   showing no record    0x26da430   -> 0x26d93c8
    4   offering a Pokemon   0x26da3b0   stored at [net+0xb0] by 0x26da23c, phase 0xbc := 3
    5   confirmed            0x26da43c   counter check, -> 0x26da2c0
    6   withdrawn            0x26da458   state 4|5 := 3, phase 0xbc := 2, counters moved
    7                        0x26da49c   counter check, phase 0xbc := 5

ハンドラは、4 番目の引数がパートナーの `[net+0x88]` と一致しない限り中止します。ポート 0 の open のボディ `01 00` は ready (セレクタ 1、カウンタ 0) で、セッションごとに 1 回送られます。

`0x26d9458` (呼び出し元は `0x10fb198` の中の `0x10fb200` だけで、それ自体は `0x110a010` からだけ呼ばれます) は、レコードが null (`0x26d94a0`) または種族が 0 (`0x2b5d3a4` -> `0x2b6849c` で `[pk+0x98]`。`0x3984e57` が最初に置くブロックの最初のハーフワード) のとき、ボディなしでセレクタ 3 を送ります。それ以外は、`0x2b65514` からの 0x178 バイトのボディを付けてセレクタ 2 を送ります (`0x26d9554..0x26d9570`)。レコードは `0x11207f8(ui, box, slot)` から得られます (`0x1109fa0..0x1109fac`)。スロットは `0x111da04` によって `[ui+0x1660]` にコピーされます (`0x11208e4..0x1120910`、`0x111fc18..0x111fc4c`)。空のスロットにカーソルがあると、`03 00` を送ります。セレクタ 3 を受け取ると、`0x26d93c8` は `[net+0x98]` を、新しい 0xb8 バイトの `0x151dc70` オブジェクトに置き換えます。tick `0x26d9094` は、これを読みません。

セレクタ 6 は、提示 (状態 3。自分のセレクタ 4 を送った後。`0x26d95d4` は 2 を要求し、`0x26d9718` が 3 を書き込む) か、確認 (状態 4。自分のセレクタ 5。`0x26d9788` は 3 を要求し、`0x26d9838` が 4 を書き込む) を取り消します。その送信役 `0x26d9898` は、状態 2 と 5 では拒否します (`0x26d98ac`: `cmp w8,#2; ccmp w8,#5,#4,ne`)。そのうえで、カウンタ `[net+0xf8] + 1` を送り (`0x26d9918`)、`[net+0xc0]` をクリアし、状態 2 にします (`0x26d9a54`)。さらに `[net+0xf8]` と `[net+0xfa]` を上げ、フェーズ 4 または 5 を 3 に戻します。受信側 `0x26da458` は、カウンタを `[net+0xfa]` に格納し、`[net+0xf8]` を上げ、`[net+0xc0]` をクリアし、フェーズを 2 にし、状態 4 または 5 を 3 に戻します。何も送りません。エコーされた 6 は、本体の確認を取り消します。

セレクタ 2 と 4 は同じボディを持ちます。2 は局がボックスに入ったとき、4 はプレイヤーが提示したときです。フェーズを動かすのは 4 だけです。提示に対して表示で応答するホストは、本体に空のパートナーの六角形を残し、エラーは出しません。`pokeldn/pla/trade_box.py` はセレクタを反映します。

ボディは `0x26dac6c` (セレクタ)、`0x26662fc` (カウンタ)、`0x26dacbc` (レコード) で読まれます。0xbc がレコードを導入し、`0x26da3b0` は手で検査します。

    0x00  1   the selector
    0x01  1   the counter, 0 on both record-carrying selectors
    0x02  1   0xbc
    0x03  1   0x81
    0x04  2   the record's length, 0x178
    0x06  376 the record

9 バイトのヘッダーの下に 390 バイトのペイロード、宛先ビットマップなし、フラグ 0x07 (アプリケーションデータ、メッセージ開始、メッセージ終了。初期化ビットなし、zlib ビットなし)、シーケンス 2 です。

メッセージはセーブだけに依存します (ホストやセッションキーが違っても同一)。そのため、キャプチャを再生できます。

レコードは Gen-8 の個体です (`pokeldn.gen8` のヘッダー、LCG、ブロックの並べ替え、16 ビットのチェックサム)。ブロックは 0x58 バイトで、保存時は 0x168 バイト、パーティ内では 0x178 バイトです。`gen8.BLOCK_ORDER[(ec >> 13) & 31]` は、復号するときはそのまま、暗号化するときは逆に適用されます。チェックサムではこの 2 つを区別できませんが、名前では区別できます。そのまま読むと、ニックネームは 0x60 (2 番目のブロック)、トレーナー名は 0x110 (4 番目) にあります。逆に読むと、どちらも 1 ブロック手前にずれます。0x0c のトレーナー ID とトレーナー名は、データ交換が運ぶプレイヤー ID と名前です。

## 交換の確定

「交換する」ボタン (Trade it) は、ゼロのキーでセレクタ 5 とカウンタ `[net+0xf8]` を送ります。送信役 `0x26d9770` は `[net+0xb8] == 3` (自分の提示を送信済み) を要求し、4 に設定します。受信側 `0x26da2c0` はフェーズ `[net+0xbc]` を 4 にします。また `[net+0xb8]` がすでに 4 であれば、`[net+0xc8]` をクリアして、その中に割り当てます。2 番目に確定する局は、ここから続きます。セレクタ 5 と 7 は、`[net+0xfa]` より小さいカウンタを破棄します (`0x26da440`、`0x26da4a0`)。

確定の後、本体はポート 1 でフェーズキーの open を告知します (初期化フラグなし)。ホストもそれを告知するまで、本体はその上で何も送りません。そうでなければ、交換画面はフェーズ 5 で待ちます。

## 交換オブジェクト自身の状態機械

`[net+0xb8]` は、ステップ 0x20 が検査する状態です。tick `0x26d9094` がこれを動かします:

    0     if [net+0x90] is set, 0x26d9170 -> state 1
    1     once [net+0x78] is set, one 64-bit store of 0x200000002 puts the state at 2 and the
          phase [net+0xbc] at 2 in the same instruction
    3, 4  while [net+0xc0] is set: read the stopwatch at [net+0xc8], and once [net+0xd0] is past
          1.5 seconds and the phase is 4 or 5, 0x26d9254 sends selector 7 and the state becomes 5
    5     no case. The object is finished

状態 5 (提示済み、両方が確認済み) では、セーブには触れません。下のジョブが交換を実行します。

## 交換の制限

交換の制限は、セーブブロック `0x96993D83` にある、分単位の u64 のカウントです。`[game manager+0x2b8]` にあるオブジェクトの `+0x70` フィールドです (マネージャは `[0x4279560]` 経由、アクセサは `0x1048f94`。vtable は `0x40f2048`、コンストラクタは `0x102500c`)。そのメソッドは次のとおりです:

    0x102518c  clear
    0x1025194  set
    0x102519c  decrement, stopping at 0
    0x10251b0  read
    0x10251b8  non-zero

登録 `0x1024d5c` (スロット `0x40f2098`) は、3 つのフィールドをセーブブロックに結びつけます。ブロックは、`0xff0ee8` が u32 のキーで 0x30 バイトのエントリを二分探索して見つけます (`0xff0f3c..0xff0f70`):

| フィールド | ブロック | 型 |
|---|---|---|
| `+0x68` | `0xAFA034A5` (キーは `0x3978f78`) | bool (`0xfddf30`) |
| `+0x70` | `0x96993D83` (キーは `0x3978f7c`) | u64 (`0xff0ee8`) |
| `+0x78` | `0x24E0D195` (`0x1024f30` で組み立て)、0x2F2 バイト | `0x1024ee4` |

PKHeX の `BlankBlocks8a.cs` も、サイズについて一致しています。セーブでは、`0x96993D83` は型 11 で 0 です。`0xAFA034A5` は false の bool です。`0x24E0D195` は、ゼロのフラグバイトの後に、直近に交換したレコードを持ちます。

`+0x78` のバイトは、まだ配置されていない受信レコードを示します。`0x10251c8` がこれを設定し (`0x102520c`)、レコードを `+0x79` にコピーします。与えられた場合は、交換後の形のレコードを `+0x1f1` にコピーします (フラグ `+0x369`)。唯一の呼び出し元は、ジョブの状態 6 にある実行役の vf `+0x58` です (`0x26ddc64`)。両方に同じ種族を `0x2b5be48` が返すときは、交換後の形を渡しません。`0x26dcc74` がこのバイトを読みます (`0x26dccfc` の `0x102527c`)。設定されていれば、レコードを配置し (`0x10325a0`)、図鑑に登録し (`0x10342b0`)、バイトをクリアして (`0x26dcdc8` の `0x1025268`)、要求の種類 3 で保存します。キャンセルは、`[executor+0xb0]` が立っているときだけ、これをクリアします (`0x26dd70c`)。`0x26dcc74` は、モード 5 のステップ 10 (`0x110accc`)、モード 9 のステップ 0 (`0x110bc88`)、およびボックスのコード (`0xc17ce0`、`0xc17e8c`) から実行されます。ほかにこのバイトを書き込む箇所はありません。

カウントを書き込むすべての箇所 (テキスト全体の呼び出し索引。ポインタのスロットがメソッドを保持するものはありません):

| 箇所 | 呼び出し元 | 値 | 条件 |
|---|---|---|---|
| `0x26dd9a0` | 実行役の vf `+0x50` `0x26dd910`、ジョブの状態 3 | 10 | 相手の `02 03` の後、どちらのレコードも動く前 |
| `0x26ddaf0` | 実行役の vf `+0x58` `0x26ddaa0`、ジョブの状態 6 | 0 | 交換が適用される |
| `0x26dd704` | 実行役の vf `+0x48` `0x26dd5f8`、キャンセル | 10 | `[executor+0xb0]` が立っているときだけ。これは状態 6 で `0x26ddc6c` が設定する |
| `0x26bd5d0` | ティッカー `0x26bd434` | 1 を引く | 60 秒ごと |

10 を設定した後、vf `+0x50` は `0x12aff48` から保存要求を受け取り、`0x265d420(request, [executor+8], 3)` (`0x26dd9e8`) で武装させます。`0x265d460` が完了を報告するまで状態 3 を保持します。これは、セーブデータの状態機械 `0x10457e4` (`0x265d668`) を動かします。ステップは `0x1048354`、`0x1048558`、`0x10485c0`、`0x1048628`、`0x1048690`、`0x10486f8` で、そのうちの 1 つは `0x298f2f4` を通して `nn::fs::Commit` に到達します。これらが、交換のコードにある唯一の保存要求です。ジョブの状態 3 より前に止まった交換は制限を設定しません。状態 3 から、状態 6 の後の保存までの間に止まった交換は、セーブに 10 を残します。

カウントダウンは、システムリスト `0x42eced0` の中で `0x277c530` が登録します (呼び出しは `0x277cc0c`、`0x277fbb0`。`0x2789df4` が組み立て、コンストラクタ `0x26bd300`、vtable `0x416c2f0`、更新 `0x26bd430` -> `0x26bd434`)。`+0x58` の状態は次のとおりです:

    0  count non-zero -> 2                                          0x26bd4bc
    2  count zero -> 0; else snapshot the count to +0x70 and start a stopwatch at +0x60
       (nn::os::GetSystemTick, ConvertToTimeSpan, 0x26bd534..0x26bd544) -> 1
    1  count changed -> 2; elapsed / 1e9 >= 60.0 (0x26bd5b4) -> decrement (0x26bd5d0) -> 2

10 は、OS の tick で数えたゲームの 10 分間の実行です。時計の設定は関係せず、ゲームを閉じている時間は数えません。ティッカーはフィールドで動きます。制限は、設定されてから 10 分間のプレイでクリアされます (フィールドに置いた製品版の本体で計測した 667 秒)。

`0x13d67b0` は、非ゼロのメソッドの唯一の呼び出し元です (`0x13d67e8..0x13d67f0`)。通信交換の相手選択メニューでは、`0x13d55fc` と `0x13d56ac` (`0x13d55dc` の中。`0x13d53c0` から呼ばれ、`[x0+0xa4] == 3` を検査します。また `0x13d5648` は、`0x13d53dc`、`0x13d5808` から呼ばれます) が、カウントが 0 でないとき `0x500000001` を返します。それ以外は `0x300000001` で、`0x13d65c0` が false のときは `0x400000001` を返します。メニューの更新 `0x13d5344` は `[obj+0xa0]` で分岐します (バイトテーブル `0x397c105`)。結果 `(n << 32) | 1` は、状態 n に移します (`0x13d5404`)。決定のコールバック `0x13ddcb4` は、ペイン `button_00` に 2、`button_01` に 3 を書き込みます (名前の FNV-1a-64。基底 `0xcbf29ce484222645`)。状態 0 からは `0x13d55dc` と `0x13d5648` にルーティングされます (`0x13d5590..0x13d55a0`)。ペイン名から見ると、`button_00` はおそらく「近くの相手」です。各状態の `common/net` ラベル (テーブル `0x397c158`) は、`0x13dbe68` を通して `pane_T_info_00` に付きます:

| 結果 | 状態 | ラベル | 文章 |
|---|---|---|---|
| `0x500000001` | 5 (`0x13d59a4`)。その後 0 に戻る | `matching_win_03` | 今は交換に接続できません。前回の接続が中断されたため、しばらく待ってください (フランス語: "Votre connexion a été interrompue lors de votre dernier échange...") |
| `0x300000001` | 3。その後、6 でマッチメイキング | `matching_win_06` | 中断された交換があると、しばらく交換できないという警告 |
| `0x400000001` | 4 | `matching_win_02` | 交換できるポケモンが 2 匹以上必要 |

## フェーズのプロトコルと、ホストだけが送るメッセージ

ジョブは、キー `01 00 00 00 00 00 00 00` でフェーズを告知します。このキーは、ジョブの作成時に登録されます。告知するオブジェクトは、それぞれフラグとハーフワードからなる 3 組を保持します:

    [obj+0x94] / [obj+0x96]   the phase this station has announced, written by 0x26d7d8c
    [obj+0x98] / [obj+0x9a]   the phase the peer has announced, on receiving selector 1
    [obj+0x90] / [obj+0x92]   written by 0x26d7e84, and on receiving selector 2

2 つの送信役は、書き込むセレクタだけが違います。受信ハンドラ `0x26d7f90` がそれを反映します。セレクタ 1 は相手の組を埋め、セレクタ 2 は 3 つ目の組を埋め、セレクタ 0 は中止します。メッセージは、セレクタとフェーズからなり、フェーズが 0x80 未満のときは、それぞれ 1 バイトです。状態 2 の分岐 `0x26d7e5c(obj, 3)` は、3 つ目の組が 3 を保持するまで待ちます。

セレクタ 2 を送るのはホストです。`0x26d7e84` に到達するのは `[obj+0x78]` の背後だけです。これは、ジョブ作成時に `0x26d7aa0` が一度だけ書き込みます。その値は、局をセッションのホストの局と比較する述語から得られます。参加者はセレクタ 2 を送らないので、そのジョブは状態 2 を、ホストからの応答でのみ抜けます。セレクタ 1 を反映するだけのホストは、両方のポケモンが表示されたまま、電波上に未処理のものがないまま、交換画面が待ち続けます。設定には、`[obj+0x78]` をゼロのままにする出口が 5 つあります。null の引数、null のキャスト、`[vtable+0xd8]()` が 2 を返さないこと、`+0x28` の局数が 2 でないこと、null の局スロットです。

ポートで局が発するすべてのメッセージは、反映されたものも含めて、自分のシーケンスの次の ID を取ります。相手の ID を再利用する反映は、カウントが食い違うと衝突し、ACK はされても破棄されます。

## 完了した交換

本体は 3、6、0xb、0xe を順に告知します。ホストはそれぞれに、同じフェーズのセレクタ 2 で応答し、ジョブを進めます:

    <-  0x7c p0  01 03      ->  01 03   the mirror     ->  02 03   the host's
    <-  0x7c p0  01 06      ->  02 06
    <-  0x7c p0  01 0b      ->  02 0b
    <-  0x7c p0  01 0e      ->  02 0e

最初の `02 03` が届くと (計測で 240 ms 後)、3 つ目の組は 1 と 3 を読みます。アニメーションの後、ボックスは元のパートナーとしてホストのプレイヤーを表示します。セーブファイルが 8 つ変わります。`main`、`main2`、両方のスロットの `backup`、両方の ExtraData ファイルです。

そのあと本体は、新しいセレクタ 2 を送ります (カーソルがどこにあっても)。ホストは、表示と、フェーズキーのクローズ (`b9 01 01 b9 02 b9 02 01 00 00`) で応答し、本体はクローズには応答しません。

## 1 つのセッションでの 2 回目の交換

1 つのセッションには、任意の数の交換が入ります。完了した交換の後、シーンは交換オブジェクトをリセットし、セッションを保ったままボックスに戻ります。

完了した交換の後、シーンは `0x110aa04` で `0x26d8fd0(net)` を呼びます (`[net+0xb8]` が 6 のときだけ)。また、ステップ `[scene+0xb4]` を 0xc に設定します。リセットは次のとおりです:

    0x26d8fec  [net+0xa0], [net+0xa2] cleared           job inputs
    0x26d8ff4  [net+0xa8], [net+0xb0] released          shown and offered records
    0x26d903c  0x200000002 to [net+0xb8]                state 2, phase 2
    0x26d9044  [net+0xc0] cleared                       stopwatch flag
    0x26d9050  [net+0xd8] released through 0x26dade4    the job
    0x26d9064  32-bit zero to [net+0xf8]                both counters

`[net+0x78]` (相手の準備完了) と `[net+0x88]` (パートナー) は保持されます。次のラウンドは、新しいセレクタ 1 なしに状態 2 から始まります。シーンの更新 `0x1109a68` (ポインタは `0x3406990`、`0x40fc090`) はモニターを実行し、その後、`0x3979c5e` (ベース `0x1109b60`) を通してモード `[scene+0xb0]` で分岐します:

| モード | ハンドラ | 内容 |
|---|---|---|
| 0 | `0x1109f00` | ボックス。カーソル、表示、交換の選択 |
| 1、2 | `0x1109b6c` | 何もしない |
| 3、4 | `0x110a65c`、`0x110a694` | |
| 5 | `0x110a7f8` | 交換。ステップごとに (ハーフワードのテーブル `0x3979c7c`、ベース `0x110a858`、ステップ 0 から 13) |
| 6 | `0x110b330` | 相手がいなくなった。エラーなし。メッセージを出し、その後モード 1 (`0x110b408`) |
| 7 | `0x110b468` | セッションのエラー。ステップ 9 でジョブをキャンセル。メッセージを出し、その後モード 9 (`0x110b508`) |
| 8 | `0x110b54c` | ステップ 9 でセッションのエラー。ジョブは 6 から 10 にある。メッセージを出し、その後 `0x115e420(..., 1)` (`0x110b60c`) |
| 9 | `0x110b72c` | 離脱中。ジョブをキャンセルし (`0x110b7ac`)、OS の tick で少なくとも 3 秒待ってから終了 |

交換が完了した後、モード 5 で:

    step 11  0x110a928  UI waits (0xc4cc88, 0x1127ab8, 0x110d8b0, 0xc6a788, 0x26bc6a4), 0x26d9eb0,
                        0x10fb2c4, 0x10fb414, 0x10fb164(..., 1) ([+0x161] = 1), 0x10fb178 (0x110a9e8),
                        0x1126408, 0x1126400, 0x26d8fd0 (0x110aa04), step 12
    step 12  0x110aae0  returns while 0x10fb170 ([+0x161]) is set, UI calls, step 13 (0x110abac)
    step 13  0x110ac80  waits for 0xc4cc88 and 0xc6a610, then 0x110acc4 b 0x110b9f0
    0x110b9f0           UI (0x1120ce0, 0x111fb5c or 0x11152b8, 0xc42438, 0xc4ba88, 0xc428b0), then
                        0x110ba44 str xzr,[x19,#0xb0]: mode 0, step 0

ステップ 11 から 13 のどの呼び出し先も、セッション、チャンネルテーブル、送信には届きません。シーンは、セッションを保ったままボックスに戻ります。ステップ 5 の分岐 `0x110ac9c` は、末尾を `0x110b9f0` と共有します。`0x10fb178` はボックスのコントローラの有効フラグ `+0x164`、`+0x16c`、`+0x174` をクリアし、`0x26d93c4` に末尾呼び出しします。これは `[net+0x98]` を新しい `0x151dc70` オブジェクトに置き換え、何も送りません。

モード 0 は毎フレーム、カーソルを読み (`0xc5294c` ボックス、`0xc4bf2c` スロット、`0x11207f8` レコード)、`0x110a010` で `0x10fb198` を呼びます。これが `0x26d9458` を通して表示を送るのは、カーソルのタプルが `+0x168/+0x170/+0x178` に保存されたものと異なるとき、または有効フラグがクリアされているときだけです (`0x10fb1a8..0x10fb1f0`)。送信後にタプルをキャッシュします (`0x10fb208..0x10fb220`)。クリアされたフラグが、交換の後の新しいセレクタ 2 の原因です。カーソルの移動がネットワークに届くのは、`0x10fb198` を通してだけです。提示 (メニュー結果 0x19、`0x110a098`) は `0x10fb25c` を実行し、`0x26d95ac` (`0x110a24c`) を通してセレクタ 4 を送ります。成功すると、`0x110a260 mov w8,#5; b 0x110a148` がモード 5 のステップ 0 に入ります。

どのモードもステップ 0 で入ります (`0x1109abc`、`0x1109ac8`、`0x1109bac`、`0x110a148`、`0x110a314`、`0x110ae14`、`0x110b408`、`0x110b508`、`0x110b9dc`、`0x110ba44`、`0x110bd98`、`0x110c9f0` の `str x8,[x19,#0xb0]`。`0x11094dc` の `stp w8,wzr` は 7 を使います)。例外は `0x11094a8` で、ボックスコントローラの `+0x160` が設定されているとき (`0x110948c` の `0x10fb15c`) は、モード 5 のステップ 1 になります。

カウンタ `[net+0xf8]` は、そこと `0x26d8c04` でだけゼロにされます。送られた (`0x26d9a60`) か受け取られた (`0x26da468`) セレクタ 6 によってだけ上がります。すべての送信役が `0x26d81fc` を通して直列化します (`0x26d91c8` のセレクタ 1、`0x26d92b8` の 7、`0x26d94d4` の 2 と 3、`0x26d9640` の 4、`0x26d97d4` の 5)。

次のジョブは、シーンのステップ 7 から `0x26d9a90` が組み立てます (`0x110ad34`。`0x26d9354` が 4 を返すとき)。そして、キー 1 で再びフェーズのチャンネルを作成します (`0x26dc398` の `bl 0x26d7aa0`)。そのフェーズは `0x26dc71c` の即値です。`0x26dc978` が 3、`0x26dc7ec` が 6、`0x26dc848` と `0x26dc874` が 0xb、`0x26dc8ac` が 0xe です。撤回なしの 2 回目の交換は、`05 00`、`07 00`、フェーズ、ポート 1 のフェーズキーを開くバイトを、バイト単位で同じに繰り返します。違うのはシーケンス ID だけなので、本体の内容が同じメッセージに 1 回だけ応答する相手は、そのどれにも応答しなくなります。

ホストが本体のフェーズキーのクローズに応答していた場合、2 回目の `01 03` は、ホストがキーを開き直すまでゲートで待ちます。ジョブは状態 1、シーンはステップ 9 にあり、タイムアウトも交換の制限もありません。

状態 1 または 2 で保留されたジョブは、`common/box` の `msg_ui_box_p2ptrd_09` の文言 (英語 "Communicating. Please stand by..."、フランス語 "Communication en cours... Veuillez patienter.") を表示します。これは「交換する」コールバック `0x110c3d8` が、メッセージヘルパー (`[scene+0xc0]`、`0x110c424` の `bl 0x26bcc14`、ラベルのハッシュは `0x110c408..0x110c418`) を通して出します。ヘルパーは、ステップを 6 にします。ヘルパーのクローズ `0x26bcfc0` は、`0x110a84c`、`0x110ac5c`、`0x110ace4` でだけ呼ばれます。`0x1128184(ui, 1)` はキャンセルのプロンプト (`InputCancel`、`0x11281bc`) を表示し、これはステップ 2 と 7 (`0x110ac00`、`0x110ad4c`) でだけ読まれます。

## 交換で書き換えられるもの

交換で送ったレコードは、カーソルがそれに届くと、表示として戻ってきます。受信したレコードは、送ったものと次のフィールドで異なります (レベル 70 のパーティ末尾と一緒に送った、レベル 50 のレコードで 23 バイト):

    0x006  2   the checksum
    0x092  1   the current HP, 235 sent, 192 stored
    0x0b8  26  the handling trainer's name, filled in with the receiver's own
    0x0d3  1   the handling trainer's language
    0x0d4  1   the current handler, set to 1
    0x0d8  1   the handling trainer's friendship
    0x16a  12  the six party stats, recomputed

それ以外はすべて、届いたとおりに保存されます。出会いのレベルがレベルより上なら、そのまま保たれます。書き込まれるなつき度は、種族データ (personal) にある種族の基本なつき度です (ゲンガーとガブリアスは 50)。

各ブロックの開始位置は、`pokeldn.gen8` の位置に、先行するブロックごとに 8 バイトを足したものです。ニックネームは 0x60 (Gen 8 は 0x58)、取り扱うトレーナー名は 0xb8 (0xa8)、トレーナー名は 0x110 (0xf8)、パーティ末尾は 0x168 (0x148) です。ブロックの中のオフセットは、そのブロックに従います。最初のブロックは Gen 8 と同じですが、技 (0x54、PP は 0x5c) は違います。Gen 8 では第 2 ブロックの 0x72 と 0x7a です。2 番目は Gen 8 の値に 8 を足したもの、3 番目は 0x10 を足したもの、4 番目は 0x18 を足したものです。ボールは出会った日付のすぐ後に移動します。

`pokeldn/pla/trade_box.py` と `pokemon.py` は、本体のバイト列を再現します。

## 提示するものの選び方

ホストが提示するレコードは、ホスト自身が組み立てます。ゲームは PKHeX の PA8 を読みますが、測定したオフセットはすべて、それと一致しています。

| オフセット | フィールド | オフセット | フィールド |
|---|---|---|---|
| 0x08 | 種族 | 0x92 | 現在の HP |
| 0x0a | 持ち物 | 0x94 | 個体値 (まとめ) |
| 0x0c | トレーナー ID、32 ビット (パネルには 1000000 の剰余を表示) | 0xa4 | がんばレベル |
| 0x10 | 経験値 | 0xac、0xb0 | 絶対的な高さ、重さ (float) |
| 0x14 | 特性 | 0xb8 | 取り扱うトレーナー |
| 0x16 | オヤブンのビット | 0xee | バージョン |
| 0x1c | 性格値 | 0xf2 | 言語 |
| 0x20 | 性格 (第 3 世代の表。9 はのうてんき) | 0x110 | トレーナー名 |
| 0x24 | フォルム | 0x134 | 出会った日付 |
| 0x26 | 努力値 | 0x137 | ボール |
| 0x3e | オヤブンの技 | 0x138、0x13a | 孵化と出会いの場所 |
| 0x50、0x51、0x52 | 高さのスカラー、重さのスカラー、スケール | 0x13d | 出会いのレベルとトレーナーの性別 |
| 0x54、0x5c | 技、PP | 0x159 | 購入した技の記録 |

`pokeldn/pla/pokemon.py` は、このマップを 4 つのテーブルとして保持します。取得した 47 個のレコードでは、オヤブンのビットとオヤブンの技は同じ 3 体に立っており、それらは 0x50、0x51、0x52 に 0xff を持ちます。スケールは 47 個すべてで高さのスカラーと等しいです。0x94 では、孵化とニックネームのビットがクリアされています。すべてのレコードは、バージョン 47、言語 2、sanity 0、付けられたリボン 0xff を持ちます。

`pokemon.build` は、376 個のゼロバイトからレコードを組み立て、取得したすべてのレコードが一致しているデフォルトの上に、与えられたフィールドを書き込み、チェックサムを書き込みます。マップされていないフィールドはゼロのままです。本体の持つレベル 68 のゲンガーに対して、選んだフィールドだけが異なります。組み立てたレコード (色違い (第 6 世代の色違い値 0)、オヤブン、ニックネーム付き、セーブが一度も持っていない種族で、値はすべてゲームのテーブルから取ったもの) は、送ったとおりに交換でき、そのとおりに表示されます。保存されたものは、送ったものと [交換で書き換えられるもの](#what-a-trade-rewrites) に挙げたフィールドでだけ異なります。ゲームが計算するステータスを持つ末尾だと、変わるのは 14 バイトだけです (チェックサムとハンドラのフィールド)。

セーブがすでに暗号化定数と性格値を持つ受信レコードは、保存されます (ボックスブロック `0x47E1CEAB`)。

`bin/pla_host.py` は、各 `(port, sequence id)` を順番に 1 回ずつ処理し、ACK されていない応答を再送します。表示は、カーソルの移動ごとに届き、取り消された提示は `04 01` として再提示されます。2 回目の交換はメッセージ本体を繰り返すので、本体で重複を除くと、その応答が落ちてしまいます。

### 習得済みの技

0x15d の 8 バイトは、ゲームの習得リストにある 61 個の技に対するビットマップです。並びはリストの順序どおりです。種族が習得できるのは、種族データが許すものだけです (0xa8 の u64)。技の画面 (Pastures Change) では、技は、その習得レベル (`mastery_la`。種族とフォルムごと、learnset の形式) が現在のレベル以下であるか、そのビットが立っているとき、スクロールとして描画されます。レベル 13 のヒコザルでは、スピードスター (20、インデックス 10) は、ビットが立っているときだけ表示されていました。

### ゲームが計算するステータス

`pokeldn/pla/stats.py` は、交換が末尾に書くステータスを再現します。各ステータスは、成長項と基礎項からなります。成長項は `(sqrt(base) * multiplier + level) / 2.5` を丸めたものです。基礎項は、HP では `((level / 100 + 1) * base)` を切り捨ててレベルを足したもの、それ以外では `((level / 50 + 1) * base / 1.5)` を切り捨てて、性格の 110% または 90% を掛けたものです。倍率は、がんばレベルと個体値のバイアス (31 以上で 3、26 で 2、20 で 1) を足した値でテーブルから読まれ、その和は 10 で頭打ちになります。レベル 68、性格 14、ゲンガーの基礎ステータスについて、本体が計算した 12 個の数値で検証しました。完璧な個体値とがんばレベル 10 では 273/210/199/322/345/220、提供元のレコードは 239/136/121/322/304/133 でした (個体値 22 とがんばレベル 9 も 10 に頭打ちになるため、そのスピードは変わりません)。

0xac と 0xb0 の絶対的な高さと重さは、種族の平均値に、各スカラーごとの `(scalar / 255) * 0.40000004 + 0.8` を掛けたものです。高さは高さのスカラーだけで求め、重さは両方の係数を掛けて求めます。計算は 32 ビットの float です。スカラー 111 と 221 を、平均 150 と 405 に当てはめると、146.11766052246094 と 452.38031005859375 になります。これは本体のゲンガーが持つ float です。

基礎ステータス、性別比、特性、経験値曲線、平均サイズ、レベルアップの習得技、PP は、PKHeX が持つゲームテーブルのコピーから得ます。`personal_la` (1 エントリあたり 0xB0 バイト。0x21 のビット 6 がゲーム内の種族を示し、その数は 264 です)、`lvlmove_la.pkl` (技のハーフワードの後にレベルのバイトが並ぶ、16 ビットの BinLinker アーカイブ)、`MoveInfo8a`、`Experience` です。

## Clone Clock と Atomic のプロトコル

この帯では、Clone のファミリーを、6.32 の clone プロトコルとは無関係な別々のプロトコルに分けます: Clone Clock 0x77 と Clone Atomic 0x74。

Clone Clock のメッセージは 18 バイトです。種別、シーケンス、big-endian の u64 の発信 tick、big-endian の u64 の応答側クロック (ミリ秒) からなります。種別 0 は要求で、受信側がマスターの場合を除いて無視されます。種別 1 は応答で、シーケンスを確認し、NTP 風のオフセットを計算して、ClockProtocol の `+0x5c` の状態を進めます (0 はリセット、1 は要求中、2 は同期済み、3 はマスター、4 は待機)。参加する本体は、状態 4 で待機し、いくつか要求を送ってから待ちます。ホストが、シーケンスと発信 tick をエコーし、ホストのミリ秒クロックを載せた種別 1 の応答を返すと、参加側は同期して送信を止めます。

Clone Atomic のメッセージは 14 バイトです。種別 (0 は announce、1 は commit、2 は ack)、世代、big-endian の u32 の要素インデックス (33 未満)、big-endian の u64 の値からなります。要素テーブルは、0x18 バイトの 33 スロットです。世代、状態 (0 は空、1 は保留、2 は commit 待ち)、u64 の値を持ち、`+0x10` には、既知の参加者からの、一致する世代の種別 2 によってだけ書き込まれる、ACK した局のビットマップがあります (参加者テーブルはプロトコルの `+0x78` にあり、ステーション 0 のホストは参加後に 1 を読みます)。要素を作るのは交換シーンだけです (ローカルの announce `0x6e1e48`)。種別 1 と 2 には保留中の要素が 1 つ必要で、ホストの種別 0 の announce は、どのスロットも埋めない種別 2 のエコーを返します。

## パケットの読み書き

`pokeldn/ldn/pia6.py` はバージョン 11 を話します。メッセージのフレーミングは 5.27 から 6.30 のものを使い、`pia5.parse_messages` が変更なしに読みます (フラグ `0x01` は、5.27 では宛先ビットマップを示していました)。

パディングのバイトは、どのレベルでも 0xFF です。メッセージの走査は、存在を示すバイトが 0x00 のとき、直前のメッセージのすべてのフィールドを継承する 1 バイトのヘッダーとして読みます。ゼロのパディングだと、ゲームは 2 つ目のメッセージを解析しようとして失敗し、パケット全体を破棄します (`0x74419c` で拒否)。本体は、暗号化バッファを `0x6f0af8` で 0xFF に埋めます。`0x6e6cb0` はブロックサイズを 16 に設定します。

`pokeldn/pla/` は、パスフレーズ (広告を読むために必要)、ゲームキー、ローカル通信 ID、`session_keys(ssid)` を保持します。`tests/test_pia6.py` は、レイアウト、`crypto.PiaCrypto` との導出の一致、取得した 2 つの広告、および `main` から読み出したすべての定数を固定します。

## ホスト

`bin/pla_host.py` は、タイトル、パスフレーズ、シーン ID、リンクコードを広告します。`pokeldn.pla.build_advertise_data(code)` は、製品版の広告をバイト単位で再構築します (`app_version` 0、`security_mode` 1)。ホストは、受信する各パケットを、自分の SSID から得たセッションキーで認証し、各 Pia メッセージをプロトコル ID ごとに表示します。

    POKELDN_RADIO=esp32:auto ./.venv/bin/python -u bin/pla_host.py --keys PROD_KEYS \
        --code 00000000 --seconds 240

検索画面の本体は、局としてのスキャンと、新しい SSID でのホストを交互に行います (見つけたホストに関連付け、その deauthentication (理由 3) でスキャンが終わります)。周期は約 5 秒で、1 回のスキャンと 2 から 4 回のホストです。関連付けられた参加者は、ホストが Net 0x2C の接続要求 (6.32 のメッセージの `host_pia.build_net_probe`) を送るまで沈黙したままです。応答があるまで 500 ms ごとです。`--no-net-probe` を指定すると、この要求を控えます。

## 本体のネットワークへの参加

参加者は、製品版の参加者の順序で、ホストになった本体に次のメッセージを返す必要があります (Net 0x50 はエミュレートしたホストから)。`pokeldn.pla.joiner` がこれらを送ります。

| ホストの送信 | 参加者の応答 |
|---|---|
| Net 0x11 | シーケンス ID をエコーした Net 0x12。メッセージフラグは `0x11`、ヘッダーの宛先は 0。初回は Session の参加要求 (type 0)、フラグ `0x01`、ヘッダーの宛先 0 |
| Net 0x50 | シーケンス ID をエコーした Net 0x51。ヘッダーの宛先 0 |
| 参加者を指名する Session type 7 | type 8。type 7 が対象として指名する location id、続けてホスト自身のもの |
| Session type 5 | type 6。自分の constant id、2 バイトのゼロ、更新のシーケンス |
| 最初の type 5 | ポート 0 での 0x81 のストリーム開始 `0f00000b 0001 0001 01 00000001 0000000000008000000000` |
| ポート 0 の 0x81 レコード | 確認応答。続けてポート 1 の自分のレコード (フラグ `0x1f`、シーケンス 1、ビットマップ `0x01`)。その後、0x7c のポート 1 でキーゼロを開く (初期化フラグ付き) |
| 0x7c のポート 0 の開始、`0000000000000000 0100` | 同じものを返す。自分のポート 0 のシーケンス 1 |
| 表示または提示 | 自分のもの。同じセレクタとカウンタ |
| セレクタ 5 と 7 | 同じ 2 バイト。7 の後、ポート 1 でフェーズキーを開く |
| フェーズキーの開始 | フェーズ 3、6、11、14 (セレクタ 1)。それぞれホストの応答の後。その後フェーズキーを閉じる |
| RTT の種別 0 | 種別 1。タイムスタンプをエコーし、最後の 2 バイトに要求側の変数 ID |

製品版の参加者は、Net 0x12 をヘッダーの宛先 0 に送ります (108 中 108)。読み取りゲートは、ホストの変数 ID 宛のものを破棄します。エミュレートした本体は、その場合、移行中の 0x11 を 0.5 秒ごとに 4 秒間送り続け、最初の 0x40 を type 7 の 4.1 秒後に送ります。宛先 0 宛なら、0x11 は 1 回だけ送られ、最初の 0x40 は type 7 の 0.10 秒後に続きます (4 席中 4 席)。type 8 が全くない場合は 9.1 秒後です。

type 7 は、本体の WaitMember (3000 + rand%1000 ms、`0x2c491b8`) が、参加要求が受理される前に終わるとき、`LeaveMeshWithHostMigrationJob` から出ます。これはスカーレットと同じです ([docs/sv.md](sv.md#what-decides-a-seat))。`bin/pla_join.py --join-delay 4.5` がそれを引き起こします。本体は、type 8 が届くまで毎秒これを再送します。その type 8 のハンドラ `0x739b08` は、2 つ目の location id が本体自身のものである 25 バイトのメッセージだけを受け取ります。`0x73f0a8` は、ジョブが `+0x68` に保持する目標と最初の値が一致したとき、ジョブの完了フラグ `+0xb0` を立てます:

    08 | joiner location id (12) | host location id (12)

参加者は、ホストが応答すると次のフェーズを送ります。数百ミリ秒後ですが、交換アニメーションをまたぐ場合 (数秒) は除きます。

製品版のホストは、参加者のものが届く前に、各フェーズをセレクタ 1 で告知し、その 0.02 から 0.04 秒後に参加者のものへセレクタ 2 で応答します。フェーズに応答するのはセレクタ 2 だけです。本体自身の `01 0e` に対して、`02 0e` を受け取る前にフェーズキーを閉じた参加者は、`02 0e` を受け取れません。その結果、交換は完了せず、本体は離脱時にエラー 2-AW7KA-0007 を表示し、10 分間の制限を保持します ([交換の制限](#the-trade-restriction))。`bin/pla_join.py` は、`02 0e` でキーを閉じ、交換の後も、本体のプレイヤーが離れるか `--hold` が終わるまで席を保ちます。`--hold-after-trade N` は、最後に待ち行列に入った交換の N 秒後に離れます。同じ席での後の交換は、すべてのステップをバイト単位で繰り返します。そのため参加者は、交換が完了すると応答したステップを忘れ、次の `--offer` を表示します。0x81 の ACK は、ポート 0 と 1 で、約 1 秒ごとに繰り返されます:

    0000002c ffff 0002 01 00000001       header: size 0x2c, lowest pending 2, bitmap 1
    00 02                                type 0 on the first, 1 on every later one; two entries
    00 0002 0001 00*16                   the host's stream: one past its sequence, then its sequence
    00 0001 0001 00*16                   its own stream

以降の ACK では、最初のエントリの 2 番目のフィールドにも、シーケンスの 1 つ先を入れます。
`tests/test_pla_joiner.py` は、台本どおりのホストを参加者に対して動かします。`tests/test_esp32.py` は、2 つのシミュレートしたボードにまたがって動かします。

## 広告

検索画面の本体からスキャンしたものです:

| | |
|---|---|
| ローカル通信 ID | `0x01001f5010dfa000` |
| LDN プロトコル | 1。AES-CTR の広告 (ソードと同じ) |
| シーン ID | 1 |
| 広告のフレームバージョン | 4 (GBA アプリ 3、ソード 2) |
| 受け入れポリシー | all |
| 参加者 | 2 のうち 1 |
| SSID | 16 バイト。セッションキーの入力 |
| アプリケーションデータ | 112 バイト |

アプリケーションデータは、0x5C のシステムプロパティブロックです (`docs/ldn.md`、6.16 から 6.41。システム通信のバージョン 21、アプリケーション通信のバージョン 0、16 バイトのユーザーパスワード、プレイヤー数の上限が有効、プレイヤー 1 人、名前のサイズ 1、エンコーディング 1、名前は 1 つのスペース)。続けて、コードを平文で持つ 20 バイトがあります:

    +0x00  16  the code as ASCII, NUL-padded
    +0x10  4   its length, little-endian

コード `0000 0000` は `3030303030303030` となり、8 個の NUL が続き、長さは 8 です。

### 広告内のリンクコード

ユーザーパスワードは同じコードで、Pia のパスワード設定関数 `0x6fc454` が暗号化したものです。トランスポートの暗号化が有効 (セッションの `+0x230`) で、モード 1 (`+0x234`) のとき、16 バイトのバッファを 0xFE で埋め、その上に NUL 埋めしたコードをコピーします。そして `0x6e68d0` でその場で暗号化します。これは AES-128-GCM で、セッションの `+0x238` のキーで暗号化します (ゲームキー `p1frXqxmeCZWFv0X`。`0x6fc8a4` で設定)。追加データはなく、タグは破棄します。4 バイトの IV はキーから取ります。`key[1] key[8] key[7] key[2]` です (`0x6fc4e4` から `0x6fc4fc`)。ここでは `1emf` になります。GCM のブロック 1 つは、固定のキーストリームとの XOR です:

    password = KEYSTREAM XOR (the code's ASCII, NUL-padded to 16)
    KEYSTREAM = AES-128-GCM(key = p1frXqxmeCZWFv0X, iv = 1emf).encrypt(sixteen zero bytes)
              = e5ab19ed742b6d40885998bf968aa166

キーストリームは、SSID、チャンネル、コード、ゲームの再起動で変わりません。`pokeldn.pla` には `link_code_keystream`、`user_password`、`link_code`、そして `parse_advertise_data` (記載されたコードを、復号したパスワードと照合する) があります。この設定関数は Pia のものなので、この帯のすべてのタイトルが、この方法で暗号化します ([無線層](ldn.md))。

## 製品版の注記

製品版の本体は、リンクコードの有無にかかわらず、どちらの役割でも、エミュレートした本体と同じ連鎖を実行します。フランス語のセーブは、英語のセーブが 2 と書くところに、ハンドラの言語 3 を書きます。`--fresh-pid` は、セーブがすでに持っているレコードを、新しい PID と暗号化定数で再送します。ホストは、提示と提示の間に提示ファイルを読み直します。フラグの変更には再起動が必要です。ホストが動作中に再起動した本体は、次の検索でエラー 2318-0006 を表示します。交換メニューを離れて、もう一度検索すると、これは消えます。

## 離脱

交換を終える本体は `nn::pia::session::LeaveMeshJob` を実行します。Session の type 3 離脱要求を送り、ホストの type 4 離脱応答を 500 ms 待って、再び送ります。送信は最大 4 回で、応答の有無にかかわらず、その後ネットワークから離れます。ステップは、SendLeaveRequest `0x73b898` (書き込み関数 `0x737ee8`、type バイト 3 は `0x737f40`、呼び出しは `0x73b990`、締め切り 0x1f4 ms は `0x73b9a8`)、WaitLeaveResponse `0x73bab8` (再試行カウンタ `[job+0x6c]`、3 を超えると `0x73bbf0` で諦める)、CompleteProcess `0x73ba54` です。

    03 | u32 random | location id (12) | address kind | IPv4 (4) | port big-endian (2)
    04 | u32 random | location id (12)                          the response, 17 bytes

位置 ID は `pia_connect._location_id` のもの (局の定数、ゼロのハーフワード、big-endian の変数 ID) で、アドレスは局自身のものです。ランダムな語は、再送を含め、送信のたびに異なります。`+0x11` のアドレス種別は、取得したすべての離脱で 0 でした。ハンドラは、種別 1 の後はアドレスとポートを 18 バイト、それ以外の後は 6 バイト読みます (`0x7380f0`)。要求は 24 バイトまたは 36 バイトを受け付けます (`0x738024`)。

type 3 のハンドラ `0x738000` (ディスパッチテーブル `0x3973f19`、基点 `0x735434`) は、セッションの `+0x50` にある constant id (`0x7473ec`) が、局自身の `+0x40` (`0x747388`) と一致するときだけ動きます。離脱する局を location id で見つけ、`04`、新しいランダムな語、要求のバイト 5 から 16 を、要求のアドレスに返します (`0x7381c0..0x738248`。`0x735fb0` を通して送信)。その後、局を削除します (`0x735b90`)。type 4 のハンドラ `0x738280` は、constant id と variable id が離脱者自身のもので、ジョブが動いている間の 17 バイトのメッセージに対してだけ、ジョブの完了フラグ `[job+0x69]` を立てます (`0x6e5f0c`)。離脱に応答しないホストは、離脱しようとする本体すべてに、4 回の送信をすべて使わせます。

| ホスト | 最初の離脱から切断まで |
|---|---|
| type 4 の応答より前の `bin/pla_host.py` (製品版の離脱 8 回) | 2.02 から 2.07 秒。4 回の要求の間隔は 0.49 から 0.55 秒 |
| type 4 で応答する `bin/pla_host.py` (製品版の離脱 2 回) | 0.046 秒と 0.066 秒。要求は 1 回 |

type 4 の応答があると、最初の type 3 は、プレイヤーが離脱を確定してから 0.15 秒以内に届きます (BOOT のマーク付き、離脱 2 回)。確定の 3.70 秒後には、フィールドが画面に戻ります。

離脱の後、交換シーンは「Communicating. Please stand by...」(`msg_ui_box_p2ptrd_09`) を、少なくとも 3.0 秒表示します。プレイヤーの離脱 (`0x110b970` のはい/いいえから `0x110bd50`)、相手がいなくなったというメッセージ (`0x110c9bc`)、セッションのエラー (`0x110b504`) は、いずれもモード 9 (`0x110b72c`、ステップ `[scene+0xb4]`、テーブル `0x3979c98`) に入ります。ステップ 0 は `0x26dcc74` を実行します。これは、保留中の受信レコード `[[[0x4279560]+0x2b8]+0x78]` ([交換の制限](#the-trade-restriction)) が立っているときだけ保存します (`0x10457e4`、要求の種類 3)。ステップ 1 は、`[scene+0x278]` の `nn::os::GetSystemTick` でストップウォッチを開始し、離脱 (`0x26be890`) を始め、交換ジョブをキャンセルします (`0x26d9e90`)。ステップ 2 は、3.0 秒が経過し (`0x110b7d8` の `fmov d1,#3.0`)、離脱のシーケンスが完了し (`0x26bdc94`)、ジョブがなくなる (`0x26d9cf0`) まで待ってから、メッセージを閉じます。ステップ 3 は、閉じ終えると true を返します。すぐに応答された離脱 (0.05 秒) と、どのホストも応答しなかった離脱 (2.0 秒) は、どちらも 3.0 秒の中で終わります。そのため、ホストの応答はフィールドの表示を動かしません。type 4 の応答がある製品版の離脱 1 回では、本体の type 3 からフィールドの表示まで 3.77 秒と計測されました。

自分の検索をホストし、局が 1 つ席に着いた状態で離脱する、エミュレートしたアルセウス 1.1.1 は、ステップ 1 (`0x110b78c`) に到達しました。ステップ 2 (`0x110b81c`) を通過したのは、その 4.33 秒後で、最後のパケットの 0.43 秒後でした。その局に渡すホスト移行 (type 7) が、3.0 秒の下限より長く続くためです。ステップ 3 (`0x110b80c`) はその 0.03 秒後に続き、シーンのデストラクタ (`0x110bec0`) はステップ 2 の 0.33 秒後でした。
`bin/pla_host.py` の局として席に着き、ボックスから離脱する、エミュレートしたアルセウス 1.1.1 は、ステップ 1 に到達し、0.07 秒以内に type 3 を送りました (すぐに応答されました)。ステップ 1 の 3.03 秒後にステップ 2 を通過し、ステップ 3 はその 0.03 秒後、デストラクタはステップ 2 の 0.33 秒後でした。離脱が下限の中で完了したため、ステップ 2 は 3.0 秒を単独で待ちます。

Pia の内部には、最初の type 3 より前のタイマーはありません ([pia.md](pia.md)、セッションの離脱)。`Session::LeaveAsync` の唯一の呼び出し元は、ゲームの離脱要求、つまり更新 `0x2ca0a10` です (vtable `0x4198ef8`、状態 `[req+0x88]`、ジャンプテーブル `0x3985448`)。その最初の更新は、Session ジョブが既に動いていなければ (`0x72a280`) `LeaveAsync` (`0x2ca0ac0`) を呼び、次の更新はジョブの結果を待ちます (`0x72a294`)。

本体が 0x7C で最後にゲームメッセージを送ってから最初の type 3 までは、ホストの離脱 9 回で 1.91 から 83.4 秒です。プレイヤーの入力も含みます。その間、本体が送るのは RTT、Net の応答、周期的な 0x81 のレコード、ホストの交換ボックスへの ACK だけです。通信上、離脱の前に固定の遅延はなく、返すべき応答もありません。

`bin/pla_host.py` は、すべての type 3 要求に type 4 の応答で答えます。`tests/test_pla_host_loss.py` の台本どおりの本体は、ジョブのタイミングを動かし、ホストの応答は unicorn の下で `0x738280` を通ります。

受け取った離脱は、本体の画面には何も変えません。本体は、ネットワークが消えたことか、相手が沈黙したことに対して動きます。本体がボックス画面にあり、何も提示していないとき:

| ホスト | 本体 |
|---|---|
| ネットワークが落ちる (離脱の有無にかかわらず) | 1 秒以内に "code d'erreur 2318-0006" (エラー 2318-0006 のフランス語表示) |
| ネットワークは生きていて沈黙する (離脱の有無にかかわらず。`--leave-sends 0`) | "Your trade partner chose not to continue trading" (フランス語 "L'autre joueur a choisi d'annuler l'échange")、その後 Communicating、その後 `DisconnectedByUser`。エラーコードなし (メッセージは約 13 秒後。A を押した後、Communicating が約 3 秒) |

`--leave-after SECONDS` を指定すると、`bin/pla_host.py` は、参加した各局に自分の ID を使って離脱を送り、実行を終えます。`--stay-after-leave` は、ネットワークを沈黙したまま保ち、交換の後で本体が離脱しても実行を続けます。離脱の形は、取得した 4 回の本体の離脱に対して固定されています。
