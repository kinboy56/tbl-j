# カートリッジ、その鍵、そしてセッションへの参加

`main` は Pia 全体 (252 個の `nn::pia` クラス、2036 個の仮想メソッド) を静的リンクし、
`nn::ldn` をインポートする。Pia より上の層では、ゲームはプロトコルバッファを使う。`main` には
78 個の P2P メッセージセットそれぞれの `FileDescriptorProto` が入っており (`gflnet.p2p.framework.pb`、`.block.pb`、`.sync.pb`。
内容ごとに 1 パッケージ: trade、battle、camp、raid)。

## LDN のパスフレーズ

    W3GoSMEn7RIIUQ89rzqBHGhGferRNb7K18ZBq2aNuj8Us9RO9Q9JYyGOZlLy8MYL

64 バイト、生データ (2 つのコピー、`0x203ff04` と `0x203ff45`)。NintendoClients wiki の
スカーレット・バイオレットの行と同一で、Pokemon LEGENDS アルセウスとは 1 文字違う (ここでは `HGhG`、そちらでは `HGHG`)。

    0x006c3eb4  adrp x1, #0x203f000 ; add x1, x1, #0xf04    リテラル
    0x006c3ec0  add  x0, sp, #0x10                          LdnCreateSessionSetting
    0x006c3ec4  mov  w2, #0x40                              64、NUL 終端された長さではない
    0x006c3ec8  bl   #0x1790450                             そのパスフレーズ設定関数

`nn::pia::local::LdnCreateNetworkJob` はパスフレーズを +0xC4 に、その長さを +0x104 に、
`NetworkConfig` の intent を +0xB8 (ローカル通信 ID) と +0xC0 に保持する。そして、パスフレーズを
`nn::ldn::CreateNetwork` (`0x017972bc`) の直前に `SecurityConfig+4` (`0x01797280..0x01797284`) へコピーする。
`LdnBackgroundProcessJob` は長さが 16 から 64 であることを要求する。

## Pia のゲームキー

    p1frXqxmeCZWFv0X

`0x01c3dc87` にある 16 バイトの ASCII 文字列で、3 つの呼び出し箇所がそのまま使う (wiki のソード・シールドの行):

    0x006ca914  mov  w8, #1 ; str w8, [sp, #0x18]     暗号化を有効化
    0x006ca91c  adrp x8, #0x1c3d000 ; add x8, x8, #0xc87
    0x006ca924  ldp  x9, x8, [x8]                     16 バイト
    0x006ca938  stur x9, [sp, #0x1c]                  -> 設定の鍵フィールド
    0x006ca93c  bl   #0x183fd10                       作成/参加

## カートリッジの読み取り

    ./.venv/bin/python tools/switch/xci_read.py <the.xci> --keys prod.keys --type Program
    ./.venv/bin/python tools/switch/xci_read.py <the.xci> --nca 87e41bc8 --exefs 0 --extract main
    ./.venv/bin/python tools/switch/nso_read.py main
    ./.venv/bin/python tools/switch/rtti_names.py main.bin 0x1900fc0 --rodata 0x1901000:0x24da168

`xci_read.py` は XCI をその場で読む。`main` はテキスト 0..0x1900fc0、rodata は 0x24da168 まで、data は
0x2635f38 まで。手法: [Switch タイトルのリバースエンジニアリング](switch_re.md)。

`/bin/message/<Language>/common/*.dat` は Gen 6/7/8 のメッセージコンテナを使う。行 *n* の鍵は
`0x7C89 + n * 0x2983` から始まり、文字ごとに左へ 3 ずつ回転する (どの行も `0x0000` で終わる)。`.tbl` は
`AHTB` インデックスで、エントリ *i* は行 *i* に対応する。

## Pia 4

Pia ヘッダーはバージョン 4 を持ち、その形は [Pia の層](pia.md) にある 2 つのバンドのどちらとも異なる。その下には、
5.27 の LDN ファミリー (鍵、IV、フレーミングは同じで、フィールドが 1 つ加わる) があり、`pokeldn/ldn/pia4.py` がこれを実装している。
`pokeldn.swsh.session_keys` は、バージョンの置き換えを行わない BDSP の導出をそのまま使う:

    session key   = ldn_session_key(GAME_KEY, application_data[12:16] little-endian)
    IV            = crc32(application_data[0:4] || the sender's MAC)[0:3] || source id || nonce
    tag           = sixteen bytes, checked in full

製品版のパケット 484 個すべてで認証に成功し、いずれも送信元 ID は 0 だった。セッションパラメータとネットワーク ID は
セッションごとに変わる。2 つ目の経路 `0x0179bff0` -> `0x01774f40` は、セッションの 2 つの
64 ビット値を対象に AES-GCM のシードを生成する。ローカルのトレードには広告 (advertisement) だけがあればよい。

## 着席

    POKELDN_RADIO=esp32:auto ./.venv/bin/python bin/swsh_join.py --keys PROD_KEYS --scan-only

ホスト中の画面をスキャンし、各アドバタイズを `scratchpad/swsh_net_facts.json` に書き出す。
`--pw-mode raw` が既定値である。

| 画面 | ローカル通信 ID | バージョン | シーン | アプリバージョン |
|---|---|---|---|---|
| 通信交換 | `0x0100ABF008968000` (ソード側) | 4 | 60001 | 7 |
| ふしぎなおくりもの (ローカル無線) | 同じ | 4 | 65535 | |

シールドはソードの ID を使う。`0x0100ABF008968000` を `mov`/`movk` で組み立てて (`0x011083e0..0x011083f0`)
`sp+0x88` に入れ (`0x01108404`。LDN の intent への経路は未追跡)、また、その `control.nacp` は
`LocalCommunicationId[0] = 0x0100ABF008968000`、`[1..7] = 0x01008DB008C2C000` を並べている。

アプリケーションデータの 384 バイト:

    0x00  4  network id、セッションごとにランダム
    0x04  4  リンクコードの ASCII 数字の CRC32、LE。コードがなければ 0 (12345678 -> 0x9AE0DAAF)
    0x08  1  システム通信バージョン、5
    0x09  1  ヘッダーサイズ、0x18
    0x0A  2  パディング
    0x0C  4  session param、セッションごとにランダム
    0x10  8  0
    0x18  2  0x1A..0x180 の CRC16 (`0x0065dcb0`、`pokeldn.swsh.beacon.crc16`)
    0x1A  2  network version word、12 ビット、0x0D70 (`0x006c17c0`、参照元 `0x02068848`)
    0x1C  1  `0x006b5c10` からのビット 0。セットは拒否される
    0x1D  1  ペイロード種別、station 情報の場合は 0
    0x1E  1  ページバイト。3 回の公開ごとに 1 と 2 を交互に (`0x0111aac0`)
    0x1F 266 プレイヤープロフィール。0xAEC のトレードスナップショットと同じだが、別のタイミングで取得する
             ([プロトコルのページ](swsh_protocol.md#the-player-profile))。末尾まで 0

`Connect failed with status code 1` は関連付けが拒否されたことを示す。同じ検索での次の試行では
関連付けできる。検索中のソードは、1 つの通信 ID の下に 2 つのネットワークをアドバタイズする。Y-Comm ビーコン (シーン 65535) と、
2 つ目のメッセージを過ぎたあとに出す、対応するネットワーク (シーン 60001) である。ビーコン上の局は
16 回の参加のうちトレードボックスに到達したのは 0 回だった (メッシュへの参加が理由 1 で拒否されるか、その最中にアドバタイズが変わった)。`bin/swsh_connect.py` は
シーン 60001 にのみ参加し、それが現れるまで再スキャンする。関連付けの後、ゲーム機は `169.254.x.255:12345` に
Pia をブロードキャストする (毎秒およそ 10 パケット)。画面には何も表示されない。参加した局が離脱したあとにゲーム機のアドバタイズを終わらせるものは
未確認のままである。

## 検索中のソードはどのようにしてパートナーを見つけるか

Y-Comm 画面では、すべてのゲーム機がシーン 65535 でビーコンネットワークを立て、約 1 秒に 1 回ブラウズする
(`0x006c3630`: ホスト `0x006c3840`、ブラウズ `0x006c3770`。条件は `0x006c4550`、`0x0183fac0` から取り、
通信 ID とネットワーク種別だけで判断する)。CRC とバージョンの関門 (`0x006c1be0`) を通過したレコードは、近くのプレイヤーの
レジストリ (`0x0110f270`) に届く。そこでは自分自身のもの (アドバタイズの 0x1F のデバイス ID と 0x2F のアカウント uid、`0x0111b160`) と、
ネットワーク ID とシーンの組を持たないものを捨てる (`0x0110f2d4`)。
ここでは何も参加しない。

通信交換、続いて通常のトレードでは、A の入力を待つ 2 つのメッセージが表示される。2 つ目のあと (「検索をキャンセルできます...」
という表示)、`0x00fba940` が `SetMode(comm, 2)` (`0x01096d10`) を呼ぶ。`0x01095f10` は
1 秒以内に状態 0、5、3、4、6 と遷移し、状態 6 は `StartRandomMatching` (`0x010fcff0`) を
シーン 60001 (`0x01096730`) で呼ぶ。フィールド画面には "Recherche..." と表示される。最初のメッセージに留まったゲーム機は
`SetMode(comm, 2)` を呼ばず、決して一致しない。

マッチング層は次の条件でネットワークに参加する (`0x006c9e70`、`0x006cb8e0`、参加 `0x006ca1c0`):

    シーン 60001、自分のものと等しい
    ノード数 1、上限 2 未満。ネットワーク種別 2。ノード数の上限が 8 以下
    advertise 0x04 が 0: リンクコードのない検索はパスワードを拒否する
    advertise 0x00 (u32) が検索側自身の値より大きい
    advertise 0x00 が、この検索で参加に失敗した ID (0x80 エントリ) に含まれない

リンクコードが変えるのは 0x04 だけである。`bin/swsh_connect.py` (コードなし) は、コード付きのゲーム機に参加してトレードする。
`bin/swsh_host.py --code 12345678` には、コード付きの検索が参加し、コードなしでは決して参加しない。大きいほうの ID が
ホストになるため、検索中の 2 台のゲーム機は一方向にしか組めない。ホストは
0xFFFFFFFF 付近の ID をアドバタイズする。

## ゲーム機が最初に発する内容

BDSP と同じ Pia Local Protocol 0x24 (`pokeldn.ldn.local_protocol`): バージョン 1、タイプ 0x11、固定 0x30
バイト、9 バイトの席 8 つ、ホスト移行のバイト。`allow_participating` は true なので、ゲーム機は
参加者を先にテーブルへ登録する。

    a9fe0e01 3039 ... 00      169.254.14.1:12345   station 0、ゲーム機、順位 0
    a9fe0e02 3039 ... 01      169.254.14.2:12345   station 1、席、順位 1

ホストは、各 station が確認応答 (0x21) するまで更新セッションを繰り返す。シーケンス ID を載せた確認応答は再ブロードキャストを止める
(13 ms 以内)。別のシーケンス ID を持つ確認応答では止まらない
(`bin/swsh_connect.py --seq-delta`)。ヘッダーのバイト 0x05 と IV の送信元 ID は、ゲーム機自身のものと同じく 0 である
(`--station-sweep` で他を巡回する)。

## Pia セッションオブジェクト

`[[0x02616a30]]` (`[0x02630f40]` も同様)。トレードのコードが station ID を読むこの場所は、Pia の
セッションオブジェクトである。サイズは 0x270 バイトで vtable を持たず、`0x006a8644` から `0x0183ddb0` (`0x0183dfd4`) が一度だけ確保する。
バックエンドはネットワークファクトリ (`[x20+0x60]`、`0x006a8600`) から得る。`+0x178` のスロットは `0x240/8`、
`+0x188` のスロットは `0x290/8`、`+0x168` のスロットは `0x248/8` (`0x0183e074`)、`0x1b8/8` のスロットが真のとき
`+0x170` のスロットは `0x248/8` になる。バイト `+0x162` で選ぶ。LDN ではファクトリは `LdnNetworkFactory` で、そのスロット 73
(`0x01791080`) が 0x7220 バイトの `LdnMatchmakeSession` を組み立てる (vtable は GOT `0x0262fbd0` から)。

| フィールド | 書き込み元 | 値 |
|---|---|---|
| `+0xf0` | `0x018418a0` (`0x01841918`) | このゲーム機自身の station ID |
| `+0xf8` | `0x018418a0` (`0x01841990`) | メッシュのホストインデックスにある station の ID。インデックスはバイト `[[0x0262f7b0]]+0xab` (`0x017bbfe0`)。`[obj+0xd4] == 4` のときはスキップする |

`0x018418a0` は、作成 (`0x018394d8`) と参加 (`0x0183d9b0`) の際、`0x018410e0` の後に走る。メッシュのホスト
インデックス `+0xab` (自分のインデックス `+0xac`) は、作成 (`0x017b092c`、`+0xac` と等しい値) と、参加の応答 (`0x017b4e4c`) で書き込まれ、
`0x017bb820` で `0xfe` にリセットされ、`0x017b99a0` で `+0xac` とともに `0xfd` にリセットされる。さらに、
ホスト移行では `0x017ca454` (`LanProcessHostMigrationJob`、
`LocalProcessHostMigrationJobNew`、Nex から) と `0x017caf48` で書き込まれる。

`MeshEventListener` の slot 2 (`0x01843580`、`[x1]` で switch、テーブル `0x02083fe8`) も `+0xf8` に書き込む:

| イベント | 格納先 |
|---|---|
| 1 | バックエンドの slot 30 (`0x01844bc4`)。変化があったときは続けて `0x018412a0(obj, 2, id)` |
| 2 | `0x017d6080` が返す ID (`0x01844a74`)。バックエンドの slot 30 (`0x01844edc`)。`0x01844f60` |
| 3 | 0。`+0x100` とともに (`0x0184415c`、`stp xzr,xzr`)。`[obj+0xd4] != 3` のとき |

`0x01837000..0x01850000` における `+0xd4` への書き込み:

| 値 | 箇所 |
|---|---|
| 0 | `0x018399c8` |
| 1 | `0x01837c1c`、`0x018396ac`、`0x0183dbbc` |
| 2 | `0x01837a8c`、`0x01839474`、`0x0183cda8`、`0x0183d94c` |
| 3 | `0x01839f7c`。`0x01839cc0` 内。呼び出し元は `0x0177d8a0`、`0x0180afe0`、`0x0180bd0c` |
| 4、それ以外は 2 | `0x0183a2cc`。`0x0183a040` 内。`w8 - 6 < 3` のとき 4 (`0x0183a2b8..0x0183a2c8`)。呼び出し元は `0x0177e8a8` と `0x01818b68` |

`0x01839cc0` の呼び出し元は `LanMatchJointSessionJob` (`0x0177d8a0`) と
`NexMatchJointSessionJob` (`0x0180afe0`、`0x0180bd0c`) に属する。`0x0183a040` の呼び出し元は同じ 2 つのジョブ
(`0x0177e8a8`、`0x01818b68`) に属する。通常の LDN の作成と参加は、モード `+0xd4` を 2 に設定する。

イベント 2 がいずれかのホスト ID の格納に至るのは、`0x01841350` と `0x01769ec0([obj+0x38])` がどちらも偽で、
符号なしの値 `[obj+0xd8] - 2` が 6 以上のとき (`0x01843980..0x018439a4`) に限られる。モード 2 では、新しい station の固定 ID を
`0x017d6080` から選ぶ。モード 4 では、slot 30 の格納を含むジョイントセッションの分岐を選ぶ。したがって、イベント 2 の slot 30 への格納には
ジョイントセッションのモード 4 が必要である。

イベント 1 の slot 30 への格納には、離脱する station の ID が `+0xf8` に一致し、`+0x100` と異なることが必要である。
また `0x01840b90(obj)` が真で、状態 `+0xd8 == 1`、かつ `[mesh+0x64] == 0` でなければならない
(`0x01844614..0x01844638`、`0x01844654..0x01844664`)。`0x0184a4b0` は、出力のワードが 0 でなく、
`obj+0x180+4*[obj+0x162]` のワードと異なる対応を見つけなければならない。
メッシュコントローラーのバイト `+0x84` が立っている場合、そのバイト `+0xc0` も立っていなければならない
(`0x01844b54..0x01844b9c`)。新しい slot 30 の値は、格納する前に `+0xf8` と異なっていなければならない。
LDN では、`0x01840b90` は仮想スロット `+0xb0` と `+0xa8` を通じて、ローカルのメッシュコントローラーの
`+0x281` と `+0x234` を調べる。
ローカルのコントローラーの構築に成功すると、両方のバイトが 1 になる (`0x017a06ac`、`0x0183c228`)。
残りのイベント 1 の関門は引き続き適用される。バックエンドの種別だけでは、この分岐は除外されない。

`LdnMatchmakeSession` の slot 30 (`0x017a23d0`) は、`[this+0x18]` が null のとき `0xff` を返す。それ以外のときは
`[[this+0x18]+0x18]+0x2c0+8` の 16 バイトのアドレスに対して `0x017672d0` を評価する。すべて 0 なら 0、
最後の 12 バイトが 0 なら先頭 4 バイト、それ以外ならエラー `0x10c07` を返す。slot 28 (`0x017a23b0`) は、
`0x018407f0` が呼び出す仮想関数である。

`0x018407f0` は、`+0xf0` が非ゼロで `+0xf8` と等しく、バックエンドの slot 28 が一致するとき真になる:
作成と参加の値が揃い、Pia のメッシュをホストしているゲーム機上で成立する。トレードをホストしているゲーム機は、コマンドに対して確認の階段を登る。
pokeldn のホストに参加したゲーム機は、共有された値に従う
([ポンプ](swsh_trade.md#the-pump))。

## ゲームレイヤーへの到達

ゲームより下の各層は双方向に動く ([Pia の層](pia.md))。ローカルプロトコル 0x24、station
ハンドシェイク 0x14、メッシュ参加 0x18、RTT 0x58、信頼性ウィンドウ 0x7C と 0x80。

参加者の 0x14 接続応答は、ソードが送る 840 バイトの形でなければならない
(`host4.build_host_response`: 0x11 にアカウント ID、0x88 にプレイヤー名、0xB1 に末尾、0xBC にトークン)。
エミュレートしたシールド 1.3.2 のホストは 56 バイトの応答 (`[0x37]` に 1、それ以降は 0) を受け入れ、
ステーションをそのメッシュに参加させたが、ゲームのメッセージは一度も送らなかった。
840 バイトの形を与えると、参加応答の 0.03 秒後に最初の ping を送り、参加者の名前でトレードボックスを開いて、トレードを完了した。
製品版のソードは 17 バイトの応答のあとにトレードを完了したが、0x11 より後のフィールドは古いバッファのバイトから読んでいる
([Pia の層](pia.md#what-a-connection-response-must-satisfy-to-be-read))。
`bin/swsh_connect.py --respond` は 840 バイトの形を送る。

放置すると、ゲーム機は `61 00 00 00 0a 00` (ping、毎秒およそ 4 回) を繰り返す。0x80 は
1 秒に 1 回 ack ID 1 を求め、0x7C は沈黙したままである。`bin/swsh_connect.py --send-data HEX
--send-protocol 0x7c` はアプリケーションデータを送る (`reliable4.build_data_message`。ゲーム機自身のものとバイト単位で一致する)。
無応答の受信チェック 5 件 ([バージョン 4](pia.md#version-4))。合格の目安: 0x80 の ack ID が 1 から外れること。
0x7C が ack を返すこと。

## ping ハンドシェイク

ペイロードは、4 バイトのリトルエンディアンのメッセージ ID と protobuf 本体からなる。ハンドシェイクが運ぶのは
次の 5 種類だけである (右の列は各 1 回のキャプチャでの数)。

    0x7C  61000000 0a00      97 SyncPingDataHolder, field 1 ping {}           x20
    0x7C  61000000 1200      97, field 2 pingReply {}                          x2
    0x7C  61000000 1a00      97, field 3 pingSynced {}                         x3
    0x7C  60ea0000 0a00      60000 BlockDataHolder, field 1 result {}          x2
                             (Result { bool isBlocking })
    0x80  60ea0000 12020801  60000, field 2 imReady { isReady: true }          x2

(`gflnet.p2p.sync.ping.pb`、`gflnet.p2p.block.pb`)。応答は 5 つの段階でゲームを進める:

    1  ping に継続的に応答する   --send-data 610000000a00 --send-mirror --send-count N
    2  信頼性ウィンドウすべてに ack を返す      0x7C, 0x18 port 1, 0x80。ack のないウィンドウが 1 つあるとメッシュが落ちる
    3  0x7C で `result{}` に応答する      ミラーはプロトコルごと
    4  0x80 で imReady に応答する         --send2-data 60ea000012020801
    5  ゲーム機が 0x84 でパーティを送る

- ping には継続的に応答しなければならない。1 回の応答では `pingReply` が 1 つ返るだけで、ゲームは
  再び ping を送り始める。
- ゲーム機が求める前に送った `pingReply` は、そのハートビートを止める。
- `result{}` への応答として 0x7C で送った `imReady` は 0x84 を引き出さない。応答は 0x80 で送る。
- ack が遅れたメッセージは再送され、後続のメッセージより遅れて届くことがある (シーケンス 9 の `pingReply` が
  `pingSynced` (10) の後に届く)。最新より大きいシーケンスだけが現在のメッセージを置き換える。再送への応答は
  `pingReply` のループとなり、`imReady` は決して届かない。

`bin/swsh_connect.py --sync-answers` は、規則がある場合は `trade.SYNC_ANSWERS` で応答し、ほかではプロトコルごとにエコーし、
規則のないペイロードを 1 つずつ表示する (それが引き起こした応答の後に表示する。ownerId を読むこと)。

## 離脱

トレードセッションを離脱するソードは、ボックスコマンド 3 を送り、約 0.77 秒後に自分の役割に応じた Pia の離脱を開始する。
各段階は応答を待ち、応答がなければタイムアウトで次の段階に進む。

参加したソードがホストを離脱する場合:

| 段階 | ソードの送信 | ホストが返すべきもの | 無応答時 |
|---|---|---|---|
| メッシュ離脱 | LEAVE_REQUEST `04 <own index>`、0x18 port 1、信頼性あり、1 回 | LEAVE_RESPONSE `08 <host index>` | 5.0 秒 |
| station の切断 | 0x14 で `03`、0.5 秒ごと | `04` | 8 回の要求、3.6 秒 |
| LDN | ネットワークを離脱する | | |

どちらも応答がなければ、ソード (製品版またはエミュレートしたシールド) は LEAVE_REQUEST の 9.0 から 9.1 秒後に LDN ネットワークを離脱する。`08 00` を 2 回送り、
`04` に応答があったときは、製品版のソードは LEAVE_REQUEST の 0.04 秒後に `03` を 1 回送り、
LEAVE_REQUEST の 0.14 秒後に離脱した。

- バージョン 4 のホストハンドラー `0x017c19a0` (メッシュ種別 4、テーブル `0x02081564`) は、`08` と自分のインデックスを
  `0x017c2450` 経由で送る。信頼性のない 2 つのコピー (`0x01851200` でバンドルなしフラグ 0、次に 1) を送り、
  ステーションをメッシュから外す。離脱側のハンドラー `0x017c0d44` は、[1] がメッシュホストのインデックスの
  ときだけそれを受け取る。
- 0x14 のハンドラー `0x017c6110` (種別 3、テーブル `0x02081804`) は、1 バイトの `04` を送信元に返し、
  そのステーションを消えた扱いにする。種別 4 のハンドラー `0x017c5fcc` は、離脱側の待機を解除する。

`pokeldn/ldn/host4.py` は両方に応答する。

クライアントを離脱するホスト中のソード (LDN のアクセスポイント) の場合:

| 段階 | ソードの送信 | クライアントが返すべきもの | 無応答時 |
|---|---|---|---|
| メッシュの移行 | MIGRATION_START `44 00 01` ([ホスト移行](swsh_trade.md#host-migration)) | MIGRATION_FINISH と、自分をホストとして名指す UPDATE_MESH (指名されたステーションから) | 5.0 秒 |
| ローカルセッション | 更新セッション (0x24 種別 0x11)。ホスト移行バイトは 1 で、新しいシーケンス ID を付けて約 0.11 秒ごと | そのシーケンス ID に対する 0x21 の ack | 10.0 秒 |
| ネットワークの破棄 | START_HOST_MIGRATION `01 13 00..` (16 バイト)、0.33 秒ごと | LDN ネットワークを離脱する | 10.0 秒 |

製品版のソードで計測した値。MIGRATION_START から最後のパケットまで:

| クライアントの応答 | メッシュ段階の終了 | 最後のパケット |
|---|---|---|
| なし (5 件のキャプチャ) | 5.0 秒 | 25.0 秒 |
| ホストとしての MIGRATION_FINISH と UPDATE_MESH を繰り返し | 0.1 秒 | 20.1 秒 |
| MIGRATION_FINISH (ack 済み)、その ack、離脱 | 5.0 秒 | 5.07 秒 |
| MIGRATION_FINISH、ホストとしての UPDATE_MESH、ack、離脱 | 0.07 秒 | 0.17 秒 |

完了だけが ack されたとき、ゲーム機はクライアントのデータを 4.8 秒間 ack する。UPDATE_MESH が
ある場合は、開始の 0.07 秒後に静かになる。

- `LocalDestroyNetworkJob::WaitUntilAllClientsDisconnection` (`0x017acd70`) は、ネットワークの接続ノード
  (`0x017a9b20`、8 スロット) を数え、ホストだけが残ったとき、または `0x2710` ms 経過したときに破棄する。
  その間、START_HOST_MIGRATION を `0x12d` ms ごとに再送する (`0x017acbd0`、`0x017a8bb0`)。
- 更新セッションは `LocalResendMessageJob` が再送する。ack (ハンドラー `0x017a9250`、ローカルの
  種別 0x21) は、そのシーケンス ID がメッセージのものと等しいときだけ送信元のビットを消す
  (`0x017aed10`)。バイナリで 10.0 秒のローカルセッション段階を区切っているものは未確認である。
- START_HOST_MIGRATION はシーケンスを持たず (シリアライザ `0x017abc60` は 0xC に 0 を書く)、再送ジョブもない。
  そのため、これを ack するものはない。

`bin/swsh_connect.py --answer-migration --update-mesh --leave-with-host` (`--preset trade` 内) は、
ホストとして finish と UPDATE_MESH を送り、ホスト移行の更新セッションを ack して、
START_HOST_MIGRATION でネットワークを離脱する。

## 運用上の注意

- ライブ実行では `--verbose` を付けない。代わりに `--capture FILE` を使う。
- ゲーム機のチャンネルはセッションごとに変わる (1 と 6 を確認)。スキャンは最も混雑しているものを残す
  ([チャンネル](ldn.md#channels))。
- `0x2D0` (確保は `0x006a970c`、`0x006a9740` で行われる) はセッションシングルトンのサイズであり
  (`0x006b4410`、グローバル `main+0x02616758`)、720 バイトのふしぎなおくりものカード (Wonder Card) ではない。
