# スカーレット・バイオレット

ポケモン スカーレット (`0100a3d008c5c000`) とバイオレット (`01008f6008c5e000`) は、Pia を `main` にリンクした Switch のネイティブタイトルです。
どちらも両方の役割で市販のコンソールと交換でき、`bin/sv_host.py` はコンソールのオフラインの通信交換検索に対してホストになり、
`bin/sv_join.py` はコンソールのネットワークに参加します。
市販のバイオレットは、スカーレットのローカル通信 ID を告知しているホストに参加し、自身の検索
ネットワークでもスカーレットの ID を告知します (`0x0100a3d008c5c000`、アプリケーションバージョン 21、シーン 4)。

どちらの起動スクリプトも、どちらの役割でもローカルのテラレイドを実行できます ([テラレイド](sv_raid.md))。また、ホストは
コンソールに公式のふしぎなおくりもののポケモンを交換します ([模擬ふしぎなおくりもの](gift_simulated.md))。
[ユニオンサークル](sv_union_circle.md) は、コンソールのユニオンサークルにゲストとして参加し、ブルーベリークエストのクリアを
ホストに報告し、ユーザーが作成した野生のポケモンをホストのプレイヤーの周囲に出現させます。

アドレスは、更新 4.0.0 のデコンプレス済みの `main` に対するオフセットです (`tools/switch/nso_read.py`)。
text `0x0..0x343fc90`、rodata は `0x3440000` から、data は `0x4383000` から。

## 無線層

| | 値 |
|---|---|
| Pia ヘッダーのバージョン | 11。Legends アルセウスの系統で、`pokeldn.ldn.pia6` がこれに対応します |
| ヘッダーのサイズ | 0x1C、GCM タグは 8 バイト |
| LDN のパスフレーズ | `W3GoSMEn7RIIUQ89rzqBHGhGferRNb7K18ZBq2aNuj8Us9RO9Q9JYyGOZlLy8MYL`、データ `0x44dfd0a` |
| Pia のゲームキー | `p1frXqxmeCZWFv0X`、データ `0x44dfcfe`、パスフレーズの直前 |
| LDN のローカル通信 ID | 両バージョンともスカーレットの `0x0100a3d008c5c000` (どちらの ID もイメージ内の定数ではなく、NACP には両方が載っています) |

パスフレーズとゲームキーは、ソード・シールドおよび Legends アルセウスのものと同じです。

## 検索中のコンソールが告知する内容

通信交換の検索は、ホスト (毎回新しい SSID) とスキャンを交互に行い、チャンネル 1、6、11 の間を移動します。
ホストの段階は約 5 秒です。

    local_communication_id  0x0100a3d008c5c000, Scarlet's, on both versions
    ldn protocol            1            advertisement version 4
    scene_id                4            app_version 21
    security_mode           1            accept_policy ALL
    participants            1/2
    application_data        132 bytes

アプリケーションデータは、0x5C バイトの Pia システムプロパティブロックと 40 バイトのゲームデータからなります。

| フィールド | 値 |
|---|---|
| システム通信バージョン | 0x15 |
| アプリケーション通信バージョン | 0x15 |
| ユーザーパスワード | リンクコードなしの 16 バイトのゼロ |
| プレイヤー上限の有効化 | 1。プレイヤー数は 1 で、ステーションが着席すると 2 |
| プレイヤー名 | 1 バイト、スペース、UTF-8 |
| 40 バイトのゲームデータ | ゼロ、またはゲームの `+0x21` の非ゼロ値 (`fb149700` を確認)。数秒ごとに交互に切り替わり、2 台目のコンソールはどちらにも関連付けます |

`pokeldn.sv.build_advertise_data` は、両方のビーコンをバイト単位で再現します。

## ゲームが使うプロトコル

市販のペアを受動的にキャプチャすると、Net、RTT、0x80、0x81 が見えます。いずれも
セッションの `/24` のブロードキャストアドレス宛てで、受信者の可変 ID は平文のフッターに入ります。残りの 6 つは
2 台の Switch 2 コンソールの間の 802.11ax によるユニキャストで、キャプチャには現れません。

ゲームのセットアップ `0x17ff030` は、順に次を作成します。ポート 0 の Reliable `0x7C` と BroadcastReliable `0x80`、
Unreliable `0x68`、ポート 1 と 2 の Reliable と BroadcastReliable、`[0x44dfcd0]` が指す
StreamBroadcastReliable `0x81` ポート (ワイヤー上では 8 個)、Clone Clock `0x77` と Clone Atomic
`0x74`。Pia は Net、RTT、Session `0x98`、MonitoringData `0xA4` を追加します。NatTraversalResult `0xA0` は
ネットワークファクトリが NAT トラバーサルを有効にした場合 (`0x6d3138`) にだけ追加されます。ローカルネットワークでは有効になりません。

| ID | プロトコル | バージョン |
|---|---|---|
| `0x2C` | Net | 0 |
| `0x58` | RTT | 3 |
| `0x68` | Unreliable | 1 |
| `0x74` | Clone Atomic | 0 |
| `0x77` | Clone Clock | 0 |
| `0x7C` | Reliable | 2 |
| `0x80` | BroadcastReliable | 3 |
| `0x81` | StreamBroadcastReliable | 3 |
| `0x98` | Session | 0 |
| `0xA4` | MonitoringData | 0 |

市販の Legends アルセウスは、参加リクエストに同じ 10 個のバージョンを載せます。市販のペアの開始時の流れ
(1 回のキャプチャからの時刻) は次のとおりです。

    +0.00   the joiner associates
    +0.06   host: Net 0x11 (station list), 0.12 s later Net 0x50
    +0.14   host: acks all eleven streams, opens two
    +0.89   joiner: RTT request, acks all eleven, opens two
    +0.97   host: first records on 0x81 port 0
    +1.26   joiner: first records on 0x81 port 1

### Net 0x11、ステーション一覧

レイアウトは Legends アルセウスのものと同じで、21 バイトのステーションスロットが 4 つあります:

    01 11 0054          version 1, type 0x11, payload size 0x54
    00000002            sequence id
    9141                host variable id, fresh every session
    eb9b2220f1480000    host constant id, the LDN MAC reordered
    0000000097392e8a    network id, the low four bytes crc32(ssid[1:16])
    01                  is network open
    0004                station slots
    00                  is migrating host
    ...                 four stations: migration state, ranking (host 0, joiner 1, empty 0xff),
                        one byte, 16 address bytes, big-endian u16 port (12345)

`01 40 00 00` は、役割を引き渡すホストが送る素の NetStartHostMigration です。市販の
スカーレットは、検索からホストになると、参加者に引き渡す座席上でこれを繰り返します
([座席を決める要素](#what-decides-a-seat))。

ホストは 4 つのステーションスロットを書き込む必要があります (ゲームの上限 2 ではなく、Pia の数です)。2 つだと、参加側のゲームは何も送らず、
関連付けから 5 秒後に切断します (49 回の参加で 4.98 から 5.01 秒)。市販のコンソールは Net 0x11 に対して
ICMP のポート 12345 到達不能で応答します。4 つだと Net 0x12 で応答し、Session の参加リクエストを送ります。
開始フラグ 0x31 (市販機) または 0x01 でも違いはありません。

### 11 本のストリーム

    0x80  BroadcastReliable         ports 0, 1, 2
    0x81  StreamBroadcastReliable   ports 0 to 7

両方のステーションは、`pokeldn.ldn.reliable5` の一括確認応答で、約 1 秒ごとに 11 本すべてを確認します。この応答は 4 つのエントリからなり、ステーションのバイトはゼロです。
エントリ *k* は、ステーション *k* の最大シーケンスより 1 つ先の値で、宛先ビットの数は 3、ビットマップには相手側のビットが入ります。
ステーションは、11 バイトの INITIALIZED メッセージで 2 本のストリームを開き、
自分のステーションインデックスのポートでレコードを送ります (`pokeldn.pla.data_exchange` と同じ)。

| ステーション | 開くストリーム | レコードを送るポート |
|---|---|---|
| ホスト、インデックス 0 | 0x81 のポート 1 と 5 | 0x81 のポート 0 |
| 参加側、インデックス 1 | 0x81 のポート 0 と 4 | 0x81 のポート 1 |

オープンのペイロードは、ポート 0 と 1 では `0000000000f38800000000`、
ポート 4 と 5 では `00 <port> 00 00 0ff0 0800000000` です。StreamData の kind 0 が、受信 0xF388 (転送 0) または 0xFF008 (4 と 5) を要求します。0xFF008 の転送は交換中には送られません。
`pokeldn.sv.streams` がこれらすべてを組み立て、`tests/test_sv.py` はそれを市販機のバイト列に固定します。

### Pia のメッセージフラグ

市販の両方のステーションは送信時に次のフラグを使います (Arceus ホストの確立用フラグは使われません):

| メッセージ | フラグ |
|---|---|
| RTT、ストリームのオープン、レコードの初回送信 | 0x00 |
| レコードの再送 | 0x40 |
| 一括確認応答 | 0xA0 |
| ホストの Net 0x11 と 0x50 | 0x31 |
| NetStartHostMigration | 0x11 |

メッセージの宛先フィールドは常にゼロです。フラグ 0x40 は、`ReliableSlidingWindow` の送信ループ `0x6f0638` で
`w4 = 1` とされたものです (送信回数 `[slot+0x14]` がゼロのとき `0x6f0908` で 0、
再送 `0x6f0a9c` または早期送信 `0x6f0c38` で 1 になります)。`0x6e7250` が、
パケットライターのオプションブロックのバイト 0 として格納します。

### RTT

11 バイト: kind、ビッグエンディアンの u64 クロック、ビッグエンディアンの u16 ターゲットです。要求は kind 0、ターゲット 0 で、
応答は kind 1 で、同じクロックと要求側の可変 ID を持ち、市販機では 20 ms 以内に返ります。

RttProtocol (vtable `0x43e5a28`) は、ステーションごとに 0x40 バイトのレコードを `[proto+0x60] + index*0x40` に保持します:
サンプル数は `+0`、リングの先頭は `+4`、容量は `+0x10` の 9 で、その後ろにリングがインラインで続き、中央値を
`+0x3c` にキャッシュします (対象の数は `+0x38`)。サンプルは、現在のクロックから返されたクロック (`0x6f34b4`) を引いたものです。
0 以下のサンプルは破棄されます (`0x6f34e0`)。要求は、すべてのリングが満杯になるまで間隔 `[0x46d1528]` で送られ、
その後は `[0x46d1520]` = 500 の間隔で送られます (`0x6f2fcc` で書き込まれ、ゲームも `0x1e7c2bc` で書き込みます)。
ステーションイベント 0 または 1 で、そのステーションのレコードは消去されます (vfunc11 `0x6f3bd8`)。新しい座席にはサンプルがありません。

GetRtt (`0x6f4498`、件数 *n* 付きの `0x6f44bc`) は、サンプルがなければ -1 を返し、それ以外は
直近の min(count, *n*) 個のサンプルの中央値を返します。その隣に min `0x6f44e4`、max `0x6f4508`、サンプル数 `0x6f452c` があります。
呼び出し元は、SessionTransportAnalyzer の監視用コピー
(`0x6f9ab0`..`0x6f9ad4`) と、`ReliableSlidingWindow` の再送期限 `0x6f0d14` だけです。後者は
`0x6f073c` の送信ループから呼ばれます:

    deadline = now + [window+0x80] + 1.4 * (max over the destinations of GetRtt(count))

サンプルがない場合、`0x6f0d14` は予定なしを示すマーカー `[window+0x5c]` を返します。メッセージはキューに入ったときに 1 回だけ送られ
(`0x6f1bbc`..`0x6f1bd4`)、サンプルが入って再設定されるまで `0x6f0a18` で飛ばされます
(`0x6f09f4`..`0x6f0a08`)。RTT のサンプルがないウィンドウは、決して再送しません。

コンストラクタ `0x6eeea8` (呼び出し元は `0x6e69f8`、`0x1800038`) は、`[window+0x80]` を
`ticks_per_second * 33 / 1000` に設定します (`0x6eef34`..`0x6eef74`。633,600 ティック、19.2 MHz で 33.0 ms)。マーカー
`[+0x5c]` は 0、基準シーケンス `[+0x30]` は 1、自分のインデックス `[+0x10]` は 0xfd、圧縮 `[+0xa4]` は 1、
早期送信の上限 `[+0x88]`、`[+0x89]` は 0 です。後で書き込むのは、vfunc17 `0x6f1f98` の `0x6f1fc8` だけです
(`ReliableProtocol::vfunc17` `0x6eebbc` と `BroadcastReliableProtocol::vfunc17` `0x6e6818` から。既知の呼び出し元はありません)。
送信ループは 16.7 ms のフレームごとに 1 回動くため、再送は
`33 + int(1.4 * RTT)` ms 以降の最初のフレームで出ます。RTT 34 ms で 83 ms、358 ms で 550 ms です。

### レコード

レコードは、ZLIB フラグ付きの 1 つの信頼性メッセージで、4 KB ウィンドウ (`484b`) の zlib ストリームです。
展開すると 1395 バイトになり、`[window+0x70]` に入ります。Pia の StreamData ヘッダーのもとでの 0x81 転送の 1 チャンクです
([プロトコル 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)):

    +0x00  1   StreamData kind: 1 the first chunk of the block, 2 a later chunk
    +0x01  1   transfer id, 0
    +0x02  1   percent of the block delivered after this chunk
    +0x03  4   zero, the capacity field of a kind 0
    +0x07  4   big-endian u32 0x00000568, the 1384 bytes that follow

ステーションのブロックは 0xF388 (62,344) バイトで、1384 バイトのチャンクが 45 個と 64 バイトのチャンクが 1 個からなり、ID は 1 から 46、パーセントの
バイトは `floor(k * 1384 * 100 / 62344)` です (2、4、6、8、0x0b、..., 25 で 0x37、37 で 0x52、46 で 0x64)。最初のチャンクには、画面に表示される
相手の情報が入ります:

    +0x0b  4   trainer id, then secret id
    +0x0f  1   version: 50 Scarlet, 51 Violet
    +0x10  1   gender
    +0x11  1   language
    +0x12  1   ball-throw style, 1 the original
    +0x13  26  the player name, UTF-16 little-endian, NUL-padded; --trainer-name on both launchers
    +0x2d  22  the account identifier, ASCII, `u-` and twenty characters
    +0x53  8   story progress, little-endian: 1 the main story cleared, 4 The Indigo Disk cleared

ブロックは `0xa52f88`..`0xa530a0` のスタック上で組み立てられます。セーブデータからトレーナーを取り、
別のセーブブロック (`0xa53054`) から投げ方のスタイルを取り、アカウント識別子 (`0x1a61a00`) を入れ、最後に
進行状況のワードを入れます。これはゲームが `0x473a040` に保持するスクリプト関数の戻り値です (`0xa5309c` で呼ばれます)。
ネイティブの `f20A702BD` (`0x877560`) がこれを設定します。3.0.1 のスクリプトダンプでは、
`BattleNetworkNetReceiver` が、0 から始まり、`FSYS_SCENARIO_GAME_CLEAR` が立っていると 1 を設定し、
`FSYS_SCENARIO_GAME_CLEAR_SU2` が立っていると 4 を OR する関数を渡します。市販の
スカーレットは 5 を送り、市販のバイオレットは全ゼロのアカウント識別子で 0 を送ります。参照実装は 1 を送ります。

ゲームのスクリプトは、ステーションのプレイヤーを、次の順で登録されたネイティブのゲッターから読み取ります:
`PlayerId`、`RomCode`、`Sex`、`LanguageId`、投げ方のスタイル、`NameStrBuf` (3.0.1 のスクリプトダンプの
`RegisterPlayerData` と戦闘のセットアップ。投げ方のスタイルは、セーブデータ自身の `ballThrowId` が埋めるスロットです)。
市販のスカーレットとバイオレットの 2 つのセーブでは、ID の組、バージョン、言語、名前が一致しました。
各セーブが捕まえたポケモンと一致し、受け取ったものを提示している間も、セーブの名前を示し続けました。受信側のプレイヤー向けに作られた
ふしぎなおくりもの (`reference.identity_trainer`、
[受信側のプレイヤー向けに作られたもの](gift_simulated.md#made-for-the-receiving-player)) がこれを読みます。

チャンク 2 から 24 はエントロピーが高く、25 から 46 はゼロです。ステーションは一式を一度に送るのが普通で、
1 番目のパケットに ID 1、25、26 から 36、46、2 番目に 2、37、38 から 45 を入れ、その後は 3 から 24 を 1 パケットに 1 つずつ送ります (市販の 48 セットのうち 41 セット)。
同一のゼロチャンクは、存在バイト 0x00 の後ろで送られ、ヘッダーのフィールドはすべて継承されます ([メッセージのフレーミング](pia.md#message-framing))。
一式は通常 0.2 秒以内に送出されます (市販の 52 セットのうち 46 セットが 0.19 秒以内)。
`pokeldn.sv.streams.decompress` がこれを読み取ります。

`pokeldn.sv.reference` は、ステーションの 44 件のレコードと 2 つの識別子フラグメントを、0x7C のポート 0 で送ります。
これらは、プレイヤーが `Player`、アカウント識別子未設定のエミュレートしたスカーレットから記録したものです。`bin/sv_host.py`
と `bin/sv_join.py` は、`--record-set`、`--send-on-open`、`--no-identity` のいずれかを指定しない限り、これらを送ります。

### 市販機の確認応答と、再送の洪水

市販のステーションは、相手のレコードストリームを、連続する範囲の 1 つ先の ack ID と、フィールド 0x50 でそれと等しい値を使って確認します。
バイト *k* のビット *b* が ID `ack_id + 1 + 8k + b` を表すマスクも付けます。ID 1 から 4 と 7 から 38 を保持するホストは、
`0005 0005 feffffff01` を送ります。相手自身の `lowest_pending` より小さい ID は、保持済みとして数えます。
`pokeldn.sv.streams.ack_position` がこれを組み立てます (`tests/test_sv.py` で固定)。`bin/sv_join.py
--ack-highest` を付けると、代わりに見た中で最大の ID の 1 つ先を送ります。

ホストは、確認応答されていないすべてのレコードを、RTT の期限ごとにフラグ 0x40 で再送します。1 パケットに 1 ラウンドで、
ID の小さい順に送られ、確認応答が届くにつれて減っていきます。存在バイト 0x00 で止まるメッセージの走査では、
各ラウンドの先頭のレコードしか読まれず、19 ラウンドかかります。`--ack-highest` を付けると、`lowest_pending` が一度に 1 から
38 へ進みます。確認応答されていない場合、ホストは毎ラウンドすべての保留レコードを再送します。RTT が小さいと、
毎秒数百件 (HT MCS3 で毎秒 435 から 494 件、電波の約 3%) になり、ボードのシリアル線の 150 KB/s を埋めるのに十分な量になります
([シリアルの上限](hardware_esp32.md#the-serial-ceiling))。ラウンド間隔は、`[window+0x80] +
1.4 x RTT` をフレームに切り上げた値で、
参加側の応答遅延と比べると次のとおりです:

| 応答遅延 | 推定 RTT | ラウンド間隔、座席の中央値 |
|---|---|---|
| 0.000 s | 0.013 から 0.017 s | 0.065 から 0.069 s |
| 0.000 s | 0.033 から 0.038 s | 0.078 から 0.116 s |
| 0.000 s | 0.053 から 0.059 s | 0.115 から 0.221 s |
| 0.318 から 0.328 s | 0.354 から 0.363 s | 0.532 から 0.555 s |

レコードの間隔は、RTT のリングが埋まるにつれてそこに収束します (4 から 5 件の応答で 0.19 s、
8 から 18 件で 0.10 s、20 件で 0.082 s)。コンストラクタ `0x6eeea8`、送信バッファ `0x6e6e94`、エンキュー `0x6f1994`、
送信ループ `0x6f0638` は、unicorn の下で 1 回の処理で 46 件のレコードを送り、期限までは何も送りません。
ホスト自身の処理がペースを決めます。応答遅延にかかわらず、`lowest_pending` が 1 から進むのは、セットを送ってから 0.5 から 1.0 s 後です
(フレームすべてが 7 ms 以内に確認応答されると 0.73 から 0.81 s)。確認応答マスクは、約 0.19 s の刻みで進みます。
ホストは、参加側のストリームのオープンとレコードセットの約 0.1 s 後に、
自分のセットを送ります (`--open-delay`、`--record-delay`)。それ以前に保持している RTT 応答は、ラウンド間隔をその遅延より短くし、
参加側がすでに保持しているレコードを再送させます。RTT 応答を 0.3 s 遅らせると、これを避けられます。市販の座席では次のとおりです:

| セット前の RTT 応答数 | 応答遅延 | 座席数 | `lowest_pending` が 1 から進む前に再送されたレコード | 1 から進んだ後 |
|---|---|---|---|---|
| 0 または 1 | 0 | 3 | 2 件はなし、1 件は 138 | 0.78 から 0.81 s |
| 3 から 6 | 0 | 4 | 122 から 137。各 ID は 0.18 から 0.20 s ごと | 0.73 から 0.80 s |
| 0 | 0.3 s | 4 | なし | 0.91 から 1.01 s |
| 1 から 7 | 0.3 s | 9 | なし | 0.50 から 0.58 s |

`--rtt-delay 0.3` は RTT 要求に 0.3 s 遅れて応答します。これによりラウンド間隔が、ホストの確認応答の遅延より大きいままになります。
`--leave-on-migration N` は、コンソールが Session の type 7 を送ってから N 秒後に座席を終了します。
`--announce-timeout SECONDS` は、告知されていない座席を離れます。どちらも再びスキャンします。`bin/sv_join.py` は
新しいレコードはすぐに確認応答し、同じレコードの再確認応答は、ストリームごとに最大 50 ms に 1 回です (`--repeat-ack-gap`)。
パケットごとに、ストリームあたり確認応答は 1 件です。

RTT のサンプルがないと、0x81 ストリームは再送しません
([プロトコル 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6))。電波上で失われたレコードは保留のまま残り、
ホストの `lowest_pending` はその ID で止まって、相手は
告知されません。

RTT のサンプルは再送を有効にします。告知ジョブには RTT のゲートがありません。損失のないエミュレートしたスカーレット 4.0.0 のホストは、
RTT の要求も応答もなしに、告知して交換を完了します。識別レコードが欠けると、BoxTrade ジョブは状態 1 (`+0xb8`) に留まり、完了したスロットの数
`0x1e51ae8` は、必要な 2 に対して 1 のままになり、再送がセットを完了するまで続きます。

両方のランチャーは、保留中の識別レコードを再試行します。初期化子と中間レコードの欠落ケースは、
`tests/test_sv_identity_loss.py` のランチャー経由で完了します。パッチを当てたエミュレータは、これらの欠落がある状態で交換を完了しました。
市販のコンソールは、役割ごとに 2 回の交換を完了しました。
保留中の識別レコードは再試行され確認応答され、その後正常に退出しました。
確認応答が 47 に達した、前回の告知されなかった座席には、
どの送信チャンクが (あったとすれば) 失われたかを確かめる、独立した電波のキャプチャがありません。

### キャプチャ内の A-MSDU フレーム

両方のコンソールは、複数の MSDU を 1 つの A-MSDU フレームにまとめます。受動的なキャプチャは、サブフレームを展開しないと
Pia パケットの大半を失います (1 件のキャプチャで、展開しなければ 313 件が読め、展開すると 3667 件が読めました)。

## リンクコード

リンクコードは告知に 2 回含まれ、シーン ID は 4 のままです。ユーザーパスワードはそのコードで、
16 バイトまで NUL で埋められ、`e5ab19ed742b6d40885998bf968aa166` との XOR を取ったもの (Legends アルセウスのマスク) です。
同じゲームキーのもとで ([docs/pla.md](pla.md))。ゲームのバイト列は、+0x00 にコードを平文で、+0x24 に長さを u32 で入れます。
`pokeldn.sv.build_advertise_data(code=...)` は、市販のコンソールが
12345678 で検索する場合を、バイト単位で再現します。

検索中のコンソールは、そのコードを告知しているホストにだけ参加します (`bin/sv_host.py --code`)。市販の
コンソールは、コードのもとでホストになると、何も告知していない参加側を受け入れました。`bin/sv_join.py --code` は、
そのコードで検索しているコンソールにだけ参加します。

コードを確認するのは、検索中のコンソールだけで、スキャンしたネットワークに対してです。そのセレクタ `0x26e955c`
(参加の前に `0x272d838` から呼ばれます) は、コードを使って検索するときにパスワードのないネットワークを
スキップし (`0x26e95f4`)、コードなしで検索するときにパスワードのあるネットワークをスキップします (`0x26e960c`)。その後、
ゲームのバイト列を +0x00 から最初の NUL まで、自分のコードとともに FNV-1a 64 でハッシュします (素数
`0x100000001b3`、オフセット基底 `0xcbf29ce484222645` は `0x26e96c8` で読み込まれ、標準の
基底ではありません)。2 つが等しくない限りネットワークをスキップします (`0x26e972c`)。パスワードの
値も +0x24 の長さも読みません。

ホストは、参加側が送るものを何も比較しません。LDN の関連付けは固定のパスフレーズを使い、
Session の参加リクエストにはパスワードのフィールドがありません。接続するステーションに対する Pia のパスワード検査 (結果 7) は、
Net 0x32 ハンドラ `0x69ec50` (`0x69ee5c`、`0x69ee70`) にあり、Net 0x32 を必要とします。その唯一の送信元
`0x69d42c` は、プロトコルの vfunc 48 で制限されています: `LdnProtocol` (`0x6a2fac`) では 0、`LanProtocol`
(`0x6ba278`) では 1 です。参加側では、LDN の接続が Pia のネットワーク検査 `0x6a22c4` を実行し、そのパスワード比較
(`0x6a24a4`) は無効にされています (`0x6b0d90`)。

参加したコンソールは、コードを再度確認しません。Net 0x50 ハンドラ `0x69ea3c` は、システムプロパティのサイズ (0x5c)、
アプリケーションデータのサイズ (最大 0x124)、4 つの Pia の識別フィールド (`0x69d9d8`) を検証し、
バイト列をネットワークプロパティにコピーして (`0x69d8a4`)、Net 0x51 で確認応答します。システムプロパティやゲームのバイト列は、
1 バイトも比較しません。LDN では、そのコピーはキャッシュされた告知データに入り、次の `nn::ldn::GetNetworkInfo` (`0x6b30d4`) がそれを上書きします。ゲームがセッションの
最初の 0x28 バイトのゲームデータを読むのは、セレクタと UpdateSessionSetting (`0x26e63b8`) の中だけで、
そこでは自分のセッションを書き直します。他の 2 つの読み取り側 (`0x268e988`、`0x268e9bc`) は +0x28 より後ろだけを読みます。
参加したコンソールは、自分のコードを Pia のステーションパスワード (join オブジェクトの vfunc `0x274bdb8`、
セッター `0x6a208c`) として保持し、ホストになるときにだけ告知します。通信交換のポート 2 の type 1 は、
BoxTrade ジョブの状態 2 (`0x1e51b68`) から来ます: kind 1、静的な空の名前 `[0x46d3e30]`、
データはありません。

## Session プロトコル

`nn::pia::session::SessionProtocol` (id vfunc `0x6d9f3c` は 0x98 を返す) は、`JoinMeshJob`、`CreateMeshJob`、
`LeaveMeshJob`、`JoinSessionJob`、`SessionPacketReader`/`Writer` と並んでいます。メッシュへの参加は Legends アルセウスのものと同じです。
Session メッセージは、パケットヘッダーに相手の可変 ID を持ち、フッターがないので、ユニキャストで送られます。
参加側は、参加リクエストのソースロケーション ID に自分の可変 ID を書きます。
ホストは、関連付けの 0.14 s 後にそれを名前付けします。

### Session の参加リクエスト

Writer `0x6d5464`..`0x6d58b0`、ホストのパーサー `0x6d5aa4`。レイアウトは市販の Legends アルセウスのもの
(`docs/pla.md` の Session の参加リクエスト。`tests/test_pla_session_v11.py` では 115 バイト) で、
`pokeldn.ldn.pia6.build_session_join` が組み立てます:

    +0    1    type 0
    +1    1    protocol count, ten
    +2    2n   (id, version) pairs, walked from the protocol manager's list
    +22   4    random, xorshift128 seeded from the system tick (`0x6c70a8`, `0x6c7184`)
    +26   12   source location id: u64 constant id, two zero bytes, u16 variable id, big-endian
    +38   1    NAT mapping, two bits
    +39   1    private-IPv6 flag
    +40   32   identification token
    +72   1    address kind, 0 for IPv4 (1 puts an 18-byte IPv6 address in place of the six bytes)
    +73   4    source IPv4 address
    +77   2    source port, big-endian
    +79   12   destination location id, the host's
    +91   1    player count
    +92   1    a flag the job sets to 1
    +93   ..   player records: a 16-byte id (`1` then `0` as two big-endian u64), a big-endian u32
               name length, a kind byte (1), the name

市販の参加側の 1 人のプレイヤーは、スペース 1 つの名前になります。パケットヘッダーには宛先の可変 ID 0 が入り、
ソースには参加側の ID が入ります。すべての再送では、メッセージフラグ `0x01` (ソースの確認をスキップ) が付きます。
ホストは、次の順で確認します:

1. プロトコル数がホストのものと等しいこと。等しくなければ何も送りません。
2. すべてのバージョンがホストのもの (`0x6ed1b8`) と等しいこと。等しくなければ、ID とホストのバージョンを付けて status 3 を返します。
3. 宛先のロケーション ID がホストの constant id と variable id であること。そうでなければ破棄します。
4. ソースの constant id とアドレスがホストのものではないこと。
5. 既知の constant id には status 1 を再び返します。閉じたセッションには status 5。ホスト側のリスナーは
   status 4 で拒否できます。

参加レスポンス (type 2、43 バイト、`0x6d6390`) は Arceus のレイアウトです。type、protocol id、version、
status、ビッグエンディアンの u32、4 バイトのランダム値、両方のロケーション ID、ルートバイト A と B、ステーションインデックス、
参加順、ステーションの更新が到達すべきシーケンス ID からなります。参加側は type 5 の更新に対して、
13 バイトの type 6 (`0x6d80a4`) で応答します: type、constant id、2 バイトのゼロ、適用済みのシーケンス
(`pokeldn.ldn.pia_connect`)。

## 座席と、その上にあるアイデンティティの洪水

上記の参加リクエストが、ステーションを座席に割り当てます。市販のスカーレットのホストは 16 ms で受け付け、41 バイトの
参加レスポンス (status 1、ルートバイトなし) とルートのないステーション更新を送り、アイデンティティを
レコードごとに 1 回ずつ、0x81 のポート 0 で流します。参加側の確認応答を受け付けないホストは、座席が終わるまですべてのレコードを
再送し続けます ([ホストに確認応答として数えさせるフラグ
](#the-flag-that-makes-the-host-count-an-acknowledgement)): 市販機では毎秒約 350 件で、
1 件あたり最大 70 回の再送です。損失のないローカル LAN 上でエミュレートしたスカーレットに対しては、59 秒で 1 件あたり 676 回の再送になりました。
ホストは、ホストの役割を参加側に渡す Session の type 7 (`LeaveMeshWithHostMigrationJob`) を、
type 8 が応答するまで毎秒 1 回送ることもあります
([座席を決める要素](#what-decides-a-seat))。

### ホストに確認応答として数えさせるフラグ

フラグのビット 5 (ZLIB、`[msg+0x29]`、`0x6efc80`) が立ったメッセージは、ステーションの解決の前に `0x6e9984` (`0x69804c`、
zlib 展開 `0x2801d0`) で展開されます。失敗すると 0x2C03 (`0x6efd5c`) を返します。フラグ 0xA0 の素の
一括確認応答は、そこで失敗します (エミュレートしたコンソールでは 600 件中 600 件)。市販の 0xA0 の確認応答は zlib の本文を持ちます。
市販の参加側の 3 つのキャプチャにある 1,774 件はすべて、展開すると 99 バイトになります。`484b62606008` で始まる 38 バイトの本文は、
レコードの 4 KB ウィンドウ、level-5 の sync-flush フレーミングで再現します。フラグ 0x00 では
同じ 99 バイトが別の経路を通ります。ホストは各レコードを 1 回だけ送ります (毎秒 6.3 件、その後は送らず、
素の 0xA0 では毎秒 115 から 257 件)。市販の両方のステーションは、一括確認応答に 0xA0 を立て、/24 の LDN ブロードキャストに送ります。
`bin/sv_join.py` は、ビット 5 を立てるときに本文を圧縮します
(`--ack-flags`、`--ack-entries`、`--ack-dest-bits`、`--ack-sweep`)。

### ストリームの最初のレコードは INITIALIZED を持つ

ステーションの最初のレコードは、START、END、ZLIB を付けた INITIALIZED を持ち、フラグは 0x1F です。後続のレコードは
0x17 です。0x17 で送られた最初のレコードは確認応答されません (198 回の送信で)。0x1F で送ると、90 ms 以内に確認応答されます。
最初のレコードで zlib の一括確認応答と INITIALIZED を使うと、参加側の識別情報は、ソースの可変 ID とノンスを除いて、
ペアの参加側と 44 件すべてでバイト単位で同一になります。
エミュレートしたホストと市販のホストは、47 まで確認応答 (マスク `feffffffff01`、続く `field_0x50`) し、
レコードを 1 回ずつ送り、両方のステーションをプレイヤーブロックとともに並べた type 5 のステーション更新を出します。

## コンソールのためのホスト

Net 0x11 の 4 つのステーションスロットに加えて、ホストは次を送る必要があります:

| ホストが送るもの | 必要な内容 |
|---|---|
| Session の参加レスポンス | 41 バイト。ルートバイトなし、ステーションインデックス 1、参加順 1、シーケンス ID 0、+8 に 4 バイトのランダム値 (Arceus の 43 バイトの形式に対して再送されます) |
| Session の type 1 参加確認 | 何も送らない。市販のコンソールは、2 秒以内に残しておいた 1 つを送りました |
| Session の type 5 ステーション一覧 | 2 回。シーケンス ID 0 で参加レスポンスとともに送り、次の ID で再度送ります (市販のホストでは 1.5 から 2 s 後) |
| その一覧の各ステーション | 79 バイト。ロケーション ID、アドレスとポート、ステーションインデックス、ビッグエンディアンの u16 参加順、NAT バイト、IPv6 フラグ、32 バイトのトークン、件数、プレイヤーレコード。ルートバイトなし (Arceus は 81 バイト) |
| その中のプレイヤー名 | スペース 1 つ (0x20) |
| すべての Session 応答のメッセージフラグ | 0x00 |
| Reliable 0x7C の確認応答 | 1 エントリの形式で、宛先ビットマップなし。確認応答されないと、コンソールはチャンネルテーブルを終わりなく再送します (測定では 90 秒で 1000 回) |
| Reliable 0x7C のすべてのデータメッセージ | 9 バイトのヘッダー、destination_bits 0、ビットマップなし |
| Net 0x11 | 1 回だけ。繰り返すと、着席したステーションに対する新しい接続リクエストになります |
| Net 0x50、更新プロパティ | 0x11 の 0.2 s 後から、ステーションの 0x51 が来るまで 500 ms ごと。+0x82 に 40 バイトのゲーム告知バイトを入れます |
| RTT | 応答のほかに自分からも要求を送る (ペアのホストでは 410 ms ごと) |
| 開始 | 参加レスポンス、最初のステーション一覧、チャンネルテーブル、両方のストリームのオープン、クロックの応答、Net 0x50、そして座席直後の 44 件のレコードすべて (市販のホストでは 0.3 s 以内)。コンソールの交換画面が描画される前の key-0x80 のオープン ([チャンネルを開く](#opening-the-channel)) |

40 バイトのゲーム告知バイトは、セッションごとに変わります。ゼロか、+0x21 の非ゼロ値 (`648cf4`、
`8170f0`、`fb149700` を確認) で、残りはゼロです。`--channel 6`、`--player-name RyuPlayer`、`--host-player-id` を付けると、
`00000000000000010000000000000000` の NetworkInfo は、ライブのエミュレートしたスカーレットのホストと
セッション ID を除いて一致します。この設定では、コンソールの最初の参加が成立します。座席より上で失敗する
セッションでは、繰り返し参加が起きます (測定では 16 から 57 回)。

### lowest_pending と 5、6 の欠番

ステーションの ID 5 と 6 は送られません (ワイヤー上は 44 件のレコード)。残りは順序が乱れて送られます (ペアのホストでは
1、2、3、46、4、7、8、19、9、15、10、16...)。すべてのレコードは、`lowest_pending` 1、宛先ビット 3、ビットマップ `[2]`、
ストリーム ID 0 を宣言します。欠番は、送信側の同じストリームの次の一括確認応答で埋まります。その `lowest_pending` は 1 から 47 に進み、
相手は空のマスクで、セットを 47 まで確認応答します。1 のままだと、相手は `ack_id` 5、マスク `feffffffff01` で応答し、
これは全セッションで続きます。
欠番のない 1 から 44 の ID も受け付けられますが、市販の送信側はこれを使いません。

送信側が `lowest_pending` を進めてよいのは、確認応答されたレコードの先までだけです。初回の一斉送信の後で直接 47 へ進めると、
失われた識別チャンクを隠してしまうことがあります。相手は、StreamData ブロックが未完成のまま 47 を確認応答し、
そのステーションは告知されません。

両方の SV ランチャーは、識別セットのために `reliable5.SendWindow` を保持します。対応する一括確認応答の
エントリは、その `ack_id` より小さいレコードと、選択マスクで指定されたレコードを解放します。250 ms ごとに、
確認応答されていないレコードは、元のシーケンス ID と Pia のメッセージフラグ `0x40` で再送されます。
送信データと一括確認応答のヘッダーは、まだ保留中の最小のレコード、または全セットが確認応答されたときは 47 を宣言します。
これにより、実際の欠損を残しつつ、意図的な欠番 5 と 6 は維持されます。

最初の INITIALIZED レコードが失われると、44 件すべてが確認応答されず、セット全体の再試行が必要になります。
中間のレコードが欠けた場合は、それだけが再試行されます。

## 2 台の間での、ゲーム独自のプロトコル

2 台のエミュレートしたスカーレット 4.0.0 のインスタンスで測定しました。両者は交換を行い、それぞれが送ったすべてのデータグラムを記録しています。
交換は Reliable 0x7C 上で行われ、ブロードキャストのストリームは識別情報の交換だけを運びます。

### ポート 2: 告知、参加、応答

Reliable 0x7C のポート 2 (1 つのステーション) と BroadcastReliable 0x80 (すべてのステーション) が、ゲームの
セッションメッセージを運びます。ポーラー `0x1954978` は `[0x475ea70]` (`0x19549e4`) と `[0x475ea7c]` (`0x1954a54`) を読み、
ディスパッチャ `0x1954aec` に渡します: 先頭バイト、type 1 から 0xD、テーブル `0x3c68988`。3 つの type が
交換を開きます:

| 時刻 | ステーション | ワイヤー | type | バイト |
|---|---|---|---|---|
| 0.00 | ホスト | 0x80 のポート 2、zlib | 7 | 展開後 167: `07b901b905b906010200bc09`、9 個のゼロバイト、`bc8080`、128 個のゼロバイト、`000000b90183`、ホストのステーション ID、`00` |
| 0.09 | 参加側 | 0x7C のポート 2 | 3 | `03b90200bc09` と 9 個のゼロバイト |
| 0.15 | ホスト | 0x80 のポート 2 | 9 | `09b9030000b90183` と参加側のステーション ID |

エンコードは、チャンネルテーブルのもの (`pokeldn.ldn.channel_table`) に、バイト列のタグ `0xbc` を加えたものです:
タグ、整数としての長さ、バイト列の順です。type 7 は、5 要素のタプル 1 つからなるタプルです (ライター `0xe464fc`):

    b9 06 ...   the type-1 body as a tuple of six: kind, capacity, a zero byte, the name as a
                nine-byte string, the data as a 128-byte string, the data length
    key         body +0x8e, the relay's counter +0x1c4 before it steps
    index       body +0x8f, the relay's counter +0x1c0 masked to seven bits, before it steps
    b9 01 ...   a tuple of one u64, the station id of the type 1's sender
    0           body +0x98

type 9 は、参加のスロットキー、結果バイト、1 つの u64 からなるタプルです。

type 7 は、中継された type 1 です。type-1 ハンドラ `0x18ceb70` は、0x8e バイトの
本体を無条件にコピーし、キーとインデックスを刻印し、両方のカウンタを進め、送信者のステーション ID を追加して、
type-7 のコンポーザ向けにキューに入れます (キュー `+0x200`、ストライド 0xa8)。`0x18d5a58` は、1 つのステーションにポート 2 のメッセージを送り、
宛先が自分自身のときは `0x1954aec` を通してディスパッチします。そのためホストは、自分の type 1 を中継します。

type-1 の本体 (`0x18ab760`):

    +0x00  kind
    +0x01  the slot's capacity: 2 for kinds 1 to 3, 4 for kinds 4 to 8 and 12, 0 for kinds 9 to 11
    +0x02  zero
    +0x03  a name of up to eight characters, NUL-terminated in nine bytes
    +0x0c  up to 128 bytes of data
    +0x8c  the data length

交換の type 1 は、kind 1、capacity 2、空の名前、データなしです。スロットは本体をスロット `+0xd0` に保持し
(コンストラクタ `0x18b73a0`)、そのキー `0x12fcabc` (スロット `+0x15e`) は本体 `+0x8e` です。中継された
type 1 は、自分のものでも相手のものでも、すべてキーを進めます。カウンタをゼロにするのは `0x12fbef0` だけです。キー 0 を指定する参加は、
`03b90200bc09` のように、カウンタがゼロにされてからの最初の告知にだけ一致します。

type-3 ハンドラ `0x1981e94` は、参加の先頭フィールドをスロットキー (`0x1981ed4`) と比べ、
受け付けた場合は type 9 を `+0x270` にキューします。そうでなければ、type 0x0D、`0d b9 01`、コードを
`+0x350` にキューします:

| コード | 拒否の理由 |
|---|---|
| 1 | どのスロットも参加のキーを持たない (`0x1981ffc`)、または `0x279c8fc` が拒否する |
| 2 | スロットが満杯: 容量 `0x1e64914` の読み取りに対して `0x18f80c8` が判断する、または `0x279c9a0` が 0xfd を返す |
| 3 | 参加の名前の FNV-1a 64 ハッシュが、スロットのものと異なる (`0x1e648a0`) |
| 4 | スロットが閉じている (`0x1e64924`、スロット `+0x160`、スロット作成時にクリアされる) |

type 0x0D は `0x1954f3c` に渡ります。ここは `0xb9` を要求し、要素 1 つのタプルをデコード (`0x279c0e8`) して、
受信側 `0x279c1ac` (`0x1954f78`) を呼びます:

    0x279c1b8  ldr  x8, [x0, #0xb8]     the pending request
    0x279c1bc  cbz  x8, ret             none: nothing happens
    0x279c1d0  strb w9, [x8, #0x43]     result = the code
    0x279c1d8  strb #1, [x8, #0x42]     done
    0x279c1dc  bl   0xc8e6c4            wakes the request's waiter at +0x48

リクエストの種類 `+0x40` も done バイトも確認しないため、参加側からの 0x0D は、
コンソールがそのコードで保持しているリクエストを何であれ完了させます。type-9 の受信側 `0x18b65c8` は、スロットのバイトでオブジェクトを選び、
メッセージを適用します。u64 がステーション自身の ID でなければ、
それを破棄します (`[[0x46d0a08]] + 0xb8`)。

ステーション ID は、ビッグエンディアンの u64 としての Pia の constant id です
(MAC `02:00:7f:00:00:02` では `7f00020000020000`)。市販のコンソールに対して、type 9 は Session の参加リクエストの constant id を運びます。
`pokeldn.sv.port2` が 3 つを組み立てます (`tests/test_sv.py` で固定)。`bin/sv_host.py
--announce` は、座席の後に type 7 を送り、type 3 には type 9 で応答します。

### 告知を送る交換ジョブ

通信交換は、ジョブを `0x1e2ea54` で作成します: config `BoxTrade` (`0x3aefac8`)、ファクトリ `0x1e2f3d4`、
mode 4、need 2。2 つのスクリプトバインディングがこれに届きます: `0x1e2e9bc` (GOT
`0x46d6608`、`0x1b9c8c4` が `0x4717068` に格納、末尾呼び出し) と `0x1e2ec84` (GOT `0x46d6610`、
`0x1e2ee40` の `bl`)。ジョブ (コンストラクタ `0x1e3bd10`、vtable `0x44568a8`、Update `0x1e51a04`):
結果 `+0x40`、状態 `+0xb8`、セッションハンドル `+0xc0`、mode と need は u16 で `+0xc8` と `+0xca`、
スロットオブジェクト `+0xd0`、リクエストハンドル `+0xf8`。

| 状態 | アドレス | 内容 |
|---|---|---|
| 1 | `0x1e51a84` | ステーション数 `[[0x46d0a08]]+0xe0` が need を下回る場合は結果 3。`0x18ab520` が mode を拒否する場合 (0、5、8 超) は結果 1。それ以外は、タイムアウトなしで、完了した need 個の識別ブロック (`[[job+0xd0]+0x10] - 0x28` 上の `0x1e52004`) を待ち、マスターでは状態 2 (`0x1639910`: 自分の ID `+0xb8` がマスター ID `+0xc0` と等しい)、クライアントでは 4 に進みます |
| 2、マスター | `0x1e51b2c` | kind `0x18ab550(mode)` (mode 1 から 8 は 2、3、4、1、0、5、5、8 を返す)、続けてリクエスト `0x18ab658`。null なら結果 8 で終わります |
| 3、マスター | `0x1e51ca8` | リクエストを、タイムアウトなしで待ちます。結果 0 なら状態 6 へ、そうでなければ `0x1e5086c` を通してジョブが終わります |
| 4、5、クライアント | `0x1e51b8c`、`0x1e51c74` | 同じ待機で、上限は 15 s |

| 結果 | 意味 |
|---|---|
| 1 | 成功、または mode が拒否された |
| 2 | 状態 3 のセッション |
| 3 | need より少ないステーション |
| 4 | クライアントの 15 s タイムアウト |
| 8 | セッションがない、またはリクエストが拒否された |

リクエスト `0x18ab658` は type-1 の本体を組み立て、`0x18ab83c` を通して送ります。`0x18ab83c` は、
中継の保留リクエスト `[relay+0xb8]` の done バイト `+0x42` がまだ 0 の間 (`0x18ab860`、
`0x18ab8e8`)、または送信が失敗した場合に null を返します。それ以外は `+0xb8` をクリアし (`0x18ab894`)、新しいリクエストを格納し
(`0x18ab8a8`。`0x18abec0`: `+0x40` は type、告知では 0、`+0x42` は done、`+0x43` は結果)、
マスター ID へ type 1 を送ります (`0x18d58b8`)。マスター自身の場合も同じです。送信が失敗すると `+0xb8` をクリアします
(`0x18ab900`)。

`0x18ab658` の呼び出し元は 4 つあります: `0x1e51b68` (BoxTrade 状態 2)、`0x18ab34c` (兄弟のジョブで同じ、
vtable `0x4456490`)、`0xa188f0` (vtable `0x4452e68`)、`0x1d99568` (vtable `0x44536d8`)。`+0xb8` に書き込むのは
4 つのリクエスト作成者だけです。`0x18ab83c` と `0x2799b10` は、保留中のリクエストがあると拒否します:

| 作成者 | リクエストの種類 | 格納 | 唯一の呼び出し元 |
|---|---|---|---|
| `0x18ab83c` | 0、告知 | `0x18ab8a8` | `0x18ab658` 内の `0x18ab6bc` |
| `0x2799b10` | 2、クライアントの参加 | `0x2799bd8` (ガード `0x2799b2c`..`0x2799b40`) | `0x1e635fc` |
| `0x2799c44` | | `0x2799cfc` | `0x1e639ec` |
| `0x2799d6c` | | `0x2799e30` | `0x1e63c88` |

後ろの 3 つの呼び出し元は、それぞれ、唯一の呼び出し元が `0x1d98xxx` にある関数の中にあります (`0x1d986d8`、
`0x1d98990`、`0x1d98c20`)。

通信交換では、type 2 の作成者は、`0x1e51c40` の BoxTrade 状態 4 から、
`0x1d986d8` と `0x1e635fc` を経由して到達します。マスターのスロットが存在した後 (`0x1d999f4`、`0x18c7a40`) に、クライアントでだけ動き、
リクエストをジョブの `+0xf8` に保持して、状態 5 に入ります。`0x1d98698` の他の呼び出し元は、
他のジョブのクラスに属します。

ドレイン `0xe44cf0` は、キュー `+0x1c8`、`+0x200`、`+0x238`、`+0x270`、`+0x2a8`、`+0x2e0`、
`+0x318`、`+0x350` を順に走査します。コンポーザが false を返すとそのフレームのドレインは終わるため、詰まった
type 7 は、その後ろの type 9 と 0x0D を止めます。
type-7 のコンポーザ `0xe45740` は、ステーション数が 1 のときはローカルにだけディスパッチします。そうでなければ、
`BroadcastReliableProtocol::vfunc20` (`0x6e6638`) に、0x80 のポート 2 から送れるかを問い合わせ、
`0x107e060` で送ります。両方が成功したときだけローカルにディスパッチします。vfunc20 は、宛先リスト `[window+0x40]` の
どのエントリも設定されていないと 0x2c27 で拒否します (`0x6efb98`)。ウィンドウにフラグメントの空きがないと 0x4c0d (`0x6f1ef8`)、
セッションまたはウィンドウがないと 0x10408 で拒否します。Pia は、ステーション参加イベントで宛先リストを埋めます
([ウィンドウの送信先](pia.md#who-a-window-sends-to-pia-6))。

type-7 の受信側 `0x18b566c` は、スロットを作成して適用します。保留中の type 0 のリクエストと、
コンソール自身のステーション ID (本体 `+0x90`) については、結果 0 で完了させます。マスターは、自分の type 7 がワイヤーに出るまで状態 3 に留まります。
中継からワイヤーまでの間では、RTT もタイマーも読まれません。

0x81 の識別情報は、ステーションごとに 1 ブロックで、そのインデックスのポート上にあります (ハンドル `0x475ea48 + 4*index`)。
1 つのレイアウトを持つ 3 つのオブジェクトについて、ストリームの送信 API `0xe22188` と受信 API `0xe22458` が動かします:

| オブジェクト: Update、vtable | 送信 | 受信 | ブロック |
|---|---|---|---|
| `0xe21104`、`0x4455ec0` のスロット 13 | `0xe21a44`、`0xe21dc4` の `bl`、`0xe21db8` の `w2 = 0xf388` | `0xe2150c`、`0xe2170c`、`0xe21708` の `w3 = 0xf388` | 0xF388 = 62,344 |
| | `0xa62c5c`、`w2 = 0xff008` | `0xa64ddc`、`w3 = 0xff008` | 0xFF008 = 1,044,488 |
| `0x1e5f87c`、`0x4458698` のスロット 13 | `0x1e617a8`、`0x1e61980`、`w2 = 0x97e08` | `0x1e61a74`、`0x1e61c0c`、`w3 = 0x97e08` | 0x97E08 = 622,088 |

交換でワイヤーに出るのは 0xF388 ブロックだけなので、ジョブの `+0xd0` オブジェクトはそのクラスに属します
(インスタンスは未追跡。`0x1e34b6c` -> `0x1e35e88` を通して構築)。

`0x1e52004` は、バイト `+0xd8` が立った相手のポインタを保持する、`+0xd0 + 0x30*k` の 4 つのスロットを数えます。コンソール自身のスロットは、
`0xe21154` でこれを得ます (`0xe21248` の `memcpy(slot, [+0x90], 0xf388)`、`0xe21258` の `+0xd8 = 1`。
`0xa536e0`、`0xd6dc88`、`0xe21128`、`0x195160c` から呼ばれます)。相手のスロットは、
`0xe212b8` (`0xa536f0`、`0xd6dc98`、`0xe21138` から呼ばれます) でこれを得ますが、
相手への送信 (`+0xda`) と相手からの受信 (`+0xd9`) が始まり、自分の 0x81 ストリームが状態 3 (`0xe2144c`、自分のチャンクがすべて確認応答済み)、
相手のストリームが状態 6 (`0xe21404`、相手のチャンクをすべて受信済み) にある場合に限ります。状態 7 はフラグを消去します
([プロトコル 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6))。0x97E08 のクラスには、
同じペア `0x1e60284` と `0x1e615e8` があります。

ワイヤー上では、type 7 はコンソールが自分のセットの最後のレコードを送った後に続き、通常は 0.11 s 以内です
(告知された 40 件の座席のうち 37 件で 0.020 から 0.106 s、他では 0.545、0.864、3.902 s)。

中継は 0x388 バイトのオブジェクト (vtable `0x44e56f8`) で、シングルトン `[0x46da9c0]` = `0x4739430` です。
存在しない場合にだけ、`0x1659b70` から `0x165a200` が作成します (`0x1659b18`)。ステーションイベントの
ハンドラは `0x2b71650` のサンクを通した `0x12fbb90` です:

| イベント | 効果 |
|---|---|
| 0、ステーションの参加 (マスター上) | `0x12fbf8c` が、自分がマスターでない限り、現在のスロットを送ります |
| 1、自分の ID | done でない保留リクエストは結果 5 で完了します (`+0x42` の `0x501`)。その後 `0x12fbef0` |
| 1、マスターの ID | `0x12fbef0` |
| 1、任意のステーション (マスター上) | その後、`0x12fcebc` が中継した要素を破棄します |

`0x12fbef0` は、`0x12fc644` を通してすべてのスロットを削除し (キーが一致する保留中の type-1 リクエストを完了させます)、
7 つのキューを空にし (`+0x1c8` 以外のすべて)、`+0x1c0` と `+0x1c4` をゼロにします。リクエストは `+0xb8` に残します。
type-0 のリクエストは、type-7 の受信側、type-0x0D の受信側、
自分の退出イベントによってだけ完了します。type 2 は type-9 の受信側 `0x18b6710`、type 3 は type-0xA の受信側 `0x1945404`、
type 4 は type-0xB の受信側 `0x279be18` によって完了します。

`0x12fbc3c..0x12fbc4c` の自分の退出経路は、クライアントの保留中の type-2 リクエストを
結果 5 で完了させます (`+0x40..+0x43 = 02 00 01 05`)。次の作成者は、その完了したリクエストを、
ゲームを再起動せずに置き換えられます。type-9 の受け付けの前に切断された場合も含みます。マスターの ID だけの退出イベントは、
リクエストを完了させません。`0x12fbc70..0x12fbc84` が呼ぶのは
`0x12fbef0` だけです。クライアントの BoxTrade ジョブは、状態 5 がウィークリファレンス `+0xf8` を通して
リクエストをポーリングする (`0x18ab588`、`0x18ab614`) 前に時計を確認する (`0x1e51c74..0x1e51ca4`、基準 `+0x108` は `0x1e51c6c` で設定) ため、15 s で結果 4 となって終わります。
タイムアウトの経路 `0x1e51d50` も、ジョブのデストラクタ `0x1e51740` も、中継のリクエストには触れません。
デストラクタは、`0x18ccdb4` を通してウィークリファレンスを解放するだけです。
リクエストは中継の `+0xb8` に保留のまま残り、`0x2799b10` と `0x18ab83c` は、
type-9 または type-0x0D の受信側、またはクライアント自身の退出イベントがそれを完了させるまで、
拒否します。

中継は、アプリケーションが終了するまで生きています。そのため `+0xb8` の保留リクエストは、
完了させる処理が動くまで、すべての座席、検索、メニューをまたいで残ります。その保持者 `0x4739430` (GOT `0x46da9c0`、ガード `0x4739440`、
GOT `0x46da9b8` 経由) は、代入 `0x165a2b4` (作成者から、`0x165a230` の `bl`) によってだけ書き込まれます。
リセット `0x279d610` (`0x279d62c` の `str xzr`、その後デストラクタと解放) は、
中継自身の破棄スロット `0x279d5ac` (スロット 3) と `0x2b71660` (`+0x20` インターフェースのスロット 1) からだけ到達します。
これらには直接の呼び出し元がなく、静的なデストラクタ `0xa15f74` (`__cxa_atexit`) があります。
スロット 3 の一般的な仮想呼び出しは、静的には除外できません。vtable `0x44e56f8` は、スロット 0 が `0x279a7b0` (デストラクタ)、
1 が `0x2b7164c`、3 が `0x279d5ac`、4 が `0x12fbb90`。インターフェース `+0x20` のスロットは `0x2b7165c`
(`ret`) と `0x2b71660`、インターフェース `+0x28` はリスナーのサンク `0x2b71650` です。基底コンストラクタ
`0x165b0c8` (`0x165a998` から) は、同じ破棄スロットを持つ 2 つ目の vtable `0x44e5768` を設定し、
`[holder+8] = 1` を設定します。

作成者は、`+0x20` インターフェースを `0xf0ba9c` (`0x165a244` の `bl`) でファイナライザのリストに登録します
(`0x4763a18` に最大 0x400 エントリ、件数 `0x4765a18`)。これは逆順に、`0x27aff48` (スロット 0) と
`0x27b0054` (スロット 1、その後件数をゼロにする) だけが走査します。どちらも `0x20e9c78` からだけ呼ばれます。これは vtable `0x44e6be0` のスロット 5 で、
`0x92d648` (`0x443ffd0` のスロット 5) から、
`nn::account::CloseUser` に至る経路上にあります。これはアプリケーションのファイナライズです。

02 は、4 番目のバイトで 03、06、0B、0E と進みます。

交換メニューに戻ります。

メッセージ 3 と 4 です。ホストのオファーに対するその確認応答は、`ack_id` 6、`lowest_pending` 5 と読めます。同一のトレーナー 2 人でも交換できます。

### ステーション自身のオファーより先に送られる確認

オファー `80000200` がまだキューにあるうちは、確認 `80000300` を送ってはいけません。市販のコンソールは、その順で送られると
クラッシュしました (黒い画面、システムエラー)。レコード自体は検査されずに格納されていました。両方のランチャーの `--offer-after-open` は、
相手の key-0x80 の告知を待ってオファーを保留させます。どちらのランチャーも、
同じステーションとポートで既にキューにあるメッセージより前に、交換メッセージをキューしません。

交換のアニメーションは、コンソールの最後のステップ `8001010e` に続き、交換メッセージは運びません。
ステータス `b90101b902b90280800100` の後、コンソールはプレイヤーが抜けるまでアプリケーションデータを送りません。

### 1 つの座席での複数の交換

キー 0x0080 は開いたままで、キー 0x0180 は交換ごとに開いて閉じます。2 回目の交換は、同じ周期を、
シーケンスを続けたまま繰り返します (ホストのオファー 16、確認 17、コミット 18、ステップ 19 から 26)。新しい関連付け、Session の交換、識別情報はありません。
`TradeStage` と `JoinerTradeStage` は、交換ごとに 1 件ずつのレコードのリストを受け取ります。`--trade-offer` は
繰り返し指定できます。コンソールがホスト移行を要求した後で座席を保持することは、未確認のままです。

### 最初のゲームメッセージと、その内容

`80 00 01 00` と 2557 バイトは、2 つの信頼性フラグメントで、START の後に END として送られます
(圧縮 238 バイト、ペアのホストから。市販のコンソールからは 195 バイト)。それぞれが独自の zlib ストリーム (`484b`) で、
メッセージは 2 つの展開結果を連結したものです:

    b9 02          a tuple of two fields
    bc 81 f6 09    a blob, 0x9f6 = 2550 bytes
    ...            2550 bytes
    04

blob は、リトルエンディアンの 3 バイト値 850 個からなり、大半は 1 です。残りはビットマスク (`0x0fffff`、
`0x0002ff`、`0x00003f`、0) で、ステーションごとに値が異なります (市販のコンソールとペアのホストの間で 38 エントリ。
エントリ 36 は `0x040000` と `0x0fffff`)。インデックスが何を数えているかは不明です。トレーナーのフィールドは含まれず、
市販のコンソールのものには、ID の組も名前も現れません。ペアのホストの
4 つのフラグメントを再生すると、市販のコンソールに受け付けられます。

### 交換メッセージが運ぶレコード

`80 00 02 00` メッセージの 348 バイトの本体は、定数 `bc 81 58 01` と、Gen 8 の暗号 (`pokeldn/gen8.py`) のもとでの 344 バイトの Gen 9 のパーティレコード (PKHeX の PK9) です。
0x08 から始まる 4 つの 0x50 バイトのブロックは、`(EC >> 13) & 31` で並べ替えられ、16 ビットの語に対して
LCG `seed = seed * 0x41C64E6D + 0x6073` が使われます。復号した本体の 0x148 までの 16 ビットのチェックサムがあります。
0x148 のパーティ末尾は、並べ替えとチェックサムの外にあり、
暗号化定数から LCG を再シードします。

    0x000  u32  encryption constant, in the clear
    0x004  u16  sanity, 0 on every record measured
    0x006  u16  checksum, in the clear
    0x008       four 0x50-byte blocks, encrypted and permuted        -> 0x148
    0x148       level, a pad byte and the six stats, encrypted       -> 0x158

フィールドの対応は PK9 ([`PKHeX.Core/PKM/PK9.cs`]) のものです。`pokeldn/gen9.py` がこれを読み書きします。

(`tests/test_sv_pokemon.py`)。種族は内部インデックスで、917 のところで全国図鑑の番号と食い違います

348 バイトの本体、または 352 バイトのメッセージを受け取ります。

### 組み立てたレコード

`pokemon.build` で零バイトから組み立てた、または `bin/sv_host.py --offer-set` (ニックネーム、ニックネームのフラグ、性格値、個体値) で編集したレコードは、
市販のスカーレットのセーブに、組み立てたとおりのすべてのサマリーフィールドを保って交換されます。交換画面は、
組み立てたレコードに適法性の検査をせずに描画します。ホストがチェックサムを書きます。サマリーのトレーナー ID は、
`(TID16 | SID16 << 16) % 1000000` です (12345 と 54321 は 993401、8131 と 64817 は 855043 と描画されます)。
特徴の行は、暗号化定数と個体値から得られます。

レベルは経験値に従います。0x148 の値が 100 で経験値がゼロのものは、レベル 1 として届き、
経験値 1,000,000 のものはレベル 100 として届きます。6 つの成長曲線 (`PKHeX.Core/PKM/Util/Experience.cs`) は、
レベル 100 でそれぞれ 1,000,000、600,000、1,640,000、1,059,860、800,000、1,250,000 を必要とします。種族テーブル
`personal_sv` (種族とフォルムごとに 0x50 バイト、`PersonalInfo9SV.cs`) は、0x00 に基礎ステータス、
0x0C に性別比、0x0F に成長曲線、0x12 に 3 つの特性を持ちます (種族 132: 曲線 0、特性 7、7、
150)。受け取ったゲームはパーティのステータスを再計算します:

    HP    = (2 * base + IV + EV/4) * level / 100 + level + 10
    other = ((2 * base + IV + EV/4) * level / 100 + 5) * nature

個体値が完璧で努力値がなく性格が補正なしのメタモンは、レベル 1 で HP 12、その他 6 x5、
レベル 100 で HP 237、その他 132 x5 と表示されます (ステータスのフィールドはゼロから)。レベル 1 で送られた HP 99/99 は、12 として届きます。

### 交換での参加側の側

ペアの参加側の 0x7C の全スクリプトです。各メッセージのシーケンスを、そのポートとともに示します:

| ポート | シーケンス | メッセージ |
|---|---|---|
| 1 | 1 | チャンネルテーブル、ホストの 4 つのキー、INITIALIZED |
| 2 | 1 | type 3 の参加、`03b90200bc09` と 9 個のゼロバイト |
| 0 | 1 から 4 | 最初のゲームメッセージ (2 回分) |
| 1 | 2 | `b90101b902b90280800001`、key 0x80 のオープン (4 番目のフラグメントの後) |
| 0 | 5 | 提示するポケモン |
| 0 | 6 | 確認 |
| 0 | 7 | コミット (先に送る) |

識別情報は、ホストの key-0x80 のオープンの 0.15 s 後に送られ、参加側自身のオープンはその 0.21 s 後です。

--trade-offer` で動きます (key-0x80 のオープンで制御される識別フラグメントには `--send-on-open` を使います)。
`tests/test_sv.py` は、ペアのメッセージのホスト側の半分でこれを駆動し、参加側の半分を固定します。

| `current_handler` | 0 | 1 |
| `ht_name` | 空 | コンソールのプレイヤーの名前 |
| `ht_language` | 0 | 受け取ったコンソールの言語 (3、フランス語) |
| `ht_friendship` | 0 | 50 |
| `nickname` | 空 | コンソールの言語での種族名 |
| `current_hp` | 0 | 計算された最大 HP (237、レベル 100 のメタモン) |
| `stats` | ゼロ | ゲームが計算する 6 つ |

それ以外はすべて、送ったとおりに保たれます。空の名前は、ソード・シールドのふしぎなおくりものレコード
(`docs/swsh_gift.md`) と同じく、種族名として戻ってきます。

元のトレーナーが受け取る側のセーブであるレコードは、手持ち 0 と手持ちの名前なしのままになります。Legends Z-A と同じです
([受け取ったレコードに交換が書き込むもの](za.md#what-the-trade-writes-into-a-received-record))。
市販のバイオレットのトレーナー向けに、そのセーブが捕まえたポケモンから作られたふしぎなおくりもののポケモンは、
([受信側のプレイヤー向けに作られたもの](gift_simulated.md#made-for-the-receiving-player))、交換後もそのように戻ってきました。

### 検索中のコンソールへの参加: 交換と、座席を決める要素

`bin/sv_join.py` は、通信交換の検索でホストになっている市販のスカーレットと交換します。番号付けはペアの参加側と同じです。
ステーション更新を座席として受け取り、コンソールの告知には type 3 の参加で応答します。
コンソールが key 0x80 を開いた後に、4 件の識別メッセージを送り、
上記の `lowest_pending` の規則を適用します。

#### 座席を決めるもの

検索で待機してホストになった市販のコンソールは、ゲームを実行するか、ホストの役割を参加側に渡します。
ゲームは、3 から 7 回の閲覧試行の後に 1 回ホストになり (`RandomMatchingSeq` `0x26e182c`、カウンタ
`rand%5+4`)、メンバーを 3000 + rand%1000 ms 待ち、参加してきたメンバー 1 人につき 5000 ms 追加します
(WaitMember、`0x26df898`)。待機がタイムアウトすると JoinRandomRecover `0x26f507c` に入り、
セッションを離れます。ほかのステーションが残っている状態でホストが離れると、`LeaveMeshWithHostMigrationJob` が動きます
(メッシュの退出 `0x6d4040` からだけ始まります)。Net のランキングが最も低いステーションに Session の type 7 を送り (`0x6a012c`)、
その後 NetStartHostMigration `01400000` を、最大 4 s まで 0.3 s ごとに送ります
([退出](#leaving))。WaitMember の中で参加が受け付けられた参加側は、ゲームが動くのを見ます。その後、退出の最中に受け付けられた参加側は、
受け付けの 1 フレームか 2 フレーム後に type 7 を受け取ります。参加側のオープンは影響しません。
`--join-delay 5` は、市販のスカーレットとの最初の座席で type 7 を引き出しました。
告知の後にプレイヤーがコンソールから抜けた場合も、type 7 を送ります。

役割を渡したコンソールは、自分のネットワークを破棄して、再び閲覧します。`--take-host`
(既定) は、告知の前に type 7 を受け取った `bin/sv_join.py` に、
座席のチャンネルとコードで、アプリのホストフラグを付けて `bin/sv_host.py` を実行させます (`bin/pla_join.py` が Legends アルセウスに対して行うのと同じです)。
市販のスカーレットは、そのホストに参加し、交換を完了しました。

ゲームを実行すると、コンソールは次の順で送ります:

| | |
|---|---|
| 座席 | 参加側の可変 ID と、そのリクエストが述べたプレイヤー ID を示す type 5 のステーション更新。その後に 41 バイトの参加レスポンス |
| 自分のオープン | 11 本すべてのストリームの一括確認応答、0x81 のポート 1 の 11 バイトのレコード、ポート 5 の別のレコード |
| 自分の識別情報 | 0x81 のポート 0 の 46 件のレコード。参加側の 44 から 47 を確認応答します |
| 自分のチャンネルテーブル | 0x7C のポート 1、キー `0x007b`、`0x0132`、`0x0232`、`0x0332` |
| `0db90101` | 0x7C のポート 2、コード 1。告知の前に送られた type 3 の参加に対する応答としてだけ |
| 告知 | 0x80 のポート 2、zlib、展開後 167 バイト: kind 1、capacity 2、コンソールのステーション ID を持つ type 7 |

参加側は、告知に type 3 の参加で応答します (`--port2-now` を付けると、代わりにチャンネルテーブルとともに送ります)。
市販のコンソールは、参加レスポンスより前に、ステーション更新だけで参加側を座席に着かせました。参加レスポンスを待つ参加側は、
セッションの間ずっと何も送りません。

## 退出

座席を離れるコンソールは、役割に応じて、Pia のジョブのどちらか一方を実行します。どちらも相手を待ち、
タイマーで諦めます。

参加したコンソールは `LeaveMeshJob` を実行します。SendLeaveRequest `0x6db590` は Session の type 3 の退出リクエスト
([docs/pla.md](pla.md#leaving) のレイアウト) を送り、500 ms の期限 (`0x6db6a0`) を設定します。WaitLeaveResponse `0x6db7b0` は、
期限切れで再送し、4 回目の送信の後 (`[job+0x6c]` が 2 を超えた後、`0x6db8e8`)、または `[job+0x69]` が立つとすぐに完了します。
Session のディスパッチャ (`0x6d4960`、テーブル `0x3c0cd3b`、type 0 から 0xA) は、type 4 を `0x6d7b10` に渡します。
これは、バイト 5 から 16 がステーション自身のロケーション ID である 17 バイトのメッセージに対して、
`[job+0x69]` を立てます:

    04 | u32 random | location id (12), copied from the request

type-3 のハンドラ `0x6d7894` は、ステーションを constant id と variable id で見つけると、まさにそれを書きます (type バイトは `0x6d7a50`、
新しい xorshift の値は `0x6c70a8` から取り、`0x6d7ad8` で送られます)。
応答がないと、市販のコンソールは、0.49 から 0.54 s 間隔で退出リクエストを 4 回送り、
最初の 2.04 s 後に認証を解除します (追跡した 1 セッション)。応答があると、退出リクエストを 1 回送り、
その 0.04 s 後に認証を解除します。
`bin/sv_host.py` は最初の退出リクエストに応答します (`--no-leave-response` で応答しないままにできます)。
`tests/test_sv_departure.py` は、unicorn の下で、その応答を `0x6d7b10` に通して実行します。

検索からホストになったコンソールは、ホストの役割を引き渡します。`LeaveMeshWithHostMigrationJob` は、次のホストに Session の type 7 を送り、
type 8 がそのステーションを指名するまで毎秒再送します (`0x6df050`、判定は `0x6ded94`)。5 s (`0x6defb8`) で諦めます。
type 7 (ライター `0x6d8de0`) は 34 バイトです:

    07 | host location id (12) | 00 | host IPv4, port | next host's location id (12) | u16

最後の u16 は、ジョブの `+0xe0` (`0x6d8ea8`) で、市販の 3 つでは 0 または 1 でした。その後、
ホスト移行の形の `NetDestroyNetworkJob` が、すべてのクライアントが接続状態の更新を受け取るまで待ちます (最大 4 s、`0x6ac68c`)。
NetStartHostMigration `01400000` は (書き込みは `0x69d310` だけ、呼び出しは `0x6aca54` からだけ)、
300 ms ごと (`0x6aca98`) に、ネットワークのステーション数が 1 になる (`0x6acaf4`) か、期限が過ぎるまで送ります。
期限は 4 s で、更新の待機がタイムアウトした場合は 2 s です (`0x6ac984`)。その後 LDN ネットワークを破棄します。
ワイヤー上では、更新は移行中フラグを立てた Net 0x11 です。参加側の Net 0x12 の後、最初の NetStartHostMigration が 45 ms 遅れて続きました。
クライアントが NetStartHostMigration でどのジョブを開始するかは未追跡です。
`NetHostMigrationJob` は DisconnectNetwork または EmulateDisconnection (`0x6a93c4`) で始まります。

type 7 にすぐ応答して座席を保持する参加側は、コンソールから NetStartHostMigration を 12 から 14 回受け取ります。
最後のものは type 7 の 3.5 から 4.1 s 後です。追跡した 1 つの座席では、コンソールのネットワークは type 7 の 4.3 s 後に落ちました
(ethertype `88b7` の LDN ブロードキャストの後)。type 7 の 3.0 s 後に退出した参加側は、コンソールの告知が 0.5 s 以内に消えたのを確認しました。
これはコンソール自身の 4 s の期限より前です。`bin/sv_join.py` は、最初の NetStartHostMigration で座席を離れます
(`--stay-on-host-migration` で保持できます)。
type 7 の 0.14 s 後にネットワークから外れます。
その時点で NetStartHostMigration は 1 回送られています。

交換が完了した後、コンソールが離れると、両方のランチャーは終了します。交換を完了しなかった座席では、
`bin/sv_join.py` は検索を再開します ([実行の終了](architecture.md#ending-a-run))。
