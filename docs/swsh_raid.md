# マックスレイドバトル

ローカルのマックスレイドバトルは、LDN シーン 60006 の上で最大 4 ステーションまで参加できる Sword/Shield のセッションです。ホストは
巣穴から「Invite Others」で開き、ゲストは自分の Y-Comm リストでそれを見つけ、ホストの名前に対する「Start Battle」で参加します。
ロビーは信頼性のあるブロードキャストプロトコル 0x80 で動き、バトルは 0x7C で動きます。
`bin/swsh_connect.py --scene 60006 --raid-join --offer-slot N` は、本体のロビーにゲストの席を取らせます。
ロビーには、選んだポケモンと共にその席が表示されます。

## ネットワーク

| 項目 | 値 |
|---|---|
| LDN シーン ID | 60006 (フィールドでは 65535) |
| 参加者 | 開いた時点では 4 人中 1 人 |
| アドバタイズデータのバイト `0x97` | `0x11` |
| Pia セッションの上限 | 4 (`0x0110e5e0`。巣穴のロビーの `0x01031c74` から呼ばれる) |
| アドバタイズの `0xb0` と `0xd4` | ボスと巣穴の記録 ([巣穴の記録](#the-den-record)) |

巣穴のロビーのコードは、`View_NestHole`、`StateGuestReady`、`StateHostReady` と並んでいます
(`0x0102aba4..0x010370cc`)。ダイマックスアドベンチャーのマッチングは `ChikaMatchingState*`
(`0x00bd1978..0x00bda158`) を通り、`0x00bd9b30` から同じ Pia セッションの上限を呼び出します。

ゲストの Y-Comm リストからは、アドバタイズにゲスト自身のデバイス ID と
アカウント uid を含むレイドが除かれます ([巣穴の記録](#the-den-record))。

## ロビーのメッセージ

すべてのロビーメッセージは ID 2000 で、`net_contents.nesthole.protocol_buffers.NestholeAsyncDataHolder` です
(記述子は `main` 内の `0x1bfde43` と `0x20677b0` にあります)。各フィールドは、`bytes` 型の
フィールド 1 を一つ持つホルダーです。

| フィールド | 名前 | サイズ | 内容 |
|---|---|---|---|
| 1 | NestholeTimeLimit | 4 | 残り秒数の u32。ホストは毎秒 3 回送ります |
| 2 | NestholePlayerInfo | 40 | 8 バイトのゼロ、u32 (0x11 は製品版 Sword、0x12 はエミュレートした Shield)、13 文字の UTF-16 名、`00 03` |
| 3 | NestholeBattleReady | 16 | プレイヤーが準備完了を押すとバイト 8 が 1 になります。バトルが始まるとバイト 12 が 1 になります |
| 4 | NestholeSelectPokemon | 352 | 8 バイトのゼロ、続けて選んだポケモンを暗号化されたパーティ PK8 (0x158) として格納 |
| 5 | NestholeBattleStart | 32 | 参加者の Pia 定数 ID を 4 つの u64 で格納 (先頭はホスト)。未使用の枠はゼロ |
| 6 | NestholeBossPokemon | 364 | 19 バイトのゼロと `ff`、続けてボスを暗号化されたパーティ PK8 として格納 |
| 7 | NestholeRewards | 120 | 15 組の u32 のペア (アイテム ID、個数)。未使用のペアはゼロ |
| 8 | NestholeBattleSeed | 16 | u64 のシード、続けて `00 ff ff ff 1e 00 03 00` |

PlayerInfo は、信頼性フラグ 0x10 を付けて、4 KB ウィンドウの zlib 圧縮 (ヘッダーは `48 4b`) で送られます。
ほかのフィールドは圧縮せずに送られます。`pokeldn/swsh/raid.py` がすべてのフィールドを組み立てます。その出力は
エミュレートしたゲスト (2、3、4) とエミュレートしたホスト (5 から 8) のバイト列と一致します。

ボスのレコードには、種族、レベル、技、個体値、PID を含むボスの情報がすべて入っています。2 回の
エミュレートしたレイドでは、BattleSeed の値に巣穴のレイド生成処理を適用しても、
ボスの暗号化定数も PID も得られませんでした。シードが何に使われているかは未解析です。

## ゲストの流れ

2 台のエミュレートした Shield の間で記録した、レイドを最後まで勝利した流れです。

1. 0x84 でのスナップショット交換 (通信交換と同じ方式)。ホストのスナップショットが先に送られた。
2. PlayerInfo、BattleReady (ゼロ)、SelectPokemon を 0x80 のポート 0 で、シーケンス 1 から 3 として送る。
3. プレイヤーが準備完了を押すと、バイト 8 を立てた BattleReady を送る。
4. 全プレイヤーが準備完了になると、ホストは BattleStart、もう一度の SelectPokemon、BossPokemon、
   Rewards、BattleSeed、そしてバイト 8 と 12 を立てた BattleReady を送る。
5. ゲストは SelectPokemon をもう一度送り、その後バイト 8 と 12 を立てた BattleReady を送る。
6. バトルは 0x7C で始まる。ポート 0 のシンク ping 80、ポート 1 のフレームワークメッセージ 40000、
   その後は各ターンごとにポート 0 の 10000 と 20000 のメッセージ。

製品版 Sword のホストに対して、バイト 8 を立てた BattleReady の後で止まるゲストは、ホストの
プレイヤーを、ホスト自身の準備完了の後も "Connexion en cours" のまま残し、エラー 2-ALZAA-0016 で終わります。

## バトル

ホストがバトルを実行し、ゲストは 0x7C で応答します。`pokeldn/swsh/raid_battle.py` はゲスト側で、
エミュレートした Shield のゲストから作られました。`bin/swsh_connect.py --raid-join` とこれを使い、
エミュレートしたホストのゲストとしてレイドを最後まで戦い、勝利しました。

バトルの前、メッシュ参加の時点でゲストは SyncClockProtocol 0x1C (毎秒 1 回の要求) を実行し、
ClockProtocol 0x77 の要求 (`00` を 16 個と `00 6f`) を 1 回送ります。どちらも宛先ビットマップ 1 です。

| ポート | メッセージ | ゲストの動作 |
|---|---|---|
| 0 | sync 80: ping, pingReply, pingSynced | ping には ping と pingReply で、pingSynced には pingSynced で応答 |
| 1 | 40000、content 0 のフレームワーク: フィールド 2 の base (10000 か 20000。0 の場合は省略)、3 ステーション定数 ID、4 クロック、5 本体 | pingSynced の後、base-10000 と base-20000 の組を 3 つ送る (本体は `00000000` と `000018fc`)。続けて、ホストの base-20000 の本体ごとに、自分のステーション ID で写し返す |
| 0 | 10000、フィールド 3 {1 ステーション、2 枠、3 バージョン} | ホストが自分の席を列挙したときに 1 回送る (base 0、16 バイトの本体: 定数 ID、枠、バージョンのバイト 0x6e) |
| 0 | 10000、フィールド 1 は空 | ホストの base-8 メッセージ (24 バイトの本体、バトルのシード) の後に送る |
| 0 | 20000、フィールド 1 {1 送信者、2 枠、3 カウンター、4 データ} | ホストのコマンドすべてに応答 |
| 0 | 20000、フィールド 3 {1 状態、2 枠} | 行動の前に {1: 2, 2: slot} を送る |

ホストのコマンドのデータは、先頭に 4 つの u16 を持ちます。順に、シリアル、種類、長さ、タグです。ゲストは、
同じシリアル、種類、タグ、長さ 4、4 バイトのゼロで応答します。ただし次の種類は例外です。

| 種類 | ゲストの送信内容 |
|---|---|
| 0x02 | 状態メッセージ、続けて行動: シリアル、0x02、0x58、タグ、続けて 88 バイト |
| 0x21 | 終了: 送信者 1、データ `0000 1e00 0000 2f00` |

ホストから届いた種類: 0x01、0x0d、0x07 (123 バイト)、0x0e、0x02、0x10 (47 バイト)、0x09 (そのターンのログ。
zlib、0.4 から 2.4 KB)、0x04、ゲストのポケモンが戦闘不能になった後の 0x11 と 0x0a、最後に 0x21。

### どのステーションがサーバーを務めるか

サーバーは、各本体が保持するテーブルで ServerVersion の記録が勝つステーションです。Pia のホスト確認
(`0x110e620`、バトルとロビーのコードに呼び出し元はない)も、BattleStart の順序も、これを決めません。

ServerVersion は `btl.net.protocol_buffers.BtlDataHolder` (ID 10000) のフィールド 3 です。ステーション ID の u64、
クライアント ID の u32、バージョンの u32 からなります。どのコピーもバージョン `0x6e` (`0x8b1778`) を送ります。各本体は、
{ステーション、クライアント ID、バージョン、有効} の枠を 8 つ保持します (バトルのネットワークオブジェクトの `+0x190 + 16 * i`)。`0x8b4030` は、
見た中で最も高いバージョンと等しい有効な最初の枠のクライアント ID を取り、
`0x8b1990` (IsServer) はそれを本体自身のクライアント ID と比較します。記録を集めるステーションは、送信元の Pia ステーション索引に対応する枠に記録を格納します
(`0x8b4440`、`0x6b5850`)。ほかの各本体は、枠を 40000 のフレームワークオブジェクト
0 から 7 として受け取ります。オブジェクト番号はフィールド 2 にあります。記録したレイドでは、ホストが
オブジェクト 0 (自分の記録、クライアント ID 0) とオブジェクト 1 (ゲストの記録、クライアント ID 1) を公開しました。

本体のクライアント ID は、BattleStart でロビーのメンバーの中にある位置です (`0x1025120`、
`0x10253bc`)。ステーションが抜けると、その枠を消して選び直します (`0x8b3f70`)。どの本体も、
IsServer が真になると昇格させる待機サーバーを一台保持します (`0x7f838c`、`0x7f87f0`)。

### 行動

88 バイトの行動は、8 バイトのエントリ 11 個からなります。1 匹のゲストの 4 つの技の間で変わったのはエントリ 2 だけです。
リトルエンディアンの u24 としては、`move id << 13 | target << 8 | 0xc1` です。

| 技 | エントリ 2 | 対象 |
|---|---|---|
| はたく (1) | `c1 28 00` | 8 |
| しめつける (20) | `c1 88 02` | 8 |
| なきごえ (45) | `c1 a2 05` | 2 |
| みずでっぽう (55) | `c1 e8 06` | 8 |

なきごえは、すべての相手に当たり、対象 2 を持ちます。単体を対象にする技は 8 を持ちます。ゲストが
行動できなかったターンは、エントリ 2 をゼロとして送りました。`raid_battle.action(move, target)` がこれを組み立てます。
`--raid-move N` は、ゲストのポケモンの技の枠を選びます。

0x7C の確認応答は 32 の枠を持ちます。枠 0 だけがゲストのストリームを追い、ほかの枠には古い ID が入っています (34460 を確認)。
枠全体の最大値を条件にした再送は、一度も再送しません。

## 巣穴の記録

巣穴のホストのアドバタイズは、そのレイドを記述します。ゲストの Y-Comm エントリの組み立て処理 (`0x00fa1560`) がこれを読みます。

| オフセット | 内容 |
|---|---|
| `0x5F` のビット 1 | ホストのバージョン: 0 なら Sword、1 なら Shield |
| `0xAF` | 活動の種類: ランク 0 では `0x11`、それ以上は `0x13 + 2 (rank - 1)`。`0xFF` は決して一覧に出ません |
| `0xB0` | 表示するボス: u16 の種族 (ビット 0 から 9) とフォルム (10 から 15)、ビット 4 と 5 を持つバイト (1 は通常、2 はキョダイマックス)、u32 の暗号化定数 |
| `0xD4` | 巣穴の記録。同じ 8 バイトの配置 |
| `0xDC` | 上位 4 ビット: 星のランク (0 から 4) |
| `0xDD` | ビット 3 から 5: 巣穴の種類。通常の巣穴は 0 |
| `0xDE`, `0xE0` | u16 の出現テーブル (ホストのバージョンのテーブルの中で数えたもの)、u16 の枠 |
| `0xE6` から `0xED` | `bin/archive/field/resident/data_table.gfpak` のファイル 8、6、7、9 の CRC16 |

`0xD4` の種族がゼロでないとき、ゲストは、自分のテーブルの CRC が一致し、巣穴の種類が 0 で、
ホストのバージョンのテーブル `0xDE` の枠 `0xE0` が、その種族、フォルム、キョダイマックスのフラグを持つ場合に限ってレイドを一覧に載せます
(`0x00ea5160`、`0x00ea51d0`)。種族が 0 の場合はこれらの確認を飛ばします。ランクは、
`0x02510b2c` のバイトが 1 か 2 で、ホストがフレンドでない場合に、バッジ数から求めたゲスト自身のランクを超えてはなりません。
`0xB0` のレコードは範囲の確認だけを行います。`pokeldn/swsh/data/nest_slots.json` は
1.3.2 の枠を持ちます (`scripts/gen_swsh_nest_data.py`)。`raid.den_advert` は巣穴の記録を
ボスを持つ枠に向けるか、ゼロにします。

ゲストは、デバイス ID とアカウント uid (`0x1F` から `0x3E`) がどちらも自分と等しいステーションを
除外します (`0x0111b160`)。

### ボスの記録

ゲストは、開始した BattleReady を送る前に BossPokemon と Rewards を確認します (`0x01030d14`、状態
10)。確認に失敗すると、2-ALZAA-0016 で抜けます。

| 確認 | 処理 | 通る条件 |
|---|---|---|
| ボス | `0x01032270` | 種族、フォルム、パーティの `+0x156` (1 は通常、2 はキョダイマックス) が、巣穴の記録が指定する項目と等しいこと。種類 0 はアドバタイズされたバージョンの基本テーブル `0xDE` の枠 `0xE0`、種類 1 から 3 はゲスト自身が保存したイベントの出現、枠 `0xE0`、種類 4 は保存したクリスタルの出現 |
| 報酬 | `0x01032570` | アイテムと個数の組はすべて、アドバタイズされたランクで枠のボーナステーブルのうち個数が一致する行か、そのランクで確率を持つドロップテーブルのアイテム (個数は問わない) であること |

レベル、技、個体値、PID、特性、色違い、トレーナーの項目は比較しません。ゼロの巣穴の記録は、
種類 0、テーブル 0、枠 0 (ワンリキー) を指します。基本の巣穴には伝説や幻のポケモンがいないので、ホストするボスは
`nest_slots.json` が一覧にする種族、フォルム、キョダイマックスの状態のどれかになります。`raid.den_advert` は、
もう一方のバージョンだけがボスを持つ場合にアドバタイズするバージョンを切り替えます。イベントのボスは、
その種族、フォルム、キョダイマックスの状態を持つ基本の巣穴の枠として表示されます。`raid.reward_choices` は、
ランクごとに枠が許す報酬を一覧にします (ボーナスのアイテムはその個数で、ドロップは任意の個数)。`raid.den_rewards` は、
そこから枠自身の行を組み立てます。

製品版 Sword のゲストは、ボスが交換で受け取った記録 (トレーナー、バージョン、出会いのデータ、ボール) だったとき、
パーティのダイマックスタイプ (`+0x156`) が 0 だったとき、アドバタイズの巣穴の記録がゼロだったとき
(基本の巣穴が持たないボス: 受け入れた記録上のミュウ、イベントのキョダイマックスストリンダーで、
キョダイマックスのビットの有無を問わない) に、BossPokemon で 2-ALZAA-0016 により抜けました。これらのレイドは、どれも一覧には出ていました。記録した巣穴のボス 2 体は、
どちらもトレーナーのデータを持たず、ダイマックスタイプは 1 でした。巣穴のボスの記録上で種族だけを変えたボスと、
`raid.boss_record` で組み立てたレベル 20 のボス (巣穴のボスの記録に、種族、フォルム、技、個体値、努力値、
性格、特性、PID、暗号化定数、パーティのステータスを入れたもの) は、受け入れられました。

記録した巣穴のボス 3 体 (ダイマックスレベル 1 のエミュレートしたハトーボーと、レベル 2 のホーホー、
レベル 7 の製品版コータス) では、パーティの HP 実数値と現在の HP は、素の HP 実数値に
`(150 + 5 * Dynamax level) / 100` を掛けて切り捨てたものでした。ほかの 5 つの実数値は素のままです。ダイマックスレベルは
`+0x90` にあり、特性の枠のビットは `+0x16` のビット 0 から 2 にあり、経験値はそのレベルの最小値です。

## ホスト

`bin/swsh_host.py --raid-boss PK8 --raid-console-serves` は、本体が Y-Comm リストから参加する巣穴のロビーをホストします
(`pokeldn/swsh/raid_host.py`)。アドバタイズとスナップショットは、エミュレートした Shield の巣穴のホストのもので、名前を変え、アカウント ID を含まないものです
(`pokeldn/swsh/data/raid_advert.bin`、
`raid_snapshot.bin`。`--advert` と `--snapshot` で置き換えます)。アドバタイズは、新しいステーションのプロファイル、ロビーの名前、ボス、そのボスの巣穴の記録
([巣穴の記録](#the-den-record)) とともに送られます。`--raid-boss` は任意の PK8 を受け取り、
`raid.boss_record` を通して送ります。スナップショットは、ゲストのものより先に送られます。
`--raid-reward ITEM:COUNT` は Rewards を、`--raid-seed` は BattleSeed を埋めます。
ホストは、アドバタイズされた巣穴の枠がそのランクで与えない `--raid-reward` の行を拒否し、枠が与える内容を表示します。
イベントの行のうち合わないものは除かれます。

アプリのマックスレイド (ホスト) ツールは、これらのフラグを、ボス (またはワイルドエリアのイベントと、基本の巣穴が持つそのボスの一つ。`raid_event.hostable`) と、
自分のポケモン、最大 15 行の報酬とともに実行します。行がなければ、ホストは巣穴の枠自身の報酬を与えます。報酬エディターが出すのは、
選んだボスがアドバタイズされている巣穴の枠のアイテムだけです (`raid.boss_den`、`pokeldn.app.raid_rewards.swsh_den`)。ボーナスアイテムの個数は固定され、
ボスを変えるとそれに従います。基本の巣穴が持たないボスでは、報酬は空のままになります。アプリから、レベル 20 のワンパチのボスと、
テンプレート "Every reward of this den" を 7 で実行しました。製品版 Sword はこのレイドに勝利し、
10 行すべてを受け取りました。
Exp. Candy XS x5、Exp. Candy S x1、Dynamax Candy x1 (ボーナスの行)、
そして 7 種のドロップを、それぞれ 7 個ずつ受け取りました。

`--raid-console-serves` を付けると、参加した本体がバトルを担当し、ホストはクライアント 1 として応答します
(`raid_battle.Master`):

| 段階 | ホスト |
|---|---|
| BattleStart | 本体を先頭に並べるので、本体のクライアント ID は 0 になる |
| 0x7C ポート 0 | ping を送り、本体の ping と pingSynced に応答する |
| フレームワークオブジェクト | オブジェクト 0 に本体の ServerVersion の記録、オブジェクト 1 に自分の記録を公開する |
| 0x7C ポート 0 | 自分の ServerVersion (クライアント ID 1) を送る |
| base 20000 | カウンターと自分の本体を公開する。0000 / 00000100、続けて 0100 / 01000100、01000200、0200 / 02000200。各本体は、本体が直前の本体を写し返すたびに公開する |
| オブジェクト 8 | 本体がこれを公開する (24 バイト、シード)。ホストは EmptyCommand (10000 のフィールド 1) で応答する |
| バトルのコマンド | ゲストが応答するのと同じように応答する。行動では、ホストのポケモンの最初の技を指定する |

エミュレートした Shield のゲストと製品版 Sword が、それぞれこの方法でレイド一回分を担当し、勝利して、
ホストの Rewards を受け取った後、メッシュの離脱要求を送りました。

### 複数の本体

最大 3 台の本体が、一つのホストしたロビーを共有します (`raid_host.RaidParty`)。ホストは、
参加したすべての本体が準備完了を押すとバトルを始めます。BattleStart は、参加順に本体を並べ、最後にホストを並べます。
最初の本体が担当します。ホストは、フレームワークオブジェクト k を本体 k の ServerVersion の記録として公開し、
自分の記録は最後に公開します。また、すべての本体が自分の本体を写し返すと、base-20000 の関門を一段進めます。

| 層 | 2 台目の本体が Pia ホストに必要とするもの |
|---|---|
| Local Protocol | セッションの更新が届く。ループバックでは、各ステーションが自分のコピーを受け取る |
| メッシュ参加の応答 | バイト 8、既に着席しているステーションを超えるアクティブなステーションの最大数。2 のとき、最初のゲストは 2 台目の接続要求に結果 1 で応答し、2 台目はエラー 2618-0502 を表示した |
| 0x84 | 送信元のストリームのポートでの ack。ステーションのストリームは、そのステーション索引のポートにある (ホストは 0、最初の参加者は 1、2 番目は 2)。ack のないストリームは終わりなく繰り返される |

ゲスト同士は直接接続します。ステーションの接続要求、互いのスナップショット (0x84)、
そしてホストと相手のゲストの両方に宛てたロビーメッセージ (0x80) を送ります。2 台のエミュレートした Shield のゲストが、一つのホストしたロビーに参加しました。
二人は準備を整え、最初のステーションが担当するレイドを、10 ターン目の終わり
(コマンド 0x1e) まで戦い、その後両方がメッシュの離脱要求を送りました。

## イベントレイド

野生エリアのイベントは、巣穴の出現と報酬のテーブルを BCAT で配信したもので、配信ごとに番号付きのインデックスがひとつあります。
Project Pokemon の EventsGallery は、各インデックスを
`Released/Gen 8/SwSh/Wild Area Events/Index NNN/` の下に保存します。その `readme.md` には、各インデックスが持つイベントが書かれています。
`pokeldn/swsh/raid_event.py` はひとつを読み、`pokeldn.app.events_gallery` はゲーム `swsh` の下に写しを保持します。

| ファイル | 内容 |
|---|---|
| `normal_encount` | 野生エリアの巣穴のイベント出現 |
| `normal_encount_rigel1`、`normal_encount_rigel2` | 鎧の孤島と冠の雪原のもの (インデックス 080 と 117 にあり、010 にはない) |
| `drop_rewards`、`bonus_rewards` | 配信の報酬テーブル |
| `dai_encount` | ダイマックスクリスタルの出現 [pkNX `NestHoleCrystalEncounterArchive`]。ここでは未解析 |

どのファイルも 0x20 バイトのヘッダーで始まります。オフセット 0 に u8 の BCAT インデックス、オフセット 4 に `ff ff ff ff`、オフセット 8 に u32 の `0x20`、
オフセット `0x10` に u32 のファイルサイズ - 4 があります。FlatBuffer は `0x20` から末尾の 4 バイト手前まで続き、その 4 バイトには
CRC が入っています [pkNX `GameDumperSWSH.GetDistributionContents`]。

出現ファイルは、テーブルのベクター (フィールド 0) です。TableID の u64、GameVersion の u32 (1 は Sword、2 は Shield)、
2 バイト、そして Entries (フィールド 4) があります。インデックス 010 のテーブルは、それぞれ 30 個のエントリを持ち、各エントリの vtable は
37 のフィールドを持ちます。ここでは次のように読みました (フィールド番号、型、内容)。

| フィールド | 型 | 内容 |
|---|---|---|
| 0 | i32 | エントリ番号。1 から 30 |
| 1, 2, 3 | i32 | 種族、フォルム、レベル |
| 4 | u16 | ダイマックスレベル |
| 5 から 10 | u32 | インデックス 010 のすべてのエントリにはない |
| 11 | u8 | 特性: 0、1、2 は一つ目、二つ目、隠れ特性。3 は最初の二つのどちらか。4 は任意 |
| 12 | bool | キョダイマックス |
| 13、14 | u64 | ドロップと報酬ボーナスのテーブル ID |
| 15 | [i32] | 星ランク 1 から 5 の 5 つの確率 (パーセント)。各バージョンでランクごとの合計は 100 |
| 16 | i8 | 性別: 0 は抽選、それ以外はレコードの性別 + 1 |
| 17 | i8 | 個体値 31 の数 |
| 18 | u8 | 色違い: 0 は抽選、1 は決して、2 は常に |
| 19、20 | u8 | インデックス 010 では 3 か 2。未解析 |
| 21 | i8 | 性格。25 は抽選 |
| 22 | i32 | インデックス 010 では 0 |
| 23 から 26 | u32 | 4 つの技 |
| 27 | f32 | インデックス 010 では、ランク 1 から 5 で 1.4、1.6、1.9、2.5、3.0。未解析 |
| 28、29 | u32 | 未解析 |
| 30 | u32 | 0 から 6。PyNXBot のスキーマによるシールド |
| 31 から 33、34 から 36 | u32 | 割合、技、値: PyNXBot のスキーマによる二つの追加技 (技 150 を割合 0 で) |

インデックス 010 は、readme の記述どおり、野生エリアのイベント #7 に当たります。ランク 3 から 5 のキョダイマックスストリンダー (Sword ではフォルム 0、Shield ではフォルム 1)、
すべてのランクのキョダイマックスマホイップ、Sword のキングラーとオーロンゲ、Shield の Orbeetle と Hatterene です。
ランク 5 のストリンダー (レベル 60、ダイマックスレベル 10、個体値 31 が 5 つ、
技 786、586、482、506) は、PKHeX の `encounter_sw_dist.pkl` のインデックス 10 の記録と一致します。

配信の報酬ファイルは、テーブルのベクター (フィールド 0) です。TableID の u64 と Entries (フィールド 1) があり、各エントリは、
ランク 1 から 5 のための 5 つの u8 の値 (フィールド 0 から 4) と、u16 のアイテム (フィールド 5) を持ちます。ゲーム自身のテーブル、
`data_table.gfpak` のファイル 7 (ドロップ) と 6 (ボーナス) は、TableID と、u32 のエントリ番号、u32 の
アイテム、そして 5 つの値の u32 ベクターからなるエントリを持ちます (`pokeldn/swsh/data/nest_rewards.json`、
`scripts/gen_swsh_nest_data.py`)。出現は、両方の中からテーブルを ID で指定します。ゲームのものを先に探します
[pkNX `NestHoleDistributionEncounterTable`]。インデックス 010 のすべてのボスのボーナステーブルと、
マホイップのドロップテーブル以外のドロップテーブルは、ゲームのものです。

ボーナスの値は個数、ドロップの値はパーセントの確率です。エミュレートした 1 つ星の巣穴のホストの報酬
(`raid.DEN_REWARDS`) は、ランク 1 のゲームのボーナステーブル `0xf966212316b78eb6` の行を、その個数のまま先頭に並べ (Exp. Candy XS x5、S x1、Dynamax Candy x1)、
続けて一個ずつの二つのアイテムを持ちました。
`raid_event.rewards` はボーナスの行を組み立て、続けてドロップごとに一行を組み立てます。各ドロップの確率を抽選するか、
すべてを残すかを選びます。

`raid_event.boss_pk8` は、`raid.boss_record` が出発点とする巣穴のボスの記録の上にボスを組み立てます。テーブルが許す種族、フォルム、レベル、技、キョダイマックス、
ダイマックスレベル、特性、個体値、性格、性別、
PID と、[ボスの記録](#the-boss-record) にあるパーティのステータスです。ステータスは、
`pokeldn/swsh/data/species.json` の個人データのテーブルから得ます (`scripts/gen_swsh_species_data.py`)。

    bin/swsh_host.py --raid-event "FOLDER/Index 010" --raid-stars 5 --raid-event-boss 4 --raid-console-serves

`--raid-stars` か `--raid-event-boss` がないと、ホストは必要なものを一覧にします。`--raid-version` はテーブルのバージョン (既定ではアドバタイズのもの) を選び、
`--raid-area` は巣穴のエリアを、`--raid-event-drops all` はすべてのドロップを選びます。
`--raid-reward` の行は、イベントのものを置き換えます。

## ダイマックスアドベンチャー

ダイマックスアドベンチャー (マックスラボ。バイナリでは `chika`) は、全プレイヤーがマックスラボで Invite Others を選ぶと、
ローカル通信上でマッチングします。最初の一人がネットワークを開き、ほかの人はスキャンで見つけて接続します。Y-Comm には決して載りません。
ホストはアクティビティの種類 0xFF をアドバタイズし、Y-Comm の一覧はそれを飛ばします。
ネットワークは、ローカル通信 ID `0x0100abf008968000`、シーン 50000、NodeCountMax 4 を持ちます。ホストは
「Communicating」の下で 3:00 から数えます。ゲストがいない場合は、参加者不足でアドベンチャーを中止します。
アドベンチャーが始まると、コンピューターのパートナーが空いた席を埋めます。

2 つのメッセージホルダーが、信頼性のある 0x80 のポート 0 で動きます。各フィールドは、フィールド 1 を一つ持つホルダーです:

- ID 7000、`net_contents.chika.protocol_buffers.ChikaAsyncDataHolder` (記述子は `0x1c3adb5`、
  `0x2066654`)、ロビー用;
- ID 8000、`net_contents.underground.protocol_buffers.UndergroundAsyncDataHolder` (記述子は
  `0x1c36fab`、`0x20681cc`)、バトルの間用。

マックスラボのロビーに送られた巣穴のメッセージ (ID 2000) は、確認応答されますが、誰も着席させません。バトルは、巣穴のレイドと同じように 0x7C で動きます
(ping 80、続けて 40000、10000、20000 のメッセージ)。違いは二つあります:

- 行動はエントリ 1 が `01 ff ff ff ff ff ff ff`、エントリ 2 が巣穴のレイドと同じ技で、残りの 9 個のエントリは `0xff` です。
  ダイナマックスのターンでは、エントリ 2 のバイト 3 が `0x80` になり、その前の状態メッセージは、
  状態 2 ではなく状態 1 を運びます。
- ゲストのポケモンが戦闘不能になった後、ホストはデータ `01 00 ff ff ff ff` の種類 0x04 を送りました。ゲストは、
  エントリ 2 がゼロの 88 バイトの行動で応答しました。

`pokeldn/swsh/lair.py` は、両方のホルダーにおけるゲスト側です。`bin/swsh_connect.py --lair-join` は、
エミュレートした Shield のロビーと製品版 Sword のロビーで、プレイヤー 1 として着席し、ホストが残した最初の提供枠を取りました
(レンタルは順番に出され、ホストが先です)。その枠は、種の行から `lair.rental_pk8` が組み立てる形で作り、最初のバトルでプレイヤーのパートナーとして戦いました。
製品版のホストは、組み立てたレンタルを
受け入れました。

レンタルは、記録されたレンタルのレコードに、その行の種族、フォルム、レベル 65、技を入れ、個体値 4 つは 31、ほかはランダムにしたものです。
性格はランダム、特性の枠は 1 か 2、性別、PID、暗号化定数を持ちます。OT は Scientist、ボールはモンスターボール、レベル 65 で出会ったことになります。
記録した二つのレンタルのパーティのステータスは、どちらも、レベル 65 での個体値と性格から求まり、
ダイマックスのボーナスはありません。

### ロビーのホルダー (ID 7000)

エミュレートした 2 台の Shield の間で計測し、冒険を最後まで勝利した記録です。プレイヤーを指定するレコードは、
Pia 定数 ID (u64) とプレイヤー番号のバイトから始まります。コンピューターのパートナーは ID がゼロで、
番号は 2 と 3 です。

| フィールド | 名前 | サイズ | 内容 |
|---|---|---|---|
| 1 | ChikaTimeLimit | uint32 | ホストから届く残り秒数 |
| 2 | ChikaPlayerInfo | 48 | 12 バイトのゼロ、13 文字の UTF-16 名、続けて `02 00 00 00 00 2d 00 00 00`。zlib 圧縮で送られる (信頼性フラグ 0x10) |
| 3 | ChikaBattleReady | 16 | プレイヤーが準備完了を押すとバイト 8 が 1 になる。冒険が始まるとバイト 12 が 1 になる |
| 4 | ChikaSelectPokemon | 360 | 8 バイトのゼロ、共有の提供枠におけるレンタルの位置 (u32)、暗号化されたパーティ PK8 としてのレンタル (レベル 65、OT Scientist)、4 バイトのゼロ |
| 5 | ChikaBattleStart | 32 | 人間のプレイヤーの定数 ID。ゲストのものが先 |
| 8 | ChikaBattleSeed | uint64 | ホストから届く。レンタルの提供と出現を決めるシード ([冒険のシード](#the-adventure-seed)) |
| 9 | ChikaRentalPokemonSeed | uint64 | ホストから届く。レンタルを選ぶ前に送られる |
| 11 | ChikaPlayerNumber | 40 | 4 つの定数 ID (ホスト、ゲスト、ゼロ、ゼロ)、続けてプレイヤー番号 `00 01 02 03` |
| 12 | ChikaBigBoss | 16 | バイト 12 が 1。各プレイヤーが PlayerInfo とともに自分のものを送る |
| 13 | ChikaBigBossFixed | 4 | 冒険の伝説のポケモンの種族 (u32)。記録では 480 のユクシー |

フィールド 6、7、10 は送られませんでした。順序は次のとおりです。参加時に各プレイヤーから PlayerInfo、BattleReady、BigBoss を送り、
バイト 8 を立てた BattleReady を送る。続けてホストから BattleStart、BattleSeed、
RentalPokemonSeed、PlayerNumber、バイト 12 を立てた BattleReady と BigBossFixed を送る。最後に各プレイヤーが
SelectPokemon を送ります。

### 冒険をホストする

`bin/swsh_host.py --lair-legendary SPECIES [--lair-seed N]` (`pokeldn/swsh/lair_host.py`) は、エミュレートした Shield のホストの
アドバタイズからマックスラボのネットワークをアドバタイズします (シーン 50000)。リンク交換と同じようにスナップショットを交換し、
その後、エミュレートしたホストのロビーを送ります。PlayerInfo、BattleReady、BigBoss、毎秒 3 回の残り時間、
準備完了。ゲストが準備完了になると、BattleStart、BattleSeed、RentalPokemonSeed、PlayerNumber を送ります。
ゲストが開始を応答すると、開始した BattleReady と BigBossFixed を送ります。
5 秒後、ホストする Sword と同じように抜けます ([離脱](swsh_session.md#leaving))。
MIGRATION_START `44 00 01`、ホストの移行バイトを持つ更新セッション、START_HOST_MIGRATION を
0.33 秒ごとに送り、本体が抜けた後か 10 秒後にネットワークを閉じます。

アプリのダイマックスアドベンチャー (ホスト) ツールは、これらのフラグを実行します: 伝説のポケモン、任意のリンクコード、
冒険のシード。シードの選択画面には、`lair.adventure` が種に対して与える 3 つのレンタルと 10 の出現が表示されます。新しいシードを引けるほか、
選んだレンタルを提供に含むシードを、ランダムな種から探せます
(約 75 個に 1 個の種が、特定のレンタルを提供に含みます)。

この方法で参加したエミュレートした Shield は、`lair.adventure(seed)` が枠 0 から 2 に与える 3 つのレンタルを表示しました。レンタルは順番に選ばれ、ホストが先です。
画面には "POKELDN is deciding..." と表示され、ネットワークが閉じるまで続きました。
その後、コンピューターのパートナーが POKELDN の席に着き、レンタルを選びました。プレイヤーは自分のレンタルを選びました。
マップの最後にいた伝説のポケモンは、BigBossFixed が指定した種族 (ミュウツー、150) で、ゲスト自身の BigBoss はすべてゼロでした。
ESP32 のボードを介して参加した製品版 Sword も同じ方法で、準備完了を押し、開始の応答をし、
ネットワークが閉じた後も冒険が続きました。
マップ上の最後のポケモンは、BigBossFixed が指定した伝説のポケモン (ルギア、249) のタイプを持っていました。

マックスラボのリンクコードは、受付で + を押して設定します。アドバタイズには、コードの 10 進の値の CRC32 が入ります。
先頭のゼロは除かれます (0000 7777 は `7777`)。製品版 Sword は、0000 7777 で検索して
それをアドバタイズするロビーに参加しました。コードなしで検索したものは、一度もそれを一覧に出しませんでした。コードありの場合、
MIGRATION_START なしでネットワークを閉じたホストは、レンタルの画面でゲストをエラー 2618-0006 のまま残しました (2 回中 2 回)。
引き継ぎを行った場合、ゲストは MIGRATION_START の 0.1 秒後にネットワークから抜け、冒険は続きました。
コードなしでは、両方の離脱が続きました。

### 冒険のシード

冒険のポケモンは、RomFS の `bin/appli/chika/data_table/underground_exploration_poke.bin` の行です。
これは 273 行の FlatBuffer で、レベル 65 のレンタルと出現が 226 行、続けてレベル 70 の伝説のポケモンが 47 行あります
(ボスのフラグが立つ)。各行は、種族、フォルム、レベル、4 つの技を持ちます。

ChikaBattleSeed は、6 つのレンタルの提供と出現を決めます。`lair.adventure(seed)` がそれらを計算します。
Xoroshiro128+ は u64 と `0x82A2B175229D6A5B` でシードされます。各選択は、次の 32 ビット出力で MT19937 をシードし、
273 個の行の番号をシャッフルします (番号 i は、i と、0 から 272 - i までの抽選値を入れ替え、`0x1ff` でマスクし、
上回る場合は引き直します)。そして、伝説ではなく、まだ選ばれていない最初の行を取ります。
4 回選んだ後、次の 2 回の選択それぞれの前に 0 から 2 の抽選を 1 回、さらに 1 回を行います。それぞれは、
着席しているコンピューターのパートナーが 2、1、0 人を超える間に行われ、続けて 0 から 2 と 0 から 9 の抽選、そして 10 回の出現の選択を行います。
各出現の選択の後には、行のタイプが 2 つある場合にもう 1 出力を加えます。コンピューターのパートナーが 3 人の場合は、
最初に 0 から 27 の抽選が来ます。

| シード | パートナー | 提供、枠 0 から 2 | 計測 |
|---|---|---|---|
| `0x000000000a577170` | 2 | マホミル、ミミロップ、オーロンゲ | ホストが枠 0、ゲストが枠 2 を取った。最初のバトルはロトム |
| `0x2721e8ab192583ff` | 2 | ウルガモス、ナマズン、Charjabug | エミュレートした Shield のゲストの提供 |

## 離脱

プレイヤーが報酬の画面を抜けると、製品版 Sword のホストは、リンク交換の後と同じように、
0.33 秒ごとに 10 秒間 START_HOST_MIGRATION を送ってネットワークを閉じます ([離脱](swsh_session.md#leaving))。
離脱しないゲストは、タイムアウトまでホストのプレイヤーをフィールドで固まったままにします。
`--leave-with-host` は最初の離脱要求で抜けます。
