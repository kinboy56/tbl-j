# ポケットモンスター Let's Go! ピカチュウ・Let's Go! イーブイ

ポケットモンスター Let's Go! ピカチュウ・Let's Go! イーブイ（2018）では、Pia が `main` に静的にリンクされており（RTTI に 269 個の
`nn::pia` クラスがあります）、ゲームの C++ コードは protocol buffer メッセージを使って、その上に載っています。通信には
`gflnet3` を使います。`gflnet3` は、その 1 年後に発売された ソード・シールド が使うミドルウェアです。

静的解析の対象は Let's Go! ピカチュウ 1.0.2（`010003f003a34000`、アップデート NSP `v131072`、SDK
5.4.151.0）です。実機での計測は、フランス版の Let's Go! ピカチュウと Let's Go! イーブイ に対して行いました。Let's
Go! イーブイ は、ピカチュウのローカル通信 ID を使うため、どちらの役割でも改造していないイーブイと交換できます。

ローカル通信での交換とバトルでは、両方のプレイヤーにリンクコードの入力を求めます。リンクコードは、固定の 10 匹から順に選んだ 3 匹のポケモンで、
2 行に並んで表示されます。その 10 匹は、ピカチュウ、イーブイ、フシギダネ、ヒトカゲ、ゼニガメ、ポッポ、キャタピー、コラッタ、
プリン、ディグダです。このコードが広告のシーン ID を決めます
（[セッションのページ](lgpe_session.md#the-link-code)）。ホストと参加は、どのコードでも動作します。

## 動作する機能

`bin/lgpe_join.py` はコンソールのセッションに参加し、`bin/lgpe_host.py` は、
コンソールが参加するセッションをホストします。1 つの席では、交換を 1 件ずつ続けて行えます。各交換の通常の保存のあと、
保存が `0x886908` のリンク終了を報告しない限り、交換ディスパッチャーは状態 7 から状態 1 に戻ります。保存は、
パーティのオファー用オブジェクトを新しいチャンネル（`0x8375a4`）上に作り直します（[セッションのページ](lgpe_session.md#the-trade-dispatcher)）。
両方のランチャーは、席ごとの交換 1 件につき 1 レコードのキューを受け取ります。ゲームは、受け取ったボックス構造体のどのフィールドも検査しません。
全 IV が 31、全 AV が 200 の色違いのレベル 100 メタモン（特性 Imposter（へんしん））は、
まとめ画面にそのまま表示されます。
Clone Protocol の引き継ぎのやり取りは、ゲームの `0x11b080` のゲートを通過し、Reliable Protocol は
identity、offer、commit、種別 4（次の交換の選択）を運びます。`pokeldn.lgpe.pb7` は、
offer と種別 4 が運ぶ 232 バイトのボックス構造体を読み書きします。

3 件のキューに入れた交換は、どちらの役割でも 1 つの席で完了します。完了した各エントリは、チェックサム付きの 260 バイトのファイルとして保存され、
コンソールが退出すると、ホストは終了コード 0 で終了します。`pokeldn.pokemon` で組み立て（レベル、性別、性格、ボール、選んだ IV と AV）、
`bin/lgpe_host.py
--fresh-pid` で提供したレコードは、受け取った側のまとめ画面にそれらのフィールドを表示します。

プレイヤーが Retour（戻る）を押すと、コンソールは席を離れます。`bin/lgpe_join.py --leave-after SECONDS` は、最初に応答した交換ステップから
その秒数が経ったあとに同じ終了処理を実行し、`bin/lgpe_host.py` は、コンソールの Retour に応答します
（[参加者の退出](lgpe_session.md#a-joiner-leaving)）。
`tests/test_lgpe_host_commit.py` は、台本どおりに動くコンソールに対して、ホストの commit 段階を検証します。誤った commit では、
コンソールは、保存の交換ロックが設定されたまま確認画面に残ります（計測されるプレイ時間で 10 分間は交換できません）。
その後、致命的なエラー画面が表示されます。

## 未解決

- ホストが取り消された投票に A 2 で応答したあと、製品版のコンソールがホストの 2 つの `0xa1` の両方に応答しなくなった原因は何か。ホストの公開は、末尾ワード 1 の A 2 と、
  その 1 秒後の末尾ワード 2 の A 2 でした。コンソールは末尾ワード 2 の下で `0 2 3` を再発行し、
  最初の A 2 から 5.0 秒後に commit clone を告知しました。ホストは告知に `82, 91, 91, 84, 81, a1, a1` で応答しました。
  1 ms 以内に送られた 7 個のデータグラムで、すべてコンソールの無線で確認応答されました。
  コンソールは、新しいクロックの下で clone type 1 の clone を再告知しました。これは、clone type 2 の `0x91` が告知を
  `0x520d30` でリンク解除したあとに、clone type 2 の `0x81` だけが行うことです（`0x51ca48` -> `0x520c30`）。
  clone type 1 の `0x82` は `0x5223c0` にしか届かず、何も送信しません。コンソールは、どちらの `0xa1` にも応答しませんでした。
  clone type 1 の `0xa1` ハンドラー（`0x51c714`、`0x522350`）は、どの結果でも送信します。`0x51e3d0` は失敗する前にメッセージカウントを消費しますが、
  製品版のコンソールは、どちらも消費していませんでした。ハンドラーの前にあるすべてのゲートは、同じ送信元、フレームカウンター、マスクの `0x81` に対して通過しました。
  対象は、受信ループの station マスクとフレームカウンターのフィルター（`0x51ae20..0x51ae84`）、宛先チェック（`0x51ce80`）、
  カウントフィルター（`0x51c1e0`）、`+0x3c` マスク（`0x51c6b0`）です。`0x522a60` が 2 を返すと、clone type 4 の `0xa1` だけが無応答になるはずです。
  同じ入力を与えたエミュレートした Let's Go! ピカチュウ 1.0.2 は、30 ms 以内に両方の `0xa1` に `0xa2` で応答し、交換を完了しました。
  エミュレートした側は、自分の `1 2 2` の 0.81 秒後に投票（`2 2 3`）を取り消しました。0.16 秒後にホストが末尾ワード 1 の A 2 を公開し、
  その 1.0 秒後に末尾ワード 2 の A 2 を公開しました。コンソールは末尾ワード 2 の下で `0 2 3` を再発行し、
  最初の A 2 から 5.4 秒後に commit clone を告知して、同じ 7 通のバーストを引き起こしました。
  製品版のコンソールも 1.0.2 で動作します。製品版で何が違うのかは、分かっていません。
