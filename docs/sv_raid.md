# テラレイド

ローカルのテラレイドは、LDN のシーン 7 上で最大 4 ステーションからなるスカーレット/バイオレットのセッションです。ホストがロビーを運営したあと、4 人のプレイヤーのポケモン、ボスと RaidPoint を含むブートストラップメッセージを参加者全員に 1 通ずつ送ります。その後、各本体が独立してバトルを戦います。`bin/sv_host.py --raid-seed` は市販の本体が参加するレイドをホストし、`bin/sv_join.py --raid-pokemon` は本体がホストするレイドに参加します。どちらの場合も、バトル開始時にプログラム側のプレイヤーが退室し、そのポケモンは本体側の AI パートナーとして戦い続けます。アドレスは、ここで計測した市販版スカーレットが動作する 4.0.0 版の展開済み `main` に対するオフセットです。バイオレット 4.0.0 には同じオフセットに同じコードがあります（[docs/sv.md](sv.md)）。

## ホスト

ホストはシーン 7、参加者 4 人、リンクコード 4970 を告知します。本体は X → ポケポータル → テラレイドバトル → オフライン検索の順で参加します。4 つの文脈フラグを付けた `--raid-seed` でレイドが決まり（[シード](#the-seed)）、`--raid-pokemon` はこちらのプレイヤーが持ち込むパーティのレコードです（PKHeX で検査されます）。`--raid-reward ITEM:QUANTITY` を繰り返し指定すると、シードの報酬を、スカーレット/バイオレットのバッグに入るアイテムの行で置き換えます（PKHeX ヘルパーの `bag` リストで、キーアイテム以外の全ポケットを対象とし、未配信のアイテムは除きます）。`--raid-partner TRAINER` は、本体が空けたスロットごとに最大 1 回ずつ指定でき（本体 1 台なら 2 回、2 台なら 1 回）、NPC パートナーをスロット順に着席させます。`--raid-partner-progress STAGE` は、そのパートナーを連れてくる進行段階を選びます（[パートナー](#partners)）。アプリのテラレイド（ホスト）ツールには、以下のフラグが含まれています。

    --channel 1 --scene-id 7 --max-participants 4 --code 4970 --scarlet-response --session-flags 0
    --session-packet-id 1 --no-session-ack --join-seq 0 --update-seq 0 --update-delay 0.02
    --rtt-probe --clock --net-stations 4 --record-delay 0.1 --record-spacing 0.003
    --host-player-id 00000000000000010000000000000000

レイドモードでは、ホストが宛先と送信タイミングの点で交換ホストと異なります。

| | レイドのホスト |
|---|---|
| メッシュ宛てのメッセージ（RTT、0x80、0x81）、セッションのステーション一覧 | 本体のアドレスではなくサブネットのブロードキャスト宛て（ldn_mitm では相手へブロードキャストが届かないため、ユニキャストで送る） |
| Net 0x11 | 1 つのシーケンスを、0x12 が届くまで繰り返す |
| ステーション一覧の本体の項目 | 本体の参加要求が指定したプレイヤー。仮のプレイヤーの場合、本体は着席するがロビーには表示されない |
| ステーション一覧 | 本体から type 6 が届くまで 2 秒ごとに再送する |
| 立ち上げ | その type 6 の後にのみ行う。最初のバルク ACK 11 件、0x81 ポート 5 の開放、RTT 要求を 1 パケットにまとめて送る。続いて 0x81 ポート 1 の開放、チャネル表、ポート 2 の type 6 を送る。20 ms 後に identity を送り、以後 3 ms ごとに 1 レコードずつ送る |
| ポート 2 の type 3 | type 9 を 2 件返す。ホストのステーションにはコード 0、本体のステーションにはコード 1 を付ける |

立ち上げ時の 0x7C、0x81 ポート 5、0x80 ポート 2 のメッセージは、確認応答されるまで 0.25 秒ごとに繰り返されます。ホストが送る ACK はすべて、そのストリームで未確認の最小のシーケンス番号を宣言します。

### 複数の本体

`--raid-players N`（1 から 3。アプリの「参加する本体」）は、1 つのロビーに最大 3 台の本体を着席させ、それぞれ空いている最小のステーション番号（1 から 3）に入ります。本体はロビーと開始を共有し、最初のターンから各本体が自分の NPC パートナーと共に自分のバトルを戦い、各自の報酬を受け取ります（[どのステーションがサーバーを担うか](#which-station-runs-the-server)）。ホストは、本体 1 台のときと同じく本体ごとに 1 組のストリームを保持します。その本体の番号は、本体 1 台のレイドで 1 としていた箇所すべてに入ります。

| | 番号 *k* の本体 |
|---|---|
| join response | ステーション番号と参加順 *k* |
| station list | 着席しているすべてのステーション（自分を先頭）。新しい着席や退室のたびに、一覧を次のシーケンスで着席中のすべての本体へ送り、各本体の type 6 が届くまで再送する |
| Net 0x11 | 自分のステーション、次に着席中の本体をインデックス順、最後に参加者。着席が変わるたびに、着席中のすべての本体へ、その本体の次のシーケンスで送る |
| destination bitmap | 3 つの宛先ビットの下で `1 << k` |
| bulk ack | エントリ *k* |
| opening | 0x81 のポート *k* と 4 + *k*（本体が送信に使うポート） |
| port-2 type 6 | 自分と、既に着席しているメンバーを参加順に、そのコードと人数付きで |
| port-2 type 9s | 自分はコード 0、着席中の各メンバーはそのコード、本体はコード *k* を最後に付ける。着席中の各メンバーは本体のものを受け取る |
| bootstrap | スロット *k* に本体のポケモン。空席には空のスロット |

空席がない状態で参加した場合、または開始後に参加した場合、その参加要求には応答されません。空席のない本体には Net 0x11 も送られません。ホストは、ヘッダーとフッターに自分の variable id が含まれないパケットと、ビットマップにステーション 0 が含まれない信頼性のあるメッセージをすべて破棄します。同じロビーの本体どうしは、同じブロードキャストを通じて互いに宛先を指定するためです。

ポート 2 のスロットは、メンバーを `+0x170` に、u8 のコードと u64 のステーション ID として保持します。`0x138d208` は、ステーションのコードを返します（非メンバーの場合は 0xfd）。市販のホストの type 3 ハンドラー `0x1981e94` は、どのメンバーも持たず、キューに入った type 9 も指定していない最小のコード 0 から 7 を選びます（`0x279c9a0`）。そのうえで、メンバーごとに自分のコードを付けた type 9 を 1 件ずつ、参加者には 1 件をブロードキャストします。受信側 `0x18b68fc` は、まだ一覧にない `(code, id)` を追記し、一覧にあるメンバーのコードは変えません。自分の ID については、他のメンバーそれぞれに対して member-joined イベントを発生させ、コードは自分のものになります。type 6（`0x12fbf8c`、コンポーザー `0xe457cc`、参加してきたステーションにのみ送る）は、メンバーの ID を `+0xa0`、コードを `+0xc0`、人数を `+0xc4`、closed バイトを `+0xc5` に載せます。その受信側 `0x279b9c4` は、メンバーごとに type 9 を再生します。

ロビーの参加者はポート 2 のメンバーです。Lua のロビー（チャンク `be21e654`、受信側 `0.15829`。ここでの `0.N` はチャンクのメイン関数のプロトタイプ N で、0 から数えます）は、すべてのメッセージを送信者のコードの下に格納し、コードを持たない送信者は 253 の下に格納します。各本体は、ロビーに入ったときに自分の状態 0x18 とポケモンを他の本体に送り、0x18 を受け取ったステーションは自分の Ready 状態とポケモンで応答します。同じロビーの本体どうしは、互いのポケモンを交換します。

信頼性のあるヘッダーの受信チェック（`0x6f0410`..`0x6f0430`）は、受信側自身のビットを検査します。その位置は、ワード `index >> 5` の `index & 31` です（ビット 0 はステーション 0）。宛先数は 1 から 23 までのどれでも構いません。市販の送信側は、ステーション数に関係なく、ステーション容量 4（`0x44dfcb0`）から 1 を引いた値（`0x6e71c4`）である 3 を書き込みます。

ホストは、本体 1 台のときと同じく、ネットワークを残っている最小のインデックスに引き継ぎます。他の本体は、Session の type 7 を伴わずに、is-migrating の Net 0x11 と NetStartHostMigration を受け取ります。各本体への is-migrating の 0x11 は、着席しているすべてのステーションに順位を付け（順位とは次にホストを担う順番です）、次のホストの type 8 が届いてから、それ以外の本体へ送られます。NetStartHostMigration は、すべての本体が自分の 0x11 に 0x12 で応答し終えたら送られ、その後に通常の Net 0x11 は続きません。全本体がネットワークから離脱するか、各引き継ぎの時間が尽きると、この処理は終わります。

本体が 1 つのバトルに残るかどうかを決める条件は次のとおりです。

| 条件 | コード |
|---|---|
| 別の本体が離脱するのを見た本体は、その本体が移行中の場合にのみ、それを残す。移行中とは、is-migrating の 0x11 によって `[net+0x249]` が立った場合、または NetStartHostMigration によって `[net+0x1c0]` が立った場合。それ以外では、セッションからその本体を外し、自分の Net ステーションをリセットする | station-left handler `0x69d08c`, `0x69d174` |
| より新しいシーケンスを持つ Net 0x11 は、離脱済みとして印されたステーションをすべて破棄する | `0x69e008`, `0x6b5074` |
| 次のホストは、すべての Net ステーションが（新しいネットワーク上で）状態 2 に達するまで最大 8000 ms 待ち、そのあと状態 1 のままのものを破棄し、Net 0x11 を送り、すべての 0x12 を待ってから Session の type 5 を送る | NetHostMigrationJob `0x6a9cd4`, `0x6aa2a8`; `0x6d44f0` |
| もう一方の本体は、その type 5 を 10000 ms 待ち、届かなければ失敗する | `0x6dc024`, `0x6dc124` |
| type 7 の末尾の u16 は、次のホストが適用したリストのシーケンス以下である | `0x6d9164` |

この方法で引き継いだ 2 台のエミュレートしたスカーレットは、次のホストのネットワーク上で 1 つのセッションを形成し（type 5 に type 6 で応答し、どちらの画面にもエラーなし）、空いた席の NPC と共にバトルを続けました。

Pia のホストは、LDN の参加者が変わるたびに、すべてのステーションへ新しい Net 0x11 を送ります。`0x69c310` は以前と現在の接続状態を比較し、`0x69c79c` は 1 つのカウンター `[NetProtocol+0x60]` を増やして、自分以外の各ステーションに全スロットを送ります。順位は IPv4 アドレスの昇順です（`0x6a05ec`）。LDN では、参加者の 0x11 の受信側 `0x69db14` は、そのエントリからはステーションを作りません（`0x6a2fac` は 0 を返す）。代わりにホストのアドレスと ID を保存し、既に持っているステーションに順位をコピーして、0x12 で応答します。参加者のステーションは、LDN のノード一覧（`nn::ldn::GetNetworkInfo`、`0x6b43a8`）から作られます（ポート 12345）。

type 5 の受信側 `0x6d7f8c` は、新たに一覧に現れた各ステーションを、その IPv4 とポートがノード一覧（`0x6a8320`）にある場合にのみ `0x6d840c` で作成します。そうでなければ type 6 を送らず、適用済みのシーケンスを 0xffff にリセットします（`0x6d81a4`）。そのため、同じ一覧が後で届いたときに改めて評価されます。

参加者からホストへ送られる Session の type 9（`0x6d4ef0`）は、`09 | its constant id | count | count
constant ids` の形式で、まだ声を聞いていないステーションを指定します（`0x6d4a60`）。3000 ms ごとに繰り返されます。ホストの受信側 `0x6d940c` は、指定された 1 つのステーションを kick ジョブ（`0x6dc878`）に渡し、すべてのステーションに一覧を再送します。

本体が参加した後、レイドのホストは packet id 0 を送ります。さもなければ、着席した本体はより大きい id に続くものを破棄します（[docs/pia.md](pia.md#version-11-what-a-receiver-drops-scarlet-400)）。packet id 87 のパケットの後に packet id 1 で再送されたステーション一覧は、2 台の本体のロビーで最初の本体を古い一覧のまま残しました（市販版もエミュレート版も）。2 台目は、最初の本体が無応答だと報告するまで「通信中...」と表示しました。以後の一覧を packet id 0 で送ったところ、エミュレート本体 2 台と市販版スカーレット 2 台が互いを一覧に載せ、1 つのレイドを戦い、ホストが退室した後も同期しました。

`10 00` 形式のランダムなプレイヤー ID と 14 バイトのランダムなバイト列は、市販の本体からは type 6 を引き出せませんでした。匿名 ID `00000000000000010000000000000000`（`pia_connect.DEFAULT_PLAYER_ID`）は着席させることができました。

## ロビー

レイドのメッセージは、0x80 ポート 0 のゲームメッセージです。u16 のハンドラーキー、種別バイト、ステップバイト（[交換](sv.md#the-trade)）を持ち、その後にゲームのシリアライザーのヘッダーとペイロードが続きます。

| バイト | フィールド |
|---|---|
| 0 | ハンドラーキー、u16 |
| 2 | 種別とステップ。u16 のメッセージ ID 1 つ（0x012f はブートストラップ、0x0193 はバトル開始） |
| 4 | 送信者ごとのカウンター（u16）。`0xa583fc` によって送信のたびに増える。市販ホストのロビーでは 0x0105 から 0x010e、ゲストでは 1、2、3… と進む |
| 6 | 圧縮（u32）。0 は無圧縮、2 は LZ4 |
| 10 | ペイロードの展開後のサイズ（u32） |
| 14 | ネットワークオブジェクト ID（u16）。送信者の `0x14ede48` が見つけた場合を除き 0 |
| 16 | コンストラクターが書き込まない 2 バイトのパディング（市販版のメッセージでは古いヒープの値が残る） |
| 18 | ペイロード |

| キー | 種別 | 内容 |
|---|---|---|
| 0x3380 | 0x2c | レイドの記述子。種族（DevID）、フォルム、★の数、テラタイプ、性別、遭遇のレコード番号 |
| 0x3380 | 0x2d | 参加者の状態。0x00 は未準備、0x01 は準備完了、0x0c はホストの開始、0x0d はゲストのその応答、0x18 はロビーへの入室、0x1e は遅れたステーションをホストが拒否（`0.30822`） |
| 0x3380 | 0x2e | 参加者のポケモン。暗号化された 344 バイトのパーティレコード |
| 0x3380 | 0x2f | バトルのブートストラップ |
| 0x3380 | 0x30 | ロビーのタイマー。残り秒数（0x91 から減る） |
| 0x0132 | 0x6e, 0x73 | 本体がバトルを読み込み中、その後に読み込み完了 |
| 0x3480 | 0x93 | バトル開始 |
| 0x007b | 0x13 | ホストが 0x3480 の後に送るバトル開始のメッセージ |

市販のゲストは、ロビーに入ったときに 0x18 とポケモンを送り、プレイヤーが Ready を押したときに 0x01 を送ります。市販のレイド 7 件では、4 人のゲストがポケモンの 1.9 から 3.6 秒後に 0x01 を送り、3 人はホストの開始（5.39 秒時点）まで何も送りませんでした。7 件すべてで、開始に 0x0d で応答してバトルを戦いました。

ヘッダーはメッセージオブジェクトの `+0x40..+0x4f` にあります。受信パス `0x18bec54` は、ID、カウンター、オブジェクト ID をオブジェクトに書き戻しますが、いずれも比較しません。LZ4 の戻り値は確認せず、展開後のサイズは出力の容量としてのみ使います。

キー 0x007b のバトル開始フレームは、12 バイトのポートアドレス（u32 3 つ）、u32 の長さ、そして先頭 32 バイトがヘッダー構造体となるペイロードからなります。このヘッダーは `0x1227714` がそのままコピーします。内訳は、0x00 に u32 の種別、0x08 と 0x10 に u64、0x18 と 0x19 に u8、0x04 と 0x1a..0x1f はパディングです。メッセージ 15 は 0x18 に `05 05` を、その後にパディング `07 26 5a 00 00 00` を載せます。メッセージ 16（種別 0x46、ビルダー `0x2898350`）は、ビルダーが書き込まないパディングに `ceaf29` を載せます。読み取り側 `0xf5a2fc`（+0、+8、+0x10、+0x18。5 または受信側自身のインデックスを受け付ける）と、種別の switch `0xe10088`（0x46 のハンドラーは `0x2897afc`）は、どちらもパディングを読みません。`0x14ab234` は、受信側のいずれかのポートがアドレスを登録していない限りフレームを破棄します。メッセージ 15 はアドレス（0x2713、1、2）宛てで、メッセージ 16 から 20 は（0x2713、3、5）宛てです。0x2713 は、書き込み元が未追跡のオブジェクトの `+0x40` にある実行時の u32 です。
そのパディングをゼロにしたメッセージ 13、15、16 を与えられたエミュレートの Scarlet 4.0.0 は、市販のバイト列の場合と同じく、バトル開始メッセージを最初の送信で全件確認応答し、ホストのポケモンでバトルを開始しました。
エミュレートの Scarlet 4.0.0 は、ホストがメッセージ 15 と 16 を送ってから 13 ms 後に、保持分岐 `0x14ab210` を取りました。`0x14ab234` がバトル開始フレームのアドレスに一致し、`0x14ab298` がそれを格納しました。

バトルはメッセージ 16 を種別で読み取ります。読み取り側 `0xe0fd68` はフレームを取り出し、ヘッダーの +0x08 の u64 が 0 であれば、+0x00 の種別で分岐します（`0xe10088`）。種別 0x46 は、`[reader+0x48]` を唯一の引数として `0x2897afc` を呼び、`0x2897afc` は自身の `+0x71` に 1 を格納します。その引数は、フレームごとの更新 `0x289358c` 自身のオブジェクトです。`0xfa4bb4` が初期化子 `0x28950c8` で構築し（`+0x40` はバトルのステートマシン、ここでは `sm`、`+0x48` はステップ対象のオブジェクト `[sm+0xa8]`、`+0x50` は読み取り側 `[sm+0xb0]`）、`[sm+0x148]`（`0xfa4c18`）に格納して、`reader+0x48` に代入します（`0xfa4c68` の `0x2892ab4`）。状態 `0x28932a4` は、`[sm+0x148]` を使って更新を呼びます（`0x28932d0`）。更新は `+0x71` を読みます。このバイトが 0 の間は読み取り側を駆動し（`0xe0f014`）、`0xfc363c([+0x48], 0)` を呼びます。1 の間は駆動を止め、フレームごとに `0xfc363c([+0x48], 1)` を呼びます。その戻り値が true のとき、`0x28935b8` がそのバイトを 0 に戻します。値が 1 のとき、`0xfc363c` は `+0xa8` のソースから項目を 1 つ取り出し、`[+0xb8]+0xa0` のシンクが空である間、`+0xa0` と `+0xb8` のシンクに渡します。シンクは deque（map `+0x60`、start `+0x98`、size `+0xa0`）を保持し、フレームごとに各要素の vf `+0x68` を進めます（`0xfc38dc`）。更新の戻り値は使われず（`0x28932d4`）、この経路上でステートマシンの `+0x68` の状態を書き込むものはありません。
エミュレートの Scarlet 4.0.0 は、種別 0x46 の分岐で、ホストがメッセージ 16 のパディングに書いたマーカー（`46000000 d16a1616`、`0500 161616161616`）を持つフレームを取り出しました。そのフレームはメッセージ 16 でした。取り出しは、ネットワークが落ちた後、エラー 7 のダイアログの後、最初のコマンドメニューの前に、更新自身の駆動で行われました（戻りアドレス `0x28935d0`、次いで `0x28932d4`）。

4.0.0 では、どの判定もパディングを読みません。受信パスは、シリアライザーのヘッダーの最後の 2 バイト（`0x18bec98`）を読み込み、比較なしで `+0x4e`（`0x18bece4`）に格納します。49 あるメッセージクラスのうち、`+0x4e` を読み込むのはシリアライザー `0x290b150` と `0x14c7904` だけで、ヘッダーを書き出すために使います。バトル開始の読み取り側 `0xe0fd68`、`0xe106a4`、`0xf5a2fc`、`0xf5a810`、`0xf5bc10` は、+0x00、+0x08、+0x10、+0x18、+0x19 の 32 バイトのヘッダーを読みます。`0xf5a454` と `0xf5ae40` は、32 バイトすべてを `0xf5bb4c` が再送するフレームにコピーし、何も比較しません。転送のコピー（`0x14ab150`、`0x14ab234`、`0x16a319c`）は、12 バイトのアドレスだけを比較します。

ホストが 0x7C ポート 1 で告知するチャンネル表は、zlib 圧縮された 6 つのキーを持ちます。リンク交換の 4 つ（`0x007b`、`0x0132`、`0x0232`、`0x0332`）と、`0x3380`、`0x3480` です。市販のゲストは、これを 2 つのメッセージで告知します。4 つのキーを含むものと、レイドの 2 つのキーを含むもの（0.79 秒後）です。ポート 2 では、ホストから type 6 が送られます。これは、種別 5 とキャパシティ 4 の下にある type 7 のセッションブロックと、先頭にホストのステーション ID を持つ 4 スロットの一覧です（`port2.build_session`）。

`pokeldn.sv.raid.RaidHost` は、ホストのメッセージを 1 台の本体へ順番に送り出します。各メッセージは、ポート 2 の応答からの時刻に、そして本体の前のステップの後に送られます。`pokeldn.sv.raid.RaidGroup` は、1 つのロビーの本体どうしが共有するものを保持します。本体 1 台が 5 秒以内に準備完了する場合、シーケンス番号は市販のホストのものになります:

タイマーは、ホストのロビーの期限までの残り秒数です。市販のホストは 180 秒のロビーを開き、その値を 1 秒ごとに送ります（`0.27104`）。そのため、表の 0x91 は、開いてから 35 秒後に届きました。こちらのタイマーは、最初の本体の応答時に 180 から始まります。進行中のロビーに参加した本体は、その時点の値を受け取ります。本体が 0x00 または 0x18 を送ると、その 0x01 は取り消されます。ポケモンは取り消されません。準備完了の本体が、新たに入ってくる各参加者にそれを再送するためです。

ゲームのコードでは、ゲストは 0x0c に対して Ready の確認なしにすぐ 0x0d で応答します。タイマーが 0 に達したゲストは、ブートストラップを待ちます（`Raid_Start_Ready`、`0.27137`）。バトルを開始するのはホストだけです。準備しないままブートストラップを持つゲストは、タイマーより前にロビーを終え（`0.27104`）、同じ方法でバトルに進みます。市販のホストは、プレイヤーの最初の選択で準備を行い、2 回目の選択で 0x0c を送ります（`0.27095`）。`Raid_Start_Ready` は、入ったときにメニューの最初の 3 項目を、ホストもゲストも同じく無効にします（`f6277C172(false)`）。ホストでは、開始する最初の項目とメニューを、他のすべてのメンバーが準備完了の間は有効にし、1 人でも準備できていなければ再び無効にします。そのため、プレイヤーは全ゲストが準備完了になってからでないと開始できません。`f6277C172(false)` が項目を隠すのか灰色にするのかは未解明です。タイマーが 0 のときは、誰も準備していなければロビーを解散し、そうでなければ開始します。`Raid_Start_Go`（`0.27140`）は、全メンバーが 0x0d で応答するまで 0x0c を再送し、その後ブートストラップを送ります。スロット *k* には、コード *k* のメンバーのポケモンが入ります。こちらのホストは、全本体の 0x0d も待ち、全本体が準備完了になったとき、またはタイマーが 0 になったときに、準備完了の者が誰であれ開始します。

ゲートされたメッセージは、対応する節目の 50 ms 後に送られます。Net 0x50 とステーション一覧は、応答されるまで 0.5 秒ごとに繰り返され、レイドのメッセージは確認応答されるまで 0.5 秒ごとに繰り返されます。市販の本体が、ブートストラップに対して 0x6e なしで 0x73 だけを返したことがあるため、メッセージ 13 はそのどちらかを待ちます。

最後の本体のメッセージ 20 から 5 秒後、ホストは、離脱する市販のホストと同じように、本体にネットワークを引き渡します（[docs/sv.md](sv.md#leaving)）。Session の type 7 は本体を指定し、その type 8 が届くまで 1 秒ごとに送られます。is-migrating の形の Net 0x11 は、その 0x12 が届くまで 0.5 秒ごとに送られ、NetStartHostMigration `01400000` は、本体がネットワークを離脱するか 4 秒経過するまで 0.3 秒ごとに送られます。メッセージ 20 の 5 秒後にネットワークを破棄したホストは、代わりに、市販のレイド 4 件のうち 1 件で、バトル開始時に本体の画面に 2318-0006 を表示させました。その後、バトルはオフラインで続きました。

Net 0x50 は、交換ホストのプロパティ本体（`NET_PROPERTY_BODY`）で、シーケンス 1、ネットワーク ID、バイト 27 を 7 に設定し、ホストの 132 バイトのアプリケーションデータを +38 に置いたものです。メッセージフラグ 0x31 の下で zlib 圧縮されます。0x31 の下で非圧縮のまま送ったところ、0x51 は返ってきませんでした。

## バトルのブートストラップ

メッセージ 0x2f は、0xaa0 バイトのレコードを LZ4 で圧縮して運びます（ブロック形式のみ、`pokeldn.sv.lz4`）。

| オフセット | サイズ | 内容 |
|---|---|---|
| 0x000 | 4 x 0x158 | 4 人の参加者のパーティレコード（暗号化済み）。ホストのものはスロット 0 |
| 0x560 | 0x158 | ボスのパーティレコード |
| 0x6b8 | 0x3e8 | RaidPoint |

シリアライザー `0xe327fc` は、メッセージオブジェクトの `+0x440`、`+0x448`、`+0x450`、`+0x458`、`+0x50` にある 5 つのレコードを、`0xe329b4` を通じて（それぞれ 0x158 バイト）書き出し、次に `+0x58` の 4 つの quadword と、`+0x78` からの 0x3c8 バイトを書き出します。オブジェクト（0x460 バイト）は `0x18bb4fc` が作り、`0x18bb5f8` が型を与えます。`0x1592b7c` がシリアライザーのヘッダーを書き、圧縮方式を選びます。`0x1592dac` と `0x1592e80` が LZ4 を実行します（`0x71d940`）。RaidPoint は丸ごとコピーされます。`0x1bae670` が `0x1bae760` を呼び、それが反射フィールドのゲッター `0x1baff98` を通じて（`+8` のポインタ、またはゼロ埋めの 0x3c8 バイトのシングルトン）、`0x1bb0018` によって `+0x78` に入れます。

空の参加者スロットは、種族 0、レベル 1、ニックネーム `Egg`、テラタイプ 19、言語 2、現在 HP 11、能力値 11/5/5/5/5/5 のレコードを持ちます。これは市販のブートストラップすべてで同じレコードです。空のスロットがすべて 0 のブートストラップは、バトル開始時に市販の本体をクラッシュさせました。ゲストのスロット 1 は、そのロビーのメッセージ 0x2e にあるレコードです。市販のホストは、メッセージを 1395 バイトで分割し、2 つ目の断片を zlib 圧縮しました。

RaidPoint の、先頭からのオフセットは次のとおりです。

| オフセット | サイズ | 内容 |
|---|---|---|

| 0x018 | u32 | 0x40（市販の黒いポイントの 1 つは `0x458F9952` を持っていた。0x40 も受け付けられる） |

レイドのテーブルでは、6 つ星のすべてのレコードの `raidTimeData` は `gameLimit` 450 と `commandLimit` 60 の active で、1 つ星のすべてのレコードは `gameLimit` 300 の inactive です。残りは 0 です。市販の黒いポイント（レコード 6045）は 1、450、0、60 を持ち、市販の 3 つ星のポイント（レコード 3019）は、inactive の bool バイトの後に 3 つの古いバイトが続き、その後にゼロが並んでいました。バイト 0x3b5..0x3b7、0x3d4..0x3d7、0x3e4..0x3e7 は、両方の市販ポイントで古いバイトを保持していました。

行動プロファイルは、ゲームのレイドテーブルにおけるレコードの `bossDesc` で、その順に並びます。行動は、0 なし、1 ボスの能力変化をリセット、2 プレイヤーの能力変化をリセット、3 わざ、4 テラオーブを吸収、です。タイミングは、0 なし、1 時間、2 HP です。行動の値は、それを引き起こすボスの HP または残り時間の割合で、シールドの最初の 2 つの値は、どちらか一方で上げる HP と時間の割合です。2026 年 8 月の 7 つ星キングアンブラについて Serebii が載せている定型の行動も、そのレコードから同じように読み取れます。HP 係数は、1 つ星から 6 つ星までそれぞれ 500、500、800、1200、2000、2500 です。

市販のポイントの報酬行は、シードの固定行、次に抽選行、最後にホストのボーナス行の順です。ボーナス行は、対象 4 の下に 3 行、対象 5 の下に 1 行です。固定行の対象は、報酬テーブルの `SubjectType` です（0 は全プレイヤー、1 はホスト、2 はゲスト、3 は一度だけ）。ゲームの enum `RaidRewardItemSubjectType` には 4 と 5 がありません。どちらの市販ポイントでも、対象 4 の行は、同じ生成器でシードの抽選をさらに 3 回引いた結果で、対象 5 の行はボスのテラピースでした。その数は、難易度に応じて `RaidGemItemRewardBoost` が与える値です（1 から 7 つ星で 0、0、2、5、10、12、0。3 つ星では 2、6 つ星では 12）。ミールパワーのテーブルの読み取り側 `0xef885c` は、レイドの 1 フィールド `AddRewardSlots` を読みます。行の 3 番目のワードは、ボトルキャップの抽選行では 1、それ以外では 0 でした。

エミュレートの Scarlet 4.0.0 のゲストは、対象 0 から 5 のそれぞれに 1 行を送ったところ、報酬画面には対象 0、2、3、5 が表示され、1 と 4 は表示されませんでした。ミールのレイドパワー（ゴースト Lv. 1）が有効な状態では、はがねテラのボスに対しては対象 4 を表示せず、ゴーストテラのボスに対しては表示しました。そこに対象 4 の行を 3 つ送ると、表示されたのは最初の 1 行だけでした。ゴーストテラのボスに対して対象 4 の行を 4 つ送ったところ、パワーがレベル 2 のときは最初の 2 行、レベル 3 のときは最初の 3 行が表示されました。

有効なミールパワーは、メモリ上で u32 の種別、u32 のタイプ、u32 のレベル、残り秒数の f32 として保持されます。食べたときは 1800 で、フィールドでカウントダウンします。上のレベル 2 と 3 の確認と、以下の確認は、ジャンボンブールのレイドパワー（ゴースト Lv. 1）のレコードのレベルとタイプのワードを書き換えるものでした。

黒いクリスタルのポイント（シード `09F3E337`、テラタイプがフェアリーのキングアンブラ）で、レイドパワー（フェアリー Lv. 3）が有効なとき、同じゲストはポイントの 19 行のうち 18 行を表示しました。すなわち、対象 0 のすべての行、対象 2 の行、対象 4 の 3 行、そして対象 5 のフェアリーテラピース ×12 です。対象 1 の行は表示されませんでした。レアアイテムのフラグを持つ 1 行、対象 4 のボトルキャップが画面の先頭に来て、他の行はポイントの順序を保ちました。このポイントは、単一のゲストで勝てるように、ボスの行動プロファイルだけ（HP 係数 100、残りは 0）を置き換えた `raid_point` のものでした。その星の数、クリスタル、`raidTimeData`、行はシードのものです。

Scarlet 4.0.0 の Lua の報酬フィルター `C07C34FC3B976E5A7.F316609DEA110601D`（バイトコードが記録する 78707 行から 78765 行まで）は、すべてのプレイヤーに対して対象 0 を、ホストに対して 1 を、ゲストに対して 2 を保持します。一度だけの報酬の資格引数が true のときは、対象 3 も保持します。対象 4 の行は先頭から N 行を保持します。N は、ボスのテラタイプに一致する有効なレイドパワーのうち最も高いレベルです。ミールの種別 5 はレイドパワーです。種別 18 は、すべてのテラタイプに一致します。対象 5 は、受け取るプレイヤーのインベントリにあるアイテム 2481（きらめきのおまもり）を必要とします。行カウンターは、対象 4 の行ごとに進みます。テストハーネスが与えたネイティブの環境ゲッターを使い、変更していない Lua 関数を実行したところ、ホストとゲストの両方で、お守りの有無にかかわらず、レベル 0 から 3 で対象 4 の行を 0、1、2、3 行保持しました。種別が一致しない場合は 0 を保持しました。一致する複数のパワーがあるときは、最も高いレベルを使いました。

市販の報酬構築に合わせたホストは、固定行ごとの対象とレアアイテムのフラグを保持し、通常の抽選行を対象 0 の下に書き込み、その後に対象 4 の下で継続の抽選を 3 回追加します。難易度に応じたテラピースのボーナスは、数量が正のときに対象 5 の下に追加します。各受信側は、自分のミールとお守りの資格を適用します。

タイマーの初期化子 `C2D7F486425487755.F0C64BA9B6853E61A`（バイトコードが記録する 79486 行から 79513 行まで）は、`raidTimeData.active` が true のとき、与えられた時間フィールドを使います。false のときは、グループバトルはゲーム上限 300、コマンド上限 60、クライアント上限 0、復活時間 30、AI 間隔 17、AI 間隔のランダム性 6 を使います。6 つ星のテーブルデータで、変更していない Lua 関数を実行したところ、それぞれ 450、60、0、0、0、0 を返しました。ゼロ埋めの RaidPoint は既定値になりました。
両方の関数は Lua チャンク `be21e65463b9a98f` にあり、SHA-256 は `c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815` です。

`raid_point` は、市販のホストと同じ方法でシードの行を組み立てます。各固定行のテーブルの対象、抽選テーブルのレアフラグ、対象 4 の下の 3 回の抽選、対象 5 の下の難易度に応じたテラピースのボーナスです。シード 7B741233（3 つ星）と 09F3E337（黒）では、その 45 行は市販ポイントのバイト列と一致します。きらめきのおまもりを持つ市販のスカーレットのゲストに、シード 7B741233 の行を送ったところ、アイステラピース x1 と x2 が表示されました。これは対象 5 の行で、ホストの対象 1 の x1 の行は表示されませんでした。選ばれた報酬は、ボーナス行なしで対象 0 の下に入るため、ゲストはそのすべてを受け取ります。市販の本体は、クイックボール x500 に書き換えた行を、他の行を消し、ボーナス行を 1 つ残した状態で受け取り、その内容どおりに付与されました。

## パートナー

すべての本体は、どのロビーのメンバーも持たない参加者スロットを、同じ NPC トレーナーで埋めます。トレーナーは、Lua が `randSeed`（0x3d8 の u64）と `raidNpcGroupID`（0x3e0 の u32）と呼ぶ、RaidPoint の 2 つのワードから抽選されます（`0.4453`）。そのゲッターの背後にあるネイティブは、RaidPoint の最初の 0x20 バイトに続く 0x3c8 バイトの構造体の +0x3b8（`0x1be5ac0`）と +0x3c0（`0x1be5c20`）を読みます。ゲストのブートストラップハンドラーは両方を読みます（`0.15829`）。市販のホストは、開始のたびに新しい `randSeed` を抽選し、両方を書き込みます（`Raid_Start_Go`、`0.27140`）。u64 のシードは xoroshiro128+ 全体を初期化し（ネイティブ `0x17ebec0`）、2 つ目のワードは `0x82A2B175229D6A5B` です。本体は 3 人のトレーナーを抽選します（`0.7804`）。各抽選は、プールに残っている n 人に対する `next_int(n)` です（n − 1 のビットでマスクし、n 以上の値は引き直す）。抽選されたトレーナーはプールから取り除かれるため、プール全体では上限が 18、17、16 と変わります。空いたスロットは、スロット順に抽選結果を受け取ります（`0.4455`）。空きが 1 つなら、位置にかかわらず最初の抽選結果を受け取ります。

パートナーのレコードは、同じ `randSeed` から xoroshiro128+ を 5 回引いて作られ、バトル内のパートナーは全員その値を共有します（`raid_partners.identity`）。抽選 0 は暗号化定数（0xffffffff の間は引き直す）、抽選 1 は TID | SID << 16、抽選 2 は PID（色違いになる場合はビット 28 を反転）、抽選 3 は身長、抽選 4 は体重で、どちらも 0x30 + next_int(0xa0) です。それ以外は、後述のトレーナーのエントリから得られ、言語は 2、種族の基本なつき度です。シード、段階、レベルだけから、これらの規則により、5 回のエミュレートしたレイドバトルの 10 件のパートナーレコードすべてが得られます。各 0x148 バイトです。

レイド開始（`0.4455` → `0.4459` → `0.4901`）は、各パートナーの `poke1` テーブル、そのレベル、`randSeed` を Lua バインディング `f92C18AA6`（`0x1905a10`）に渡します。これは、シードが `randSeed` である pml の InitialSpec を組み立て（`0x1905ce0`）、テーブルをそれに変換し（`0x160ffd0`）、PokemonParam を作成します（`0xdebe4c` → `0xdec698` → `0xdef2b8`）。シードされた `0xdef2b8` は、スペックが設定しない項目（EC、ID、PID、IVs、特性、性別、性格、身長、体重、スケールの順）について、すべての抽選を独自の xoroshiro128+（`0xdf78bc`、`next_int` `0xdf78d8`）から行います（`0xdf011c`）。バインディングの第 3 引数は true なので、コンバーターは乱数で決まる身長、体重、スケールをサイズクラス M（SizeType 3、`0x1611cc4`）に変換します。`0xdf011c` は、それを 0x30 + next_int(0xa0) で抽選します。乱数の場合は next_int(0x81) + next_int(0x80) になります。unicorn の下で実行すると、`0xdef2b8` は、サイズクラス M の場合にのみ、10 件のレコードの EC、PID、身長、体重を再現しました（他のクラスでは再現しませんでした）。

コンバーターは、暗号化定数が抽選される前に、`sex` が 0 のエントリの性別を、その未設定のフィールドから決めます。種族のメス率が (2^64 - 1) mod 100 = 15 以上ならメス、15 未満ならオスです。50 の場合は、バインディングの第 4 引数（0）が決めます。性別が一種類の種族、または性別なしの種族は、自身のものを保持します（`0x1611d1c`）。Growlithe と Arcanine はメス、Magnemite、Magneton、Bronzong は性別なし、その他のパートナーはオスです。`gemType` が 0 のとき、テラタイプは種族ごとのテーブル `0xe78418` に任され、キーは 種族 × 10000 + フォルムです。Haxorus はドラゴン、Clodsire はじめんになります。

`0x3e0` の u32 が、抽選に使うプールを選びます。データテーブルのフィールド `difficulty_0`*N+1*（`0.7797`）、そのトレーナー、そのポケモン（下の表）を決めます。0 と 1 では先頭 16 人、2 では 18 人全員、3 と 4 でも 18 人全員です。プールは RomFS のテーブル `world/data/raid/raid_trainer_01`（16 行、段階 0 と 1）、`_02`（18 行、段階 2）、`_03`（18 行、段階 3 と 4）です。行は `raidTrainerInfo` を持ち、トレーナー ID は `raid_assist_NPC_1` から `_52` まで、`npcPresetIndex`（行のインデックス。`0.4459` がトレーナーのモデルに渡す）、`nameTextLabel`（全プールで行 0 以降は `TRNAME_RAID_ASSIST_01`）を保持します。トレーナーの 1 体のポケモンは、`world/data/trainer/trdata/trdata_array` にあるエントリの `poke1`（`PokeDataBattle`）です。種族、フォルム、レベル 16、40 または 80、`tokusei` 2 から 4（特性スロット 1、2、または隠れ特性）、3 つのわざ、`gemType`（2 + テラタイプ）、個体値 31/10/31/31/10/31（HP 攻撃 防御 素早さ 特攻 特防）、努力値 HP 252、防御 128、特防 128、性格 がんばりや、モンスターボール、色違いなし、`sex` 0、スケール 128、持ち物なし、です。`raid_trainer_04` から `_07` はフィールドのトレーナー（`area04_trainer_*`、`area05_trainer_*`）の一覧ですが、それを読むものは不明です。`scripts/gen_sv_partner_data.py` は、プールを `pokeldn/sv/data/raid_partners.json`（`raid_partners.game_pool`）に復号します。パートナーのポケモンは、プリセットではなく、バトルスロット 0 にいるポケモン（ホストのもの）のレベルの int(0.8 × そのレベル) で作られます（`0.4455`、`0.4901`）。そのため、Serebii のレベル 16、40、80 は、レベル 20、50、100 のホストのものです。pokeldn のレイドでは、スロット 0 に `--raid-pokemon` が入ります。市販のスカーレットでは、自身のポケモンのレベル（100 と 84）に関係なく、Eli の Gardevoir がレベル 100 の隣でレベル 80、レベル 37 の隣でレベル 29 で表示されました。最初の段階の Eli の Kirlia と Charlotte の Staravia は、レベル 100 の隣でレベル 80 で表示され、プールの 16 人を超えるトレーナーでした。段階 5 では、市販のスカーレットのパートナーは、ボスの名前を付けられたピカチュウで、その後バトルがクラッシュしました。そのため `raid_point` は、段階 4 を超える段階を拒否します。

## シード

レイドは、32 ビットのシードと、本体の状態（バージョン、地域（Paldea、Kitakami、Blueberry。テーブルの接頭辞は `""`、`su1_`、`su2_`）、ストーリーの進行、クリスタル）から決まります。xoroshiro128+ は、シードと定数 `0x82A2B175229D6A5B`（`0xe29340`）から始まります。その最初の抽選（100 面の値）は、ストーリー段階の上限に照らして標準クリスタルの星の数を決め（黒いクリスタルは 6）、2 つ目の抽選は、その星の数とバージョンの中で出現率によって遭遇を決めます。`0xe29404` は、テーブル名を `%sdifficulty_%02d` で組み立て、そのレコードを `0x1eab5e4` に渡します。`0x1eab5e4` は `raidEnemyInfo` を読みます。`0x2935b68` は、3 つの接頭辞と 6 段階をすべてたどります。同じシードから新たに作った xoroshiro は、ボスを抽選します。EC（シードの下位半分に `0x229D6A5B` を加えたもの。そのためボスのレコードからシードを取り出せます）、偽のトレーナー ID、PID、完璧な個体値、個体値、特性、性別、性格（Toxtricity の性格は、そのフォルムの一覧から）、身長、体重、スケールを、PKHeX の `Encounter9RNG.GenerateData` と同じ順序で決めます。テラタイプと報酬の抽選は、それぞれ別の新しい生成器を使います。

`pokeldn.sv.raid_encounter` は、これを `pokeldn/sv/data/raid_base.json` の上で実装しています。このデータは `scripts/gen_sv_raid_data.py` が、Tera-Finder の遭遇一覧と報酬テーブル、PKHeX の personal テーブル、ゲームの RomFS にある 18 個の `raid_enemy_XX_array` テーブル（`arc/worlddataraidraid_gem_item_reward_boostdata.bin.trpak`、独自の `.bfbs` スキーマを持つ FlatBuffers）から生成したものです。すべての文脈で 12600 を超えるシードについて、そのボスは PKHeX.Core 26.8.26 とフィールドごとに一致します。ただし、市販のテーブルがテラルール 0（種族自身のタイプ）を与える Paldea の 6 つの遭遇（レコード 5094 から 5099）は例外で、PKHeX はこれをルール 1（任意のタイプ）として扱います。クリスタルの構築を行う `0xe26ff0` は `gemType` を読み、0 と 1 のどちらでも 18 のうちいずれかを抽選します（`0xe27414` の `cmp w9, #2`。値が 18 未満になるまで引き直す）。これは PKHeX と同じです。一般的なコンバーター `0x160e108` は 0 を種族のタイプとして扱いますが、レイドの経路には乗りません。シード `BD13FB43`（Violet、Paldea、4 つ星）から作ったボスのレコードは、市販のブートストラップとバイト単位で一致します。`7B741233`（Scarlet、Paldea、5 つ星）から作ったものは、ニックネームと言語を除けば、フランス語の市販スカーレットと一致します。市販のホストは自分の言語と、その言語の種族名を書き込みます（`Embrylex`、3）。生成器は英語（2）です。本体は、どちらの場合も、ボスを自分の言語の名前で表示します。

レイドのテーブルにおける種族は、ゲームの DevID です。全国図鑑番号 916 までは図鑑番号どおりで、917 からはゲーム独自の順序になります（Tinkatink は図鑑番号 957 で、DevID は 1000）。`gen9.internal_index` として扱います。ディスクリプターと RaidPoint も DevID を持ちます。種族 1000 を指定したディスクリプターと RaidPoint を表示した市販のスカーレットは、Tinkatink として一覧に載り、そのまま戦いました。

黒いクリスタルのレコードは、努力値付きでバトルレベル 90 を持ち（例: 防御 128、特防 128）、捕獲レベルは 75 です。標準のレコードでは、2 つのレベルが一致し、努力値は 0 です。ブートストラップのボスのレコードと RaidPoint のサマリは、バトルレベルと努力値を持ち、RaidPoint の `+0x2c` は捕獲レベルを持ちます。`09F3E337`（Scarlet、Paldea）から作った黒いボスは、ニックネームと言語を除けば、フランス語の市販スカーレットと一致します。

## イベントレイド

Poke Portal News の配信には 5 つのファイルがあります。`raid_enemy_array`、`fixed_reward_item_array`、`lottery_reward_item_array`、`raid_priority_array` は、基本テーブルのレイアウトを持つ FlatBuffers です。`event_raid_identifier` は、優先度テーブルの `VersionNo`（`20221202`）を繰り返す u32 です。1.3.0 以降の配信では、それぞれが対象のパッチ（`_1_3_0`、`_2_0_0`、`_3_0_0`）の下に再び入り、古いほうのコピーは無効化されています。最新のものが読み込まれます。`raid_enemy_array` のレコードは標準のものと同じで、`RomVer`（0 は両バージョン、1 はスカーレット、2 はバイオレット）、`DeliveryGroupID`、`Difficulty`（星の数。7 は 7 つ星のレイド）、`CaptureRate`（0 は捕獲不可、1、2 は 1 回捕獲可能）、そして独自の報酬テーブル名を持ちます。`BossPokePara` は、標準のボスが抽選する内容を固定します。

| フィールド | イベントのレコード |
|---|---|
| `Sex` | 0 は抽選。1 はオス、2 はメスで、性別の抽選は行わない |
| `Seikaku` | 0 は抽選。性格は値 + 1 で、抽選は行わない |
| `TalentType` | 1: `TalentVnum` の完璧な個体値。2: `TalentValue` の 6 つの個体値。いずれも抽選なし |
| `RareType` | 0 は抽選。1 は色違いにしない（偽のトレーナーに対する色違いの PID は、ビット 28 を反転）。2 は常に色違い（上位半分を、色違い用の xor 値 0 で書き換える） |
| `ScaleType` | 0 は 2 回抽選。1 から 5 は 1 回抽選し、0-15、16-47、48-207、208-239、240-255 のいずれかに当たる。6 は `ScaleValue` |
| `Item`、`EffortValue` | ボスの持ち物とバトル時の努力値（7 つ星のピカチュウは でんきだま を持つ） |

レコードの `TimeDesc` は、その `raidTimeData` であり、RaidPoint は 0x030 にそれを持ちます。7 つ星のすべてのレコードは active で、`gameLimit` は 450 から 900、`commandLimit` は 60 です。5 つ星のレコード 5 件も同様です（`gameLimit` は 320 から 450）。残りの 420 件は inactive です（2026-09-06 のギャラリーによる）。

レイドの巣は、配信グループ 1 から 10 のいずれかに属します。`raid_priority_array` が各グループの巣の数を数えます。シードからの xoroshiro は、標準クリスタルの星の数に使われる 100 面の抽選を引いて捨てます。次に、そのグループのレコードのうち、本体のバージョンに一致し、かつストーリー段階が許す星の数のものの出現率の合計未満の値を引きます。そして、テーブル順でその値が範囲に入るレコードを選びます [PKHeX `EncounterDist9.GetIsPossibleSlot`]:

| 進行 | 段階 | 抽選される星の数 |
|---|---|---|
| 最初（テラレイド） | 0 | 1, 2 |
| 3 つ星 | 1 | 1 から 3 |
| 4 つ星 | 2 | 1 から 4 |
| 5 つ星、6 つ星 | 3 | 3 から 7 |

出現率 0 のレコードは、決して抽選されません。ボスとそのテラタイプは、標準のレイドと同様に、レコードの固定フィールドを使って抽選されます。報酬は、レコードの固定テーブル、次に配信独自のテーブルからの抽選結果です。7 つ星のレイドの数は、6 つ星のレイドと同じように数えます。出現率はあるがアイテムのない抽選スロットは合計に含まれますが、何も与えません。数量 0 の行も同様です。Scarlet における Gimmighoul の 2023 年最初のラウンドの抽選テーブルはこのように不正で、すべてのスロットが空か数量 0 であるため、そのレイドは固定行のみを与えます。

`pokeldn.sv.raid_event` は、配信フォルダ（[EventsGallery](https://github.com/projectpokemon/EventsGallery) のイベント、またはその `Files`）を読み込み、ホストが配置する `Raid` を生成します。

    ./.venv/bin/python bin/sv_host.py ... --raid-pokemon FILE --raid-seed 52E6B438 \
        --raid-event "EventsGallery/Released/Gen 9/SV/Raid Events/002 Charizard the Unrivaled" \
        --raid-version scarlet --raid-progress 6star [--raid-event-group 1] [--raid-catch-normal]

RaidPoint は、レコードの捕獲率と、クリスタルとしてセーブのレイド内容を持ちます。2 はイベント、3 は 7 つ星のイベントです（Tera-Finder の `RaidContent`）。

エミュレートした Scarlet 4.0.0 のゲストは、両方のレイドと戦いました。Eevee Spotlight（20221125）は、シード `00000002`、最初の進行、クリスタル 2 で、1 つ星の Eevee が捕獲され、報酬画面にはシードの行が順番に並んで表示されました。Charizard the Unrivaled（20221202）は、シード `00000001`、6 つ星の進行、クリスタル 3、`raidTimeData` 1、600、0、60 で、ボス名は「Charizard the Unrivaled」、タイマーバーは 1 分ごとに長さの約 10 分の 1 ずつ減りました。制限時間は 600 秒でした（本体自身の制限は 300 秒）。
ESP32 基板を介した市販の Scarlet は、同じ 2 つのレイドと戦いました。1 つ星の Eevee に勝ち、捕獲が提示され、シードの報酬が与えられました。Charizard the Unrivaled は 7 つ星として表示され、そのタイマーバーはゆっくり縮みました。また、標準の黒いレイド（シード `00000004`、Pincurchin）とも戦いました。その RaidPoint は、レコードの `raidTimeData` 1、450、0、60 を持っていました。

アプリのテラレイド（ホスト）ツールは、ダウンロードと更新を行うギャラリーの独自のコピーからイベントを選び、レイドのバージョン、進行、クリスタルを、そのイベントが出現するものに絞り込みます（[イベントレイド](gui.md#raid-events)）。提示されるクリスタルは `raid_event.dens` から得られます。これは、優先度テーブルに巣を持ち、そのバージョンにレコードを持つ配信グループです。Walking Wake のスポットライトは、スカーレットにはグループ 1、バイオレットにはグループ 2 を提示します。

捕獲率 2 は、セーブごとに 1 回だけ捕獲できることを意味します。7 つ星のレコードはすべてこれを持ち、各スポットライトの回の 5 つ星の Walking Wake と Iron Leaves、Dialga と Palkia のスポットライト、色違いの Rayquaza も同様です。セーブは、捕獲されたレコード番号を、番号と捕獲済みフラグの組として 1 件 8 バイトで保持します（ブロック `0x8B14392F`。2.0.1 以降は、撃破フラグが `0xA4BA4848` のもので、PKHeX の `RaidSevenStar9`）。再放送では同じ番号が繰り返されるため（Walking Wake は 7 回のラウンドすべてで 2023022801）、あるラウンドでの捕獲は他のラウンドの捕獲を塞ぎます。色違いの Treasures of Ruin のスポットライトのレコードは 0 で、一度も捕獲されていません。ホストの概要には、そのルール（`caught once per save`、`cannot be caught`）が示されます。

本体は、ロビーのディスクリプター（0x2c）のレコード番号で、その一覧を確認します。Mighty Mewtwo（2023090101）を捕獲済みだった市販のバイオレットは、そのホストのディスクリプターを示されると、ロビーで「Tera Pokemon は捕まえられません」と表示しました。RaidPoint の捕獲率が 1 でも 2 でも同じでした。バトルの前に RaidPoint は送られないためです。セーブが捕獲済みとしていた Magikarp the Unrivaled（2026071701）に対しては、同じ本体が次のようになりました。

| ディスクリプターのレコード番号 | RaidPoint の捕獲率 | ロビー | 勝利後 |
|---|---|---|---|
| 2026071701（レコード本来の番号） | 2 | 捕まえられない旨の表示 | 捕獲なし |
| 2026071701 | 1 | 捕まえられない旨の表示 | 捕獲なし |
| 2026071799（代用の番号） | 1 | 警告なし | 捕獲 |
| 2026071799（再度） | 1 | 警告なし | 捕獲 |

セーブが捕獲済みとして一覧にするレコード番号は、RaidPoint がどの捕獲率を持っていても、勝利後の捕獲を塞ぎます（2 行目）。捕獲率 1 での捕獲は、代用の番号を一覧に加えません（4 行目）。`--raid-catch-normal` は、1 回だけ捕獲可能なレコードを通常の捕獲として提供します。RaidPoint の捕獲率は 1 にし、ディスクリプターには代用のレコード番号を入れます。代用番号は、レコードの日付に接尾辞 99 を付けたものです（`raid_event.stand_in`: 2026071799）。どの配信もその接尾辞は持っていません（すべて最大 14）。概要には `served as a normal catch of record 2026071799` と表示されます。一度も捕獲されていないレコードは 0 のままです。

代用番号はディスクリプターにのみ入ります。ボスのレコードと RaidPoint の捕獲率は、イベントのものとバイト単位で同じです。PK9 のフィールドにはレコード番号を保持するものがありません。PKHeX.Core 26.8.26 のレイド遭遇（`EncounterDist9`、`EncounterMight9`）にもレコード番号はなく、配信グループのみを持つため、捕獲の適法性はそれに依存できません。ギャラリーにある 1 回だけ捕獲可能なレコードのすべてについて（Kingambit の 2 回目のラウンドは除く。それはそのリリースより新しいものです）、出現する各バージョンで、シードごとに 3 つ、Magikarp は `000FD5D7` で、計 331 回のレイドを検証しました。ホストが送るボスのレコードは、PKHeX 自身による遭遇の変換が与えるものをテストトレーナーに与えると、そのシードからのそのレイドにおける PKHeX の捕獲と一致し、適法でした。7 つ星の捕獲が適法なのは、本体がそれを与える Mightiest Mark（`RibbonMarkMightiest`）を持つ場合だけです。本体が 2026071799 のもとで捕獲した Magikarp は、それを持っています。

固定報酬行の対象 3（`Encounters.txt` の `Only Once`。7 つ星のレイドの TM と特性パッチ）は別のルールです。`raid_point` はテーブルの対象を書き込み、各本体の報酬フィルターがそれを適用します。
イベントのボスは任意の種族になり得るため、レイドのボスを超える personal エントリ、わざの PP、名前は `pokeldn/sv/data/species.json` から得られます（`scripts/gen_sv_species_data.py`、`raid_base.json` の PKHeX リビジョン）。

EventsGallery の 153 件の配信フォルダ（2026-09-06）に対して、すべてのテーブルはその JSON として復号されます。pkNX のリッパーが作る分布と 7 つ星の遭遇は、PKHeX.Core 26.8.26 の 174 と 55 のすべてと一致します（Kingambit の 2 回目のラウンドは、そのリリースより新しいものです。`000 Base Data` はゲーム自身のプレースホルダーです）。20 080 体のボスと、各イベント、バージョン、段階、グループごとに 40 のシードは、PKHeX の `GenerateSeed32` とフィールドごとに一致します。PKHeX は、各レコードをその段階で許容します。`scripts/check_sv_raid_events.py` は、各配信の 537 件の遭遇と、そこから抽選されたレイドが、`Encounters.txt` と一致することを確認します（Gimmighoul の不正なラウンドを除く）。PKHeX の 229 件の遭遇それぞれについて、シード `00000001`、`12345678`、`9ABCDEF0`、`DEADBEEF`、`52E6B438`、`0000F00D` で、`boss_fields` がギャラリー上のそのレコードに対して抽選する暗号化定数、個体値、特性番号、性別、性格、身長、体重、スケールを得ます。

## シードの検索

アプリのレイドシードの欄は、ツールの文脈でシードが与えるボスと報酬を表示します。「Find a raid」は、フィルターが残した文脈すべてについて、最初のシード（入力したもの、またはランダムに選んだもの）から、種族、星の数、テラタイプ、性格、性別、色違い、サイズの印、個体値の範囲を満たすシードを検索します（`pokeldn.sv.raid_search`）。結果は、ボスの能力値によるスコア（HP と防御の合計の積、どちらか一方の防御、より高い攻撃能力、または合計値）か、欲しい報酬（下の「最も欲しい報酬」）で順位付けされます。種族を選ばない限り、種族ごとの結果は 1 つだけ残ります。

### サイズの印

PKHeX では、Scarlet または Violet にいたポケモンについて、スケール 0 のミニの印と、スケール 255 のジャンボの印が許可されています（`MarkRules.IsMarkAllowedMini`、`IsMarkAllowedJumbo`）。ファインダーのサイズの印の条件は、ボスのスケールが 0（ミニの印）、255（ジャンボの印）、またはいずれか（任意の印）であることを求めます。スケールは、身長と体重の後に抽選されます（`boss_fields`）。

| スケールの規則 | スケール | 0 または 255 になる確率 |
|---|---|---|
| 2 回抽選（規則 0）。標準と黒いクリスタルのすべてのボス | `next_int(0x81) + next_int(0x80)` | それぞれ 16 512 分の 1 |
| 0 から（規則 1）または 240 から（規則 5）のイベントの帯 | `next_int(16) + low` | 触れる側の端について 16 分の 1 |
| イベント固有の値（規則 6） | レコードの `scale` | 常にまたは決して |

`raid_search.size_marks` は、選択したクリスタル、星の数、種族について、イベントのボスが取りうる印を示し、ファインダーはそれ以外を灰色にします。

### 欲しい報酬

「報酬」の節は、開くまで折りたたまれており、報酬を指定します。指定するのは、アイテムの行と、レイドがそのアイテムを与えるべき最少数です。レイドのアイテム数は合計され、同じアイテムの 2 行は加算されます。結果には、そのあと報酬が表示されます。折りたたんだ状態でも行は残り、検索はそれを無視します。提示されるアイテムと数量は、検索したレイドが与えられるものです（`raid_search.reward_choices`）。文脈が抽選するすべての遭遇（その段階、そのバージョンでの星の数、またはイベントの巣）について、選択した星の数、種族、テラタイプに絞り込み、固定行と、レイドが引く最大数までのアイテムの抽選結果（抽選に他に何もない場合は、引く数と同じ数）を含みます。ボスが取りうる各テラタイプについては、そのかけらの名前と、素材となる種族を示します。Paldea、Kitakami、Blueberry の文脈をすべて同時に指定すると、約 1 秒で 343 のアイテムが一覧に出るため、一覧はページ外で作られます。検索は、欲しいものを与えられない遭遇を飛ばし、そのあとボスより先にシードの報酬を抽選します。

最も欲しい報酬は、指定された報酬の順番で結果を並べます。最初のアイテムが多いほうが勝ち、同点なら 2 番目のアイテムが多いほうが勝ちます。各行の最少数は、依然として最低限として残ります。レイドのアイテムの合計は、検索したレイドが与えうる合計のうち、少ない順からの位置としての桁として扱われます（`raid_search.ranked_rewards`）。黒いクリスタルでは、素材が 8 から 30 まで 2 刻みで、12 段階です。先頭のアイテムの桁が一つのスコアになり、それが 2^31 未満に収まり、ヘルパーが 64 ビットのランクでシードの横に保持します。それ以降のアイテムは最少数だけを求めます。既知のすべてのレイドには 5 つのアイテムが収まります（イベントの Exp. Candy L は 59 の合計を持ち、どのアイテムよりも多い）。黒いクリスタルでは、4 つのハーブ、パッチまたはキャップと、4 つの素材を順位付けします。

### ヘルパーのスキャン

PKHeX ヘルパーは、すべてのコアでシードをスキャンします（`services/pkhex/RaidScan.cs`。`pokeldn.sv.raid_scan` が梱包して送り、独自のヘルパープロセスで動きます）。シードの遭遇、スケールまでのボス、スコア、すべてのフィルター、報酬を、文脈のテーブル上で `select`、`boss_fields`、`rewards`、`tera_type` が行います。文脈ごとの最良のシード（または種族ごとの最良）を挙げ、`search` はそれらのレイドを通常の Python コードで作るため、結果、その順序、シードと文脈の間の同点は Python のスキャンによるものです（`tests/test_sv_raid.py` が両者を比較します）。

スキャンは、遭遇のあと大半のシードを除外します。遭遇の各行の最良の順位は、リクエストごとに一度だけ計算されます。完璧な個体値は、落ちうるところではすべて 31 とし、そのほかの個体値は個体値フィルターが通す最良の値とし、性格は最良のものを選び、報酬で順位付けする場合は、その行が与える各アイテムの最大値を用います。その行が、これまでに保持した順位を超えられないシードはそこで止まります。通過したシードは、完璧な個体値のあと、および全個体値のあとに改めて確認されます。その際は、どの性格がそれらに与える最良の値とも比べます（性格は能力を 1/10 変えますし、どのスコアも各能力とともに増えます）。報酬で順位付けする場合、まず報酬を抽選します。抽選は、欲しいアイテムを与える抽選行だけを見ます。残った行では、最初のアイテムが保持された順位の先頭の桁に届かない時点で、抽選を止めます。各リクエストは、先行するリクエストが保持した順位を持ち（種族ごとの場合は種族ごとに 1 体のボス）、検索の最初のリクエストだけが文脈のテーブルを持ち、ヘルパーはそれをダイジェストで保持します。

1 回のリクエストは 16 777 216 のシードを持ち、ヘルパーが約 4 分の 1 秒でスキャンできる分だけ、最大 268 435 456 まで増えます。1 回の検索は、選んだ文脈の数だけ、各文脈で最大 4 294 967 296 のシードを対象にします（`most_seeds`）。ファインダーは 1 億を提示し、そして「すべてのシードを検索する」では、すべてを検索します。「最初の一致で止める」は、スコアに関係なく最初に一致したレイドで答えます。最良のものを挙げるのではありません（`stop_at_first`）。一致があった最初の文脈の最も早いシードが得られ、文脈は順番に検索されます。ヘルパーがない場合（ヘルパーをビルドしていないソースのチェックアウト）、Python は毎秒約 22 000 シードをスキャンし、100 万のシードと文脈の組まで扱い、ファインダーは 100 000 を提示します。

Apple M4（10 コア）で、ヘルパーが温まった状態で計測した結果です。

| 検索 | 時間 |
|---|---|
| 1 つの文脈の 10 000 000 シード（Scarlet、Paldea、6 つ星、標準） | 0.02 秒、色違いを求める場合は 0.03 秒 |
| 42 の文脈それぞれの 10 000 000 シード | 0.51 秒 |
| 42 の文脈それぞれの 100 000 000 シード（ファインダーの既定） | 5.2 秒 |
| 1 つの文脈のすべてのシード | 6.1 秒 |

## 本体どうしのバトル

4 つ星のクリスタルをホストする 1 台と、Poke Portal から参加する 1 台の、2 台のエミュレートした Scarlet 4.0.0 で計測し、空いた席には NPC のパートナーが 2 人いました。ホスト側の本体は、バトル全体を通じてセッションに残ります。バトルのメッセージはすべて、宛先 (0x2713, x, y) の、キー 0x007b のバトル開始フレームです。その 32 バイトのヘッダーには、+0x00 に種別、+0x08 に u64 のステップカウンター、+0x10 に u64 のラウンド、次に +0x18 と +0x19 に 5 と、バトラーまたはステーションのバイトがあります。

| 種別 | 送信元 | サイズ | 内容 |
|---|---|---|---|
| 0x01、0x05、0x11、0x15、0x25、0x29、0x47、0x49 | ホスト（アドレス (0x2713, 1, 2)） | 50 から 20626 | ステップ。各ゲストは同じカウンターの下で、種別 + 1 で応答する |
| 0x02、0x12、0x16、0x26、0x2a、0x48、0x4a | すべてのステーション（アドレス (0x2713, 3, 5) または (0x2713, 2, 2)） | 50 | ステップへの応答 |
| 0x06 | 自身のバトラーについてはステーション。ホストは自身のもの、各 NPC のもの、そして再度ゲストのものについて送る | 250 | 1 体のバトラーのコマンド。+0x19 はバトラーのスロット（0 はホスト、2 はゲスト、3 と 4 は NPC） |
| 0x15 | ホスト。行動するバトラーごとに 1 つ（ボスを含む） | 20626 | ラウンド。+0x20 に 5 つの 0x70 バイトの行動ブロック（スロット 0 はホスト、1 はボス、2 はゲスト、3 と 4 は NPC）、+0x250 にそのブロックの行動数をスロットごとに 1 バイトずつ（[行動](#actions)）、+0x258 にサーバーのコマンドキューの長さ、+0x25c からキュー。圧縮（deflate）後で 123 から 802 バイト |
| 0x46 | ホスト。開始時に 62 回 | 54 | |
| 0x51 | ホスト | 86 | |

約 4 分で、参加者の 2 方向は、0x80 ポート 0 で 475 件の信頼性のあるメッセージを運び、ワイヤー上で 27979 バイトでした。一方向では、1 秒に最大 80 件でした。NPC のコマンドと、種別 0x15 のレコードを送るのはホストだけです。

バトルはサーバーとクライアントに分かれます。ホストのビルダー `0x113c8a0`（種別 0x15 は `0x113c908`）は行動ブロックをコピーし、ラウンドを実行し（`0x113e3d0`）、それが生成したサーバーのコマンドキューを追加します。ホストの AI は NPC のコマンドを作り、ボスの行動はゲストには 0x15 の内側でしか届きません。ゲストはキューを再生し、種別 0x13、0x15、0x17、0x19、0x1f、0x23、0x25、0x4d では、同じビルダーでホストの行動ブロックから本体を組み立て直し、サイズとバイトを比較します（`0xf5cfa4`）。不一致は受信タイムアウトのハンドラー `0xf5bfd4` に進みます。バトルをホストするステーションは、同じ状態から Scarlet 自身のエンジンが作るのと同じキューを生成しなければなりません。

### どのステーションがサーバーを担うか

バトルサーバーは、ポート 2 のメンバー一覧の最初のエントリです。この一覧は、各本体がロビーのホストの Session type 6（メンバーは `+0xa0`、コードは `+0xc0`、人数は `+0xc4`、コンポーザー `0xe457cc`）と、type 9 の受信側 `0x18b68fc` から作ります。`pokeldn.sv.port2.build_session` は、ホストを先頭に置きます。

| 段階 | コード |
|---|---|
| レイド開始 `0.4455`（Lua）が、サーバーのスロットを 0 に設定する: `setup:f4891D27C(0)` | `0x182ca10` -> `0x2d36398`、setup `+0x94` |
| メンバー i について、i をスロット 0、2、3、4 に対応させ、メンバーのコードを `+0x99+slot` に格納し、自身のコードについては、そのスロットを `+0x90` に格納する | `0x1ccd15c` がポート 2 の `+0x170` にあるメンバーのベクターをたどる。`0x2d363a0`、`0x130ea2c` |
| `0x2a1cd74` が、バトル開始時に一度だけ、setup の `+0x94` を `net+0x58` に、`+0x90` を `net+0x5c` にコピーする | `0x18915c4` から |
| `!setup.710 && slot == net+0x58` のとき、本体がサーバーになる | net vf `+0x78` = `0x2a1d994`。config `+0x2c` は `0xfa363c` を通じ、サーバーの `+0x490` に保持 |
| 0x15 のチェッカーは、サーバーでない本体にのみ設置される | `0xfb0ee8` |
| 受信タイムアウトまたはチェックの失敗は、net vf `+0x70` = `0x2a1d920` を呼ぶ。レイドでは `net+0xca` を設定し、`0x18e217c` が `net+0x58` を本体自身のスロットに設定する（`net+0xf0`。`0x2a1cda8` で一度だけ書き込まれる） | `0xf5bfd4` |

setup の `+0x710` は、ビルダーのフィールド 22 が true のときに限り、Lua バインディング `f3AF42713` を通じて `0x7faed0` によってのみ設定されます。レイド開始がそれを設定することはありません。サーバーを名指しするメッセージはなく、メンバーの順序がそれを決めます。サーバーへのリンクを失った本体は、バトルの残りの間、自身をサーバーにします。各本体はそれを独立に行います。ロビーのホストが先頭に挙げたものが送信を止めると、各本体は独自のバトルを戦います。

メンバーのベクターは追記のみで、書き込み元は 3 つあり、すべて `0x18b65c8` -> `0x18b68fc` を通ります。type 6 または 7 のセッションブロック（`0x18b566c`、エントリ `(block+0x98 code, block+0x90 host station)`、最初に追記）、type 6 のメンバーの再生（`0x279ba2c`）、type 9（`0x1954bac`）です。どのブロックよりも前の type 9 は破棄されます（`0x18b65e4`）。すべての本体のエントリ 0 は、その最初のブロックが名指すホストです。2 台のエミュレートした Scarlet 4.0.0 で計測しました:

| ロビーのホストが送ったもの | 本体がしたこと |
|---|---|
| ブロックのホストが受信側の本体自身のステーションである type 6 | ポート 2 の参加を送らず、エラー 7 |
| ブロックのホストを名指しする、ロビーでのポート 2 の type 10（`0a b9 02 <slot> b9 01 <u64 station>`、パーサー `0x279bbdc`、消去 `0x194562c`） | セッションから離脱 |
| ブートストラップの後の同じ type 10 | 「The raid has been abandoned!」と表示 |
| 本体が 320173（読み込み完了）を報告した後の同じ type 10 | それぞれが、2 人の NPC パートナーと単独で戦った |
| 空のブートストラップの参加者を指すメンバーのコード | バトルの読み込みが中断された（2162-0001） |
| 5 人のメンバー。5 番目は（Lua によってスロット 0 に再マップされ、Lua はインデックス 1 から 3 のみを再マップする）本体 | ロビーはメンバーを一覧に出さなかった。開始とブートストラップの後、両方の本体がバトルのフレームより前に離脱した |

ブートストラップの参加者 k は、コード k のメンバーに属します。フェイルオーバーした本体は、他のすべてのバトラーを独自の AI で動かします。スロットごとのリーダーは、バトル開始時にサーバーだった本体についてのみ構築されます（`0xfa52b0`、`0xfa5314`）。その本体自身のコードは、自身のステーションを持つ最初のベクターのエントリのコードです（`0xd5f3b4`）。また、Lua のスロットループ（`0.4455` @1206..@1248）には break がないため、最後に一致したエントリが本体のスロットを設定します。

### バトルの乱数

ラウンドのすべての乱数は、0x28 バイトの xoroshiro128+ オブジェクト 1 つ（vtable `0x4500bd0`）から得られます。

| オフセット | サイズ | 内容 |
|---|---|---|
| 0x00 | 8 | vtable |
| 0x08 | 2 x u64 | 状態 |
| 0x18 | u64 | シード |
| 0x20 | u64 | 抽選を行った回数 |

サーバーのメインモジュール（0x378 バイト、コンストラクター `0x12742d0`）は、それを `+0x10` に保持します。ラウンドのコードは `[[x+0x10]+0x10]`（`0x11440e8`）として到達します。モジュールの初期化子 `0x127d824` は、状態をシードと `0x82A2B175229D6A5B` に設定し、回数を 0 にします（`0x127d9a8`）。シードは、そのパラメータブロックの `+0x20` から取ります。ゲストのチェッカーは、その語をバトル設定の `+0x718`（`0x2891748`）から埋めます。レイド開始 `0.4455`（@1152..@1157）は、Lua バインディング `fAF4A81E0`（セッター `0x7faf1c`）を通じて `+0x718` を RaidPoint の `randSeed` に設定します。パートナーのシードはバトルのシードでもあり、ブートストラップを書くステーションがそれを選びます。サーバーが構築するスロットごとのモジュール（`0x126ba88`、`0xfa9f90` から）は、シード 0 で初期化されます。

`randSeed` `D64EB3974D89705E` でホストされたレイドと戦うエミュレートした Scarlet 4.0.0 では、サーバーの乱数はそのシードを保持し、それに等しい状態が、後のラウンドで 7 ステップ進み、回数は 7 になりました。そのラウンドでは 4 回抽選されました。

抽選は `s0 + s1` を加えて状態を進めます。回数は、呼び出しごとに 1 増えます（引き直しごとではありません）。

| 関数 | 抽選 |
|---|---|
| `0x11440f0(rand, n)` | n 未満の u64。`s0 + s1` を n − 1 のビットでマスクし、n 以上の間は引き直す。n が 2 未満のときは 0 を返し、抽選は行わない |
| `0x114da8c(rand, p)` | `(s0 + s1) & 0x7f` を、100 以上の間は引き直す。p 未満のとき true |

多くのラウンド関数は、これらを呼ぶ代わりにステップをインラインで行います。

### わざごとのダメージと抽選

標準のレイドに対してランダムなポケモンで行ったオラクルバトルで計測しました（233 バトル。うち 29 は、すべての抽選を記録したもの）。わざの使用は、この順に抽選します。

| 抽選 | タイミング | 決めるもの |
|---|---|---|
| `chance(25)` | 使用者がまひしている | 完全まひ |
| `chance(accuracy)` | わざに命中率がある（100 の場合も抽選する） | 命中 |
| `below(24)`、`below(8)`、`below(2)` | 攻撃わざ。急所ランク 0、1、2 ごと | 0 のとき急所 |
| `below(16)` | 攻撃わざ | 乱数 r。ダメージに (100 − r) / 100 を掛ける |
| `chance(p)` | 確率 p の追加効果（Body Slam は 30） | その効果 |

ボスに対する怯みの追加効果は何も抽選しません（[ラウンドキューにおけるわざ](#a-move-in-the-round-queue)の節に規則があります）。能力を下げる発生率 100% の追加効果（Spirit Break、Bulldoze）は、あるラウンドでは `chance(0)` を抽選し、別のラウンドでは何も抽選しません。同速の 2 体のバトラーは、最初の行動の前に `below(2)` を抽選します。

バトルは、最初のラウンドの前に `below(100)` を一度抽選します。ダメージは Showdown の Gen 9 の計算式です（データは Pokemon Showdown の `moves.json` と `typechart` から）。パーティレコードの能力値を使い、ボスはテラタイプとしてのみ防御するものとします。能力ランクの変化の前にボスに命中した 1346 回のうち 921 回がこれに当てはまり、すべての抽選を記録した 140 回のうち 137 回では、記録された乱数と急所の抽選が記録どおりのダメージを与えました。当てはまらない命中は、ボスのシールド中に起こるもの（計算式の約 0.45 倍）か、それぞれ固有の規則を持つわざ（Body Press、Rising Voltage、連続攻撃わざ）によるもの、または残りの HP で上限がかかるものです。


ボスの HP 総量は、レコードの HP に RaidPoint の HP 係数を掛けて 100 で割ったものです（[バトルのブートストラップ](#the-battle-bootstrap)）。勝ったオラクルバトルのうち、1 つ星で 78、2 つ星で 84、3 つ星で 125、4 つ星で 35 が、`0x37 (2, 2, damage)` でレコードの HP のちょうど 5、5、8、12 倍の後に終わりました。それ以外は、シールドと固有の規則を持つわざによって、より少ないダメージで終わりました。

### ラウンドキューにおけるわざ

ラウンドのキューでは、バトラーのわざは 1 回分のコマンド列です。バトラーのクライアント上の位置は、バトラー 1、3、4、5 では 0 から 3、ボスでは 4 です。A は使用者、T は対象、M はわざ、`type` はわざのタイプ番号、`cat` は分類（1 は物理、2 は特殊）です。プレイヤーのわざがボスに命中し、ボスの反撃がプレイヤーに命中したオラクルのラウンドで計測しました:

| command | meaning |
|---|---|
| `0x05 (A, 0, pp)` | プレイヤーのわざが始まり、PP を消費する（相手が Pressure を持つ場合は 2、それ以外は 1）。ボスのわざには PP はない |
| `0x07 (A, 0)` | わざが使われる |
| `0xc9 (A, 0, M, T's position, 0)` | わざと対象 |
| `0x7b (M, n, A)` | n は、このラウンドより前のラウンド数 |
| 0 だけからなる `0xcf` のグループ 6 つ | 20、5、5、5、19、20 バイト |
| `0x7e (0, ...)`、`0x7e (1, 0, 0, 0, 0, 0)`、`0x7e (2, e, e, e, e, e)` | 1 つ目: T の位置 + 1 に 1。3 つ目: 位置ごとの相性コード。なしの場合は 7 |
| `0x8b (A's position, T's position, M, type, 0, 0, 1, tera, 0, 0)` | 命中。`tera` は、ボスがテラタイプの攻撃わざを使ったとき 1（そのような命中 448 件すべて）、それ以外は 0 |
| `0x37 (T, 2, damage)`、`0x37 (T, 5, 1)`、`0x02 (T, A, damage, 3)` | ダメージ |
| バイト `T, e` を持つ `0xd0` | e は相性。7 は等倍、6 はいまひとつ、8 はこうかばつぐん |
| `0x8e (1, 1, M)`。いまひとつのとき `0x8e (1, 3, M)` と `0xca (A, 575, 0xffff0000)`。こうかばつぐんのとき `0x8e (1, 2, M)` と `0xca (A, 574, 0xffff0000)` | 相性のメッセージ |
| `0x20 (A, 24)` | こうかばつぐんの命中のみ |
| `0x42 (T, A, A's position, type, cat, M, damage)` | 命中の記録 |
| 吸収わざで、使用者の HP が満タン未満のとき（吸収） | `0xa7 (T, 51)`、`0x03 (A, heal)`、`0x9a (A, heal)`、`0xcb (A, 290, T)`。回復量はダメージに吸収の割合を掛けたもので、四捨五入し、使用者に足りない HP が上限 |
| 追加効果（ある場合） | 例えばまひ: `0x13`、`0x90`、`0xa7`、`0xcb (2, 92, T)` |
| バイト `01 00` を持つ `0xd1`、`0x2e (2, A − 1)` | |
| `0x85 (7, damage)` | ボスへのダメージのみ |
| `0x7c ()`、`0x08 (A, 0)`、`0x1d (A, T's position, type, 1, 0, M, M)`、`0x5b (A, M)` を 2 回、`0x1e (A, 0)` | わざの終了 |

ラウンドは `0xb2 (0)` で終わります。動いた各バトラーについて `0x37 (b, 7, 1)`、続いて `0x75 (3, n)`、`0xc5 (1)`、素早さの順で各バトラーについて `0x43 (b)`（パーティレコードの素早さで、ボスを含む）、ラウンドの行動者について ID 順に `0x23 (b)`（バトルの最初のラウンドでは 5 体すべて）、最後に `0x2d (0)` です。`0x75 (3, n)` は、このラウンドを含め、これまでのラウンド数を数えます。

ボスを倒す命中はバトルに勝ちます。その `0x42` の後に、`0x49 (2, A, M)`、`0x09 (A, 0)`、`0x37 (2, 1, 1)`、`0xcb (2, 0, 2)`、`0x94 (2, 0)`、`0x37 (2, 8, 1)`、`0x5f (2)`、`0x62 (2)`、`0x6c (2)`、`0x5d (2)`、各プレイヤーについて ID 順に `0x41 (b, 2)`、8 を除く 0 から 13 までの k について `0x33 (2, k)`、`0x80 (2)`、`0x29 (2)`、`0x38 (A)` が続き、その後にわざの通常の終了が続きます。その後は誰も動かず、ラウンドは、生き残っているバトラーの `0x43`、`0x23` の一覧、`0x2d (0)` だけで終わります。`0x85 (7, damage)` とダメージのコマンドは、ボスに残っていた HP を持ちます。

プレフィックスは `0xb5 (0)` で始まり、ラウンドの行動者について ID 順に一度、動く順番で一度、`0x51 (b, 1)` を実行します。2 回目の実行では、Stall（特性 100）を持つバトラーが最後に動き、`0x51 (b, 0)` を伴います。選んだわざが独自のハンドラーを登録するバトラーは、各実行の後に、その実行の順で `0x5a (b, M, speed)` と `0x5b (b, M)` を加え、さらにわざの順で 2 回加えます。最初に動いたバトラーの後に動く各バトラーの前に、そのようなバトラーは全員そのペアをもう一度繰り返します。ハンドラーを登録するわざで動く行動者は、その `0x05` の直前に `0x5a (b, M, 0x72000 + speed)` を加えます。どのわざがハンドラーを登録するかは、オラクルバトルで各わざを使い、`0x5a` を観察して計測しました。見られたわざ 631 件のうち 347 件がハンドラーを登録しました（Facade と Body Slam を含み、Night Slash は含まない）。

ボスは最初からテラスタルしています。テラタイプの攻撃わざで、基礎威力 60 未満、優先度がなく、1 回だけ命中するものは、60 として命中します。これは Gen 9 のテラルールです（Smoliv のテラノーマルのたいあたりは、基礎威力 40 では 2 となるところ、4 のダメージを与えました）。わざの追加効果はそれぞれ、Showdown の順で `chance(n)` を抽選します。ただし、ボスに対する怯みは例外で、何も抽選しません。プレイヤーの Ice Fang がボスに命中すると、凍りの確率だけを抽選します（凍りは `0x13 (2, 3, 0, 1, 4)` とメッセージ 97 と 98 で表示され、ボスは行動の前に、解凍のために `chance(20)` を抽選します）。ボスの Ice Fang がプレイヤーに命中すると、両方を抽選します。ボスを倒す命中は、追加効果の有無にかかわらず、まず `chance(0)` を抽選します。

この方法で、Showdown のわざデータと Gen 9 のダメージ計算式から組み立てたところ、554 件のオラクルバトルのうち 56 件の最初のラウンドがオラクルとバイト単位で一致し、異なるものはありませんでした。残りは、拒否された何かを含んでいます。開始の本体からボスを倒すところまで連鎖させると、20 の完全なバトルがすべてのラウンドでオラクルと一致しました。同じスクリプト化されたコンソールに対して端から端まで提供すると、この方法で組み立てたサーバーは、オラクルサーバーが送ったすべてのフレームを、同じ順番で、同じフレームに本体へ送りました。両方が提供した 19 のバトルで一致し、20 件目はオラクルサーバーが失敗しました。
バトラーが行動するか命中を受けるときに、Showdown のコールバックがラウンドを変えうる特性または持ち物を持つ場合、そのラウンドは拒否されます（Hustle の攻撃、Rivalry の威力、Friend Guard の 0.75、Dark の命中後に素早さが上がる Rattled、Gale Wings の優先度）。ただし、コーパスでその特性または持ち物が働かないと計測された場合は除きます。また、バトルが交代時に作用する特性を持つ場合も拒否されます（Intimidate は、最初のラウンドの前に攻撃者の攻撃を下げます）。

### アクション

ラウンドのアクションヘッダー（リクエストブロック、0x238 バイト）は、クライアントスロットごとに 1 つの 0x70 バイトのブロック 5 つで構成されます。各ブロックには、16 バイトのアクションを最大 7 つまで入れられます（u64 のアクションワード、u32 の行動者バトラー ID、コードが書き込まない 4 バイト）。+0x230 には、スロットごとに 1 バイトで、そのブロック内のアクション数を数えます。サーバーはそれらをスロット順に、0x8c バイトのアクションエントリへ復号します（`0x1145e40`、デコーダー `0x11461b4`）。アクションワードの下位 4 ビットが種別です。

| 種別 | エントリ種別 | ワードのフィールド |
|---|---|---|
| 1 | 1（わざ） | ビット 4..7 は対象のバトル位置、8..23 はわざ、ビット 25 はフラグ |
| 2 | 2 | ビット 4..19 と 20..27。次の u32 |
| 3 | 3（交代） | ビット 4..7 はパーティのインデックス（行動者はそのパーティのポケモン）、8..11、ビット 12 |
| 4 | 6 | ビット 4..11、12..15、16..23 |
| 5 | 4 | ビット 4 |
| 6 | 5 | ビット 4..11 |
| 7、10、11 | 7、8、9 | なし |
| 9 | 10 | ビット 4..11 |
| 12 | 11 | ビット 4..11。次の u32 |
| 13 | 14 | ビット 4..7、8..11、12..15、16..27、32..43、44..55、56..59、60..63 |

ビット 0..3 が 3 で、ビット 12 が立っているワードはスキップされ、種別 0、8、14、15 も同様にスキップされます。記録されたプレイヤーのアクション `41 67 03 00 ...` は、対象位置 4、わざ 871（Torch Song）のわざ（種別 1）です。

レイドにおけるバトラー ID は、1 がスロット 0 のポケモン、2 がボス、3 がスロット 2、4 がスロット 3、5 がスロット 4 です。ステーションの type 0x06 のコマンドは 0xe8 バイトです。0x20 バイトのヘッダー（+0x19 がスロット）、+0x20 のカウントバイト、その後に +0x28 から（u64 のワード、u64 の行動者）のペアが続きます。そのスロット自身のアクションと、そのスロットに対するボスの反撃を運びます。スロット 2 のゲストのコマンドは、`move 871 at position 4 by battler 3` と `move 204 at position 1 by battler 2` を持っていました。ステーションは、自身のポケモンに対するボスのわざを選びます。

サーバーは、行動するスロットごとに、1 ラウンドのリクエストブロックを埋めます。

| 段階 | コード |
|---|---|
| 投稿者のスタック上の 0x240 バイトのブロック。すべてのアクションのワードと行動者をゼロにし、カウントをゼロにし、種別（0x15）を +0x238 に置く | スロットごとのリーダーの段階 `0xf6df44` 内の `0xf6e6a8`。他の種別は `0xf71d10` |
| スロットの type 6 のメッセージ（リーダーの +0x30 が格納先、u32 の +0x38 がスロット）をコピーする。カウントバイトをクリアし、各ペアの u64 ワードと行動者の下位 u32 を追加し、カウントを増やす。上限はなく、7 を超えるカウントは次のスロットにあふれる | `0xf702ec` -> `0xf7065c`（キー 6、0xe8 バイトのメッセージ）。キー 0x10 は `0xf72038` へ（1 アクションの 0x30 バイトのメッセージ。スロットが最大 6 を保持している間に取る） |
| 0x240 バイトを、型ハッシュ `0xae1b39fccfd09053` のジョブとして投稿する | `0xf6ffb8`。ジョブクラスの vtable `0x4494198`（コンストラクター `0x17b52a4` が 0x240 バイトをジョブの +0x78 にコピーする） |
| ジョブは、そのブロックをサーバーオブジェクトの +0x210（ビルダーの [o+0x40]）にコピーする | `0x16e4f84` -> `0x113bac0` |
| ステップカウンター +0x198 を増やす。そのステップについて既に受信したボディ（[[server+0x448]+0x38] のデックに対する `0xe63734`）があれば、それがビルドを置き換える。なければ種別 0x15 でビルダーが作る | `0x113bad8` -> `0x113c8a0` |

したがって、ラウンドのブロックは 1 つのスロットのアクションを保持します。各アクションの 4 つの未書き込みバイトと、バイト 0x235..0x237 は、投稿者のスタックから来て、種別 0x15 のボディにそのまま届きます。ラウンドはそれらのどれも読みません。2 台のエミュレートした Scarlet 4.0.0 の間の各 type 0x15 のレコードは、それらのバイトを除けば、行動するスロットの type 6 のコマンドから作られたブロックと同じです（コマンドが通信に乗っていた 10 件のレコードすべてで一致。ボス自身のスロット 1 のブロックにはコマンドがありません: [ボスの行動](#the-bosss-actions)）。4 つのエミュレートしたセッションのラウンドを、その行動だけから実行すると、それらのバイトを除いて、本体の 20576 バイトのボディが得られました。

### サーバーのコマンドキュー

type 0x15 のレコードのキュー（ボディの +0x23c、長さは +0x238）は、コマンドの連なりです。コマンドは、ビッグエンディアンの u16 の ID と、その ID の形式によってビッグエンディアンのビット列にパックされた引数からなり、先頭でバイト単位に揃えられます（ライター `0x119bf58`、ジャンプテーブル `0x3c6aa7c`）。ID から形式へのマップは、`0x3c6abe4` にある (u16 ID, u8 形式, u8 0) の 208 行から作られ、同じ ID については後の行が優先されます。ID は 0 から 205 までです。ID 0xce から 0xd4 は、リーダー `0xe515f0` 自身が読みます（ジャンプテーブル `0x3c6a90c`）。

| ID | 本体 |
|---|---|
| 0xce | なし。キューの終わり |
| 0xcf, 0xd2 | グループ。u8 のバイト数、その後にその数のバイト |
| 0xd0 | u8 の数（最大 4）、その後にその数のバイト |
| 0xd1 | 2 バイト |
| 0xd3 | 1 バイト |
| 0xd4 | なし |

形式バイトと、その引数の幅（ビット）:

|---|---|---|---|
| 0x00 | なし | 0x57 | 32, 8, 8, 8, 8, 8, 8 |
| 0x01 | 8 | 0x62 | 32, 16 |
| 0x02 | 8, 8 | 0x63 | 8, 8, 32 |
| 0x04 | 5, 3, 8, 16 | 0x65 | 32, 16, 16, 16, 16 |
| 0x10, 0x20 | 32, 16、その後 32 を 8 個 | 0x66 | 8、その後 32 を 5 個 |
| 0x11 | 16 | 0x67 | 32、その後 16 を 6 個 |
| 0x12 | 8, 16 | 0x72 | 32, 32 |
| 0x14 | 5, 3, 5, 3 | 0x75 | 32, 8, 32, 32, 32 |
| 0x17 | 16 を 7 個 | 0x83 | 32, 32, 32 |
| 0x1a | 16 を 10 個 | 0x84 | 8, 32, 32, 32 |
| 0x21 | 32 | 0x85 | 8, 8, 32, 32, 32 |
| 0x22 | 8, 32 | 0x86 | 8 を 6 個 |
| 0x23 | 5, 5, 5、1 ビットのパディングの後 | 0x93 | 32, 8, 8 |
| 0x28 | 32 を 8 個 | 0x96 | 32 を 6 個 |
| 0x29 | 32、その後 8 を 8 個 | 0xa3 | 32, 8, 16 |

すべてのキューは、コマンド 0xb5 で始まります。スロット 2 が Hex（わざ 506）をボスに使ったラウンドでは、`0x5a (3, 506, 212)`、`0x5b (3, 506)`、`0xc9 (3, 0, 506, 4, 0)` を運びました。エミュレートした Scarlet 4.0.0 のサーバーから記録したすべてのキュー、および 2 台のエミュレートした本体の間の type 0x15 のレコードは、計 20 件で、最後のバイトまで復号でき、同じバイト列に再エンコードできます。
これまでに見られた 0xcf のグループは、すべてゼロで埋められています。

### バトル開始時のボディ

メッセージ 0x11 のボディは、長さのワードを持たないコマンドキューです（[サーバーのコマンドキュー](#the-server-command-queue)）。バトラー ID は、スロット 0 が 1、ボス（スロット 1）が 2、スロット 2 が 3、スロット 3 と 4 が 4 と 5 です。バトラーはそれぞれ位置 ID − 1 にいます。ボディは、各バトラーを ID 順に繰り出し、その後に交代時のイベントを実行し、最後に `0x2b (0)` で終わります。

| コマンド | 内容 |
|---|---|
| `0x3d (pos)`、`0x16 (pos, 0, 0, 0)`、`0x5e (id, ability)`、`0x61 (id)`、`0x6b (id)`、`0x4e (id)` | 1 体のバトラーの繰り出し。`ability` はその特性 ID |
| `0x25 (id)`、`0xc7 (id, 0)`、効果、`0xc8 (id)` | 特性の発動 |
| `0xcb (id, text, params..., 0xffff0000)`。引数を 10 個になるまでゼロで埋める | バトルのメッセージ |

| 交代時のイベント | 効果 |
|---|---|
| Pressure (46) | `0xcb (id, 162, id)` を囲む発動 |
| Intimidate (22) | 対象ごとに、`0x0d (target, 1, 1)`、`0x93 (target, 1, 1, 0)`、`0xcb (id, 32, target, 1)` を囲む発動 |
| Frisk (119) | 持ち物を持つ相手ごとに、`0xcb (0, 146, id, target, item)` を囲む発動 |
| Unnerve (127) | 他のすべてのイベントより前に、`0x25 (id)`、`0xc7 (id, 127)`、`0xca (id, 679, side, 0xffff0000)`、`0xc8 (id)`。`side` は、プレイヤーの Unnerve が 1、ボスの Unnerve が 0 |
| Anticipation (107) | 相手が、そのポケモンにこうかばつぐんの攻撃わざ、または一撃必殺わざを知っているとき、`0xcb (id, 145, id)` を囲む発動 |
| Air Balloon (541) を持つ | バトラーの特性の後に `0xcb (id, 137, id)` |

233 件のオラクルバトルのうち 224 件では、イベントはバトラーの素早さの順（パーティレコードの素早さ）で実行されました。残りの 9 件は、先に動く Unnerve（127）が関わるか、素早さの同点によるものでした。同じバトルで、161 の特性は交代時のイベントを生みませんでした。また、持ち物のうち Leftovers（234）、Life Orb（247）、270、Focus Sash（275）は、いずれもイベントを生みませんでした。

Intimidate は、`0x25 (I)` と `0xc7 (I, 0)` で始まり、ID 順に各相手について（ボスには 4 人のプレイヤー、プレイヤーにはボス）`0x0d (F, 1, 1)`、`0x93 (F, 1, 1, 0)`、`0xcb (I, 32, F, 1, 0xffff0000)` を実行し、`0xc8 (I)` で閉じます。マイペースを持つ相手は、その内側で独自の `0x25`/`0xc7`、`0xcb (F, 69, F, 0xffff0000)`、`0xc8` で応答し、何も失いません。Defiant を持つ相手は、下がった後に `0x0c (F, 1, 2)`、`0x92 (F, 1, 2, 0)`、`0xcb (F, 18, F, 0xffff0000)` で応答します。Frisk は、持ち物を持つ最初の相手を `0xcb (0, 146, I, F, item, 0xffff0000)` で指定し、以降の相手は `0xca (0, 752, F, item, 0xffff0000)` で指定します。相手に持ち物がなければ、イベントはありません。Defiant、Hyper Cutter、Klutz、Light Metal、Moxie、Poison Touch、Wind Power には開始時のイベントがありません。この方法で組み立てると、554 件のオラクルの開始ボディのうち 420 件が一致し、異なるものはありません。

### サーバーのメッセージ

サーバーが送るすべてのメッセージは、`0x113bad8(server, kind, destination)` の 1 ステップです。

| 段階 | コード |
|---|---|
| ステップカウンター `server+0x198` を増やす | |
| そのステップについて既に受信したボディ（[[server+0x448]+0x38]、`0xe63734`）は再利用される。なければ、その種別とラウンドカウンター `server+0x488` でビルダーが動く | `0x113c8a0` |
| 32 バイトのヘッダー: u32 の種別、+0x08 の u64 のステップ、+0x10 の u64 のラウンド、+0x18 の宛先（全ステーションで 5）、+0x19 に 5 | スタック上のバイト +0x04..+0x07 と +0x1a..+0x1f は一度も書き込まれない |
| メッセージオブジェクト: サーバーのアロケーター `[server+8]` からの 0x50 バイト、vtable `0x44ed338`、+0x40 にヘッダーとボディのバッファ、+0x48 に u32 の長さ | `0x1227714`、デストラクター `0x28015b4` |
| `server+0x490` が設定されているとき、宛先スロットごとのリンクに載せる（宛先 5 はスロット 0 から 4 と 0xff）。リンクはスロット別に `server+0x1a0` のマップにあり、各リンクの送信 deque は `[link+0x48]` にある | `0x113cd5c`、`0x113e17c`、`0x113d33c`、`0x113d4a0` |
| サーバーのログ `[server+0x50]` と、着席している各宛先スロットの送信済みエントリに載せる（ログまたはエントリに既にそのステップがある場合を除く） | `0x113c718`、`0x113c4cc` |
| {u8 `[[server+0x448]+0xc4a5]`、u64 のステップ、u8 `+0xc4a4`} を x8 に書き込む: ラウンドの結果 | |

メッセージの deque は libc++ の `deque<message*>` です。マップは +0x40、start は +0x80、size は +0x88、ブロックごとに 0x200 個のポインタです（`0x113d5e0`、`0x113d810`、消去 `0x131be1c`）。サーバーは、スロットごとに 2 つのエントリを持ちます。スロットに送ったもの（マップは `server+0xc8`、`0xf6f324`）と、スロットから送られてきたもの（マップは `server+0x130`、`0xe634c8`）です。`0xf6f0a8` はヘッダーの種別でメッセージを探し、`0xf6fd7c` はそれを消去し、`0xe63380` はスロットが特定のステップのメッセージを送ったかを問い合わせます。リンクのメッセージは、宛先 (0x2713, 1, slot) のバトル開始フレームとしてワイヤーに届きます。u16 のキー 0x7b、u32 の setup `+0x2c`、u32 の 1、u32 のスロット、u32 の長さ、そしてメッセージです。リンクをネットワークへ排出するコードは、まだ特定できていません。

### ボスの行動

レイドのボスの追加行動は、+0x10 にある RaidPoint の行動プロファイルのコピーの後に、4 つのリスト（+0x5c + 8i の u8 種別、+0x60 + 8i の u32 の値、カウント +0x7c）で待機しています。ラウンドエンジンのリストは `[module+0x1b0]`（`0x16e5c90`）で、ラウンドごとにリセットされます。サーバーのフレームごとのマシンは、独自のリストを保持します。

| 種別 | 追加するもの | 値 |
|---|---|---|
| 1 | シールド（`0xf6f87c`）。開始前に、時間がプロファイルの +0x14 パーセント以下、または HP が +0x12 以下のとき | 時間による場合はタイマーの `0xf70af0`、HP による場合は 0 |
| 2 | シールドの終了（`0xf6f87c`、+0x18 に対して `0xf70010`） | 1 |

これらのどれも乱数を抽選しません。すべての発動は、ボスの HP の割合か残り時間（バトルタイマーの `0xf91070`）のしきい値です。リクエストブロックのアクション（`0x114fb2c`）としては、ワードの種別は 12、ビット 4..11 はリストの種別、ビット 32..47 はその値、行動者はレイドバトラーの ID です（`0x114fc70`）。

ラウンド中は、空のリストが HP の発動で埋められます（`0x11425b0`）。その中にシールドがなければ、そのラウンドでアクションが実行されます（`0x1145be0`）。ラウンドの後、結果のバイト `0xc4a5` が次のステップを選びます。ServerCommand（`0x16e4f6c`）は、ビルダーの `0xc4a4` が設定されているとき代わりに 8 を渡し、レイドのアクションはそのバイトをそのまま渡します（`0x16e4ff0`、ジャンプテーブル `0x3c61c38`）。0 はなし、4 は空のラウンド（`0x16e5cac`）、6 はシールドを持つときのラウンドのリスト（`0x16e5ad0`）、7 はバトルの終了（[バトルの終了](#the-battles-end)）です。レイドのアクション（`0x18c92a8`、ペイロードは `0x17b5f3c` がコピー）は、4 つの状態で実行されます。

| 状態 | サーバーの動作 |
|---|---|
| 0 | すべてのステーションにメッセージ 0x47 を送る。理由 0 でバトルタイマーを一時停止する（`0x18c9a68`） |
| 1 | 着席しているすべてのスロットがそのステップのメッセージを送るまで待つ（`0xe63380`） |
| 2 | スロット 1 がアクションを保持するリクエストブロック（カウントバイト +0x231）。理由 0 でバトルタイマーを再開する（`0xe63ac4`）。そのブロックをラウンド（0x15）として送る |

シールドのないリストは、状態 2 から始まります。フレームごとのマシンは、ボスのリストが空の間、プロファイルの時間の発動を、リストのコピーについて確認します（`0xf6d62c`）。そのどれかが発動すると、コピーをメッセージ 0x51 として送ります（`0xf71b74`）。0x51 は、サーバー自身のスロットを通じてマシンに戻り、そのリストを埋めます（[サーバーの流れ](#the-servers-flow)）。アクションを保持するマシンのリストは、レイドのアクションを投稿します（`0xf6d8d4`）。

2 台のエミュレートした Scarlet 4.0.0 の間で、次のプロファイルを持つ 4 つ星のボスは、スロット 1 のラウンドを 3 回もたらしました（種別 3 の Sunny Day は時間 80 パーセント、種別 1 は HP 75 パーセント、種別 2 は HP 40 パーセント、シールドは HP 50 パーセントまたは時間 30 パーセント）。1 回目は、種別 4、値 0 だけで（0x47 はなく、0x51 が伴う）。次に、ゲストの攻撃の後に 0x47 と、種別 4、値 2 を伴う種別 1。そして再び 0x47 と種別 1 です。75 パーセントの行動は、それを越えたスロット 0 のラウンドの内側で実行されました。

| イベント | コード |

### バトルのタイマーが切れる

フレームごとの実行の先頭で、フレームごとのマシン（`0xf6d538`）は、制限時間 N+0x8a と [[module+0x1b0]+8] の i16（`0xf91070`）でバトルタイマーを読みます。符号付きの値として 0 以下の結果は、ボスのリストとリーダーより前に、タイムアップの分岐 `0xf6d830` を取ります。

| 段階 | コード |
|---|---|
| 結果 0 と N+0x94 = 2 を N に保持する。既に結果がある場合を除く（強制しない） | `0xe7d570(N, 0, 2, 0)` |
| server+0x208 の 0x29 ボディ: N 自身のスロット、結果（`0x166882c`）、N+0x94 | `0xe7d4c8` |

| それ以外: 種別 0 を投稿した AddExpBattleEnd | `0x16e5230`（ハッシュ `0x23607a0597b3a656`） |

マシンは、どのジョブも実行されていないときにのみ動くため、ラウンドやレイドのアクションの間に切れたタイマーは、そのジョブが終わった後に見られます。ExitBattleEnd は、0x2b をすべてのステーションに送り、すべての応答を待ちます。0x2b は 0x29 ではないため、RaidCapture は続かず、フェードアウトが 0x35 を送り、その後 0x37 を送ります（[バトルの終了](#the-battles-end)）。レイドはタイムアップで 0x25 を送りません。

rme10 のセッション（下記）で、記録されたメッセージは 416.5 秒までとし、その後のステーションは、5 と 0x37 を除く奇数のメッセージに 0.1 秒後に応答し、コマンドは送らない状態で、時計を 10 秒刻みで 700 秒まで進めました。unicorn の下のゲーム自身のサーバーコードと `Server` は、すべてのスロットに同じメッセージを同じ順番で、書き込まれないバイトを除いてバイト単位で一致するように送りました。それらは、ボスの最後の時間制アクションのラウンド（種別 3、残り時間の 10 パーセント）、続いてボディ `00 00 00 00 02 00`（スロット 0、結果 0、2 で決定）を伴う 0x2b、0x35、0x37 です。

ボスが勝つレイドも同じ方法で終わります。同じセッションで、414.5 秒から、ステーションが各リクエストに対して、自分のポケモンがボスに Growl（わざ 45）を使うコマンドで応答し、ボスがそのポケモンにわざ 0x1cc で応答する状態で、ゲームのサーバーコードと `Server` は、すべてのスロットに同じ 1311 件のメッセージを同じ順番で送りました。倒れたプレイヤーのポケモンは、タイマーの 300 秒のうち 75 秒を減らし（[[module+0x1b0]+8] の i16 は、439.7 秒で -75、-150、そして -225 に下がった）、-225 のとき、タイムアップの分岐は 0x2b（スロット 0、結果 0、2 で決定）、0x35、0x37 を送りました。倒れたポケモンのスロットは、リーダーの下位状態を経由します（[サーバーの流れ](#the-servers-flow)）:

| メッセージ | 宛先 | 内容 |
|---|---|---|
| 0x21 | 倒れたスロットのみ。ヘッダーだけ | スロットに戦えるメンバーがいなくなったときに送る。その応答 0x22 がリーダーのタイマーを開始する（reader+0x50、制限は `0x1ffe4e8` から） |

1 回の復活ラウンドでは、`3 (5, 277)`、`cb`、`3d (4)`、`16 (4, 0, 0, 113)`、`5e`、`61`、`6b`、`4e`、`98 (4, 0, 0, 1)`、`20 (5, 0x12)`、`25`、`c7`、`cb`、`c8` がキューに入りました。テストは、このバトルについても、`Server` をゲームのメッセージと照合します。

### サーバーの流れ

本体では、各段階はジョブとして実行されます。最初は Wild::Setup、次に ServerRequest（`0x138d178`、1 つのスロットにメッセージ 5 を送る）、ServerCommand（`0x16e4f10`、投稿されたリクエストブロックをラウンドとして実行し、その結果の次の段階を続ける）、RaidAction、そしてバトルの終了です。Wild::Setup（`0x2a1f54c`、11 の状態、ジャンプテーブル `0x3c61c1e`）は、メッセージ 1 を送り、すべてのスロットの応答を待ち、0x11 を送ります（セットアップ種別 4 は代わりに `0x2017ba4` を使います。レイドのセットアップの +0x30 は種別 0 で、捕獲の 0x29 が示すとおり、勝利時に 0x29 を送る種別です）。そのうえで、すべての応答を待ち、着席している各スロットが送ったものを消去し（`0xe0f5f8`）、0x11 の結果のバイトが 1 のとき、メッセージ 3 を送ります（その後、応答の後に 0x13 を送ります。そのバイトは開始フラグ [[o+0x40]+0x28] で、それを 1 にするのは `0x2840fac` だけです。これは `0x2840f70` 経由で 7 か所（`0x284b710`、`0x284b8f0`、`0x285c5d0`、`0x286d480`、`0x286d784`、`0x286d9b0`、`0x28780f8`）から呼ばれ、計測したレイドの開始では、それを設定したものはありませんでした）。次に、着席している各スロットの 3 と 4 を消去し、バトルタイマーを開始します。フレームごとのマシン（`0xf6d538`）は、5 つのスロットごとのリーダー（`0xf6df44`）とボスのリストを進めます。サーバー側にあるプレイヤーのスロットのリーダーは次のとおりです:

| リーダーの状態 | 条件 | その後 |
|---|---|---|
| 0 | スロットの送信済みエントリに、5、0xd、0xb、0xf、9、7、0x21、3、0x23、0x15、0x17、0x19、0x13、0x47、0x1f、0x1d のどれも含まれない | そのスロットへの ServerRequest（`0xf70078`）、状態 1 |
| 0 | それ以外 | 応答済みのペアを両方のエントリから消去する（`0xf6edf4`。0x15/0x16、0x23/0x24、0x11/0x12、0x13/0x14、0x17/0x18、0x19/0x1a、0x1b/0x1c、0x1d/0x1e、0x25/0x26、0x1f/0x20） |

スロットが属する側は、表 `0x3c6a45a`（0, 1, 0, 0, 0）を N+0x95 と照らして決まります。そのリーダーは、応答されたペアを消去するだけです。リーダー（`0xf6df44`..`0xf6edf0`）は、表より多くの経路を持ちます。4 を送ったスロットは、種別 0x13 のブロックで応答されます。レイドでは N の側において、リーダーの reader+9 で下位状態が動きます。0 は、ハッシュ `0x935acb1823e1803f` の 8 バイトのリクエストを通じて、スロットに {slot, 0x21} を尋ねます（`0xf6f6d8`）。3 は、制限 `0x1ffe4e8` を表 `0x3c69d1c` から読んで、reader+0x50 にタイマーを作ります。1 は、そのタイマーが切れると種別 0x23 のブロックを投稿します（`0x2016bc8`）。2 は 0x23/0x24 を待ちます。0xd/0xe は、種別 0x1b のブロックを投稿するか、0xe のボディの最初のバイトが 0 のときはリクエスト {slot, 7} を投稿します。7/8、0xb/0xc、0xf/0x10、そして受信した 0xa は、種別 0x17、0x19、0x15、0x17 のブロックを投稿します。投稿されたブロックのバイト +0x23c..+0x23f は、種別の後にあり、スタックです。

フレームごとに、レイドの実行ステップ `0x2d383b8(N)` が `0x2d38694` で進み、サーバーの受信リンク（[N+0xb0] 上の `0xe0f040`、`0xe0fd68`、`0xe0f854`）を進めた後、ジョブグラフ `0xfc363c(G, 1)` を進めます。G = [N+0xa8] です（0xe8 バイト、vtable `0x44ee6e8`。その +0x40 はジョブのコンテキストで、vtable `0x44ee808`）:

| G+ | オブジェクト | |
|---|---|---|
| 0x98 | リクエストのファクトリー（0x48 バイト） | 投稿されたリクエストは 0x50 バイトのメッセージオブジェクトで、ジョブの型ハッシュ、カウンター、ジョブのペイロードを持つ |
| 0xa0 | スケジューラー（0x78 バイト、vtable `0x44eea68`） | 投稿されたリクエストは、+0x40..+0x50 のベクターにあり、`0x1479b10` が追記する |
| 0xa8 | 源（vtable `0x44947d8`） | vf 0x68 の `0x14641ec` が開始するリクエストを選ぶ |
| 0xb0 | フレームごとのマシン（vtable `0x4493530`、`0x17e1c5c` が作成） | vf 0x68 の `0xf6d538`。+0x40 はコンテキスト、+0x48 はファクトリー、+0x50 はスケジューラー |

`0xfc363c(G, 1)` は、ジョブを保持している間、実行器だけを実行します。実行器が空のときは、マシンを実行し、その後に源の選択を実行します。レイドでは（セットアップ +0x498 のビット 0x400）、ハッシュ `0x5c307d44ea569b63` を持つ最初の投稿済みリクエスト（レイドのアクション、`0xf71928`）が選ばれます。モジュールの開始フラグ（[[module+0x1f0]+8]）より前では、ハッシュ `0x2e9e7a3009002c36` の最初のもの（Wild::Setup、`0xf7093c`）が選ばれ、それ以外は最初に投稿されたものが選ばれます。選択によりスケジューラー（`0xfc3f58`）から外れ、実行器の vf 0x68（`0x17b410c`）がそのハッシュの名前のジョブを作って積み、実行器が動きます。実行器（`0xfc38dc`）は、一番上のジョブの vf 0x68 を実行します。0 はフレームを終え、2 はジョブを取り出して、継続 [job+0x70] があればそれを積み、フレームを終えます。それ以外の値では、一番上のジョブを再び実行します。したがって、マシンとそのリーダーは、ジョブのないフレームでのみ動き、フレームごとに 1 つの投稿済みリクエストが開始します。また、レイドのアクションが他のリクエストの後に投稿された場合は、それらより前に開始します。これにより、レイドのアクションの後にラウンドとして送られる 3 つのコマンドという、捕獲の順序が得られます。

マシンのタイムドチェックは、ボスのリストのコピーを、メッセージ 0x51（`0xf71b74`）として、サーバー自身のスロットの受信リンク（`0xe0f440(server, N+0x95)`、`0xf71980`）に送ります。次のフレームで、受信リンクの段階がそれをマシンの vf 0x78 `0x2016290` に渡します。これは 0x24 バイトをマシンのボスのリスト [+0xf8]+0x5c にコピーし、マシンはそこからレイドのアクションを投稿します。マシンの vf 0x70 `0x20162bc` は、他の 2 つのメッセージを受け取ります。これらは +0x40 の u64 で区別されます。`0x0ab4bce035f3012b`（0x2588 バイトのペイロード。`0x201665c` のジョブとして投稿される）と、`0xde3856ecc4fe200c`（種別 14 のアクション 1 つのリクエストブロック。ServerCommand として投稿される）です。

エンジンが組み立てたセッション上で unicorn の下で動く Scarlet 自身のサーバーコード（`scratchpad/battle/timeup/gameserve.py`。毎秒 30 フレームで `0x2d383b8` を毎フレーム、ステーションのメッセージは中継された順序で、その捕獲時刻に）は、本体の 24 フレームを、ヘッダーとリクエストブロックの書き込まれないバイトを除いて、それぞれバイト単位で、ゲストに送ります。受信リンクの段階がない場合、0x51 のコピーはボスのリストに届かず、80 パーセントの行動は決して発動しません。

`Server` は、組み立てたセッション上でこのフローを Python に移植したもので、サーバーの部分をフレームごとに、実行ステップ（`0xe0f040`、`0xe0fd68`、`0xe0f854`、`0xfc363c(G, 1)`、そしてそのステップが動いたときは `0x2898350`）として実行します。これは毎秒 30 フレームで、受け取った各メッセージの時刻までマシンの時計に従い、各メッセージの後は 1 フレーム期間です。アイドルとしてスキップできるフレームはありません。倒れたスロットのタイマーを待つリーダーは、マシンを毎フレーム 1 つのわざとして報告させ、そのたびにサーバー自身のリンクにメッセージ 0x46 を積むためです。unicorn の下では、移植された 216 個の関数すべてについて、ゲーム自身のコードは、記録されたバトル、タイマーが切れた後、勝利による終了、そしてボスが勝つバトル（下記）のイベントの後に、移植版と同じページを残します。

ホストは、サーバーが受け取る各メッセージを、ローカルのクライアントのものもゲストのものも含めて、1 つのキューを通じてゲストに中継します（アドレス x 3、0.05 から 0.15 秒ごとに 1 フレーム、ゲスト自身のメッセージを含む）。そのため、キューの順序は、サーバーがそれらを読んだ順序になります。ゲストの応答が、ローカルのクライアントより 0.5 秒前に送られていても、サーバーにはその後に届きえます。キャプチャ内のエミュレートしたホスト自身のブートストラップ（メッセージ 0x2f）と、その中継された順序のステーションのメッセージから、それぞれマシンの時計上の捕獲時刻で、サーバーは本体の 24 フレームすべてを同じ順序でゲストに送ります。種別 1、0x11、4 つのリクエスト、13 のラウンド（うち 3 つはボスのもの）、2 つの 0x47、そして 0x25、0x29、0x49 です。どれもヘッダーの書き込まれないバイトとリクエストブロックの（[アクション](#actions)）を除いて、本体のものとバイト単位で一致します。ボスの時間制行動は、タイマー自身の開始から、本体のフレームで発動します。unicorn の下で、リフトされたすべてのステップについてゲーム自身のコードは、提供されたバトル全体を通じて同じページを残します。

### ラウンドの再現

ラウンドは、種別 0x15 のビルダー `0x113c8a0` で停止したエミュレートした本体から、unicorn の下で正確に再生されます。メモリは、再生が最初に触れるときに、GDB スタブから 1 ページずつ取得されます。`tpidrro_el0` の後ろにあるスレッドローカルのページはスタンドインであり、その `+0x1f8` は偽のスレッドを指します。SVC 0x10、0x11、0x12、0x1a、0x1b、0x1d、0x1e は 0 を返します。11 の再生したラウンドは、本体がその後に自分で組み立てたボディとバイト単位で一致し、1 つのラウンドは 159 から 353 ページに触れました。

サーバーの Python 移植は、それを実行します。ゲスト関数ごとに 1 つの関数で、オフセットを main からの距離でキーにしています。ビルダー `0x113c8a0` は、メッセージ種別 1、5、17、21 について Python で動きます。ラウンドのドライバー `0x113e3d0` は、わざの選択、ダメージ `0xf7c344`、ひんし `0x1144df8`、ターン終了 `0x114a094` を含み、バトル開始 `0x113dca8` は、繰り出し、持ち物、特性、交代のハンドラーを含みます。停止した 86 台の本体（49 ラウンド、5 回のバトル開始）にわたり、移植版はゲスト自身のコードと同じボディと同じメモリページを残し、ゲストへ戻される呼び出しは一つもありませんでした。移植版が割り当てるヒープは、SDK の `nn::mem::StandardAllocator` を、スレッドキャッシュの上で、そのキャッシュの作成と TinyMT32 のキー（`0x525f448`）とともに移植したものです。バトル状態の構築段階 `0x2891748`、`0x2892ac0`、`0x2d381a4`、`0x2892dd4` も Python で動き、エントリを含めてゲームと同じページを残します。`__cxa_guard_acquire`（`0x53c49a0`）は、バイト 0 もバイト 1 も立っていないとき 1 を返し、ガードのバイト 1 を 2 に設定します。

Hex のラウンドは、書き込んでいない 16838 バイトを読みます。内訳は、静的イメージから 1496 バイト、コマンド形式のマップ（`0x2d381a4` が作る）から 5372 バイト、サーバーオブジェクト（同じく `0x2d381a4` が作る）から 2926 バイト、バトラーとそのポケモン（`0x2892ac0` が作る）から 2414 バイト、メインモジュール群（`0x2891748` が作る）から 1756 バイト、データテーブルから 2278 バイト、ラウンドの行動ブロックから 576 バイトです。

データテーブルは、関数内の静的変数が保持する romfs のファイルです:

| 静的変数 | ファイル | オブジェクト |
|---|---|---|
| `0x47420b8` | `avalon/data/personal_array.bin` | マップ。キーは種族 * 10000 + フォルム（u32） |
| `0x47420d8` | `avalon/data/growTable.bin` | FlatBuffers のルート。[T+0x30] の vf +0x70 を通す |
| `0x4742568` | `avalon/data/waza_array.bin` | マップ。キーはわざ（u16） |
| `0x4742548` | `avalon/data/tokusei_array.bin` | マップ。キーは特性（u16） |
| `0x4734e50` | `world/data/battle/battle_item_conversion/battle_item_conversion_array.bin` | 配列 |

マップは、+0x68 にある libc++ の `unordered_map` です。バケットは +0x68、バケット数は +0x70（レコード数以上の次の素数）、最初のノードは +0x98、サイズは +0xc0、負荷率は +0xc8（1.0）、既定のレコードは +0xd0（キー 0 のレコード）です。ノードは {next, hash = key, key, 読み込んだファイル内のレコードへのポインタ} で、+0x30 はファイルのリソースです（FNV ハッシュは +0x48、パスは +0x50）。アイテム配列（`0x1821674` が埋める）は、+0x28 から 0x18 バイトのエントリを持ちます。内容は、u32 のインデックス、u32 の 0、u64 のハッシュ、u16 のアイテム、6 バイトのゼロです。エントリ i はファイルのレコード i で、そのハッシュは main `0x3c61260 + 8 * index` の u64 です。ファイルは `arc/data.trpfs` から取り出され（`tools/switch/trpfs_read.py`。Oodle のエントリはゲーム自身の `OodleLZ_Decompress`（`0xcc8750`）を通す）、97 台の停止した本体が保持していたそのバイト列は、すべて抽出したファイルと一致します。

バトルの開始も、停止した本体がない移植版の中で動きます。静的イメージと romfs だけから、移植版はゲームのヒープを組み立てます。これは、「Application」の数えるアロケーター（`0x3b78d3d`、上限 0xa0000000、GlobalHeap アロケーター 0x4763918 の上）、弱参照ハンドルのテーブル（`0x165dd08`）、5 つのデータテーブル（personal `0x164498c`、ID ハッシュ `0x1730f6c`）です。セッションとサーバーオブジェクト N は、その後、ゲーム自身の生成器（下記）から作られ、ブートストラップからのレイド開始のセットアップフィールドを持ちます。その後、N の開始状態が 4 つの構築段階を実行し、種別 0x11 のビルダーが動きます。5 つのセッション（268、345、328、422、268 バイト）のバトル開始ボディは本体のものと一致し、その後の 9 ラウンドの 20576 バイトのボディも、それぞれ行動するスロットの 2 つのアクションから組み立てたものが一致しました（[アクション](#actions)）。ただし、リクエストブロックの書き込まれないスタックのバイトは除きます。バトルのシードを変えても、開始ボディは変わらず、1 つのラウンドの 123 バイトが変わります。ヒープのアドレスも弱参照ハンドルの ID も、ボディには現れません。本体の ID は世代 3 の 0x1b5xx であり、移植版の ID は 0..0x58 で、そのすべてのオブジェクトは別のアドレスにあります。

N の開始状態（`0x1269824`）は次のとおりです。状態 0 は、セットアップの時間制限（+0x48a..）を N+0x8a にコピーし、選挙オブジェクトを N+0x138 に、[N+0x48]+0x140 を N+0x190 に入れ、サーバーの構築 `0x2891748` を実行し、乱数ホルダー（N+0x1a0）をセットアップの +0x718 で初期化します（`0x281c260`。これは一度抽選する）。N+0x30 にそのシードを設定し、N+0x120 の 6 x 5 のコマンドペアを作り（`0x132ecfc`）、[N+0x110] に、N+0x120 とマネージャーの通信ホルダー（`0x169ffa0`）を使った u32 のセットアップ +0x2c を与えます。状態 2 はモードによってステップマシンを選び（レイドでは `0x2d380a4`）、状態 3 がそれを実行します。その状態 0 は、ルールと N+0x95 により書式バイト N+0x98.. を設定し、次にステップ `0x2892ac0`、`0x2d381a4`、`0x2892dd4` を実行します。

レイドの開始は、セットアップの Lua バインディングを通じて、セットアップを Lua（0.4455 → 0.4893 → 0.4945）から書き込みます。これらのフィールドは、4 台の本体のセットアップで同じ値を持っていました。u32 +0x2c は 10003（`fD8E195CA`。そのためビルダーが読む 0x2713 は [N+0x110]+0x40 にある）、u32 +0x34 はモード 2、+0x8c は 1、+0x8d はルール 5、u32 +0x90 は本体のスロット 2、u32 +0x94 はサーバーのスロット 0、メンバーのコード +0x99.. は（0, 0xff, 1, 0xff, 0xff）、+0x488 と +0x489 は 1、+0x498 は 0x400、u32 +0x4b0 は 12000、u32 +0x4b4 は 400、+0x4dd と +0x4df は 1、u32 +0x4ec は 0、+0x706 は 1、+0x714 は 8。参加者ごとに、+0x18 から 0x1c バイトのエントリ 6 個（u16 +0x10 は 30（ボスは 26）、u8 +0xd は 1。ホストのエントリは 1 から 5、ゲストは 0 から 5）。ブートストラップが、シード（+0x718）、時間制限（+0x48a、+0x48c、+0x48e）、ボスの行動プロファイル（+0x514）、パーティのホルダー（+0xa0..）を与えます。unicorn の下では、ゲスト自身のコードが、これらのフィールドから、移植版と同じマネージャー、S、N+0x48、N、および状態 0 の書き込みを行います。ただし、ゲームがスタックのパディングからコピーするバイトは除きます。

4 つの部分は対象外です。S のジョブ（`0x159f018`。そのコンストラクターにはエンジンのジョブスケジューラーが必要で、どのバトルのコードも S+0x40 を読みません）、ジョブグラフのリンク（`0x1193e44`、`0x11fd13c`）、リソースシステム（setup+0x720 は `0x1ffbb68` を通じ、ローダー N+0x1a8 は `0x1802edc` と `0x1929dc4` を通じ、状態 1 がそれを待ちます）、そして選挙オブジェクトにステーション ID を与える Pia ネットワークマネージャー `[[0x46d6ca0]]` です。

データシステムの初期化 `0x1641afc` は、`0x1643a48`（personal、growth）、`0x1641cf0`（moves）、`0x1641d78`（abilities）を実行します。各テーブルはアロケーターから作られ、その静的な領域にリセットされ（`0x1643e68`）、`0xf0ba9c` を通じてレジストリ 0x4763a18 に追加されます（カウント u32 は 0x4765a18、最大 0x400）。ファイルのレコードをファイルの順に、その数を確保してから挿入すると、本体のノード一覧が得られます。静的イメージと 5 つのテーブルは、プレイヤー自身のダンプから来ます。main と SDK は v4.0.0 のアップデートの ExeFS から（main のビルド ID `421c5411b487eb4d049dd065fec9547773e8e598`）、各 NSO のセグメントは .bss とともにそのメモリオフセットに、RELATIVE の再配置は main `0x8504000` と SDK main + `0x4e6d000` に、そして GLOB_DAT、JUMP_SLOT、ABS64 のスロットは、そのシンボルをエクスポートする最初のモジュールに（main を SDK より前に）束縛されます。テーブルは、ベースゲームの上にアップデートの RomFS から来ます（`arc/data.trpfs`、Oodle は `0xcc8750` 経由）。M4 で読み込みに 3 秒かかり、セッションと N の開始状態の構築は 2.4 秒です。

弱参照ハンドル（weak-handle）のエントリは 0x20 バイトです。u64 の ID（u32 のインデックス | u32 の世代 << 32）、+8 に解決された値、+0x10 にオブジェクト、u16 +0x18 は弱参照の数、u16 +0x1a は強参照の数、u32 +0x1c は状態（-1 は解放済み、-2 は生存中）。ブロックは 0x400 個のエントリを保持します（`0xc1adec`）。解放された ID は、`0xb44724` で伸長される `deque<u32>` に入ります。

### サーバーの流れ（計測）

これらは、[バトルの提供](#serving-the-battle)のスクリプト化されたコンソールに対するオラクルサーバーについて成り立ちます。それらから組み立てたサーバーは、プレイヤーが勝った 9 つの完全なバトルにわたり、通知を含めて、本体に同じフレームを送りました。

| 規則 | 計測結果 |
|---|---|
| ヘッダーのカウンター | `step` は、送信、ブロードキャスト、または 1 つのリクエストごとに 1 増える。`round` はメッセージ 1 で 0、0x11 から 1、0x15 と 0x25 ごとに増える |
| フレームあたり 1 つのジョブ | メッセージ 1 は Wild::Setup を開始する。これは、すべてのスロットが 1 に応答した後に 0x11 を送り、すべてのスロットが 0x11 に応答した 1 フレーム後に終わる |
| リクエスト | ジョブが動いていないフレームで、未応答のものが何もないスロットには、リクエスト（5）が投稿される。リクエストはフレームごとに 1 つずつ、スロットの順 0、2、3、4 で開始する |
| コマンド | スロットの 6 は、ラウンド（0x15）をすべてのスロットに送るジョブとして投稿される |
| 再び尋ねる | 送られてきたすべてのラウンドに応答したスロットは、次のフレームで再び尋ねられる |
| 勝利 | 勝つラウンドの次のフレームに、空のラウンド 0x25（20576 のゼロバイト）が続き、その後にボディ `00 00 01 00 01 00` を伴う 0x29、0x49、0x35、0x37 が続く。それぞれ、すべてのスロットが直前のものに応答した後に 1 回送られる。0x25 と 0x49 への最後の応答の 2 フレーム後、他のものの同じフレーム |
| タイムアップ | ボディ `00 00 00 00 02 00` を伴う 0x2b（233 バトルのうち 63） |
| 通知 0x46 | ジョブが開始するフレームごとに 1 つ。または、ジョブが動いていないときにラウンドの応答（0x16）が読まれるフレームごとに 1 つ |

### バトルの提供

`bin/sv_host.py --raid-serve [NAME]` は、バトルの間ネットワークを保持し、ホストのステーションから `pokeldn.sv.raid_battle.RaidBattle` で提供します。これは、ブートストラップと 2 人の NPC パートナーから組み立てられたプラグインのバトルサーバー（[バトルサーバー](plugins.md#a-battle-server)）と、本体ホストが自分用に保持するステーションです。pokeldn はバトルサーバーを同梱しません。それを追加するプラグインがない場合、フラグは拒否されます。提供されるセッションは、こちらのポケモン、ボス、1 台の本体（ステーションインデックス 1、ブートストラップの参加者 1、スロット 2）、2 人の NPC パートナーを着席させるため、このフラグは本体 1 台を取ります。

| 部分 | ホストが送るもの |
|---|---|
| サーバーから本体へのメッセージ | 宛先 (0x2713, 1, 2) のフレーム |
| スロット 0、1、3、4 | 奇数のステップごとに、0.05 秒後に種別 + 1 で応答する。スロット 0、3、4 には、スロットのポケモンがボスに最初のわざを使い、ボスがそのポケモンに最初のわざを使う type-6 コマンドを伴うリクエスト（5）を送る（[アクション](#actions)） |
| サーバーが読むすべてのメッセージ（本体自身のものを含む） | 本体へ中継し、宛先 (0x2713, 3, 5) とする |
| バトルを進めた各サーバーフレーム | そのフレームのメッセージの後に、スロット 0 から通知 0x46（ステップ 0、4 バイトのゼロのボディ）を、宛先 (0x2713, 3, 5) で送る |

各フレームは、0x80 ポート 0 で、圧縮（deflate）された 1 つの信頼性のあるメッセージとして送られます（フラグ `COMPLETE_ZLIB`）。圧縮後の最大は 903 バイトでした。Scarlet 4.0.0 の送信を再現するサーバーは、最初の 6 フレームとして、市販のホストが送った 6 つのバトル開始メッセージ（`raid.HANDOFF`）を、スタックが埋めたヘッダーのバイトを除いて、同じ順番で送ります。そのため `--raid-serve` は、`HANDOFF` の代わりにそれらを送ります。

ホストは、本体が 0x37 に応答したとき、または 0x37 を送ってから 5 秒後に、提供を止めてネットワークを閉じます。0x37 への応答そのものは、サーバー上でタイムアップを再実行するため（[サーバーの流れ](#the-servers-flow)）、ローカルのステーションは応答せずに離脱します。失敗（サーバーが例外を出す、または組み立てに失敗する）が起きると、提供を止め、フラグなしのホストと同じようにネットワークを引き渡します。その後、本体はフェイルオーバーして自分のバトルを戦います（[どのステーションがサーバーを担うか](#which-station-runs-the-server)）。

## 参加

`bin/sv_join.py --raid-pokemon FILE` は、シーン 7 のネットワークに参加し、ゲストとして加わります。本体のプレイヤーは、クリスタルを開き、グループとして「挑戦」を選んで待ちます。アプリのテラレイド（参加）ツールがそれを実行します。`pokeldn.sv.raid.RaidGuest` と参加者は、次を順に行います。

| 段階 | ゲスト |
|---|---|
| Net | メッセージフラグ 0x11 の下で、0x11 と 0x50 に応答する |
| Session | 参加応答に付いてくるステーション一覧には応答せず、その再送には少なくとも 1 秒後に応答する。その後のすべての一覧にも応答し、バイト 9 を設定した時計の要求を送る |
| channels | ホストの 6 つのキーのテーブルを、4 つと、レイドの 2 つに分ける。4 つを告知する。0.24 秒後にポート 2 に参加し、テーブルの 0.79 秒後にレイドのキーを告知する。0x7C の ACK を 0.25 秒遅らせる |
| identity | 着席の 0.44 秒後に、標準のレコードセット（`pokeldn.sv.reference`）を、トレーナー名のもとでレコード 1 として送る |
| lobby | その 0.27 秒後に、状態 0x18 とそのポケモン。2 秒後に状態 0x01 |
| start | ホストの状態 0x0c が届いたら状態 0x0d。準備完了として 0x0d を送ったゲストは確認応答されたが、準備完了としては表示されなかった |
| battle | ホストの 0x3480 の 0x93 に応答し、type 4 が届くまで 0.5 秒ごとに Session の type 3 の離脱を送り（最大 4 回）、ネットワークを離脱する。バトル中の市販のスカーレットは、4 回のどれにも応答しなかった |

市販のホストに対して、ゲストはロビーにトレーナー名で表示され、準備完了になり、ホストに開始させました。そのポケモンはバトルに残りました。
