# ESP32 無線機

USB シリアルで接続した ESP32 ボードが無線機です。`firmware/esp32/` を実行し、LDN のベンダーアクションフレームと
イーサネットフレームを運びます。広告の暗号処理、LDN の認証、IP、Pia はホストに残ります。`pokeldn.ldn.esp32_wlan` は
LDN ライブラリにボードで動くファクトリを渡すので、`ldn.scan`、`ldn.connect`、`ldn.create_network` は変更なしで動き、
ホストに Wi-Fi ドライバは要りません。

## 対応ボード

| チップ | ホストとの接続 | 結合イメージ |
|---|---|---|
| クラシック ESP32 (ESP32-D0WD, WROOM-32E) | USB シリアルブリッジ経由の UART0 | `pokeldn-radio.bin` |
| ESP32-S3 | ネイティブ USB Serial/JTAG | `pokeldn-radio-s3.bin` |
| ESP32-C3 | ネイティブ USB Serial/JTAG | `pokeldn-radio-c3.bin` |
| ESP32-C6 | ネイティブ USB Serial/JTAG | `pokeldn-radio-c6.bin` |
| クラシック ESP32、ESP32-C6 | Bluetooth LE (iOS アプリ)、および上記の USB | `pokeldn-radio-ble.bin`、`pokeldn-radio-ble-c6.bin` |

全ターゲットは 2.4 GHz を使います。ESP32-S2 は非対応です。Seeed Studio の XIAO ESP32C3 と XIAO
ESP32S3 にはオンボードアンテナがなく、付属の外付けアンテナの接続が必要です。N8R2 や N16R8 などの大型の S3 ボードは
オンボードアンテナを搭載しています。UART とネイティブ USB のソケットが別々にある S3、C3、C6 のボードは、
無線通信にネイティブ側のソケットが必要です。USB Serial/JTAG は
GPIO19 (D-) と GPIO20 (D+) を使います。詳しくは
[Espressif の USB ガイド](https://docs.espressif.com/projects/esp-idf/en/v5.2/esp32s3/api-guides/usb-serial-jtag-console.html) を参照してください。
C3 では、ネイティブ USB が GPIO18 (D-) と GPIO19 (D+) を使います。詳しくは
[Espressif の C3 USB ガイド](https://docs.espressif.com/projects/esp-idf/en/latest/esp32c3/api-guides/usb-serial-jtag-console.html) を参照してください。
USB 識別子 `303a:1001` は複数のチップで共有されています。書き込み時に esptool がチップを判別します。
S3 を UART 側のソケット (DevKitC 上の WCH CH343 ブリッジ) から書き込むことは成功しますが、その後ファームウェアは
そのソケットでは応答しません。USB シリアルブリッジ経由でどのファームウェアも応答しない場合、デスクトップアプリは
ROM ブートローダーからチップの種類を読み取り (esptool `detect_chip` の後にハードリセット)、
そこで見つかった S3、C3、C6 を誤ったソケットに挿されていると表示します。

Seeed Studio の XIAO ESP32C3 は、ネイティブ USB Serial/JTAG に USB-C ソケットを使います。
無線を使う前に、付属の外付けアンテナを接続してください。BOOT は GPIO9 で、オンボードの LED は
充電インジケーターです（[Seeed のボードガイド](https://wiki.seeedstudio.com/XIAO_ESP32C3_Getting_Started/)）。
C3 のビルドは 160 MHz で動きます。ワイヤーとボタンのタスクはコア 0 で動き、デュアルコアのターゲットでは
これらのタスクをコア 1 で動かします。

macOS でネイティブ USB 経由の XIAO ESP32C3 revision 0.4 は、2,000,000 バイトの BENCH 転送を 1429 メッセージで運びました。
欠落も不正なチェックサムもなく、ホストのボーレート設定が 115200 のときは 880.1 KB/s、
1500000 のときは 878.3 KB/s でした。ホストのボーレート設定は USB の速度を変えません。
起動時の空きヒープは 152656 バイトです。

Seeed Studio の XIAO ESP32C6 (ESP32-C6FH4、内蔵フラッシュ 4 MB) は、ネイティブ USB Serial/JTAG に
USB-C ソケットを使います。RF スイッチは GPIO3 が low の間に給電され、GPIO14 でセラミックアンテナ (low) か
U.FL ソケット (high) を選びます（[Seeed のボードガイド](https://wiki.seeedstudio.com/xiao_esp32c6_getting_started/)）。
C6 のファームウェアは Wi-Fi の開始前に両方を low にするため、ボードはセラミックアンテナから電波を出します。
イメージはすべての C6 ボードで同じで、アンテナの接続は要りません。ESP32-C6-DevKitC-1 では、
GPIO3 と GPIO15 はピンヘッダーにしか出ておらず、GPIO14 は引き出されていません。
アドレサブル RGB LED は GPIO8 にあります（[Espressif のユーザーガイド](https://docs.espressif.com/projects/esp-dev-kits/en/latest/esp32c6/esp32-c6-devkitc-1/user_guide.html)）。
そのため XIAO のピン設定は、そのボードの無線部品には影響しません。
BOOT は GPIO9 です。GPIO15 の黄色のユーザー LED (low の間点灯) は LED の点灯テストに使われ、赤い LED は
充電インジケーターです。ビルドは 160 MHz で動き、C3 と同じくワイヤーとボタンのタスクはコア 0 で動きます。

C6 は Wi-Fi 6 チップです。ステーションは 11b/g/n に制限されるため、アソシエーション要求には
他のすべてのターゲットと同じく HE 要素が入りません。受信ヘッダー (`esp_wifi_he_types.h`) には `sig_mode`、
`mcs`、`cwb` がありません。そのためファームウェアは RX_SNIFF と RX_CENSUS の `sig_mode` を `cur_bb_format` から、
HT MCS のバイトを `he_siga1` 内の HT-SIG から導きます。レートのバイトは、`wifi_phy_rate_t` ではなく、
OFDM フレームの L-SIG レートコードです。ESP-IDF v6.1 の C6 Wi-Fi ライブラリは、ファームウェアが使う
すべての非公開シンボルをエクスポートしており、そのオフセットは C3 と同じ `lmacConfMib` です。

macOS のネイティブ USB 経由の XIAO ESP32C6 revision 0.2 は、2,000,000 バイトの BENCH 転送を 1429 メッセージで運び、
欠落も不正なチェックサムもありませんでした。速度は 824.6 KB/s で、アップリンクコマンド 5000 件のうち
5000 件を取りこぼしなく受け付けました。起動時の空きヒープは 255196 バイトです。セラミックアンテナを使った
ファイアレッドの参加セッションでは、ボードが受けたホストからの ETH_TX コマンド 5155 件をすべて数え、
不正なワイヤーフレームも USB の再同期もありませんでした。

Seeed Studio の XIAO ESP32S3 (ESP32-S3 revision 0.2、フラッシュ 8 MB、PSRAM 8 MB) は、ネイティブ USB Serial/JTAG に
USB-C ソケットを使い、付属の外付けアンテナが必要です。BOOT は GPIO0 です。GPIO21 の黄色のユーザー LED
(low の間点灯) は LED の点灯テストに使われます。macOS のネイティブ USB 経由では、2,000,000 バイトの BENCH 転送を
1429 メッセージで運び、欠落も不正なチェックサムもなく、883 KB/s で動きました。アップリンクコマンド 5000 件のうち
5000 件を取りこぼしなく受け付けました。起動時の空きヒープは 212416 バイトです。

別のボードが指定されていない限り、以下のクラシック ESP32 の計測は ELEGOO ESP32-D0WD-V3 ボードを使っています。
ボードごとの完了したトレードは [ボード別のトレード](#trades-by-board) にあります。

### リセット後の USB リンク (C6, S3)

ポートを開くと、USB Serial/JTAG 経由で C6 または S3 がリセットされます (リセット理由 11、コアリセット)。
両チップの ESP-IDF 既定値である `CONFIG_ESP_SYSTEM_BBPLL_RECALIB=y` の場合、アプリケーションの起動処理は
`recalib_bbpll()` を実行します (`esp_system/port/soc/esp32c6/clk.c`、S3 でも同じ)。CPU リセット以外のリセットでは、
これが `rtc_clk_cpu_freq_set_xtal()` を呼びます。この関数は USB の利用側を確認せずに BBPLL を止めてから再起動します。
ホストと通信している間、USB Serial/JTAG は 48 MHz のクロックをこの PLL から取ります。
XIAO ESP32C6 では、その後リンクが文字化けした状態で立ち上がることがあり、ボードを抜くまでその状態が続きました。
ファームウェアは動き続け、そのブート以降 SOF のフレーム番号は動きませんでした。
`USB_SERIAL_JTAG_INT_RAW` には PID、CRC5、ビットスタッフィングのエラーが残り (正常時は `0000b50a` のところ `0000b5b2`)、
返信が IN FIFO に詰まったままでした。クロック有効化、パッド、PCR のレジスタは正常なボードと一致していました。
EP0 上の GET_CONFIGURATION は失敗し、esptool の USB リセットには応答がありませんでした。

| C6 イメージ | ポートを開いた回数 (リセットと起動) | ボードを抜くまでリンクが停止 |
|---|---|---|
| recalibration 有効 | 113 | 1 (113 回目のオープン時) |
| recalibration 無効 | 900 | 0 |

C6 と S3 のビルドは `CONFIG_ESP_SYSTEM_BBPLL_RECALIB=n` を設定します。その Kconfig のヘルプは、
ESP-IDF v5.2 以降でビルドされたブートローダーであれば、この設定を認めています。どの結合イメージも
独自の v6.1 ブートローダーを持ちます。recalibration 無効の XIAO ESP32S3 は、300 回のオープンすべてに応答しました。
C3 にはこの設定はなく、障害も出ませんでした。recalibration 無効の状態では、C6 の 600 回のオープンのうち 4 回で、
応答がない状態が一度起き、次のオープンでは macOS がデバイスを再列挙した後に正常なリンクに戻りました
(「Device not configured」)。

C6 と S3 のビルドには USB ウォッチ (`usbwatch.c`) が入っています。5 ms ごとに SOF のフレーム番号を読み、
フレームのカウントが始まるか、ホストがバイトを送った後で、2 秒の停止が起きるとチップを再起動します。
再起動の前後の USB とクロックのレジスタは、次の HELLO の際に LOG 行として報告されます。
これは停止した USB のフレームクロックを検出するものです。ドライバが止まっていても SOF は進むことがあり、
チップを再起動しても行き詰まった USB ペリフェラルが回復する保証はありません。再起動時に実行中の転送は終わります。
`idf.py` の環境で `POKELDN_USB_BEACON=1` を設定してビルドすると、どちらのイメージも、USB リンクが停止している間、
これらのレジスタ、観測した SOF の変化、読み取ったホストのバイト数を 1 秒ごとに、ベンダーアクションフレーム
(カテゴリ 127、OUI `02:55:53`) としてグループアドレス `03:55:53:42:57:00` に送ります。スニッフィング用のボードは
`esp32_sniff.py --mac 03:55:53:42:57:00` でこれらを保存します。4 バイトのベンダーヘッダーの後のフレーム本体は
u32 リトルエンディアンで、順に稼働時間 (ms)、SOF の変化、ホストのバイト数、`wire_dropped`、停止回数、
そして `usbwatch.c` に列挙された 16 個のターゲット固有のレジスタです。
S3 は USB エンドポイント、SYSTEM のクロックとリセット、GPIO19/20 をスナップショットします。
C6 は USB エンドポイント、PCR のクロックとリセット、GPIO12/13 をスナップショットします。
S3 のサポートはファームウェア 1.6.2 から始まります。

## 役割

| 役割 | ボードの動作 |
|---|---|
| idle | 1 つのチャンネルでプロミスキャスモード。Nintendo LDN のプレフィックス `7f 00 22 aa` を持つすべてのアクションフレームをホストに送る |
| station | BSSID によって本体のネットワークに参加する。ホストから導出した CCMP 鍵を使う |
| access point | ホストの BSSID 上に SSID を隠した WPA2 ネットワークを作る。鍵は同じ方法で導出する |

本体のネットワークには 4-way ハンドシェイクがありません。両端とも、広告のサーバーランダムから CCMP 鍵を導出します。
ファームウェアは、ESP-IDF の非公開の `struct wpa_funcs` テーブル (`esp_wifi_driver.h`) の 4 エントリを置き換えます。
このレイアウトは v6.1 のバイナリブロブの ABI です。ファームウェアは他のリリースに対するビルドを拒否します。

- `wpa_sta_connect` は、標準のコールバックの前後で、Switch の station が送る RSN 要素 (CCMP、PSK、capabilities `0x000c`) をインストールします。標準のコールバックはそれを組み立て直します。
- `wpa_sta_rx_eapol` は EAPOL を破棄します。アソシエーション応答を受け取ったら `esp_wifi_set_sta_key_internal` で station の鍵を設定し、その後 `esp_wifi_auth_done_internal` でポートを開きます。
- `wpa_ap_join` は station を hostapd のテーブルに追加し、オーセンティケーターのステートマシンなしでアソシエーション応答 (`esp_send_assoc_resp`) を送るため、EAPOL-Key のメッセージ 1 は送られません (`AP_START` フラグのビット 0 が標準の join を維持します)。station の MAC をキューに入れ、メインループがペアワイズ鍵 (`esp_wifi_set_ap_key_internal(CCMP, mac, 0, key)`) をインストールしてポートを開きます (`esp_wifi_wpa_ptk_init_done_internal(mac)`)。これは hostapd の `PTKINITDONE` の順序です (`wpa_auth.c:2290-2332`)。グループ鍵はインデックス 1 で `WIFI_EVENT_AP_START` の時点に設定されます。
- WPA2 の station について、`esp_wifi_wpa_ptk_init_done_internal` は `WIFI_EVENT_AP_STACONNECTED` (イベント 14、`ieee80211_supplicant.o`) を発行する唯一の関数です。鍵をインストールするためにそのイベントを待ってはいけません。4-way ハンドシェイクがないのでイベントは来ず、本体の最初の暗号化フレームが破棄されます。

## アクセスポイントのフレーム

softAP のビーコン、プローブ応答、アソシエーション応答は、閉じた
`libnet80211.a` の中で組み立てられます。v6.1 のブロブ (`ieee80211_output.o` のオフセット) から読み取り、`vendor/LDN` の
access point が Switch に送るものと比べています。

| 項目 | Switch 向けの形式 | ESP32 softAP | 設定可否 |
|---|---|---|---|
| 非表示 SSID 要素 | 32 バイトのゼロ | 長さ 0 (`ieee80211_beacon_construct` 0xc4) | 不可 |
| Supported Rates | `82 84 8B 96 0C 12 18 24` | `8B 96 82 84 0C 18 30 60` | 不可。同じ 12 レートと基本ビットで、9 と 18 は Extended に入る |
| Extended Rates | `30 48 60 6C` | `6C 12 24 48` | 不可 |
| capability、beacon | `0x0511` | `0x0431` (short preamble の定数、`ieee80211_getcapinfo` 0x7b) | 不可 |
| HT 要素 | なし | 11b/g/n に存在 | 削除。ファームウェアが 11b/g に設定する |
| RSN capabilities | `0x000c` | hostapd 自身の値 | 設定。`wpa_ap_get_wpa_ie` が Switch の要素を返す |
| WMM | なし | 11g に存在 | 11b のみの設定の場合だけ削除される |

非表示の softAP は、指定された宛先へのプローブにのみ応答し、プローブ応答には実際の SSID を入れます。設定された SSID を含まない
アソシエーション要求は破棄されます (0x9c6)。`esp_wifi_80211_tx` はビーコンを受け付け、アソシエーション応答は拒否します
(`ieee80211_raw_frame_sanity_check` 0xf9)。ブロブ自身の
ビーコンは止められません。

## シリアルプロトコル

フレームは `COBS(type | payload | crc32-le(type | payload))` の後に `0x00` が続く形式です。CRC は CRC-32/ISO-HDLC
(`zlib.crc32`) です。クラシック ESP32 は 115200 ボーで起動します。`BAUD` は両端を切り替え、ボードはリセットするまで
そのレートを保ちます。S3 では
`BAUD` は確認応答されますが、USB の転送レートは変わりません。`0x00` より前のもの (ROM のブートテキストを含む) は、
チェックサムに失敗して破棄されます。

| type | 方向 | payload |
|---|---|---|
| `0x01` HELLO | host | なし。CREDIT 0 の後に INFO で応答される。ホストは直前に `0x00` を送る。これは、誤ったレートの HELLO がボードのデコーダーに残した途中のフレームを終わらせるためで、ファームウェアは空のフレームを読み飛ばす |
| `0x02` BAUD | host | u32 のボーレート。古いレートで RESULT を返した後に切り替える。切り替えは UART の排出を最大 3 秒待つ (115200 のときリングには 1 秒を超える RX_MGMT が入る)。1500000 での最初の HELLO は失われることがある (計測では 4 回に 1 回ほど)。`open_serial` が再試行する |
| `0x03` CHANNEL | host | u8 のチャンネル。idle のときのみ |
| `0x04` STA_JOIN | host | u8 のチャンネル、6 バイトの BSSID、32 バイトの SSID (LDN の SSID の 16 進テキスト)、16 バイトの鍵、6 バイトの station MAC (ゼロはランダム)。任意: u8 の固定データレート (AP_START のビット 3..5 の表)、u8 の最大送信電力 (0.25 dBm 単位、`esp_wifi_set_max_tx_power`、8 から 84、ドライバは 61 で頭打ちにする)、u8 のフラグ: 1 は全フレーム前に RTS、2 は再送前に RTS を送らない (`esp_wifi_internal_set_rts`) |
| `0x05` STOP | host | なし。idle に戻り、鍵を消去する |
| `0x06` AP_START | host | u8 のチャンネル、6 バイトの BSSID、32 バイトの SSID、16 バイトの鍵、u8 の最大 station 数、u8 のフラグ: 1 は標準のアソシエーションと 4-way ハンドシェイク、2 は station に QoS を付けない、4 は station のデータフレームごとの 40 バイトのコピーを作らない、ビット 3..5 は固定データレート、`0x40` は 1000 TU ごとのビーコン、`0x80` はプロミスキャス受信なし。任意の 2 番目のフラグバイト: 1 はドライバのノイズフロア確認を無効、2 はその間隔を 250、4 は各 40 バイトのコピーの先頭に受信時刻を入れる、8 は再送上限を 7 と 4、`0x10` は station の正常なデータフレーム以外のすべてのフレームに RX_CENSUS。その後、任意の最大送信電力 (0.25 dBm 単位) |
| `0x07` AP_KICK | host | 6 バイトの MAC、u16 の理由。認証を解除する |
| `0x08` ETH_TX | host | イーサネットフレーム。ドライバが station の鍵またはグループ鍵で暗号化する。ドライバのキューが満杯 (`ESP_ERR_NO_MEM`) の場合は、1 ms ごとに最大 100 ms 再試行する。去った station へのフレームは `0x3015` (`ESP_ERR_WIFI_NOT_ASSOC`) ですぐに失敗する。station はイーサネットの送信元を 802.11 の送信元アドレスとして送る。LINK の MAC と異なる送信元は、一度も確認応答されない (49 件中 49 件) |
| `0x09` RAW_TX | host | FCS なしの 802.11 フレーム (`esp_wifi_80211_tx`)。広告に使う |
| `0x0A` SNIFF | host | u8 のチャンネル、6 バイトの MAC。その MAC との間のすべての管理フレームとデータフレーム、およびチャンネル上のすべてのアクションフレーム (LDN の広告は、本体が移動する先のネットワークを決める) を、そのまま RX_SNIFF として送る。MAC ff:ff:ff:ff:ff:ff はチャンネル上のすべてのフレームを RX_CENSUS として送る |
| `0x0B` STATUS | host | なし。STATUS で応答される |
| `0x0C` BENCH | host | u32 のバイト数、u16 のメッセージサイズ (8 から 1600)。RESULT の後、UART が受け付ける速さで BENCH メッセージを送る |
| `0x0D` LED | host | u8 のパターン、u8 の最大輝度、u16 の周期 (ms、0 はパターンの既定値)、u16 の継続時間 (ms、0 は次の LED コマンドまで)。RESULT。古いファームウェアは `0x106` で応答する |

| `0x81` INFO | board | u8 のプロトコルバージョン (1)、6 バイトの station MAC、6 バイトの AP MAC、u8 のチップのリビジョン、テキスト |

| `0x8F` RX_CENSUS | board | FCS 失敗と制御フレームを含め、受信したすべてのフレーム: u32 の受信時刻 (µs)、i8 の RSSI、i8 のノイズフロア、u8 の `rx_state` (0 は正常)、u8 のパケット種別 (0 は管理、1 は制御、2 はデータ、3 はその他)、u8 の `sig_mode`、u8 のレートコード、ビット 7 を 40 MHz とする u8 の MCS、FCS を含む u16 の `sig_len`、フレームの先頭 16 バイト |

### ホストのウォッチドッグ

ファームウェア 1.4.0 から、ホストは毎秒 ALIVE を送ります (`esp32.ALIVE_EVERY`)。周期は INFO の `version=` のテキストから決まります。
HELLO の後の最初の ALIVE でウォッチが有効になり、HELLO で無効になります。そのため ALIVE を送らないホストは監視されません。
有効な状態で、idle 以外のボードが 5 秒 (`HOST_SILENT_US`) ホストのコマンドを読まないと、STOP の後始末が動きます。
access point はビーコンを止め、station は切断されます。station は接続を切ります。
その後、ホストがコマンドを再び送るまで、ホスト宛てのメッセージはすべて数えずに破棄されます。そうしないと、USB のボードから
ホストがいなくなったとき、キューに入った各メッセージや聞こえた各メッセージが
500 ms の書き込みと `wire_dropped` になり、LED のアラームは `flash3` の点灯し続ける状態になります。

XIAO ESP32C6 で、`frlg_trade_host.py` のトレードルームにいる市販のファイアレッドに接続し、ホストを SIGKILL で止めたとき、
本体には 2318-0006 が表示され、その後の JOIN の検索にはホストが一覧に出ず、LED は idle の表示に戻りました。
破棄がないと、LED は `flash3` のまま点灯し続けました。

## シリアルの上限

クラシック ESP32 の UART を 921600 ボー、8N1 で使うと、ボードからホストへの回線は 92.16 KB/s を運びます。
1 つのメッセージのコストは、ペイロードに、type のバイト、4 バイトの CRC、COBS のオーバーヘッド (254 バイトごとに 1 バイトと区切り文字) を加えたもので、
RX_MGMT の場合はさらにチャンネルと RSSI の 2 バイトです。Pia のペイロードは AES-GCM の暗号文なので圧縮できません。

| 通信 | 回線へのコスト |
|---|---|
| station のデータフレーム、ホスティング中 | RX_ETH としてのフレーム。AP フラグ 4 が設定されていない限り、40 バイトの RX_MGMT のコピーに 48 バイト (`POKELDN_ESP32_AP_FLAGS=4`) |
| station のデータフレーム、参加中 | RX_ETH としてのフレームのみ。station モードでは管理フレームだけを通す |
| 近くの LDN の広告 | アクションフレーム全体。ネットワークごとに毎秒約 10 件 |

送信キューは 384 件のメッセージを保持し、空きヒープが 64 KB を下回ると受け付けません。128 件のキューは、
スカーレットのホストの最初の連続送信でオーバーフローします (計測では 337 件のメッセージが落ちました)。回線の速度で動く本体は、
ヒープをその下限に保ちます (`heap_min` 63976、`queue_max` 95、`refused_heap` 219)。キューが満杯になる前に、ヒープが RX_ETH を拒否します。

上限を決めるのは USB ブリッジです。`tools/ldn/esp32_bench.py --port PORT --bauds

macOS で使った場合:

| ボーレート | 計測値 | メッセージ | 欠落 | 不正なチェックサム |
|---|---|---|---|---|
| 921600 | 91.7 KB/s | 1400 バイトのメッセージ 1429 件 | 0 | 0 |
| 1000000 | 99.4 KB/s | 1400 バイトのメッセージ 1429 件 | 0 | 0 |
| 1500000 | 149.1 KB/s | 1400 バイトのメッセージ 4286 件 | 0 | 0 |
| 1500000 | 140.2 KB/s | 100 バイトのメッセージ 20000 件 | 0 | 0 |
| 2000000、3000000 | ボードは新しいレートでは HELLO に一度も応答しない | | | |

921600 で CREDIT を使ったレジェンズ Z-A の席では、拒否されたアソシエーションはなく、最初のメッセージは 1.68 秒 (1500000 では 1.7 秒) でした。

### ホストからボードへのコマンドの欠落と CREDIT

本体から大量の通信が来ると、ホストのコマンドはハンドラに届く前に失われることがあります。7.5 秒でボードに 660 件の ETH_TX を渡したスカーレットの席では、
92 件しか数えられませんでした (`tx_eth + tx_eth_failed`)。残りには CCMP のパケット番号が使われず、`tx_eth_retried` は 0 でした。
各原因について、その対策なしで計測した結果と、ファームウェアの対策を以下に示します:

| 原因 | 対策なしで計測した結果 | ファームウェアの対策 |
|---|---|---|
| Wi-Fi タスクと同じコア 0 上の UART 割り込み | 上記の席 | reader タスクからドライバをインストールし、コア 1 で動かす |
| reader タスク内で、満杯の Wi-Fi キューを待つ ETH_TX。16 KB のリングが埋まり、FIFO がオーバーフローする | 1500000 での `esp32_bench.py --uplink 5000` (空のネットワークへの 5000 件のブロードキャスト ETH_TX): 369 から 429 件が欠落、`uart_fifo_ovf` 305、`wire_rx_bad` 169。921600 では欠落なし | CREDIT: どちらのレートでも 5000 件中 0 件の欠落 |
| FIFO が 120 バイトで排出される (`UART_FULL_THRESH_DEFAULT`)。1500000 では満杯から 53 µs | CREDIT を使ったスカーレットの席: 1901 件中約 210 件が欠落、`uart_fifo_ovf` 235 | しきい値 32 (`uart_set_rx_full_threshold`)、640 µs: 1691 件中 10 件、`uart_fifo_ovf` 0 |
| `uart_read_bytes` (IDF 6.1 `uart.c:1738`) は、`length` に達するまでリングの項目ごとにタイムアウトを待ち直す | 15 ms ごとの 21 バイトのコマンドが 461 ms 遅れて読まれた (`--trickle 5`)。スカーレットの席の `read_max_us` 311644 | 1 バイトを待ってから `uart_get_buffered_data_len` を使う: 20.3 ms |
| `uart_write_bytes` は満杯の TX リングでビジーループする (`uart.c:1662`)。書き込み側 (優先度 20) は reader (19) とコア 1 を共有する | スカーレットの大量通信で ETH_TX が最大 707 ms 保留された。`esp32_pair_bench.py AP STA --flood 0 --send 20 --bench`: `read_max_us` 7982767、74 件の送信が拒否 | フレームが収まるまで書き込み側がスリープする (`uart_get_tx_buffer_free_size`): 30382 µs、拒否なし ([スカーレット・バイオレット](sv.md#the-retail-acknowledgement-and-a-flood-of-retransmits)) |
| 32 バイトごとに `UART_DATA` イベントを、オーバーフローのイベントを運ぶ 64 件のキューに入れる (`uart.c:1369`、`1543`)。1500000 では 14 ms で満杯になる | 長いコマンドの間のオーバーフローが数えられないことがある | reader より上位のタスクが毎ティック排出する。`uart_events_full` |

ウィンドウを無視した場合 (`--uplink 5000 --no-flow`)、`uart_fifo_ovf` の 1 回ごとに 136.5 バイト、ほぼ FIFO 1 つ分が失われ、
`uart_events_full` は 0 のままです。満杯のリングは `UART_DATA` イベントを止めます。

ボードが一度 CREDIT を送ると、ホストは書き込み済みで未報告のデータを 8 KB 未満に抑えます (`esp32.FLOW_WINDOW`)。書き込みは writer スレッドから行われるため、
ランチャーの trio ループはキューに入れるだけです。512 件を超えるフレームがキューにあると、ETH_TX と RAW_TX は破棄されます (`Radio.tx_dropped`)。
ウィンドウが閉じている間に CREDIT が動かなければ、0.3 秒間変わらないカウントは回線上でバイトが失われたことを意味し、ホストはウィンドウを開き直します
(`Radio.flow_resyncs`)。カウントを送らないボードは忙しいとみなされ、5 秒の猶予が与えられます。無音だけを理由に再同期してはいけません。
忙しいリーダーは最大 0.7 秒保持するため、その時点で再同期すると 16 KB のリングに対して 16 KB が送信中になります。失われたと記録されたバイトは
失われたままです。損失が許す量を超える CREDIT はウィンドウを縮めます。CREDIT は送信キューの先頭に割り込みます (キューに 1 件まで) が、
スカーレットの席の RX_ETH 150 KB/s の後ろで、約 0.5 秒遅れて届きます。CREDIT を持たないボードはウィンドウを開かず、ホストは絞らずに書き込みます。
カウントは u32 です (`wire.c` の `s_consumed`)。ホストは自分のバイト数と突き合わせて展開するため、4 GiB を超えるストリームでもウィンドウは保たれます。
ボードは読み取った 1024 バイトごとに CREDIT を送ります (`wire.c` の `CREDIT_STEP`)。そのため CREDIT は、書き込みがまだ返っていない
1.5 KB の ETH_TX の一部を数えることがあります。ホストはそれを、書き込み済みのバイトに回線上のフレームを加えて数えます。拒否された場合、フレームの末尾は次のステップに届かず、
約 20 ms 後の idle の CREDIT までウィンドウが閉じたままになります。ESP32-S3 の USB 接続 (ファームウェア 1.6.2、Windows) では、
1514 バイトの ETH_TX を 3000 件連続で送ると、拒否された場合は 15.9 秒、数えられた場合は 8.5 秒かかりました (0.29 と 0.54 MB/s)。
Switch への TCP 転送は 0.31 から 0.52 MB/s になりました。ボードは 50 ms を超えるコマンド (`slow command`) と、
100 ms を超えるリーダーのターン (`reader held`) をログに出します。

アイドル時のカウントと、キューより先に送られる CREDIT を使うと、ボードはホストが渡したすべての ETH_TX を数えました。
228 回のボードのセッションで 520315 件中 520315 件です (クラシック ESP32 はファームウェア 1.2.0 まで、C3、C6 は 1.0.0)。
すべてのオーバーフローとワイヤーのカウンターは 0 で、繰り返されるアイドル時のカウントはすべて書き込み済みのバイト数と一致しました。
そのうち 6 セッションでは、ホストは毎秒 500 件を超える ETH_TX を書き込み、ボードからホストへの回線は 148 から 152 KB/s で動いていました。

アイドル時のカウントを導入する前のファームウェアは、オーバーフローを数えないままホストのコマンドをいくつか失いました。
921600 で CREDIT なしの場合は 2333 件中 6 件、1500000 で CREDIT をキューの末尾に置いた場合は 1691 件中 10 件でした。
どちらも `wire_rx_bad` は 1、`tx_eth_retried` は 0 です。欠落は、ボードからホストへの回線が上限にあるときのホストの最初の連続送信で起きました
(921600 で 1 秒に 91.4 KB)。そのファームウェアの書き込み側は、reader より上で満杯の TX リングをビジーループし、UART のイベントキューを排出するのは reader だけでした。
そのため、読み取りが飢餓状態にある間のオーバーフローは数えられませんでした。複数の失われたコマンドに対して `wire_rx_bad` が 1 つなのは、
連続した 1 区間の欠落と整合します。どのバッファがバイトを捨てたかは計測していません。それらのトレースには CREDIT がないためです。

HELLO は両方のカウントをリセットするため、ホストは何も送信中でなくなるまで HELLO を保留し、ボードの CREDIT 0 が届くまでその間ウィンドウを閉じたままにします。
セッションの途中の HELLO の後に絞らずに書き込んだホスト (スキャンは HELLO を 1 つ送ります。`EspFactory.create_monitor`) は、
0.5 秒間保持された模擬の 16 KB のリングを 76423 バイト超えました。これは `tests/test_esp32.py::test_a_hello_mid_session_does_not_open_the_window` で固定されています。
`tools/ldn/esp32_cmd_loss.py TRACE` はトレースを照合します。書き込まれた ETH_TX を `tx_eth + tx_eth_failed` と突き合わせ、
HELLO 以降に書き込まれたバイトを最後の CREDIT と突き合わせます。

### 送信のタイミング

落ち着いたスカーレットの席では、ETH_TX はドライバ内で平均 0.12 ms、最大 1.57 ms を使い、本体は参加側の 44 件のレコードをすべて、送信から 0.35 秒後に保持しました。

TX_DONE は、ボードと相手を区別します。大量通信中のスカーレットの席では、フレームは ETH_TX から TX 完了まで中央値 1.0 ms、最大 6.8 ms 待ち、
本体の無線は 1267 件中 1267 件を確認応答しました。TX_DONE は、落ち着いているときはボード時刻から 15 ms、
最悪の 1 秒では 446 ms (最大 590 ms) でホストに届きました。大量通信の下ではボードからホストへの回線が詰まります。
ボード時刻から最小の到着オフセットを引くと、回線上でのメッセージの遅れがわかります。

2 ボードのベンチ (`tools/ldn/esp32_pair_bench.py`、200 バイトの station フレーム) は、station のフレームをすべて届けます。
毎秒 20 件では 187 件中 187 件 (ETH_TX から TX 完了まで平均 1.6 ms、最大 10.7 ms)、access point から毎秒 100 件の 1200 バイトの
ブロードキャストがあるときは 1227 件中 1227 件でした (電波の約 96% を使用。平均 26.8 ms、最大 218 ms)。

計測の罠: スニッファーのボードの回線は、他のボードと同じくバーストで詰まります。そのため、報告されたフレームが電波に出てから 1 秒後に
ホストへ届くことがあります。1500000 で動かし、相手の確認応答によって配信時刻を測ってください。自分の回線が飽和しているとき、
他のボードのフレームの数え方は少なめになります。BENCH はペイロードを一度だけ埋めます。乱数で埋めると、回線のレートより遅くなりました。
ボードがアクセスポイントとして送る大量通信は 1 Mbit/s でブロードキャストされ、毎秒約 90 フレームを超えて電波を埋めます。

## 保持と受信の取りこぼし

### ファイアレッドの保持

ボードをアクセスポイントとした 5 回のファイアレッドのトレードで、1 トレードにつき 1 行です。本体はすべての
フレームを確認応答しました。待ち時間は ETH_TX から TX 完了までです。再送率は、スニッファーが再送ビットを付けて見た
データフレームの割合です。

| チャンネル | フレーム数 | 待ち時間の中央値 | 待ち時間 p99 | 待ち時間の最大 | 100 ms を超える保持 | 再送 AP / 本体 |
|---|---|---|---|---|---|---|
| 1 | 7489 | 1.24 ms | 116 ms | 261 ms | 5 | 13.3% / 12.8% |
| 6 | 13670 | 0.85 ms | 18 ms | 108 ms | 1 | 10.5% / 7.7% |
| 11 | 7069 | 0.86 ms | 9 ms | 46 ms | 0 | 15.0% / 5.7% |
| 1 | 7332 | 1.03 ms | 25 ms | 88 ms | 0 | 20.6% / 9.4% |
| 1、24 Mbit/s 固定 | 6892 | 0.73 ms | 69 ms | 185 ms | 5 | 2.8% / 14.3% |

ホストからボードまでは、中央値で 0.12 から 0.47 ms (ソケットから ETH_TX の書き込みまで) と 3.1 から 3.4 ms (ETH_TX からボードまで) を加えます。
100 ms を超える待ち時間はすべて先頭ブロッキング (head-of-line) です。本体が確認応答していない 1 つのフレームが 108 から 261 ms の間保持され、
その後ろのフレームはまとめて完了します (5 ms 以内に最大 10 件)。アクセスポイントのアクションフレームは送信を続けます。
スニッファーは、先頭フレームのコピーを 1 から 3 個、54 または 48 Mbit/s で捉え、その間に本体のフレームが挟まっています。
すべて電源管理ビットはクリアです。本体はそのチャンネルで起きたままです。チャンネルが保持を決め、再送率は決めません。

| 送信元 | 54 Mbit/s での初回送信 | 再送 |
|---|---|---|
| ボード (アクセスポイント) | 91 から 100% | 77 から 92% は 54 Mbit/s、その後 48、まれに 6 または 36 |
| 本体 | 92 から 99% | 48、36、24、18 から 1 Mbit/s まで |

アクセスポイントのフラグバイトのビット 3 から 5 は、そのデータレートを固定します (`esp_wifi_internal_set_fix_rate`。0 はレート制御)。
`POKELDN_ESP32_AP_FLAGS=0x28` は 24 Mbit/s に固定します。再送率は 2.8% に下がりましたが、保持は残りました。

| bits 3..5 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| レート (Mbit/s) | 1 | 11 | 6 | 12 | 24 | 36 | 54 |

ボードがコピーの間に約 100 ms 待つ原因はわかっていません。`tools/ldn/esp32_hold.py CAPTURE
TRACE` は各待ち時間を段階に分けます。TX 完了は長さで対応付けます (順不同で完了するため)。
`tools/ldn/esp32_hold_air.py` は、保持のたびにスニッファーが捉えたものを一覧にします。

### チャンネル

長い待ち時間はチャンネルの占有率に従います。これらのトレードを計測したとき、チャンネル 1 には本体のホーム用アクセスポイントもあり、
長い待ち時間の原因になっていました:

| チャンネル | トレード数 | 待ち時間 p99 | 待ち時間の最大 | 100 ms を超える保持があったトレード数 | ボードが取りこぼした、本体の初回コピー |
|---|---|---|---|---|---|
| 1 | 9 | 13.5 から 116 ms | 65 から 261 ms | 5 | 4.9 から 8.5% |
| 6 | 1 | 18 ms | 108 ms | 1 | |
| 11 | 4 | 9 から 11.2 ms | 19 から 46 ms | 0 | 3.3%、5.5%、6.0% |

チャンネル 11 では、同じ p90 の待ち時間 (4.5 ms) でも、ボードは同じ数だけ初回コピーを取りこぼします。違うのは末尾だけです
(20 ms を超えるフレームが 8 件と 9 件、対して 42 から 137 件)。受信の取りこぼしが保持を生んでいるわけではありません。
`config/host.local.toml` は `[host] channel` を受け取り、本体は 1、6、11 のいずれかのホストに参加します。

### ボードは聞こえない側

スニッフィング用のボードは、すべての ACK を 10 バイトの RX_SNIFF として保持します。ACK は受信者だけを示すため、
`tools/ldn/esp32_hold_air.py` は直前のデータのコピーと対応付けます。確認応答されて再送されたコピーは、送信者が ACK を取りこぼしたことを意味します。
チャンネル 1 での 1 回のファイアレッドのトレード (6744 フレーム):

| 送信元 | 初回コピー | 直後の ACK なし | 確認応答されて再送 |
|---|---|---|---|
| ボード | 6514 | 490 (7.5%) | 56 |
| 本体 | 4517 | 428 (9.5%) | 2 |

このトレードでは、ボードは本体より大幅に多くの ACK を取りこぼしました (56 対 2)。保持の間、ボードは本体のデータも ACK も聞けません。
保持されたフレームのコピーは約 40 ms 間隔で出ていき、本体からボード宛てのフレームの 42 から 66% に再送ビットが付きます
(セッション全体では 11 から 14%)。一方、スニッファーは両側を -19 から -21 dBm で聞き取っています。

本体の再送が、ボードの受信取りこぼしです。スニッファーとシーケンス番号で照合すると
(`tools/ldn/esp32_rx_copies.py HOST_TRACE SNIFF_TRACE --ap BSSID --sta MAC`)、本体が 2 回以上送ったフレームは、
再送ビット付きの 1 つのコピーとしてボードの RX_MGMT ヘッダーのコピーに届いていました (1027 件中 1008 件)。
同じシーケンス番号の早いコピーがないそのようなコピーは、ボードのトレースだけから取りこぼしを示します。
ボードは 54 と 48 Mbit/s、-20 dBm で、本体の初回コピーのうち 4.5 から 12.1% を取りこぼしました。取りこぼされた初回コピーは、
別の本体のフレームの後に続く割合が 37 から 52%、聞き取れたコピーでは 28 から 32% です。RSSI、レート、長さに差はありません。

### 2 ボードでの受信取りこぼし

`tools/ldn/esp32_pair_bench.py AP STA --flood 0 --burst N --send R` は、station のボードに 200 バイトのフレームを送らせ、
access point のヘッダーのコピーから、初回コピーを取りこぼしたフレームを数えます。どちらのボードも、ほかに電波の少ない状態で
access point として取りこぼします。station は -43 から -48 dBm で聞こえます。毎秒 20 から 100 フレームで 5.5 から 22.2%、
同一の 30 秒の実行でも 6.1 から 43.7% の幅があります。station の ACK 待ちの最長は、チャンネル 1 で 89 から 100 ms、チャンネル 11 で 8 から 22 ms です。
ヘッダーのコピーに受信時刻を入れると (2 番目の AP_START フラグバイトのビット 2、`rx_ctrl.timestamp`、RSSI の後の u32 の µs)、
取りこぼしは 102.4、51.2、25.6、1024 ms と 50 および 100 Hz でほぼ平坦になります。

| 条件 | 初回コピーの取りこぼし |
|---|---|
| station のレート (STA_JOIN のレートバイト、`--sta-rate N`)、チャンネル 11 | 54 Mbit/s OFDM 2.3 から 4.0%、6 Mbit/s OFDM 1.9 から 5.4%、1 Mbit/s DSSS 0.04 から 0.2% |
| station の送信電力 (`--sta-power`、0.25 dBm 単位)、54 Mbit/s | 78 (既定、19.5 dBm) 1.5 から 3.1%、28: 4.5 から 12.9%、12: 15.3 から 20.8%。access point はどの値でも -33 から -35 dBm と読む |
| チャンネル、54 Mbit/s | 1: 3.7 から 9.7%、3: 0.8%、5 から 9: 0.8 から 2.3%、11: 2.1 から 5.7%。13 は拒否された (`0x102`) |
| ESP-IDF のドライバ、チャンネル 3 | v5.5.5 5.0%、v6.1 4.1% |
| STA_JOIN のフラグ 1、全フレーム前に RTS | 2.1 から 2.3%、対して 4.6 から 4.8%。フラグ 2、再送前に RTS を送らない場合は 3.7 から 4.9% |

次の変更では結果は変わりません: 1000 TU ごとのビーコン (AP `0x40`)、プロミスキャス受信なし (AP `0x80`)、
ノイズフロアの確認なし (2 番目のバイトのビット 0。`g_pm+21` を消して libpp の `pm_noise_check` が早期に戻るようにする)、
またはその `NoiseTimerInterval` (`pp.o` の `.data`、u16 100) を 250 にすること (ビット 1)。静的受信バッファーを 25 個にすること
(`CONFIG_ESP_WIFI_STATIC_RX_BUFFER_NUM`、既定は 16 個)、240 MHz、`CONFIG_ESP_WIFI_EXTRA_IRAM_OPT=y`、
access point の送信電力を 19.5、10、3.5 dBm のいずれにすること、Bluetooth を切った Switch がスリープしていること。
取りこぼしは信号の余裕ではなく、変調方式とチャンネルに従います。6 Mbit/s は 54 とほぼ同じ頻度で取りこぼし、DSSS はほとんど取りこぼしません。
2 つのドライバは `libphy.a` と `hal_mac_rx.o` をバイト単位で共有し、同じレジスタ書き込み、受信割り込み、バッファーの再利用、
送信完了のコードを使います。v6.1 は、フレームごとの経路に `wifi_assert` を追加し、`wpa_ap_join` に 1 つの構造体を渡します
(v5.5.5 は 9 個の引数を渡す)。

チャンネル 1 と 11 は、毎秒 44 から 107 件の近隣フレームで 8.7 から 13% 占有されており、チャンネル 3 から 9 は 0.3 から 1.7%、
ノイズフロアはすべて -96 dBm でした (`tools/ldn/esp32_census.py`)。access point 自身のセンサス (2 番目のフラグバイト `0x10`) は、
取りこぼしの 3 ms 前に近隣フレームを 13.1% の確率で見つけ、聞き取れたコピーの前では 11.0% でした。取りこぼしの 2 ms または 5 ms 前に
プローブ要求が来た割合は 0.0% または 1.1% で、聞き取れたコピーでは 0.0% または 0.1% でした。取りこぼしの 85 から 91% は
access point に痕跡を残さず、FCS の失敗すら出ませんでした。

ボードは、自分の送信の直後にくるフレームを最も頻繁に取りこぼします。ファイアレッドの本体は、ボードのビーコンが ERP バイト 0 を持つにもかかわらず、
すべてのデータフレームを RTS/CTS の後ろに送ります。データは、ボードの 6 Mbit/s の CTS の 60 µs 後 (44 µs と SIFS) に続き、
1 つのトレードで 4034 件中 329 件が取りこぼされました。ベンチでは、54 Mbit/s で 4 個のバーストを送ると、
1 個目のフレームは 0.5 から 3.0%、2 個目は 2.4 から 4.6%、3 個目は 4.7 から 8.7% (通常最も多い)、4 個目は 2.6 から 7.6% でした。

ESP32 の station は、すべての再送を、データの 128 µs 前の RTS の後ろに送ります (`lmacConfMib` +42、RTS 前の再送回数 0、RTS のしきい値 2346 は +22)。
`esp_wifi_internal_get_rts` と `_set_rts` は、どちらもパックされた `{u16 threshold, u8 retries before RTS, u8 long, u8 short}` を通じてアクセスします。
ACK と CTS のレートテーブルは `0x3ff73400`..`0x3ff7341c` にあります。90 秒間に access point が聞いた 8527 件の RTS のうち、
311 件 (3.6%) には応答があり、CTS の後のデータは取りこぼされました。上の数字はそれらを除いています。
ドライバは再送をソフトウェアで行います。`lmacRetryTxFrame` (libpp の `lmac.o`) は、`lmacConfMib` の上限 (short +21、long +20、既定は 32) まで
`lmacTxFrame` を通して再送します。その上限は `esp_wifi_internal_set_retry_counter(short, long)` で設定されます。
access point から毎秒 100 件のユニキャストフレーム (`--flood 100 --unicast`) を送ると、フレームの待ち時間は最大 24 ms でした。
2 ボードでは 100 ms の保持を再現できません。

station ボードの遅い送信 (3 ms 超、`--done-out`) は、ビーコンの間隔に関係なく、102.4 ms の周期の 20 分の 2 の区間に集まります
(29 から 43%、対して 2 から 12%)。周期の計算には `tools/ldn/esp32_bench_fold.py FILE PERIOD_US` を使います。
`tools/ldn/esp32_bench_drift.py` は、両ボードのクロックをホストと比べ (600 秒間で 1.9 ppm の差)、折り畳みの周期を走査します。

## ユーザー空間のスタック

`pokeldn.ldn.userspace_ip` は、背後にカーネルのないインターフェース向けに、IPv4、UDP、ARP をホストのプロセス内で扱います。
スタックは、ポートが存在する間、呼び出し元のインターフェース名で登録されます (参加側は `ldnclient`、access point は `ldn-tap`)。
`userspace_ip.lookup(name)` はカーネルのインターフェースに対して None を返します。ランチャーはこれで経路を選びます。

- アドレスと近隣情報は、LDN ライブラリの `add_address` と `add_neighbor` から得ます。受信したフレームの送信元アドレスは、近隣として学習されます。
- `.255` で終わる宛先、またはブロードキャストアドレスと等しい宛先は `ff:ff:ff:ff:ff:ff` に送られます。近隣のエントリがないユニキャストの宛先は、ARP 要求を送り、データグラムを破棄します。スタック自身のアドレスへの ARP 要求には応答します。
- 1472 バイトを超えるデータグラムは分割されます。受信した断片は再構築されます (タイムアウト 5 秒)。UDP のチェックサムは計算されます。
- `udp_socket(port)` は、インターフェースにバインドされた UDP ソケットの代わりになります。`packet_socket()` は、IPv4 のイーサネットフレームをそのまま配送する `AF_PACKET` ソケットの代わりになります。どちらも、キューに入ったデータグラムごとに 1 バイトを流すソケットペアを使うため、`select` と `trio.lowlevel.wait_readable` は macOS、Linux、Windows で動きます。TCP のソケットペアは Nagle のバッファリングを無効にするため、準備完了のバイトが reader にすぐ届きます。
- ボードのフレームは、ランチャー自身の trio ループ内の trio タスクを通ってスタックに届きます。そのループ内でブロッキングする `select` があると、それらが飢え、各データグラムは丸ごとタイムアウトまで待たされます。`trio.move_on_after` の下で `trio.lowlevel.wait_readable` を使って待ってください。スカーレットの参加側が `select(0.05)` でブロックすると、50 ms ごとに 1 件のメッセージしか処理せず、その間に本体はレコードを再送します (計測では 50 から 70 秒)。

## ボードの LED とボタン

LED のパターンは、クラシック ESP32 のボードでは GPIO2 を、S3 では GPIO21 を反転させて駆動します (XIAO ESP32S3 の黄色のユーザー LED。arduino-esp32 の XIAO_ESP32S3 バリアントの `LED_BUILTIN`)。C6 では GPIO15 を反転させて駆動します (XIAO ESP32C6 の黄色の LED)。C3 のファームウェアは LED のピンに触れません。BOOT のトレースマーカーは、クラシック ESP32 と S3 では GPIO0、C3 と C6 では GPIO9 を使います。

ELEGOO ESP-32 Type-C ボード (CP2102、ESP32-D0WD-V3) には、Espressif のモジュール名のない無印のモジュールが、PCB アンテナ付きで載っています:

| 部品 | 接続先 | 制御可否 |
|---|---|---|
| 赤い LED | 3.3 V ライン | 不可。ボードに電源がある間は常に点灯 |
| 青い LED | GPIO2、high で点灯 | 可 |
| EN ボタン | チップのリセット | 不可 |
| BOOT ボタン | GPIO0 | 可。押すたびに BUTTON (`0x8E`) を送り、LED を点滅させ、画面を起こす |

GPIO2 と GPIO0 はストラッピングピンです (ダウンロードモードのためにリセット時に low かフローティング)。ファームウェアは起動後にだけ GPIO2 を駆動します。
ROM ブートローダーからは、GPIO2 の IO_MUX (`0x3FF49040`、`MCU_SEL` 2)、出力選択 (`0x3FF44538` = `0x100`)、
`GPIO_ENABLE_W1TS`、`GPIO_OUT_W1TS` (ビット 2) への書き込みで LED が点灯します。

ファームウェアは、コア 1 の優先度 1 のタスクから 10 ms ごとに、LEDC PWM (13 ビット、5 kHz) で青い LED を駆動します。
デューティは、レベルの 2.2 乗です。見た目を変えるときは 150 ms かけて切り替わります。

| パターン | id | 既定の周期 | 形状 |
|---|---|---|---|
| auto | 0 | | 下表のモードごとの見た目 |
| off、on | 1、2 | | |
| breathe | 3 | 3000 ms | 持ち上がったコサイン |
| blink | 4 | 1000 ms | 周期の半分だけ点灯。80 ms のなめらかな縁 |
| flash3 | 5 | 1000 ms | 周期の最初の 60% の間に 3 回点滅 |
| ramp-up、ramp-down | 6、7 | 1000 ms | 1 回だけ、3 次のイーズイン・イーズアウトで動き、その後保持 |
| pulse | 8 | 1200 ms | 素早く膨らみ、ゆっくり 3 次で下がる |

| モード | 自動の見た目 |
|---|---|
| boot | 1 回の pulse、900 ms |
| idle | breathe、暗め、4 秒 |
| 本体に参加中 | 速い blink、250 ms |
| ホスト中、station なし | breathe、明るめ、1.5 秒 |
| 参加済み、または station をホスト中 | on、暗め |
| スニッフィング | off |

受信または完了したすべてのフレームで、LED の上に短く明滅します。
参加の失敗 (LINK `0xFFFF`、`0xFFFE`)、鍵の拒否、ボードからホストへのメッセージの破棄、ホストのコマンドの欠落があると、
flash3 が 1.5 秒間再生されます。トレードまたはふしぎなおくりもの配信の完了は、800 ms かけて全点灯まで上がり、
3 秒間保持されます (`pokeldn.ldn.show_done`)。ソード・シールドの配布ホストは、読み戻しのないビーコンなので、そのような瞬間はありません。
`tools/ldn/esp32_led.py --port PORT PATTERN` で見た目を設定します。`--demo` は各見た目を表示します。

## 画面

I2C 接続の SSD1306 128x64 の 1 ビット OLED は任意です。ユーザーの報告では、同じファームウェアで 128x64 の SSD1315 と SSD1309 の
モジュールも動作しています。起動時、ファームウェアは 0x3C、次に 0x3D を調べます。どちらも応答しない場合は、ピンを解放して何も開始しません。
画面がある場合は、最後のコアの優先度 1 のタスクが 50 ms ごとにフレームを描画し、400 kHz で送信します (1031 バイト、約 23 ms)。

| ターゲット | SDA | SCL | ボードのピン |
|---|---|---|---|
| ESP32 | GPIO21 | GPIO22 | DevKit V1 D21, D22 |
| ESP32-S3 | GPIO8 | GPIO9 | |
| ESP32-C3 | GPIO6 | GPIO7 | XIAO D4, D5 |
| ESP32-C3 | GPIO5 | GPIO6 | 0.42 インチ OLED ボード自身の 72x40 画面。2 番目に調べる |
| ESP32-C6 | GPIO22 | GPIO23 | XIAO D4, D5 |

VCC は 3V3 に、GND は GND に接続します。一般的な 4 ピンのモジュール (GND、VCC、SCL、SDA) は、独自の 3.3 V レギュレーターと、
SCL と SDA の 4.7 k プルアップを持ちます。アドレス抵抗で 0x3C (シルク印刷 0x78) か 0x3D (0x7A) を選びます。
そのパネルはセグメント 127 を列 1 に、COM0 を行 63 に割り当てるため、ファームウェアはセグメントの再マップ (`A1`)、
COM スキャンの反転 (`C8`)、代替の COM ピン (`DA 12`) を設定します。

ESP32-C3 の 0.42 インチ OLED ボード (ABRobot など別名でも販売) は、GPIO5 と GPIO6 に 72x40 のパネルを載せ、GPIO8 には LED があります。
ファームウェアはこれに触れません。128x64 の INIT で駆動すると、パネルはフレームの列 30..101 と行 24..63 を表示します。
これは反転スキャンの最後の 40 行です。列はベンダーの例の x オフセット 30 です。行は、行 12 に描いたアイドル時の画面の写真から読み取りました。
最初に見えた行は「pokeldn」の文字の最下行で、フレームの行 23 です。シーンの 1 ピクセルのずれは、どちら向きにもありえます。
ベンダーの例の y オフセット 12 は u8g2 のテキストのベースラインです。これらのピンで画面が見つかった場合は、その窓にコンパクトなシーンを描きます。
画面上の 1 行は最大 12 文字で、スプライトは半分のサイズになり、2x2 ブロックのうち 2 つが点灯しているとき、ピクセルが点灯します。
`tools/ldn/screen_preview.py --panel 72x40` でそれらを描画します。

ホストのコマンドがない場合、画面は無線機の状態を表示します: idle、参加中、ホスト中 (モンスターボールの周りのリング)、
リンク済み。リンク済みの場合は、本体とモンスターボールの間のケーブルが、無線機が各方向に数えたフレームごとに 1 桁を運び、
最大 70 ms に 1 回です。合計は下記のとおりです。

OLED の画素は点灯している時間に応じて劣化するため、画面は静止画の表示時間を制限します。
無線機が参加中、参加済み、ホスト中、スニッフィング中、トレードまたは配布のアニメーションの再生中は全輝度です。
これらの最後から 60 秒間、そして DISPLAY コマンド、HELLO、BOOT の押下の後の 60 秒間も全輝度です。その後、画面は
コントラスト 1、2+2 クロックのプリチャージ (`81 01 D9 22`) に暗くなり、600 秒後に消灯します (`AE`)。パネルは RAM を保持します。
次の上記のイベントは、次のフレームで点灯させます。そのフレームは `AF` の前に送られます。
アイドル時のシーンは、2x2 の正方形の周りを 60 秒ごとに 2 ピクセル動きます。`scene_draw` は輝度を返し、`tests/test_esp32_screen.py` がタイミングを保持します。

4 ピンの 0.96 インチモジュールのコントラスト、プリチャージ、VCOMH の設定。INIT の `81 CF D9 F1 DB 40` から目視で判断:

| 設定 | 見え方 |
|---|---|
| contrast `80` | 変化なし |
| contrast `40`、`20` | それぞれ一段階暗くなる |
| contrast `10` から `01` まで | これ以上の変化なし、読める |
| contrast `00` | 黒 |
| contrast `01`、pre-charge `22` | さらに暗くなるが、読める。安定 |
| contrast `01`、pre-charge `11` | ちらつく。VCOMH `20` または `00` では読めない |
| contrast `01`、VCOMH `00` | 正常に見え、安定 |

DISPLAY (`0x0E`) は、次のいずれかの op を運びます:

| op | レイアウト |
|---|---|
| `0` SHOW | u8 の show、u16 の保持秒数 (0 は次の show まで)、title、NUL、line、NUL。各テキストは最大 21 文字の ASCII |
| `1` SPRITE | u8 のスロット (0 は自分、1 は相手、2 は配布)、u8 の幅 <= 64、u8 の高さ <= 64、`(width + 7) / 8` バイトの行を MSB から。幅 0 はスロットを空にする |
| `2` LOBBY | u8 のスター数 (0..7、0 はなし)、u8 の参加数、u8 の席数 (1..3、参加数以上)、title、NUL、name、NUL、Link Code、NUL。ロビーの show を開始する |
| `3` JOINED | u8 の参加数。ロビーの席数まで。ロビーの show がなければ拒否される |

| show | id | 描画内容 |
|---|---|---|
| auto | 0 | 無線機の状態 |
| trade | 1 | 右半分にスロット 0、左に \"offering\" とその行、下にケーブル |
| traded | 2 | スロット 0 が点滅してボールに戻り、ボールが去り (2.1 秒)、保持まで (最低 3.1 秒) パケットが行き交い、ボールが到着して開く (1.6 秒)。その後スロット 1 に \"received\" とその行を 10 秒間表示する。\"offering\" と同様、ボード側の表示 |
| gift | 3 | スロット 2 を持つふしぎなカード (空のときは贈り物の箱)、その横に行 |
| gifted | 4 | カードが右に去り、その後 \"delivered!\" |
| arrived | 5 | シーンなし。まだ待機中の traded の show があれば、そのボールをここで入れる |
| lobby | LOBBY | 右半分にスロット 0、左の上に title、その後に name、スター、\"joined/seats joined\"、コード。72x40 ではテキスト行のみ |

traded または gifted の show の前に送られた trade や gift の show は、それが終わるまで待ちます。trade、gift、lobby の show は、
動作中だった無線機が idle に戻ったときに終わります。無線機が開始する前に送られたものは残ります。
HELLO は画面を、空のスロットを持つ無線機の状態にリセットします。idle のシーンは、ファームウェアのバージョンで終わります。

`pokeldn.app.screen` はランチャー側です: `offer`、`received`、`arrived`、`gift`、`delivered`、`lobby`、`joined` はすぐに戻り、
1 つのスレッドで順番に実行されます。ホストされている マックスレイド、ダイマックスアドベンチャー、テラレイド は、ロビーを表示し
(そのボス。キョダイマックスの形を含むか、伝説のポケモン)、中の本体が変わると `joined` を送ります。どのランチャーも、
トレードの最後のステップで、本体のトレードアニメーションの前に `received` を呼びます。その保持時間は、そのステップから
受け取ったポケモンが本体に現れるまでの、タイトルごとに計測された時間です。そこから 2.5 秒を引き、ボールが本体のものと同時に開くようにします:

| タイトル | 開始点 | 本体に受け取ったポケモンが現れるまで | アニメーション後の最初のメッセージ |
|---|---|---|---|
| ファイアレッド・リーフグリーン | START_TRADE | 22.7 秒 | READY_FINISH_TRADE ([ファイアレッドのリンク](frlg_link.md)) |
| Let's Go ピカチュウ・イーブイ | ステップ `0e` | 15.3 秒 | type 4 のペイロード ([Let's Go のセッション](lgpe_session.md#the-trade-animation)) |
| ソード・シールド | 最後の syncCommand 40 | 15.0 秒 | なし ([ソード・シールドのトレード](swsh_trade.md#the-trade-animation)) |
| BD/SP | `tradeState` 5 | 18.6 秒 | なし ([BDSP のトレード](bdsp_trade.md#the-completed-trade)) |
| LEGENDS アルセウス | `01 0e` | 28.5 秒 | ボックスのメッセージ `00 02` ([LEGENDS アルセウス](pla.md#the-completed-trade)) |
| スカーレット・バイオレット | `8001010e` | 19.8 秒 | なし ([スカーレット・バイオレット](sv.md#the-trade)) |
| レジェンズ Z-A | 4 番目のステップ | 26.2 秒 | 次の `01 01` のプレビュー ([レジェンズ Z-A](za.md#a-trade-with-a-retail-console)) |

各時間は 1 回のセッションで手作業で計測したもので、最大 2 秒遅れることがあります。本体がアニメーションの後にメッセージを送る場合は、
ランチャーはそこで `arrived` を呼びます。レコードは PKHeX ヘルパーを通り、全国図鑑番号と名前が設定されます。
スプライトは、種族番号 386 までは PokeAPI のファイアレッド・リーフグリーン版 (64x64)、それ以降は既定のものを使います。
アプリのスプライトキャッシュとダウンロード設定を通します。スプライトは 1 ピクセルあたり 1 ビットに変換されます:

1. 見える画素に切り抜かれ、64 より大きい場合 (カードでは 40) は、面積で縮小されます。各出力画素は、その範囲の暗い方の 3 分の 1 の値を取ります。
2. 輝度がしきい値を超える画素が点灯します。しきい値は、見える画素のうち最も暗い 8 分の 1 の輝度に 6 を足したもので、20 から 60 の範囲に収められます。そのため輪郭は暗くなり、暗いポケモンの体は点灯したままになります。
3. 点灯している画素が、その最も明るい 4 近傍より 40 以上低く、かつ 0.72 倍未満のとき、暗くします。これが内側の線です。

`tools/ldn/esp32_screen.py --port PORT` は、無線通信なしで、ボード上でトレードと配布を再生します。
`tools/ldn/screen_preview.py OUT.gif` は、ホスト用に `scene.c` と `screen.c` をビルドし、スクリプト化されたセッションをオフラインで描画します。

### E32R40T ボード

E32R40T (4.0 インチ ESP32-32E ディスプレイとして販売) は、SPI 接続の 480x320 ST7796S パネルを持つクラシック ESP32 です。
ファームウェアは別ビルドで、`idf.py` の環境で `POKELDN_DISPLAY=E32R40T` を設定します (既定は `OLED`)。リリースイメージは OLED ビルドです。

| 信号 | GPIO |
|---|---|
| CS, DC, SCK, MOSI | 15, 2, 14, 13 |
| バックライト、high で点灯 | 27 |
| RGB LED、low で点灯: 赤、緑、青 | 22, 16, 17 |

パネルは、同じ 128x64 のフレームを中央に 3 倍 (384x192) で表示します。点灯した画素は白地に黒で描かれ、40 MHz の SPI で送られます。
最後のフレームと同じフレームは再送しません。GPIO2 はパネルの DC なので、ボードの LED は GPIO17 の青い LED になります。
パネルには減光の段階がないため、OLED が消えるときにバックライトも消えます。

## ビルドと書き込み

ファームウェアのリリースは、`firmware/esp32/version.txt` の `major.minor.patch` を使い、ESP32、S3、C3、C6 で共有します。
リリースをビルドする前に、修正では patch、互換性のある機能追加では minor、非互換な変更では major を上げます。
ESP-IDF はバージョンをアプリケーションの記述子に埋め込みます。INFO は `version=...` として報告し、Boards ページは
ボードの確認が戻ると、それを表示します。バージョンのないビルドは `version unknown` と表示されますが、
シリアルプロトコルが一致すれば使えます。シリアルプロトコルとデスクトップアプリのバージョンは独立しています。
ワイヤーの契約が変わったときにプロトコル番号を上げます。

ESP-IDF v6.1 (タグ `v6.1`、コミット `fff9895c82d744c7237be8847347bdd1b07c6643`) は 4 つのターゲットすべてをビルドします。
`install.sh esp32,esp32s3,esp32c3,esp32c6` でツールをインストールしてから、IDF の環境を有効にします。

    cd firmware/esp32
    idf.py set-target esp32   # esp32s3, esp32c3 or esp32c6 for those chips
    idf.py build
    idf.py -p <port> flash

コンソール出力は無効です (`CONFIG_ESP_CONSOLE_NONE`、`CONFIG_ESP_CONSOLE_SECONDARY_NONE`)。クラシック ESP32 では UART0 がホストのリンクなので、
ファームウェアは GPIO1 と GPIO3 を自分で割り当てます (`uart_set_pin`)。S3 では、ファームウェアは USB Serial/JTAG ドライバをコア 1 にインストールします。
C3 と C6 はコア 0 にインストールします。

デスクトップアプリは、書き込みに使うのと同じ接続で esptool を使ってチップを判別します。書き込みの前に、統合イメージのブートローダーを、
チップのフラッシュオフセット (ESP32: `0x1000`、S3、C3、C6: `0x0`) で検証します。カスタムイメージも対象です。
esptool 5.4.0 の `write_flash` は、統合イメージがパディングで始まると、チップの確認をスキップすることがあります。
USB ブリッジの ID からファームウェアを選んではいけません。4 つのイメージすべてのパッケージングについては [デスクトップのビルド](gui.md) で扱っています。

### Bluetooth

`POKELDN_BLE=1` を付けたビルドは、USB のシリアルがないホスト向けに、ホストのリンクを Bluetooth LE でも運びます。
iPhone のアプリは、Apple の MFi アクセサリープログラムなしでは USB のシリアルデバイスを開けませんが、CoreBluetooth はそのようなものを必要としません。
その場合、ボードは電源としてだけ USB が必要です。

    POKELDN_BLE=1 idf.py -B ../../scratchpad/esp/build-ble \
        -D SDKCONFIG=../../scratchpad/esp/build-ble/sdkconfig \
        -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.defaults.ble" build

ボードはサービス `7a1e0101-5d2c-4c3e-9f4b-504f4b454c44` で `POKELDN-RADIO` として広告します。ホストは COBS のストリームを
`...0102` に書き込み (応答なし書き込み)、ボードは自分の分を `...0103` で通知します。セントラルが `...0103` を購読している間は、
ワイヤーの読み書きはそこで行われ、ケーブルからは何も出なくなります。購読されていなければ、ケーブルはこれまでどおりリンクを運びます。
フレーミング、CRC、CREDIT は変わりません。ボードは 15 ms の接続間隔、2M PHY、247 バイトの MTU を要求します。
その HELLO のテキストは `link=ble` で終わり、Board ページはこれを Bluetooth の無線ファームウェアとして表示します。
`POKELDN_RADIO=esp32:ble` (または `esp32:ble:NAME`) で、どのランチャーからでも開けます (`pokeldn/ldn/esp32_ble.py`、bleak)。

クラシック ESP32 では、デュアルモードのコントローラーが空きヒープを 32 KB 残し、ワイヤーの 64 KB の下限を下回っていました。
そのため `wire_send` はすべてのメッセージを拒否し、ホストに届いたのは CREDIT だけでした (CREDIT は下限を迂回します)。
`sdkconfig.defaults.ble` は BLE 専用のコントローラーを使い、静的 Wi-Fi の RX バッファーを 25 個ではなく 10 個にします。
`ble.c` はクラシック Bluetooth のメモリを解放し、受信バッファーを 10 KB (FLOW_WINDOW と 1 フレーム分) に設定します。
最後のその段階の前は空きヒープが 60 KB あり、その後も十分な量が残ります。Mac から計測すると、接続と HELLO は 1.3 から 1.7 秒、
HELLO の往復は 1 回 63 ms (200 回連続)、接続間隔およそ 2 回分でした。

無線機は、Wi-Fi と Bluetooth でアンテナを共有します (ソフトウェアの共存)。そのため、BLE の接続イベントのたびに、
本体のチャンネルの電波時間が使われます。それがリンクのループにどれだけの影響を与えるかは計測していません。

Mac からの BLE での FireRed ホスト: 本体は参加し、「POKELDN の応答を待っています」の表示で止まりました。その間、ホストは ACK 待ちのフレームを 6 個後ろに保持していました。
電波は清潔でした (`tx_eth_failed=0`)。問題はホストとのリンクでした: `wire_dropped=7056`、`refused_queue=3112`、`queue_max=384`、`heap_min=29924`。
ボードのホスト宛てのメッセージは、通知が運べる量を超え、384 件のキューがオーバーフローしました。そのうち 8031 件は TX_DONE で、
ホストが読まない診断用のものでした。BLE 経由では、ボードは TX_DONE を送らず、キューにさらにメッセージがあるとき、書き込み側は複数のフレームを 1 回の通知にまとめます。
次の実行では何も落ちず (`queue_max=26`)、本体は 1 秒あたり 1 フレーム未満の速さで部屋に到達しました。15 から 30 ms の間隔では HELLO の往復が 63 ms かかり、
15 ms (最小と最大が一致する、Apple のアクセサリールールにおける唯一の例外) では 32 ms になりました。Mac から BLE で行った FireRed のホストとのトレードは、
プレイヤーが「ずっと良い」と評したペースで完了し、その後、本体はきれいに退出しました。

BLE 経由の FireRed の参加側は、RFU のハンドシェイクを終えられませんでした。本体には 2318-0013 が表示されました。
27 バイトのリンク層パケットでは、ボードは毎秒約 217 フレームを聞き取り、ホストは 6522 件中 757 件を受け取りました。
データ長拡張 (251 バイトのパケット) でベンチは 14.1 から 28.1 KB/s に倍増し、次の参加側の実行では 796 件中 776 件の RX_ETH が届きました。
それでも参加側は、24 フレームのウィンドウがほぼ埋まった本体の 30 に対して、毎秒 5 T スロットしか送れず、
ボードはヒープの下限で 581323 件のメッセージを拒否しました (`heap_min=30296`)。クラシック ESP32 は Bluetooth 4.2 の部品で、2M PHY はありません。

XIAO ESP32C6 (Bluetooth 5) では、同じビルドで 33.6 KB/s のベンチになり、HELLO の往復は 62 ms でした。また、Mac から BLE で完了した
FireRed の参加側のトレードでは、参加側は本体と同じペースで進みました (それぞれ毎秒 18 T スロット)。プレイヤーの話では、ケーブルよりは遅いとのことです。
C6 の BLE イメージは、1 MB のアプリパーティションを 13 KB 以内まで使います。ボードはその名前だけを広告します。
iOS アプリはサービスのフィルタなしでスキャンし、`POKELDN-RADIO` に一致させます。

接続時のみ 15 ms を要求した XIAO ESP32C6 は、30 ms で動きました (iPhone 13 Pro から HELLO 1 回 61.5 ms。ファイアレッドの部屋は遅々として進まず)。
セントラルが購読したあとに改めて要求すると、15 ms になりました (STATUS の `ble_itvl_us=15000`、HELLO 1 回 32.1 ms)。
接続時の要求は、セントラルがまだサービスを探している間に届きます。

macOS では、責任アプリに Bluetooth の許可がないプロセスで bleak が中断します (SIGABRT)。
`open -n -a Terminal FILE.command` で開始したスクリプトは、Terminal の許可の下で動きます。

### USB ホストのリンク

S3、C3、C6 は、USB Serial/JTAG 上で同じ COBS、CRC、CREDIT のプロトコルを使います。どちらのドライバのリングも 16 KB です。
IDF v6.1 の `usb_serial_jtag_write_bytes` は、フレーム全体をキューに入れるか、タイムアウト後にゼロを返します。
書き込み側は 20 ms 待ちで再試行し、500 ms 進まなければメッセージを破棄として数えます。`write_max_us` にはこの待ちが含まれます。
reader は 20 ms のタイムアウトで、利用可能なバイトを取ります。このパスでは UART のオーバーフローとフレーミングのカウンターは 0 のままで、
USB の欠落は計測しません。受信割り込みは、16 KB の RX リングが満杯のとき 64 バイトのパケットを破棄し、何も数えません
(`usb_serial_jtag.c:144` は `xRingbufferSendFromISR` の結果を無視します)。CREDIT のウィンドウがリングの満杯を防ぎます。
そこでの欠落は、ボードの最後の CREDIT を超えて書き込まれたバイトとしてだけ現れます。
`POKELDN_ESP32_BAUD` は全ターゲットで受け付けられ、クラシック ESP32 の回線レートだけを変えます。

PC は 1 秒のシリアル書き込みタイムアウトを設定します。書き込みが失敗または不足すると、読み取りエラーと同じボード喪失のハンドラを通じて
セッションが終わります。失敗したフレームは書き込み済みとして数えません。レートの交渉でも、制限のない `flush()` を呼ぶ代わりに、
OS の出力キューの待ちに上限を設けます。初期の HELLO とレートの交渉のあと、有効なボードのフレームが 1 秒ない場合は STATUS の問い合わせをキューに入れます。
3 秒間無音が続くとセッションは USB エラーで終わり、ボードを抜いて挿し直すよう求めます。アイドル中のファームウェアは CREDIT を繰り返します。
繰り返さない古いファームウェアは、STATUS に応答できます。不正なバイトは生存の証拠として数えません。
繰り返される CREDIT は回線で失われたバイトを回復できますが、完全に無音のボードは、より多くの書き込みを受け入れさせるために繰り返し再同期されることはありません。

本体なしで長いアップロードを再現するには、ネイティブ USB ポートと空の AP を使って、2 時間のホストからボードへのソークを実行します
(`COM5` はボードのポートに置き換えてください):

```sh
./.venv/bin/python tools/ldn/esp32_bench.py --port COM5 --bauds 921600 \
    --soak 7200 --size 1400 --rate 460000
```

この実行は CREDIT のフロー制御で 1400 バイトのイーサネットフレームを送り、イーサネットのバイト数を毎秒 460000 にすることを目標とします。
5 秒ごとに、累積のフレーム数、バイト数、CREDIT、ボードの STATUS を表示します。ボードまたはホストが追いつけなければ、実際のレートは低くなることがあります。
`--rate 0` はペース制御を外します。USB のソークでは単一のボーレートを使ってください。ネイティブ USB はボーレートの値を無視します。
最終的なボードのカウントは Wi-Fi の送信失敗を含むので、確認するのはコマンドハンドラへの配送であり、電波での受信ではありません。
USB の失敗や最終フレーム数の不一致は、0 以外の終了コードで終わります。端末の出力は保存してください。
`POKELDN_ESP32_TRACE` を使うと、ワイヤーのメッセージも追加で記録できますが、数時間に及ぶ全ペイロードのトレースは数 GB になることがあります。
ソークが成功したら、報告された 54 分の失敗を超えて続く、本体の完全なアップロードを実行してください。
空の AP のテストでは、本体の確認応答や Wi-Fi の全負荷は再現されません。

USB はライターのエンコードより速く排出するため、回線の全速のボードからホストへのストリームでは、ライターは決してスリープしません。
USB ターゲットでは reader の優先度が 21 で、ライター (20) より上で動きます。UART のビルドでは 19 のままにします。回線レートでライターがスリープするためです。
XIAO ESP32S3 で、884 KB/s の BENCH 中に 15 ms ごとに 14 バイトの ETH_TX を送った場合 (`esp32_bench.py --trickle 300 --flood`):

| reader の優先度 | `read_max_us` | 数えた ETH_TX |
|---|---|---|
| 19、ライターより下 | 53951079 | 3055 件中 785 件。残りはホストの 512 フレームのキューで破棄 |
| 21、ライターより上 | 20493 | 3052 件中 3052 件 |

BENCH は 884 KB/s のままで、5000 件のアップリンク ETH_TX は 15.4 秒かかり (13.5 秒に対して)、欠落はありませんでした。
優先度を上げた状態での FireRed の参加側のトレードでは、ETH_TX 5629 件中 5629 件を数えました。XIAO ESP32C6 の優先度 21 では、
820.6 KB/s の BENCH 中に 20 ms ごとに送った 14 バイトの ETH_TX は、読み取りの間隔が最大 19997 us で、221 件中 221 件を数えました。
FireRed のホストと Legends Z-A のホストのトレードは、本体でエラーなく続きました。

## 実行

`POKELDN_RADIO=esp32:<port>` は、すべてのランチャーの `ldn` 呼び出しをボードに向けます。`esp32:auto` は、存在する唯一の USB シリアルポート
(`/dev/cu.usbserial-*`、`/dev/cu.SLAB_USBtoUART*`、`/dev/cu.wchusbserial*`、`/dev/cu.usbmodem*`、`/dev/ttyUSB*`、`/dev/ttyACM*`、
Windows では USB COM ポート) を使います。複数ある場合は、どれかを選ぶことを拒否します。ポートを開くとボードがリセットされることがあるためです。
ポートはプロセスごとに 1 回、DTR と RTS を解放して開きます。macOS の CP2102 ボードは、どちらでも開くときにリセットします。
リセットしない古いボードは、前のプロセスの `BAUD` を保持するので、ホストは 115200 で HELLO を送り、`POKELDN_ESP32_BAUD` と、
アプリが提示する各レート (921600、1500000) を順に、0.5 秒の 5 パスずつ試し、そのあとで要求されたレートに切り替えます。
アプリのボードの確認は、見つけたレートをそのままにします。921600 のままのボードに 115200 だけで HELLO を送ると、
`no reply 0x81 to command 0x01` で終わります。
Windows は COM ポートを排他的に開きます。保持しているハンドルがあると、このプロセスでも別のプロセスでも、2 回目の open は
`PermissionError(13, 'Access is denied.')` で失敗します。そのため、HELLO に決して応答しないボードは、ランチャーが再試行する前にポートを閉じます。
開いているポートの下で USB デバイスを取り外すと、次の読み取りは同じように失敗し (`GetOverlappedResult failed` または `ClearCommError failed`)、
その後のすべての書き込みも失敗します。ランチャーは、書き込みを続けずに `[esp32] The board disconnected from USB` で実行を終えます。

Windows 11 の Silicon Labs ドライバ 11.6.0.420 で、CP2102 のクラシック ESP32 を計測しました:

| `open()` の前に設定する線 | 開いた回数 | リセットのバナー | ROM ダウンロードモード | その後 |
|---|---|---|---|---|
| DTR と RTS を解放 (ホストの open) | 40 | 0 | 0 | 動作中のファームウェアの CREDIT フレーム。HELLO に 0.06 秒で応答、30 件中 30 件 |
| pyserial の既定、両方を assert | 20 | 20、`rst:0x1 (POWERON_RESET),boot:0x13 (SPI_FAST_FLASH_BOOT)` | 0 | 起動時のファームウェアの INFO。open の約 0.3 秒後 |
| DTR を解放、RTS を assert | 20 | 0 | 0 | ポートが開いている間は 1 バイトもなし。RTS が 2 トランジスタの自動リセット回路で EN を low に保持する |

ROM ダウンロードモードに入ったボードは HELLO に決して応答せず、アプリの確認は pokeldn のファームウェアがないと報告します。
ほかのプロセスがポートを保持していると、open は即座に失敗し、アプリはポートがビジーだと報告します。

ボード上では、ランチャーは nl80211 の手順をすべて省きます。`--phy auto` は `esp32` に解決され、vif は削除されず、
`iw`、`ip`、`nmcli`、`sysctl` は実行されません。参加側の `--mac` はボードの station のアドレスになります。macOS では root は不要です。
スキャンは 5 GHz のチャンネル (36 以上) を飛ばします。ボードは 2.4 GHz だけなので、5 GHz でホストしている本体には届きません。
FRLG のホストはビーコンを注入しません。ボードの access point が自分でビーコンを出します。

`POKELDN_ESP32_TRACE=FILE` は、すべてのシリアルメッセージを 1 行ずつ追記します。各行は Unix 時刻、`>` (ホスト) または `<` (ボード)、
種別、16 進のペイロードです。

| ツール | 役割 |
|---|---|
| `tools/ldn/esp32_first_contact.py` | 新しいボードに対する最初の実行。`--flash` で esptool によりビルドを書き込み、続けて HELLO、STATUS、チャンネルと送信元ごとの LDN アクションフレームを数える idle のスキャンを行う。`--keys` を付けると、LDN ライブラリのスキャンで各ネットワークを復号する |
| `tools/ldn/esp32_sniff.py` | 2 つ目のボードをスニッファーとして使う (SNIFF) |
| `tests/test_esp32.py` | 2 つのシミュレートされたボード (`pokeldn.ldn.esp32_sim`) での LDN ライブラリのホストと station。スキャンから、2 つのユーザー空間スタックを通る分割された UDP まで |

CH9102 または CH343 の USB ブリッジは CDC ACM として列挙されます。Linux では `/dev/ttyACM0`、macOS では `/dev/cu.usbmodem*` になります。

### OFDM を復号できないボード

本体の広告は HT MCS 3 です ([Discovery](ldn.md#discovery))。そのため、OFDM を復調できないボードは DSSS のビーコンだけを聞き、
広告は 1 つも聞こえません。`esp32_first_contact.py` は、どのチャンネルでも LDN のアクションフレームを 0 件と数えます。
ファームウェアまたはホストの不具合と区別するには、次の 2 つの確認を行います:

| 確認 | 正常なボード | OFDM を復号できないボード |
|---|---|---|
| 本体または混雑した access point の近くで `tools/ldn/esp32_census.py` | 正常なフレームに `OFDM` と `HT` が含まれる | 正常なフレームがすべて `DSSS`。OFDM のフレームは `rx_state` 65 で失敗する |
| access point に station として参加し、access point が送るユニキャストフレームのレート | HT MCS 5 から 7 (HT40 の access point) | 約 97% が DSSS 5.5 Mbit/s。OFDM 6 または HT MCS 1 を超えることはない |

このようなボードでも、station の関連付けと ping は成功します。access point のレート適応が DSSS に戻るためです。
一般的な ESP32-WROOM-32 DevKit (ESP32-D0WD-V3 revision 3.1、CP2102) は、pokeldn 以外のファームウェアでは両方の確認に失敗します。
同じチップの WROOM-32E ボードは両方を通過し、ソード・シールドの配布ネットワークを聞き取り、ふしぎなおくりもの を配信できます
([issue 1](https://github.com/Decryptu/pokeldn/issues/1))。

OnePlus CPH2621 (Android 16) の [Android 開発者向けプロトタイプ](../examples/android/README.md) は、USB-C で XIAO ESP32C6 に給電し、
既存の Python ホストをネイティブの USB CDC ストリームで動かします。ファイアレッドのトレードは、有効な PK3 の受け取り、セーブの障壁、
部屋からの退出まで完了しました。最初のホストは毎秒約 10 の親スロットで動き、移動は遅く、アニメーションの待ちも長くなりました。
LDN とゲームのプロトコルを 1 つの Trio スレッドで動かすとループの速度が上がり、Python のスレッドを 1 つの高性能コアに制限すると、
部屋での移動が滑らかに戻りました。繰り返しのトレードも正常に完了しました。70 秒の部屋の時間窓と 30 秒のアニメーションの時間窓の両方にわたって、
毎秒 51.1 件のユニークな親 UNI スロットを計測しました。受け取ったピカチュウは PKHeX の検証を通り、本体はきれいに退出しました。
この携帯電話での、300 パケットの単独送信テストでは、制限のないウォームアップ後の実行で 99 と 113 パケット/秒に達しました。
コア 6 では 265 と 281 パケット/秒に達し、元の CPU マスクに戻すと低いレートに戻りました。この計測は、
他の Android 端末に対するアフィニティ要件を示すものではありません。

FireRed の本体がボードのアクセスポイントに参加すると、ネットワークが一覧に出ます (ゼロ長の非表示 SSID、レートの順序、
capability `0x0431`、WMM 要素を受け入れます)。オープン認証を行い、認証の 24 ms 後にアソシエーション要求を 1 つ送ります。
その内容は、capability `0x0431`、listen interval 10、32 文字の 16 進数としての SSID、レート `02 04 0b 16 0c 12 18 24` と `30 48 60 6c`、
power capability `00 14`、RSN capabilities `0x0000`、WMM 情報要素、ベンダー要素 `00 22 aa 10 01 02` です。
その LDN 認証要求は、`STA_JOINED` の 40 ms 後に `RX_ETH` に届きます。最初のブロードキャストには、ファームウェアの転送が必要です
([station のブロードキャスト](ldn.md#a-stations-broadcasts))。

スカーレットを参加側にした場合: ボードは最初のアソシエーション試行で席に座りました。`STA_JOIN` から `LINK` まで 0.35 秒でした。
セッションの参加には 0.93 秒で応答があり、告知は席に座った 5.8 から 7.7 秒後に届きました。本体の最初のバースト
(46 件のレコード、約 50 KB) が、ボードからホストへの回線を 92 KB/s で飽和させます。

### 参加

`STA_JOIN` は 1 回のアソシエーション試行を行います。指定したチャンネルと BSSID での高速スキャンの後、オープン認証とアソシエーションを行います。
市販のソード・シールドの対応ネットワークは、10 回のボードの参加のうち 2 回で試行に失敗しました。`LINK` は理由 `0xc9`
(access point が見つからない。`STA_JOIN` の 2.4 秒後) か、`0x2` (認証の期限切れ。1.3 秒後) で down になりました。
その間もボードは、そのチャンネルの広告を聞き続けていました。同じ検索で新しい `STA_JOIN` を送ると、アソシエーションできました。
成功した参加では、`STA_JOIN` の 0.23 から 0.34 秒後に `LINK` が up と報告されます。ホストは、参加のタイムアウト内で `STA_JOIN` を最大 3 回送ります
(`pokeldn.ldn.esp32_wlan.JOIN_ATTEMPTS`)。本体のネットワークが特定の試行を取りこぼす理由はわかっていません。

## 未解決

- softAP は WMM を交渉しますが、Switch のホストはしません。トレードは、それがあってもなくても完了します。
  `POKELDN_ESP32_AP_FLAGS=2` (`AP_FLAG_NO_QOS`) は、アソシエーションの後に station の QoS フラグをクリアします。
  その場合、ボードは通常のデータを送り、本体は QoS データを送り続けます。レジェンズ Z-A、LEGENDS アルセウス、Let's Go、リーフグリーンの
  トレードは、この設定で完了します。QoS データなしで聞いた 2 件の Z-A のトレードでは、ボードのフレームの 11.9%、本体のフレームの 11.5% が再送され、
  QoS データありでは、それぞれ 1.3% でした。この違いを設定のせいだと断定できるものはありません。
- ボードの access point に参加したスカーレットの本体は、一度告知を確認応答しましたが、ポート 2 の参加を送りませんでした。

- access point の受信経路のどれが、station の OFDM 初回コピーの 1 から 22% を取りこぼし、ファイアレッドの保持中に ACK を取りこぼすのかは
  わかっていません。除外した設定は [2 ボードでの受信取りこぼし](#receive-misses-on-two-boards) にあります。
- Espressif の ESP32-WROOM-32E モジュールが、access point として ELEGOO ボードの無印のモジュールより少なくフレームを取りこぼすかは計測していません。
  easyworld は、クラシック ESP32 は ESP32-WROOM-32E でなければならず、古い ESP32-WROOM-32 は安定してトレードできないと報告しています。

  そのシールドには Espressif のロゴ付きで ESP32-WROOM-32E と書かれています。
