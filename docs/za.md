# Pokemon LEGENDS Z-A

Pokemon LEGENDS Z-A (タイトル ID `0100f43008c44000`) は、Pia を `main` に静的リンクした Switch のネイティブタイトルです。パケットヘッダはバージョン 16 で、GBA アプリケーション向けに `pokeldn.ldn.crypto` が書くものと同じです。

## ダンプ

ベースアプリケーション `v0` (4.3 GB)、アップデート `0100f43008c44800` `v393216` (2.1 GB)、Mega Dimension DLC `0100f43008c45002`。

| NCA | id | コンテナオフセット | セクションキー |
|---|---|---|---|
| Program (アップデート) | `4a70b3ff963bfe412681185cea68bf55` | `0x2085d0` | `b9de1a0334576634f8fdafdd703f7f9a` |
| Control | `3e7ba1cd223145fa4f299a8f4cafd4cb` | `0xbd0` | `a8cb59338ce785237048d52452eb6adf` |

Program NCA は、セクション 0 に exeFS、セクション 1 に BKTR RomFS を持ちます。exeFS には `main` (33,970,422 バイト)、`main.npdm` (1,700)、`rtld` (8,550)、`sdk` (6,247,676) があり、`subsdk0` はありません。展開後の `main` は、テキストが `0..0x3163f70`、rodata が `0x3164000` から、データが `0x3bc2000` から始まります。このページのアドレスは、そのイメージ内のオフセットです。Control RomFS のデータは NCA の `+0x14c00` にあり、セクションカウンタは `0000000000000005` です。`control.nacp` によると、表示バージョンは 2.0.2、ローカル通信 ID は `+0x30b0` に 8 個あり、すべて `0100f43008c44000` です。

## パケットヘッダ

ヘッダバージョンは 16 で、wiki の表では Pia 6.39 から 7.2 に当たります。レイアウトは `pokeldn.ldn.crypto.PiaHeader` (29 バイト、マジック `32AB9864`、暗号化されているとバージョンバイトに `0x80` が立つ。[Pia](pia.md) を参照) です。

    0x24fadbc   initializer: magic at object +0x08, 0x10 at +0x0c, memsets nonce +0x15 (8), tag +0x1d (16)
    0x24faefc   validator: magic, (version & 0x7f) == 0x10, (length - 0x1d) >> 6 below 0x71
    0x24fb1e0   receive path, branches on bit 7 of the version byte
    0x24fb4b0   send path, writes 0x10 back to +0x0c when it seals nothing
    0x24fb46c   padding-size setter: ORs into bits 4..7 of object +0x0d (wire byte 0x05)

オブジェクトは nonce と tag を、ワイヤ上のオフセットより 8 バイト上に保持します。これは Pokemon LEGENDS アルセウスのバージョン 11 ヘッダが `pokeldn.ldn.pia6` で行っている方式と同じです。

## アドバタイズ

ローカル検索画面の本体はネットワークをホストし、112 バイトを広告します。内訳は 0x5C の Pia システムプロパティブロックと、20 バイトのゲームデータです。リンクコードによって変わらないフィールドは次のとおりです。

| フィールド | 値 |
|---|---|
| ローカル通信 ID | `0100f43008c44000` |
| LDN プロトコル | 1 |
| アドバタイズのバージョン | 4 |
| シーン ID | 1 |
| アプリケーションバージョン | 6 |
| セキュリティモード | 1 |
| 受け入れポリシー | ALL |
| 参加人数 | 1/2 |
| システム / アプリケーション通信バージョン | 22 / 6 |
| プレイヤー名 | 1 バイト、空白、UTF-8 |

SSID とチャンネルはセッションごとに決まります。ゲームバイト列は、リンクコードを ASCII で書き、16 バイトまで NUL で埋めたあと、その長さを little-endian の `u32` で格納したものです。レイアウトとパスワードフィールドは Pokemon LEGENDS アルセウスのものと同じです ([pla.md](pla.md) の広告内のリンクコードの節)。Z-A のゲームキーからは、マスク `1068a742ac3a8787ab6066a161f5d5e1` が得られます。`pokeldn.za.build_advertise_data(code)` はリンクコードだけから各広告を再現し、`tests/test_za.py` がその両方を固定します。

## 着席 (seat)

検索中の本体は局 (station) を受け入れ、すぐに Pia で話し始めます。最初のデータグラム (109 バイト) は 0.02 秒時点で届きます。パケットは `AES_ECB(game_key, ssid)` で認証され、ネットワーク ID は `CRC32(ssid[1:16])` です (32 件すべてを復号できました)。応答がないと、本体は自分の変数 ID から宛先 0 へ、プロトコル 1 (Net) で次を送ります。

| メッセージ | |
|---|---|
| `01 11 ...`、118 バイト | 接続状態。シーケンス ID 2 と 3、毎秒 2 回 |
| `01 40 00 00` | 状態に応答がなくなったら、ホスト移行を開始 |

接続状態のレイアウトは `pokeldn.ldn.pia_connect.parse_net_conn_request` が読むものです。スロットは 4 つで、2 つが埋まっています。どちらもポート 12345 で、ホストは `169.254.x.1`、参加者は `169.254.x.2` です。約 14 秒 (実測 14.4 秒) で止まりますが、局は着席したままです。

エミュレートした組 (768 パケットを取得) での開始は次のとおりです。

- ホストが最初に 109 バイトを送信します。関連付けから 48 ms 後です。参加者は 47 ms 後に 45 バイトで応答し、続いて 125 バイトを送ります。
- ヘッダの nonce は、局ごとのカウンタです。ランダムな 64 ビットの基点から始まり、送信するパケットごとに +1 されます。
- 参加者の最初のパケットは、送信元 0、宛先 0、パケット ID 0、フッターなし、非圧縮です。2 つ目のパケットは自分の送信元 ID を持ち、zstd で圧縮されています。
- ホストの次のパケットは、その ID 宛てで、2 バイトの受信者フッターを持ちます。

背後に Pia ホストのないネットワークに対して LDN 接続が成功した参加者は、7.94 秒後にきれいに切断されます。タイマーは Net の接続期限 (8000 ms) です。

    0x251b1bc   LdnProtocol vtable 0x3c8aef8 slot 0x1d8: mov w0, #0x1f40
    0x2513520   NetBackgroundProcessJob StartConnectNetwork: job+0xa0 = now + ticks_per_ms * 8000
    0x25141c4   the WaitConnected step 0x25140bc, while the host is unknown: deadline against now
    0x25143a0   expiry: result 0x647a, state byte +0x100 = 5, a 5000 ms deadline (slot 0x1e8),
                then StartDisconnectNetwork

期限は LDN 接続の完了より前に始まるため、待ち時間は 8 秒より 0.06 秒短くなります。LdnProtocol のタイミングスロット 0x1b0 から 0x1f8 は、6000、1000、500、10500、4500、8000、20000、5000、5000、10000 ms を返します。特定できているのは 0x1d8 と 0x1e8 だけです。

## 市販本体でのセッション

参照用の参加者が送る Session join を受け付けた局は、すぐに受け入れられます。本体の送信は次のとおりです。

| seat からの時刻 | 本体が送るもの |
|---|---|
| 0.02 秒 | Net 接続状態、118 バイト |
| 0.05 秒 | Session join 応答、type 2、37 バイト、参加者の変数 ID 宛て |
| 0.06 秒 | Reliable (プロトコル 10) 106 バイトと、Broadcast Reliable (プロトコル 11) 2 件 |
| 0.08 秒 | Net update property、type 0x50、150 バイト |
| 0.5 秒以降 | RTT 要求、毎秒約 3 件 |
| 1.12 秒から繰り返し | Session の update session、type 5、185 バイト |

join は、Net の確認応答で次を満たす必要があります。プロトコル 10 件 (`1:0 3:5 5:1 6:0 9:1 10:3 11:4 12:4 13:7 15:0`)、アプリケーション通信バージョン 6、識別トークン `0x06` とそれに続くゼロ、PlayerInfo の名前は空白 1 つ。GBA アプリケーションの 6 プロトコルとバージョン 0x58 を並べた join には応答がなく、本体は seat から 8.7 秒後にホスト移行を始めます。上の 10 プロトコルを持つ join でも、ゲームメッセージに応答しないと、seat から 27 秒後にホスト移行となり「no partner found」で終わります。Net、Session、RTT、Reliable のすべてに応答し、ゲームメッセージには応答しない参加者 (`--game` を付けない `bin/za_join.py`) は、市販の検索本体の seat に 150 秒間とどまります。その後、退出するまで本体は毎秒約 32 パケットを送り、退出要求に応答してから「no partner found」を表示します。

ホストのプロトコル数と異なる join は、type 0 のハンドラ `0x254a030` (比較先は `0x256c9f0`、`0x254a090`) が応答も局の作成もせずに破棄します。プロトコルバージョンやアプリケーションバージョンが違う場合は、37 バイトの type 2 で、結果 3 (`0x254a2e4`) または 4 (`0x254a290`) が返されます。ホストの WaitMember は 3000 ± 999 ms を引きます (ランダムな u64 は符号付きとして読まれます)。期限切れの時点で、参加者が Net 層にあってセッションに入っていない場合、LeaveMeshWithHostMigration は次のホストを 8000 ms 待ち (`0x255a520`)、その後 Net 0x11 のシーケンス 3 と Net 0x40 を送ります。10 個のプロトコルのうち 9 個しか並べない参加者には、市販の検索本体から Session メッセージは届きません。最初の Net 0x40 は seat から 8.74 から 11.01 秒後に届き (予測は 8.05 から 12.1 秒)、本体は新しい SSID で新しいネットワークを開き、なお検索を続けます。上の 8.7 秒はこの経路によるものです。

同じ参加者は RTT に応答せず、1.16 秒の type 6 のあとは何も送らないため、キックされます (キック)。キックは次の順で進みます。14.24 秒から Session type 13 を約 0.5 秒おきに 9 件送り、19.31 秒から 0.5 秒ごとに Net 0x11 のシーケンス 3、23.31 秒から 0.3 秒ごとに Net 0x40 を送ります。25.13 秒に最後のパケットを送ったあと、本体に「no partner found」が表示されます。27 秒での終了は、この流れによるものです。自分の変数 ID から 10 秒間何も送らない参加者がこれにあたります。

## ゲーム独自のやり取り

Pia より上では、ゲームは Reliable (プロトコル 10) と Broadcast Reliable (プロトコル 11) で動作します。サブヘッダは `pokeldn.ldn.reliable` が解析します。交換では、以下のアプリケーションペイロードを運びます (参照キャプチャでは 20 種類)。各ペイロードは確認応答が返るまで再送され、両方の局で同じ集合になります (局 ID だけが異なります)。メッセージ ID ごとに、初出の順に並べると次のとおりです。

| id | バイト数 | 運ぶ内容 |
|---|---|---|
| `1400` | 106 | 局のアイデンティティ。プレイヤー名は UTF-16 |
| `1403` | 9 | アイデンティティのチェックサム (SyncDataSet)。後述 |
| `0100` | 1211 | 選択画面を描画するもとになるレコード |
| `0101` | 354 | 提示。9 バイトのヘッダ、344 バイトのポケモンレコード、末尾 1 バイト |
| `0102`, `0104` | 5 | 手順メッセージ |
| `0200` | 5 | 確認の手順。末尾バイトは 3、6、0x0b、0x0e |

`pokeldn.za.reference` には、アイデンティティ、その続きのメッセージ、プロトコル 11 の開始部分、選択レコードが含まれます。プレイヤー名が `Player` のエミュレートした組から記録したものです。`bin/za_join.py` と `bin/za_host.py` がこれらを送ります (別のセットは `--game-dir` で指定します)。

アイデンティティは、2 要素の `b9` タプルです。先頭は u32、続いて 0x5d バイトの `bc` blob を 1 要素に持つタプルです。blob は 6 要素のタプルです。先頭の 4 要素は、セーブのトレーナー ID (上位半分がシークレット ID)、性別、言語、プレイヤー名です。続くのは、32 バイトのゼロで埋めたフィールドなどです。

ゲームは、この 4 要素をセーブのトレーナーブロック (PKHeX の `MyStatus9a`) から埋めます。このブロックはプレイヤーステータスオブジェクトの +0x40 にあります。

| 要素 | ブロック内オフセット | 取得処理 |
|---|---|---|
| トレーナー ID | +0x00 | `0x824b2c` |
| 性別 | +0x05 | `0x505c24` |
| 言語 | +0x07 | `0x23c398` |
| 名前 (13 文字) | +0x10 | `0xc90ce4` でコピー |

ビルダーは `0xc90b04` で、値を GOT が `0x3ec7638` に保持する名前のエントリに格納します。

受信側の本体は、同じ順序で要素をデコードします (`0x9131ec`)。名前ボックス `T_pname_%02d` (`0xb13fd4`) は、言語を 1 から 11 の範囲でゲームの言語テーブル (`0x33a308c`) と照合します。11 はラテンアメリカ・スペイン語です。性別は名前とともにテキストへ渡されます (`0x6b9fb8`)。

記録したアイデンティティは、女性のプレイヤーの英語版セーブのものです。トレーナー ID は `0x378913cf` (参照セッションのポケモンのトレーナーである 5071 と 14217)、性別と言語は 1 と 2 です。受信側プレイヤー向けのギフトは、4 要素すべてを読みます (`reference.identity_trainer`、[受信側プレイヤー向けに作ったギフト](gift_simulated.md#made-for-the-receiving-player))。

    1400 b902 82<u32> b901 bc5d b906 82<u32> 01 02 bc1a <name> bc20 <32 bytes> ...

名前は 26 バイトの UTF-16LE で、NUL で埋められています。最大 12 文字で、プロトコル 10 メッセージのオフセット 0x18 にあります (プロトコル 11 では局のプレフィックスの分だけ後ろ、0x1c)。記録した `Player` をここに入れると、市販本体は交換相手として `Player` と表示しました。両方の起動スクリプトは、`--trainer-name` (既定値 `POKELDN`) をここに書き込みます (`pokeldn.za.reference.named`)。

チャネル 0x14 は、ゲームが局間で同期させるキーと値のストアを運びます (`gfa::network::p2p`、`0x7796a0` で構築。メッセージ ID は `0x1400 | index`)。1400 は UpdateValue (`0xc1bdf4`)、1402 は DeleteAllValues、1403 は SyncDataSet (`0xc4b1b4`) です。アイデンティティの外側の u32 `0x2abe85e2` はその値のキーで、`0xdf1b30` にある定数です。これは `UserData` の FNV-1a 32 で、ゲームがアイデンティティを格納する名前です。1403 は、送信側の値をキー順に並べたものに対する u32 を 1 つ運びます。`h = 0` から始めて `h = crc32(le32(fnv1a32(value) + h))` で計算されます (`0xc4b270`。FNV-1a は `0xc4b31c`、標準の CRC-32 は `0xc4b420`)。アイデンティティの場合、値は `bc5d` の後ろの 0x5d バイトです。受信側は再計算し、すべての局の値が一致したときだけ次に進みます (`0xb8c724`、`0xb8c660`)。記録した `Player` のアイデンティティは、記録済みメッセージ `1403b9018269fb308f` になります。古い 1403 のまま名前を変えたアイデンティティを送ると、市販本体は検索画面のままになります。1400 と 1403 は送りますが、0100 は送りません。`pokeldn.za.reference.sync_message` は、送るアイデンティティに対する 1403 を作ります。

### 交換コマンド

交換セッションのセットアップ `0xca2928` は、セッションのコマンドチャネル (session+0xc8) で 5 種類のコマンド型を購読します (型は ctti の文字列で名前付けされています)。ID は `0x100 | index` で、チャネルのリスト (+0x60) における型の位置です (`0x96129c`、`strcmp` で走査)。各ペイロードは、先頭が u16 のラウンドで始まる `b9` 構造体です。

| id | コマンド | ハンドラ | ハンドラが読むペイロード | ハンドラの処理 |
|---|---|---|---|---|
| `0100` | CommandReady | `0x2dc4c7c` | ラウンド、1200 バイト | 1200 バイトを session+0x604 にコピーし、session+0xf0 を設定 |
| `0101` | CommandSelectPokemon | `0xb2a44c` | ラウンド、344 バイトのレコード、1 バイト | レコードを読み込む (「提示されたポケモン」を参照)。そのバイトの bit 0 が 0 なら選択になる |
| `0102` | CommandConfirmTrade | `0xc8dda0` | ラウンド | session+0x152 がラウンドより大きければ無視する。そうでなければ相手の状態 +0x134 を 4 にする |
| `0103` | CommandCancelTrade | `0x2dc51ac` | ラウンド、u32 の理由 | +0xab4 = 理由 (1 と 2 を入れ替えたもの)、それ以外は 0。+0x152 = ラウンド。+0x150 += 1。その後 `0x2dc41f8` |
| `0104` | CommandFinalAgreement | `0x2dc52b4` | ラウンド | +0x152 がラウンドより大きいか、自分の状態 +0x130 が 4 か 5 でなければ無視する。そうでなければ相手の状態を 5 にする |

キャンセルの送信者 `0x964a60` は、自分の状態 +0x130 が 2 か 5 の間は何も送りません。それ以外では、ラウンド +0x150 + 1 を送り、+0x130 = 2 にして、+0x150 と +0x152 を進め、相手の状態を 3 から 5 のいずれかから 2 に下げます (理由が 0 のときは 3)。ハンドラは +0x152 より厳密に小さいラウンドだけを拒否します。そのため、キャンセル後に古い ConfirmTrade や FinalAgreement は無視され、より大きいラウンドは受け入れられます。SelectPokemon はラウンドを読みません。

セッションオブジェクト (0xab8 バイト。`0xca2658`、`0xca2704` で構築、vtable `0x3e3a6e8`) は、+0x40 に設定を持ちます (u16 0x201、下位バイトがチャネル)。また +0x48 と +0x88 に呼び出し可能オブジェクトを、+0x150 から +0xab7 にはゼロを持つため、両方のラウンドは 0 から始まり、セッションで最初に送られる `0102` と `0104` は `b90100` です。`0x964568` (自分の状態 6。呼び出し元は実際の交換経路 `0x95f8f4` 内の `0x9601dc`) は、自分の提示 +0x120 と相手の PokemonParam +0x128 をクリアし、両方の状態を 2 にします。さらに +0x118、+0x11a、+0xd0 をクリアし、+0x150 と +0x152 をゼロにします。そのため、着席した局での次の交換はラウンド 0 から始まり、まだラウンド 1 にある回答も受け入れられます。`pokeldn.za.host` は交換ごとにラウンドをリセットします。

| 自分の状態 | 書き込み元 | 条件 |
|---|---|---|
| 5 | session update `0x95f600` (`0x95f680`) | 自分の状態が 3 か 4、バイト +0x148 が設定済み、タイマー +0x138 が 1.5 秒以上、相手の状態が 4 か 5、`0x963710` が真 |
| 6 | delegate invoke `0xdfda8c`、`0x964e78` で設定 | 交換ワーカーの状態 6 のデリゲート |
| 7 | `0x2dc4b94`、`0x964f0c` で設置 | ワーカーの状態 7 のデリゲート。2.0.2 では到達不能 |

### 参加者がそれらのストリームで負うもの

参照用の組とエミュレートしたホストの確認応答で計測しました。

- プロトコル 10 はホストの変数 ID 宛て、プロトコル 11 はメッシュ ID 0x0001 宛てです。どちらも 2 バイトの受信者フッターにホストの変数 ID を持ちます。
- ゲームのパケットはすべて zstd で圧縮されます。
- 純粋な確認応答は、ストリームの基点 0xfff0 とメッセージフラグ 0x40 に乗ります。シーケンスを進める確認応答は、後ろに穴のあるデータとして読まれます。アプリケーションデータはメッセージフラグを持ちません。
- プロトコル 11 の確認応答は 74 バイトです。局の 4 バイト、ストリームのバイト、個数 4、続いて次に期待する halfword と 16 バイトのマスクからなる 4 件のエントリがあり、最後のエントリは途中で切れています。エントリ 1 は参加者のストリームです。ホストは残り 3 つで、待機中の基点 0xfff0 を報告します。
- アイデンティティは INIT の下で送られ、その後に選択レコードが続きます。そのあとは新しいシーケンスの下で繰り返し送られ、毎回同じ 1211 バイトです (計測では約 0.5 秒後、その後は毎秒約 4 回)。
- サブヘッダの受信者数は、プロトコル 11 では 3、プロトコル 10 では 0 です。
- プロトコル 11 では、サブヘッダの長さは 4 バイトの局プレフィックスの後ろにあるペイロードを数えます。そのため、各フレームは宣言より 4 バイト多く持ちます。開始は `00000001` と `1402 b900`、アイデンティティはプレフィックスとプロトコル 10 のアイデンティティ全体、9 バイトのメッセージは `1403b9018269fb308f`、確認応答はプレフィックスと 18 バイトの完全なエントリ 4 件です。宣言された長さで切れたフレームは破棄されます (ホストは開始部分を毎秒約 10 回再送します)。末尾の 4 バイトが誤っているフレームは確認応答されますが、ホストは検索画面のままになります。

LDN NodeInfo のローカル通信バージョン (0x40 バイトの +0x2E) は、参照局では 6 です。0 も同じように扱われます。

### キープアライブ

設定の +0x290 は、ミリ秒単位の送信無音の上限です (`0x257d12c` -> `0x256a238`。負の値は 0x10407 で失敗し、0 は 1000 になります)。`SessionPacketWriter` (vtable `0x3c8da30`) の vfunc 7 `0x2544004` は、送信ごとの局マスクを使って `0x256a2d0` を呼びます (`0x2568924`)。状態 2 で ID が 0x17 以下、かつバイト +0xa0 がクリアされている他の局 (`0x25770d8`) は、送信先になったときに +0xb0 を刻印されます。+0xb0 が上限より古いと、フラグが立てられます (送信先に含まれない局を含む)。フラグの立った局 (`0x2568928`) には、追加のパケットが送られます (`0x256a89c(p, 0, 0)`)。これはプロトコル 0、bit-0x10 のバイト 0xfd、ポート 0、フラグ 0、空のペイロードを持つ Pia メッセージ 1 つです。そのため、着席した局は、1 秒間何も送られていなければパケットを受け取ります。これを確認したキャプチャはありません。メッセージのヘッダは、存在バイト `04` とプロトコル `00` です。ライター `0x256dccc` は、新しいヘッダと異なるフィールドだけを出力します (プロトコル 0xFF、中間バイト 0xFD、ポート 0)。受信側のリーダーは、プロトコル確認なしでバケットテーブルにメッセージをキー (プロトコル、中間バイト、ポート) 付きで格納します (`0x2566844`、`0x25670f0`)。ID 0 を持つ Protocol クラスはないため、どのプロトコルもこれを読みません。各プロトコルは自分のキーのチェーンだけをたどります (Reliable の `0x256fed0` は何も削除しません)。PacketReader の vfunc 6 `0x2565ce0` は、まず `0x2566030` を呼びます (`0x2565d34`、唯一の呼び出し元)。これは全バケットのすべてのノードをリンクから外し、プールの空きリストに戻し、バケットをゼロにします。そのため、読まれなかったメッセージは次の受信パスの開始時に回収され、プロトコル 0 のメッセージが溜まることはありません。ノードプール (`0x10c10`) が満杯になると、パケットの残りは破棄されます。バイト +0xa0 は、キック中の局を示します。設定されるのは `0x2577094` だけで、呼び出し元は `0x255b4a0` と、ホスト以外の局のドレイン `0x2548b60` です。

### パケット ID

パケット ID は送信側ごとに 2 つのカウンタで動きます。宛先 0x0001 用のものと、それ以外の宛先用のものです (0 とホストの変数 ID は後者を共有します)。`nn::pia::session::SessionPacketReader::vfunc11` `0x2566920` は、どのプロトコルよりも前に確認します。未知の送信元か局がない場合は受け入れます。それ以外では、宛先によってコントローラを選び (0x0001 は station+0x78、それ以外は station+0x50)、`0x2576ad0` がパケット ID (ワイヤ上の 0x0a) とビッグエンディアンの nonce (ワイヤ上の 0x0d) を確認します。

    id == 0                                         accept, nothing recorded
    last id == 0                                    last id = id - 1
    last nonce == 0 and nonce != 0                  last nonce = nonce - 1
    (s16)(id - last id) < 1                         reject
    nonce != 0 and (s64)(nonce - last nonce) < 1    reject
    otherwise                                       last id = id, last nonce = nonce if non-zero

拒否されたパケットは `0x25655d8` に送られて破棄されます。繰り返された ID、または 0x8000 以上先の ID がこれにあたります。宛先 0 用の別カウンタを持つ参加者は、ホスト ID のカウンタを超えるまで、すべての Net 0x51 が破棄されます。ホストは、どれかが通るまで Net 0x50 を繰り返します (計測で約 10 秒)。その間、更新シーケンス 1 は遅れます。
Net 0x51 のハンドラ `0x2504100` は、ヘッダのフィールドを読みません。デシリアライズ (`0x250f930`) を行い、長さと type 0x51 を確認し (`0x2504150`)、送信元を局と照合します (`0x250c60c`、`0x24fba00`)。そして、メッセージ +4 にある局と確認済みシーケンスを `0x250daa8` に渡します。

### join の残り

- Net: 接続状態 0x11 には 0x12 で、更新プロパティ 0x50 には 0x51 で応答します。
- Session: type 5 の update session には、15 バイトで応答します。内容は、type、局の LDN 定数 ID、更新のシーケンス (ビッグエンディアン u32)、0x0001 です。GBA アプリケーションの応答 (生の MAC、シーケンスなし) では、Z-A のホストは更新を 2 秒ごとに無限に繰り返します。

更新シーケンス 1 を受け入れたホストは、約 50 ms 後に選択レコードを送り (計測では seat から 1.2 秒と 1.25 秒後)、交換ボックスに移ります。

### プロトコル 10 での交換

両側は、選択レコードの後に 354 バイトの `0101` を送ります (計測では約 2.5 秒後)。提示の末尾バイトは、局が頼まれずに送るプレビューでは 1 です (市販本体は、交換ボックスでカーソルが動くたびに 1 つ送ります)。プレイヤーが選んだ場合は 0 です。ホストは件数ではなく、このバイトで判断します。1 で送られた選択は確認応答されますが何も描かれず、相手は空きスロットのまま「Communicating」で待ちます。

参加者はホストの選択に自分の提示で応答し、`0102b90100` で確定します。ホストも同じものを返して確定します。両方が `0104b90100` を送ります (ホストは参加者の `0102` の 1.5 秒後に送ります)。参加者は 4 つの `0200b901XX` の手順を送ります。03 と 06 はすぐに、0b と 0e は交換アニメーションと交換ワーカーのランダムな待機の後です ([交換コマンド](#the-trade-commands))。ホストはプロトコル 11 で `0000000202` を送り、各手順にはプレフィックスの下で `0201b901XX` を返します。`bin/za_join.py --trade-offer` で参加者側を実行します。

#### 技ごとのフラグ

PA9.cs の plus 技レコードは 360 ビットです。k が 264 未満のビットは 0xd6 + k/8 に、それ以上は 0x94 + (k - 264)/8 にあります (スカーレットのテラタイプは 0x94 と 0x95 にあり、ここではフラグ 264 から 279 になります)。技のインデックスは、rodata `0x3303fb0` にある 340 個の u16 技 ID における位置です。これは線形探索 `0xe669e0` で求めます (見つからないと -1 で、呼び出し元はいずれもフラグを飛ばします)。`0x631834` はフラグを立て、`0x673448` は下げ、`0xe438e4` は配列をクリアし、`0xe43068` は 1 つ読みます。技 446、328、103、784 を持つイワークは、フラグ 33 38 88 91 103 106 157 174 225 231 328 444 446 457 784 を持ちます。技 58、103、162、247、328、403、423、446、542、573、784 がリストに含まれます。

スカーレットの u16 は 0x14、特性スロットのビットは 0x16 にあります。GetAbility `0xe43bec` は、299 (0x12b) 未満なら保存された値を返します。それ以外は、パーソナルテーブルから `0xe5d368(species, form, bit 2 ? 2 : bit 1)` の値を返します。0x14 を読むのは、タイプ取得処理 `0x99c84` と `0xa4354` だけです (特性 121 の種族 493 と特性 225 の 773 は、持ち物からタイプを取ります。`0xe5d528`、`0xe5d5a0`)。作成ルーチン `0xe3eb34` と `0xbb8f04` は、`0xe5d368` から値を書き込みます。本体が作ったレコードは 5、30、38、81、151、187 を格納します。

### 受け取ったレコードの読み込み時の検査

相手の `0101` は `0xb2a44c` に届きます。これは CommandSelectPokemon に登録されています (`0xca33d8`、呼び出し元は `0xca2928`)。デシリアライザ `0xb4e248` は、3 要素を持つ tag 0xb9 を要求します (`0xb4e33c`)。先頭を u16 として読み (`0xa91178`)、2 番目が 0x158 バイトちょうどの tag 0xbc であることを要求し (`0xb4e4b8`)、3 番目を struct+0x15a に保持します。どのエラーでもハンドラは呼ばれません (`0xb4e1c8`)。ハンドラは PokemonParam を確保し (`0x82713c`)、344 バイトを `0x270994` で読み込みます。

1. `0xe47e94` は 0x148 バイトをコアに、16 バイトを末尾にコピーし、両方を復号してチェックサムを比較します。不一致なら Bad Egg のビットを立てます。高速モードを解除するため、読み込みの最後にはチェックサムを書き直して再暗号化します。不正なチェックサムは、Bad Egg のビットを立てたうえで修正された状態で保たれます。
2. `0xe3f18c`: 種族がゼロでなければ、`0x2901a4(species, form)` がその組をパーソナルテーブル (`0xe366b0`。キーは `species * 10000 + form` のマップ) で探し、FlatBuffers のフィールド 1 のバイト (vtable +6、`0xe3bbfc`) を読みます。無ければ 0 です。0 なら Bad Egg のビットを立てます (`0xe51698(acc, 1)`)。キーがないときは、フィールド 1 を持たない種族 0 のエントリである map+0x80 にフォールバックします。
3. `0xe41750(pp, 1)` は、経験値から求めたレベルを末尾に書き込み、種族、フォルム、能力値のレベル、個体値、ハイパートレーニングのビット、努力値、能力値の性格から最大 HP と 5 つの能力値を再計算します。現在 HP はゼロならゼロのままで、それ以外は最大 HP の増加分だけ上がります。
4. `0xe42584` は、スロット 0 から数えたゼロでない技の PP を、PP アップを含む最大値 (`0xe6646c`) に抑えます。タマゴまたは Bad Egg (`0xe4c950`、`0xe485f0`) は、`[0x3f0784()+0x380]` が設定されているか `0xe483b4` が真でない限り飛ばされます。
5. `0xb2a4a4` は、session+0x88 の呼び出し可能オブジェクトを PokemonParam で呼び、その結果は無視します。PokemonParam を session+0x128 に移し、3 番目の要素の bit 0 が 0 のとき (選択) は相手の状態 +0x134 を 3 にします。この呼び出し可能オブジェクトは常に `0xad2c68` で、下記の名前の検査です (`0xca20a4` が `0xca2520`、`0xca25d8` でこれを使う設定を組み立てます。ほかに参照するものはありません)。

技を覚えるリスト、ボール、出会いのデータ、トレーナー ID、特性、末尾のレベルは、どれも検査されません。作成されたレコードが失敗するのは、チェックサムが誤っているか、パーソナルテーブルのフィールド 1 がゼロの場合だけです。どちらも Bad Egg になり、拒否はされません。拒否された名前は書き直されます。チェックサムが不正なレコードは、提示のニックネームの下に、タマゴのアイコン、レベル 0、オスの記号で描かれ、"Trade it" が提示されます。交換すると、概要が空の "Egg" としてボックスに入り、ゲームは続行します。

### 受け取ったポケモンの名前の検査

`0xad2c68` は、空のレコード (IsEmpty `0x13778`) に対しては何もせず返ります。それ以外では `0x89f250` を実行します (もう 1 つの呼び出し元は `0x89de34`)。これは 0x20000 バイトのバッファ (`0x912e10`) を使って、グローバル `0x612d3d0` に `nn::ngc::ProfanityFilter` を開き、`0x9138d4(str, len, language)` で 3 つの名前を検査して、終了処理 (`0x912d80`) を行います。

| 名前 | 渡される言語 | 失敗時 |
|---|---|---|
| ニックネーム、0x58 | レコードの言語 (0xd5) | `0x8a0370` が、その言語での種族名を書き込み (`0xe33ca0`)、ニックネーム済みのビット (0x8c の bit 31) を消す |
| オリジナルトレーナーの名前、0xf8 | レコードの言語 (0xd5) | `0x3d8a248[language]` を、`0xe579a0` で書き込む |
| ハンドラの名前、0xa8 | ハンドラの言語 (0xc3) | `0x3d8a248[language]` を、`0xe5a190` で書き込む |

言語が 12 以上なら、テーブルはインデックス 0 として扱われます。`[0x3f0784()]+0x380` と accessor+0x1a がどちらも 0 のとき、`0x8a0370` はタマゴまたは Bad Egg (`0xe4c950`、`0xe485f0`) に対しては何も書き込みません。置き換え用のテーブル `0x3d8a248` は 12 個の UTF-16 文字列を持ちます。0、1、6 は `ゼット.`、2 は `Z`、3 は `Zed`、4、7、11 は `Zeta`、5 は `Zett`、8 は `제트.`、9、10 は `Z.` です。

次のとき、`0x9138d4` は名前を失敗させます。

- 長さが 0 か、先頭の単位が 0 である。
- 7 単位以上で、いずれかの単位が 0x3041..0x3090、0x30a1..0x30fa、0x4e00..0x9fcc、0xac00..0xd7a3 のいずれかの範囲にある (範囲は `0x3308840`、`0x33087b8` にある)。
- 言語が 1 から 5、7、11 のいずれかで、最初の 0 より前のいずれかの単位が 0x4e00..0x9fa0 にある (0x4edd を除く)。
- L (`0x444330` から得る) が 0、6、または 11 より大きい。
- フィルタの vfunc +0x28 が非ゼロの結果を返す。これは `0x913ad0` が `(&result, pattern, &str, 1)` で呼び、パターンは `0x339f650[L - 1]` です。

長さの走査 `0x913a80` (0x10 タグの連なりは飛ばす) が 0 と測る文字列は、フィルタを通さずに合格します。フィルタの呼び出しがエラーを返した場合も同様です (`0x913b08`)。ハンドラの言語が 0 でハンドラ名が空のときは `ゼット.` になり、オリジナルトレーナーの名前が空のときは、レコードの言語の文字列になります。その後、交換が完了するとハンドラの名前は上書きされます。PKLDN と参照用の名前は合格します。

L はゲームのテキスト言語で、シングルトン `0x6131800` の +0x14 バイトです (GOT `0x3ec7800`。+0x80 で構築済みとされると、`0x410a20` を経由して `0x444330` が読みます)。レコードの言語バイトと同じ番号付けで、メッセージディレクトリテーブル `0x3e278b8` (ストライド 0x18、`0x940dd8`) のインデックスになります。0、1、6 は "jpn"、2 は "English"、3 は "French"、4 は "Italian"、5 は "German"、7 は "Spanish"、8 は "Korean"、9 は "Simp_Chinese"、10 は "Trad_Chinese"、11 は "Latam"、12 は "item" です。ローダー `0x410a30` は、言語引数が 0 のとき L を使います (`0x410a68`)。

起動時に `0xaa1340` は、`0x17d6368` が `nn::oe::GetDesiredLanguage()` から作るインデックスを +0x10 に格納します (ja、en-US、fr、de、it、es、zh-Hans、ko、nl、pt、ru、zh-Hant、en-GB、fr-CA、es-419 が 0 から 14、それ以外は 15)。`0x741760` はこれを `0x330f728` の表 `1 2 3 5 4 7 9 8 2 2 2 10 2 3 11` によって L に対応づけます (14 より上は 2)。そのため、起動時の値は 1 から 5 か、7 から 11 です。セッター `0x17d62ec` は +0x14 を書く唯一の箇所です。ほかの呼び出し元は、言語選択ビュー (`0x2c204ac`)、トレーナーレコードの +0x47 を使う `0xbb9d30`、そして任意の整数を格納するスクリプトバインディング `0x1673170` です (Lua 名 `f21813187`、モジュール `cE461829E`、`0x16734c0`)。出荷されている 4 つの Lua パック (`/arc` の `scriptluabinrelease` にある dll_util、event_ik、main、main_dynamic) のどれも、このバインディングやモジュールの名前を含みません。

言語選択ビューが格納するのは、表示する 10 個の値だけです。そのビューの vfunc `0x2c20b80` は、モデル `[view+0x118]` の +0x50 に、2 バイトのエントリ (L、ラベルのインデックス) のベクタを作ります (`0x2c200d4`)。現在の L が 10 個のいずれかならそれが先頭に、そうでなければ 2、7、11、3、5、4、1、8、9、10 の順で並びます (バイトは `0x33a19b5` にあり、インラインでも作られます)。10 個になるまで `01 00` で埋めます。`0x2c20c98` は、`Button_00` から `Button_09` に、(view, i) を保持するハンドラを割り当てます。ハンドラ `0x2c21234` は `0x2c2047c([view+0x118], i)` を呼び、これは同じベクタのエントリ i の先頭バイトをセッター (`0x2c204ac`) に渡します。

パターン `0x339f650[L - 1]` は、`nn::ngc` の単語リストの集合です。そのため、レコードの言語にかかわらず、受信側の本体の言語がそれを選びます。

### 受け取ったレコードに交換が書き込む内容

交換のステップ 6 は、交換オブジェクトの vfunc +0x80 `0xcbc68c` を呼び、それが `0xcbc7fc` を呼びます。`0xcbc9e8` がヌルを返さない限り (`0xcbc854`。更新を飛ばす)、プレイヤーのトレーナーレコードから構造体を埋めます (GOT `0x3ec28d8` のシングルトンの `0x505c30`。`0x882104` を使用)。内容は、+0x40 の u32 (トレーナー ID とシークレット ID)、性別 +0x45、言語 +0x47、+0x50 からの名前 13 単位です。相手の PokemonParam (交換オブジェクトの +0x78) を `0x825358` で包み、ラッパーのスロット 167 (`0xcbc888`、+0x538。両方のラッパー vtable では `0xcebfe0`) を呼びます。これは `0xcebfe8` へのサンクです。

- オリジナルトレーナーの性別 (`0xe4f570`、0x125 の bit 7)、u32 0x0c (`0xe49d50`)、名前 (`0xe510c0`) がすべて構造体と一致する場合: 0xc4 = 0 (`0xe58a70`) とし、`0xe3f900` を呼び、1 を返す。
- それ以外: 0xc4 = 1 とし、構造体の名前 (`0xe5a190`)、性別を 0xc2 (`0xe5a3a0`)、言語を 0xc3 (`0xe5a5c0`) に設定する。ハンドラの思い出 0xc9、0xca、0xcb と u16 の 0xcc は 0 にする (`0xe59910`、`0xe59b30`、`0xe59f70`、`0xe59d50`)。`0xe340ac(species, form)` を仲良し度 0xc8 に設定する (`0xe58eb0`)。`0xe3f900` を呼び、0 を返す。

受け取ったポケモンは、受信側のプレイヤーがそのオリジナルトレーナーでない限り、そのプレイヤーをハンドラとして持ちます。各セッターは、まだ暗号化されている (+0x18) レコードに対して、再集計 (`0xe5d810`) を行い、不一致なら Bad Egg のビットを立てます (`0xe58b60..0xe58b80`)。Bad Egg の場合は、`0x3f7ef98` の受け皿に書き込みます (`0xe58bcc`)。

`0xe380c0` は、`0x7961b0` が "avalon/data" として設定するディレクトリ (`[[0x3f7f038]]`) から `personal_array.bin` を読み込みます。`waza_array.bin`、`tokusei_array.bin`、`growTable.bin` も同様に読み込みます。

1445 個のテーブルからなる FlatBuffers のベクタで、キーは 1445 個すべて異なります。フィールド 0 は種族とフォルムの halfword で始まり、マップビルダー `0xe36170` が `species * 10000 + form` をキーとして登録します (キー 0 は map+0x80)。種族は 0 から 1010 まで並び、すべて存在します。フォルムが 0 より大きいエントリは 434 件です。917 以上のキーは第 9 世代の内部インデックスです。フィールド 1 は、364 種の 594 組 (種族、フォルム) で 1、残りの 851 組では存在しません。この 594 組は、1010 までの PKHeX の `personal_za` の存在リストと一致します。PKHeX の 1011 から 1016 (14 組) はエントリがなく、Bad Egg として届きます。Mega Dimension DLC はパーソナルテーブルを含みません (唯一の PublicData NCA は 101,376 バイトで、692 バイトの RomFS を持ちます)。種族 95、333、407、471、707、714、716 はフォルム 0 に存在します。

ボックス格納と交換の経路で、Bad Egg の拒否は見つかりませんでした。`0x962388` が箱に入れるのは、空でも (IsEmpty `0x13778`) タマゴか Bad Egg でもない (IsEgg `0x18e4c`) ポケモンだけです。ただし、実際の交換経路 `0x95f8f4` は、`0x961964` (`0x960000`) を通じて選択をボックスに直接入れます。交換では、タマゴと Bad Egg の判定は作業を飛ばすだけです。PP の抑制 `0xe42584` と能力値の再計算 `0xe41750` がこれにあたります (後者は `0xc34b5c` で飛ばされます)。

## 市販本体との交換

リンク交換の検索中の市販 Z-A は、`bin/za_join.py` と交換し、作成されたレコードを保持します。交換のあと、本体は同じ seat で交換ボックスに戻り、再び交換できます。`0x964568` が両方の状態を 2 に、両方のラウンドを 0 にリセットします ([交換コマンド](#the-trade-commands))。

参加者は、繰り返しの `--trade-offer` を扱います。4 番目の手順の 2.7 秒後に次のレコードをプレビューし、本体の次の選択でラウンド 0 のもとでそれを選びます。`bin/za_join.py` と `bin/za_host.py` は、ldn_mitm の上でレコードのキューを順番に交換します (`tests/test_za_host.py` は参加者側をスクリプト化します)。参加者は、1 つの seat で市販 Z-A のホストと、キュー内の 2 件のレコードを交換しました。

本体の交換アニメーションは 4 番目の手順のあとに実行され、交換コマンドは運びません。市販 Z-A が `bin/za_host.py` に参加した場合、4 番目の手順から、アニメーションは 1.1 秒で始まり、受け取ったポケモンは約 26 秒で表示されます (手で押した場合は最大 2 秒遅れる)。本体の次のプレビュー (`01 01`、354 バイト) は 30.2 秒に届き、プレイヤーが操作できるのは約 31.7 秒です。その間、本体はプロトコル 10 のメッセージを送りません。
本体のホストフェーズの後半に形成された seat は引き継がれます。最初のデータグラムは遅れて届き、更新シーケンス 1 は続きません。本体は Session type 9 を 1 秒ごとに繰り返し送ります (wiki の番号ではホスト移行の開始にあたり、wiki ではキックが 12、Z-A では 13 です)。Net を再開するまで続きます (計測では、関連付けから最初のデータグラムまで 1.4 秒。通常の seat では 0.1 秒未満。Net は 6.5 秒で再開)。市販のスカーレットの検索も、実機で同じ動作をしました。どちらの側のコードも追えていません。

## ホスト

検索中の本体もスキャンし、タイトルの広告とリンクコードを載せたネットワークに参加します。`bin/za_host.py` はそのようなネットワークをホストします。`pokeldn.za.host` は、エミュレートした組の交換とバイト単位で一致することを固定しています。

| seat からの時刻 | ホストが送るもの |
|---|---|
| 0 秒、応答があるまで 0.46 秒ごと | Net 接続状態 0x11。シーケンス 2、4 スロット、ホストと参加者はどちらもポート 12345 |
| Session join を受けたとき | 参加者の ID 宛ての join 応答 (type 2、37 バイト)、0x0001 宛ての update session (type 5、シーケンス 0) |
| それと同時 | プロトコル 10 上の INIT の下のアイデンティティ。プロトコル 11 では、アイデンティティと `1403b9018269fb308f` を、プレフィックス `00000002` でまとめて送る |
| それと同時 | Net update property 0x50。0x51 を受けるまで 0.5 秒ごと |
| 0.2 秒以降 | 0x0001 宛ての RTT 要求、毎秒約 3 件。参加者の各要求への応答 |
| 更新 0 が確認応答されてから 1.15 秒後 | update session のシーケンス 1 |
| 更新 1 が確認応答されたあと | 1211 バイトの選択レコードを 60 ms 間隔で 2 回 |
| 2.7 秒後 | プレビュー `0101` |

GBA アプリケーションのホストとは、次の点が異なります。

- update session 内のホストの局エントリは、識別トークン `0x06` を持つ。
- 更新のシーケンスは 2 回書かれる。+1 と +21 の位置。
- プロパティ更新は、シーン ID の後ろに `02` を持つ。GBA アプリケーションは `01` を書く (下記の CloseParticipation)。
- ブロードキャストの確認応答は、エントリ 1 で参加者のストリームを報告し、残り 3 つでは 0xfff0 を報告する。

市販 Z-A は `bin/za_host.py` に参加して交換します (提示の目印: [プロトコル 10 での交換](#the-trade-on-protocol-10))。どちらの役割でも、任意のリンクコードが使えます (`--code`。12345678 で試験済み)。

ホストは 4 番目の交換手順の後もセッションを保持し、本体が退出したときに閉じます。本体は交換のあと交換ボックスに戻り、B で退出してもエラーは出ません。ホストは本体の退出後に閉じます。`--hold-after-trade` を指定すると、時間指定での終了になります。全体の `--seconds` の上限は引き続き適用されます。交換のセーブのあとにタイマーでネットワークを閉じ、引き継ぎをしないホストでは、本体に「Error Number: 6」が表示されます。時間指定での終了時 (`--seconds` の上限と Ctrl-C) には、`bin/za_host.py` が着席している本体にまずセッションを引き継ぎます ([ホストの退出](#a-host-leaving))。ボックスに戻ったエミュレートした Z-A 2.0.2 は、この引き継ぎに type 10 と 0x12 で応答し、"Your trading partner chose to quit trading. The Link Trade will now end." を表示して、エラーなしでリンク交換の画面に戻りました (2 回ずつ 2 回の試行)。ホストで交換したあとボックスにいる市販 Z-A も、`--hold-after-trade 5` で同じメッセージを表示し、エラーはありませんでした。4 番目の手順の 20 秒後、本体がまだ交換アニメーション中に送った同じ引き継ぎでは "Error Number: 6" が表示されました。ただし交換はセーブ済みでした。交換後の本体の最初のプレビューは、4 番目の手順の 30 秒後に届いたので、時間指定での終了はそのプレビューから数えられます。

ホストした seat は、繰り返しの `--trade-offer` から、キューのレコードを順番に交換します。次のレコードは、前の交換の 4 番目の手順の後にプレビューされます。プレイヤーが退くと、本体は退出します。交換後にボックスへ戻った本体は、カーソルの下にあるポケモンをプレビューするため、`--offer-out` は選択だけを残します。

コード 00000000 でリンク交換の検索をホストしたエミュレートした本体は、(検索の開始時、下記) スロット 13 を実行しました。これは `0xc8a198` から、4 番目の引数に定数 1 を渡して呼ばれています (`0xc8a194` の `mov w3, #1`)。約 10 秒後、CloseSession ステップ `0x19d7a70` (戻りアドレス `0x19d7acc`) からタスクビルダー `0x1a228f0` に入り、CloseParticipation (戻りアドレス `0x255c490`) から facade のインデックス 19 に入りました。その間、参加者は着席したままで、交換ボックスが開きました。ボックスから退いても、どちらにも再び到達しませんでした。

3 つのドライバすべてのスロット 13、14、16 にブレークポイントを置いたエミュレートした Z-A 2.0.2 では、ローカルドライバだけが実行されました。プライベートバトルの「Create a Room」はスロット 14 の CreateSession (`0x19a3790`、戻りアドレス `0x2a50170`) に入り、リンク交換の検索は `0xc8a198` から、4 番目の引数 1 でスロット 13 (`0x19a1310`) に入りました。どちらも同じドライバオブジェクト上です。LAN やサードドライバのステップは実行されませんでした。マネージャオブジェクトは静的なシングルトンで、ローカルドライバはヒープオブジェクトです。

モード 3 でタスクを作る呼び出しはないため、2.0.2 では LAN ドライバが設置されることはありません。ゲームの最初の命令の前にブレークポイントを置いたエミュレートした本体では、起動、フィールド、Link Play のページ、リンク交換のページ、リンクコードの入力画面のいずれでも、セッターには到達しませんでした。コード 00000000 を確定すると、戻りアドレス `0x1912240` からモード 0 でセッターに入り、0.6 秒後に `0x191213c` からモード 1 で入ってローカルドライバ (`0x199eaa0`) を作りました。さらにその 1.0 秒後、ローカルドライバのスロット 13 が (`x2` 2、`x3` 1) 実行されましたが、局は存在しませんでした。参加者が始まったのは 4 分後です。ヒットしたあと 0.3 秒で再設定したブレークポイントは、2 回目の呼び出しを逃します。


市販本体のリンク交換の検索では、広告はポリシー 0 を持ち、seat には 2/2 のノードがいます。Pia のプレイヤー数 (広告データ +0x16、`e1 01 01 00` から `e1 01 02 00` へ。変化する唯一のバイト) は 2 に変わります。その後、本体が 1 回送る Net 0x50 (150 バイト、シーケンス 1、受け入れ状態 `02`) の直前にポリシー 1 が広告され、着席したセッションの間はポリシー 1 のままです。その前にホスト移行はないため、市販の `02` は CloseParticipation によるものです。これはスロット 13 のステップ `0x19d7a70` が開始し、ローカルドライバ上でリンク交換のコードが到達する唯一のビルダーです。
参加者側の基板で復号した 4 つの着席セッションでの計測では、プレイヤー数 2 は 0.07 から 0.59 秒、ポリシー 1 が初めて広告されたのは Net 0x50 の 2 から 48 ms 前で、0.09 から 0.64 秒です。2/2 の参加者がいるとき、ポリシーが拒否するものは、容量でも拒否されるものだけです。

## 退出

局は、2 つの `nn::pia::session` ジョブのどちらかを通じて退出します。どちらも、相手の局からの応答を待ちます。ディスパッチャ `0x2547490` が読む Session 型は次のとおりです (テーブル `0x336a9b7`、型 0 から 17)。

| type | サイズ | 送信元 | メッセージ |
|---|---|---|---|
| 3 | 22 | 退出する参加者 | 退出要求。type、ランダムな u32、定数 ID (8、ビッグエンディアン)、変数 ID (2)、アドレスタイプ 0、IPv4、ポート |
| 4 | 15 | ホスト | 退出応答。type、ランダムな u32、要求からコピーした退出者の定数 ID と変数 ID |
| 9 | 30 | 退出するホスト | ホスト移行の開始。type、ホストの定数 ID と変数 ID、0、ホストの IPv4 とポート、次のホストの定数 ID と変数 ID、`00 01` |
| 10 | 21 | type 9 で指名された局 | 応答。type、自分の定数 ID と変数 ID、その後にホストのもの |

`pokeldn.za` は、この 4 つすべてを組み立てます (`build_leave_request`、`build_leave_response`、`build_migration_ack`)。

### 参加者の退出

`LeaveMeshJob::SendLeaveRequest` (`0x2557e54`) は type 3 をホストに送り、500 ms の期限を設定します。`WaitLeaveResponse` (`0x2558098`) は type 4 を受け取ると完了し、期限ごとに再送します。送信は合計 4 回です (カウンタ +0x9c、`0x25581e0` の `cmp w8, #2; b.gt`)。その後、応答がなくても完了します。type 4 は `0x25474f8` が、15 バイトのときだけ、かつバイト 5 から 14 が局自身の ID (+0x1b8、+0x1c0) のときだけ受け取ります。そのとき、ジョブのバイト +0x99 を設定します。ホストの type 3 ハンドラ `0x254c5ac` (22 または 34 バイト、ホストのみ) は、`0x254c740` で type 4 を書き、局を削除します (`0x2548500`)。

type 4 を送らないホストに参加した市販 Z-A は、type 3 を約 0.5 秒おきに 4 回送り、最初の送信から 2.0 秒後に認証を解除されました (3 回の退出で 1.99、2.02、2.03 秒)。`bin/za_host.py` は各 type 3 に type 4 で応答します。`bin/za_join.py` は、`--hold` か `--hold-after-trade` で退出するとき、自分の type 3 を送り、type 4 を受け取るか 4 回目の送信のあとに先へ進みます。

### ホストの退出

`LeaveMeshWithHostMigrationJob` は次のホストを指名します (`CalcNextHost` `0x255a6fc`)。その後 `SendStartHostMigrationMessage` (`0x255a91c`) が、5000 ms の期限 (`0x255a8c8`) まで、type 9 を 1 秒ごとに送ります。期限を過ぎるとジョブは `0x6c0e` で失敗します。`WaitStartHostMigrationAck` (`0x255abb4`) は、バイト +0xe0 が設定されるとすぐに完了します。type 10 のリーダー `0x2550a64` は、ホストの場合にだけ、かつバイト 11 から 20 がホスト自身の ID のときだけ 21 バイトのメッセージを受け取ります。バイト 1 から 10 が指名された次のホストのものであるとき、`0x255a630` を通じて +0xe0 を設定します。

type 9 に応答がない状態で、プレイヤーが退いた交換をホストしていた市販 Z-A は、type 9 を 1 秒間隔で 5 回送りました。その後、送信元 0 から Net 0x11 のシーケンス 3 を 0.5 秒ごとに約 4 秒、続いて Net 0x40 を約 2 秒送り、最初の type 9 から 10.82 から 10.86 秒後に沈黙しました (4 回の退出)。基板で追跡した 1 回では、そのネットワークは 11.26 秒後に消えました。エミュレートした組では、参加者が 48 ms 後に type 9 へ type 10 で応答し、ホストは Net 0x11 のシーケンス 3 を送り、参加者は `0112000000000003` で応答しました。ホストのネットワークは、type 9 の 0.25 秒後に消えていました。参加者の type 10 と 0x12 は、ヘッダフラグ 2、宛先 0、パケット ID 0、フッターなしで送られました。

type 10 と 0x12 が同時に送られた場合、市販のホストは type 9 の 0.04 秒後に 0x11 を送り、続いて Net 0x40 (`01 40 00 00`、送信元 0) を 0.3 秒ごとに 4.06 秒間送りました。その間、参加者はネットワークに残っていました。2 回目の type 9 は届きませんでした。

Net 0x11 は、退出するホストの接続状態を、`NetDestroyNetworkJob` (`0x2516444`) の移行形式で送ったものです (ジョブ +0xd8 のフラグは、切断する局がホストのとき設定されます。`0x2503c44`)。`0x2501930` はシーケンス (NetProtocol+0x15c) とバイト 29 を進めます。バイト 29 は移行中かどうかのバイトで、NetHostMigration の状態 NetProtocol+0x12d0 が 1 の間は 1 になります (`0x250f084`)。ホストは各クライアントに、そのシーケンスの Net 0x12 を求めます。クライアントはシーケンスを保存し、NetProtocol+0x308 を設定して応答します (`0x2503164`、`0x25035c0`)。ホストはすべての 0x12 を最大 4000 ms 待ち、その後 0x40 を 300 ms ごとに送ります。送る期間は 4000 ms です。待機が期限切れだった場合は 2000 ms です。ホストが 1 人になるまで送り、その後ネットワークを破棄します (`0x251693c`、`0x25169f8`)。

移行形式は、開始時の 0x11 と 3 か所で異なります。シーケンス、バイト 26 (開始時の形式では 1、移行形式では 2。意味は未確認)、バイト 29 です。市販のホストもエミュレートしたホストも、送信元 0、宛先 0、パケット ID 0、ヘッダフラグ `0x3` (確立中、圧縮)、フッターなしで送ります。0x40 も同じ方法で、フラグ 2 で送られます。type 9 は、ホストの変数 ID から、指名された局の変数 ID 宛てに、フッター付きで送られます。

0x40 は次のホストの処理を開始します。ホストでない局上の `0x2503d44` は、NetHostMigration の開始 `0x25099a4` を呼びます。これは次のホストを選び (`0x2505d10`)、`NetHostMigrationJob` (`0x2509da0`) を実行します。LDN では、古いネットワークを離れます (`0x2503b14`)。次のホストはネットワークを開き (`0x2507050`)、残りのクライアントを 6000 ms 待ちます。戻らないクライアントは外されます (`0x250acf0`)。クライアントは 1000 ms 待ってから再接続します。成功すると NetProtocol+0x12d0 がクリアされ、ホストは結果 1 か 2、クライアントは結果 3 を NetProtocol+0x12d4 に格納します。失敗すると、エラー `0xc406` とともに結果 4 を格納します。

リンク交換は引き継ぎの時点で終わります。type 9 のハンドラ `0x2550684` は、退出するホストの局を削除し (`0x2548500`)、その後 `ProcessHostMigrationJob` を開始します。これはセッションの局数 (session+0x110) を減らします。交換シーンの更新 `0x95f398` は、局数が 1 より大きいときだけ交換を実行します (`0x95f45c`)。それ以外では、理由 3 で交換を終了します (`0x95f508`)。相手の退出要求もこの終わり方に至ります。2 局の交換では、退出する側が唯一の相手なので、移行の内容にかかわらず交換は終わり、退出する本体はネットワークを破棄します。

2 台のエミュレートした Z-A 2.0.2 (Ryujinx、loopback 上の LDN) で計測しました。ホストのプレイヤーが退いたとき (B を押し、次に Yes)、両方は交換ボックスに着席していました。もう一方の局は、自分を指名した 30 バイトの type 9 を受け取り、type 10 で応答し、バイト 29 が立ったシーケンス 3 の Net 0x11 を受け取り、0x12 で応答し、type 9 の 0.12 秒後に 0x40 を受け取りました。0x40 の 4 ms 後にネットワークを離れ、0.24 秒後に、ネットワークを作らずに LDN サービスを終了しました。画面には "Your trading partner chose to quit trading. The Link Trade will now end." と表示され、本体 A はそれをリンクプレイのメニューに戻しました。2 回ずつ 2 回の試行が一致しました。

最初の 0x40 で退出した参加者は、type 9 の 0.09 秒後にネットワークから離れていました (交換はなし。プレイヤーが交換ボックスから退いた)。

`bin/za_join.py` は、自分を指名した type 9 に type 10 で応答し、その後の Net 0x11 に 0x12 で応答します。最初の Net 0x40 でネットワークを離れます (本体が 1 秒間沈黙したときも離れます)。

`pokeldn.za.host.HostSession.leave` も同じ退出を行います。type 9 (`build_start_migration`) を、type 10 が来るまで、または 5 秒間、毎秒送ります。移行の 0x11 は、そのシーケンスの 0x12 が来るまで、または 4 秒間、0.5 秒ごとに送ります。その後、0x40 を 0.3 秒ごとに 4 秒間送ります (0x12 が一度も来なかった場合は 2 秒間)。または本体がネットワークを離れるまで送ります。応答がない場合は、最初の type 9 から 11 秒後に終わります。`tests/test_za_host.py` は、これを `bin/za_join.py` に対して実行し、type 9 と両方の Net メッセージを、エミュレートした組のバイト列に固定します。
